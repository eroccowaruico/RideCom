# 常設セキュリティ監査

[開発方針の常設監査](../../../docs/policies/開発方針.md#常設のセキュリティ監査)を着手・再開時に適用する。最初のファイル閲覧・ツール実行より前に、今回扱う情報、保存先・出力先と必要な検証を決める。コミット前に変更を監査する。push 前には送信する履歴・送信先・自動配置の条件と受入済みの記録を照合する。同じ条件で受け入れた変更の判定はそのまま使う。節目の間は変更監査で `clear` を得た小単位をコミットし、その場で push して preview を同期する。調査だけの作業でも、得た情報を共有する前に対象の出口を確認する。

[mainの100コミットごとの区切り](../../../docs/policies/開発方針.md#100コミットごとのフルセキュリティ監査)を含む定期実行では[全領域の監査](references/監査範囲.md#定期実行でプロジェクト全体を調べる)を毎回行う。領域ごとに[前回の証拠を使う範囲と再検査の条件](references/監査範囲.md#前回の証拠を使う範囲と検査をやり直す条件)を適用する。作業再開時にも詳細検査の期限を確認し、期限に達した領域や記録が欠けた領域をその時点で調べる。修正時は[変更資料の要求](references/監査範囲.md#変更時は監査側から変更の説明を求める)を実行する。どちらも[個人情報の非保持](references/監査範囲.md#個人情報を残さないことを確かめる)と[稼働状態](references/監査範囲.md#権限内で稼働中のサーバーを照合する)を確認する。

[採用部品の監査](references/監査範囲.md#採用部品の危険性保守状況使用版を調べる)では、直接・間接依存、同梱バイナリ、CI とランタイムのバージョン、既知の危険性、保守の継続と終了を確認する。

利用者のデータ、通話、認証、配布物を扱う本番コードの指摘を優先する。開発・検証用の処理も実際の権限と影響先をたどり、[影響と費用に見合う対策](references/監査範囲.md#影響と費用に見合う対策を選ぶ)を選ぶ。監査資料には、その判断に使った証拠と対策後に残る危険を許可された分類語で含める。GitHub Actions については[公式 Action を使う場合の判定](references/監査範囲.md#github-公式の-action-を使う場合の判定)を適用し、ワークフローの実際の用途・権限に見合う対応を示す。

監査担当と主担当は、現在の使い方・権限・保護策で安全要件を満たすと確認できた所見を「対応不要」で閉じる。利用経路（自動起動・外部入力を含む）も配布への影響もない機能の同梱は、その一例である。修正・再ビルド・バックログ登録・次回更新の宿題にせず、元の作業を続ける。この所見だけでコミット・push・配布を保留しない。後の監査でも既存の根拠を使い、利用経路や配布条件の変更、採用中のバージョンに該当する脆弱性やストアからの通知など、判断を変える具体的な事実が生じたときだけ再開する。

## 他の変更と並行して監査する

通常の変更は担当者の既存の作業フォルダで監査する。判定担当は受け取った資料を読むだけで、branch・worktree・共有 index を所有しない。共有 index を使う時間が競合するときは[差分を固定して先に監査する手順](references/並列作業での監査.md)を使う。通常の変更監査では、判定待ちの間に主担当が同じ変更の残る検証を進め、結果を必要とするコミット・送信・配布の直前に合否を確認する。

同じ節目の全体監査は一担当が一度だけ実施し、他担当は既存の作業記録にある対象・進行状況・結果を参照する。全体監査は対象コミットを固定して読み取る。未完の間に次の節目が来たら、[節目ごとに監査を終える手順](references/監査範囲.md#監査中に次の節目を迎えたとき)に従う。[提供前の機能](references/監査範囲.md#途中実装の機能を監査するとき)は、有効化前に必要な検査と現在の安全性を区別する。定期の全体監査が進行中なら、他担当もその節目の証拠集め・是正・再検証に取り組み、通常作業は[全体監査の終了条件](references/監査範囲.md#監査中に次の節目を迎えたとき)を満たし、同じ区切りの他の定期作業も完了してから再開する。以後の変更や push では、その操作に関係する保留条件を照合する。要求・仕様・設計・スキル・ルール・バックログなどの文書は、受入済みの文書だけを[文書を main に反映する手順](../../../docs/policies/開発方針.md#ブランチ運用)で随時 origin/main に push する。製品の送信・配布は[100コミットの規定](../../../docs/policies/開発方針.md#100コミットごとのフルセキュリティ監査)に従う。

## ローカルで証拠を作る

- 対象の入口から、アプリ・Worker・CI・監査自身の保存、ログ、エラー、成果物、外部送信まで、変更が届く出口をたどる。実データ、環境変数一覧、Keychain、資格ストア、本番のログやダンプをモデルに読ませることは禁止する。ファイル名・絶対パス・URL・コマンド引数・例外文にも個人情報や秘密が入り得る。開発用のチャット、端末出力、テスト失敗、Git・通知・引継ぎも出力先に含める。
- 許可されたローカル環境で、信頼済みの検査コードと架空の値を使う。正常時・失敗時の出力をローカルの判定器へ直接渡し、固定語の結果だけを取り出す。値の一部・マスク・ハッシュ、差分、原文、ファイル名、自由記述を監査モデルに渡すことは禁止する。通常は既存の main で対象差分を取り出す。検査器やそのテスト自体を変更する場合は、信頼済みコミットから検査器を一時ディレクトリへ取り出し、対象の作業フォルダからその検査器を実行できる。新版の動作は資格なしの隔離環境で先に検証する。
- コミット対象をステージした後、対象 worktree のルートを現在地として `python3 -I -S <信頼済みスキルのディレクトリ>/scripts/check_staged.py` を実行する。[検査器](scripts/check_staged.py)は index の追加・変更後の blob と変更パスをローカルで検査する。終了 0 の `checked` は既知パターンの検出なし、`empty` は差分なし。終了 1 の `review` は候補あり、終了 2 の `unavailable`、異常出力、タイムアウトは検査不能とする。候補は `private-key`、`credential`、`personal-data`、`sensitive-file`、`opaque` の固定語だけ。バイナリ・リンク・2 MiB を超える blob 等は `opaque` とし、秘密鍵等の保管用ファイルは内容を開かずに分類する。
- 標準 index を監査した同じ内容でコミットする。別 index・パス指定コミット・自動ステージで内容が変わる場合は、その対象を検証してから共有する。未ステージの作業、過去のコミット、アーカイブ・ログ等の別の送信物は個別の対象とする。送信する各コミット・成果物を受入済みの証拠に対応付け、記録の欠落や条件の変化がある対象だけ追加で監査する。Git のメッセージ・作者・コミッターも共有される。今回作成したコミットは、送信前に作者とコミッターの名前・メールアドレスをリポジトリで使う Git の設定と照合し、メッセージが公開範囲に合うことを確認する。監査のために別の名義を作らない。検査器は未知の資格形式、人名、住所、位置情報などの完全な検出器ではない。これらは入力と出口の対応、実データの排除、架空の識別値を使う出力試験で確認する。実際に混入していると分かった場合はローカルで修正・再検査する。既知の誤検出や不透明な形式はその対象に限って独立した形式検査・出口試験で解消し、一括除外しない。

## 人の定例作業が必要になる経路を監査する

[資格の定期更新と安全性](../architecture-refinement/SKILL.md#定期更新と安全性の確認)と[ログ記録規約](../../../docs/policies/ログ記録規約.md#記録禁止)を使う。人が秘密を閲覧・転記・配布する工程を探し、初回設定から通常利用、期限越え、失効、障害復旧までを確認する。

| 判定項目 | 必要な証拠 |
|---|---|
| `scope` | 定期は全領域に証拠があり、変更時は実際の変更集合と箇所別の変更前後・影響・証拠が一致する |
| `retention` | 個人情報がサーバー・監査・運用の出口に残らず、製品仕様に基づく端末内の保存・削除を確認できた |
| `live` | 本番と主に自動テストに使う Preview を個別に判定し、環境の分離と各用途に必要な設定を既存の読み取り権限で確認できた |
| `dependencies` | 対象部品の由来・使用中のバージョン・脆弱性・保守状況を確認し、必要な修正とサポートの提供条件を満たす |
| `egress` | 架空の個人情報・資格・鍵材料を使い、成功・失敗時とも許可した出力項目だけが届く。診断や成果物にも生の識別子・音声・招待情報が残らない |
| `access` | 発行・保存・利用の主体を分離し、最小権限と環境分離を維持する。権限外の利用を拒否する |
| `renewal` | 発行元の資格までたどり、初期設定後に人が何もせず期限を越えても利用が継続する。提供元管理または必要時の短命資格発行をローカルの時計・代替 provider で確かめる |
| `revocation` | 期限切れ・失効・取消後に旧資格を拒否する。更新失敗時は安全に停止し、限定的な再試行・復旧後も権限を保つ |
| `operations` | 通常の検査・更新・復旧を無人で繰り返せる。失敗検知と通知に秘密が入らず、再実行で権限・資格・副作用が増えない |

## 最新 Astra へ判定を依頼する

主担当が実行環境のモデル一覧から Astra 系列の最新版を選ぶ。実行環境が同系列の latest エイリアスを提供すればそれを使い、それ以外は利用可能な正式モデル ID のバージョンを比較して最新を明示指定する。監査ごとに新規の独立した担当を起動する。Codex の `spawn_agent` では `fork_turns="none"` と選択した `model` を指定し、ツール使用・ファイル閲覧・再委任をさせず、下表の許可項目と判定規則だけを渡す。作業履歴や利用者の依頼原文を継承させない。Astra の最新版・独立した入力境界・実行結果のいずれかを確認できない場合は `incomplete` とする。

| 引き渡す項目 | 許可する値 |
|---|---|
| 対象 | `project`（確定版の全体） / `staged-change` / `observation`（読み取りや Git 以外の成果物） |
| 対象の説明 | 定期は領域別の網羅状況、変更時は[変更資料](references/監査範囲.md#変更時は監査側から変更の説明を求める)の安全な論理名・変更前後・影響・検証結果 |
| 検査状態 | `checked` / `empty` / `review` / `unavailable` / `not-applicable`（Git の変更を扱わない作業） |
| 検出分類 | 検査器が定義する固定語の集合 |
| 検出候補の別検証 | `pass` / `fail` / `unknown` / `na` |
| 上表の各判定項目 | `pass` / `fail` / `unknown` / `na` |

適用の有無は変更前に対象のデータフローから決める。定期・変更ともに[途中実装の機能の判定](references/監査範囲.md#途中実装の機能を監査するとき)を適用する。動く部分は到達先まで監査し、動作しないことを確かめた部分はその証拠で受け入れる。初回の内部配布では、配布後に初めてできる試験や、その配布で実行しない復旧・資格切替の試験を配布前の残件に数えない。定期は領域ごとに判定し、対象に該当する不合格・未確認を引き継ぐ。本番運用前の過去ログは、[運用実績と読み取り権限による判定](references/監査範囲.md#権限内で稼働中のサーバーを照合する)に従う。変更時は差分と送信に関係する稼働状態の証拠を直近の全体監査から引き継ぎ、前提が変わった項目を確認する。変更に無関係な既存の問題は全体監査の所見として保持する。該当項目で証拠が欠ければ `unknown` とする。`na` は対象への経路がない場合に限る。監査自身の変更では `egress` と `operations` を必ず検証する。

変更資料が足りない場合、Astra は `incomplete` と不足項目を返す。不足項目は `location` / `before-after` / `impact` / `evidence` で示す。主担当は不足分を自動で補って再判定する。それ以外は判定と該当項目の固定語だけを返す。失敗または未解消の検出候補は `hold`、検査不能・必要な証拠の不足は `incomplete`、適用項目と全候補の検証が揃えば `clear` とする。`project` または `staged-change` で `empty` / `not-applicable` の場合も `incomplete`。主担当は指定モデルの実行結果、検査状態、適用項目と根拠を照合する。想定外の応答は転記せず `incomplete`。変更・ステージし直し・成果物の再生成後は実際の差分・証拠・送信物の同一性を確かめ、変わった対象とその影響を再検証・再判定する。

判定記録には実行モデルの正式 ID、対象と成否を残す。主担当が報告や引き継ぎを書くときは、いま予定している操作を基準にする。その操作を止める指摘があれば、何が起きるか、根拠は何か、次に誰が何をすれば進めるかを示す。主担当が実行できる確認や是正は自分で行い、依頼者には本人の操作が必要な場合だけ頼む。現在の操作を止める指摘がなければ、次の操作を示して終える。解消済みの問題、対象外の項目、将来の別操作の受入条件を現在の指摘として列挙したり、バックログへ再登録したりしない。必要な証拠が足りないときは、判定を左右する事実を既存の記録か最小限の追加確認で確かめる。未解消の検出候補も該当箇所だけを調べる。安全要件を満たさないと確認した場合に、権限内で修正・再検証する。判定に依存する操作だけを保留する。定期監査中は上記の節目の手順に従う。人に依頼するのは所有者だけができる初回同意、失効・本番切替などの権限判断、既存手段で解消できない例外に限る。秘密値を人に尋ねたり貼り付けさせたりすることは禁止する。
