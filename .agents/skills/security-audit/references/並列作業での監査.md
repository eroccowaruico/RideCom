# 差分を固定して先に監査する

変更の実装担当が検証と監査資料を準備し、独立した最新 Astra が判定し、統合担当が受理した対象だけをコミットする。[ブランチ運用](../../../../docs/policies/開発方針.md#ブランチ運用)に沿って通常は既存の main を使う。別の実装版を同時に実行する必要があるときだけ同方針の隔離条件を検討する。監査の順番待ち、他担当の未ステージ差分、全体監査の読み取りは隔離を必要としない。

## 共有 index を空けたまま依頼する

標準 index が空いていて短時間で判定できる場合は従来の `--changes` を使える。取り合いになる場合は、統合担当が手元だけに基準コミットと候補 tree の完全な Git ID を保持する。すでに確定した実装コミットを扱う場合は、その親とコミットを直接指定できる。複数コミットの送信では、途中で追加して削除した機密情報も共有されるため、送信される各コミットを検査する。

未コミットの変更では、所有する変更だけを基準コミットに重ねた候補 tree を作る。次は**指定ファイル全体が自分の変更**の場合の例。呼び出し元が所有パスを位置引数に設定し、対象リポジトリのルートで実行する。Git ID とパスはモデル・通知へ送らず、Git の生の診断も出力しない。

```sh
base=$(git rev-parse --verify HEAD 2>/dev/null) || exit 2
candidate=$(
  exec 2>/dev/null
  set -eu
  umask 077
  test "$#" -gt 0
  audit_dir=$(mktemp -d)
  trap 'rm -f -- "$audit_dir/index" "$audit_dir/index.lock"; rmdir -- "$audit_dir"' EXIT
  export GIT_INDEX_FILE="$audit_dir/index"
  git read-tree "$base" &&
  git --literal-pathspecs add -A -- "$@" &&
  git write-tree
) 2>/dev/null || exit 2
python3 -I -S "$audit_checker" --changes "$base" "$candidate"
```

上の `audit_checker` は信頼済みの検査器。基準と候補の ID はローカルで最終照合まで保持し、通常どおり、証拠および変更資料を最新 Astra へ渡す。検査器自体には `GIT_INDEX_FILE` を設定しない。共有 index、作業ファイル、branch の参照は動かない。同じファイルに他担当の編集が混在する場合は所有する hunk だけを一時 index に適用して検証する。分離できない変更は同じ担当と統合順を調整する。

## 受入済みの差分だけを統合する

- 判定待ち、`hold`、`incomplete` では、その変更に依存する受入・共有を保留する。独立した変更はそれぞれの証拠と判定で先に進める。保留したコミット・成果物を含む push・配布は、その対象の受入まで待つ。Astra が利用できない場合も同じ扱いとし、未判定を承認に読み替えない。
- `clear` を受けたら統合担当一人が標準 index を短時間だけ使う。他担当が使用中ならそのステージを保持し、空いた時に受入対象だけをステージする。信頼済み検査器の `--match-index <基準コミット> <候補treeまたはコミット>` で、現在の HEAD から標準 index への**全差分**を候補と照合する。`matches` はパス、追加・削除、モード、変更前後の blob が一致したことだけを示す。終了 1 の `changed` と終了 2 の `unavailable` ではコミットを待ち、対象を補正・再確認する。
- 別担当のコミットで HEAD が進んでも、基準からの履歴が連続し、対象差分、依存先・権限・検証条件、成果物と送信先が同じなら、取得済みの検証結果と Astra 判定を引き継ぐ。共通処理・依存・稼働設定等が変わって証拠の意味が変わる場合は、差分が一致しても影響する検証と Astra 判定をやり直す。未解決のマージ、追加の親や新しい送信対象がある場合はそれぞれの履歴・統合結果も監査する。
- 照合からコミットまで index の書き手を一人に保ち、直前の親と `git write-tree` の結果をローカルで控える。通常コミット後、実際の親・tree と照合し、フックや他作業で変わっていたら送信を止めて実物を再監査する。push・preview 同期は同じコミットの受入済み結果を使い、各送信先・実際に含む履歴に対応する証拠を確認する。
