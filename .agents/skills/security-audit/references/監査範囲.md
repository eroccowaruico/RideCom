# 定期監査と変更監査の受入条件

## 定期実行でプロジェクト全体を調べる

定期実行ごとに共有 main の最新の確定版を読み取り専用の基準とし、前回からの変更がゼロでも全領域を対象にする。信頼済みの検査器を `--project <対象コミットの完全なID>` で実行すると、そのコミットの全追跡ファイルのパス・blob を検査する。引数を省くと現在地の HEAD が対象になる。大きいもの・不透明なもの・資格の保管容器も候補として集約する。Git の履歴、編集途中の作業、実際の配布物やサーバーについてはこの結果を流用できない。

各領域について前提・対象と実際に取れた証拠を照合する。資源の存在を確認できず対象を特定できないときは未確認とする。サブモジュール、バイナリ、バックアップ等の実物をモデルに渡すことは禁止する。公開済みの版・履歴への混入が疑われる場合は公開済みの範囲もローカルで検査する。

| 領域 | 何を確かめるか |
|---|---|
| App、拡張、Watch、パッケージ | OS 権限、認証・認可、入力検証、通信相手・暗号化、端末内保存・同期・バックアップ・削除、音声・招待・通知の露出。成功と拒否の両方を契約試験で確認する |
| Worker、ストレージ、通知・外部連携 | データの取得項目と用途、最小権限、テナント・環境間の分離、失効、期限・消去、障害時の挙動と利用量の上限。待機データ・失敗経路・復元による再出現も含める |
| ビルド・依存関係・CI・配布 | 依存の出所・固定版と利用可能な既知脆弱性情報、ビルド権限・署名、成果物に埋め込まれた設定、診断・ログ・クラッシュ報告・公開資料の出口を確認する。外部の照会に私有コード・利用者情報を渡すことは禁止する |
| 運用と監査自身 | 監視・転送・保存・退避先、資格の自動更新・失効・復旧、監査プロンプト・通知・作業履歴・一時ファイルの非保持。適用した検査と未確認項目を列挙する |

## 変更時は監査側から変更の説明を求める

監査担当の入口で、実装担当に次の表を**要求する**。主担当が Git とテストから自動で埋め、不足は監査担当が項目名を返して**担当へ再要求**する。通常委任で利用者に説明や実値の提示を求めることは禁止する。

| 必須項目 | 渡す情報 |
|---|---|
| 箇所・操作 | `--changes` で実際の index から領域と追加・変更・削除・置換を抽出する。その領域で変更した公開可能な機能・型・操作を、正本で照合済みの論理名で特定する。削除、依存更新、設定だけの変更も含む |
| 変更点・内容 | 各箇所で **変更前 → 変更後** に誰が何を読み、保存・送信・許可・拒否するかを示す。実値を含まない契約の組で表す。例は「サーバーの通話参加 / 表示名 / 永続化あり → 永続化なし / 相手への配信なし」。漠然とした「修正済み」では受理しない |
| 影響・証拠 | 呼出元・受取先、データの種類、権限、保持・削除の変化、正常系・失敗系の検査項目と結果。サーバーへ届く変更は実配置との一致も確認する。まだ配布していない版は稼働版と区別する |

モデルに渡せるのは点検済みの機能・操作の論理名と分類語だけ。動的なパス・識別子、コミット本文、差分・ソース原文、値を加工したものは禁止する。安全な論理名がない場合は「端末アプリ／連絡先の削除」のように製品仕様の語彙を組み合わせる。同一分類の複数変更は箇所別の変更前後を保持する。入力する語を監査対象のファイルから直接コピーすることは禁止する。箇所・変更前後・影響・証拠のいずれかが欠ける間は `incomplete`。ステージ・配布内容が変われば要求を取り直す。

## 個人情報を残さないことを確かめる

サーバー、ログ、分析・テレメトリ、監査記録、CI 成果物には個人情報を残さない。氏名・メール・IP・精密位置・音声・連絡関係・ユーザーと結び付く識別子、URL、リクエスト本文を、通常・例外・リトライ・障害報告を含めて確認する。ハッシュ・短縮・仮名・暗号化だけで非保持を証明できない。機能上必要と正本に明記された端末内の連絡先や最小限のサービス用状態は、主体・目的・識別可能性・保存場所・期限・削除を個別に照合する。仕様との矛盾、不要な保持、削除後の復活が見つかった経路は保留する。

実在する人のデータは取得せず、ローカルの架空の識別値で入力から DB、SQLite WAL、キュー、キャッシュ、ログと相手への出力までを検査する。保存が許された一時状態は期限・アカウント削除・復元後も試す。サーバー側の基準は[表示名を保存しない境界](../../../../docs/spec/server/Worker.md#表示名を保存しない境界)、実行例は[表示名の永続化・配信の試験](../../../../server/test/privacy.test.mjs)。単一試験の合格はその経路の証拠に限る。

## 権限内で稼働中のサーバーを照合する

定期・変更のどちらでも、既存の認証済み管理接続とプロジェクトで特定した対象があれば、実際にメタデータを読み取る。本番と固定 Preview を別々に確認する。確認が必要な構成は[Worker 仕様](../../../../docs/spec/server/Worker.md)と[Cloudflare 設定手順](../../../../docs/development/Cloudflare試用手順.md)が正本。

- Cloudflare では対象 Worker / Preview のデプロイ有無と稼働版、Logpush、Observability の全体・ログ・トレース、永続化、invocation logs、クエリ除去、外部転送先の有無を照合する。親設定と個別設定の組合せを読む。設定が省略された場合は既定値が確認できるまで未確認とする。必要に応じて認証方式、公開範囲、環境間の binding 分離、保持期限・削除設定のメタデータも確認する。
- 監査の権限上限は対象資源の読み取りとする。Cloudflare API の許可一覧に Read と Write が併記されていれば Read で実行できる操作を選ぶ。監査を通すための Edit・Write・Admin、追加トークンの発行、接続の再認可や権限昇格を要求することは禁止する。認証情報は接続先に管理させる。コネクター内で対象を限定し、応答を「有効・無効・存在・不在・一致・不一致・不明」へ射影した結果だけを返す。実ログ、利用者レコード、音声、secret の値、デプロイ作者・アカウント ID を監査に取り込むことは禁止する。確認のための実通話、外部からの能動的な攻撃試験、追加権限付与、配置や設定変更は行わない。
- 本番・Preview ごと、項目ごとに観測済みと未確認を記録する。取得できないときは既存の同等な読み取り API や、同じ環境・配置・設定に有効な読み取り証拠を照合する。なお観測できなければ、環境・項目と「権限不足」「対象不明」「タイムアウト」等の理由だけを記録し `unknown` にする。変更が依存する項目なら `incomplete` として該当する受入を待つ。無関係な変更は自身の証拠で個別に判定し、観測の不足は全体監査に残す。台帳・ローカル設定のみで実態を合格にしない。設定の確認だけで過去ログ・バックアップや永続データの非保持を証明できた扱いにしない。既知の危険な設定は `fail`、証拠不足は `unknown` として、影響する受入・共有を保留する。

## 採用部品の危険性・保守状況・使用版を調べる

全体点検では全依存を棚卸しする。変更監査では新規採用・削除・更新・意図しないダウングレードと、その影響で変わる間接依存を確認する。依存の記述に差がなくても、変更によって処理するデータ、権限、外部入力への露出、配布有無が変わる部品は対象に含める。

| 観点 | 確認する事実と判定 |
|---|---|
| 実際に動く版 | npm の lockfile の全階層、SwiftPM の解決済み版・revision、同梱する WebRTC 等のバイナリの元 revision・checksum、CI Action とランタイム、ビルド／配布ツールを採用元・実行先別に確認する。宣言した範囲から解決版を推測しない。可変タグ・再ビルド不能・配布物の出所不明は個別に扱う |
| 既知の危険性 | 提供元のセキュリティ告知、公開アドバイザリーの影響版・修正版、撤回・バックポート、悪性配布の公表情報をローカルの解決版と照合する。間接依存や開発専用ツールでも署名・CI 資格や成果物へ届く経路を評価する。該当する高・重大の脆弱性、侵害された配布元、完全性の不一致は新規採用・影響する配布を保留する |
| 古い版・サポート | プロジェクト全体と採用中の系列を分け、サポート期限、セキュリティ修正の提供先、必要な最低修正版、実際に実行するランタイムを確認する。新しいメジャー版がある場合も現系列へのバックポートを確認する。必要な修正の欠落、サポート終了かつ代替保守なし、更新で脆弱な版へ戻る場合は保留する |
| 保守頻度と継続性 | 公式の保守方針、アーカイブ・廃止宣言、直近の実質的なリリース、脆弱性報告への対応・修正までの期間、後継への移行案内を合わせて見る。自動コミットの日時だけで保守中と推定しない。更新間隔の長い安定部品も保守窓口・修正経路を確認する。高権限・外部入力を扱う部品で保守の裏付けが取れなければ、採用判断を未確認とし、権限を減らす案や保守中の代替を比較する |

公開情報は取得日・対象範囲を確かめる。公開データを取得し、非公開の名前・リポジトリ URL・lockfile・プロジェクトの依存の組合せは外部へ送信せずに照合する。例えば [OSV のエコシステム別公開データ](https://google.github.io/osv.dev/data/)で候補を抽出し、提供元の告知と照合する。[GitHub Advisory Database](https://docs.github.com/en/rest/security-advisories/global-advisories)は通常の reviewed と malware の対象範囲が異なる。情報源の欠落、取得失敗、解決版不明、判定不能な版形式は `unknown` とする。既知の一致がゼロでも、保守状況・由来・未収録の部品は個別に判定する。

監査結果には、公開可能な部品名、直接／間接・実行先、使用版、影響版またはサポート範囲、保守の根拠、該当する公開告知、判定と次の対応を残す。非公開部品は安全な論理名にする。高リスクなら新規採用を保留し、既存利用は影響する経路を特定して修正版・サポート中の系列・代替・撤去の順に成立性を検討する。更新は変更の受入条件と回帰試験を備えた別の実装単位で行う。
