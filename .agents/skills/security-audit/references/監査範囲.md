# 定期監査と変更監査の受入条件

## 定期実行でプロジェクト全体を調べる

定期実行ごとに共有 main の最新の確定版を読み取り専用の基準とし、前回からの変更がゼロでも全領域を対象にする。信頼済みの検査器を `--project <対象コミットの完全なID>` で実行すると、そのコミットの全追跡ファイルのパス・blob を検査する。引数を省くと現在地の HEAD が対象になる。大きいもの・不透明なもの・資格の保管容器も候補として集約する。Git の履歴、編集途中の作業、実際の配布物やサーバーについてはこの結果を流用できない。

各領域について前提・対象と実際に取れた証拠を照合する。資源の存在を確認できず対象を特定できないときは未確認とする。サブモジュール、バイナリ、バックアップ等の実物をモデルに渡すことは禁止する。公開済みの成果物や変更履歴への混入が疑われる場合は公開済みの範囲もローカルで検査する。

| 領域 | 何を確かめるか |
|---|---|
| App、拡張、Watch、パッケージ | OS 権限、認証・認可、入力検証、通信相手・暗号化、端末内保存・同期・バックアップ・削除、音声・招待・通知の露出。成功と拒否の両方を契約試験で確認する |
| Worker、ストレージ、通知・外部連携 | データの取得項目と用途、最小権限、テナント・環境間の分離、失効、期限・消去、障害時の挙動と利用量の上限。待機データ・失敗経路・復元による再出現も含める |
| ビルド・依存関係・CI・配布 | 依存の出所・固定したバージョンと利用可能な既知の脆弱性に関する情報、ビルド権限・署名、成果物に埋め込まれた設定、診断・ログ・クラッシュ報告・公開資料の出口を確認する。外部の照会に私有コード・利用者情報を渡すことは禁止する |
| 運用と監査自身 | 監視・転送・保存・退避先、資格の自動更新・失効・復旧、監査プロンプト・通知・作業履歴・一時ファイルの非保持。適用した検査と未確認項目を列挙する |

節目の是正をコミットしたら、その結果を含むコミットを同じ節目の監査対象として記録する。影響する項目を再検証し、有効な証拠を引き継いで全体判定を更新する。全体の合格と同じ区切りの他の定期作業の完了がそろえば、通常の push に戻る。

push で自動的に起きる配置や CI の権限・情報の送信先は、送信前に確認する。安全に送信できる根拠がそろったうえで、送信後に初めて観測できる GitHub 上の実行結果や TestFlight 配布後の実機動作は、担当と確認時点を既存の検証記録に残す。送信自体の安全性に必要な証拠が欠ける場合は引き続き未完とする。

### 途中実装の機能を監査するとき

定期監査・変更監査ともに、現在の配布物と稼働環境で、誰がどの入口から機能を起動できるかを調べる。実装途中でも、意図した操作で動く部分は、その入力・権限・データ・副作用を通常どおり監査する。開発者だけが明示的に起動できる場合は、起動条件と隔離の実効性を確かめ、その環境から届く範囲を検査する。開発用でも本番の資格やデータを使えれば、そこまで対象に含める。意図しない入口から動く場合は、配布対象から外すか、既存の機能設定で既定を無効にし、処理を実行する側で拒否する。画面を隠しても、API、旧クライアント、起動時処理、キューや再試行から呼べることがある。該当する入口ごとに、設定が欠けた場合も含め、権限の行使・読み書き・外部送信の前に止まることを確かめる。過去に稼働した経路では、既存データや実行待ちの処理も照合する。

配布物に含まれない、または実運用の呼出元がなく副作用も生じないと確認できた項目は、その根拠を記録して今回の検査を閉じる。無効化した場合は、対象環境で無効である証拠と拒否試験の結果を残す。動く範囲の安全性と残りが意図せず動かないことを確認できれば、今回の変更は `clear` にできる。未実装部分の完成や成功時の機能試験は、既存のバックログに有効化前の受入条件として残す。次回は有効化、呼出元の追加、設定・配布構成の変化を契機に見直す。現に届く経路、既存データへの影響、無効化を確認できない項目は元の所見を維持する。

### 監査中に次の節目を迎えたとき

進行中の監査は対象コミットと完了条件を固定して続ける。途中で迎えた節目は既存の作業記録に着手待ちとして残す。発見した関連課題はバックログに登録し、この監査の判定を妨げるものだけを是正する。次の監査に着手したら、今回の対象で全領域を照合し、前の対象から増えた変更、変更の組合せ、稼働環境・依存先・公開告知の変化、証拠の期限切れを調べる。有効な試験結果を引き継ぎ、影響した項目と未解決の所見に検査を絞る。履歴や証拠が途切れた場合は根拠を失った範囲を再検査する。

未確認の項目について、今ある証拠と権限では判定を進められない場合は、再開条件を一度記録し、他の監査項目を進める。固定した対象の必須項目がそろったら、独立した最新の Astra に全体判定を依頼する。`clear` を得た節目と対象を記録してその回を閉じる。次の節目ではこの記録から続ける。

### 前回の証拠を使う範囲と、検査をやり直す条件

定期監査では上表の全領域を毎回確認し、今回の対象コミットで `--project` を実行する。主担当は既存の監査記録から領域ごとに、最後に詳しく検査した日、対象コミット、実行環境、検査結果と未解消の所見を取り出す。前回以降に受け入れた変更は、変更監査で得た証拠を各領域に対応付ける。定期監査では、個別に安全と判定した変更の組合せ、稼働環境の変化、新しい脆弱性情報、個別監査で扱っていない経路を評価する。例えば、入力元を増やす変更とログ項目を増やす変更が別々に合格していても、組み合わせると利用者の入力がログに残る経路を再検査する。

| 今回の状況 | 確認すること |
|---|---|
| 変更が小さく、前回の検査結果が今も使える | コードの差分に加え、配布中のアプリのバージョン・依存部品・OSやランタイム・権限・稼働設定を照合する。前回以降の脆弱性告知とサポート期限を確認し、別の領域の変更で入力元や送信先が変わっていないかをたどる。前提が保たれている項目は前回の試験結果を使い、重い試験の再実行を省く |
| 前提が変わった、または新たな告知が出た | 例えば Worker の依存部品に新しい告知が出たら、Worker 自体の差分がゼロでも、稼働中の Worker のバージョンと外部入力がその条件に該当するかを調べる。共通の認証や CI の権限変更は利用側まで追い、影響を受ける項目の試験をやり直す。影響範囲を特定できないときは検査対象を広げる |
| 前回の検査が古い、または根拠をたどれない | 初回、対象の記録欠落、履歴の不連続、検査期限の到来時は、その領域を現行構成から洗い直す。稼働中のアプリやサーバーのバージョン・権限・データの保存先を確認し、正常系と拒否・削除・復旧など該当する契約試験を再実行する。全領域に当てはまる場合は全体を詳しく検査する |

検査期限は、領域を最後に詳しく検査した日から原則90日とする。サポート終了や資格の期限など、それより早く前提が変わる項目は早い方を使う。長期休止後は作業再開時に期限を確認し、期限に達した領域は次の100コミットを待たずに詳しく検査する。軽い照合だけで最後の詳細検査日を更新することは禁止する。

各回の記録には、領域ごとの「再利用した証拠と今回確認した前提」「やり直した検査と理由」「残る所見と次の検査期限」を短く残す。未確認・保留は解消する証拠を得るまで引き継ぐ。必要な稼働状態や告知を確認できなければ当該項目を未確認とし、必要な証拠がそろうまで全体の合格を保留する。今回の全領域の結果をまとめ、最新 Astra が改めて全体を判定する。

## 変更時は監査側から変更の説明を求める

直近の全体監査で確認した領域ごとの構成・権限・情報の送信先と検査結果を、変更監査の出発点にする。今回の差分から呼出元・依存先・出力先をたどり、その範囲で前提が今も有効かを照合する。有効な証拠は引き継ぎ、変更した経路、影響先、必要な証拠が不足した項目を検査する。例えば端末内で完結する文言修正なら、その文言がログや通信に流れず、送信時の自動配置にも影響しないことを確認すれば、全体監査で済ませたサーバーの保持・削除試験は繰り返さずに済む。

監査担当の入口で、実装担当に次の表を**要求する**。主担当が Git とテストから自動で埋め、不足は監査担当が項目名を返して**担当へ再要求**する。通常委任で利用者に説明や実値の提示を求めることは禁止する。

| 必須項目 | 渡す情報 |
|---|---|
| 箇所・操作 | `--changes` で実際の index から領域と追加・変更・削除・置換を抽出する。その領域で変更した公開可能な機能・型・操作を、基準となる資料で照合済みの論理名で特定する。削除、依存更新、設定だけの変更も含む |
| 変更点・内容 | 各箇所で **変更前 → 変更後** に誰が何を読み、保存・送信・許可・拒否するかを示す。実値を含まない契約の組で表す。例は「サーバーの通話参加 / 表示名 / 永続化あり → 永続化なし / 相手への配信なし」。漠然とした「修正済み」では受理しない |
| 影響・証拠 | 呼出元・受取先、データの種類、権限、保持・削除の変化、正常系・失敗系の検査項目と結果。サーバーへ届く変更は実配置との一致も確認する。未配布の成果物は稼働中のバージョンと区別する |

モデルに渡せるのは点検済みの機能・操作の論理名と分類語だけ。動的なパス・識別子、コミット本文、差分・ソース原文、値を加工したものは禁止する。安全な論理名がない場合は「端末アプリ／連絡先の削除」のように製品仕様の語彙を組み合わせる。同一分類の複数変更は箇所別の変更前後を保持する。入力する語を監査対象のファイルから直接コピーすることは禁止する。箇所・変更前後・影響・証拠のいずれかが欠ける間は `incomplete`。ステージ・配布内容が変われば要求を取り直す。

## 個人情報を残さないことを確かめる

サーバー、ログ、分析・テレメトリ、監査記録、CI 成果物には個人情報を残さない。氏名・メール・IP・精密位置・音声・連絡関係・ユーザーと結び付く識別子、URL、リクエスト本文を、通常・例外・リトライ・障害報告を含めて確認する。ハッシュ・短縮・仮名・暗号化だけで非保持を証明できない。機能上必要と基準となる資料に明記された端末内の連絡先や最小限のサービス用状態は、主体・目的・識別可能性・保存場所・期限・削除を個別に照合する。仕様との矛盾、不要な保持、削除後の復活が見つかった経路は保留する。

実在する人のデータは取得せず、ローカルの架空の識別値で入力から DB、SQLite WAL、キュー、キャッシュ、ログと相手への出力までを検査する。保存が許された一時状態は期限・アカウント削除・復元後も試す。サーバー側の基準は[表示名を保存しない境界](../../../../docs/spec/server/Worker.md#表示名を保存しない境界)、実行例は[表示名の永続化・配信の試験](../../../../server/test/privacy.test.mjs)。単一試験の合格はその経路の証拠に限る。

## 権限内で稼働中のサーバーを照合する

本番と固定 Preview は用途・資格・データ・受入結果を分ける。Preview は主に自動テストに使う。架空の入力、テスト用の資格と保存先、外部への送信先、CI の配備権限を確認し、本番との分離を確かめる。同じソースでも本番の実効設定は本番側で確かめる。

例えば、隔離された Preview に通知用の鍵がなければ、その鍵が必要な通知テストを未確認として残す。無効な機能の成功試験を本番や全体監査の合格条件に加えず、Preview に本番の鍵を求めない。Preview が実際に扱う入力・保持・送信の安全性は全体監査でも確認する。本番のデータ、資格、通知先、配置先を共有する場合や、分離を確認できない場合は、本番に届き得る範囲まで評価する。

定期監査では、既存の認証済み管理接続で対象を特定できれば、本番と固定 Preview のメタデータを個別に読み取る。変更監査では、差分と push に伴う配置が影響する項目を照合する。同じ環境・配置で有効な読み取り結果を使い、前提の変化や証拠の不足がある項目を読み直す。確認が必要な構成は[Worker 仕様](../../../../docs/spec/server/Worker.md)と[Cloudflare 設定手順](../../../../docs/development/Cloudflare試用手順.md)に従う。

- Cloudflare では対象 Worker / Preview のデプロイの有無と稼働中のバージョンを照合する。Logpush、Observability の全体・ログ・トレースの各設定、永続化を調べる。invocation logs、クエリ除去、外部転送先の有無も照合する。親設定と個別設定の組合せを読む。設定が省略された場合は既定値が確認できるまで未確認とする。必要に応じて認証方式、公開範囲、環境間の binding 分離、保持期限・削除設定のメタデータも確認する。
- 監査の権限上限は対象資源の読み取りとする。Cloudflare API の許可一覧に Read と Write が併記されていれば Read で実行できる操作を選ぶ。監査を通すための Edit・Write・Admin、追加トークンの発行、接続の再認可や権限昇格を要求することは禁止する。認証情報は接続先に管理させる。コネクター内で対象を限定し、応答を「有効・無効・存在・不在・一致・不一致・不明」へ射影した結果だけを返す。実ログ、利用者レコード、音声、secret の値、デプロイ作者・アカウント ID を監査に取り込むことは禁止する。確認のための実通話、外部からの能動的な攻撃試験、追加権限付与、配置や設定変更は行わない。
- 本番・Preview ごと、項目ごとに観測済みと未確認を記録する。取得できないときは既存の同等な読み取り API や、同じ環境・配置・設定に有効な読み取り証拠を照合する。なお観測できなければ、環境・項目と「権限不足」「対象不明」「タイムアウト」等の理由だけを記録し `unknown` にする。変更が依存する項目なら `incomplete` として該当する受入を待つ。無関係な変更は自身の証拠で個別に判定し、観測の不足は全体監査に残す。台帳・ローカル設定のみで実態を合格にしない。設定の確認だけで過去ログ・バックアップや永続データの非保持を証明できた扱いにしない。既知の危険な設定は `fail`、証拠不足は `unknown` として、影響する受入・共有を保留する。

## 影響と費用に見合う対策を選ぶ

主担当は `dependencies` と `devDependencies` の区分を手掛かりに、どこで動くか、誰が入力を渡せるか、どの権限とデータを使うかを確認する。依存部品のほか、設定・監査ツール・手作業にも同じ基準を使う。問題ごとに起きる条件、起きたときの被害、現在の対策でどこまで防げるかを確かめ、利用者や配布物に大きな被害が及ぶ経路から扱う。

| 実際の使われ方 | 判断の例 |
|---|---|
| 本番の通話・認証・保存 | 外部入力が問題の処理に届き、個人情報や通話に影響するなら、該当機能の公開を保留する。修正版の適用や入力の制限後に、同じ条件で安全に処理できることを確かめる |
| 開発用でも署名・配布に関わる | ビルド時に実行する部品が署名資格を読める、または配布物を書き換えられるなら、本番への影響を評価する。重大な被害を具体的に想定できる場合は、安全を確認するまで該当する署名・配布を待つ |
| 隔離した開発・文書検査 | 架空の入力だけを扱う検査で、実際の資格情報や配布物からの隔離を確認できたら、その用途を継続できる。残る改善は通常の依存更新と合わせる。外部入力・権限・成果物の利用先が変われば再判定する |

対策を選ぶときは、現行の保護で運用する案も含め、更新、権限の縮小、機能の停止など実行できる案を比べる。必要な安全性を満たす案の中から、実装・検証の時間、配布を待つ時間、サービス利用料、今後の保守負担が小さいものを選ぶ。独自実装の更新漏れ、手作業で秘密を扱う機会の増加、障害時の復旧の遅れも、対策によって新たに生じる危険として評価する。個人情報の非保持や最小権限などの必須条件は費用を理由に免除しない。

主担当は採用した対策を権限内で実施し、問題が起きる条件で効果を再検証する。継続利用を選ぶ場合は、その判断を支える証拠、残る危険、見直す条件を既存の作業記録に短く残す。費用や工数の違いで判断が変わる場合だけ見積もりの幅を示し、実施後の負担と照合する。同じ証拠が今も有効なら再利用し、新たな課金や人手を伴う検査は、その結果で判断が変わる範囲に絞る。

## 採用部品の危険性・保守状況・使用したバージョンを調べる

外部ライブラリとフレームワークは公式配布物または無改変の上流ソースから採用する。更新時は取得元・コミット・ビルド引数・パッチの有無・成果物の照合値を確認する。公式 SDK に未使用 API が含まれる場合は、既存の証拠から呼出元・権限・自動起動・外部入力と配布への影響を判断する。例えば WebRTC のカメラ API がシンボルやヘッダーにあるだけで、使う経路も現行の配布への影響もなければ対応不要とする。同じ所見から除去方法や別ターゲットの調査を始めない。実際に起動する機能や、同梱だけで採用中のバージョンに影響する脆弱性・配布条件は、その影響範囲で監査する。

全体点検では全依存を棚卸しする。変更監査では新規採用・削除・更新・意図しないダウングレードと、その影響で変わる間接依存を確認する。依存の記述に差がなくても、変更によって処理するデータ、権限、外部入力への露出、配布有無が変わる部品は対象に含める。

| 観点 | 確認する事実と判定 |
|---|---|
| 実行環境にある依存部品のバージョン | 採用元・実行先ごとに依存を確認する。npm の lockfile は全階層を調べ、SwiftPM は依存関係の解決で選んだパッケージのバージョンと revision を調べる。同梱する WebRTC などのバイナリは元の revision と checksum を確認する。CI Action、ランタイム、ビルド・配布ツールも対象とする。宣言した範囲から依存関係の解決後に選ばれたバージョンを推測しない。可変タグ・再ビルド不能・配布物の出所不明は個別に扱う |
| 既知の危険性 | 提供元のセキュリティ告知、公開アドバイザリーの影響を受けるバージョンと修正済みのバージョン、撤回・バックポート、悪性配布の公表情報をローカルの依存関係の解決後に選ばれたバージョンと照合する。間接依存や開発専用ツールでも署名・CI 資格や成果物へ届く経路を評価する。該当する高・重大の脆弱性、侵害された配布元、完全性の不一致は新規採用・影響する配布を保留する |
| 使用中の依存部品とサポート期限 | プロジェクト全体と採用中の系列を分け、サポート期限、セキュリティ修正の提供先、必要な最低修正版、実際に実行するランタイムを確認する。依存部品の新しいメジャーバージョンがある場合も現系列へのバックポートを確認する。必要な修正の欠落、サポート終了かつ代替保守なし、更新で脆弱性のあるバージョンに戻る場合は保留する |
| 保守頻度と継続性 | 公式の保守方針、アーカイブ・廃止宣言、直近の実質的なリリース、脆弱性報告への対応・修正までの期間、後継への移行案内を合わせて見る。自動コミットの日時だけで保守中と推定しない。更新間隔の長い安定部品も保守窓口・修正経路を確認する。高権限・外部入力を扱う部品で保守の裏付けが取れなければ、採用判断を未確認とし、権限を減らす案や保守中の代替を比較する |

公開情報は取得日・対象範囲を確かめる。公開データを取得し、非公開の名前・リポジトリ URL・lockfile・プロジェクトの依存の組合せは外部へ送信せずに照合する。例えば [OSV のエコシステム別公開データ](https://google.github.io/osv.dev/data/)で候補を抽出し、提供元の告知と照合する。[GitHub Advisory Database](https://docs.github.com/en/rest/security-advisories/global-advisories)は通常の reviewed と malware の対象範囲が異なる。情報源の欠落、取得失敗、依存関係の解決後に選ばれたバージョン不明、解釈できないバージョン表記は `unknown` とする。既知の一致がゼロでも、保守状況・由来・未収録の部品は個別に判定する。

監査結果には、公開可能な部品名、直接／間接・実行先、使用したバージョン、影響を受けるバージョンまたはサポート対象の範囲、保守の根拠、該当する公開告知、判定と次の対応を残す。非公開部品は安全な論理名にする。高リスクなら新規採用を保留し、既存利用は影響する経路を特定して修正版・サポート中の系列・代替・撤去の順に成立性を検討する。更新は変更の受入条件と回帰試験を備えた別の実装単位で行う。

### GitHub 公式の Action を使う場合の判定

`actions/checkout` と `actions/setup-node` は GitHub が保守する公式 Action を使う。使用するリリースと固定した完全なコミット ID の対応を確認し、提供元の修正版・サポート期限を追う。setup-node 自体のバージョンと、これで選ぶ Node.js のバージョンは別々に確認する。

指摘を書く前に、誰がどのイベントからどのコードを実行できるか、ジョブの実効権限と参照できる秘密、実行結果の送り先を確認する。検査結果だけが残るのか、キャッシュ・署名・公開する成果物に結果が引き継がれるのかで、影響する範囲が変わる。

- **通常の利用。** 例えば、手動の文書検査では信頼するコードを読み取り権限で実行し、checkout 後に資格を残さない。署名や配布への経路もなく、利用条件に該当する問題がなければ、固定した公式 Action の利用を続ける。間接依存のバージョンが告知に一致したら、その機能を呼ぶか、問題を起こす入力を誰が渡せるかを調べる。一致だけを根拠に、専用スクリプトへの置換、手動検査の停止、製品の配布保留を求めない。未確認の条件と上流の修正状況はその Action の所見として残す。
- **対応が必要な利用。** 例えば、外部のプルリクエストのコードを、書き込み権限や配布用の秘密を持つジョブで実行する場合は、そのジョブの実行を保留する。確認できた条件、影響先、保留を解除できる変更を示す。公式の修正版への更新、入力・起動条件の制限、不要な権限や資格の削除を先に検討する。本番や配布物にも影響する経路があれば、そこまで保留する。
- **判断材料が足りない場合。** 署名・配布など重大な影響が具体的に疑われ、その可否を決める証拠が欠ける場合は、該当する操作を未確認として保留する。独自実装を検討するのは、公式 Action の更新や設定変更でも具体的な危険を解消できず、代替手段の検証・継続保守を含めても危険を減らせる場合に限る。
