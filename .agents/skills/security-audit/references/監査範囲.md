# 定期監査と変更監査の受入条件

## 定期実行でプロジェクト全体を調べる

定期実行ごとに共有 main の最新の確定版を読み取り専用の基準とし、前回からの変更がゼロでも全領域を対象にする。信頼済みの検査器を `--project` で実行すると、現在地の HEAD に追跡された全ファイルのパス・blob を検査する。大きいもの・不透明なもの・資格の保管容器も候補として集約する。Git の履歴、編集途中の作業、実際の配布物やサーバーについてはこの結果を流用できない。

各領域について前提・対象と実際に取れた証拠を照合する。資源の存在を確認できず対象を特定できないときは未確認とする。サブモジュール、バイナリ、バックアップ等の実物をモデルに渡すことは禁止する。公開済みの版・履歴への混入が疑われる場合は公開済みの範囲もローカルで検査する。

| 領域 | 何を確かめるか |
|---|---|
| App、拡張、Watch、パッケージ | OS 権限、認証・認可、入力検証、通信相手・暗号化、端末内保存・同期・バックアップ・削除、音声・招待・通知の露出。成功と拒否の両方を契約試験で確認する |
| Worker、ストレージ、通知・外部連携 | データの取得項目と用途、最小権限、テナント・環境間の分離、失効、期限・消去、障害時の挙動と利用量の上限。待機データ・失敗経路・復元による再出現も含める |
| ビルド・依存関係・CI・配布 | 依存の出所・固定版と利用可能な既知脆弱性情報、ビルド権限・署名、成果物に埋め込まれた設定、診断・ログ・クラッシュ報告・公開資料の出口を確認する。外部の照会に私有コード・利用者情報を渡すことは禁止する |
| 運用と監査自身 | 監視・転送・保存・退避先、資格の自動更新・失効・復旧、監査プロンプト・通知・作業履歴・一時ファイルの非保持。適用した検査と未確認項目を列挙する |

## 変更時は監査側から変更の説明を求める

監査担当の入口で、実装担当に次の表を**要求する**。主担当が Git とテストから自動で埋め、不足は監査担当が項目名を返して**担当へ再要求**する。通常委任で利用者に説明や実値の提示を求めることは禁止する。

| 必須項目 | 渡す情報 |
|---|---|
| 箇所・操作 | `--changes` で実際の index から領域と追加・変更・削除・置換を抽出する。その領域で変更した公開可能な機能・型・操作を、正本で照合済みの論理名で特定する。削除、依存更新、設定だけの変更も含む |
| 変更点・内容 | 各箇所で **変更前 → 変更後** に誰が何を読み、保存・送信・許可・拒否するかを示す。実値を含まない契約の組で表す。例は「サーバーの通話参加 / 表示名 / 永続化あり → 永続化なし / 相手への配信なし」。漠然とした「修正済み」では受理しない |
| 影響・証拠 | 呼出元・受取先、データの種類、権限、保持・削除の変化、正常系・失敗系の検査項目と結果。サーバーへ届く変更は実配置との一致も確認する。まだ配布していない版は稼働版と区別する |

モデルに渡せるのは点検済みの機能・操作の論理名と分類語だけ。動的なパス・識別子、コミット本文、差分・ソース原文、値を加工したものは禁止する。安全な論理名がない場合は「端末アプリ／連絡先の削除」のように製品仕様の語彙を組み合わせる。同一分類の複数変更は箇所別の変更前後を保持する。入力する語を監査対象のファイルから直接コピーすることは禁止する。箇所・変更前後・影響・証拠のいずれかが欠ける間は `incomplete`。ステージ・配布内容が変われば要求を取り直す。

## 個人情報を残さないことを確かめる

サーバー、ログ、分析・テレメトリ、監査記録、CI 成果物には個人情報を残さない。氏名・メール・IP・精密位置・音声・連絡関係・ユーザーと結び付く識別子、URL、リクエスト本文を、通常・例外・リトライ・障害報告を含めて確認する。ハッシュ・短縮・仮名・暗号化だけで非保持を証明できない。機能上必要と正本に明記された端末内の連絡先や最小限のサービス用状態は、主体・目的・識別可能性・保存場所・期限・削除を個別に照合する。仕様との矛盾、不要な保持、削除後の復活が見つかった経路は保留する。

実在する人のデータは取得せず、ローカルの架空の識別値で入力から DB、SQLite WAL、キュー、キャッシュ、ログと相手への出力までを検査する。保存が許された一時状態は期限・アカウント削除・復元後も試す。サーバー側の基準は[表示名を保存しない境界](../../../../docs/spec/server/Worker.md#表示名を保存しない境界)、実行例は[表示名の永続化・配信の試験](../../../../server/test/privacy.test.mjs)。単一試験の合格はその経路の証拠に限る。

## 権限内で稼働中のサーバーを照合する

定期・変更のどちらでも、既存の認証済み管理接続とプロジェクトで特定した対象があれば、実際にメタデータを読み取る。本番と固定 Preview を別々に確認する。確認が必要な構成は[Worker 仕様](../../../../docs/spec/server/Worker.md)と[Cloudflare 設定手順](../../../../docs/development/Cloudflare試用手順.md)が正本。

- Cloudflare では対象 Worker / Preview のデプロイ有無と稼働版、Logpush、Observability の全体・ログ・トレース、永続化、invocation logs、クエリ除去、外部転送先の有無を照合する。親設定と個別設定の組合せを読む。設定が省略された場合は既定値が確認できるまで未確認とする。必要に応じて認証方式、公開範囲、環境間の binding 分離、保持期限・削除設定のメタデータも確認する。
- 認証情報は接続先に管理させる。コネクター内で対象を限定し、応答を「有効・無効・存在・不在・一致・不一致・不明」へ射影した結果だけを返す。実ログ、利用者レコード、音声、secret の値、デプロイ作者・アカウント ID を監査に取り込むことは禁止する。確認のための実通話、外部からの能動的な攻撃試験、追加権限付与、配置や設定変更は行わない。
- 本番・Preview ごと、項目ごとに観測済みと未確認を記録する。権限不足・対象不明・タイムアウトなら `unknown`。台帳・ローカル設定のみで実態を合格にしない。設定の確認だけで過去ログ・バックアップや永続データの非保持を証明できた扱いにしない。既知の危険な設定は `fail`、証拠不足は `unknown` として、影響する受入・共有を保留する。
