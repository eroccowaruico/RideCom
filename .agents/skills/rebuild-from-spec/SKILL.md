# 文書から同じ振る舞いを再現する

[用途別のストーリーマップ](../../../docs/requirements/README.md#用途別のストーリーマップ)で今回の立場と背景を選び、活動の順、体験、UIまたは画面外の結果、適用するSLO、実現する仕様の所有元へたどる。条件分岐は[条件と結果の記述](../../../docs/policies/文書作成規約.md#条件と結果の記述)に従い、比較式・論理式とデシジョンテーブルで示す。仕様から逆に、影響する利用者・画面・内部契約と影響の閉じる境界を説明できるか確かめる。

着手時、要求や設計の判断が変わった時、検証後の区切りに適用する。対象は今回の利用用途と変更が届く契約。[文書作成規約の再実装に必要な記録](../../../docs/policies/文書作成規約.md#再実装に必要な記録)を基準に、既存の正本で足りる記述はその見出しを参照する。

- **用途から始める。** [要求とユースケースの対応](../../../docs/requirements/README.md#要求とユースケースの対応)から対象をたどり、[core-story-first](../core-story-first/SKILL.md)で今回成立させる最小の体験を選ぶ。着手前に「誰が、どんな条件で何をすると、誰に何が起きれば合格か」を書けるか確かめる。新しい指示・訂正は理由とともに該当する要求または設計案へ反映する。
- **変更前後の契約を照合する。** [architecture-refinement](../architecture-refinement/SKILL.md#常時適用)で、操作の入口から状態の所有者、呼出先、利用者が観測する結果までをたどる。要求・仕様・実装・テストが食い違えば、要求者の決定と観測事実を照合する。仕様の記載漏れは補い、実装の不具合は期待を保って修正・再検証する。意図が未決なら論点と選択による違いを課題に残す。
- **実装を見ずに受入例を導く。** 区切りに、対象の正本だけを入力として、通常時と結果の変わる境界について、前提・入力・期待出力・合否の測り方を具体化する。既存テストやソースを失っても同じ判定を作れるかを問う。値や手順をコードや会話でしか特定できなければ、根拠を確かめて正本を補い、もう一度文書から導く。
- **観測を次の判断へ返す。** 導いた期待と実際のテスト・必要なE2Eの結果を照合する。差が出たら原因に応じて仕様・実装・試験の該当箇所を直し、同じ条件で判定し直す。通った範囲は条件・結果・証跡へつなぎ、残る差や環境待ちは次の一手と再開条件を残す。次のAIは[文書入口](../../../docs/README.md)から当該用途の正本と最新の検証をたどり、その一手からループを再開する。

**初めて担当する人が、手順だけで操作できるようにする。** 利用・設定・運用の操作、前提、確認結果、復旧方法が変わったら、同じ変更で対応するマニュアルや手順を必ず起こすか更新する。外部サービスを使う機能では、App・サーバーの実装とリポジトリで管理できる設定を先に整え、管理者のアカウント・署名・鍵が必要な操作を[外部設定の手順](../../../docs/policies/開発方針.md#applecloudflare等の外部設定を常に手順化する)へまとめる。新規手順は機能と一緒に起こし、既存手順に影響する変更・撤去・移行・鍵更新は必ず同じ変更で改訂する。引継ぎ前に、初めて操作する人が対象環境と権限を確認し、値の取得元から登録先へ進み、期待結果または中止・復旧の判断まで、順にたどれるかを差分と照合する。実装済み・管理者の設定待ち・実環境での確認待ちを記録する。[Apple・Cloudflareの実施例](../../../docs/development/Cloudflare試用手順.md#利用者が行うapplecloudflareの設定と受入順)

**成功と失敗を後から照合できるようにする。** 安定した条件・効く理由・変更を閉じる境界・崩れた時に戻す処理は所有元の仕様へ記す。観測と仮説は区別する。音声の不具合・修復・試案の採否を扱った区切りでは、担当に[比較記録の手順](../../../docs/development/音声E2Eテスト.md#音声トラブルの比較記録)に沿って該当の検証履歴へ記入させ、完了・引継ぎ前に根拠と突き合わせて監査する。直接担当する場合も同じ記録を作る。比較や因果判断に足りない箇所は具体的に指摘し、既存の証跡で補えるものはその場で補う。不明なものは何を照合すれば判別できるかを担当に示し、追記後に再確認する。追加検証の要否と規模は変更の影響と手元の証拠から判断する。

採用済みの改善も未実装機能も[共通バックログ](../../../docs/policies/文書作成規約.md#改善と未実装を同じバックログで扱う)で扱い、担当が変わっても該当する課題の見出しを引き継ぐ。残る差は[分類の判断と完了時の移動](../../../docs/policies/文書作成規約.md#分類の判断と完了時の移動)で未実装・未確認・要改善に振り分ける。次の担当は[バックログの管理方法](../../../docs/backlog/README.md#管理のしかた)から今回有効な順序と再開条件を取得する。

再実装を実証するときは元のコードとテストを保存し、独立した作業領域で対象の最小契約を文書だけから実装・試験する。既存実装との比較は期待結果を定めた後に行う。文書から受入例を導けた範囲、実際に再実装して通った範囲、製品環境で確認した範囲をそれぞれ明示する。
