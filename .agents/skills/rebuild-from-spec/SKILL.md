# 文書だけで再実装できるか監査する

- **着手・再開時**に、[core-story-first](../core-story-first/SKILL.md)で選んだ用途と、[architecture-refinement](../architecture-refinement/SKILL.md#常時適用)で特定した契約を対象にする。[再実装に必要な記録](../../../docs/policies/文書作成規約.md#再実装に必要な記録)から対象の要求・仕様・検証記録と未解決の指摘をたどり、対象の振る舞いと合否を文書だけで判断できるか確かめる。
- **「Cloudflare側で設定を変えたから読んで」と依頼された時**は、[稼働中の設定をリポジトリに取り込む手順](#cloudflareで変更した設定を取り込む)を適用する。
- **復旧元や設計判断を変更する時、作業を再開・引継ぎする時**は、[複数の資産を同時に失ったときの復旧](../../../docs/policies/文書作成規約.md#複数の資産を同時に失ったときの復旧)を適用する。担当がテスト・環境・文書・プロダクトから一緒に失うものを選び、残る復旧元だけで最初の操作、復旧の順番、合否と採用理由を説明できるか試す。復旧元も同時に失う場合や理由が推測にとどまる場合は、該当する手順と根拠を直し、同じ喪失条件で再監査する。
- **課題の登録・変更・完了時**は、[要求間のリンク](../../../docs/policies/文書作成規約.md#関連する要求と影響を受ける利用者を結ぶ)を受け手の立場からもたどる。「一方の条件を変えると、誰のどの受入結果を見直すか」を文書だけで答えられるか確かめる。答えられなければ、抜けた立場と操作を示し、該当する要求・課題を直して同じ例で再監査する。
- **試験を作る・変える・結果を引き継ぐ時**は、[試験データと判定の再現条件](../../../docs/policies/開発方針.md#試験データを作り直し同じ条件で判定する)を適用する。担当に共有mainの生成元と手順を示してもらい、前回の保存状態がなくても開始から片付けまで説明できるか確かめる。前回との差が製品と試験のどちらにあるか判断できなければ、不足する条件を指摘し、同じ事例で再監査する。

- **以前と似た失敗が出た時**は、前のコードを動かす前に、同じ条件で成功した記録と今回の実測を照合する。該当する検証履歴に、操作ごとの値・合否・実行名と、まだ区別できない原因を残す。音声では[比較記録の手順](../../../docs/development/音声E2Eテスト.md#音声トラブルの比較記録)を使う。次の担当が過去の状態を再現せずに、保存済みの事実と新たに測る必要がある点を区別できるか確かめる。
- **指示・判断・実装・観測が変わった時**は、担当がその仕様や検証結果を管理する文書を更新する。何を変えたか、その理由と結果を書く。更新や要約の後は、主担当が[次の読者が同じ意味に読めるか](../../../docs/policies/文書作成規約.md#次の読者が同じ意味に読めるか確かめる)を元の指示と照合する。スキル自身の指示文も対象にする。[日本語の技術文書を検査する手順](../../../docs/policies/文書作成規約.md#日本語の技術文書を検査する)を実行する。修正した文は原文と照らし、条件・例外・確かさが変わっていないことを確かめる。単独作業では自分で書いて読み直す。
- **検証後・各作業の区切り・引継ぎ前**に、主担当が[再実装の監査](../../../docs/policies/文書作成規約.md#再実装の監査)を実施する。文書だけで振る舞いと合否を導き、差分・証跡と照合する。
- **実装や品質試験の結果を引き継ぐ時**は、[実装状況と品質目標の判定](../../../docs/policies/文書作成規約.md#実装状況と品質目標の合否を引き継ぐ)を適用する。[試験の分類](../../../docs/policies/開発方針.md#テストの分類と影響範囲による実行)を参照し、基準の試験と、限界を調べる任意の試験を別々に選べるか確認する。次の担当者が記録だけを読んで、何が動くか、未実装・未測定・目標未達はどれか、失敗したら何を確かめるかを説明できるか試す。音声では[過去の結果と比べる手順](../../../docs/development/音声E2Eテスト.md#音声が壊れたか品質が変わったかを判断する)で、今回の合否と以前からの変化を別々に確かめる。
- **品質に関する判断を更新する時**は、[品質に関する判断を更新する手順](../../../docs/policies/文書作成規約.md#品質に関する判断を更新する)を使う。担当が既存の記録を更新し、主担当が成功例と失敗例をたどる。別の担当に、なぜその実装を残すか、どこで壊れたかを説明してもらう。今の結果と目標の差を試した範囲に限って述べ、次に試す変更と採否の条件を決められるかも確かめる。
- **必要な記録が欠けている、または言葉を略したために判断が分かれると気づいた時点で**、その記述をもとに進める開発を保留する。主担当は[監査の停止・再開条件](../../../docs/policies/文書作成規約.md#監査の停止再開条件)に従い、担当に不足のある文書を直させ、同じ例で再監査する。合格後に開発を再開する。

試験環境や試験データの準備を変えたら、[試験を作り直す条件](../../../docs/policies/開発方針.md#試験データを作り直し同じ条件で判定する)を適用する。既存状態を失っても、別の担当が記録された入力と手順で同じ受入操作を再現できるか確かめる。破棄してよいと決まっているデータはその判断を引き継ぎ、試験後に新しく用意できた範囲と既存状態で確認した範囲を記録する。

## Cloudflareで変更した設定を取り込む

1. 依頼された環境と項目を特定し、既存の読み取り権限で現在の設定を取得する。本番、固定Preview、Previews Baseのどこで変えたかを区別し、継承値と個別の設定を照合する。設定値を取り込む前に、対象を上書きするデプロイや自動配置を起動するpushは保留する。[環境別の設定と配置手順](../../../docs/development/Cloudflare試用手順.md#管理画面とプレビューの設定)
2. 読み取った値と、同じ環境のリポジトリ定義、手元で編集中の差分を比べる。依頼された非機密の変更だけを、その設定を管理する箇所に反映する。Workerの設定は `server/wrangler.toml` の該当環境へ、管理画面で管理する設定は既存の復旧手順へ記す。秘密値は取得・転記せず、再登録に必要な参照名と手順を残す。取得不能・非表示は「未確認」とし、削除や既定値への変更と区別する。
3. 配置せずに設定を検証し、取り込んだ項目から同じ構成を再現できるか確かめる。手元の変更と競合する場合や、費用・セキュリティなどの既存要件と両立しない場合は、双方の意図と影響を示し、その項目の採否を依頼者に確認する。結果は環境別に、取り込んだ項目と未確認の項目を報告する。
4. 読み取りと取り込みの依頼は、Cloudflareへの書き込みを含まない。後に配置する時は、対象と上書きされ得る設定を直前に読み直し、取り込み後の変更も保つ。配置後は同じ環境で実効値を確認する。文書やスキルだけのpushでも自動配置が動く場合は、この手順を適用する。

## 記録を分け、読んで判断できるか確かめる

1. **読者が次に決めることを先に書く。** 利用者が知りたい操作、実装担当が守る動作、調査担当が比較する結果を挙げる。誰がどの場面で何を判断するか説明できない見出しは、目的と対象が伝わる名前に直す。
2. **変更する理由が違う情報を分ける。** 仕様には期待する動作・理由・変更してよい境界を置く。検証履歴には条件・操作ごとの実測と当時の合否を残す。今の判断は検証状況の入口に、これから変えることは既存の課題に置く。同じ基準は一か所を参照し、試験当時の値は履歴に保つ。独立して合否や修正箇所が変わる操作は別の行にする。同じ理由と条件で一緒に変わる行はまとめる。
3. **初めて読む人の順番で検算する。** 見出しから用途を選び、成功例と失敗例の入力・操作・観測点をたどる。次の担当が「どの条件で何が起きたか」を一文で言え、値と判定式から同じ結論を出せるか確かめる。推定には根拠と反証できる条件を添える。「改善した」だけなら、何がどれだけ変わり、他の指標はどうなったかまで戻って読む。
4. **指摘には直し方と再監査の問いを添える。** 「対象の見出し／決められないこと／読み方が分かれる具体例／直す文書と必要な根拠／再監査で答える問い」を短く示す。たとえば2つの操作をまとめて「音声が劣化」と書いた場合は、どちらの操作がどの目標を外れたのかを問う。担当が同じ履歴の該当行を分け、主担当が同じ例を読み直す。根拠がなければ、分かっている範囲と次に必要な観測を書かせる。
5. **試験は答えたい問いで分ける。** 操作の結果が正しいか、決めた品質を満たすか、どの条件で崩れるかを別々に判断できるようにする。安価な試験で判定式を確かめ、実際の経路が必要な問いだけを結合試験や実機試験に残す。入力の準備と測定方法が共通なら再利用する。
6. **記録の不足と試験を増やす仕事を区別する。** 既存の値で判断できれば、その値を使う。代表例と境界・失敗例から仕組みが働くと確かめた後は、[試験範囲の引継ぎ](../../../docs/policies/開発方針.md#試験する組み合わせをバックログへ引き継ぐ)を使う。未確認の組み合わせと再開条件を読者がたどれれば、網羅のためだけにこの作業を続ける必要はない。既知の不具合は該当する課題で追う。
