# 品質・コスト・コンテキストを保つ実行管理

Codexの主担当は原則としてSolとする。利用者が特に難しいと判断してAstraを選んだ依頼では、そのAstraが主担当を務める。ここでのSol・Astra・Terraは、いずれも実行時にその環境で選べる各系列の最新版を指す。

[AGENTS.md](../../../AGENTS.md)が指定する規約と対象仕様を適用する。選択・範囲・完了は[core-story-first](../core-story-first/SKILL.md)、回帰・GUI実行・配置は[開発方針](../../../docs/policies/開発方針.md)の該当節に従う。既読資料は今回必要な節だけ確認し、モデルや並行数によらず品質条件を維持する。

## 最初の判断

主担当は着手時に、実行環境が示す自分のモデル名とバージョンを確認する。モデルを切り替えたときも確認し、そのモデルで直接進める費用を分担の比較に含める。モデル名や単価が分からない場合は推測を避け、作業量や引き継ぎの手間など、分かる条件から判断する。

主担当がAstraなら、複数の仕様が矛盾したときの判断や改善設計に自分の時間と費用を充てる。方針が決まった実装はSolに、定型の確認はTerraに任せる場合と比べる。主担当がSolなら、通常の実装と検証を自分で進め、専門的な判断が必要な論点に絞ってAstraを使う。どちらの場合も、委任先の利用料に加え、主担当が依頼を説明し、結果を検証する費用も見込む。

主担当が直接完了するのを基本とする。サブエージェントの利用は任意とし、利用者の指示と権限の範囲で主担当が必要性を判断する。専門的な検討、別の読み手による確認、短時間での処理に利点があり、依頼と結果の確認にかかる手間を含めても有益なときに呼ぶ。

前提や例外を1つ取り違えるだけで結論が変わる仕事は、主担当が元の指示と資料を読み、判断と検証を自分で行う。例えば、2つの仕様が矛盾する場合は、それぞれの適用条件を主担当が照合する。必要に応じて、根拠を個別に確認できる調査や独立したレビューを他の担当に頼む。

作業量が多いときは、同じ品質基準で、主担当が単独で進める場合と独立した作業を分担する場合の費用と所要時間を比べる。サブエージェント間の引き継ぎでは、説明や返答待ちに加え、要約で前提や例外が抜けた場合の再調査・修正・再検証まで見込む。見積もりに自信がないときは、連絡と手戻りの負担を大きめに見る。分担に利点があれば、下表から仕事に合うモデルを選ぶ。途中で解釈の食い違いや度重なる確認が生じたら、主担当の判断で、依存する作業を同じ担当にまとめるか、自分で引き取る。

| 作業 | Codexでの役割分担 |
|---|---|
| 通常の調査・実装・検証・進行管理 | 主担当が依頼の解釈から実装・検証まで進める。委任した部分も主担当が結果を確認し、採否を決める |
| 大規模な構成の監査、セキュリティ上の問題の分析、論理的不整合の検知 | 主担当がAstraなら、問題の根拠を調べて改善を設計する。他のモデルが主担当なら、必要に応じてこの検討をAstraに依頼する。主担当が設計の採否を決め、実装・検証を進める |
| 言葉の意味・ニュアンスの確認やレビュー | 必要に応じてTerraとSolの視点を組み合わせる。例えばTerraが文面から読み取った意味を返し、Solが原文や利用場面と照合する。最終的な表現は主担当が決める |
| 速さを優先する簡易タスク | 対象が明確な抽出や既知の手順の実行は、委任で早く終わる場合にTerraを候補とする。すぐに済む作業は主担当がその場で終える |

常設のセキュリティ監査の判定は[専用スキル](../security-audit/SKILL.md)に従い、主担当のモデルにかかわらず、独立した最新版のAstraに許可された変更資料と定型結果だけを渡す。モデルが利用できない場合の扱いも同スキルに従う。

モデルごとの思考設定・コンテキスト上限・ツール利用可否は互換とは限らない。ラベルをモデル間の能力・費用の共通尺度として扱わず、実環境で選択可能な設定だけを使う。失敗時は入力・再現・環境・権限・検証を先に切り分け、能力不足の根拠がある場合に担当や設定を見直す。モデル選択の運用例は[モデル選択と再利用](references/モデル選択と再利用.md)を参照する。

## 通常運用の境界

作業人数・独立性・実際の利用可能枠に合わせて[実作業を中心にした構成](references/実行管理と指示更新.md#実作業を中心にした構成)を選ぶ。委任先が一人なら主担当から直接依頼する。管理役は継続的な調整に利点がある場合に置く。主担当は要求解釈、範囲・費用・品質の変更、未解決対立、最終受入を判断する。

再利用は[文脈の継続条件](references/モデル選択と再利用.md#渡したコンテキストと再利用性で分担を決める)を満たす担当へ行う。担当の管理役は同時に一人とし、[所有と連絡](references/実行管理と指示更新.md#担当契約と連絡)・[再委任と総枠](references/実行管理と指示更新.md#再委任と総枠)を守る。起動失敗や一人への集中は[分担の復旧と定期見直し](references/実行管理と指示更新.md#分担の復旧と定期見直し)で改善する。

**[開発方針の小さく動く単位](../../../docs/policies/開発方針.md#小さく動く単位で検証・コミットする)で検証し、仕様を更新してコミットし、未コミットの滞留を抑える。** [担当ごとの運用](references/品質・レビュー・引継ぎ.md#動作を保つ小さな完了単位)を適用する。[ブランチ運用](../../../docs/policies/開発方針.md#ブランチ運用)に従い、並行作業も既存のmainで進める。編集・検証の干渉をそこで解消できず隔離した場合は、[mainへのmerge許可・保留と管理](references/実行管理と指示更新.md#管理役単位のworktreeとmainへの段階的merge)は親/主担当が必ず担う。共有資源・編集所有を分け、コミットは指定した単一実行者が他作業の差分・indexを保護して行う。

主担当は実行環境に従い、ツールから親への通知、承認処理、利用者への報告を引き受ける。主担当は必要な実行と最終品質の責任を保持する。

ゴール遂行中はスキルを参照専用とし、現行ルール内で分担を改善する。恒久的な問題は[改善記録と後続の改訂](references/実行管理と指示更新.md#作業中の改善記録と後続のスキル改訂)へ残し、明示されたスキル保守の工程で反映する。
