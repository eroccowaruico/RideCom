# 製品要求

## 目的と背景

RideComは、スキー、スノーボード、ツーリング、ドライブなどで、仲間と気軽に通話を楽しむためのiOS/macOSアプリである。音楽を聴きながらグループで同時通話を続ける。カメラを使う撮影やビデオ通話は提供しない。iPhone（iOS）での利用を最優先とする。iPadOSは同じアプリを利用する端末として画面・操作の違いを考慮し、macOSにもデスクトップとして使える体験を求める。近距離とInternetが混在する移動中でも、接続経路がある限り手動の繋ぎ直しを減らす。少人数の試用から公開へ進められること、従量課金による費用増大を抑えることを重視する。

本書は統一して満たす目的・価値・品質を定める。達成状況や作業一覧は持たせない。製品の要求と、[開発方針](../policies/開発方針.md)・[文書作成規約](../policies/文書作成規約.md)の作り方の要求を区別する。

## 利用者に提供すること

| 要求 | 背景・期待する結果 |
|---|---|
| ログインして自分の通話情報を使う | すべての通話でAppleログインを必須とし、メール・本名を要求しない。ログイン済み端末は圏外でも近距離通話を使い、別アカウントのユーザー一覧・グループを混在させない |
| 同一ユーザーのWebRTC接続を1端末にする | 複数端末へ同じユーザーでログインしていても、WebRTC接続はユーザー単位で原則1端末に限る。端末やグループを変えて通常の同時接続を増やせないようにする。障害回避・復旧のための一時的な2端末接続には検討余地を残すが、常用の複数接続は提供しない |
| 本人の名前と自分の呼び名を分ける | 本人が好きな表示名を設定して相手へ伝えられる。サインイン後に名前を一度も設定していなければ、最初に名前の入力を求め、未設定の既定名のまま仲間へ伝えない。受け取り側は本人の名前を確認・保持したまま自分用の呼び名に変更でき、本人の名前へ戻せる。呼び名の編集は他端末へ配信せず、グループ内だけの関係をグループ外の操作権限へ変えない |
| グループで同時通話できる | 招待して同じグループへ参加し、認証済みの相手と会話できる |
| 閲覧と通話先変更を区別する | 別グループを見るだけで通話を切らず、接続先の変更は明示的に行える |
| 選んですぐ接続し、通知から応答できる | 接続していない間に相手・グループを選ぶとそのまま接続を始め、別の画面で改めて接続操作を求めない。接続中に別の接続先へ入るときは今の接続を切断してから選び、切替の確認は置かない（2026-11-11の利用者指示）。グループ通話中はその画面から人を追加できる。呼び出しの通知から接続でき、接続を選んだ後に重ねて操作を求めない。通知には「接続」と、通知を閉じるだけの「無視」を置く（断ったことを相手へ送る拒否は置かない） |
| <a id="選んだ相手だけを呼び出す"></a>呼び出しは親切な知らせとして1回送り、会話の始め方は利用者に任せる | 2026-11-10の利用者指示による（2026-11-02の「電話のように受ける」を改める）。RideComはインカムやWeb会議と同じ道具で、目の前でもインターネットでも「よーいドン」で同じ時間に入ったり、メッセージなど他の連絡手段も合わせて使ったりして会話を始める。電話のように相手を鳴らして呼び出すものではなく、通知は親切で添えるだけである（Zoomで最初の人が入ったと知らせるのに近い）。1対1は、相手を選んで接続を始めるたびに相手へ必ず1回だけ呼び出しの通知を送る。グループは通話の開始を誰にも通知せず、会話中に自分と直接つながっている（個人で登録している）人だけを選んで呼び出せる。どちらも呼びっぱなしとし、届かない・応答がない場合でも再送・応答待ちの表示・追いかけをしない。断ったことを相手へ送る拒否は置かない。通知では誰からかが分かるようにする。通知の許可は初回の起動でOSの許可だけを求め、通知の設定はOSの設定に任せる。通知が届くのは個人で登録している相手からだけとする。グループへの招待の通知は、個人で登録している相手から、その人が選んだ相手にだけ届ける。グループの一部の人だけが会話しているときに、他のメンバーへ一斉に知らせたり自動で参加させたりしない。会話中に届いた呼び出し・招待で今の会話を鳴らして遮ったり、切り替えたりしない。CallKitは使わず標準の通知だけで実現する [受け手が通話中の場合の通知](#受け手の通話を遮らずに知らせる) |
| 圏外でも近距離で会話できる | Wi-Fiアクセスポイント・ルーター・テザリングがなく、セルラーも圏外の場所で、近くの参加者同士はInternetやサーバーを必要とせず通話を開始・継続できる。Appleログインを完了し、同じグループの招待・鍵を共有済みで、端末の近距離の無線機能と必要なOS権限が有効なことを前提とする。アクセスポイント不在と端末のWi-Fi機能OFFを混同しない |
| セルラーがあっても近距離を優先する | 相手へ届く近距離経路を音声の伝送の第一候補とし、全員へ近距離で送れるときは不要なInternet音声コピーを送らない。近距離経路の未準備・不達や遠隔参加者のために必要なInternet経路は使い、混在通話を切断しない。近距離接続をInternet資格取得やサーバー応答待ちに従属させない |
| 混在した経路でも通話を維持する | 一部離脱、近距離のみ・Internetのみの参加者が混在しても、届く経路がある参加者同士の会話を維持する |
| 経路によらず操作の意味を統一する | ミュート、個別音量、全体音量、音声効果を同じ意味で操作できる |
| 音声の鮮度を優先する | 遅れた音声をため込まず、会話に必要な低遅延を優先する。過負荷時の欠落は許容する |
| 音声機器の変化を理解できる | Bluetoothや有線機器が消失した際、停止理由と復帰方法が分かり、接続状態と音声の状態を区別できる |
| インカムを電話型の通話にしない | 仲間との連続会話を、CallKitによる電話と同じシステム通話へ変更しない。通知には通常のAPNsとUserNotificationsを使う。CallKit・VoIP Push・AppleのPushToTalk frameworkを使わない（2026-11-17の利用者確認）。CarPlayではWidgetのボタンから既存のインカムを操作する体験を求め、専用の電話型通話アプリを目的にしない |
| WatchをiPhone通話の音声・操作端末にする | 通話処理はiPhoneが持ち、Watchはそのマイク・スピーカーと操作端末として接続する。複数人の音声合成、エフェクト、VADなどの音声処理もiPhoneへ集約し、Watchでミキサーを動かさない。Watchはマイク入力・iPhoneで処理済みの音声再生・操作を担い、通信に必要な最小限の入出力・符号化・復号以外の処理を持たせない。この経路だけを提供し、Watch単体では動作させない。Watch独自の通話処理・グループ参加・直接のRTC接続は作らない。Watchから操作するときはWatchのマイクとスピーカーで会話し、Widgetに近い簡単な操作だけを提供する。ログイン、購入、ユーザーやグループの管理、詳細設定もiPhone側に置く |
| Widget・Watchから指定相手への通話を開始する | Widgetは画面へ配置・設定する際に登録済みユーザーまたはグループを指定し、その通話先専用のリモコンとして開始・終了・ミュートを操作する。WatchはiPhoneに保存済みのユーザー・グループから通話先を選んで開始できる。いずれも毎回iPhoneで先に通話を開始する条件を設けない。ユーザー追加・グループ作成・メンバー追加などの管理は行わない。Watch音声もWatch自身の操作から開始できることを採用条件とし、満たせなければ音声機能は提供せずiPhone通話のリモコンに限定する。その場合も通話先の選択と開始操作は必須とする |
| Watchで押している間だけ話せる | Watchのマイクは操作部を押している間だけミュートを解除し、それ以外は常にミュートする。2026-11-01の利用者指示により、通常のマイク切替とモード選択はWatchに置かない。指を離したときや押下を取り消したときは、ミュートに戻す。操作の中断時と切断時もミュートに戻す。接続や操作が復帰しただけでは送話を再開しない。通話と相手の音声の受信は押下ごとに開始・終了せず維持する。AppleのPush to Talk機能への統合を求めるものではない |
| 音楽と会話を両立する | 音楽との共存、発話に応じた送信抑制、自己録音による入力・出力確認を提供する |
| 自分が送信する音を確認できる | 録音チェックでは、通話と同じ設定・エフェクトを適用した送信音声を5秒分録音し、選択した出力先で先頭から末尾まで再生して本人が確認できるようにする。Watch使用時も音声処理と録音はiPhoneが担う |
| 不要な再接続を求めない | Wi-Fiの不安定化、別ネットワークへの移動、セルラーの不安定化が複数端末で重なっても、到達可能な経路で通話を維持し、経路回復後は自動復旧する。利用者が終了した通話や自動切断タイマーで終了した通話は再開せず、介入が必要な場合は理由を示す |
| 通話の接続状態を音で知る | 通話中に相手との接続が不安定になったときや、意図せず完全に切れたときは、画面を見なくても状態の違いが分かるよう、それぞれ短く穏やかな効果音を数秒おきに鳴らす。相手に声が届いていない可能性を伝え、返事がない理由を通信の状態から判断できるようにする。グループ通話では、接続が完全に切れた相手の名前を自動の音声案内で知らせる。無言やミュートの間は接続の異常として案内しない。状態が回復したときや、自分で通話を終了したときは繰り返しを止める |
| 接続の放置を自動切断する | 電池消費、長時間接続による不具合、通信運営費用を抑えるため、通常利用とWatch利用で個別に自動切断時間を選べる。選択肢は1・3・5・10・15・30分、1・2・3・6・8・12・24時間とし、無制限は設けない。初期値は通常3時間、Watch5分。通信断と自動復旧で期限を延長せず、期限到達時は終了して自動再接続しない。利用権の24時間の再開猶予とは独立して扱う |

Watchはリモコンのみを既定とし、Watchのマイク・スピーカーによる通話は初期起動・設定欠落・リセット時にOFFとする。Watchから開始しただけで音声の所有先をWatchへ移さず、音声通話は開発者向け設定の明示オプションとして扱う。Watchの公開は必須としない。配布見送り中はStandard設定のWatch専用項目・セクション・案内・遷移入口を非表示にする。MacにはWatch専用設定・案内・入口を表示しない。iPhoneのAdvancedでは、Watch専用の操作部品を画面に残す。操作部品は無効（disabled）にする。「無効」などの文字だけで代用しない。設定値の変更・保存も、Watch機能の有効化もできないようにする。項目名と値を表示し、配布見送りの文言は画面に追加しない。開発専用の設定は一般のAdvanced設定と区別して扱う。非表示の対応は再公開可否の判断や実機確認を待たない。2026-11-21の利用者指示により、リモコン機能の提供には次の根拠を必要とする。対象は音声通話を除く、公開予定のリモコン全機能である。iPhoneがロック中でもバックグラウンドでも、前面に戻す操作やロック解除を求めずに各操作が完了すること。その結果も確認できること。この両方を実証する。Watch自身のロック・手首の暗転・背景化は別条件として扱い、操作可能な状態と制約を明示する。根拠が揃わなければ当面Watchをリリースしなくてよく、本体アプリの公開をWatch完成待ちにしない。リモコン既定・Watch音声OFFだけを公開可の根拠にしない。

Watchの音声操作はWatch内でマイクのON/OFFを完結させ、押下ごとのiPhoneミュート連動を要求しない。iPhoneの既存VAD・通話処理を継続し、少量の通信削減より操作応答と処理の軽さを優先する。iPhone側のWatch向け媒体接続・必要な音声回路は交換可能な音声デバイスのプラグインとして責務を分離し、AppにWatch固有の符号化・媒体処理を残し続けない。Watch専用ミキサーや別VADを設ける要求ではない。

Watchから開始した通話は、明示終了または設定した自動切断期限まで入出力ともWatchに固定する。Watch Appを開いたまま手首を下げ画面が暗くなっても音声と受話を維持し、送話は暗転で閉じる。押下解除で閉じるのはWatchローカルの送話gateだけとし、相手の受話経路を止めない。省電力で音声通信を休止する場合も、Watchのnative再生経路は無音を出せる状態で維持し、次の受話に再初期化を要求しない。

入力バーで分かるのはマイク入力の有無や大きさであり、エフェクトを適用して相手へ送る音の内容・聞こえ方までは判断できない。送信者自身が何を送っているか確認して設定を調整できるように、録音チェックでは実際の送信処理を通した音を聞けることを必須とする。

## 共通の品質方針

| 要求 | 判断の基準 |
|---|---|
| アプリケーション名 | 正式名称をRideComに統一する。アプリ・Widget・Watchの表示、通知、権限説明、招待・共有文、翻訳、製品を説明する現行文書に同じ名称を使う |
| 対応端末 | iPhoneとiPadを同じiOS版で支援し、macOSも支援する。macOSをiOSの単純移植で済ませない。WidgetはiPhone・iPad・Mac、WatchはiPhoneとの連携を対象とし、通話状態を各OSで利用可能なシステム表示へつなぐ |
| 対応OSバージョン | 初回リリースはiOS/iPadOS/macOS/watchOS 27.0以降を支援する。以降は可能な限り最新メジャーと直前メジャーの最大2世代を支援し、下位OSだけの互換経路を長期維持しない |
| 安全なグループ通話 | 認証済みの同一グループだけで通話し、全経路の音声を保護する。秘密・音声内容をログへ出さない |
| 簡単な仕様と復旧 | 利用条件や上限の目的は費用の膨張と明らかな悪用を防ぐこととし、必要最低限にする。制限には余裕を持たせ、厳密な強制より実装・保守・運用・処理の総コストを優先し、複雑な管理を増やさない。切替や既存通話の終了を含む選択肢から、理解しやすく復旧しやすい方法を選ぶ。デッドロックや復旧操作へ進めない袋小路を避ける |
| 分かりやすい状態 | 接続、音声停止、失敗、未取得の計測値を区別し、成功していない状態を正常に見せない |
| アクセシビリティ | 色だけに依存せず、VoiceOver、文字サイズ、各端末の入力方法・画面サイズで利用できる |
| 走行中の操作 | バイクの運転中やスキー・スノーボードの滑走中は手で端末を操作できない前提とする。接続は出発前に済ませ、走行中は操作なしで会話が続くことを主な体験にする。操作は止まっている間に、携帯を取り出さずに（Apple Watch・ウィジェット・Siri等）、グローブをしたまま行える。端末を解除せずに触れられる表示から、取り消せない操作で接続を失わない |
| 操作直後のバックグラウンド移行 | スキー・バイク等では、操作した直後に画面をロックしたり別のアプリを使ったりすることを通常の利用とする。利用者が最後に行った操作で期待する処理は、前面表示を維持しなくてもバックグラウンドで最後まで進み、その結果と状態を保持する。前面を開いたまま待つ操作も、処理の続行・通話成立・切断からの復旧のためにアプリをフォアグラウンドへ戻す操作も、利用者にはできない前提とし、求めない。開始・相手待ち・相手参加後の通話成立、通話継続・切断後の復旧、ミュート・終了、招待・返信・削除等の受け付けた操作に適用する。相手の応答や接続経路を待つ場合も、その待ち状態と続行を維持し、アプリが背景へ移ったことだけで操作を失敗・取消・消失させない |
| 双方バックグラウンドでの成立と再接続 | 双方がバックグラウンド・画面ロック中でも、開始済みの待受から通話成立へ進む。通話途中に意図しない切断が起きた場合も、利用可能な接続経路が戻れば双方を前面へ戻すことなく再接続し、通話を再開する。どちらか一方の前面復帰・再操作を成立や回復の条件にしない |
| 通話開始時のマイク許可 | OSで通話に使うマイクの使用を拒否した場合は、開始操作に対してマイクの許可が必要なことをダイアログで伝える。許可されるまで通話の開始・参加に進めず、閉じると開始前の画面に戻る。聞くだけで参加する人も、マイクの使用を許可してから、アプリ内のミュートを使う |
| 無発話・マイクOFF・再生なしでの接続維持 | 聞く専門の人、長時間話さず時々だけ話す人を通常の利用者として扱う。自分または双方のマイクがOFF・ミュート、VADが無発話、受信音声がなく再生されない、または受信を消音している場合も、それだけを理由に接続・開始済み待受・自動復旧を停止しない。音声packetや可聴出力の有無を、通話を続ける意思や接続維持の条件と同一視しない。次の受話・許可された送話が手動の繋ぎ直しなしに再開できること。明示終了・設定した自動切断期限・正当な利用枠や認可の終了条件は別に扱う |
| Standardの直感的で誤操作しにくい操作 | バイク・スキーでの利用を前提に、説明文を読んで理解させるより、明確なコントロールとSF Symbols等の意味が通じるピクトグラムで操作と現在の状態が伝わる画面にする。グローブでも狙った操作を確実に行える大きさ・間隔・操作距離を確保し、隣の操作や破壊的操作を誤って実行しにくくする。見た目から期待する操作と実際の結果を一致させ、操作後の状態変化も明確に伝える。必要な短いラベル・状態・アクセシビリティの名前は残し、記号だけで意味不明にしない |
| 音声品質 | 低遅延と会話の安定性を重視し、音響品質は実機で評価する |
| 音声の組合せによる連続性検証 | 音声の途切れは、対応するcodec・サンプリング周波数・bitrate・音声処理の組合せで検証する。音声処理は送信側の声の分離、受信側の相手別・全体の分離、VAD等の有効状態と切替を含む。既定設定や各設定単独の成功だけで全体を合格にしない。実際に適用された値とfallbackを記録し、非対応の組合せは区別する。短い相槌・語頭・語尾、長い無発話後の再開、処理のON／OFF切替を含め、相手側の実出力と連続性を確認する |

### 双方背景と無音状態を組み合わせた受入

2026-11-18の追加指示。以下は実装方式ではなく必須の製品動作とする。個人・グループ、Internet・Localの該当経路を対象に、両端の実行状態と接続、実音声の結果を照合する。

| 双方背景での通話中に経路断・一時切断が起き、その後経路が復帰する | 双方背景のまま再接続し、通話・受話と許可された送話を再開する。片側だけの回復や制御接続だけで成功にしない |
| 片方が聞き専でマイクOFF、もう片方が長く話さず時々だけ話す | 無発話中も接続を維持し、次の発話を相手へ届ける。無音の長さで勝手に終了しない |

| 明示終了または既定の終了条件に到達 | 終了の意思・期限を尊重し、接続維持・自動復旧を理由に通話を復活させない |

OSの実行制約は検証して成立する方式を選ぶ設計上の条件として扱い、前面表示を維持する手順やアプリを前面へ戻す手順を要求達成の代わりにしない。実現できない条件が判明した場合は制約と影響を明示して未達の要求として記録し、必要な方式変更・対策を追跡する。コード・単体試験と実機の背景実行の証拠を区別し、実機で期待結果まで確認した範囲を受け入れる。既存の背景継続・開始待ち・復旧の[課題](../backlog/README.md)は本要求と照合する。本追記は要求の明文化であり、実装・実機受入の完了を示さない。

## iCloud自動保存と端末変更時の復元

iCloudへの自動バックアップ（保存）は確定要求とする。端末変更・再インストール・本人の端末追加時に、招待・登録を最初からやり直さず、保存した相手・グループとの関係と自分の設定を復元できることを目的とする。単に名前や一覧が戻るだけでなく、有効な関係について通話へ進める状態まで復元する。

本人のiCloudにあるRideComのアプリデータ用領域を利用する。旧端末を紛失して署名用の秘密鍵を使えない場合も、新端末で本人確認を済ませて新しい鍵を登録し、有効な通話相手・グループとの関係と通話に必要な資格を復元する。通常の端末変更だけを理由に相手への再招待・返信のやり直しを求めない。退出・削除・除外・失効した関係を古い保存から復活させず、iCloudアカウント・アプリ内ログイン・Store購入アカウントを同一と決めつけずにデータを分離する。購入の確認はStoreKitの確認・復元を根拠とし、バックアップ中の購入済み表示だけで権利を付与しない。

自動保存・最終保存の成否・復元可能範囲を区別し、圏外・容量不足・iCloud未使用等で未保存の場合は復元済みと見せない。iCloudへ接続できない間も端末内のデータと基本通話を維持し、接続回復後に保存を再試行する。具体API・暗号化／鍵の移行方法・競合解決・保存頻度は設計で決める。過去の任意時点へ戻せる世代管理やリアルタイム通話の端末間引継ぎは、本要求だけで提供を確定しない。

|---|---|
| Standardの高音質・低音質 | Standardは高音質／低音質の2つの組合せを選べるようにする。基本codecはAAC、サンプリング周波数は使用機器に合わせて自動決定して固定し、bitrateは選択に応じて内部で選ぶ。機器変更時の再決定と固定する期間を設計し、要求値と実適用値・fallbackを区別する。具体bitrate・AACの採用形式・初期選択は未指定であり、比較後に決める。低音質を理由に欠落・遅延の基準を緩めない |
| 設定保持と実状態 | 選択を保存し、再起動・機器変更・Standard／Advanced切替後も表示と実効値を一致させる。Advancedの個別設定とプリセットの対応・優先関係を明示する。バースト／ストリームの違いと切替後に残る設定を仕様で説明し、初期値はバーストとする。Streamの選択制限追加は別判断とする |
| 低帯域と品質の評価 | 現在の品質を保つ推奨を維持しつつ、通信量節約のための低bitrate候補を比較する。48kHz・32kbpsと24kHz・16kbpsを手動候補として扱い、8〜12kbps付近等も聞き取りと実通信量による評価対象にするが、対応済み・推奨済み・自動切替必須とはしない。圧縮による波形変化と処理・転送による欠落を区別し、codec往復・実通信・機器の周波数変換・電池負荷を照合して推奨下限を決める |
| 声の分離の位置と確認 | 自分の声の分離は設定に置き、録音テストにも適用する。両モードの通話画面から自分の声の分離設定を外す。受信側の分離は相手の声への処理であることが分かり、有効時も効果と連続した受話を保つ。無効化だけを不具合修復の完了条件にしない |

音声連続性の受入では、8人・複数経路・異なる遅延／codec／bitrate、1〜3秒の無音・短い相槌・同時発話・無音後の再開を組み合わせる。AACは代替PCMの成功で済ませず実際の符号化・復号・出力まで照合する。各相手の時計・経路は独立して扱い、小さい通信遅延では早く再生し、揺れは必要な分だけ吸収する。切替で避けられない不連続は対象と無音時間を示し、それ以外へ固定待機を加えない。欠落・重複・時間ずれ・clickを加えた負例も検出し、微小な欠落を許容するために既存の波形判定を緩めない。物理端末・Bluetooth・実無線の口から耳までの結果は自動試験のアプリ内計測と分けて受け入れる。音声の再送禁止と制御からの独立は[パッケージ要求](パッケージ要求.md#rtc全体の制御と音声の配送契約)に従う。

## 利用者向けの平易な日本語と英語

Standardの画面・設定・ダイアログ・エラー・案内・通知などには、平易な日本語と英語を使う。内部実装を知らない利用者にも、誰に何をする操作か、今はどんな状態か、押すと何が起きるかが伝わる表現にする。「試行」「再試行」のような処理側の語、専門用語・略語・AIが意味を圧縮した短縮語や抽象的な名詞だけで、利用者に解読を求めない。短くするために、相手・対象・作用・失敗や未完了の意味を落とさない。

同じ言葉に異なる作用を持たせず、登録・拒否・閉じる・削除・切断・送信の中止等の違いを保持する。たとえば文脈に応じて「もう一度送る」「もう一度接続する」、英語では「Send again」「Connect again」等の具体的な操作で伝える。実際に行う処理へ合わせて選び、一括置換で意味を変えない。必要な短いラベル・状態とVoiceOverの名前は残し、説明文の大量追加を第一の解決策にしない。Advancedの技術詳細は正確な用語を保ち、一般利用者も使う共通ダイアログ等は同じ平易さを守る。

## 付録：省電力機構の考え方

2026-11-02に利用者から提示された、省電力を再検討するための参考の考え方を整理する。本付録は各技術の導入を定める要求ではなく、既存の「通信コストとバッテリー消費の徹底削減」の背景資料とする。現行のバースト送信を前提とし、CNGなどの導入予定は設けない。再検討の作業と適用可否は[バックログ](../backlog/改善候補.md#バースト通信の省電力再検討)へ分ける。

### 音声レイヤー

無言の区間に不要な符号化・音声packet送信・復号を減らし、発話に必要な処理へ集中するという考え方である。

| 技術 | 仕組みの考え方 | 期待する省電力と適用条件 |
|---|---|---|
| VAD（Voice Activity Detection／音声活動検出） | 入力から人が話す区間と、無音・背景ノイズ等の非発話区間を判別する | 判定を符号化・packet送信の抑制へつなげられれば、CPU処理と通信を減らす余地がある。検出そのものの処理や、次の発話を検出する入力は必要となる。小声・発話の立上がり・短い相槌を保つことが前提 |
| CNG（Comfort Noise Generation／快適ノイズ生成） | 音声の送信を休止する方式で、完全な静寂による切断感を和らげるため、受信側で背景雑音を合成する。ホワイトノイズ等は例であり、方式によって背景音の特徴も使う | 送信音声と音声復号の仕事を減らせる可能性がある一方、雑音生成や再生の処理は残る。背景音情報を送る方式もある。現行のバースト送信へ追加する計画ではなく、考え方の参考として保持する |
| DTX（Discontinuous Transmission／不連続送信） | 非発話区間の音声送信を休止する、または背景音情報等の少量の更新へ減らす。VAD・CNGと組み合わせる方式がある | codec・packet化・送信制御が協調する仕組みで、ネットワーク側だけの機能には限定されない。符号化・送信・受信処理の削減余地を考える参考とする。完全停止の可否と更新間隔は方式依存 |

送信頻度を「数秒に1回」程度まで下げるという提示例は、削減の方向性として残す。具体的な共通値にはしない。例えば[OpusのDTX](https://www.rfc-editor.org/rfc/rfc6716.html#section-2.1.9)には400msごとのframeという説明があり、方式ごとの条件がある。[CNGのRTP表現](https://www.rfc-editor.org/rfc/rfc3389.html)も、すべてのcodec・媒体経路に同じまま適用されるものではない。

### 通信・アーキテクチャレイヤー

不要な送受信や周期的な起床を減らし、通信処理と無線が休止できる時間を増やすという考え方である。実際の省電力効果は、通信量だけでなくOS・無線・媒体経路と処理の動きに依存する。

| 技術 | 仕組みの考え方 | 期待する省電力と適用条件 |
|---|---|---|
| 接続状態に応じたビットレート制限・輻輳制御 | 帯域の詰まり、遅延、損失等に応じて送出量を調整する。GCCやBBRは、この方向性を考えるために挙げられた例 | 過剰な送出、送信待ち、損失に伴う再送等を抑えられれば、通信負荷・無線の高負荷時間を減らす余地がある。再送の有無は媒体の信頼性設定にも依存し、bitrateを下げれば必ず再送や消費電力が減るという関係ではない |
| ICE／TURNのキープアライブ最適化 | 接続維持のための確認packetと周期処理の送信頻度を、必要な接続性を保てる範囲で整理する。STUN Binding等はその例 | 不要な起床を減らし、無線が休止できる時間を増やす余地がある。NAT保持、送信同意の再確認、TURNの割当・permission・channelの更新は役割と期限が異なる。接続維持と期限を満たす条件を先に区別する |

[GCCの設計資料](https://datatracker.ietf.org/doc/html/draft-ietf-rmcat-gcc-02)はRTP媒体向けの参考となるInternet-Draftであり、[BBR](https://github.com/google/bbr)とは適用するトランスポートや制御点が異なる。アルゴリズム名の例示と、音声codecのbitrateを実際に変える処理は分けて考える。[WebRTC Data Channel](https://www.rfc-editor.org/rfc/rfc8831.html#section-6.1)にはSCTP側の輻輳制御があり、WebRTCを使うだけで独自音声payloadのbitrateが自動調整されるとは限らない。

接続維持の参考は[ICE keepalive](https://www.rfc-editor.org/rfc/rfc8445.html#section-11)、[Consent Freshness](https://www.rfc-editor.org/rfc/rfc7675.html#section-5)、[TURN](https://www.rfc-editor.org/rfc/rfc8656.html)。送信間隔を広げる考え方は、これらの必要な期限・確認と、通信断からの復旧を満たす範囲で扱う。「切断されなかった最大の間隔」を、異なるNAT・ネットワークや背景動作でも安全な値と一般化しない。

### この考え方を読む基準

本付録の省電力効果は期待する方向であり、RideComで測定済みの効果ではない。現行のバースト送信・codec・転送経路で、既に減らせている仕事と残る仕事を区別する。参考技術を一式で追加する前提を置かず、採否が必要になった項目だけを、会話の品質・低遅延・接続維持と処理・通信・電池消費の観測から判断する。
