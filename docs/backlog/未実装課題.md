# 改善・機能の課題と候補

改善・機能の未完了課題と採用判断待ちの候補を一元管理する基準となる資料。1見出しが1課題で、着手の順番は[バックログの着手順](README.md#着手順)だけに置く。課題は本書の見出しで参照する。判断・再開の条件は一覧で確認する。

確定した要求は[製品要求](../requirements/製品要求.md)・[パッケージ要求](../requirements/パッケージ要求.md)または開発方針等に従い、各課題の「要求の根拠」から参照する。各課題には要求との差分として残る作業・完了条件・未決事項を置く。候補の参照リンクは判断を制約する既存要求であり、候補自体の採用根拠ではない。進捗と次の着手は一覧から追う。終わった作業は外し、実態は[仕様](../spec/)、確認の結果は[検証の履歴](../validation/history/)、実機・実サービスの確認待ちは[未確認事項](../validation/未確認事項.md)へ置く。採用前の案も本書で状態・採用条件を保持し、一覧の判断・再開待ちで追う。管理の統合だけでは採用・実装を決定しない。2026-11-17の整理で外した完了済みの経緯は[旧未実装課題の完了済み経緯](../development/history/旧未実装課題の完了済み経緯.md)に原文を保持する。

## プロダクト文書を用途から探せる構造へ移す

**重要度は最重要の一つ。** 2026-11-21の要求者指定。人が操作や疑問から必要な文書を探せて、変更前後をレビューでき、非フロンティアモデルでも重複や矛盾を増やさず移行できることを求める。[用途から仕様までの構造](../policies/文書作成規約.md#用途から仕様までの構造)

[構造設計・移行手順・セルフレビュー記録](プロダクト文書の構造と移行手順.md)に沿って、まず「呼び出し通知を無視する」を移す。次の担当はそこで使った作業票から別の一件を再開する。完了条件は、対象文書すべての行き先を説明でき、入口から要求・現行動作・実測・残課題を探せること、元の条件と参照を保持し、未決の矛盾に根拠と担当課題があること。スキル・エージェント指示・開発規約は対象外。

## 監査対応で複雑になった実装を標準の仕組みに戻す

**重要度は高。** 監査の指摘を受けて変更した箇所を、指摘、変更前後の差分、実際の利用経路からたどる。標準のAPIや配布手順を独自の処理で置き換えた箇所、同じ検査を複数の場所に追加した箇所、通常操作が難しくなった箇所を先に調べる。[影響と費用に見合う対策](../../.agents/skills/security-audit/references/監査範囲.md#影響と費用に見合う対策を選ぶ)

|---|---|

| 変更前後を検証する | 通常操作、失敗と復旧、安全性を守る条件を同じ手順で確かめる。標準へ戻した後もどの要件を満たすか、独自の処理を残した場合はその根拠を記録する |

## 異常終了を継続監視しPC利用を阻害する再発を抑える

**要求の根拠:** [異常終了を継続確認しPCの利用阻害を抑える](../policies/開発方針.md#異常終了を継続確認しpcの利用阻害を抑える)。

| 残作業 | 完了条件 |
|---|---|
| 対象と発生条件の照合 | ホスト／Simulator／対象端末の区別、プロセス名・バージョン・時刻・終了理由／crash report、直前の実行操作とPCへの影響を照合する。古い報告と新規発生、意図した試験終了と予期しない終了を区別し、原因未確定のままOS由来と断定しない |

| 対策後の受入 | 同じ起動・操作・終了・反復条件で異常終了・再起動連鎖・資源残留とPCの応答性を対策前後で比較する。対象・観測期間・回数・残る制約を示し、必要なテスト品質を落とさず通常のPC利用を妨げないことを確認する |

## 接続の不安定さと切断を聞き分けられるようにする

[製品要求の「通話の接続状態を音で知る」](../requirements/製品要求.md#利用者に提供すること)に沿って、接続が不安定な場合と完全に切れた場合を区別する。それぞれ短く穏やかな効果音で知らせる。状態が続く間は数秒おきに繰り返す。状態が変わったら音も切り替える。回復または利用者の終了操作で繰り返しを止める。通常の無言やミュート、音声が届き続けている経路切替、呼び出し通知とは区別する。

音の違い、音量、長さ、状態ごとの間隔と鳴り始める条件をデザインで決める。グループ通話では、接続が完全に切れた相手の名前を端末が自動で読み上げる。3人以上の実機試験で、切れた相手が分かり、残った相手とは話し続けられることを確かめる。複数人が切れた場合や短時間で切断と復旧を繰り返す場合を含め、読み上げの頻度は会話を妨げすぎないようデザインで決める。受入では、2台で通信を不安定にしてから完全に切り、復旧させる。ロック中も通話に使っていた出力先で2種類の音を聞き分けられること、会話や音楽を妨げすぎないこと、無言やミュートでは鳴らないことを確かめる。[背景通話の復旧課題](#バックグラウンド中に通話が意図せず切れる)と合わせ、経路の判定と音が一致することを確認する。

### 個人通話とグループ通話の案内を利用場面から決める

[1対1で接続する場面](../design/操作の流れ.md#1対1で接続する)と[走行中に会話する場面](../design/操作の流れ.md#走行中に会話する)を起点に、話す人と聞く人が、端末をしまったまま何を知る必要があるかを書き出す。

| 利用場面 | 挙動を決めるための問い |
|---|---|
| 個人通話で相手がまだ参加していない、または会話が始まった後に応答が途切れた | 最初からつながっていない場合と、接続が不安定になったり完全に切れたりした場合で、何を伝えれば状況が分かるか |
| 個人通話で相手と初めてつながった、または接続が戻り会話を再開できた | 相手に声が届くようになったことを、どの時点でどう伝えるか |
| グループ通話でまだ誰ともつながっていない、または一部の相手だけが参加している | 誰と話せる状態かをどう知らせるか。参加予定の相手がまだ来ていないことを必要に応じてどう伝えるか |
| グループ通話で1人または複数人との接続が切れた | 切れた人の名前をどの順で読み上げると分かりやすいか。残る相手との会話が続いていることをどう伝えるか |
| グループ通話で初めてつながった相手がいる、または切れた相手の一部か全員との接続が戻った | 新たに話せる相手を知らせる必要があるか。接続と切断が続くとき、いつ案内を繰り返すか |

各場面で発生条件、伝える内容、効果音と名前の読み上げのタイミング、間隔、止める条件を決める。近距離とインターネット経由の両方で、画面を見ずに期待した状態を把握できることを受入条件にする。通話の種別は保存されている個人通話・グループ通話の区別を使い、グループに2人しか参加していない場面も確かめる。

## グループの削除と退出を同期する

## 音声の途切れと遅延

**Build 2240で再発した近距離の音の途切れは、[最優先の3件](README.md#着手順)の次に扱う。** 2026-11-24、依頼者が近距離通話で音がまた途切れると報告した。後続の短い試験で合格した範囲は下記のとおり。報告された途切れの原因と対処は、同じ欠落が再現する条件で判定する。

まずMacやSimulatorの近距離通話で、発話・短い相槌・発話再開の区間を再現する。欠落した区間の送出・受信・復号・再生を照合して、欠落が始まる段を特定する。修正後に同じ条件を試し、両方向の最終出力に発話の欠落がないことを確認する。既存の遅延基準も維持する。[音声経路の試験](../validation/未確認事項.md#macの近距離quic探索とapp音声e2e)

中断前の短い入力から計算した320サンプルの再生余裕は、新しい符号化ストリームに持ち越さなくなった。iPhone Simulator 2台の近距離で発話の連続性は両方向とも合格した。計測余裕込みの遅延は124.54 msと126.96 msで、片方向は125 msの基準に届いていない。次は同時に近い送出が生じる収録周期と、受信の描画予約を照合する。[修正前後の通話の測定](../validation/history/近距離オフライン通信.md#中断した符号化ストリームの余裕を次の通話音声へ持ち越さない)

2026-11-24。保存済みグループの近距離試験で、連続パケットの間隔が送信記録の約10〜11msから受信記録の約76〜80msへ伸びていた。AudioMixerで約76msの間隔を与えると、再生時に64.67〜70.00msの無音が出た。送信キューとUDPを測った20秒の既定AAC通話では、有声欠落は0で受信間隔も最大14.68msだった。次は間隔が伸びた条件を捉え、同じパケットの送信・UDP・App受信を照合する。通常到着時も残る約125msの遅延判定は有声欠落と分けて追う。[無音の再現](../validation/history/近距離オフライン通信.md#到着間隔が約76msになった音を再生し無音の長さを測る)・[送受信の計測](../validation/history/近距離オフライン通信.md#既定aacで送信キューから相手の受信までを照合する)

近距離の背景試験では、iPhone Simulator 2台で経路復旧後の受話まで進んだ際、発話に最長10 msの欠落が残った。この発話のどの段で欠落が生じたかを確かめる。[背景からの自動復旧の測定](../validation/history/複数端末の経路断と自動復旧.md#macが後から参加し背景のiphone-simulatorへ発話を届ける)

2026-11-23。iPhone Simulator 2台の近距離で、出力ミュートから戻した試験は2回とも遅延か発話欠落の基準を外れた。[測定結果と判定](../development/history/バックログの優先順位と進捗の記録.md#音声e2eで無音の結果と発話の遅延を区別する)に条件と数値を記録した。

2026-11-25。WebRTCのローカル試験で、Mac受話の復号後からミックス出力までの間に10 msの有声欠落が1回現れた。同じ条件での再試験では欠落0、両方向とも遅延125 ms以内だった。近距離で報告された途切れとの関係は未判定。[MacとiPhone Simulatorの測定](../validation/history/Cloudflare検証.md#macの本番通話の準備とローカルでの受話を照合する)

**要求の根拠:** [適用する要求・方針](../requirements/製品要求.md#共通の品質方針)。

**2026-11-20の追加要件:** codec・サンプリング周波数・bitrate・音声処理の対応組合せで途切れを検証する。要求と既存の試験定義を照合し、不足する組合せの試験定義・実行結果対応は[音声組合せ試験の残作業](#音声の対応組合せと処理切替の試験を要求に揃える)として管理する。音声処理本体の欠落・遅延修復は本課題で継続する。

既定AACで、有声区間の欠落0と約125msの両方を満たす。収録リングの取出しが114ms遅れた条件でのデータを渡すスレッドの状態が未確認。専用スレッドと既存キューの比較では同じ遅れは再現しなかった。リング待ちが短い条件でも起きる再予約は、レベル測定・発話判定、通信、再生予約の経過を分ける。端末内の受信処理待ちはAppの到着時刻を使って揺れの学習から除いた。双方向の後参加とマイクOFF後の受話再開で、復号PCMと実出力の位置、前後の発話、有声欠落と遅延を照合する。[データを渡す方法の比較](../validation/history/音声同一性と途切れの再現.md#収録配送の専用スレッドと既存キューを入れ替えて比較する)、[到着時刻の回帰](../validation/history/音声同一性と途切れの再現.md#到着後の処理待ちを通信の揺れに含めない)

OSからの入力とリング待ちの計測、再生待ちの比較・採否は[音声の検証履歴](../validation/history/音声同一性と途切れの再現.md#背景の近距離通話で収録コールバックとリング待ちを測る)に残す。最初の受信処理に100ms以上かかる条件が再現したときは、native UDPの送受信とRTCでのデータの受け渡しの時刻を照合する。

Release Build 1700のiPhone Simulator 2台では、Internet未応答時の近距離通話で両方向の有声欠落は0、遅延は比較余裕込み127.21／133.29msだった。定常区間で照合した実波形62箇所はすべて予約からの予測時刻の1ms後に出力された。起動時の無音再予約とnativeの書込位置を比較した。書込位置より前に予約すると、語頭や直後の音を欠く条件があった。固定の前倒しは採用せず、同じ発話の収録・符号化・復号・予約の経過を比較し、縮められる区間を選ぶ。利用可能な経路では[PCM16 16kHz](#送信側で欠けるpcm16-16khz)の欠落の再現も進める。[定常再生と実波形の照合](../validation/history/音声同一性と途切れの再現.md#定常再生の方向差が残る時点を実波形で確認する)、[予約位置と語頭の照合](../validation/history/音声同一性と途切れの再現.md#予約を早めた場合の語頭と後続の実描画を照合する)

### 指示と目的

バイク・スキーのインカムで滑らかな会話を成立させる。低遅延の通信条件では口から耳まで約125 msを快適性の上限とし、アプリ内部で固定待機を積み増さない。既存の音声同一性の判定を緩めず、1%未満でも発生する欠落・重複・境界のポップノイズを検出して減らす。修正と自動テストをコミットする。

### 対象

- 入力、音声処理、符号化、送受信、復号、混合、出力と、それぞれの接続における待機時間を測る。
- 小さい通信遅延では早く再生し、揺れがある場合は必要な分だけ吸収する。各相手の時計・経路を独立して扱う。
- 8人、複数経路、異なる遅延・コーデック・ビットレートの組合せを検証する。
- AACは代替PCMの成功で済ませず、実際のAAC符号化・復号・出力を確認する。
- 1〜3秒の無音、短い「うん」「ふん」、同時発話、無音後の再開を含む会話を検証する。
- 設定切替で避けられない不連続は対象・無音時間を明示し、古い音を遅れて再生しない。それ以外の設定は待機を加えず適用する。
- 音声にはTCP相当の信頼性あり転送・再送・reliableコピーを使わない。制御のみ別契約とし、データをすぐに渡して遅延を抑える方法で修復する。
- 欠落・重複・時間ずれ・クリックを意図的に加えた負例が失敗することも検証する。
- 実装はpackageとAppの責務を保ち、置換した経路を削除する。packageを検証してからAppを変更する。

### 現状と検証の境界

自動化では実AVAudioEngine・実コーデック・Simulator・通信経路の出力と入力時刻を保存する。物理iPhone同士、Bluetooth、無線環境の口から耳の遅延は別途実機測定が必要であり、自動検証だけで達成扱いにしない。

### 送信側で欠けるPCM16 16kHz

2026-11-17の[QUIC移行後のLocal測定](../validation/history/近距離制御のQUIC移行.md#標準配置のmacとiphone-simulatorの音声測定)で、PCM16 16 kHzの有声区間欠落を両方向で再現した。送受信時刻を照合した区間にパケットの未着はなく、復号直後にも欠落があった。送信側のVAD・音声処理・符号化のどの段階で発話が弱まるか、英語の往復発話で照合する。

2026-11-03、Simulatorの入出力を固定してLocal通信のquickを再開した（`.validation/audio-e2e-20261103-230313-300842`）。`pcm16-16k-voicechat`だけは、両方向とも復号直後の音声に0.7〜1.8%（最長20ms）の欠落が残った。受信packetの連番・収録時刻・到着間隔に欠けはなく、劣化のないPCM16でも復号直後に欠けるため、送信側のVAD・音声処理が発話区間を無音にしている可能性が高い。既定のAAC-ELD、Opus 24kHzは同じrunで欠落0。受信の待ち学習（`fb1d5524`ほか）とは独立の課題として、送信PCMの観測と、16kHz・voicechat profileでのVAD判定の再現から着手する。

11月19日のMac／Simulatorと、Build 1703のiPhone Simulator 2台の各8秒では、両方向とも復号・最終出力の有声欠落0だった。以前の復号直後の欠落は、別のOS・機器で再現する場合や、長時間の利用中または出力切替後に再現する場合は、同じ時刻の送信PCM・発話判定・復号を比較する。Build 1704では受信分離ON時に遅着後の再予約で26.69msの空白が出た。記録した再生位置での再試験では、予約を一律に早めた両条件（5ms、10ms）で後続の遅着で新たな空白が発生した。現行の待ちを保つ。OFF時の欠落条件も追う。[相手別受信分離の比較](../validation/history/近距離制御のQUIC移行.md#pcm16-16khzで相手ごとの受信音声の分離だけを切り替える)、[保存した描画位置での再試験](../validation/history/近距離制御のQUIC移行.md#pcm16の遅着後の予約を早めると次の空白が増える条件を確認する)

## 近距離の送信側で声の分離が効かない

**最優先の2番目。ネット通話の次に扱う。** 2026-11-24、依頼者がBuild 2240の近距離通話で送信側の声の分離がまったく効かないと報告した。「声の分離」はノイズリダクションの日本語名。[音質と音声設定の要求](../requirements/製品要求.md#音質選択と音声設定の体験)・[Build 1222の報告](../validation/未確認事項.md#build-1222で報告された送信側の声の分離)

同じ発話と周囲の雑音で、対応する音声入力のオン・オフ・再オンを手元で比較する。設定、送信処理の実際の適用、相手の再生を照合する。オンと再オンで発話が保たれ、オフの場合より雑音が減ることを完了条件とする。騒音・風・マイクなど物理条件でしか判断できない差は、必要な条件だけを検証一覧で追う。同じ入力で受信側の声の分離の効果も確認する。送信側と受信側を個別に切り替え、雑音が減るかを方向ごとに判定する。受信側も効いていなければ、送信側と同じ最優先の区切りで修正し、合否は方向ごとに記録する。[受信側の関連課題](#build-1222で受信側の声の分離をonにすると音声が途切れる)・[Advancedの送受信診断](#advancedで送受信を診断できるように戻す)

Release相当の端末内試験では、送信の雑音成分がONと再ONでともに約5.4 dB下がった。受信全体と相手別も定常出力の試験が合格し、切替時の最大無音は既存の基準内だった。近距離のAAC-ELD通話でも、送信は相手の復号時点で約5.4〜5.8 dB、受信全体と相手別は再生で約5.3〜5.4 dB雑音が減った。合成音を加えた発話の照合率と、受信分離ON時の遅延に不合格が残る。試験音を除いた発話の一致率はPCM16で100%になり、AAC-ELDでは復号直後に差が残った。通信なしでも48・64 kbpsのAAC-ELDで差が残った。128 kbpsでは近距離通話を含めて試験音を除いた照合は100%になったが、補助計測の遅延は125 msを超えた。報告時の騒音・機器での効果は実機で測る。[bitrateの比較](../validation/history/音声同一性と途切れの再現.md#aac-eldのbitrateを変えて復号と近距離の受話を比べる)・[近距離通話の測定](../validation/history/音声同一性と途切れの再現.md#近距離通話の復号と再生で声の分離を測る)・[処理と切替の測定](../validation/history/音声同一性と途切れの再現.md#release相当の送受信で声の分離の効果と切替を確かめる)

## Advancedで送受信を診断できるように戻す

**最優先の3番目。送信側の声の分離の次に扱う。** 2026-11-24、依頼者がBuild 2240のAdvancedで、診断の表示がおかしく情報も足りないと報告した。声の分離の状態と、以前見えていた送信の数値を確認できず、実機試験で音がどこまで進んだかを切り分けにくい。コーデックもオンの表示だけで、処理が進んでいるか分からない。[送受信診断の要求](../requirements/製品要求.md#音質選択と音声設定の体験)・[送信パイプラインの現行仕様](../spec/App/UI/Diagnostics.md#送信パイプライン)・[Build 1253の診断の指摘](../validation/history/音声同一性と途切れの再現.md#advancedのtxでvadと声の分離の実状態を並べる2026-11-20)

- Advancedの送信（TX）と受信（RX）の各タブで、その方向の声の分離のオン／オフを常に表示する。項目を展開せずに読めることと、音声の未計測時も設定を確認できることを確かめる。
- TXとRXの各プラグインで、設定をオフにして音声が素通しされた場合と、オンで処理が適用された場合の表示を照合する。利用できない場合や未計測の場合も、その状態を確かめる。
- 通話試験でパケットを流し、止め、再開する。TXとRXの各プラグインで、現在パケットを処理しているかを、オン／オフとは別に判定できることを確かめる。
- 選択中の通話で、音声パケットの実際の送信・受信を各タブにリアルタイムで表示する。発話・休止・再開を試す。送信と受信の表示が音声の流れに応じて変わることを、画面を開いたまま確かめる。符号化やプラグインの処理、相手側の再生は別の観測として扱う。
- コーデック名は実際に使うものを表示する。TXの符号化とRXの復号は、処理中・停止中・未計測を区別し、再開時はその場で表示が更新されることを確かめる。
- 送受信、プラグイン、コーデックの各段を手元の試験で個別に止める。診断を開いたまま、処理が止まった段と動き続ける段を判別できることを確認する。表示形式は、実装側で変化を読み取りやすい表現にする。

## Build 1222で受信側の声の分離をONにすると音声が途切れる

**要求の根拠:** [適用する要求・方針](../requirements/製品要求.md#音質選択と音声設定の体験)。

2026-11-19の利用者によるバグ報告。分類は改善（音声の連続性に関する不具合）。Build 1222で受信側の声の分離をONにすると音声が途切れる。相手別・受信全体のどちらの操作か、対象OS・機器・経路・codec、切替直後だけか継続中もかは未確認。iOS Simulatorでは切替直後に100ms以上の無音を記録した。受信mixの固定を試した構成では120ms基準を超えたため、送信側の修正は送信の経路に絞った。[比較試験](../validation/history/音声同一性と途切れの再現.md#送信側の声の分離をoffからonに戻すと効き方が変わる2026-11-20)。

同じ入力・通信条件でOFF／ON／切替時を比較し、受信・復号・分離処理・混合・最終出力のどこで欠落や停止が生じるかを観測する。分離を無効にすればよいという回避だけで完了にせず、対応環境でONのまま効果と連続した受話を維持する。相手別と受信全体を分け、同時適用や解除後の回復も影響範囲に応じて確認する。[音声の途切れと遅延](#音声の途切れと遅延)と関連付けるが、送信側の分離無効や既存の欠落と同一原因とは決めつけない。

[Build 1450の実装と検証](../validation/history/音声同一性と途切れの再現.md#固定した混合比を製品の受信分離に適用する)で再ON後の継続的な減衰を修正した。相手別の切替で別の相手の音が続くことを[iPhone Simulatorの製品経路](../validation/history/音声同一性と途切れの再現.md#製品の相手別受信分離で別の相手の出力を保つ)で確認した。[AACの形式切替に続くiPhone Simulatorの試験](../validation/history/音声同一性と途切れの再現.md#aacの形式切替後に続く受信分離の無音を測る)では、全体ONと相手別ONの両方で最大無音120ms以下を確認した。次に、実通話中の全体・相手別の切替対象の一時的な無音・減衰と再生時刻のずれを調べる。実通話の受入では、出力でも発話と相槌の連続性が揃うことと、相手別／全体の効果の維持を確認する。

後のDebug構成では、切替機能は動作するが、受信全体と相手別の分離をオンにしたときの無音が上限を超えた。[3回分の波形の合否と切替時間](../validation/history/音声同一性と途切れの再現.md#aacの定常波形と受信分離をオンにしたときの無音を分けて比較する)を参照する。次は受信の再生予約と、AAC 16 kHzで定常波形の誤差が増えた区間を別々に確認する。Build 1222の利用者報告と同じ原因かは未確認。

リント作業から最重要事項として引き継ぐ。iPhone Simulatorで音声機器を `Loopback Audio` に指定し、`scripts/audio_e2e.py --switches-only` で再現する。受信全体と相手別の分離をオンにした各区間で最長無音が120 ms以下かを確認する。AAC 16 kHzの定常音は、2 msごとの誤差の実効値が最大0.006以下かを確認する。切替試験全体の合否も記録する。[現在の結果・保つ実装・次の改善](../validation/README.md#音声の設定切替で守る動作と現在の品質)を確認してから着手する。

## グループの中で登録済みの相手を呼び出す

**要求の根拠:** [適用する要求・方針](../requirements/製品要求.md#利用者に提供すること)。

送り主が一人を選んだときは、[受け手の通知の要求](../requirements/製品要求.md#受け手の通話を遮らずに知らせる)も適用する。選ばれた相手が通話中なら会話を遮らず、選ばれなかったメンバーには通知しない。[受け手側の課題](#背景の通話中は呼び出しを静かに届ける)

グループ通話中、未接続のメンバーから個人登録済みで通知許可のある人を選ぶ。選んだ人に、対象のグループを示す通常のAPNsを1回届ける。グループの情報は端末間で暗号化する。候補の表示と送信直前で登録関係、通知許可、用途別grantと失効を確かめる。未登録・不許可・削除後、古い画面からの送信は拒否する。未接続時の通知操作は対象のグループを開き、会話中は今の通話を維持する。[呼び出しの画面差分](画面実装とデザイン見本の差分.md#未接続のメンバーの呼び出し)、[巻き込みを防ぐ規則](../design/通知の設計.md#巻き込みを防ぐ規則)

受入は[つながり方の前提](../design/操作の流れ.md#つながり方の前提)のユースケースを次の順に確認する。

1. [相手のいない場所で待つ](../design/操作の流れ.md#相手のいない場所で待つ)。時間の経過や送信の失敗で表示が変わらないことを確認する。
2. [同じ時間に入る](../design/操作の流れ.md#同じ時間に入る)。
3. [通知を放っておく](../design/操作の流れ.md#通知を放っておく)。送り主へ何も返らないことを確認する。
4. [後から自分で入る](../design/操作の流れ.md#後から自分で入る)。
5. [圏外で近くの仲間と始める](../design/操作の流れ.md#圏外で近くの仲間と始める)。通知なしで近距離だけでつながり、エラーを出さないことを確認する。
6. [会話中に呼び出しが届く](../design/操作の流れ.md#会話中に呼び出しが届く)。通話が切り替わらないことを確認する。

通知の到着だけでは接続しない。残る差の一覧は[通知の設計](../design/通知の設計.md#現行との差と依存)。

| 決定済みの条件 | 内容 |
|---|---|
| 通知は1回添えるだけ | 2026-11-10・11の利用者指示。1対1とグループのどちらでも、参加者は場所に集まるだけで、通知は親切に1回添える（[つながり方の前提](../design/操作の流れ.md#つながり方の前提)、[製品要求](../requirements/製品要求.md#利用者に提供すること)） |
| 作らないもの | 断ったことを伝える拒否は設けない。応答待ち・不在・再送・取消・送信結果の表示は作らない。Time Sensitive、呼び出し通知の合図と読み上げ、通知からの通話切替も対象外。アプリ内の通知切替と相手ごとの許可は設けない。サーバーの応答APIと送信側への転送も作らない |
| 使う技術 | SwiftUIと通常のAPNs・UserNotificationsを使う。CallKit・VoIP Push・PushToTalkは使わない |
| 通知できる相手 | 送信者が個人で登録している相手だけ。同じグループにいるだけの相手には通知しない（2026-11-04） |

グループへの招待の配達は[グループ招待の自動送信の実行契約](../spec/App/通信仕様.md#グループ自動配送の実行契約)で扱う。

## 背景の通話中は呼び出しを静かに届ける

**要求の根拠:** [適用する要求・方針](../requirements/製品要求.md#通知と画面の一貫性)。

受け手が通知を無視しても、送り主へ拒否を知らせたり再送したりしない。[呼び出しを1回だけ送る要求](../requirements/製品要求.md#選んだ相手だけを呼び出す)と[送り主側の課題](#グループの中で登録済みの相手を呼び出す)を一緒に確認する。

[本番で送る通知](../../server/src/NotificationDelivery.ts)はグループ招待を静かに届ける一方、呼び出しには一律で既定の通知音を指定する。両者を取り違えず、通話中の相手に届く呼び出しで音楽と会話への実際の影響を測る。

通常のAPNsで、待機中はOSの通知音を1回、通話中は通知センターへ静かに届ける。拡張が起きない場合の通知をpassive・音なしにする案を先に署名済みAppと実APNs Sandboxで確認する。起動できた場合は通話の実状態に応じて表示と音を変える。待機・通話中・拡張が作動しない3条件を分け、通話中のタップ／「接続」では今の通話を開く。[試作の検証](../validation/history/通知Appの接続と認可の検証.md#背景に届く通知の音と割り込みレベル2026-11-19)、[実環境受入](../validation/未確認事項.md#通常通知の受入)

## 同じ本人でログイン中の全端末を通知と個人通話の対象にする

[製品要求の「人を指定する通知と個人通話」](../requirements/製品要求.md#人を指定する通知と個人通話)に沿って、相手の人を選んだときの通知先と通話先を見直す。相手の招待や登録に使った端末を特定しなくても、同じ本人がRideComにログイン中の全端末を対象にする。通知を表示できるかは各端末のOSの許可に従い、1回の呼び出しを端末の数だけ繰り返さない。

相手が2台にログインした状態で、両方の通知と、どちらからでも個人通話に参加できることを確かめる。2台から同時に参加を選ぶ場合も、同一ユーザーのWebRTC接続を原則1台とする要求に従う。サインアウト、アカウント切替、端末資格の失効後は、対象外になった端末へ新たな通知を届けず、古い通知からも参加させない。

新しい端末を登録・復元した後、相手に端末の選び直しや再招待を求めずに通話できることを確認する。[個別通話の鍵](#個別通話の鍵を全経路で一致させる)と[iCloud復元](#icloud自動保存と招待をやり直さない端末復元)の検証を共有する。[復元・通知・通話・失効を同じ場面で確かめる条件](機能拡張の実装前整理.md#端末復元通知通話失効を同じ場面で確かめる)を参照する。有効な端末への到達と、失効した端末の除外を同時に確認する。

着手前と受入時は[3つのアカウントを切り替える共通の確認条件](機能拡張の実装前整理.md#3つのアカウントを切り替えて関連する機能を確かめる)を使う。

## 個別通話の鍵を全経路で一致させる

機種変更で端末鍵が変わる条件は、[iCloud復元の先行検証](#最初に端末鍵が変わる場合を検証する)と一緒に確認する。そこで判明した本人確認と鍵の条件を、本課題の受入にも使う。

**要求の根拠:** [適用する要求・方針](../requirements/製品要求.md#招待登録と個別通話の一貫性)。

**分類:** 機能。**状態:** 連絡先の招待では両端が同じ個別通話鍵を保存する（[通信仕様](../spec/App/通信仕様.md)の「個別通話の完成」）。残作業の受入は現行ビルドで作った招待と通話を対象とする。個人登録を兼ねる署名付きグループ招待では、新規の確認済みアカウント対で同じ鍵を選ぶことを確認した。[通常グループの返信が完了した新規端末対](../spec/App/通信仕様.md#通常グループの招待返信で端末宛て個別通話を準備する)にも対応した。双方が[確認済みの相手端末を一台ずつ持つ初回の個別通話](../spec/App/通信仕様.md#保存ユーザーを指定する個別通話)は、通常グループの相互登録から鍵の一致まで確認した。残る条件は下表で追う。

2026-11-02、実機で保存済みの相手との個別通話だけが近距離で繋がらない不具合を調べた。両端末が同じ個別通話IDを導出する一方、通信鍵をそれぞれ乱数で作っていたため、近距離の発見に使うgroupHashが一致せず、相手を別groupとして無視していた。同じ実機でgroup経由の通話は成立しており、Multipeer自体は動作している。連絡先の招待（`rideintercom://contact`）の完了時に、両端末が招待のgroup秘密から同じ鍵を導出して保存するよう修正した（[通信仕様](../spec/App/通信仕様.md)の「個別通話の完成」）。次の経路は未対応で、同じ食い違いが起こり得る。

| 経路 | 現在地・残作業 |

**優先。移行の着手条件が揃い次第進める。** 2026-11-23の依頼。解消したい重複は、アプリ本体のバンドルID `com.yowamushi-inc.RideIntercom.RideIntercom` のように、1つのID内に `RideIntercom` が2回続く箇所。依頼者がGitHubリポジトリ名を `RideIntercom` から `RideCom` に変更した。この作業環境では改名後の接続先から取得し、共有ブランチへ送信できることを確認した。反映済みの箇所を確認し、既存配布を引き継ぐために残す識別子と、名称変更が残る箇所を記録する。[現行の名称と識別子](../development/開発環境.md#開く入口)・[Apple側の登録先](../development/OS権限と配布設定.md#identifierとapple-developerでの設定)・[macOSの表示名とアイコンの課題](#macos版のアプリ名とアイコンが他osと一致しない)

完了条件は、既存の配布を引き継げることを根拠とともに記録し、その条件で揃えられる名称を整理して、合意した範囲を反映すること。改名後のリポジトリに対して、各作業環境のGitの接続先、CI、Cloudflareの連携、現行手順の参照先を確認し、残る差分を揃える。移行と復元の手順を記し、影響する経路でビルド、既存アプリの更新、既存データの引継ぎを確かめる。

App Store Connectに商品を作成し、1週間チケットと月額、標準の無料トライアルの提供条件を揃える。月額は家族共有の有効化、iOS・Macへの共通提供を扱う。公開商品を有効にする条件は、購入・更新・解約・失効・復元・取得失敗からの再試行と、それぞれの利用権反映を検証できること。月額・週券の重複と切替も確かめる。公開商品を有効にするまで、未設定時の試用と現行の認証・所属・費用条件を保つ。

購入・試用・無料配布・検証配布を区別し、有効な試用・無料チケット・TestFlightは購入者相当とする。StoreKitの確認・復元を根拠とする[現行の購入契約](../spec/App/利用権仕様.md#復元判定不能ユーザー切替)、[グループ操作と24時間の再開条件](../spec/App/通話利用権仕様.md)を保つ。公開商品の前に[料金と共有範囲](#ファミリー共有と料金の再見積もり)を決める。実商品と各OSの確認条件は[公開商品の受入](../validation/未確認事項.md#storekitと公開商品の受入)で追う。

着手前と受入時は[3つのアカウントを切り替える共通の確認条件](機能拡張の実装前整理.md#3つのアカウントを切り替えて関連する機能を確かめる)を使う。

## ファミリー共有と料金の再見積もり

**要求の根拠:** [適用する要求・方針](../requirements/製品要求.md#購入復元共有と公開条件)。

2026-11-01の追加要望。家族利用と少人数通話を含めて費用を見直し、利益を過度に求めず、赤字を避けられる料金を決める。

| 課題 | 求める方針 | 完了条件 |
|---|---|---|
| 家族が使えるアプリ内課金にする | ファミリー共有を有効にし、家族で利用できることを前提にする | 商品別のApple対応・App Store Connect設定・StoreKit側の権利反映・復元を確認する。4人家族全員が利用するケースを受入と予算へ含める。4人全員が別々に購入する収入を前提にしない |
| MacとiOSの課金を共有する | Mac版もiOS版と同じアプリ内課金の共有でよい | OS別の二重購入を前提にせず、両OSで同じ購入・ファミリー利用権を認識・復元できる商品構成と運用を確認する。端末数・同時通信数の制限とは分ける |
| 少人数利用を含めて費用を見直す | 2人通話も相当数ある想定とし、グループ人数は平均4人を基準に見積もる | 2人通話、4人の平均ケース、4人家族全員の利用を比較する。平均4人という全体前提と2人通話を含めた分布・比率の置き方を明記し、従来の人数前提のまま金額だけ決めない |
| コストに見合う価格を決める | 利益を優先しすぎず、必ず赤字を避けられるよう費用に見合った課金額を決めたい | [既存の費用試算](../development/Cloudflare費用試算.md)を、家族共有・OS間共有・購入件数と実利用者数の差を含めて再計算する。利用時間、経路・通信量、基盤費用、販売手数料等の前提と上振れ時の余裕を明示し、原価・赤字を防ぐために必要な範囲・価格候補の根拠を示す。赤字回避に必要な利用量の想定範囲や費用上限も決め、価格だけで未定の利用量まで保証した扱いにしない |

既存の[週券と月額の共有範囲](利用権とデータ保持の設計.md#購入の復元ユーザー切替とファミリー共有)では、週券は個人用、月額はファミリー共有としている。今回の「家族で使える課金」の要望に対し、各商品の共有範囲・提供方式を照合して必要な見直しを行う。Appleで可能かを確認する前に、全商品が既に共有できるとも、週券は今後も必ず共有対象外とも決めない。購入の独自台帳を増やす解決を既定にしない。

価格・商品構成・平均人数の変更は本書への記録だけでは現行試算へ反映済みにならない。再見積もり時に前提・計算・価格候補を更新し、無料招待と24時間猶予による購入件数と利用量の差も含めて確認する。

## アカウント削除のサービス範囲と別端末への反映

**要求の根拠:** [適用する要求・方針](../requirements/製品要求.md#購入復元共有と公開条件)。

**分類:** 機能。**状態:** 端末内の削除・再認証・server資格失効・Apple認可取消・稼働媒体回収は実装済み（[通信仕様](../spec/App/通信仕様.md#appleログインと端末内データ)）。配布版の削除対象は本番Workerの登録。同じ端末の別sessionと他の本人端末への反映は対応が残る。実Apple認証・実サービスの回収時間は[未確認事項](../validation/未確認事項.md#appleログインの実受入)で受け入れる。

- この端末に本番Workerの登録がなければ「この端末のデータ削除」とApple手動解除を提供する。同じ本人が別端末だけで本番Workerに登録した場合は、実サービス側の登録を確認し、本人確認と削除先を解決する仕組みが残る。近距離通話のためだけにInternet登録を必須にしない。
- 同じ端末の保存領域を使う別sessionのサインアウト／削除は、前面復帰・背景開始操作とApple確認復帰時の再読込で反映し、保持済みの旧ログインを失効させる。すでに継続中の別プロセスへの即時通知、別の本人端末と共有済みの相手端末への反映は引き続き未完了。端末内の旧repository書戻し拒否と、遠隔の媒体・通知・招待権限失効は同じ完了条件ではない。別端末へ削除が届いたときは利用権の照合結果と通知・媒体・招待の許可も取り消す。実サービスの受入は[Appleログインの実受入](../validation/未確認事項.md#appleログインの実受入)で追う。
- Workerのコードを戻しても、現行の保存状態を使うと削除済みの資格を拒否できることをローカルで確認済み。SQLiteを削除前の時点へ戻す運用は保留中。導入する場合は隔離環境の架空のアカウントで、旧資格による通話・通知・招待と、復旧した予約やアラームによる送信を拒否できることを確かめる。現在有効な別アカウントへの影響も確認する。[Workerの配置と保存の復旧](../development/Cloudflare試用手順.md#workerの配置を戻す場合に保存状態を維持する)

## 低帯域の推奨を決める

**要求の根拠:** [適用する要求・方針](../requirements/製品要求.md#音質選択と音声設定の体験)。

**分類:** 改善。**状態:** 手動候補（AACの48kHz・32kbpsと24kHz・16kbps、Opusの24／32kbps）は実装済み（[設定値一覧](../spec/App/Configuration/設定値一覧.md#aacの低帯域手動候補)、[Codec契約](../spec/packages/Audio/Codec.md)、[比較記録](../validation/history/低帯域codecの通信なし比較.md)）。既定48kbps・従来の品質推奨と波形判定は維持する。実ネットワーク量・聞き取り・電池に基づく推奨と最終受入が残る。Opusの8／12／16kbpsは実験では変換できており、追加候補として保持する。

| 課題 | 目的・範囲 | 状態・完了条件・確認点 |
|---|---|---|
| 低ビットレートでの通信を許容する | 通信量を抑えるため、低ビットレートによる音声波形の変化・劣化を許容できるようにする | 低帯域候補の実装は一部完了。実通信評価は未完。同じ入力・codec・周波数・音声処理条件でビットレートだけを変えて比較し、波形の崩れがビットレートの影響だけであることを確認する。通信なしのcodec往復と実通信の結果を照合し、音声処理や転送による欠落・不連続を低ビットレートの影響として扱わない。許容する範囲と確認方法は着手時に定める |
| 低帯域向けに48kHz・32kbpsと24kHz・16kbpsを選べるようにする | 端末の入出力は48kHzが多いという利用想定を踏まえ、通信状況に応じて32kbps、さらに厳しい場合は16kbpsを利用者が選べる候補を用意する | Appの選択候補は実装済み。効果・実適用値の受入は未完。数値は推奨値ではなく、codec・OSごとの対応と実適用値を確認する。端末入出力の実際の周波数と通信用の周波数を分け、48kHzと24kHz間の変換による影響・負荷も評価する。自動切替の実装は今回の要望として確定しない |
| 聞こえと実通信量から低帯域時の推奨下限を決める | 32kbps・16kbpsでも実通信では多い可能性があるため、電話・VoIPを参考にした8〜12kbps付近も含めて評価し、実用になる最も低い推奨値を探る | 未評価。比較候補の数値を対応済み・推奨済みと扱わず、発話の明瞭度・短い相槌・雑音下の聞き取り・連続性・遅延と、ヘッダー・暗号化・制御等を含む実際の通信量で判断する。選べる最小値と推奨下限を区別し、条件により使えない値は明記する。値・codec・周波数は測定と試聴の後に決める |
| 現在の波形を維持できる推奨設定を残す | 現行品質を保つ推奨と、帯域節約のため劣化を許容する推奨を利用目的に応じて選べるようにする | 現行の設定・実適用値・基準波形・品質判定条件は[Codec仕様](../spec/packages/Audio/Codec.md)に保持。低帯域向けの追加によって置き換えたり合格基準を一律に緩めたりしない。周波数とbitrateを同時に変えた差をbitrateだけの影響と判断せず、変換・圧縮・転送・再生を分けて評価する |

2026-10-30の補足。冒頭の「24kHzで16bps」は、後続の「16kbps」に合わせ16kbpsとして記録した。32kbps・16kbps・8〜12kbps付近はいずれもこれから検証する候補であり、現行推奨の変更や最低値の確定ではない。[候補と評価の順序](機能拡張の実装前整理.md#低帯域向けの候補と推奨の決め方)を参照する。

| 再開したとき | Watchからの開始 → native入力 → iPhoneでの処理 → Watchのnative再生までの実経路を先に閉じ、SDK buildや操作の成功だけで完成にしない。既知speech対照は未実施の候補 |
| 実機の受入 | 手首の暗転と音声の継続、無線、遅延、電池消費、長時間利用は[未確認事項](../validation/未確認事項.md#iphone依存watchの実機操作と音声)で追う |

## Watchのロック中リモコン操作を根拠にリリース可否を判断する

**要求の根拠:** [適用する要求・方針](../requirements/製品要求.md#利用者に提供すること)。

**分類:** 機能。**重要度:** 高。2026-11-21の要求者指定。Watchを提供する前提自体を先に判断する。リモコン既定化や設定移動だけでは公開可能と扱わず、根拠が揃わなければ当面Watchをリリースしない選択を認める。iPhone等の本体アプリのリリース必須条件にWatchの完成を加えない。

スキー・バイクではiPhoneのロック解除やアプリを前面へ戻す操作を要求できない。Watchの音声通話を除く、公開するリモコンの全機能がこの条件で効くことを採用条件とする。「ロック状態」は、まず操作対象のiPhoneがロック・背景にある状態を必須とし、Watch自身のロックと手首の暗転・背景化も区別して、操作できる条件とOS上できない条件を明記する。Watch自身がロック中に直接操作できると根拠なく約束しない。

| 次の作業 | 判断に必要な条件・証拠 |
|---|---|
| 公開する全操作の棚卸し | 通話先の選択、開始、ミュート・解除、終了、状態更新・表示など現行のリモコン操作を列挙する。Watchのマイク・スピーカーによる通話は除くが、リモコンからのiPhone通話の開始・終了は含む。対象漏れを防ぎ、公開対象と開発専用を分ける |
| ロック・背景での成立確認 | iPhoneが既にロック中の操作、操作直後のロック・背景化、待受からの開始、通信断と復帰について、iPhoneに各操作が反映され、その結果をWatchで受け取るまで実機で確認する。iPhoneの前面化・ロック解除・再操作を成立条件にしない。未接続など実行不能時は成功表示を出さない |
| 根拠の記録 | 端末・OS・アプリのバージョン、両端のロック／背景状態、前提、手順、期待値、実測結果・ログ、制約を操作ごとに残す。build成功、Simulator、前景だけのApp試験、要求の送信成功だけでは成立の根拠にしない。OS制約の判断には公式資料も添える |
| リリース可否の決定 | 全公開リモコン操作について上記の根拠が揃えば提供を判断する。不成立・未確認が残る間は[通常Releaseの非同梱](../spec/App/Watch操作.md)を維持し、iPhone側の設定・案内・マニュアルをその提供範囲に揃える。未検証機能を既定OFFにしただけで公開可としない |
| デザインへの引継ぎ | 公開範囲、操作可能な状態、遅延・失敗・結果未確認の表示、非提供時に除く導線をデザイン残課題へ渡す。仮のUIは仮と明示し、実状態と表示が一致する受入条件を揃える |

この課題はリリース判断とその反映が未完のためバックログで管理し、実装済み操作の実機確認だけになった範囲は検証文書へ移す。[配布見送り中の設定表示](../validation/history/AppleWatch実機への導入とXcode起動.md#配布見送り中の設定表示)は反映済み。採否の根拠を確認してから以後の提供範囲を決め、[Watch音声実験の中断](#watch音声中断中)を維持する。

### RTCの近距離方式とWebRTC実装を独立して差し替えられるようにする

2026-11-24の追加指示。Multipeer Connectivityから近距離のQUIC・UDPへ移行した例と、OSのWebKitを使うWebRTC実装への交換候補を踏まえて境界を点検する。[RTCの差し替え要件](../requirements/パッケージ要求.md#rtcの通信実装を交換できる境界)・[RTCの現行の責務](../spec/packages/RTC.md#役務と所有関係)・[近距離制御の移行記録](../validation/history/近距離制御のQUIC移行.md)

現行の `RTCCallRoute` と `CallSessionFactory` を起点にする。近距離経路を作る箇所と、インターネット経路が使うWebRTC実装やシグナリングの境界をたどる。近距離の方式を廃止しても、WebRTCの設定や実装まで変更する必要がない構成にする。WebRTC実装を交換するときも、近距離経路とAppの通話処理をそのまま使える設計にする。旧名 `multipeer` が残る識別子は、保存値や診断で使われているかを点検する。

WebKitは将来の候補として扱う。採用の判断前に、現行のDataChannelによる音声転送、制御との分離、Cloudflare SFUとの接続を対象OSで確かめる。ロック中の継続・再接続、音声品質、カメラを使わない配布条件も確認する。[現行の媒体契約](../spec/packages/RTC.md#cloudflareの媒体契約)

完了条件は、既存の境界を使い、経路またはWebRTC実装の交換・除外に必要な変更箇所と、共通処理を維持できる根拠を示すこと。同じ契約試験で開始・停止・認証・データ転送・診断を照合する。現行の圏外、混在中継、切断後の復旧は、影響する経路で回帰を確認する。

## Watchはリモコンを既定にし通話を開発者向けオプションにする

**要求の根拠:** [適用する要求・方針](../requirements/製品要求.md#利用者に提供すること)。

[Watchの相手一覧](../../RideIntercomWatch/WatchCallView.swift)は開始ボタンから音声コントローラーを呼ぶ。また[製品要求](../requirements/製品要求.md#利用者に提供すること)に「Watchから開始した通話は…Watchに固定」と「開始しただけで音声の所有先をWatchへ移さず」が併記されている。前者が適用されるのはWatch音声を明示選択した場合と分かるよう揃え、同じ相手を選んでもリモコン既定ならiPhoneで受話が続くことを確かめる。

配布見送り中の設定は[現行仕様](../spec/App/UI/Settings.md#自動切断)に反映済み。通常設定のWatch項目はiPhoneのAdvancedに限り、既存の自動切断Pickerを操作不可のまま表示する。項目名と保存値を表示し、配布見送りの理由や「無効」等の文言は追加しない。[端末別の検証](../validation/history/AppleWatch実機への導入とXcode起動.md#watch設定を表示する端末)

**2026-11-21の優先度再指定:** 利用できることを確認していないWatch音声はStandardから設定・案内を外した。再公開の判断は[ロック中の全公開操作](#watchのロック中リモコン操作を根拠にリリース可否を判断する)の根拠に従う。音声実験の中断を継続する。

**分類:** 機能。Apple Watchの既定をリモコンにし、マイク・スピーカーを使う通話は開発者向け設定で利用者が明示的に有効にする。リモコン開始で既存のiPhone音声を使い、指定時刻の切断・ミュート・終了へつなぐ処理は[App回帰](../validation/history/Watch音声のApp接続とデバイス分離.md#watchの開始操作からiphoneの音声を使う)で確認した。Watchの画面と音声設定への接続が残る。

| 残る作業 | 完了条件 |
|---|---|
| リモコンのみを既定にする | 初期起動・設定欠落・リセット時はWatchの音声通話をOFFにする。最低限の開始・終了・ミュート等、どこまでをリモコンに含めるかは現行操作を照合して定め、iPhone側の通話操作に接続する。Watchからの開始だけでWatch音声へ自動移行しない |
| Watch通話を明示オプションにする | OFFの間はWatchのマイク・スピーカーの通話経路を起動せず、通話の音声所有先をWatchへ切り替えない。ONの保存・再起動後の反映・OFFへの復帰・既存保存値の移行と、通話中の切替の扱いを定める。無断でONにせず、iPhone通話を意図せず終了させない |
| 受入 | 既定のリモコン操作とiPhone音声の維持、明示ON時だけのWatch音声、OFFへの復帰を実画面・実機で分けて確認する。リモコンの成功をWatch通話の音声成立と扱わない |

既存の[Watch音声の中断](#watch音声中断中)は維持する。この設定・既定動作の変更要求を、Watch音声の追加実験を再開する指示とは解釈しない。[既存の接続設計](機能拡張の実装前整理.md#watch音声の確定範囲と接続設計)と[製品要求](../requirements/製品要求.md)の既定動作との差を実装前に整理し、実装と同じ変更で設定・Watch操作の仕様とマニュアルを更新する。

### 最初に端末鍵が変わる場合を検証する

旧端末を紛失し、その端末や秘密鍵を使えない機種変更を想定する。保存した相手やグループとの関係、通話に必要な資格、端末固有の鍵を分け、本人が新端末で鍵を作ったときに、サーバーと相手側の端末がどの情報で本人を確認するかを現行仕様と実装からたどる。旧端末の鍵を必須とする箇所があれば、保存・本人確認・通話のどこで止まるかを記録する。

iCloudの実装を待たず、仕様上復元できる情報だけを入れた試験用データで先に検証する。相手の端末には旧端末とやり取りしたときの情報を残しておく。新端末が新しい鍵で登録した後、相手に再招待・再承諾を求めず、既存の個人通話とグループ通話で双方に声が届くかを確かめる。初回登録に通信が必要か、登録後の圏外通話で何が必要かも記録する。別人の鍵や削除・除外で失効した関係は受け入れないことを確認する。

先行検証で、旧端末の参加情報を直接読み込むと止まり、新端末用に組み直すと相手が受け入れることを確認した。本人と参加資格を確認した入力から、新端末の参加情報と通話鍵を[端末内へ保存する処理](../spec/App/通信仕様.md#新端末に確認済みの通話関係を保存する)を実装した。[検証記録](../validation/history/端末変更と通話関係の復元.md)

| 残作業 | 完了条件 |
|---|---|
| 復元時の本人・参加資格の照合 | 新端末は[要求を作る前](../spec/App/通信仕様.md#個別通話の復元を保存時の相手端末に照合する)と[保存する前](../spec/App/通信仕様.md#新端末に確認済みの通話関係を保存する)に自分のiCloudを読み直す。照合先は、[署名付き要求に含まれる受諾IDを端末内とiCloudの両方に照合する](../spec/App/通信仕様.md#現在の保存を照合して復元の確認を返す)。中継期限後、削除がどちらのiCloudにも反映されていない場合の判定は残る。複数端末と通常グループの照合先、退出・除外・失効の確認もつなぐ |
| 通話鍵の受け渡し | 通常グループの照合先では、[現在の所属を照合して新端末宛てに通話鍵を暗号化する](../spec/App/通信仕様.md#通常グループの照合先が現在の通話鍵を暗号化する)。照合先を選び、要求と応答を通信で届ける。新端末側は[本人の名前と招待経緯を保って応答から保存する](../spec/App/通信仕様.md#新端末に確認済みの通話関係を保存する)。個別通話は、双方がアプリを開けない間も照合先の証明を更新できる条件を確かめる。[実装済みの受け渡し](../spec/App/通信仕様.md#中継を通じて復元の要求を送り通話鍵を保存する) |
| 自動保存と復元の設計・実装 | 設定・相手・グループ・有効な関係と資格の保存範囲、端末固有情報との分離、保存頻度・失敗時の再試行・復元入口を定める。APIと鍵の安全な移行方式を選び、名前や一覧だけでなく通話可能な関係を復元する |
| 削除・失効と障害 | [iCloud側で変わっていない個別通話の相手だけを除く処理](../spec/App/通信仕様.md#アプリの操作を起点に復元候補を自動保存する)を実装済み。削除の反映後も残る端末間の編集、グループの削除・除外後の古い復元、iCloud／アプリのアカウント切替、圏外・容量不足・保存失敗まで確認し、他人のデータ混入・資格復活・空データでの上書き消失を防ぐ。購入はStoreKitで別に復元する |
| UI・仕様への反映 | 自動保存・未保存・復元結果が分かる表示と操作をデザインへ渡し、実装と同じ変更で仕様・手順・受入結果を記録する。過去世代の任意復元と通話中の端末引継ぎは今回の必須範囲へ追加しない |

実際のiCloud、近距離・Internet経路を使った復元後の双方向通話は、[iCloudの自動保存から機種変更後の通話までの実環境受入](../validation/未確認事項.md#icloudの自動保存から機種変更後の通話までを確認する)を行う。

同じ端末で最後のグループや相手まで続けて削除した場合は、途中で保存できなくても、[自動保存の照合](../spec/App/通信仕様.md#アプリの操作を起点に復元候補を自動保存する)で削除前と保管先が一致することを確かめ、空の候補へ更新する。別端末が保管先を変えていた場合も、確認済みの登録が同じ相手の削除は反映する。残る差分を端末間で統合する処理はこのあとに扱う。

設計論点は[実装前整理](機能拡張の実装前整理.md#icloudへの保存と自分の端末間同期)。進行順は[共通一覧](README.md#着手順)で管理する。実iCloudを使う自動保存・復元の動作確認が残る。

| 実適用と出力を照合する | 要求値・実適用・fallbackを記録し、短い相槌と語頭・語尾、長い無発話後の再開、音声処理のON／OFF切替を実出力で確認する。結果に対象ソース・設定・環境を対応付ける |
| 時間と影響に応じて実行する試験を選べるようにする | [テスト分類の課題](#テストを対象要求影響と所要時間で選択実行できるようにする)と連携し、変更の影響に応じた短い集合と長時間の集合を独立実行できるようにする。未実行の対応組合せを残し、合格範囲を明示する |

## StandardにAACベースの高音質・低音質プリセットを用意する

**要求の根拠:** [適用する要求・方針](../requirements/製品要求.md#音質選択と音声設定の体験)。

**分類:** 機能。2026-11-20の利用者要求。Basic（本リポジトリのStandard）画面では「高音質」「低音質」の2つの組合せを選べるようにする。基本codecはAACとし、機器に合わせたサンプリング周波数を自動決定して固定し、選んだ音質に応じてbitrateを内部で選択する。今回はバックログ・要求管理のみで、実装・実画面受入は未実施。

| 残作業・条件 | 完了条件 |
|---|---|
| 一般向けの2つの選択 | Standardでは高音質／低音質の意味と現在の選択が分かるコントロールにまとめる。codec・周波数・bitrateの個別値を選ぶ操作は求めず、内部値はAdvanced／Diagnosticsで確認できるようにする |
| 機器に応じた周波数 | 使用中の音声機器・経路の実対応とAACの対応形式を照合し、サンプリング周波数を自動決定して適用する。単に希望値を渡しただけで適用済みとせず、実入力形式・送信形式と必要な変換を区別する。機器変更時の再決定・固定する期間と通話中の扱いを設計する |
