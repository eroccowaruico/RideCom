## 近距離制御のMultipeerからの移行

**区分:** 機能（基盤移行）。
**状態:** Network.framework＋peer-to-peer Wi-Fiを採用決定済み。RTC packageで、一時的な自己署名identityの生成と、それを使うQUIC（mutual TLS）の接続の成立を2026-11-17に確かめた（[RTC仕様](../spec/packages/RTC.md#近距離制御のquic移行の準備)）。framing、証明書のfingerprintを束縛したhandshake、相手1人との認証済みの接続（`LocalControlLink`）、探索と全員との接続の管理（`LocalControlTransport`）も実装し、実際のBonjourとQUICで確かめた。UDP媒体との接続、経路（`MultipeerLocalRoute`の置き換え）、隊列の自動試験、App音声E2E、端末間（peer-to-peer Wi-Fi）の確認は未着手で、現行の近距離制御はMultipeerのままである。以下のプロトコル選定理由、移行条件、保留候補を維持する。

2026-11-17の繰り返し実行で、近距離の接続を止めるときにMultipeer内部のBonjourの処理でAppが落ちる場合がある（約420回のうち3回）ことを確かめた。Appのコードからは避けられておらず、この移行で解消を確かめる対象に加える（[観測](../validation/未確認事項.md#間欠的に失敗する実multipeerの招待テスト)）。

2026-11-02の追加依頼。Xcode 27 SDKでMultipeerConnectivity全体が非推奨となった（[TN3213](https://developer.apple.com/documentation/technotes/tn3213-moving-from-multipeer-connectivity-to-network-framework)。各APIは「Deprecated in iOS 27.0」、移行先はNetwork.framework）。削除ではないため現行のbuild・動作は継続するが、今後の修正は期待できない。同日に代替手段を調査し、利用者の回答で方針を決めた。今回は記録だけを行い、実装・テストには着手していない。

現在MCSessionが担うのは、探索・招待、暗号化必須のsession、handshake・presence・操作のreliable配送だけである。Local音声は既にNetwork.frameworkのUDP（`includePeerToPeer = true`）で送っている（[RTC仕様](../spec/packages/RTC.md)）。TN3213は、Apple peer-to-peer Wi-FiがMultipeer専用ではなく、Network.frameworkからも使えることを明記している。移行後も、AP・セルラーがない屋外の近距離通話（[製品要求](../requirements/製品要求.md)）を同じ無線で成立させる。最低対応OSが27.0のため、iOS 26で追加された`NetworkListener`・`NetworkBrowser`・`NetworkConnection`をavailability分岐なしで使える。

| 代替手段 | 判断 |
|---|---|
| Network.framework＋peer-to-peer Wi-Fi | 採用。iOS/macOS両対応で、端末の組ごとのペアリングが不要。既存のUDP媒体と同じ基盤 |
| Wi-Fi Aware＋DeviceDiscoveryUI | 第1段階は不採用。対応機種と端末の組ごとのペアリングが制約になる。[改善候補](改善候補.md#近距離通信の追加経路と統合)へ置く |
| Core Bluetooth | 第1段階は不採用。音声主経路には帯域・距離・遅延が不足し得る。補助経路として後から検討する（[改善候補](改善候補.md#近距離通信の追加経路と統合)） |
| Nearby Interaction、GameKit、SharePlay、インターネット共有 | 対象外。音声・制御のデータ経路にならない、Multipeer系の旧方式である、またはAP・Internet不在の要求を満たさない |

| 論点 | 2026-11-02に決めた方針 |
|---|---|
| 制御protocol | QUICを使う。handshake・presence・操作をQUICのreliable streamへ移し、message境界はframingで保つ。64 KiBの受信上限など現行のLocal制約を引き継ぐ |
| 暗号化と認証 | TLS-PKIを基本路線とする。端末ごとに一時的な自己署名identityを生成してmutual TLSを張る。相手証明書はTLS層の信頼評価では受け入れ、既存のgroup共有鍵によるhandshake MACへ証明書fingerprint等を含めて通信路へ束縛し、そこで認証する。Apple OSにidentityの生成APIがないため、生成は最小の自前実装とした（外部依存を増やさない。2026-11-17）。束縛は、handshakeのMACへ送信側・受信側の両方の証明書のfingerprintを含める方式とした（2026-11-17）。TLS-PSKは旧APIだけの機能で、TLS 1.3とQUICに対応しないため使わない |
| 接続の形 | 届く相手とはすべて直接接続する部分メッシュとし、全員が直接届くことを前提にしない。隊列で先頭と最後尾が直接届かない場合も、既存の[重複破棄付き転送（最大8hop）](../spec/packages/RTC.md#混在通話と経路)で中間の端末が中継する。特定の端末をserverにするclient-server構成は、その端末の離脱や隊列内の位置で全体が切れるため採らない。同じ相手との重複接続はpeer IDの比較で片方を閉じ、既存の[招待競合の回避](../spec/packages/RTC.md#近距離接続試行の競合回避)の辞書順を引き継ぐ |
| 探索とプライバシー | 最低限とする。`NetworkListener`でBonjour serviceを広告し、TXTには現行と同じgroupHashを載せる。自動接続のため、service名には端末名を使わず通話世代ごとの識別子を使う。識別子のrotation等の追加対策は、利用規模・利用場所から現時点では行わない |
| 音声 | 第1段階は既存の`_ride-audio._udp`のUDP媒体を維持し、UDP媒体用のnonceを新しい制御経路のhandshakeから渡す。QUIC datagramへの統合は[改善候補](改善候補.md#近距離通信の追加経路と統合)とする |
| 旧版との互換 | 維持しない。Multipeer版と新版の混在通話は不可とし、同じ版同士で使う。利用者の操作・表示（Settingsの近距離ON/OFF、接続・切断、経路の表示）は変えない。保存済み設定の`RouteKind.multipeer`は名前を変えずに読むか、[移行の対象・条件・復旧](../policies/開発方針.md#技術選定方針)を定めてから変える |
| 電力 | 第1段階はTN3213の基本どおりとする。通話停止で探索・listener・connectionを破棄し、途中参加・再発見のために通話中は探索を維持する現行の扱いを引き継ぐ。Bluetooth併用等の省電力・補助経路は後から検討する |

**完了条件**:

- RTC packageの独立工程として実装・検証してからAppへ接続する。RTCから`MultipeerConnectivity`のimportをなくし、Multipeer専用の回避策（CFNetwork初期化、MCPeerIDの63 byte制約、MainActorでのnative資源の所有）を不要になった範囲で除く。
- 既存のLocal契約を新しい経路で維持する。対象は、handshake拒否と`connectionFailed`の区別、旧session通知の拒否、制御切断時の再handshakeとUDP媒体資格の保持、Local優先、経路変更・backoffである。既存のLocal関連テストを移植して全件成功させ、件数を減らして合格にしない。
- 隊列の形を自動試験する。直線に並んだ4端末（A–B–C–D。A–C、A–D、B–Dは直接届かない）の仮想経路で全方向の音声が中継で1回ずつ届くこと、中間端末の離脱で分断し、復帰後に自動合流することを確認する。
- 双方から同時に接続した場合に1本へ収束すること、group鍵を持たないpeer・別groupのpeer・証明書とhandshakeの束縛が一致しないpeerを認証しないことを確認する。
- App音声E2Eの`--transport local`で、既存基準（125ms、音声同一性、欠落0、所有資源の回収）を満たす。
- 実装と同じ変更で[RTC仕様](../spec/packages/RTC.md)、[アーキテクチャ](../spec/アーキテクチャ.md)、[OS権限と配布設定](../development/OS権限と配布設定.md)のBonjour service（QUICは`_udp`）、[音声E2E手順](../development/音声E2Eテスト.md)のMultipeer記述を更新する。
- AP・セルラーがない屋外でのiPhone間通話、隊列での距離と中継、移動・画面ロック・消費電力は[未確認事項](../validation/未確認事項.md)へ記録し、自動検証の合格と区別する。

### 指示と目的

バイク・スキーのインカムで滑らかな会話を成立させる。低遅延の通信条件では口から耳まで約125 msを快適性の上限とし、アプリ内部で固定待機を積み増さない。既存の音声同一性判定を緩めず、1%未満でも発生する欠落・重複・境界のポップノイズを検出して減らす。修正と自動テストをコミットする。

### 対象

- 入力、音声処理、符号化、送受信、復号、混合、出力と、それぞれの接続における待機時間を測る。
- 小さい通信遅延では早く再生し、揺れがある場合は必要な分だけ吸収する。各相手の時計・経路を独立して扱う。
- 8人、複数経路、異なる遅延・コーデック・ビットレートの組合せを検証する。
- AACは代替PCMの成功で済ませず、実際のAAC符号化・復号・出力を確認する。
- 1〜3秒の無音、短い「うん」「ふん」、同時発話、無音後の再開を含む会話を検証する。
- 設定切替で避けられない不連続は対象・無音時間を明示し、古い音を遅れて再生しない。それ以外の設定は待機を加えず適用する。
- 音声にはTCP相当の信頼性あり配送・再送・reliableコピーを使わない。制御のみ別契約とし、低遅延の即時配送で修復する。
- 欠落・重複・時間ずれ・クリックを意図的に加えた負例が失敗することも検証する。
- 実装はpackageとAppの責務を保ち、置換した経路を削除する。packageを検証してからAppを変更する。

### 現状と検証の境界

開始時点では入力とミキサーのtapが約100 ms単位にまとまり、送信100 ms・受信200 msの待機を要する。従来の全文照合は音声の連続性を検査するが絶対遅延と微小なクリックを保証しない。AAC ELD v2のモノラル条件ではOS変換が失敗してPCM16へ代替される。

自動化では実AVAudioEngine・実コーデック・Simulator・通信経路の出力と入力時刻を保存する。物理iPhone同士、Bluetooth、無線環境の口から耳の遅延は別途実機測定が必要であり、自動検証だけで達成扱いにしない。

### 送信側で欠けるPCM16 16kHz

2026-11-03、Simulatorの入出力固定後に再開したLocal通信のquick（`.validation/audio-e2e-20261103-230313-300842`）で、`pcm16-16k-voicechat`だけ両方向とも復号直後の音声に0.7〜1.8%（最長20ms）の欠落が残った。受信packetの連番・収録時刻・到着間隔に欠けはなく、劣化のないPCM16でも復号直後に欠けるため、送信側のVAD・音声処理が発話区間を無音にしている可能性が高い。既定のAAC-ELD、Opus 24kHzは同じrunで欠落0。受信の待ち学習（`fb1d5524`ほか）とは独立の課題として、送信PCMの観測と、16kHz・voicechat profileでのVAD判定の再現から着手する。

### ファミリー共有と料金の再見積もり

2026-11-01の追加要望。家族利用と少人数通話を含めて費用を見直し、利益を過度に求めず、赤字を避けられる料金を決める。

| 課題 | 求める方針 | 完了条件 |
|---|---|---|
| 家族が使えるアプリ内課金にする | ファミリー共有を有効にし、家族で利用できることを前提にする | 商品別のApple対応・App Store Connect設定・StoreKit側の権利反映・復元を確認する。4人家族全員が利用するケースを受入と予算へ含める。4人全員が別々に購入する収入を前提にしない |
| MacとiOSの課金を共有する | Mac版もiOS版と同じアプリ内課金の共有でよい | OS別の二重購入を前提にせず、両OSで同じ購入・ファミリー利用権を認識・復元できる商品構成と運用を確認する。端末数・同時通信数の制限とは分ける |
| 少人数利用を含めて費用を見直す | 2人通話も相当数ある想定とし、グループ人数は平均4人を基準に見積もる | 2人通話、4人の平均ケース、4人家族全員の利用を比較する。平均4人という全体前提と2人通話を含めた分布・比率の置き方を明記し、従来の人数前提のまま金額だけ決めない |
| コストに見合う価格を決める | 利益重視にしすぎず、それでも絶対に赤字にならない程度のコスト見合いで課金額を決めたい | [既存の費用試算](../development/Cloudflare費用試算.md)を、家族共有・OS間共有・購入件数と実利用者数の差を含めて再計算する。利用時間、経路・通信量、基盤費用、販売手数料等の前提と上振れ時の余裕を明示し、原価・赤字を防ぐために必要な範囲・価格候補の根拠を示す。赤字回避に必要な利用量の想定範囲や費用上限も決め、価格だけで未定の利用量まで保証した扱いにしない |

既存設計には[週券は個人用・月額はファミリー共有](利用権とデータ保持の設計.md#購入の復元ユーザー切替とファミリー共有)という整理がある。今回の「家族で使える課金」の要望に対し、各商品の共有範囲・提供方式を照合して必要な見直しを行う。Appleで可能かを確認する前に、全商品が既に共有できるとも、週券は今後も必ず共有対象外とも決めない。購入の独自台帳を増やす解決を既定にしない。

価格・商品構成・平均人数の変更は本書への記録だけでは現行試算へ反映済みにならない。再見積もり時に前提・計算・価格候補を更新し、無料招待と24時間猶予による購入件数と利用量の差も含めて確認する。

## アカウント削除のサービス範囲と別端末への反映

**分類:** 機能。**状態:** 端末内の削除・再認証・server資格失効・Apple認可取消・稼働媒体回収は実装済み（[通信仕様](../spec/App/通信仕様.md#appleログインと端末内データ)）。削除対象の公開サービス範囲、同じ端末の別sessionと他の本人端末への反映は未完の判断・動作として残る。実Apple認証・実サービスの回収時間は[未確認事項](../validation/未確認事項.md#appleログインの実受入)で受け入れる。

- 仮置き：この端末に公開Internet資格がなければ「この端末のデータ削除」とApple手動解除を提供する。任意URLで別端末が使った未知サービスのアカウントまで発見できない。公開版のサービス固定・サービス履歴／再認証からの削除先解決を確定し、どこまで削除するかUIと契約を揃える。現在のLocal通話・開発用手動資格を削除機能のためだけにInternet登録へ強制移行しない。
- 同じ端末の保存領域を使う別sessionのサインアウト／削除は、前面復帰・背景開始操作とApple確認復帰時の再読込で反映し、保持済みの旧ログインを失効させる。すでに継続中の別プロセスへの即時通知、別の本人端末と共有済みの相手端末への反映は引き続き未完了。端末内の旧repository書戻し拒否と、遠隔の媒体・通知・招待権限失効は同じ完了条件ではない。通知・利用権は共通処理へ接続済みであり、これらについても別端末への削除反映と実サービスの受入を確認する。

接続先数については「公開版は公式サービス1つに固定し、手入力は開発・試用向けにするか」を確認中。暫定案は単一公式サービスとするが、既存の接続先切替はまだ変更していない。現在の削除は現在登録またはサインアウト時に退避した最後の登録が対象であり、過去に切り替えた複数サービスの一括削除ではない。公開版の接続先制約とログインの導線を揃えた後にこの残件を閉じる。複数サービスを提供する場合は、登録履歴・各サービスの削除結果・再認証を個別に保持する必要がある。

2026-11-02、実機で保存済みの相手との個別通話だけが近距離で繋がらない不具合を調べた。両端末が同じ個別通話IDを導出する一方、通信鍵をそれぞれ乱数で作っていたため、近距離の発見に使うgroupHashが一致せず、相手を別groupとして無視していた。同じ実機でgroup経由の通話は成立しており、Multipeer自体は動作している。連絡先の招待（`rideintercom://contact`）の完了時に、両端末が招待のgroup秘密から同じ鍵を導出して保存するよう修正した（[通信仕様](../spec/App/通信仕様.md)の「個別通話の完成」）。次の経路は未対応で、同じ食い違いが起こり得る。

| 経路 | 現在地・残作業 |
|---|---|
| 通常groupの招待で登録された相手 | 未解決。個別通話の鍵は各端末の乱数のまま。相手が個別通話の招待URLを受け入れた場合だけ一致する。group秘密は他の参加者も知るため、そこから個別通話の鍵を導出してよいかを決めてから対応する |

## 低帯域の推奨を決める

**分類:** 改善。**状態:** 手動候補（AACの48kHz・32kbpsと24kHz・16kbps、Opusの24／32kbps）は実装済み（[設定値一覧](../spec/App/Configuration/設定値一覧.md#aacの低帯域手動候補)、[Codec契約](../spec/packages/Audio/Codec.md)、[比較記録](../validation/history/低帯域codecの通信なし比較.md)）。既定48kbps・従来の品質推奨と波形判定は維持する。実ネットワーク量・聞き取り・電池に基づく推奨と最終受入が残る。Opusの8／12／16kbpsは実験では変換できており、追加候補として保持する。

| 課題 | 目的・範囲 | 状態・完了条件・確認点 |
|---|---|---|
| 低ビットレートでの通信を許容する | 通信量を抑えるため、低ビットレートによる音声波形の変化・劣化を許容できるようにする | 低帯域候補の実装は一部完了。実通信評価は未完。同じ入力・codec・周波数・音声処理条件でビットレートだけを変えて比較し、波形の崩れがビットレートの影響だけであることを確認する。通信なしのcodec往復と実通信の結果を照合し、音声処理や配送による欠落・不連続を低ビットレートの影響として扱わない。許容する範囲と確認方法は着手時に定める |
| 低帯域向けに48kHz・32kbpsと24kHz・16kbpsを選べるようにする | 端末の入出力は48kHzが多いという利用想定を踏まえ、通信状況に応じて32kbps、さらに厳しい場合は16kbpsを利用者が選べる候補を用意する | Appの選択候補は実装済み。効果・実適用値の受入は未完。数値は推奨値ではなく、codec・OSごとの対応と実適用値を確認する。端末入出力の実際の周波数と通信用の周波数を分け、48kHzと24kHz間の変換による影響・負荷も評価する。自動切替の実装は今回の要望として確定しない |
| 聞こえと実通信量から低帯域時の推奨下限を決める | 32kbps・16kbpsでも実通信では多い可能性があるため、電話・VoIPを参考にした8〜12kbps付近も含めて評価し、実用になる最も低い推奨値を探る | 未評価。比較候補の数値を対応済み・推奨済みと扱わず、発話の明瞭度・短い相槌・雑音下の聞き取り・連続性・遅延と、ヘッダー・暗号化・制御等を含む実際の通信量で判断する。最低選択可能値と推奨下限を区別し、条件により使えない値は明記する。値・codec・周波数は測定と試聴の後に決める |
| 現在の波形を維持できる推奨設定を残す | 現行品質を保つ推奨と、帯域節約のため劣化を許容する推奨を利用目的に応じて選べるようにする | 現行の設定・実適用値・基準波形・品質判定条件は[Codec仕様](../spec/packages/Audio/Codec.md)に保持。低帯域向けの追加によって置き換えたり合格基準を一律に緩めたりしない。周波数とbitrateを同時に変えた差をbitrateだけの影響と判断せず、変換・圧縮・配送・再生を分けて評価する |

2026-10-30の補足。冒頭の「24kHzで16bps」は、後続の「16kbps」に合わせ16kbpsとして記録した。32kbps・16kbps・8〜12kbps付近はいずれもこれから検証する候補であり、現行推奨の変更や最低値の確定ではない。[候補と評価の順序](機能拡張の実装前整理.md#低帯域向けの候補と推奨の決め方)を参照する。

## グループ名の自動生成

## 自分の声の分離を設定へ集約して録音テストにも適用する

2026-11-17の利用者要求。分類は機能・デザイン。今回はバックログへの記録のみ。自分自身の声を分離する送信側Voice Isolationを設定画面に持ち、Standard・Advanced両方の通話画面から操作を外す。両画面は同じ保存設定と実処理を使い、表示モードの切替で値を変えない。

録音テスト（Audio Check）にも同じ設定を適用し、通話で送る自分の声に分離を適用した結果を録音・再生で確認できるようにする。設定ON／OFFで実際の送信処理と録音テストの処理が一致すること、保存・再起動・画面モード切替後も一致すること、非対応環境の表示と実処理を確認する。設定項目が既に存在することだけで完了とせず、実録音・再生と通話の送信出力で受け入れる。

対象は自分の声の送信側分離であり、相手別・受信全体の声の分離を通話画面から外す要求には広げない。現行の[設定](../spec/App/UI/Settings.md)・[通話画面](../spec/App/UI/Call.md)を照合し、実装と同じ変更で仕様・マニュアルを更新する。表示名・配置・対応可否の説明は[デザイン引継ぎ](改善候補.md#自分の声の分離の設定と録音テスト)で追跡する。
