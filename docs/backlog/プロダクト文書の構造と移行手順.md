# プロダクト文書の構造と移行手順

2026-11-21の依頼を受けた移行設計。対象はRideComの用途、要求、デザイン、仕様、使い方、製品運用、検証、残課題。最初の移行対象は「呼び出し通知を無視する」。着手順と残作業は[移行課題](未実装課題.md#プロダクト文書を用途から探せる構造へ移す)で追う。

## 読む人が何を知りたいかで入口を作る

現状の[文書入口](../README.md)では、「目的から読む」より前に個別の検証履歴が6件並び、後半にはファイル一覧がある。[通信仕様](../spec/App/通信仕様.md)には通話・招待・削除の契約が同居する。「この通知を閉じると相手にどう見えるか」を知る人に、ファイル名や処理の所有者を先に選ばせる構成になっている。

移行後は文書入口の先頭で「使いたい・困っている」「何を満たすべきか」「今どう動くか」「何を確かめたか・何が残るか」を選べるようにする。利用者は操作の答えへ直接進める。複数の観点を比較する人は、[既存の用途別ストーリーマップ](../requirements/README.md#用途別のストーリーマップ)で同じ場面の要求・仕様・検証を並べて開ける。索引には質問とリンクを置き、仕様値や進捗は各リンク先で更新する。

| 知りたいこと | 移行後に本文を管理する場所 | 他の場所に残すもの |
|---|---|---|
| 誰が何のために使い、どの条件で何を達成できるべきか | requirements に採用済みの要求とその理由。用途別ストーリーマップを観点間の入口にする | design には利用者の立場、場面の順序、対象となる要求への参照 |
| どの画面で何を選べるか。一般向けと詳細表示の違いは何か | design に体験・判断理由・画面見本。spec/App/UI に現行画面の操作と状態 | 見本が先行していればデザイン残課題へ。HTMLの見本と画像は対応するデザインから開けるようにする |
| 操作の結果、何が保存・送信・表示されるか | spec/App に機能の契約。spec/packages は共有部品の入出力、spec/server はサーバー側の受付・配送・回収。既定値は既存の設定値一覧 | 画面・他の層は、自分が渡す入力・受け取る結果と所有元の節への参照を持つ |
| 利用者・運用者は何をすればよいか | manual に利用者の手順と失敗時の戻り方。development の製品運用手順にApple・Cloudflareの設定や復旧 | 利用者の手順はその場で読んで実行できる長さで完結させる。内部の設定契約と運用の根拠はリンクする |
| どこまで確認でき、何が残ったか | validation に条件・実測・未確認、backlog に変更や判断が必要な課題と全体の着手順 | 現行仕様から該当する観測へ結ぶ。history は日時・版・当時の条件を持つ証拠として保存する |

上の配置には既存のディレクトリを使う。長い仕様は、別の操作として独立して確認でき、更新する主体も異なる節から切り出す。例えば個人削除を切り出す場合、通話終了・保存・配送・受領のどの境界を扱うかを元の通信仕様に示す。単なる行数超過やOSの数を理由に同じ契約を分割しない。

### 探せる構造になったかを試す

最初の一件では、入口に全ファイルを再掲する方法と、目的と場面のリンクを先頭に置く方法を、次の三問で比較する。レビュー時は入口だけを開き、たどったリンク名、着いた見出し、その場で読めた答えを記録する。

| 読む人の質問 | 移行後にたどる道 | 合格とする答え |
|---|---|---|
| 利用者「呼び出しに入りたくない。相手に断ったと伝わる？」 | 文書入口 → 使い方 → 呼び出し通知の節 | 本文に自分の操作と相手への結果があり、仕様を開かずに判断できる |
| 実装をレビューする人「無視した端末から何を送る？」 | 文書入口 → 用途別ストーリーマップの通知の行 → App通知仕様の該当節 | 通知を閉じる動作・送り主への送信の有無を説明でき、同じ行から要求と照合できる |
| 試用を判断する人「ロックしたiPhone同士の復旧を確認できた？」 | 文書入口 → 検証状況 → 背景通話の該当項目 | シミュレータでの観測と、実機で確認済みの条件・残条件を区別できる |

索引をもう一枚作らず、[既存の目的別案内](../README.md#目的から読む)を先頭へ、現在の機能別リンクを用途別の行へ寄せる。入口で個別履歴を外すときは検証状況から同じ証拠に着けることを先に確かめる。上の三問は目標経路で、移行時に実際のリンクで受け入れる。

## 一つの操作ずつ移す

| 順番 | 担当者が行うこと | 次へ進める条件 |
|---|---|---|
| 1. 範囲を固定 | 最新mainのコミット、利用者の質問一つ、元ファイルと見出し、移行先、関連する要求・証拠を下の作業票に書く | 指定した節だけを読んで開始条件・操作・結果を説明できる |
| 2. 原文を照合 | 各記述を「維持」「同じ意味をまとめる」「履歴」「判断待ち」に分類する。本人と相手、期限と単位、例外・失敗、OS・版、検証環境を原文から抜き出す | 移行元の各条件に行き先が一つ以上あり、異なる効果を同一扱いしていない |
| 3. 本文を移す | 結果を定義する節へ根拠付きで寄せ、元の索引と利用者の手順をつなぎ直す。先に移動、次に同義文の統合を差分で分けて見せる | レビュー担当が元の節と新しい節を並べ、追加・削除・残した差を説明できる |
| 4. 実際に探す | 文書入口から元の質問に答え、仕様から要求・根拠へ戻る。参照、見本、検証記録の条件と結果を確認する | 検索語やソースコードを知らない読者が操作の対象と結果に到達し、実装済み・未確認・未実装を読み分けられる |
| 5. 小単位を閉じる | 差分・検査結果・未決事項と次の元見出しを記録し、その操作の変更だけをコミットする | 最新mainと統合した版で検査に通り、次担当が同じ作業票から続けられる |

### 似た文と矛盾した文を区別する

| 移行元で見つけた組合せ | 扱い方 |
|---|---|
| 同じ対象・条件・結果を、同じ読者に二度定義している | 所有元に本文を残し、もう一方はその節を参照する。利用者向けの「何もしなくても送り主には伝わらない」のように、その場の判断に必要な短い説明は残す |
| 同じ語でも操作や条件が違う | 一語でまとめず条件を分ける。例として「通知を無視する」と「招待を拒否する」は相手への効果を照合して別に扱う |
| 要求・実装・観測が食い違う | 各々の種類と出典を保つ。[グループ招待の7日と同期要求の28日](未実装課題.md#グループ招待の同期データの保存期限を要求に揃える)は、数値、起算点、受諾と配送の対象を別々に記録し、既存課題へ結ぶ。移行を理由にどちらかの値を採用しない |
| 要求同士が食い違う | 確定した判断と適用範囲を探す。[Watchの既定と明示オプション](未実装課題.md#watchはリモコンを既定にし通話を開発者向けオプションにする)のように条件を補う根拠があれば引用箇所を残す。根拠が定まらなければ両方の元見出し・誰がどの場面で困るか・判断すべき問いを既存課題か新規の一件に記録し、該当する文を保留する |
| 古い検証結果や見本に現在と異なる動作がある | 当時の版、端末、入力、結果をそのまま履歴に残す。現行動作へたどる入口を分ける。実機未確認と「試して失敗した」も区別する |

移行差分を読む人は、作業票の各行について元の条件が先の節から読み取れるかを逆向きにも確認する。見出しが残っていても「相手へ何も送らない」が消えたらその単位は未完了とする。

### 最初に渡す作業票

- **質問**　「呼び出しの『無視』を押すと、相手に断ったことが伝わるか」。[要求の通知行](../requirements/製品要求.md#利用者に提供すること)、[通知を放っておく場面](../design/操作の流れ.md#通知を放っておく)、[通知操作の実装契約](../spec/App/通知仕様.md#責務と入口)、[利用者の手順](../manual/使い方.md#通話の呼び出し通知を使う)の該当箇所を読む。
- **残す条件**　「無視」を押すと自分の通知が閉じ、送り主へ応答を送らない。何もしなくても応答は送られないが、通知を閉じる操作はしていない。「接続」を押した場合、グループへの参加招待を拒否する場合は別の操作として保つ。
- **提出物**　移行元の見出し／原文の条件／移行先の見出し／維持・統合・保留の理由／検査結果／次の一手を1行ずつ書く。実行中は下記の移動対応記録の該当行に置き、課題からその行を参照する。製品仕様の新しい一覧として並行管理しない。

試行後は、同じ手順を「招待・登録・削除」「待受・通話・音声・復帰」「端末別操作と設定」「本人確認・購入・復元」「製品の配布・運用」に適用する。各まとまりで最初に扱う操作は共通バックログの優先順に従う。仕様整理・デザイン整理で同じ節を移した場合は、その差分と受入結果をここから参照して一度で閉じる。

## 非フロンティアモデルに渡す指示と再開方法

移行を始める担当は `git -c core.quotePath=false ls-files docs` で基準版の対象を確認する。[既存の移動対応記録](../validation/文書整理記録.md)に今回用の区画を設け、対象の文書・見本・画像ごとに「未着手／一部／完了／判断待ち」と移行先を記す。一つのファイルに複数の役割があれば見出しまで分ける。現位置を保つ文書も「維持」と行き先を記載する。製品運用と開発環境の話が同居する場合は製品手順の節だけを対象にする。既存規約・スキルから参照される見出しは元のパスに残し、移す必要があれば旧見出しの下から新しい正本へ案内する。

担当するモデルには次の枠を埋めて渡す。必要な入力は小単位ごとに作り、過去のチャットを引き継ぐ必要はない。

> 対象は〈基準コミット、利用者の質問一つ〉。読む箇所は〈元のファイルと見出し、根拠の該当行〉。編集先は〈正本の節、参照元の節〉。残す条件は〈対象者・操作・相手への結果・例外〉。意味の違う文や根拠のない判断は原文を保持して保留理由を書く。提出するのは〈元→先の対応、差分、検査結果、残った問い、次に読む見出し〉。一つの質問で完了できなければ、残りの条件を作業票へ戻す。

初回の「無視」は上の記入例を使う。次担当には、別の問い「電波が一度切れて戻ると、自動切断の期限が延びるか」を渡す。[通話側の期限](../spec/App/通信仕様.md#自動切断タイマー)、[利用者の設定](../spec/App/UI/Settings.md#自動切断)、[OSごとの確認状況](../validation/未確認事項.md#自動切断の実os受入)が入力になる。期限の起点・復帰で延長しない条件・利用権の再開猶予との違いを回収する。移行を広げる前に、利用可能な非フロンティアモデルでこの一件を試し、渡した入力、モデル名、正しく保持できた条件、補足が必要だった箇所を記録する。補足が要ったら手順と入力例を直し、会話履歴のない状態で再試行する。

### 各単位の検査・中断・巻き戻し

1. 作業開始時に `git rev-parse HEAD` と `git status --short` を記録する。対象語と旧見出しを `rg -n -F '通話の呼び出し通知を使う' . --hidden -g '!.git'` のように検索する。改名時は旧パス・旧アンカー・HTMLのid・画像参照も調べる。外部に配ったリンクや保護対象の文書、スクリプトが固定パスを参照する場合は既存の入口を維持する。
2. 変更した相対リンクを呼び出し元のファイルから開き、期待した見出し・見本の該当箇所まで表示されることを確かめる。旧リンクを残す場合は旧入口からもたどる。Settingsの識別子一覧やバックログの課題見出しなど、検査が特定ファイルに期待する項目はその契約を保持する。
3. `python3 scripts/check_documentation.py`、`python3 -m unittest scripts.tests.test_documentation`、`git diff --check` を実行する。対象の差分と作業票を突き合わせ、消えた各条件の行き先、移動前後の見出し、三問のうち今回変えた経路をレビューに出す。
4. 統合直前にoriginとmainの更新を確認する。基準以降に同じ節が更新されていれば、その差を読み、作業票を更新して検査をやり直す。他担当の変更が解釈できない節は一旦保留し、独立した節を先に閉じる。
5. 中断時は最後に受け入れたコミット・未完の節・次の操作を作業票に記す。統合後に条件消失や参照切れが見つかった場合は後続の編集を確認し、その移行差分だけを取り消すか旧入口を復元して再検査する。全体完了時は基準版の一覧に移行中の追加・改名を照合し、対象全件の行き先と保留の担当課題を確認する。

## 設計段階の敵対的セルフレビュー

| 回・問い | 実際に照合した例と初案の問題 | 手順に反映した変更 |
|---|---|---|
| 1. 初めて読む人が入口で迷わないか | 現在の入口では目的別案内の前に履歴リンクが6件あり、ファイル名「使い方」を発見しても「無視」の答えに着けるかは分からない。分類の表だけでは改善を判定できなかった | 利用者・実装レビュー担当・試用判断者の三問に、入口からの経路と正答を設定。証拠への経路を先に作ってから履歴を入口から移す |
| 2. 似た語をまとめたとき重要な差が消えないか | 通知の「無視」と放置は送り主への効果は同じでも受取側の操作が違う。招待の7日と同期の28日、Watchのリモコン開始と音声開始は、多数決や新しい文の日付だけでは解決できない | 主体・条件・効果を逆向きに照合する手順を追加。要求、現行実装、当時の観測を分け、判断の出典がない箇所は保留にする |
| 3. 途中から別のモデルが作業し、検査だけ通して誤って完了にできないか | 一時ディレクトリで通常仕様の参照先見出しだけを改名した例を作った。旧アンカーが残っていても既存の文書検査はエラー0件。同じ節への並行編集や、作業票にない文書もこれでは見つからない | 見出し単位の実リンク確認、対象一覧との突合、基準コミットからの差分確認・復元手順を追加。次担当向けの記入枠と、別の題材による非フロンティアモデルでの試行を移行の受入に含めた |
