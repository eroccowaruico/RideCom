# バックログ

実装・修正・判断が残る課題の入口。今着手できる作業は[着手順](#着手順)、依存先や再開条件がある課題は[判断や再開を待つもの](#判断や再開を待つもの)を参照する。受入の条件と結果は検証文書を参照する。2026-11-20に改善候補と未実装の管理を統合し、採用前の案も一覧から漏らさず追う。

## 管理のしかた

採用済みの改善と未実装機能は、下の同じ着手順・再開待ちで選ぶ。他の担当から引き継ぐときも、用途と完了条件が一致する既存の行と詳細を更新する。[候補の採用・進捗・完了の共通ルール](../policies/文書作成規約.md#改善と未実装を同じバックログで扱う)

| 文書 | 置くもの | 置かないもの |
|---|---|---|
| 本書 | 全課題の順位・状態・次の一手を1行ずつ | 課題の詳細（リンク先に置く） |
| [課題と候補](未実装課題.md) | 改善・機能の未完了課題と採用判断待ちの案。状態・残作業・完了条件または採用条件を持つ | 完了済みの経緯だけの記録 |
| [旧改善候補の参照先](改善候補.md) | 既存リンクから統合後の詳細への参照 | 独立した課題・状態・順位の管理 |
| [画面実装とデザイン見本の差分](画面実装とデザイン見本の差分.md) | 残るデザイン判断と実画面の差。画面 → 部分 → 個々の差の階層 | 機能の契約（未実装課題に置く） |

| 場面 | 行うこと |
|---|---|
| 課題の単位 | 1課題は、利用者が目的を達成できる一連の操作、または1つの不具合とする。部品・API・テスト件数の増加だけを課題の完了としない |
| 課題を足す | 改善・機能は未実装課題へ、デザインは画面差分へ見出しを足す。見出しごとに着手順か判断・再開待ちのどちらかへ1行足す。採用から検討する案も同じ課題文書へ置き、判断・再開待ちの表で状態と次の判断を管理する |
| 課題が進んだ | 終わった作業を課題から外し、残る作業だけを残す。実態は[仕様](../spec/)へ、確認の結果は[検証の履歴](../validation/history/)へ、実機・実サービスの確認待ちは[未確認事項](../validation/未確認事項.md)へ置く。「済」を付けて残さない |
| 課題が終わった | 見出しと本書の行を外す。順位が変わるなら着手順を並べ直す |
| 基本順位を決める | コア体験の阻害・デグレ、重大な不確実性、依存関係と利用者価値を比べる。高重要度の候補は[重要度の重みと予測時間](../policies/開発方針.md#高重要度の候補を時間当たりの効果で選ぶ)で次の一手を比べる |

分類（改善・デザイン・機能）と規約の正本は[文書作成規約](../policies/文書作成規約.md#バックログの分類と全体優先順位)、デザイナーへの引継ぎ条件は[開発方針](../policies/開発方針.md#機能実装とデザイン判断の引継ぎ)。2026-11-17の整理で外した完了済みの経緯は[旧未実装課題の完了済み経緯](../development/history/旧未実装課題の完了済み経緯.md)に原文を保持する。

文書検査で、未実装課題（第2レベル）と画面差分（第3レベル）が一覧から1回ずつ参照されること、両表に分類・状態・次の行動があることを確認する。採用前の案も同じ一覧と課題文書で追う。区切りでは一覧と詳細を変更・検証の証拠に照合し、状態が変わった行と完了条件を更新する。

## 次に行う受入

以下は実環境を利用できる場合の受入順である。実装に今着手できる順は[着手順](#着手順)で管理する。

招待は、利用者が指定した順で[新しい相手へのグループ招待](../validation/未確認事項.md#新規相手招待の実環境受入)、次に[登録済みの相手へのグループ自動配送](../validation/未確認事項.md#登録済み相手へのグループ自動配送の実環境受入)を実環境で受け入れる。[実環境の設定と受入順](../development/Cloudflare試用手順.md#利用者が行うapplecloudflareの設定と受入順)

実機を使える最初の区切りで、[近距離とInternetの背景通話8条件](../validation/未確認事項.md#ios背景実行の調査と受入マトリクス)を進める。まずマイクOFF・受話なしの待機後の発話と実経路断からの自動復旧を同じ通話で確認し、実出力の時刻を[Diagnosticsの処理順・分岐・状態](../validation/未確認事項.md#画面デザインの実環境受入)と照合する。

個人削除は実機が揃った区切りで、[近距離](../validation/未確認事項.md#近距離の個人削除の実機受入)と[Internet](../validation/未確認事項.md#internetの個人削除の実環境受入)を確認する。双方が先に削除した場合も同じ手順に含める。

## 着手順

**意味の全体修復の個別指定（2026-11-21）:** 画面・文書ですでに短縮・圧縮により意味を失った表現の総点検と修正を最重要の一つとする。異なるモデルを少なくとも3種類使って最低3回レビューし、重要指摘の全対応まで閉じる。五つの定期整理の末尾へ追加して待たせる課題ではない。

**archiveの最優先指定（2026-11-21）:** AIの通常コマンドからの署名付きarchiveをOrganizerへ追加できるか確認し、可能なら現在の小単位を安全に閉じた次に対応する。認識・選択の実受入と手順整備まで閉じたら個別指定を解除する。登録だけでは配布送信しない。

2026-11-21に指定された五つの最重要課題は、下表の順で[全体整理のサイクル](../policies/開発方針.md#全体整理のサイクル)の初回に扱う。各課題を受け入れたら完了分を一覧から外す。以降の周回は作業記録に残した次の主題から再開する。

招待の起動・保存・返信・取消・失敗後の再試行と共有の画面照合を終え、実環境の受入は上記の順で行う。実機を待つ間は、要求者が重みを置いた既定設定・Standardの主要操作・診断・音声処理を、利用への影響と次の区切りまでの所要時間で比べて進める。[招待の指定の経緯](../development/history/バックログの優先順位と進捗の記録.md#build-1520の優先順位と残課題の照合)

2026-11-21の要求者の再指定により、Watchの扱い変更を高優先度で先頭へ置く。もともと早期対応を求めていた指示の再確認であり、使えない機能を残さないため、現在の小さな作業を安全に閉じた次の区切りで着手する。Watch音声の実験再開・音声完成や実機待ちを、この既定動作の変更の着手条件にしない。設定移動とリモコン既定化が完了したら、この個別優先指定を閉じ、残課題の基本順位を見直す。

2026-11-21の追加指定により、Watchのリモコン全機能がiPhoneのロック・背景中も成立する根拠を先に確認し、Watchをリリースするか判断する。根拠が揃わなければ当面非提供でよく、リモコン既定化だけでリリース可能とはしない。これをWatchの残る設定・画面整備より先の高重要度課題とする。[配布見送り中の設定](../validation/history/AppleWatch実機への導入とXcode起動.md#watch設定を表示する端末)は反映済み。Watch音声実験の中断は継続する。

2026-11-21の追加指定により、要求と実装、同じ操作の導線・効果、表示と実状態、OS間の同じ契約が食い違う課題を優先する。Watchの採否判断・既定化を先頭に保ち、コア音声を壊す処理、招待経路による鍵の違い、削除・除外後の状態不一致、主要操作や画面幅による機能喪失、通知先・表記の不一致を上位へ並べ直した。単なる新機能・配色や余白の好みと同列にしない。候補や未確認を確認済みの不具合と断定せず、まず差を確認できる最小経路を通す。テスト分類の高い品質重要度も維持する。

依存・実機待ちがある高重要度の課題は、その理由と次に動かせる単位を保持する。とくに双方背景の切断・復旧と、削除・除外に対応する確認表示は低優先度へ落としたものではない。実装・実機条件が揃った最初の区切りで関連する動作と表示を一緒に照合する。変更の意図・効果が揃った課題は、この優先指定を外して基本順位を再評価する。完了したものを高優先度のまま残さない。

[用途と要求の横断点検](../development/history/バックログの優先順位と進捗の記録.md#2026-11-21の用途と要求の横断点検)では、登録そのものが完了しない条件、移動後も招待や削除が届かない条件、週をまたいだ同期、停車中の音声操作の順に今回の課題を置いた。

着手時は明示指定と依存を確かめ、上位候補を[重要度の重みと予測時間](../policies/開発方針.md#高重要度の候補を時間当たりの効果で選ぶ)で比較する。選択が変われば行を並べ直す。Watchの非提供表示とiPhone受話遅延を比較した[11月21日の判断](../development/history/バックログの優先順位と進捗の記録.md#watchの提供表示とiphoneの受話遅延を時間当たりの効果で比較する)を参照する。[ビルド番号に応じた見直し](../policies/開発方針.md#ビルド番号で決まる定期作業)と[20コミットごとのコードと文書の整理](../policies/開発方針.md#20コミットごとのコードと文書の整理)を適用する。過去の判断・検証の推移は[バックログの履歴](../development/history/バックログの優先順位と進捗の記録.md)を参照する。
