# バックログ

実装・修正・判断が残る課題の入口。今着手できる作業は[着手順](#着手順)、依存先や再開条件がある課題は[判断や再開を待つもの](#判断や再開を待つもの)を参照する。受入の条件と結果は検証文書を参照する。2026-11-20に改善候補と未実装の管理を統合し、採用前の案も一覧から漏らさず追う。

## 管理のしかた

別の利用者の体験にも関わる課題は、[関連する要求を結ぶ規約](../policies/文書作成規約.md#関連する要求と影響を受ける利用者を結ぶ)に従い、詳細から相手側の要求と課題をたどれるようにする。

採用済みの改善と未実装機能は、下の同じ着手順・再開待ちで選ぶ。他の担当から引き継ぐときも、用途と完了条件が一致する既存の行と詳細を更新する。[候補の採用・進捗・完了の共通ルール](../policies/文書作成規約.md#改善と未実装を同じバックログで扱う)

| 文書 | 置くもの | 置かないもの |
|---|---|---|
| 本書 | 全課題の順位・状態・次の一手を1行ずつ | 課題の詳細（リンク先に置く） |
| [課題と候補](未実装課題.md) | 改善・機能の未完了課題と採用判断待ちの案。状態・残作業・完了条件または採用条件を持つ | 完了済みの経緯だけの記録 |
| [旧改善候補の参照先](改善候補.md) | 既存リンクから統合後の詳細への参照 | 独立した課題・状態・順位の管理 |
| [画面実装とデザイン見本の差分](画面実装とデザイン見本の差分.md) | 残るデザイン判断と実画面の差。画面 → 部分 → 個々の差の階層 | 機能の契約（未実装課題に置く） |
| [利用権とデータ保持の設計](利用権とデータ保持の設計.md)、[機能拡張の実装前整理](機能拡張の実装前整理.md) | 実装前に決めた条件と調査結果の設計記録。課題から参照する | 作業の一覧・順位（本書と未実装課題に置く） |

| 場面 | 行うこと |
|---|---|
| 課題の単位 | 1課題は、利用者が目的を達成できる一連の操作、または1つの不具合とする。部品・API・テスト件数の増加だけを課題の完了としない |
| 課題を足す | 改善・機能は未実装課題へ、デザインは画面差分へ見出しを足す。見出しごとに着手順か判断・再開待ちのどちらかへ1行足す。採用から検討する案も同じ課題文書へ置き、判断・再開待ちの表で状態と次の判断を管理する |
| 要求が確定した、または優先順位が変わった | 要求・着手順・課題の詳細を揃える。以前の候補や設計資料から現行課題へリンクする |
| 次の作業を選ぶ | 優先指定を前回の実績と照合する。最優先課題を後に回すときは、先行する作業へリンクする。優先する理由と再開条件を記す。待たずにできる作業も示す |
| 課題が進んだ | 終わった作業を課題から外し、残る作業だけを残す。実態は[仕様](../spec/)へ、確認の結果は[検証の履歴](../validation/history/)へ、実機・実サービスの確認待ちは[未確認事項](../validation/未確認事項.md)へ置く。「済」を付けて残さない |
| 課題が終わった | 見出しと本書の行を外す。順位が変わるなら着手順を並べ直す |
| 基本順位を決める | コア体験の阻害・デグレ、重大な不確実性、依存関係と利用者価値を比べる。高重要度の候補は[重要度の重みと予測時間](../policies/開発方針.md#高重要度の候補を時間当たりの効果で選ぶ)で次の一手を比べる |
| 一時・個別の優先指定を適用する | 指定者・対象・理由・適用する作業や利用場面・見直し条件を対象行または表の導入に添え、該当範囲の着手順に反映する。指定解除後は基本順位で再評価する。[基本順位と依頼ごとの優先指定](../policies/文書作成規約.md#基本順位と依頼ごとの優先指定) |

分類（改善・デザイン・機能）と規約は[文書作成規約](../policies/文書作成規約.md#バックログの分類と全体優先順位)、デザイナーへの引継ぎ条件は[開発方針](../policies/開発方針.md#機能実装とデザイン判断の引継ぎ)。2026-11-17の整理で外した完了済みの経緯は[旧未実装課題の完了済み経緯](../development/history/旧未実装課題の完了済み経緯.md)に原文を保持する。

文書検査で、未実装課題（第2レベル）と画面差分（第3レベル）が一覧から1回ずつ参照されること、両表に分類・状態・次の行動があることを確認する。採用前の案も同じ一覧と課題文書で追う。区切りでは一覧と詳細を変更・検証の証拠に照合し、状態が変わった行と完了条件を更新する。

## 次に行う受入

以下は実環境を利用できる場合の受入順である。実装に今着手できる順は[着手順](#着手順)で管理する。

本番のネット通話と呼び出し通知を最初に受け入れる。続いて、声の分離、Advancedの送受信診断、近距離の音の途切れを確認する。各項目で手元の検証から始める。依頼者の報告により[TestFlight公開とITMS-90683](../validation/history/配布ビルド採番とOrganizer認証調査.md#testflight公開とitms-90683の完了)は完了。圏外の近距離通話、ロック中の復旧、通知・招待は[機能ごとの検証一覧](../validation/未確認事項.md#testflightのネット通話通知招待の受入)から確認する。

背景通話は[近距離とInternetの背景通話8条件](../validation/未確認事項.md#ios背景実行の調査と受入マトリクス)で残る確認を管理する。マイクOFF・受話なしの待機後の発話と経路断からの自動復旧を同じ通話で確かめ、実出力の時刻を[Diagnosticsの処理順・分岐・状態](../validation/未確認事項.md#画面デザインの実環境受入)と照合する。

個人削除の検証条件は[近距離](../validation/未確認事項.md#近距離の個人削除の実機受入)と[Internet](../validation/未確認事項.md#internetの個人削除の実環境受入)で管理する。双方が先に削除した場合も同じ手順に含める。

## 着手順

[ローカルmainの未送信履歴](#ローカルmainの未送信履歴を解消する)の復旧中は、台帳の更新後も[作業を切り替える前の確認](../policies/開発方針.md#作業を切り替える前の確認)で引き継いだ製品差分と共有先を照合する。復旧の区切りが成立してから、到来済みの定期作業を1件ずつ完了させ、その是正を共有するたびに同期状態を確認する。

進行中はローカル・クラウドで合わせて1件とする。担当交代時は既存の作業記録から、共有mainに反映済みの変更と今の1件の残作業を確認する。通常作業を選ぶ前に、[節目の完了条件](../policies/開発方針.md#節目の目的と成果の確認)を確認する。[全体監査の引き継ぎ](../development/history/バックログの優先順位と進捗の記録.md#進行中の全体監査の引き継ぎ)で、その回の調査が終了したかと、次の作業に関係する保留条件を確認する。同じ区切りの定期作業がすべて完了したら、以下の着手順に戻る。

### 未完の定期作業

到来した回と未完の有無は、共有mainを取得してから `python3 scripts/check_periodic_work.py` で確認する。各回の結果は[定期作業の受入記録](../development/history/定期作業の受入.tsv)からたどる。

Build 1800から滞っていた全体整理は、2026-11-23の依頼に従って2周を終えた。通常の周期に戻り、2,520コミットの回でデザイン資料とユースケースを整理し、通常換算2460ビルドの回でテスト全体の点検を終えた。[2周の完了](../development/history/バックログの優先順位と進捗の記録.md#第2周のテスト全体と2周の整理を受け入れる)・[デザイン資料とユースケースの完了](../development/history/バックログの優先順位と進捗の記録.md#2520コミットのデザイン資料とユースケースを受け入れる)・[通常周期のテスト全体の完了](../development/history/バックログの優先順位と進捗の記録.md#通常換算2460ビルドのテスト全体の整理を受け入れる)

通常換算2520ビルドのコード全体整理、2580ビルドの仕様全体整理、[2640ビルドのコード全体の再整理](../development/history/バックログの優先順位と進捗の記録.md#通常換算2640ビルドのコード全体の再整理を受け入れる)を受け入れた。次の全体整理の主題は、デザイン資料とユースケース。[コード全体の整理](../development/history/バックログの優先順位と進捗の記録.md#通常換算2520ビルドのコード全体整理を受け入れる)・[仕様全体の整理](../development/history/バックログの優先順位と進捗の記録.md#通常換算2580ビルドの仕様全体整理を受け入れる)

### 定期作業を完了した後の通常作業

Macのミュート待機と後参加、双方向の受信、終了後の回収は、作り直した固定Previewの実中継で確認した。端末登録が止まる不具合を修正した[Mac Release Build 2859](../validation/実機確認待ち.md#端末登録が止まる不具合の修正版をmac-build-2859で用意する)で、本番の接続先と署名を照合した。Macの試験用アカウントの端末資格で稼働状態を照会し、別のアカウントとの双方向再生まで確かめる。Sandbox通知は非公開の標準Workerで送信を予行した。実配置では専用Workerを作成できる認証が必要。実APNsの応答とトレースを確認してから、通知先登録と端末への到着を試す。[実中継の結果](../validation/history/iOS音声E2Eと通話障害修復.md#固定previewの実中継でmacの後参加と終了を確かめる)・[Sandboxの配置確認](../validation/history/Cloudflare検証.md#専用workerを作成できる権限を確かめる)

進行中の作業に必要な実機試験の準備は、最新の実機確認待ちに合わせて同じ作業の中で更新する。[TestFlightと同じ端末での試験準備](未実装課題.md#testflightと同じ端末で実機試験に備える)

**最優先は、本番のネット経由で通話が成立することと、サンドボックス・本番で呼び出し通知が相手に届くこと（2026-11-25の依頼者指定）。** まず本番で入室から双方向の再生までを確かめる。通知は環境ごとに受信と「接続」の結果を確認する。既存のビルドで試せる項目は先に進める。新しい配布版が必要なら、[現行ビルドの内部試用判定](未実装課題.md#現行ビルドの音声を判定し条件を満たせば内部testflightに出す)をその準備として行う。条件を満たしたビルドは定期Archiveを待たずに出す。

音声の詳細な比較と声の分離は、通話・通知の成立に必要な範囲から扱う。音声の試験は対応する組み合わせを揃え、通話品質の受入ではAACの合格を優先する。受信側の声の分離も効いていなければ、送信側と同時に直す。Advancedの診断と近距離の音の途切れも[着手順](#着手順)で追う。

**Cloudflareと開発環境の移行を早めに進め、iCloud自動保存と端末復元も優先する（2026-11-24の依頼者指定）。** ネット通話の復旧に必要なCloudflareの差分は復旧と一緒に扱う。端末鍵の検証から始め、自動保存と復元を実装し、再招待なしで既存の相手と通話できるところまで進める。[優先順位を変更した経緯と関連課題](未実装課題.md#要求を記録してから実装を最優先にするまで)

**招待の個別調整より先に、機能ごとにどのログインアカウントを使うかを照合する。** 招待の再送やバックグラウンドでの送信を一件直しても、アカウントがすべて一致する試験では、返信の宛先を取り違えても見逃す。[3つのアカウントを切り替える共通の確認条件](機能拡張の実装前整理.md#3つのアカウントを切り替えて関連する機能を確かめる)に沿って、対象の変更を既存の仕様・試験と照合する。切替で期待結果が分かれるのに証拠が足りない箇所を先に試し、結果に応じて個別の修正を選ぶ。

招待の試用はネット通話の復旧後に行う。端末操作が必要な場合は[実機試験の手順](../policies/開発方針.md#実機試験をいつでも始められるようにする)に従って担当者が行う。

**意味の全体修復の個別指定（2026-11-21）:** 画面・文書ですでに短縮・圧縮により意味を失った表現の総点検と修正を最重要の1つとする。異なるモデルを少なくとも3種類使って最低3回レビューし、重要指摘の全対応まで閉じる。5つの定期整理の末尾へ追加して待たせる課題ではない。

**署名付きArchiveの優先確認（2026-11-21）。** Organizerの一覧表示は確認済み。署名検証済みのiOSとMacのArchiveを一覧から選び、詳細を照合する確認が残る。新たに作成する場合は[標準のArchive手順](../development/開発環境.md#xcode標準のバージョン管理とarchive)に従い、Xcodeの日付フォルダに直接保存する。[Organizerで残る確認](../validation/未確認事項.md#organizerで署名付きarchiveを選んだ後の詳細を照合する)

招待の起動・保存・返信・取消・失敗後の再試行と共有の画面照合を終え、実環境の受入は上記の順で行う。実機を待つ間は、要求者が重みを置いた既定設定・Standardの主要操作・診断・音声処理を、利用への影響と次の区切りまでの所要時間で比べて進める。[招待の指定の経緯](../development/history/バックログの優先順位と進捗の記録.md#build-1520の優先順位と残課題の照合)

2026-11-21の追加指定により、Watchのリモコン全機能がiPhoneのロック・背景中も成立する根拠を先に確認し、Watchをリリースするか判断する。根拠が揃わなければ当面非提供でよく、リモコン既定化だけでリリース可能とはしない。これをWatchの残る設定・画面整備より先の高重要度課題とする。[配布見送り中の設定](../validation/history/AppleWatch実機への導入とXcode起動.md#watch設定を表示する端末)は反映済み。Watch音声実験の中断は継続する。

2026-11-21の追加指定により、要求と実装、同じ操作の導線・効果、表示と実状態、OS間の同じ契約が食い違う課題を優先する。Watchでは採否判断が既定化に先行する。コア音声を壊す処理、招待経路による鍵の違い、削除・除外後の状態不一致、主要操作や画面幅による機能喪失、通知先・表記の不一致も、基本順位で先に扱う。単なる新機能・配色や余白の好みと同列にしない。候補や未確認を確認済みの不具合と断定せず、まず差を確認できる最小経路を通す。テスト分類の高い品質重要度も維持する。

依存・実機待ちがある高重要度の課題は、その理由と次に動かせる単位を保持する。とくに双方背景の切断・復旧と、削除・除外に対応する確認表示は低優先度へ落としたものではない。実装・実機条件が揃った最初の区切りで関連する動作と表示を一緒に照合する。変更の意図・効果が揃った課題は、この優先指定を外して基本順位を再評価する。完了したものを高優先度のまま残さない。

[用途と要求の横断点検](../development/history/バックログの優先順位と進捗の記録.md#2026-11-21の用途と要求の横断点検)では、登録そのものが完了しない条件、移動後も招待や削除が届かない条件、週をまたいだ同期、停車中の音声操作の順に今回の課題を置いた。

着手時は明示指定と依存を確かめ、上位候補を[重要度の重みと予測時間](../policies/開発方針.md#高重要度の候補を時間当たりの効果で選ぶ)で比較する。選択が変われば行を並べ直す。Watchの非提供表示とiPhone受話遅延を比較した[11月21日の判断](../development/history/バックログの優先順位と進捗の記録.md#watchの提供表示とiphoneの受話遅延を時間当たりの効果で比較する)を参照する。[ビルド番号に応じた見直し](../policies/開発方針.md#ビルド番号で決まる定期作業)と[コードと文書の定期整理](../policies/開発方針.md#コードと文書の定期整理)を適用する。過去の判断・検証の推移は[バックログの履歴](../development/history/バックログの優先順位と進捗の記録.md)を参照する。
