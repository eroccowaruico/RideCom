これから作るもの・直すもの・判断するものの入口。作業を選ぶときは本書の[着手順](#着手順)だけを見る。順位を持つ表は本書だけに置き、他の文書には順位を書かない。

| [改善候補](改善候補.md) | 未採用の案と判断待ちの事項。採用・再開の条件を持つ | 採用して着手する作業 |

| 場面 | 行うこと |
|---|---|

| 課題を足す | 採用済みなら未実装課題へ見出しを足し、本書の着手順へ1行足す。未採用・判断待ちなら改善候補へ足し、本書の[判断や再開を待つもの](#判断や再開を待つもの)へ必要な場合だけ足す |
| 課題が進んだ | 終わった作業を課題から外し、残る作業だけを残す。実態は[仕様](../spec/)へ、確認の結果は[検証の履歴](../validation/history/)へ、実機・実サービスの確認待ちは[未確認事項](../validation/未確認事項.md)へ置く。「済」を付けて残さない |

| 順位を変える | 利用者が明示した順、コア体験の阻害・デグレ、重大な不確実性、依存関係と利用者価値で比べ、本書の表だけを直す |

## 着手順

各小単位に加えbuild no.が10進む区切りで、利用用途への重要度を見直す。同程度に重要な候補は、効果と必要時間を比較して選ぶ。2026-11-18は1080から1090の区切りで初回マイク許可を優先した。2026-11-19は1090から13進んだ1103で再確認した。音声の途切れ・遅延を対象に含める。最優先は操作直後のロック・他アプリ移行を含む双方背景での通話開始・維持・復旧。双方をロックする受入には二台の実機が必要で準備待ち。実機なしで進められる候補では、見込み約15〜25分の接続開始多重通知を先に選んだ。局所回帰と同じ実App音声試験で、両端の発行を約1500回から各1回に抑えた。次は音声品質を通信なしの既存測定から切り分け、初回を約30〜60分に絞る。候補が絞れた後に必要な実出力だけを再測定する。次の区切りは1113。背景の実環境確認は実機準備待ち。音声欠落は製品と同じ受信設定のローカル試験で復号後から出力までに絞れたため、同じ到着順をAudioMixerで再現する短い試験（見込み15〜30分）を先に選ぶ。利用者の招待導線の改善は画面設計と実画面の受入が必要で、媒体の原因確定と独立の単位に置く。この確認時の基準は1113。

1113から10進んだ1123で再確認した。双方をロックした通話は利用用途への影響が最も大きく、2台の実機受入が残る。新規相手と登録済み相手への招待はローカルで作成から受領まで確認済みで、グループ内の入口と未完了表示は実画面・Markdown・HTMLの調整が残る（見込み30〜60分）。通信を外した20ms／100msの欠落は修正し、現在の近距離両方向で既定AACとPCM16 16kHzの欠落を観測しなかった。既定AACの片方向の遅延が判定余裕込み132.08msで、通常設定の会話に影響する。既存の音声E2Eで復号後から実描画までを先に計測し、8〜15分を目安に減らせる待ちの有無を判断する。16kHzの別設定の遅延と招待画面の改善は独立して追う。次回の重要度チェックの基準は1123とする。

1127の区切りで、既定AACは通信を外しても判定余裕込み127.40ms、送信音声分離ON/OFFの出力差は55.64msと分かった。再生キューだけを縮める採否の根拠には欠け、音声分離を維持できる候補の前後比較が必要。次の独立単位は、未接続のグループ画面から同じ招待へ入り、未完了の相手を見分けるStandardの実画面（見込み25〜40分）。利用者が報告した招待上の行き詰まりを既存の実UI試験で再現・検証できるため、追加の音声方式の比較より先に進める。

1123から15進んだ1138で再確認した。双方ロックの開始・待ち・再接続は2台の実機受入が必要。Standardのグループ招待で保存した相手を開き直せるようにし、OS共有のプレビューが未送信状態を変えていた問題も修正した。次は同じ誤表示が残る旧形式の個人招待を、共通の共有完了処理で改める最小単位（見込み15〜25分）。既定AACの音声分離を保つ低遅延案の比較（見込み30分以上）と、Advancedの追加状態表示はその後の独立単位とする。次回の重要度チェックの基準は1138。

1142の区切りで、旧形式の個人招待は共有取消・コピー・再起動をiPhone Simulatorで確認した。次はAdvancedのGroup Settingsで、新しい相手ごとに未共有・共有済みを保存記録の値から見分け、同じ詳細へ進めることを確認する（見込み15〜25分）。招待の流れを揃えるという利用者の優先指示に従い、既定AACの低遅延案の比較より先に進める。10ビルドごとの重要度チェックの基準は1138を維持する。

1145の区切りで、AdvancedのGroup Settingsは共有前・取消後・コピー後・返信後を確認した。次は登録済み相手への招待を保存した直後に背景へ移る経路を優先する。現行の配送処理はSwift Taskで開始し、iOSの有限な背景実行時間を先に取得していない。保存直後の送信と期限切れ後の再試行を確かめる最小単位（見込み25〜35分）とする。操作直後のロックという必須条件に直接関わり、2台の実機を待つ間も局所検証できるため、既定AACの比較より先に進める。重要度チェックの基準は1138を維持する。

1138から10進んだ1148で再確認した。双方ロックでの通話の開始・待ち・再接続は、近距離とInternetの両方で引き続き最優先の実機受入。登録済み相手への招待は、保存直後の有限な実行時間を要求し、時間切れから同じ配送を再試行できるようになった。次は受諾直後の個人招待の返信を優先する。現在は背景移行で有限な返信sessionも直ちに停止する。相手が応答可能な状態で「登録」直後に背景へ移り、保持した同じ返信をOSの実行時間内に届けられるかを最小単位とする（見込み25〜35分）。利用者の最後の操作に直接関わり、試行できる条件を分離できるため、既定AACの低遅延候補の比較（見込み30分以上）より先に進める。次回の重要度チェックの基準は1148。

1151の区切りで、明示登録後の返信をOSの時間内に続け、時間切れでも同じ返信を再開できることをApp試験で確認した。招待と通話の実機受入を待つ間は、既定AACで音声分離を維持し、再生開始の実I/O周期と先行時間の関係を短い実音声試験で切り分ける（見込み20〜30分）。判定余裕込み125msと音声の連続性を基準にする。10ビルドごとの重要度チェックの基準は1148を維持する。

1152の区切りで、既定AACの実I/O周期は2.67msから1.33msに変わったが、収録callbackは10.67ms、判定余裕込みの出力は127.40msだった。I/O周期変更で改善が得られなかったため、音声分離を保つ別の低遅延候補は処理段階を先に絞る必要がある（見込み30分以上）。先に、押した直後の操作を遅らせる可能性があるiOSの音声session操作のRuntime Warningを現行SDKと既存Setting試験で照合する最小単位（見込み15〜25分）。10ビルドごとの重要度チェックの基準は1148を維持する。

## 判断や再開を待つもの

着手順に入れず、条件が満たされたら着手順へ移す。

| 待っているもの | 待つ理由 | 再開の条件 | 詳細 |
|---|---|---|---|
| Watch音声の会話E2E | 2026-11-02の利用者指示で追加実験を停止 | 利用者の再開指示 | [Watch音声（中断中）](未実装課題.md#watch音声中断中) |
| 設定のグループの切れ目 | 標準の間隔では見本どおりにできず、デザインの判断が要る | 見本を通常の間隔にするか、並びを変えるかの決定 | [設定の主画面](画面実装とデザイン見本の差分.md#主画面) |
| 長押しから設定を開く導線 | 対象箇所と操作の採用判断が必要 | スワイプ等の現行導線を照合し、見つけやすさ・誤操作・アクセシビリティを確認して対象を決める | [長押し設定の検討](改善候補.md#長押しから設定を開く導線の検討) |
