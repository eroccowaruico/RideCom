# バックログ

これから作るもの・直すもの・判断するものの入口。作業を選ぶときは本書の[着手順](#着手順)だけを見る。順位を持つ表は本書だけに置き、他の文書には順位を書かない。

## 管理のしかた

| 文書 | 置くもの | 置かないもの |
|---|---|---|
| 本書 | 全課題の順位・状態・次の一手を1行ずつ | 課題の詳細（リンク先に置く） |
| [未実装課題](未実装課題.md) | 採用済みで残っている作業。1見出しが1課題で、残る作業・完了条件・決定済みの条件を持つ | 実装済みの経緯、未採用の案 |
| [改善候補](改善候補.md) | 未採用の案と判断待ちの事項。採用・再開の条件を持つ | 採用して着手する作業 |
| [画面実装とデザイン見本の差分](画面実装とデザイン見本の差分.md) | 実画面とHTML見本の差。画面 → 部分 → 個々の差の階層 | 機能の契約（未実装課題に置く） |
| [利用権とデータ保持の設計](利用権とデータ保持の設計.md)、[機能拡張の実装前整理](機能拡張の実装前整理.md) | 実装前に決めた条件と調査結果の設計記録。課題から参照する | 作業の一覧・順位（本書と未実装課題に置く） |

| 場面 | 行うこと |
|---|---|
| 課題の単位 | 1課題は、利用者が目的を達成できる一連の操作、または1つの不具合とする。部品・API・テスト件数の増加だけを課題の完了としない |
| 課題を足す | 採用済みなら未実装課題へ見出しを足し、本書の着手順へ1行足す。未採用・判断待ちなら改善候補へ足し、本書の[判断や再開を待つもの](#判断や再開を待つもの)へ必要な場合だけ足す |
| 課題が進んだ | 終わった作業を課題から外し、残る作業だけを残す。実態は[仕様](../spec/)へ、確認の結果は[検証の履歴](../validation/history/)へ、実機・実サービスの確認待ちは[未確認事項](../validation/未確認事項.md)へ置く。「済」を付けて残さない |
| 課題が終わった | 見出しと本書の行を外す。順位が変わるなら着手順を並べ直す |
| 順位を変える | 利用者が明示した順、コア体験の阻害・デグレ、重大な不確実性、依存関係と利用者価値で比べ、本書の表だけを直す |

分類（改善・デザイン・機能）と規約の正本は[文書作成規約](../policies/文書作成規約.md#バックログの分類と全体優先順位)、デザイナーへの引継ぎ条件は[開発方針](../policies/開発方針.md#機能実装とデザイン判断の引継ぎ)。2026-11-17の整理で外した完了済みの経緯は[旧未実装課題の完了済み経緯](../development/history/旧未実装課題の完了済み経緯.md)に原文を保持する。

## 着手順

各小単位に加えbuild no.が10進む区切りで、利用用途への重要度を見直す。同程度に重要な候補は、効果と必要時間を比較して選ぶ。2026-11-18は1080から1090の区切りで初回マイク許可を優先した。2026-11-19は1090から13進んだ1103で再確認した。音声の途切れ・遅延を対象に含める。最優先は操作直後のロック・他アプリ移行を含む双方背景での通話開始・維持・復旧。双方をロックする受入には二台の実機が必要で準備待ち。実機なしで進められる候補では、見込み約15〜25分の接続開始多重通知を先に選んだ。局所回帰と同じ実App音声試験で、両端の発行を約1500回から各1回に抑えた。次は音声品質を通信なしの既存測定から切り分け、初回を約30〜60分に絞る。候補が絞れた後に必要な実出力だけを再測定する。次の区切りは1113。背景の実環境確認は実機準備待ち。音声欠落は製品と同じ受信設定のローカル試験で復号後から出力までに絞れたため、同じ到着順をAudioMixerで再現する短い試験（見込み15〜30分）を先に選ぶ。利用者の招待導線の改善は画面設計と実画面の受入が必要で、媒体の原因確定と独立の単位に置く。この確認時の基準は1113。

1113から10進んだ1123で再確認した。双方をロックした通話は利用用途への影響が最も大きく、2台の実機受入が残る。新規相手と登録済み相手への招待はローカルで作成から受領まで確認済みで、グループ内の入口と未完了表示は実画面・Markdown・HTMLの調整が残る（見込み30〜60分）。通信を外した20ms／100msの欠落は修正し、現在の近距離両方向で既定AACとPCM16 16kHzの欠落を観測しなかった。既定AACの片方向の遅延が判定余裕込み132.08msで、通常設定の会話に影響する。既存の音声E2Eで復号後から実描画までを先に計測し、8〜15分を目安に減らせる待ちの有無を判断する。16kHzの別設定の遅延と招待画面の改善は独立して追う。次回の重要度チェックの基準は1123とする。

1127の区切りで、既定AACは通信を外しても判定余裕込み127.40ms、送信音声分離ON/OFFの出力差は55.64msと分かった。再生キューだけを縮める採否の根拠には欠け、音声分離を維持できる候補の前後比較が必要。次の独立単位は、未接続のグループ画面から同じ招待へ入り、未完了の相手を見分けるStandardの実画面（見込み25〜40分）。利用者が報告した招待上の行き詰まりを既存の実UI試験で再現・検証できるため、追加の音声方式の比較より先に進める。

1123から15進んだ1138で再確認した。双方ロックの開始・待ち・再接続は2台の実機受入が必要。Standardのグループ招待で保存した相手を開き直せるようにし、OS共有のプレビューが未送信状態を変えていた問題も修正した。次は同じ誤表示が残る旧形式の個人招待を、共通の共有完了処理で改める最小単位（見込み15〜25分）。既定AACの音声分離を保つ低遅延案の比較（見込み30分以上）と、Advancedの追加状態表示はその後の独立単位とする。次回の重要度チェックの基準は1138。

1142の区切りで、旧形式の個人招待は共有取消・コピー・再起動をiPhone Simulatorで確認した。次はAdvancedのGroup Settingsで、新しい相手ごとに未共有・共有済みを保存記録の値から見分け、同じ詳細へ進めることを確認する（見込み15〜25分）。招待の流れを揃えるという利用者の優先指示に従い、既定AACの低遅延案の比較より先に進める。10ビルドごとの重要度チェックの基準は1138を維持する。

1145の区切りで、AdvancedのGroup Settingsは共有前・取消後・コピー後・返信後を確認した。次は登録済み相手への招待を保存した直後に背景へ移る経路を優先する。現行の配送処理はSwift Taskで開始し、iOSの有限な背景実行時間を先に取得していない。保存直後の送信と期限切れ後の再試行を確かめる最小単位（見込み25〜35分）とする。操作直後のロックという必須条件に直接関わり、2台の実機を待つ間も局所検証できるため、既定AACの比較より先に進める。重要度チェックの基準は1138を維持する。

1138から10進んだ1148で再確認した。双方ロックでの通話の開始・待ち・再接続は、近距離とInternetの両方で引き続き最優先の実機受入。登録済み相手への招待は、保存直後の有限な実行時間を要求し、時間切れから同じ配送を再試行できるようになった。次は受諾直後の個人招待の返信を優先する。現在は背景移行で有限な返信sessionも直ちに停止する。相手が応答可能な状態で「登録」直後に背景へ移り、保持した同じ返信をOSの実行時間内に届けられるかを最小単位とする（見込み25〜35分）。利用者の最後の操作に直接関わり、試行できる条件を分離できるため、既定AACの低遅延候補の比較（見込み30分以上）より先に進める。次回の重要度チェックの基準は1148。

1151の区切りで、明示登録後の返信をOSの時間内に続け、時間切れでも同じ返信を再開できることをApp試験で確認した。招待と通話の実機受入を待つ間は、既定AACで音声分離を維持し、再生開始の実I/O周期と先行時間の関係を短い実音声試験で切り分ける（見込み20〜30分）。判定余裕込み125msと音声の連続性を基準にする。10ビルドごとの重要度チェックの基準は1148を維持する。

1152の区切りで、既定AACの実I/O周期は2.67msから1.33msに変わったが、収録callbackは10.67ms、判定余裕込みの出力は127.40msだった。I/O周期変更で改善が得られなかったため、音声分離を保つ別の低遅延候補は処理段階を先に絞る必要がある（見込み30分以上）。先に、押した直後の操作を遅らせる可能性があるiOSの音声session操作のRuntime Warningを現行SDKと既存Setting試験で照合する最小単位（見込み15〜25分）。10ビルドごとの重要度チェックの基準は1148を維持する。

1153の区切りで、音声session開始・終了はすでにiOS標準の非同期APIに移行済みと確認し、元の警告が出た実UIケースが警告なしで通った。次は招待を優先する利用者指示に沿って、Advancedの通話メニューから新しい相手へ進む入口を再確認する（見込み15〜25分）。通話メニューの自動操作が進まなかった結果を、いまの画面と実入力で切り分ける。10ビルドごとの重要度チェックの基準は1148。

1148から10進んだ1158で再確認した。双方をロックした通話の成立・待機・継続・復旧は重要度が最も高く、2台の実機での受入が残る。Advancedの通話メニューでは、新しい相手への招待、登録済み相手の配送状態、個別通話の相手の設定が実Appで通った。次に、個別通話の古い鍵が競合したときにStandardが案内する共有操作を、既存の個別通話を使って実画面で再現する（見込み15〜25分）。招待の案内から操作を完了できるかを、鍵の自動同期の方式と独立して確認できるため、既定AACの追加比較（見込み30分以上）や近距離媒体の片方向・初回不達のApp試験（見込み25〜45分）より先に選ぶ。次回の重要度チェックの基準は1158。

1161の区切りで、Standardの競合案内から同じ相手への共有を開き、取消・コピー後も通話へ戻れることを実UIで確認した。以降の招待はMacのOS共有と2実機・実APNsの受入が主に残る。次は片方向の近距離媒体が開始から届かない場合に、通信を続けられるかを既存の二端末音声試験で確かめる（見込み25〜45分）。双方ロックの実機受入を待つ間に、通話開始を阻む経路条件の再現と修正要否を先に決められるため、既定AACの追加比較より優先する。10ビルドごとの重要度チェックの基準は1158を維持する。

1158から10進んだ1168で再確認した。双方をロックした通話の開始・待機・継続・復旧は最優先で、2台の実機受入が残る。2台のSimulatorでは、両経路が利用可能になった後の最初の片方向遮断、通話途中の両方向遮断と復帰で双方向の再生に成功した。操作直後の利用に関係し、同じ音声試験を使える「媒体が全経路で届かない間に切断し、復帰後も終了状態を保つ」を次の最小単位に選ぶ（見込み25〜40分）。既定AACの追加比較（見込み30分以上）やInternet確立までの詳しい計測（見込み30分以上）は、その後の独立単位とする。次回の重要度チェックの基準は1168。

1170の区切りで、全媒体不達中の切断と経路復帰後の終了状態を2台のSimulatorで確認した。次は、Internetだけで先に入った側が待機し、後参加した相手と双方の再生が成立する最小の実App試験を先に進める（見込み20〜35分）。既存のローカルWorker/SFUと2台の構成を再利用でき、音声分離を保つ既定AACの追加の低遅延実験（見込み30分以上）より少ない手順で、近距離を使えない地点の開始条件を確認できる。双方ロック・実SFUは実機環境待ち。10ビルドごとの重要度チェックの基準は1168を維持する。

1172の区切りで、Internetだけの待機と後参加後の双方向再生を2台のSimulatorで確認した。次は近距離だけの後参加を同じ2台で確認する（見込み15〜25分）。待機と後参加の片側だけが確実に成立しないリスクを、共通の音声検証で小さく確認できる。既定AACの低遅延実験と実環境の受入を分けて追う。10ビルドごとの重要度チェックの基準は1168を維持する。

1174の区切りで、近距離だけの待機・後参加とInternet側の回帰を確認した。次は、双方が通話を選んだ直後に設定アプリへ移り、元のAppを前面へ戻さず待機・後参加と音声再生ができるかを、同じ2台のSimulatorとInternet経路で先に試す（見込み20〜35分）。操作直後に別アプリを使う利用条件に直接関わり、実機を待ちながらOS状態と音声の確かめられる範囲を広げる。既定AACの低遅延実験より先に選ぶ。10ビルドごとの重要度チェックの基準は1168を維持する。

1176の区切りで、両端が通話開始直後に別アプリへ移り、背景のまま待機・後参加・双方向再生へ進むことを近距離とInternetで確認した。次は成立済みのInternet通話で両端が背景のままSFU接続を失い、自動再接続して双方向再生が戻るかを、同じ2台とローカルfixtureで確かめる（見込み25〜40分）。利用者が移動中に切断へ対処できない問題に直接関わり、成立済みの試験入口を再利用できるため、低遅延の候補追加より先に選ぶ。10ビルドごとの重要度チェックの基準は1168を維持する。

1168から10進んだ1178で重要度を再確認した。両端が背景のInternet通話で、試験SFUの接続断から同じ通話へ自動復旧し、双方向の実音声が戻った。次は、圏外で使う近距離だけの通話で、背景中にUDPの受信口を失っても端末が経路を作り直し、同じ通話で声が戻るかを確認する（見込み25〜40分）。両端の実機ロックは最優先の受入として残る。既存の近距離音声試験を使って独立に評価できるため、既定AACの低遅延候補の追加比較（見込み30分以上）より先に選ぶ。次回の重要度チェックの基準は1178。

1180の区切りで、両端が背景にある近距離通話のUDP受信口を閉じた後、新しい受信口と双方向再生が自動で戻ることを確認した。次は背景でどちらも話さない時間を作り、次の発話が操作なしに相手へ届くかを既存の実音声E2Eで確かめる（見込み25〜40分）。移動中にときどき話す使い方で重要な一条件で、低遅延の候補追加より先に確認する。実機での長時間・マイクOFF・画面ロックの受入は引き続き残る。10ビルドごとの重要度チェックの基準は1178を維持する。

1182の区切りで、近距離とInternetの両方で、双方が背景のまま約60秒の無発話を経ても通話を維持し、次の発話を双方向で再生できた。次は近距離で双方のマイクをOFFにし、片側だけの明示的な解除後、聞き専の相手へその声が届くかを確かめる（見込み25〜40分）。同じ2台と既存の共通操作を利用でき、聞き専と相槌の継続に直結するため低遅延の候補追加より先に選ぶ。実機の長時間ロック・native再生停止は受入待ち。10ビルドごとの重要度チェックの基準は1178を維持する。

1184の区切りで、近距離の背景通話で双方のマイクを約60秒OFFにし、片側だけの解除後に聞き専の相手が発話を再生することを確認した。次は同じビルドでInternetだけを使い、SFUと信頼性のある制御を介して同じ操作から受話できるかを確認する（見込み15〜25分）。新規実装なしで近距離との違いを確認でき、既定AACの候補追加より先に選ぶ。ロックした物理端末と実SFUの受入は続ける。10ビルドごとの重要度チェックの基準は1178を維持する。

同じ1184の区切りで、Internetのみでも双方マイクOFFと片側解除の後の受話を確認した。次は、近距離で通話を始めた時点で音声が片方向だけ途切れ、Internetが後から利用可能になるまでの実音声を確かめる（見込み20〜35分）。ネットワークが切り替わる移動時に相手の声が戻るかに直接関わる。既存の両経路E2Eで検証できるため、低遅延案の追加比較より先に選ぶ。実機の長時間ロック・native再生停止・解除操作の入口は受入待ち。重要度チェックの基準は1178を維持する。

## 判断や再開を待つもの

着手順に入れず、条件が満たされたら着手順へ移す。

| 待っているもの | 待つ理由 | 再開の条件 | 詳細 |
