## 同時通信の制限を見直す案

2026-11-01の追加要望。現行は同一ユーザーのWebRTC接続を1端末とし、既存通話を残して追加側を拒否する（[通信仕様](../spec/App/通信仕様.md)、[server仕様](../spec/server/Worker.md)）。利用制限は事故や復旧不能を避け、独自の台帳・監視・状態管理を増やさない。

| 課題 | 利用者の意図・候補 | 検討・受入条件 |
|---|---|---|
| 同時通信の制限単位を見直す | 1ユーザー1通信が好ましいが、厳しくロックすると事故が起きそう。1端末1通信、同一ユーザーは2端末程度までを落とし所の候補にする | 「2端末程度」は今回の候補であり、確定済みの数値・実装済み上限にしない。同一端末の二重通信、端末切替、クラッシュ・通信断・古い予約残りを、少ない状態管理で扱える方式を比較する |
| 他で通信中の場合は後からの操作で復帰する | 「他で通信中」と拒否されるだけでは苦しいため、新しく開始した側を優先する | 後勝ちの切替先・終了対象を定義し、古い接続の自動再接続と奪い合わない。新しい側が開始できず解除操作にも進めない袋小路を避け、旧側には終了・切替理由が分かる。独自の厳密な端末間lockや大きな管理基盤を追加することを前提にしない |

現行の[製品要求](../requirements/製品要求.md)は「同一ユーザーのWebRTC接続を原則1端末」とし、[既存課題](../development/history/旧未実装課題の完了済み経緯.md#appleでのログインと通知先の識別)には旧通話を残して追加側を拒否する実装が記載されている。今回の2端末程度・後勝ち候補は、その制約を見直す課題として扱う。現行の仕様が既に後勝ちであるとは書き換えない。Multipeerを含む「1端末1通信」の対象と、serverのWebRTC予約制限との関係も整理する。

2026-10-31の追加方針として、仕様を簡単に理解でき、失敗後も戻れることを優先する。人数・端末数の上限を厳密に強制するための複雑な調停や待ち合わせは増やさない。WebRTCは原則1端末という目的を保ちつつ、必要なら一時的な2接続や旧通話を終了する切替を選べる。現在の追加接続拒否は現行仕様として残し、切替・回収の見直しでは復旧経路と一緒に評価する。

### VoiceProcessingIOと既定デバイスの開始安定性

2026-11-02の録音修正では、端末本体のAudio Checkから他音声duckingを外し、送信エフェクト・VAD・codecによる録音を維持する仕様を採用した（[現行仕様](../spec/App/音声処理仕様.md#audio-check)）。通常通話のduckingと、Simulatorの既定デバイスで入力形式を取得できない問題の根本調査は、利用者指示に従い改善候補へ分ける。Watchの実装と保留範囲は維持する。

| 改善候補 | 観測と再開条件 |
|---|---|
| 他音声duckingを使うnative I/Oの開始安定性 | iPhone SimulatorでVoiceProcessingIO切替時の`IsFormatSampleRateAndChannelCountValid`例外を観測した。通常通話と実機での発生条件、入出力形式とgraph構築・切替順の関係を最小対照で調べる。録音チェックへ再導入する場合は、明示的な採用判断と、開始・停止・再実行のnative検証を要する |
| Simulatorの既定音声デバイス取得 | 既定割り当てで`Unsupported input hardware format or buffer size`による録音開始失敗を観測した。検証用Simulatorの入出力を同じ実デバイスへ固定する条件と分け、OS・デバイス形式・割り当ての原因を確認する。利用者のMac全体の既定入出力を変更する回避策は採用していない |
| Macの初回音声準備時間 | `.validation/recording-button-mac-acceptance-20261102/`では実マイク録音・全量再生・再実行は成功したが、初回のnative準備付近に約35秒の遅延を観測した。入力準備と5秒の録音を分け、デバイス初期化・権限・native音声処理のどこで待つかを限定観測してから改善する。原因は未確定で、テストの録音量・再生量の条件は維持する |

## 画面と診断の改善候補

現行画面は[Call](../spec/App/UI/Call.md)、[Settings](../spec/App/UI/Settings.md)、[Diagnostics](../spec/App/UI/Diagnostics.md)、[Watch操作](../spec/App/Watch操作.md)を正とする。設計見本は候補であり、現行の操作・情報を保持し、標準コントロールとアクセシビリティを確認して採否を決める。

| 候補 | 検討・受入 |
|---|---|
| 診断の新データ・原因判定・ページ化 | 追加の実測値と必要性、根拠に基づく原因の示し方、情報量に応じたページ分割を設計する。推測を確定原因と表示しない |
| 状態色とメーター | 通話・送話・ミュート・失敗等の全状態色と音声メーターを設計案と照合し、色以外の文字や記号でも状態を区別する |
| Watch配色 | Watchの送話状態色を表示条件とともに検討する。Watch音声・通信の成立とは分ける |
| 通信経路切替 | Standardの設定入口と現行動作は[Settings](../spec/App/UI/Settings.md)を参照する。通話中の切替、最後の経路を無効にする操作、表示・保存・実処理の一致を条件ごとに確認し、必要な案内を検討する |
| 画面構成 | 円形の主要操作、設定の残る画面分割など、未適用の見本を現行操作や標準コントロールとの整合から判断する |

実Watch・VoiceOver・屋外視認などは[未確認事項](../validation/未確認事項.md#画面デザインの実環境受入)で扱う。

## 自分の声の分離の設定と録音テスト

2026-11-17のデザイン引継ぎ。機能要求は[自分の声の分離を設定へ集約](未実装課題.md#自分の声の分離を設定へ集約して録音テストにも適用する)を参照する。Standard・Advancedとも自分の声の分離操作を通話画面から外し、設定で変更して録音テストでも聞き比べられる配置・表示名・説明を決める。一般向けは自分の送信音へ適用することが分かる表現にし、Advancedは実処理との対応を示す。受信側の分離と混同させず、非対応環境の扱いを含め実画面で受け入れる。今回は記録のみで、画面変更は未実施。

## Standardの個人間通話の表示

2026-11-17のバグ報告に伴うデザイン引継ぎ。[機能側の不具合](未実装課題.md#standardの個人間通話にメンバー一覧が表示される)と一体で追跡する。Standardの個人通話ではメンバー一覧を出さず、相手の表示と必要な通話操作で構成する。通常グループと個人間専用グループを人数で混同せず、Advancedの内部実装に対応する表示と分離する。既存デザインと実画面を照合して修正し、画面遷移後にも一覧が再出現しないことを受け入れる。今回は記録のみ。
