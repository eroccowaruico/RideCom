## 認証ユーザーと削除後の再登録

Workerの`account.test.mjs`で、複数端末・再ログイン・全端末の資格の期限切れ後の同一公開ID、削除後の新ID、並行再登録・再起動・古い削除再送、残存する通話予約の迂回拒否を確認する。Appの`InternetAccountTests`では公開IDと資格の内部locatorが異なる登録応答を保存できることと、不正なlocatorの拒否を確認する。これは保存ユーザーの本人確認や通知許可までの結合確認ではない。

## 署名付き端末証明

Workerの`account.test.mjs`でBearerの本人と端末への証明発行、bodyによる他人のID指定の無視、秘密の非公開、期限、削除・再登録、不正鍵・仮ID・署名設定欠落を確認する。Appの`DeviceIdentityCertificateTests`はJOSE生成のES256署名とCryptoKitの相互運用、署名・発行元・用途・期限・各ID・公開鍵の検証を扱う。`InternetAccountTests`は取得と資格保存の一連の処理、不一致時の資格回収、再起動、サインアウト、欠落／破損した秘密鍵の保持を確認する。相手による秘密鍵の所持確認と保存ユーザーへの対応は後続の検証対象である。

## App音声・機器

GeneratedDuplexAudioTestsは実PCM16 codec、現行のGroupRelay暗号化、共通の受信待ち、Appのdecodeを通す。双方向各30,000フレーム・9,600,000サンプルを使い、順序、誤差、重複の拒否を検査する。合成時間であり実音響品質の確認ではない。

App単体・結合テストはオフラインAVAudioEngineと偽のハードウェア境界を用いる。SessionManagerのruntime eventを入力し、資源解放・接続維持・再試行を検証する。

## 実発話E2E

独立した`RideIntercomAudioE2E` schemeを[音声E2Eテスト入口](../development/音声E2Eテスト.md)から実行する。MacとiPhone Simulatorの両端で、録音済みの異なる発話をLocal / WebRTCへ送り、相手の実出力engineの波形を照合する。全codec指定・16/24/48kHz・bitrate境界・session profile・VAD・各effect・音量・muteと復帰を設定マトリクスで扱う。iOSのcaptureは実OS backendを起動し、callbackのマイクsampleだけをfixtureへ差し替える。サーバーはlocalhostのWorker/SFU fixture、アプリのHTTP/WS clientとWebRTC媒体は実物である。物理マイクのAEC品質・Bluetooth・実Cloudflareの保証は含まない。

## Local探索

実Bonjour探索の反復start/stopとSimulatorの接続・切断UIを扱う。端末間の無線通信・実機相互通話は確認待ちへ分ける。

## 全体監査で追加した異常系

| 領域 | 自動検証 |
|---|---|
| 音声入力境界 | 非有限PCM/時刻、channel 0・過大format、PCM16 sliced Data、偽compressed envelope count/offset、5.1拒否とinterleaved入力 |
| 出力backlog | Mixer/SessionManagerの20並行offline fixtureで、破棄後の最初のblockから最新音声が出ること、旧音声が再開後に出ないこと |
| graphと並行性 | bus/source/faderの反復追加削除、effect設定の再正規化、VADの並行更新・reset・snapshot、全packageの任意Thread Sanitizer実行 |
| RTC | control overflow後の回復、queue上限、二重start・重複route、不正Local ID、旧channel callbackの所有期間 |
| App保存 | secret/runtime非保存、破損保持・書込停止、鍵準備/manifest commit失敗の復旧、削除、8人上限、同鍵再招待・通話中に異なる鍵を拒否 |
| App音声 | sample長に基づくVAD、preroll再送防止、remote時計に依存しない発話期限、離脱graph解放、未知codec/不正RTC format拒否 |

## リアルタイム会話の追加範囲

[音声E2E手順](../development/音声E2Eテスト.md)のrealtime / codec / group / switches / conversationを独立して実行する。通常のpackage・App結合・UIテストの成功だけでは音声合格としない。各処理のsample clock・queue上限・異常値、native AAC、8人の混在経路、相槌を別々に判定する。微小欠落とclickの負例、設定切替時の無音と通常区間、capture→render遅延も個別に判定する。実機無線・Bluetooth・実Cloudflareは[未確認事項](未確認事項.md)で扱う。


## 新しい相手の招待と登録

ContactInvitationPresentationTestsは署名プレビュー／取消の非保存、共有token再利用とexport再認可、明示受諾と既存通話の分離を扱う。ContactInvitationPersistenceTestsは保存失敗・再起動・通知の有界停止・取消に加え、近距離の実通信adapter二者から双方のUsers保存とディスク再読込までを扱う。資格保存とアカウントはfixtureで、実機・Internet配送とは区別する。

ContactBootstrapTestsは、登録と明示的な再試行の直後に背景へ移る経路で、有限の実行時間を取得済みなら同じ返信を保持し、再試行の連打でも時間を追加取得しないことを確認する。時間切れの前後で署名付き到着確認まで進め、期限切れの実行時間を解放して保存済みの返信を再開する。ContactReplyUITestsは個人／グループ招待を両モードで開き、保存済みの同じ相手から返信の共有・再試行に進み、到着確認後に待ち表示が解消することと、期限切れの案内を確認する。[実行記録](../development/history/バックログの優先順位と進捗の記録.md#招待返信の再試行を背景へ引き継ぐ)

StandardInterfaceUITestsはUsersの＋、OS共有取消／Copy、日英の受諾確認と再起動後の保存、通話中の待機／再試行／端末内取消を扱う。既存InvitationSharingTestsと共有UI回帰でグループ招待の維持も確認する。実行結果は[画面改修の履歴](history/画面デザインと録音操作の整理.md#usersの新規招待と受諾画面)を参照する。

GroupContactInvitationUITestsは新しい人の名前とグループを保存し、Standardの通話・グループ設定から同じ人を開き直す。OS共有の取消後に「まだ送っていません」を保ち、コピー完了で同じ詳細が「受け取り待ち」に変わること、署名付き返信後に対応する枠が通常のメンバーになることを確認する。Advancedのグループ設定は同じ条件で保存値の`sent`がfalseからtrueになることを確認する。

期限切れのStandard UI試験では、隔離された検証構成で過去の時刻に保存し、通常の時刻でグループ設定から開き直す。共有を取り消した場合も同じ人と参加先に未送信の新しい招待が1件だけ残ることを確認する。GroupContactInvitationTestsは、期限切れの枠やグループを外す際と、旧保存を再読込する際の取消を確認し、同じ人から個人招待を共有してもグループの枠が戻らないことを確かめる。[実行記録](../development/history/バックログの優先順位と進捗の記録.md#期限切れの招待を更新する条件を予約枠と揃える)

## 登録済みの相手へのグループ自動配送

RegisteredGroupInvitationUITestsは、既知の8台を持つ相手を選んで保存し、配送中にOS共有を開いて閉じても待機を保つことを両モードで確認する。隔離されたUI試験で、前面への復帰を合図に1台分の確定結果を既存の保存処理へ渡す。開いたままの同じ行と完了後のグループ設定を確認し、Standardでは相手が「受け取り済み」、Advancedでは該当端末が`received`で、残りが`pending`になる。Advancedの`Invite`へ配送記録の前から進めることも確認する。通信・署名付き受領・失敗時の保持はGroupDeliveryFlowTestsとGroupDeliveryPersistenceTestsで確認する。[実行記録](../development/history/バックログの優先順位と進捗の記録.md#自動配送の受取表示と共有位置を確かめる)
