# 近距離オフライン通信の調査と検証

## QUIC移行後の再調査

2026-11-18、利用者から「Multipeerを使わなくなっても、ネットワーク自体がない山中でつながるか。元々の構想は維持する」と依頼された。調査対象は`4435695`の現行コード・要求・試験とAppleの一次資料。今回は静的調査と試験設計を行い、App・packageのテストや設備なし実無線試験は再実行していない。以下の2026-10-30の結果と、[QUIC移行時の結果](近距離制御のQUIC移行.md)を、今回の実行結果と区別する。

| 調べたこと | 現行の根拠と判断 |
|---|---|
| MultipeerなしでAP不在の通信が可能か | Appleの[TN3213](https://developer.apple.com/documentation/technotes/tn3213-moving-from-multipeer-connectivity-to-network-framework)はNetwork.frameworkでもApple peer-to-peer Wi-Fiを利用できると明記する。[TN3151](https://developer.apple.com/documentation/technotes/tn3151-choosing-the-right-networking-api)はWi-Fiネットワーク設定不要の方式として説明する。Multipeer廃止そのものは設備不要の構想を失う理由にならない |
| 探索・制御・音声の設定 | `LocalControlTransport.swift`のBonjour browser、`LocalControlTLS.swift`のQUIC listener／connection、`LocalDatagramTransport.swift`のUDP待受・service解決・送信で`includePeerToPeer = true`。制御接続と媒体はセルラー禁止で、媒体のinterface固定はない。`CallSessionFactory`は`RouteKind.multipeer`に現行`LocalCallRoute`を生成する。名前が残っていてもMCSessionを使う経路ではない |
| 圏外の本人確認と開始 | `AppleAccountSession.refresh()`は資格照会の通信失敗時も保存済みログインを保持し、資格取消を確認した場合は破棄する。`connectSelectedGroup()`は保存済みグループ鍵でLocal接続を開始する。これはコード上の確認であり、起動・利用権・通知・Internet登録を含む製品Appの設備なし開始を実証した結果ではない |
| 隊列中継 | 既存の部分メッシュと`GroupRelay`の最大8hop転送を維持している。`GroupContinuityTests.fourRidersRelayAlongALineAndRejoinAfterTheMiddleRiderReturns`は仮想4端末・Internetなしの直線隊列、中間離脱・復帰を扱う。`eightLocalPeersTalkWhileInternetIsUnavailable`も仮想経路。実際の無線距離・中継品質とは区別する |
| 移動と品質 | UDPには`betterPathUpdateHandler`・`viabilityUpdateHandler`によるflow切替がある。Apple DTSの[解説](https://developer.apple.com/forums/thread/751839)もUDP経路移行の処理と実測の必要性を説明する。QUIC移行後のMac–Simulator音声測定は実UDP転送まで進んだが、既定AACの一方向で判定値130.29 msとなり125 msを超え、音声E2E全体は不合格だった。これは山中の無線測定ではなく、接続実装だけで品質合格とは言えない |
| 残る不足 | AP未接続・セルラーOFFの実iPhone間で、圏外からの新規起動、双方向音声、ロック中継続、隊列・分断・復帰を受け入れた証拠は記録されていない。Wi-Fi機能ON、事前ログイン・鍵共有・必要な利用権・権限の前提を維持して試験する |

結論は「設備不要の経路は実装に残るが、山中での製品受入は未完」。新しいtransportを前提にせず、元の構想を現行方式で実証する[設計と残作業](../../backlog/未実装課題.md#apもセルラーもない場所からの近距離通話を実証する)を追加した。制御はつながるが音声だけ届かない条件、音声品質、背景切断は既存の修復課題と相互参照し、今回完了扱いにはしていない。

## 背景と成立条件

2026-10-30、Local音声をMCSessionから認証済みUDPへ分離したことで、アクセスポイントとセルラー電波のどちらもない屋外の通話を失っていないか調査した。出発点は`44518d19`。Wi-Fiなしはアクセスポイント未接続を指し、Wi-Fi無線機能OFFと区別する。

| 調査対象 | 確認した内容と判断 |
|---|---|
| Network.frameworkの近距離通信 | Appleの[TN3151](https://developer.apple.com/documentation/technotes/tn3151-choosing-the-right-networking-api)は、peer-to-peer Wi-FiをWi-Fiネットワーク設定なしに使えると説明し、Network.frameworkの`includePeerToPeer`を案内している。現行UDPは探索・待受・送信すべてで有効であり、APやセルラーを必須とする構造ではなかった |
| Multipeerだけでなければ不可能か | [TN3213](https://developer.apple.com/documentation/technotes/tn3213-moving-from-multipeer-connectivity-to-network-framework)は、MultipeerだけがApple peer-to-peer Wi-Fiを使えるという理解を明確に否定している。制御はMCSession、音声はNetwork.frameworkでも近距離無線を使える |
| Multipeerの信頼なし | [`MCSessionSendDataMode.unreliable`](https://developer.apple.com/documentation/multipeerconnectivity/mcsessionsenddatamode/unreliable)は即時に送れなければ破棄し、順序を保証しない。音声向けbest-effortの選択肢である。ここから下位transportが常にUDPであるとは断定しない。再送なしUDPを明示できる現在の媒体分離を維持した |
| 端末の無線機能 | Bluetoothで制御peerを見つける可能性と、UDP音声が到達することを同一視しない。現在のLocal音声はpeer-to-peer Wi-Fiまたは利用可能なLANを必要とし、Wi-Fi機能OFFでBluetoothのみの通話は提供しない |
| 消費電力 | [peerToPeerIncluded](https://developer.apple.com/documentation/network/nwparametersprovider/peertopeerincluded(_:))はpeer-to-peer資源の電力負荷と不要時の停止を指摘する。通話停止でbrowser・listener・送受信flowを破棄する現行lifecycleを維持。通話中は途中参加・再発見のため探索を維持する。実消費電力は実機確認が必要 |

## 移動による経路変更の追加調査

Apple DTSの[peer-to-peer解説](https://developer.apple.com/forums/thread/751839)では、UDP/TCPの確立済み接続は別の経路へ自動移行せず、`betterPathUpdateHandler`を使う必要があると説明している。現行実装にはこのhandlerがなかった。AP接続から屋外のpeer-to-peerへ移る条件を想定し、利用可能な旧flowは保持しながら新flowを作り、ready後に切り替える処理を追加した。到達性喪失の通知も扱い、失敗中の音声packetごとの接続連打は2〜30秒のbackoffで防ぐ。再接続のために音声をためたり再送したりしない。

同資料はpeer-to-peer Wi-Fi自体が条件によって数百msの遅延を生じ得るとも説明している。無線区間の125ms達成はAPI選択だけで保証できない。アプリ内の待ちを減らす要求と125msの判定基準は維持し、実機で無線区間も含めて測る。

## 修正した差分

Localのpeer-to-peer設定自体にAP依存は見つからなかった。一方、全員が近くてもLocal / Internetへ常に同じ音声を送る経路方針は、近距離優先・通信費削減の要求と不一致だった。

| 変更 | 振る舞いと限界 |
|---|---|
| Local優先 | 即時UDP送信を受け付けた認証済みpeer集合をRTC route契約で返す。Internetの全既知参加者をLocalがカバーしたpacketはInternetコピーを省く。接続状態だけでは判断しない |
| 代替経路と混在 | Local未準備・送信上限・遠隔参加者があればInternet音声も即時送信。到着ACKや再送、追加の待機はない。SFU fan-out時の近隣重複は先着だけ再生 |
| 近距離parameters | UDP parametersの重複を共通化し、peer-to-peer有効、特定interface固定なし、セルラー禁止を全経路へ適用 |
| 要求と操作案内 | AP・セルラーなしの開始/継続、セルラー利用可能時のLocal優先、必要な端末無線機能を要求とマニュアルに明記 |

UDPの送信受付は受信確認ではない。無線損失のゼロ保証や、悪いLocalリンクでもInternetより必ず速いことは意味しない。音声を再送せず、受信側の既存の期限・連続性制御を維持する。Internetの制御接続・遠隔の参加者の探索は残るため、音声コピー削減を全サーバー費用ゼロとは扱わない。

試作で期限切れとなったBのパケットは、送信から受信処理まで327.52 msかかった。その後に再生位置を取り直した。現行の比較では、Bで収録後の入力が揃うまでの待ちが増え、学習した1,534サンプルを使う予約が定常区間まで続いた。試行間で定常区間を決めた到着と予約が違う。起動時の大きな遅着と、周期差を見込むことによる効果を分けるには、保存した入力・到着時刻・描画位置を同じ条件で再生する必要がある。

試作も両端のXCTest各1件は通過した。125 ms基準は両方向とも未達だった。試作差分を作業ツリーから取り除き、音声設定の復元とSimulator 2台の回収を確認した。証跡は `.validation/code-2520-capture-cadence-margin/` の試作差分と集計。次回用番号は2593。

### 同じ到着と描画位置で必要な予約余裕を比べる

近距離の現行版3試行から、起動時に予約した2,409件をAudioMixerに再入力した。`startupReceived` から収録時刻、受信処理を始めた時刻、描画済み位置、書込可能位置、フレーム長を取り出した。起動時の復号WAVから、各フレームが有声扱いかを実装と同じRMSとピークで求めた。時刻は最初の復号時刻を起点にそろえ、余裕0で全予約の先頭サンプルが実測と一致した。[試験の採取手順](../../development/音声E2Eテスト.md#internetの応答を待たずに始める)

| 保存した試行 | 照合した予約 A／B | Bの追加学習がなくなる最小の余裕 | 448サンプルを見込んだ場合の予約位置の変化 A／B |
|---|---:|---:|---:|
| 起動直後の予約を採った試行 | 431／507件 | 448サンプル（9.33 ms） | 480／−1,185サンプル |
| 起動直後の送信時刻を採った試行 | 368／367件 | 96サンプル（2.00 ms） | 448／−833サンプル |
| 入力の受け渡しを測った試行 | 373／363件 | 192サンプル（4.00 ms） | 448／−833サンプル |

48 kHzで0から448サンプルまでを1サンプルずつ増やした。Aの追加学習は余裕0で全試行とも0件。Bは現行版だと各1件あり、上表の値で0件になった。予約位置の変化は起動区間の最後の50件で一致した。固定の448サンプルは、この発話と到着の条件ではBの遅着による追加学習を避ける一方、Aの予約を遅らせた。両方向の低遅延を保つ対策には採用しない。次は、遅着から復旧するときに学習する待ちのうち、入力周期で説明できる部分を切り分け、無線の実際の揺れに備える余裕と比較する。

この比較はAudioMixerの予約への再入力。新たな出力波形や125 msへの適合は、前節までの実測範囲に限る。各試行のXCTest添付から抽出した入力、再入力の方法、3件のパッケージ試験の結果は `.validation/code-2520-cadence-reservation-replay/` に保存した。試作テストを作業ツリーから回収した。
