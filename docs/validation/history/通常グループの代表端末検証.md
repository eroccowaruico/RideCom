## 統合時レビューで見つかった候補枠の修正

従来の`authenticatedPeerIDs.sorted().prefix(7)`は、本人の人数より前に端末を7件へ絞っていた。7人の代表が接続中にID順の早い追加端末が現れると、接続中の代表がプロフィールから消えて離脱と扱われ、本人の代表置換または無関係な人の音声許可脱落が起きた。確認済みでmembershipも継続する代表を優先し、通常groupの一時プロフィール候補だけを7人×2端末の14件へ拡げた。保存人数8人と登録端末数の契約は変えていない。

## メンバー除外後の音声とグループ鍵の境界（2026-11-19）

基準は `65ccbe33`。操作側・残る相手・除外された相手の3端末相当で、送信元が分かる試験用PCMを既存のRTC音声処理に通し、各端末に配送された音声を確認した。除外の操作は、現行Appと同じように操作側の受信音声許可から対象を外し、残る相手の許可を保つことで再現した。

| 経路 | 操作側の許可だけを変更 | 残る2端末だけが新しい鍵で接続 |
|---|---|---|
| 近距離・直接の仮想経路 | 操作側の音声が除外された端末に届く | 残る2端末の双方向音声を確認。旧鍵側の音声配送は0 |
| 近距離・中継の仮想経路 | 残る1端末を経由して音声が届く | 同上 |
| Internetの仮想経路 | 操作側の音声が除外された端末に届く | 同上 |
| 近距離＋Internetの仮想経路 | 両経路を持つ残る1端末を経由して音声が届く | 同上 |
| ネイティブQUIC／UDP | 操作側の音声が除外された端末に届く | 残る2端末の双方向音声を確認。旧鍵側の音声配送は0 |
| ネイティブWebRTCとローカルSFU | 操作側の音声が除外された端末に届く | 同上 |

6条件を各5回確認した。仮想経路は同じネットワークに3端末を残し、RTCの音声パケットを最後まで通した。ネイティブ近距離は実QUIC／UDPで直接つないだ。WebRTCは製品のDTLS／SCTPを使い、ローカルSFU代替が中継先を固定した。媒体出力はRTCの受信イベントで、マイク・スピーカー・物理端末の動作を含まない。

鍵を置き換えた試験では、残る2端末へ試験から新しい鍵を用意し、既存のprepare／startで通話を作り直した。最初のprepareから双方向の新しい音声が届くまで、QUIC／UDPが1.109〜1.192秒、ローカルWebRTCが0.258〜0.267秒。その時間に鍵配送・Appの受領・ロックからの復帰は含まれない。鍵を分離する効果と、通話を作り直す案の中断を確認した。接続を維持して音声鍵だけを切り替える案は未検証。

一巡目で、Appが決める自端末での受信許可、RTCの共有鍵と中継、Workerの招待配送の境界を照合した。二巡目で、送信と中継をローカルの受信許可に従属させると、再生しない端末を経由する既存の混在通話にも影響することを既存試験と照合した。現行の再招待は同じgroup IDに異なる鍵が来ると上書きを拒否するため、除外を伴う新しい鍵の受領は招待受領と別の認可を要する。受取側で操作の権限を検証し、古い鍵や招待へ巻き戻らないことを[残る要件](../../backlog/未実装課題.md#受取確定後のメンバー除外)に記録した。

証跡は `.validation/group-removal-credential-boundary-20261119` の `virtual.log`、`native-final.log`、`repeat-2.log`〜`repeat-5.log` と、一時的な計測用の差分。4つの仮想経路に、残る端末の双方向音声と旧鍵の分離の回帰を残した。ネイティブの一時計測コードを回収した後、RTC全体139件とネイティブの5件が成功した（`rtc-regression.log`）。製品のApp、RTC、Workerの動作には変更を加えていない。
## 接続を維持した音声鍵の切替（2026-11-19）

`fba781c8` を基準に、接続・中継に使う共有鍵を保ち、音声だけを別の鍵へ切り替える試作を行った。既存のRTCの共通中継処理で、送信元・通話・送信順・鍵の世代を認証対象にして音声を包んだ。中継端末は音声鍵を持たなくても暗号文を転送できる。暗号化には [Apple CryptoKitのAES-GCM](https://developer.apple.com/documentation/cryptokit/aes/gcm) を使用した。

最初に同じ音声鍵で3端末の送受信を成立させた。次に残る2端末に切替を知らせて送信を停止し、70msの待ちを挟んで順に新しい鍵を設定した。旧鍵から届く音声と、片方がまだ鍵を待つ間にもう片方が新しい鍵で送った音声は、残る端末の受信イベントに出なかった。両方の設定後に新しい試験音声を送ると、残る2端末で双方向に届き、旧鍵を保持する端末には届かなかった。残る端末の接続試行回数と相手の識別子は維持され、切断状態も発生しなかった。

| 経路 | Releaseでの確認 |
|---|---|
| 近距離直接、近距離中継、Internet、近距離＋Internetの仮想経路 | 4条件を各5回確認。近距離中継と混在では、旧鍵を持つ端末を唯一の中継役にして双方向の音声を確認した |
| Mac上のネイティブQUIC／UDP | 5回確認。最後の鍵の設定後、双方向の受信を観測するまで約10.5〜15.5ms。続く40パケットは各回すべて到着 |
| Mac上のネイティブWebRTCとローカルSFU | 5回確認。最後の鍵の設定後、双方向の受信を観測するまで約11.0〜14.7ms。続く40パケットは各回すべて到着 |

ネイティブ経路は10ms間隔で受信を観測した。上の時間は新しい鍵で送信を始めてからRTCの受信イベントまでで、鍵の配送時間・切替待ち・実際の発音を含めない。旧鍵の端末は試作と同じ版を使い、切替後も既存の制御メッセージを受け取った。

Releaseの単独計測では、各方式・各入力で2,000件を既存の音声送信・受信処理に通した。AAC ELDの80B入力は、処理時間の95パーセンタイルが36.6µsから41.5µs、包んだ結果が421Bから497B。PCM16の960B入力は38.1µsから46.8µs、1,296Bから1,387B。Macでの暗号化・復号と共通中継処理の比較で、無線転送・バッテリー・実機の負荷は未測定。

一巡目は、両経路の音声保護と中継をRTCの共通処理に置き、誰が除外できるかと鍵を誰へ届けるかをAppが判断する境界を照合した。二巡目は、旧世代の鍵への差し戻し、切替中に届いた音声、旧鍵を持つ端末での中継、近距離とInternetをまたぐ経路を確認した。製品で使うには、署名付き除外の認可と配送、鍵が届いていない端末の扱い、圏外や再起動をまたぐ世代の永続化、旧版の参加条件を決める必要がある。すでにAppや音声出力へ渡されたデータ、ロック中の切替完了、実サービスでの配送は未検証。
