# 複数端末の経路断と自動復旧

2026-11-01の複合通信障害への要望に対し、`a7786236`から隔離したRTC工程で`GroupContinuityTests`の仮想経路を拡張した。既存のRouteManagerと暗号化GroupRelayで成立したため、製品コードは変更していない。

| 検証 | 確認できた範囲 |
|---|---|
| 4端末・3経路の同時断 | Localだけ、Internetだけ、両経路のgateway 2台を構成。2端末のInternetと別端末のLocalを同時に失敗させ、残存Localの会話を確認 |
| 異なる復帰順 | Internetだけの端末が先に戻る場合とgatewayが先に戻る場合をparameterized testで確認。Appからstartし直さず既存retryで再参加し、相互の新しい音声が届く |
| 別ネットワークへの移動 | 最後のLocalを他の参加者のいないネットワークへ復帰。Localの発見と相手への到達性を分け、Internet経由で会話を維持 |
| 古い音声と全体切断 | 圏外中に送ったmarkerが復帰後に再生されず、残存経路のある端末群が全体disconnectedへ変化しないことを確認 |
| 影響範囲 | 同じfixtureを使うsuite全3メソッド・5ケースが28.704秒で成功。既存8端末のInternet不達、混在中継とgateway離脱も成功 |
| 入力一致 | RTC関連39入力の試験前後一致。mainへのコピー後も39入力が一致。`.validation/network-recovery-delivery/{source-before,source-after,summary,delivery-check}.json` |

初回は実行環境のsandbox制限で失敗した。その後、新しい試験の最後の経路は既存2→4→8秒のbackoffに入るため、fixtureの一律6秒待機が先に満了した。製品のretryや合格条件は緩めず、その復帰段階の待機に説明と上限を付けた。先行ログと最終`final.log`を保存している。

本試験は経路の失敗通知と到達性を仮想化する。実Wi-Fi／セルラーの揺らぎ、OSによるネットワーク通知、実SFU、Appの本人profile再認証、音響品質・電池消費を証明しない。これらは[混在グループの受入](../未確認事項.md)に残す。

## 背景中の切断の再調査の基準（2026-11-18）

利用者の重大報告を最優先で確認した。iPhone 18 Pro（iOS 27.2.1）はpair済みだがDeveloper Mode=disabled、DDIサービス不可、tunnel=disconnectedであり、現在は実機のデバッグ受入を実行できない。接続情報だけを読み、端末の設定やアプリを変更していない。発生時のLocal／Internet経路と背景移行からの時間を利用者へ確認中。原因は未確定のまま維持する。

background-call-lifecycle-baseline-20261118でiOS AppのCallLifecycleTests・BackgroundCallOwnerTests・BackgroundCallStorageTestsの25件が成功し、失敗・skip・runtime warningは0、入力指紋は標準採番以外一致した。これは模擬backendの制御・経路障害・音声session操作・アカウント所有の基準であり、実OSの背景継続や実無線の切断を再現した結果ではない。buildの次回番号は1059になった。

現行コードではrecoverableなlinkFailedでもstopAudioPipelineがsessionの非active化を要求する。これは既存の候補であり、背景で実行が停止するか、今回報告と同一原因かは未確認。明示終了・自動終了・利用権による停止と、背景移行・経路障害・session停止の時系列を両端で照合してから対策を選ぶ。通常の自動切断は初期値3時間、Watchは5分だが、報告端末の実設定と発生時間は不明である。原因未確定のまま音声sessionを保持する回避策は追加しない。

実機条件の確認を待つ間は、バックログの重要度に従い、制御は成立するがUDP媒体が届かない場合の経路選択・復旧を独立した最小単位で検証する。音声の途切れ・遅延の品質評価は今回の対象外を維持する。

## iOSの背景制限の調査と実Appの待機往復（2026-11-18）

利用者の追加指示により、近距離とInternetの通話成立・初回接続・相手待ち・再接続をそれぞれ受入対象にした。Appleの現行資料を調べ、背景で音声処理を続けている状態と、実行停止の対象になった状態を区別した。根拠と8条件は[背景実行マトリクス](../../backlog/未実装課題.md#ios背景実行の調査と受入マトリクス)へ保持する。待受だけの無音再生や新たな背景通信権限は使わない。

実AppのBackgroundCallLifecycleUITestsを追加した。ios-background-waiting-baseline-accepted-20261118のiOS UI2件が成功し、両モードで新groupの相手待ち→Home→35秒→前面復帰→同じ通話→明示終了まで通った。失敗・skip・runtime warning 0、入力指紋は標準採番以外一致。最初の試行はHome直後の状態確認が早すぎて停止したため、OSの遷移を待つようにした。次の試行はStandardの終了確認に同名のOS要素が複数あり、firstMatchへ修正した。どちらも製品の背景切断の再現に数えない。

bounded試行では所有するSimulatorだけでNative Networkログを収集し、復帰時のlistener inbox再開を観測した。実Appは本番のRTC factoryを使うが、本人確認・保存先は隔離fixtureである。Simulatorの35秒往復は物理iOSの停止、背景での相手の後参加、成立済み通話の双方向音声、実SFU、長時間の維持を証明しない。この試験の成功で8条件を完了扱いにしない。

XcodeBuildMCPのlist_simsはホストのxcrunがCommand Line Toolsを参照してsimctlを見つけられなかったため、既存のlease付き自動検証入口からDEVELOPER_DIRを指定した。ホストのXcode選択設定や利用者のSimulatorは変更しない。build 1060で利用用途への重要度を再比較し、背景継続・待機・再接続を最優先に保った。最終build後処理の次回用番号は1062。次は停止対象の接続意思とNative資源を分離し、前面復帰で元の期限・接続先・ミュートを保つ実装を検証する。
