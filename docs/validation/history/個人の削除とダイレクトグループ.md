# 個人の削除とダイレクトグループ

2026-11-15。個人（保存ユーザー）を削除してもダイレクトグループ（`kind == .direct`）がAdvancedのGroupsに残り、メンバーにも相手が残る不具合（2026-11-10の利用者報告）を直した記録。

## 原因

`GroupRepository.removeUser`がusersから相手を除くだけで、groupsを全件そのまま書き戻していた。「一覧からの削除はgroup内のID・鍵・進行中の通話を保持する」という通常グループ向けの契約が、ダイレクトグループにも当てはまっていた。

## 直したこと

| 対象 | 動作 | 正本 |
|---|---|---|
| 削除 | 相手のダイレクトグループ（端末宛ては相手member ID、アカウント宛ては相手principalで対応）・鍵・未応答の受取証明を、usersの削除と同じatomic commitで消す。通常グループは変えない | [通信仕様](../../spec/App/通信仕様.md)の「ユーザー更新」「一覧削除」 |
| 進行中の通話 | その相手との通話を切断し、選択も外す | 同上、[Call画面仕様](../../spec/App/UI/Call.md) |
| 確認 | 接続中の相手を削除するときは、グループの削除と同じく本文「今の接続は切断されます。」と確定「切断して削除」。Standard・Advancedの行のDelete、相手の設定の`Delete User`、受け取った招待の「この相手を削除」で同じ | [Call画面仕様](../../spec/App/UI/Call.md)、[招待と登録の設計](../../design/招待と登録の設計.md#接続中の相手グループを削除するとき) |
| 既に残ったデータ | 読込時（通話のない時点）に、相手の保存ユーザーがいないダイレクトグループを鍵とともに消してcommitする | [通信仕様](../../spec/App/通信仕様.md)の「ユーザー更新」 |

古い招待での復活は、既存の処理済みIDと連絡先招待の記録の拒否のまま防ぐ（ダイレクトグループがなければ受取証明は`invalidUpdate`で拒否される）。新しく発行した招待で登録し直すと、新しいダイレクトグループができる。

## 検証

| 範囲 | 条件 | 結果 |
|---|---|---|
| macOS App単体テスト | `scripts/validate.sh macos`（標準TestAction、基準commit `1076190`に本修正を加えたsource） | 成功。新規`DirectGroupDeletionTests`（同時削除と通常グループの保持、保存失敗で両方残る、孤立データの読込時整理、通話中の削除で切断）と、旧契約（削除後も通話を維持）を前提にしていた10件のテストを新しい契約へ改めたもの |
| iOS UIテスト | 専用Simulator（iPhone 17 Pro）で`testDirectCallsReuseUserDestinationWithoutAddingParticipants`と`testStandardUserSettingsShowTheNamesReceivingAndDelete` | 成功。接続中の相手の削除で確定が「Disconnect and Delete」・本文「The current connection ends.」、削除後にCurrent Callが消え、AdvancedのDirect Groupsの件数が1減る |

## 範囲外

相手の端末への削除の反映（相手側にも自分のダイレクトグループが残る）と相手側の接続の終了は[インターネットとローカル接続での招待・削除同期](../../backlog/未実装課題.md#招待と削除の同期)で扱う。確認を出している間に接続の状態が変わったときに古い確認を閉じる動作は、グループの削除と同じく未実装。
