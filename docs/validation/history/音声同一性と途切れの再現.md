# 音声同一性と途切れの再現

## 指示と対象

2026-10-29、利用者から「iPhone同士の音声がブツブツ切れ、実用にならない。複数の音声を用意し、実際のテスト出力が同一性を保つか確認する」と依頼された。実機固有の問題とは扱わず、通信込みのSimulator試験と、通信を外した結合試験で確認した。

対象はHEAD `0280f4d5`上の作業ツリー。音声処理の製品コードは変更せず、E2Eの入力・測定・判定だけを追加した。既存のproject・Package.resolved・開発環境文書の変更は今回の変更に含めていない。各runのsource-manifest.jsonが当時のsourceと設定のSHA-256を保持する。

## 結論

音声の同一性・連続性は不合格。Local / WebRTCの18測定すべてで従来の部分照合は合格水準だったが、全時間を対象にした連続性判定では不合格となった。通信・VAD・送信Isolationを外したiOS単独の2条件でも不合格となり、通信に依存しない音声処理経路の問題を再現した。実機でしか検出できない問題という説明ではない。

## 原因の範囲と未修復

結合試験の20ms入力ではTX sourceの予約リセットは0回だが、RX sourceは36回、実出力は12回だった。100ms入力ではTX sourceが70回、RX sourceが9回、実出力が23回だった。sourceの値は起動からの累計、実出力の値は20秒の測定区間の増分である。

`MixerPCMSource`と`SystemAudioOutputStreamBackend`は、100msの予約予算を超えると`.interrupts`で既存予約を置き換える。実captureでは100ms分のframe、Mixer tapでは複数の20ms frameのまとまった転送が観測される。データを渡す周期と予約予算の境界、およびsinkから再生へ渡す際の時間連続性が調査対象となる。リセット回数と欠落の同時観測は原因候補を絞る証拠であり、各欠落の原因が確定したことや、予算を広げれば解決することを意味しない。

製品の修復は未完了で、品質検査では引き続き不合格とする。過去の132測定成功は当時の部分照合基準での到達確認であり、今回の連続性基準での合格実績に読み替えない。修復は[未実装課題](../../backlog/未実装課題.md)、iPhone同士での最終確認は[未確認事項](../未確認事項.md)へ引き継ぐ。

### 送信分離の再ONで同じ症状が出たときの比較

初回ONでは意図した量の雑音が残り、OFFを経由した再ONだけで抑制が強くなった。通信と受信を経由しない送信処理の出力で差を再現できた。iOS SimulatorのRelease試験で、各状態に同じ `speech-ja` の先頭8秒と振幅0.03の397 Hz正弦波を入力した。送信処理を動かしたまま順に切り替え、各出力の先頭1秒を除く6秒間の397 Hz成分を測った。

| 操作順と送信出力の判定 | Build 1378 修正前の振幅 | Build 1382 修正後の振幅 |
|---|---:|---:|
| ① 初回ON（初回 > 0.005 かつ 初回 < OFF × 0.8） | 0.01607 | 0.01607 |
| ② OFF（バイパス時の基準） | 0.03008 | 0.03008 |
| ③ 再ON（初回 × 0.8 ≤ 再ON ≤ 初回 × 1.2） | 0.00199、不合格 | 0.01607、合格 |

壊れていたのは「送信の分離を再度有効にすると、初回と同じ混合比で音が出る」という契約。OFFでmixを100%に書き換え、ONで50%に戻す経路では、設定値が50%でも出力が初回と異なった。修正 `e2a79960` は送信のAudio Unit生成時に50%を決め、切替時のmix書き換えを外した。再発時はまずこの3点の振幅と送信切替の差分を比べる。送信出力で3点とも一致し、通話の最終出力だけに差が残る場合は、同じ発話区間の復号直後・ミキサー・最終出力を比べ、修正する段を絞る。

比較元は `.validation/transmit-isolation-toggle-red-1378/isolation.log` と `.validation/transmit-isolation-final-1382/isolation.log` の `Tone amplitude at 397 Hz`。各runの `source-manifest.json` で試験時のソースを照合できる。元の不具合が入った変更とAudio Unit内部の挙動は特定していない。ここで復旧を確認したのは送信出力の抑制量。Build 1382でも送信ON時の無音141msは上限120msを超え、上記の通話遅延も基準未達だった。

### 到着後の処理待ちを通信の揺れに含めない

### 起動時の無音再予約でpacket化の待ちを減らす案を比較する

再生中のplayer clockと直近の描画ブロックから現行コードと同じ書込位置を計算した。48kHzの1サンプルずつ識別できるPCMを240 sampleずつ連続予約し、全480 sampleの値・順序・間隔と、実描画開始が指定位置の±1 sampleに入ることを調べた。通常予約と、予約済みの無音を `.interrupts` で置換する条件を各8回測定。オフセットは、書込位置に対し前後1描画ブロック、−96／−1／0／+96 sample。1描画ブロックはMacが256 sample、Simulatorが512 sample。提出位相を変え、実際の位相も記録した。条件ごとの位相は4分割のうち2〜4区分を通った。

| 失敗を観測した条件 | 先頭で欠けたサンプル | 観測回数 |
|---|---:|---:|
| Macの通常予約、書込位置より1描画ブロック前 | 256（5.33ms） | 1／8 |
| Macの通常予約、書込位置より96 sample前 | 96（2ms） | 1／8 |
| iOS Simulatorで無音を置換、書込位置より1描画ブロック前 | 480（10ms、2バッファ全部） | 1／8 |

両環境のそれぞれ96試行のうち、書込位置とそれ以降の48試行はいずれも全サンプルが指定位置で連続して描画された。前へ出しても描画できた試行はあったが、上表の3件で実出力が欠けた。同じ語頭と後続を保つ条件では、書込位置を越える前倒しを一律には使えない。試験は予約済み無音と合成PCMのnative描画を対象とし、起動時のAAC内部状態や物理端末ごとの余裕までは確定していない。

## 送信90%と受信80%で声の分離を切り替える

2026-11-25。Macのアプリ試験で、送信、受信全体、相手別をそれぞれON／OFF／再ONにした。従来の構成では3つの処理すべてで50%となり、指定値の検査が9か所で失敗した。試作では送信90%、受信全体と相手別は80%で、すべての操作で割合が保たれた。[設定と配線](../../spec/App/Configuration/Bindings/Audio/Effectors/SoundIsolation.md#通話の音声保持)

Simulatorの送信単体試験では、397 Hzの付加音がOFFで0.03008、初回ONと再ONでともに0.00476だった。OFFから約16.0 dB下がった。受信では、分離の対象にした600 Hzと1,100 Hzが基準の約20%になった。相手別の切替中、対象外の相手の定常音を保った。

最初の連続切替試験では、送信分離中の600 Hzが約0.010〜0.011となり、試験が求める0.012を下回った。この試験は処理を切り替えたときの無音と波形の段差を測る。分離後にも検査用の音が残るよう、合成入力の振幅を0.15から0.22へ変更した。出力の判定値は維持した。

再試験では、送信・受信の分離とコーデックの切替を含む14区間すべてで、定常波形の検査が通過した。切替の最大無音は100 ms、最大サンプル段差は0.00893だった。音声破棄、再生リセット、処理失敗は0件。共有I/Oの入力モード切替も通過した。[切替試験の判定条件](../../development/音声E2Eテスト.md#切替時の基準を確かめる試験と切替間隔の限界を調べる試験)

同じRelease相当のAAC-ELDの通話を、ローカルWorkerを通るWebRTCで比較した。試作と50%の対照に使った発話、設定、試験手順は同じ。ビルド番号と分離の割合だけが異なる。次の表は合成雑音を加えていない受信方向で測った、最終出力の発話欠落の最大値。

| 有効にした分離 | 50% | 送信90%・受信80%の試作 |
|---|---:|---:|
| 全OFF | 0 ms | 0 ms |
| 送信の初回ON | 0 ms | 30 ms |
| 送信の再ON | 0 ms | 50 ms |
| 受信全体ON | 0 ms | 20 ms |
| 相手別ON | 10 ms | 30 ms |

試作の送信ONと再ONは、復号直後にもそれぞれ30 msと20 msの欠落があった。受信側だけONの場合、復号に欠落はなく、受信ミックス以降に現れた。合成雑音を加えた方向では、全OFFに比べて送信ON・再ON時の付加音は復号後に約15〜18 dB減った。受信ONでは再生時の付加音が約12〜14 dB減った。この方向の発話一致率は全OFFでも基準に届かなかった。設定ごとの効果と発話の欠落を分けて扱い、音声の判定値は維持する。

欠落が出た方向と同じ合成発話を、通信なしで実Audio Unitへ入力した。分離OFF、50%、80%、90%でそれぞれ試した。2周目と3周目を照合した。4条件とも発話一致率は100%だった。有声欠落も0だった。次は、収録後から送信の分離・Dynamics・符号化までを順に比べる。受信の欠落は復号直後と分離後の波形を引き続き比べる。

通話で発話が欠けたため、送信90%・受信80%の試作は製品へ反映していない。証跡は `.validation/code-2520-isolation-mixes/` の試作差分、切替試験、WebRTCの比較、分離器単体の試験。各通話試験で入力の一致と専用Simulatorの回収を確認した。次回用番号は2620。
