# 文書作成規約

本書は文書・計画・要求管理の作り方を定める。アプリが利用者へ提供する価値と機能は[製品要求](../requirements/製品要求.md)、実装の制約は[開発方針](開発方針.md)へ分ける。

## 望ましい行動を示す書き方

本リポジトリの文書全体に適用する。規約・要求・計画・README・AGENTS.md等のエージェント入口・スキルと参照資料も、次の基準で記述・更新する。

| 記述の種類 | 書き方 |
|---|---|
| 通常の指針・優先順位 | 望ましい行動・選択・配置・完了状態を肯定形で具体的に示す。「何を、いつ、どの範囲で行うか」と判断根拠を記す。例: 「周辺を先に作らない」→「重大な不確実性を最小実装で先に検証する」 |
| 条件・未完了時の対応 | 適用条件と次の行動を示す。例: 「未検証で完了にしない」→「必要な検証と回帰が成功した範囲を完了とし、残りは未確認として記録する」 |
| 真の禁止事項 | 機密漏えい、無断のデータ破壊・権限拡大、検証結果の捏造など重大な害を防ぐ境界と、利用者が明示した禁止は「禁止」と明示する。対象・理由・適用範囲と、許可範囲内の代替行動を併記する。通常の好みや優先順位は上の指針として記す |
| 事実・仕様の境界・履歴 | 非対応、失敗、未実行、能力上の限界は事実として正確に記録する。過去の引用・証跡・コード例は意味と原文を保持する。否定形の解消と、事実や制約の変更を区別する |
| 表現変更の受入 | 変更前後で適用対象・必須/推奨の強さ・実行順序・数値と単位・例外・権限・完了条件を対照する。同じ状況で同じ判断になることを受入条件とし、曖昧さや情報差があれば補ってから反映する |
| 正本と参照 | 共通ルールは正本へ集約し、スキル・入口には担当する判断と必要な節への参照を置く。意味・強制力・条件・例外を保持して表現を整える |

## 記述規則

| 項目 | ルールと理由 |
|---|---|
| 基本ルール | [開発方針](開発方針.md)を適用する |

| 表現 | 条件・対象・行動・完了状態が実装時に判断できる文で記述する |
| 図表優先 | 認識齟齬を防ぐため、仕様は図表を使う。特に画面・状態・設定は表を優先する |

| 詳細度 | 実装者が迷わないよう、背景、理由、現状との違い、明確な仕様、体験の差、実装方針、注意点をできる限り詳しく説明する |

### 条件と結果の記述

境界値は単位付きの比較式（`<`、`≤`、`=` 等）、複合条件は名前を付けた述語と `AND`・`OR`・`NOT` で表す。入力の定義・単位・観測時点を近くに置く。条件によって結果が分かれる処理はデシジョンテーブルを基本にし、各行に条件、出力または次状態、発生する副作用と担当を載せる。条件に関係しない入力と、値が不明・未取得の入力は区別する。境界の等号、該当なし、失敗時を含め、対象の入力に結果が一つ決まるか確認する。重なる規則を順に適用する場合は優先順を明記する。背景・選択理由・成功した仕組みは文章で添える。

表の各入力をどの公開契約から得るか、出力を誰が受け取るかを確認する。画面の変更だけで保存形式やプラグイン内部の条件まで書き換えるなら、同じ判断を複数箇所に持っていないかを見直す。一方を差し替えても維持する入出力・失敗時の動作を仕様上で説明できることを、低結合の判断に使う。[送信形式変更の例](../spec/App/音声処理仕様.md#送信形式変更の判定)

## プランの策定

- 要件を満たすための具体的な実装ステップを示す。
  - 実装の依存関係を明確にした上で、実装が円滑に進む順序や優先順位を明確にする。
- 経験や前提知識の少ない実装者やモデルでも、そのまま実装に入れる具体的な内容とステップを示す。
- 背景、理由、現状との違い、明確な仕様、体験の差、実装方針、注意点などをできる限り詳細に説明する。
- プランは作業手順や指示だけではなく、設計書や仕様書のような形式で、実装者が完了条件を理解できるように記述する。
- 実装者が判断に迷わない、実装をストレートに進められる内容とする。
- プラン冒頭に指示内容と背景を記載する。修正時は特に指示がない限り既存の内容・情報量を維持して指摘を反映する。

## 更新責任

バックログに記録する内容のうち、確定した利用者要求は同じ変更で製品要求・パッケージ要求へ、開発上の恒常ルールは対応する方針へ反映する。課題には正本の該当見出しへの根拠リンクと、未実装の差分・完了条件・未決事項を残す。バックログだけを要求の唯一の保存先にせず、仕様や実装の存在だけを要求の代わりにしない。判断待ちの案は確定要求へ昇格させず、既存要求への参照を候補の採用根拠と混同しない。

| 対象 | ルール |
|---|---|
| 実装 | [製品要求](../requirements/製品要求.md)を満たすこと |
| 外部サービスの設定手順 | App・server・構成や権限の変更でApple／Cloudflare等への設定が変わるたび、同じ変更で[設定手順の正本](開発方針.md#applecloudflare等の外部設定を常に手順化する)を更新する。実装不足と利用者の設定待ちを分ける |
| 仕様 | 実装前の設計案は`docs/backlog`に置く。実装と同じ変更で`docs/spec`を更新し、常に現行実態と一致させること |
| 画面 | 画面設計案は課題へ置き、実装と同じ変更で画面項目定義を更新すること |
| 構想メモ | 未採用案も`docs/backlog/未実装課題.md`へ統合し、採用済みと判断待ちの状態・条件を明記する。旧`改善候補.md`は参照専用とし、順位と次の行動は共通一覧で管理する |
| 差分整理 | 未実装の作業は`docs/backlog/未実装課題.md`、未確認は`docs/validation/未確認事項.md`へ分ける。現行の制限・非対応時の挙動は仕様に残す。目的と情報を保持したまま、現行仕様・残課題・未確認へ正しく分類する |

### 記載後に元の指示と意図を照合する

要求、課題、設計、仕様、手順、検証記録、担当者への引継ぎ、AIに作業を指示するスキルを書くときは、新規・更新・要約・翻訳のたびに、書き終えた文章を元の指示・背景・訂正に照らして読み直す。形式・リンクの自動検査とは別に毎回行い、転記や要約の正しさを更新後の文章だけから判断しない。単独作業では記載者自身が照合する。

- 対象・利用者・画面・状態・適用条件・優先順位・除外範囲が指示どおりかを確認する。
- 要求された操作と結果を具体例に戻し、表示だけの変更、操作可否の変更、保存や実処理の変更を取り違えていないか確認する。たとえば「コントロールを無効化」は既存コントロールを残して操作不可にする要求であり、「無効」という文字への置換ではない。補足説明を付けても、操作不可の代わりにはならない。
- 記載から別の担当が導く期待動作・完了条件を元の指示へ照らし、意味の欠落、逆転、根拠のない追加条件や範囲拡大を修正する。確定した要求と提案・未決事項を区別する。
- 要求・課題の詳細・共通一覧など同じ内容を載せた箇所も照合し、一方だけ異なる意味を残さない。記録しただけの状態と実装済みを区別する。

照合結果と修正点は、今回の変更の説明または既存の検証記録へ簡潔に残す。意図が定まらない箇所は推測で確定せず、その箇所を未決として扱う。元の指示で判断できる内容を再確認する必要はない。

#### 日本語の技術文書を検査する

仕様、要求、バックログを含む `docs/` 配下のMarkdownと開発スキルをtextlintで検査する。本文と表のセルに[日本語技術文書向けのルール](https://github.com/textlint-ja/textlint-rule-preset-ja-technical-writing)を適用する。表の項目名や状態には句点を求めない。

初回と依存の更新時は、Node.js 22.12以降で1行目を実行する。文書をコミットする前に2行目を実行し、失敗したら文章を直してから再検査する。

```sh
npm ci --prefix tools/doc-lint --ignore-scripts --no-audit --no-fund
python3 scripts/check_documentation.py
```

通常の検査では、新しい文書を全文検査する。既存文書では、導入時にそのファイルで検出した指摘と照合する。新たに「要修正」が出たら検査は失敗する。コミットの前後で同じ基準を使う。

| 場面 | 検査と修正の基準 |
|---|---|
| 通常の説明 | 技術文書向けプリセットの基準を使う。目安は1文100文字以内、読点は3個まで。名詞の列挙を区切る読点は数えない。文を分けるときは、条件がどの操作にかかるかを保つ |
| 文体と引用 | 仕様は常体、利用手順は敬体で書ける。本文と箇条書きはそれぞれ文書内の文体をそろえる。画面の問いを引用する場合は「表示しますか？」のように元の疑問符を保つ |
| 原因や見込みが未確定 | 推量を表す語句は「要確認」として表示する。観測した事実と推測を元の記録で照合する。確証のない原因を断定せず、何を確認すれば分かるかを添える |

指摘を直した後は、元の要求と照合し、条件と例外を保っていることを確かめる。表の結果欄も、設定を変えられる条件を残したうえで「設定を変更できます」と書ける。文の意味が決まらない場合は[監査の停止・再開条件](#監査の停止再開条件)に従う。

既存の指摘も含めてすべて調べるには `npm --prefix tools/doc-lint run lint:all` を使う。端末で直接実行すると、ファイル、行、桁、ルール名を確認できる。浅いクローンで導入時のコミットを参照できない場合は、Gitの履歴を取得してから検査する。

#### 次の読者が同じ意味に読めるか確かめる

会話に参加していなかった読者の立場で、変更した文章から「誰が、いつ、何をすると、誰に何が起きるか」を自分の言葉で説明する。書き手が省いた主語や条件を会話の記憶で補う必要があれば書き直す。決定と希望、許可と義務、観測した結果と原因の推定を元の言葉に照らし、理由や例外によって判断が変わる部分を残す。

| 読み直す場所 | 意味が変わる例と確かめ方 |
|---|---|
| Standard画面と一般利用者が見るダイアログ | 見出し・本文・各ボタンを一緒に読み、日本語と英語それぞれで、押した後に起きることを説明する。「グループタブを表示しますか？」に対する「今はしない」／“Not Now” は、表示の案内を閉じる選択。「招待を断る」／“Decline invitation” と書けば、相手の招待まで断る意味になる。実際の操作、読み上げ、両言語の説明が一致するかを[画面文言の検査手順](開発方針.md#利用者向け文言の意味と平易さを継続検査する)で確かめる |
| 仕様・検証記録・引継ぎ | 「音声改善済み」では、次の担当が何を確かめたのか分からない。[送信側の声の分離の記録](../validation/history/音声同一性と途切れの再現.md#送信分離の再onで同じ症状が出たときの比較)なら「シミュレータで送信側の声の分離を入れ直すと、試験音に含めた397 Hzの音は初回と同じ大きさまで弱まった。一方、切り替えたときの無音は141ミリ秒で、上限の120ミリ秒を超えた」と書ける。戻った性質と残る問題の両方が伝わるかを確かめる |
| 作業を指示するスキル・手順 | 「適宜対応」「差分を閉じる」のような表現は、その一文を読んだ担当が選ぶ操作に戻す。たとえば「文書と測定結果で対象の端末が違う場合は、測定に使った端末を検証記録に追記し、同じ条件の結果を比べ直す」。初めて読む担当が作業を始める条件と終える条件を判断できるかを試す |

新しい略称や名詞をいくつも重ねた言い方を作らず、読者が使う名詞と具体的な動詞を選ぶ。技術仕様では、照合に使うAPI名・ログの項目名・単位を正確に保ち、読者に説明が必要な語は初出で役割を添える。表の見出しや画面の問いで対象が明らかな場合は、その文脈を生かす。

変更中は `python3 scripts/review_wording.py` で読み直す候補のファイル・行・問いを確認できる。コミット後は `--base` に変更前のコミットを指定する。通常の検証でも `wording-review.log` に候補を残す。語が見つからなくても、削った一文にしかなかった条件や、自然に読める誤訳は元の指示と比較して初めて分かる。意味が二通りになる箇所は[監査の停止・再開条件](#監査の停止再開条件)に従って直し、同じ場面でもう一度読み直す。繰り返し誤解された言い方は、何と何を取り違えたのかを該当する用語集か手順の例に残し、語から見つけられるものは候補の検査にも加える。

### コード全体整理の次の回に仕様全体を簡素化する

2026-11-21の利用者指定。[次回のコード全体リファクタリング](開発方針.md#次回リファクタリングの全体簡素化)を行う回の、その次のリファクタリング機会では、仕様全体の整理を最重要として扱う。コード整理の要求を置き換えず、二つの回の順序と各完了条件を分けて管理する。

App・UI・package・server・通信・音声・設定・配布・自動化等の現行仕様を全体から見渡し、参照する要求・方針・設計・手順も照合する。同じ契約の重複、矛盾、古い前提、責務の分散、不要な層・分割・中継・例外・独自管理を作らせる記載をすべて特定し、所有する正本へ統合・修正する。文章の短縮だけで閉じず、文書どおり実装したときに冗長な構成へ戻らないことを確認する。要求・現行仕様・設計案・履歴・検証の役割を混ぜて一冊へ集めることは統合の目的にしない。

重要な情報は落とさない。目的・背景・理由、責務と依存、操作と状態遷移、可否・例外・失敗と復旧、既定値・数値・単位、OS／通信／codecの必要な差、認証・秘密・保存と通信互換性、品質・受入条件、未決・未確認の区別を保持する。整理前の重要情報と統合先を対応付け、移動・統合・削除の理由と参照先を確認する。重要情報を会話履歴やコードの読解だけに依存させず、簡素化後の文書から同じ振る舞いを再実装・検証できる状態を保つ。

整理後の仕様全体に敵対的レビューを3回行い、各回は修正後の最新文書と参照先を対象にする。構成・責務と重複、重要情報と条件の保持、実装・要求との整合と文書だけでの再実装を含む観点で反証する。対象・指摘・重要度と理由・対応差分・再検査結果を記録し、重要な指摘はすべて対応する。3回目の修正で生じた問題も再確認し、重要指摘を残したまま回数だけで完了にしない。後続課題への先送りや根拠のない重要度の引下げで対応済みとしない。指摘を不採用と判断する場合は反証と判断理由を残す。

小単位ごとに内容・参照・実装との照合を行い、commitとmain／origin／preview同期を閉じる。完了時には、統合前後の情報対応、不要な構成を招く記載の修正例、3回のレビューと重要指摘の対応、文書からの再実装の監査結果を示す。仕様と実装の食い違いが残る場合は解消または未達を明示し、未確認を受入済みへ変えない。受入後は[全体整理のサイクル](開発方針.md#全体整理のサイクル)に従い、次の回でコード全体を再整理する。

### 再コード整理の次の回にデザイン資料とユースケース全体を再構成する

2026-11-21の利用者指定。[次回のコード全体整理](開発方針.md#次回リファクタリングの全体簡素化)→[仕様全体整理](#コード全体整理の次の回に仕様全体を簡素化する)→[再コード全体整理](開発方針.md#仕様全体整理の次の回にコード全体を再び簡素化する)の、さらに次のリファクタリング機会では、デザイン資料とユースケース全体の再構成・簡素化を最重要として扱う。先の三つの回とは別の実施回・成果として管理する。

デザインシステム、Standard／Advanced・各OS・端末の設計、見本、操作・通知・招待の流れ、要求からのユースケース対応とストーリーマップを横断して見直す。重複・矛盾・古い前提と、冗長な画面・導線・層・独自状態管理など無駄な構成を生む記載をすべて洗い出し、正本・参照・必要な差分へ統合する。重要情報を保持しながら全体構成を練り直し、シンプルに記載する。文書の短縮だけでなく、それに従った設計・実装が不要な複雑さへ戻らないことを確かめる。

ペルソナ定義のない人物・一般的な「ユーザー」は、元の利用用途と背景に応じたペルソナへ対応付ける。既存定義で足りなければ、その用途に根拠のある目的・状況・制約で定義し、根拠のない人物属性や新しい用途を追加しない。方向のある関係・操作では、招待する側／受ける側、通知の送り主／受取人、削除・除外する側／反映を受ける側等の立場と、誰から誰へ何が届くかを明記する。ペルソナと場面ごとの立場を区別し、同じ人が別場面で反対の立場になることも表現する。利用者の動機、場面、端末・接続・権限、前景／背景、無音・聞き専、グローブ等の制約、操作・遷移、本人と相手に届く結果を保持してユースケースを改訂する。

重要な目的・理由・条件・例外・失敗と復旧、操作可否・状態・情報の所有、アクセシビリティ、安全性、必要なOS／画面差分、未決・仮実装・未確認の区別は落とさない。整理前の人物・ケース・契約と整理後のペルソナ・立場・ケース・正本を対応付け、網羅性と意味の保持を検査する。要求・設計案・現行仕様・検証結果を混ぜず、資料の整理だけで製品や実画面を受入済みにしない。

この回の最新資料全体に対して、新たに敵対的レビューを3回行う。各回で構成と重複、ペルソナ・立場・方向と用途の整合、重要情報・ケース・画面間の契約の保持を含む観点から反証し、前回の修正も再検査する。対象・指摘・重要度と理由・対応差分・再検査結果を残し、重要な指摘はすべて対応する。先の三つの回のレビュー回数は流用しない。3回目の修正後の重要指摘も確認し、先送り・根拠のない重要度引下げや回数の消化だけで完了にしない。指摘の不採用には反証と判断理由を残す。

小単位で内容・参照・要求との意図照合、必要な設計見本・関連仕様との整合を検査し、commit・main／origin／preview同期を閉じる。重要指摘や重要情報の欠落・ケース不整合が残る間は未完とする。受入後は、次の回で[テスト全体の構成・実効性・品質を見直す](開発方針.md#デザインユースケース整理の次の回にテスト全体を見直す)。

### 意味が削られた既存表現を画面と文書の全体で修復する

2026-11-21の利用者要求。すでに短い語や圧縮表現へ置き換わり意味が痩せた言葉を、画面上・ドキュメント上で総点検して修正することを最重要課題の一つとする。新しい文言の混入防止だけでは完了にせず、既存の文言・本文全体を対象とする。Standardとダイアログを重点としつつ、Advanced・各OS／端末・共通画面・通知・アクセシビリティ文言、要求・仕様・デザイン資料／見本・ユースケース・手順・エージェントルール・バックログ等も照合する。

元の利用者指示、用途・背景、過去の意味を保持した版と現行の操作・契約を根拠に、主体・相手・対象・方向・条件・操作・結果・理由・強制力・例外・数値・未決や未確認の区別が失われていないか調べる。失われた情報を日常的で具体的な日本語・英語へ戻す。長文化や元の語への一律な差戻しを目的にせず、伝わる意味を回復する。元の意図を推測で追加せず、根拠が足りない箇所は未決として記録する。履歴・引用・証跡の原文を改変して過去の事実を消さず、現行正本の訂正と必要な注記を区別する。

修正後に少なくとも3回、各回で異なるモデルを利用してレビューを行う。少なくとも3種類の異なるモデルによる点検とし、同じモデルの別セッション・担当・思考設定だけを別モデルとして数えない。各回には元の根拠と最新の修正内容、前回指摘と対応を渡し、意図の保持と分かりやすさを再検査する。使用モデル名・利用可能な版情報、対象、根拠、指摘と重要度、対応差分・再確認結果を記録する。必要なモデルを利用できない場合は不足を明示し、同一モデルによる代替を条件達成と扱わない。

重要な指摘はすべて対応し、3回目の修正後にも意味の欠落や新しい曖昧さがないか再確認する。回数だけの消化、根拠のない重要度引下げ、後続課題への移記だけで完了にしない。機械の単語検査・リンク検査だけで分かりやすさを受入済みにせず、必要な実画面・操作と文書から導く判断を照合する。根拠→修正前→失われた意味→修正後の対応を示し、小単位で検証・commit・main／origin／preview同期を閉じる。

## 再実装に必要な記録

コード・テスト・会話履歴を失った場合にも、別の担当が[文書入口](../README.md)から対象の利用用途を選び、同じ操作、外部との互換性、品質を再現して合否を判定できる状態を保つ。変更が届く範囲について、次の問いに答える既存の正本を更新し、内容の分かる見出しで結ぶ。

| 再実装する担当が知る必要のあること | 記録する内容と置き場所 |
|---|---|
| 誰が何のために使い、なぜこの挙動が必要か | 利用者・相手・場面・背景・目的・守る制約は製品要求と用途別の索引へ。仕様の選択を左右した理由はその契約に添え、決定済みの要件と未決の案を区別する |
| 同じ入力から何が起きればよいか | 現行仕様に初期状態、入力、操作順、本人・相手への出力と副作用を示す。結果が変わる境界では既定値・範囲・単位、権限、失敗・中断・再開時の遷移、保存・通信形式と旧版との互換性を該当する範囲で具体化する |
| どの部品を、どんな環境で組み合わせるか | アーキテクチャ・機能仕様に責務の所有元、公開契約、依存先と組立順を残す。開発手順にはツール・依存の版、必要な資産の取得・生成方法、設定、ビルド・試験の入口を記す。鍵などは安全な供給手順を参照する |
| どう作り直せば同じ結果だと分かるか | 期待結果・許容差と測定条件を要求・仕様に置く。代表入力と境界例は期待出力まで具体化し、試験コードがなくても再作成できるようにする。実測値・実行環境・証跡は検証記録へ、未確認は再開条件とともに未確認事項へ置く |

安定した仕組みは効く条件・理由、変更を閉じる境界と崩れた時に戻す処理を所有元の仕様へ記す。観測と推定を区別し、音声の成功・失敗・修復・試案の根拠は[音声トラブルの比較記録](../development/音声E2Eテスト.md#音声トラブルの比較記録)で検証履歴へつなぐ。利用・設定・運用の前提、操作、確認、復旧が変わるたび、同じ変更で利用者または開発者の手順を作成・更新する。外部設定は[更新責任](#更新責任)に従う。

### 再実装の監査

監査の対象は今回の用途と変更が届く契約。着手時に期待を定め、各区切りで次の問いを該当する正本に当てる。新しい指示や訂正は理由とともに要求または該当する設計案へ反映する。共通の書き方や判定方法が増えたら、その規約・手順の所有元を改訂し、スキルには適用の契機と参照だけを保つ。

| 問い | 判定のしかた |
|---|---|
| 目的から実現方法へ往復できるか | [用途から仕様までの構造](#用途から仕様までの構造)に沿って、製品利用・開発・調査の該当ストーリーから体験、UIまたは画面外の結果、SLO、担当する仕様へ進む。逆向きに、その契約を変えたとき影響する利用者・画面・呼出元を特定する |
| 一つの判断を一か所で変更できるか | [仕様の分類と所有者](../spec/アーキテクチャ.md#仕様の分類と所有者)に沿い、UI・プラグイン間の契約・保存・ログなど、変更が届く判断ごとに所有元をたどる。同じ値や条件を独立に書き換える文書が複数あれば、所有元に統合し、利用側には見出し参照と固有の差だけを残す。過去の測定値・条件は当時の証跡として保持する |
| 初めての担当が何を作り、どう合否を決めるか | コード・テスト・会話を見ずに[文書入口](../README.md)から部品の組立順、対象操作の入出力と副作用をたどり、通常例と結果が変わる境界・失敗例の期待を具体化する。[条件と結果の記述](#条件と結果の記述)から各例の次状態・測定方法・合格値が一意に決まるかを見る。運用手順なら、初見で対象環境・権限を選び、値の取得から登録、確認、失敗時の中止・復旧まで判断できるかを試す |
| 判断を何で裏付け、どこから再開できるか | 先に導いた期待を要求者の決定、実装差分、既存の実測・試験と照合する。[分類の判断と完了時の移動](#分類の判断と完了時の移動)に沿って、未実装・要改善は同じ課題、確認だけなら検証の該当項目に残す。[基本順位と依頼ごとの優先指定](#基本順位と依頼ごとの優先指定)から次の一手と再開条件が決まるか確認する |

#### 監査の停止・再開条件

| 条件 | 主担当と作業担当が行うこと |
|---|---|
| 対象の記録が監査の問いを満たさない（例：同じ入力に二つの期待結果がある、仕様の根拠や観測条件をたどれない） | 検知時点で監査を不合格とし、その記述に依存する実装・後続工程を保留する。主担当は正本の見出し、判定できなかった具体例、足りない根拠を示す。作業担当は既存の決定・差分・証跡を確認して正本を直す |
| 根拠や要求者の判断が必要で、まだ記録を直せない | 保留を維持し、必要な判断・証拠と再開条件を既存の課題か未確認事項に残す。担当交代時も保留を引き継ぎ、そこから再監査する |
| 修正した正本だけで同じ例の期待・合否が一意に決まる AND 根拠を照合できる AND 対象の記録不備がすべて解消した | 主担当が再監査の合格を記録し、保留を解除する。条件が一つでも欠ければ正本の修正へ戻る |

監査結果は既存の検証記録または引継ぎに、対象の見出し・照合した例・根拠とともに短く残す。記録が整い、実装や試験が要求と食い違うと判明した場合は、その差を対象に修正・再検証する。製品の未確認事項は確認済みの範囲と分けて管理する。

文書から受入例を導けた範囲、独立に再実装して試験を通した範囲、製品環境で確認した範囲を区別する。追加検証は変更の影響と既存の証拠に応じて選ぶ。再実装を実証する場合は、元のコードとテストを保全し、独立した作業領域で文書だけを使って最小の契約を実装・試験してから既存の動作と比較する。[設定の正規化を再実装した記録](../validation/history/文書役割分離記録.md#文書だけから設定の振る舞いを再実装した範囲)

## バックログの分類と全体優先順位

バックログは「改善」「デザイン」「機能」を分類として持ち、一つの一覧で管理する。改善候補と未実装は管理を分離せず、改善・機能の詳細は`docs/backlog/未実装課題.md`へ集約する。採用済み・判断待ち・中断中は状態で区別し、未採用を実装確約に変えない。改善は既存品質・不具合・性能・構造の修復や向上、デザインは画面・表示・操作体験の判断と調整、機能は未実装の振る舞いや契約を扱う。複数に関わる課題は主たる区分に詳細の正本を置き、関連区分から相互参照する。情報を重複して独立管理せず、目的・経緯・未決事項・受入条件を保持する。

`docs/backlog/README.md`を区分横断の優先順位の入口とし、各課題の区分、状態、全体での着手順、優先理由、依存・阻害条件、次の行動、詳細の参照先を一覧で管理する。区分内だけの順位で作業を選ばず、利用者の明示した優先順位、コア体験の阻害・デグレ、重大な不確実性、依存関係と利用者価値を全体で比較する。状態・依存・判断が変わった際には全体の着手順も見直す。採番IDを付けず内容の分かる見出しで参照する。

残項目の管理はシンプルに保つ。順位・状態・次の行動は既存の一覧、残作業・完了条件は参照先の課題へ集約し、管理項目や重複する一覧は判断・再開に必要な最小限にする。小さな区切りごとに既存項目を更新し、完了した内容を仕様・検証記録へ移して残項目を減らしながら、重要なものから進める。

デザイン残項目には、機能側の仮実装からデザイナーへ渡す判断材料を保持し、バックログのデザイン区分へ概要と参照を置く。デザインから生じた未実装機能は機能区分へ記録する。引継ぎの内容とタイミングは[開発方針](開発方針.md#機能実装とデザイン判断の引継ぎ)を適用する。機能実装済み・デザイン未確定・機能未実装・検証待ちを区別して追跡する。

既存バックログをこの分類へ整理する際は、現行項目の情報とリンクを保持して移行する。規約の追加だけでは分類移行済みと扱わず、既存項目の再編は別の作業として行う。

### 改善と未実装を同じバックログで扱う

「改善・機能・デザイン」は作業の種類を示す。「採用前・着手可能・再開待ち」は作業の状態を示す。採用した改善と未実装機能は、[共通のバックログ](../backlog/README.md#管理のしかた)で同じ着手順、優先指定、依存・再開条件、完了条件を使う。例えば既存の通話で起きる途切れは「改善」、新しい招待経路は「機能」で、どちらも同じ一覧から次の一件を選ぶ。

| 判断する場面 | 更新する正本 |
|---|---|
| 新しい提案・報告 | 用途・期待結果・完了条件が同じ課題を候補と採用済みの両方から探す。既存要求との差が確認できれば修正すべき改善として扱い、採否を決める必要がある案は改善候補に根拠と判断条件を記す |
| 候補を採用する | 背景・根拠・完了条件・優先指定を既存の課題へ統合するか、新しい見出しへ移す。同じ変更で旧候補を整理し、共通一覧に着手順か再開待ちの一行を置く。デザインの詳細は画面差分に置く |
| 別の担当が進める・一部だけ完了する | 最新の一覧と詳細を照合して、同じ課題の残作業と次の一手を更新する。前の担当が完了した部分の仕様・証跡や、引き続き有効な優先指定を引き継ぐ |
| 実装・修正が終わる | 現行仕様と確認済みの結果をそれぞれの正本へ移す。確認だけが残れば未確認事項へ、追加実装・修正が残れば同じ課題へ。対象の作業が尽きた時点で一覧と詳細を閉じる |

### 基本順位と依頼ごとの優先指定

基本順位はコア体験への影響、既知の阻害、重要な不確実性、依存、次の区切りで得る価値と所要時間で決める。一時的な優先・保留や個別の要求者の指定がある場合は、対象の課題・依頼者または利用場面・指示の根拠・適用範囲・終了または見直し条件を既存の着手順か再開待ちに添える。期間が明示されていなければ日付を推定せず、対象完了や次の指示など実際の区切りを示す。

明示された優先指示は、次の区切りで実際の着手・結果と照合する。完了条件を満たすか要求者が変更するまで有効とし、保留時は理由・先にできる作業・再開条件を同じ課題で追う。たとえばWatch音声の実験を保留していても、要求者が決定した一般向けの入口・案内の是正は独立して進める。方針が未決なら、同じ課題に高優先度と判断待ちを明示して要求者に確認する。

実行時は依存を満たした候補に、その依頼・利用者に有効な指定を適用し、残りを基本順位で選ぶ。個別指定を製品全体に適用する範囲は要求者の明示に従う。競合する指定の範囲が決められなければ判断待ちに理由を残す。指定の完了・解除・失効時は通常の基準で着手順を見直す。課題の詳細は一つに保ち、現在の適用順と指定の理由を同じ入口から読めるようにする。

## 構造・命名・履歴の管理

| 対象 | 規則 |
|---|---|
| 製品要求 | `docs/requirements/製品要求.md`に、目的、利用者の価値、背景、統一方針をまとめる。Howは最小限にし、API・処理順はspec、実装状態・作業一覧はbacklogやvalidationへ置く |
| packageの恒久要求 | `docs/requirements/パッケージ要求.md`へ共通基盤の恒久的な責務・判断基準を記録。API詳細は仕様、完了条件は課題、証跡は検証へ分ける |
| 作り方の制約 | `docs/policies`へ集約。ツール操作や執筆規則はpoliciesへ置く |
| 仕様と要求 | specは現行のAPI・動作・設定・制約。要求はWhy/Whatと統一方針。未実装設計はbacklog、未確認一覧はvalidationへ置く |
| ファイル名 | 日本語文書は内容と役割が分かる名前にする。App/RTC等の実装上の固有名は維持。内容・役割・保存期間を説明できる具体名を使う |
| 移動 | 同じ変更で参照と索引を更新。空になった旧文書ディレクトリはrmdirで除く。文書清掃の対象は所有する文書と参照へ絞り、生成物・依存・Xcode内部の状態は専用の資源管理工程で扱う |
| 過去計画 | `docs/development/history`に旧計画として原文を保持し、現行との差と現在の参照先を添える。現行の実行用promptには最新の正本を参照する |
| ツール入口 | AGENTS.md / CLAUDE.md / .github/copilot-instructions.mdは共通正本への必須参照だけにし、規約本文は正本へ集約する |
| 継続検査 | scripts/check_documentation.pyで参照、到達性、着手順・再開待ちと課題詳細の対応（画面差分を含む）、分類・状態・次の行動の記載、採用判断待ちの案も統合した課題詳細と判断・再開待ちの一覧から追えること、空文書ディレクトリ、Settings記載を検査する。過去原文のコードブロックは履歴のリンクとして区別する |

過去資料の採番・旧パスは原文保全のため引用内に残す。現行規約の識別には説明的な見出しを使う。

## パッケージ要求の管理

対象は[パッケージ要求](../requirements/パッケージ要求.md)。packageが持つ恒久的な責務と判断基準を記録する。現状との差は課題、確認待ちは検証へ分ける。Appの暫定実装や既存コードの棚卸しはspec・backlogへ分類する。

| 工程 | ルール |
|---|---|
| パッケージ更新 | 要求を参照してApp側で回避している内容が解消されているか確認する。この工程での要求文書の扱いは参照と適合確認に限定する。要求の改訂は独立した要求判断の工程で扱う |
| App追従 | package APIを適用後、App仕様を実態に揃え、課題を更新する。未確認事項と証跡は検証へ記録。恒久要求は責務と判断基準として維持する |
| 追加判断 | 共通の責務方針は要求、実装すべき差分は課題へ記録する |

### 追記する内容

| 記録する項目 | 内容 |
|---|---|
| package | 変更対象package |
| packageが所有する責務 | Appではなくpackageが持つべき責務 |
| 責務をpackageへ配置する理由 | package独立性、OS差分吸収、準異常系処理、runtime情報通知、設定受け取りのどれに関わるか |
| 要求を満たす判断基準 | 利用者やAppが何を同じ意味で扱える必要があるか。具体的なAPI・処理順は仕様または課題の設計案へ分ける |

### App追従時の扱い

| 項目 | 方針 |
|---|---|
| App 側暫定実装 | App側の都合として扱い、Appの仕様や課題へ記録する |
| package に既にある責務 | `docs/spec/packages` と `docs/spec/App/Configuration/Bindings` を参照し、App 仕様から該当の正本を参照する |
| 新しい不足の判断 | App が OS 差分、継続可能な準異常系、runtime report/event、設定受け取りを自前で補う必要が出た場合だけ追記する |


## 分類の判断と完了時の移動

一つの用途に複数の残件があるときは、操作・環境・受入条件ごとに判断する。

| 条件 | 状態と更新先 | 次の判断 |
|---|---|---|
| 要求を採用済み AND 必要な振る舞いが未実装 | 共通バックログに主分類を付ける | 最小ストーリーの完了条件を定める |
| 実装済み AND 当該条件で結果が未確認 | 検証の未確認事項 | 確認する環境・期待結果・再開条件を残す |
| 実装済み AND 観測結果が要求を満たさない | 共通バックログで改善またはデザインに分類。失敗の証跡は検証履歴 | 期待と実際の差、変更できる所有元を示す |
| 実装済み AND 当該条件で受入済み | 現行仕様と検証履歴 | この範囲の残件を閉じる。他の環境は個別に判定する |
| より良くする案があり採否が未決 | 改善候補 | 効果と採否を判断できる条件を残す |

| 問い | 置き場所 |
|---|---|
| なぜ必要か・何を統一して求めるか | requirements。作り方への共通制約はpolicies |
| 今のコードは何を行うか | spec。設定値、API、例外・制限も実態として記録 |
| これから何を作るか | backlog。未採用案と実装課題を分け、完了条件・設計案を置く |
| 実装したが何をまだ確かめていないか | validation/未確認事項 |
| どの条件で何を確認したか | validation/history。過去の条件と結果を保持し、現在の結果を別の記録として追加する |
| どう設定・操作・再実行するか | manual / development。試算は前提と確認日付きの開発資料 |

分類は文書名だけでなく本文にも適用する。要求・仕様には他分類への参照を置けるが、課題表・未確認表・試験結果は各分類の正本へ置く。実装後は課題から作業を外し、実態を仕様へ、確認待ちを検証へ移す。達成済みでも恒久要求は維持する。APIが値を取得できないことや非対応OSでのエラーは現在の仕様であり、現行仕様へ記録する。
