# 文書作成規約

本書は文書・計画・要求管理の作り方を定める。アプリが利用者へ提供する価値と機能は[製品要求](../requirements/製品要求.md)、実装の制約は[開発方針](開発方針.md)へ分ける。

## 望ましい行動を示す書き方

本リポジトリの文書全体に適用する。規約・要求・計画・README・AGENTS.md等のエージェント入口・スキルと参照資料も、次の基準で記述・更新する。個別の失敗を共通ルールやスキルに反映するときは、同じ判断が必要になる条件、取る行動、完了条件を書く。元の事例と、対象や前提を変えた別の事例に当てはめる。元の指示が求める行動・停止条件・合格といえる範囲を、改訂した規定から導けるか照合する。判断が食い違う場合や元の事例を知っている人しか判断できない場合は、共通の条件を直し、両方で再確認する。具体例と結果は作業記録に残す。発生時の条件・判断の経緯・検証結果は作業記録に、未実装・未修正・未決の事項は既存のバックログに置く。共通の規定には、そこから分かった適用条件・根拠・行動・受入条件を残す。環境固有の操作は該当する仕様・手順からたどれるようにする。

| 記述の種類 | 書き方 |
|---|---|
| 通常の指針・優先順位 | 望ましい行動・選択・配置・完了状態を肯定形で具体的に示す。「何を、いつ、どの範囲で行うか」と判断根拠を記す。例: 「周辺を先に作らない」→「重大な不確実性を最小実装で先に検証する」 |
| 条件・未完了時の対応 | 適用条件と次の行動を示す。例: 「未検証で完了にしない」→「必要な検証と回帰が成功した範囲を完了とし、残りは未確認として記録する」 |
| 真の禁止事項 | 機密漏えい、無断のデータ破壊・権限拡大、検証結果の捏造など重大な害を防ぐ境界と、利用者が明示した禁止は「禁止」と明示する。対象・理由・適用範囲と、許可範囲内の代替行動を併記する。通常の好みや優先順位は上の指針として記す |
| 事実・仕様の境界・履歴 | 非対応、失敗、未実行、能力上の限界は事実として正確に記録する。過去の引用・証跡・コード例は意味と原文を保持する。否定形の解消と、事実や制約の変更を区別する |
| 表現変更の受入 | 変更前後で適用対象・必須/推奨の強さ・実行順序・数値と単位・例外・権限・完了条件を対照する。同じ状況で同じ判断になることを受入条件とし、曖昧さや情報差があれば補ってから反映する |
| 記載先と参照先 | 共通ルールは該当する文書にまとめ、スキル・入口には担当する判断と必要な節への参照を置く。意味・強制力・条件・例外を保持して表現を整える |

## 記述規則

| 項目 | ルールと理由 |
|---|---|
| 基本ルール | [開発方針](開発方針.md)を適用する |
| 採番禁止 | ルール、要求、見出し、表の識別に採番ID・番号の付与は禁止する。識別には内容の分かる見出しを使い、参照の安定性を保つ |
| 表現 | 条件・対象・行動・完了状態が実装時に判断できる文で記述する |
| 図表優先 | 認識齟齬を防ぐため、仕様は図表を使う。特に画面・状態・設定は表を優先する |
| 文章の扱い | 仕様の構造と比較は図表で示し、背景や意図を文章で補足する |
| 詳細度 | 実装者が迷わないよう、背景、理由、現状との違い、明確な仕様、体験の差、実装方針、注意点をできる限り詳しく説明する |

## 用途から仕様までの構造

| 層 | 基準となる資料に残すこと | 次にたどるもの |
|---|---|---|
| 用途と背景 | [要求の入口](../requirements/README.md)で製品利用・開発・トラブルシュートを分ける。誰がどんな事情で何を達成したいか、開始条件と妨げを記す | 同じ機能でも目的・成功条件が違えば別ユースケースにする |
| ユースケースとストーリーマップ | 活動を時間順に並べ、各活動の下に本人・相手の操作、判断、例外・復帰を置く。複数活動を通って価値が届く最小の一連の体験を示す | 製品は画面・画面外で届く結果、開発は再現手順と成果物、調査は観測点と復旧判断へ結ぶ |
| 体験・UI・品質目標 | ストーリーごとに本人や相手が知覚する結果、操作面と状態遷移を示す。画面を閉じていても成立すべき体験にはその条件を書く | SLOは対象・適用条件、指標と単位、観測の始点・終点、目標の比較式、測定区間・集計方法を対応付ける。未決の目標値は判断待ち、未測定の結果は検証待ちとして扱う |
| 実現する仕様 | [仕様の分類と所有者](../spec/アーキテクチャ.md#仕様の分類と所有者)から、各判断・状態・副作用の所有者へたどる。画面側には利用する操作・表示契約を、提供側には振る舞いを置く | 現行仕様から利用するストーリーと観測へ戻れる見出し参照を置く。仕様・測定結果・残作業はそれぞれの基準となる資料へ結ぶ |

### 条件と結果の記述

境界値は単位付きの比較式（`<`、`≤`、`=` 等）、複合条件は名前を付けた述語と `AND`・`OR`・`NOT` で表す。入力の定義・単位・観測時点を近くに置く。条件によって結果が分かれる処理はデシジョンテーブルを基本にし、各行に条件、出力または次状態、発生する副作用と担当を載せる。条件に関係しない入力と、値が不明・未取得の入力は区別する。境界の等号、該当なし、失敗時を含め、対象の入力に結果が1つ決まるか確認する。重なる規則を順に適用する場合は優先順を明記する。背景・選択理由・成功した仕組みは文章で添える。

表の各入力をどの公開契約から得るか、出力を誰が受け取るかを確認する。画面の変更だけで保存形式やプラグイン内部の条件まで書き換えるなら、同じ判断を複数箇所に持っていないかを見直す。一方を差し替えても維持する入出力・失敗時の動作を仕様上で説明できることを、低結合の判断に使う。[送信形式変更の例](../spec/App/音声処理仕様.md#送信形式変更の判定)

## プランの策定

- 要件を満たすための具体的な実装ステップを示す。
  - 実装の依存関係を明確にした上で、実装が円滑に進む順序や優先順位を明確にする。
- 経験や前提知識の少ない実装者やモデルでも、そのまま実装に入れる具体的な内容とステップを示す。
- 背景、理由、現状との違い、明確な仕様、体験の差、実装方針、注意点などをできる限り詳細に説明する。
- プランは作業手順や指示だけではなく、設計書や仕様書のような形式で、実装者が完了条件を理解できるように記述する。
- 実装者が判断に迷わない、実装をストレートに進められる内容とする。
- プラン冒頭に指示内容と背景を記載する。修正時は特に指示がない限り既存の内容・情報量を維持して指摘を反映する。

## 更新責任

バックログに記録する内容のうち、確定した利用者要求は同じ変更で製品要求・パッケージ要求へ、開発上の恒常ルールは対応する方針へ反映する。課題には基準となる資料の該当見出しへの根拠リンクと、未実装の差分・完了条件・未決事項を残す。バックログだけを要求の唯一の保存先にせず、仕様や実装の存在だけを要求の代わりにしない。判断待ちの案は確定要求へ昇格させず、既存要求への参照を候補の採用根拠と混同しない。

| 対象 | ルール |
|---|---|
| 実装 | [製品要求](../requirements/製品要求.md)を満たすこと |
| 外部サービスの設定手順 | App・server・構成や権限の変更でApple／Cloudflare等への設定が変わるたび、同じ変更で[設定手順](開発方針.md#applecloudflare等の外部設定を常に手順化する)を更新する。実装不足と利用者の設定待ちを分ける |
| 仕様 | 実装前の設計案は`docs/backlog`に置く。実装と同じ変更で`docs/spec`を更新し、常に現行実態と一致させること |
| 画面 | 画面設計案は課題へ置き、実装と同じ変更で画面項目定義を更新すること |
| 構想メモ | 未採用案も`docs/backlog/未実装課題.md`へ統合し、採用済みと判断待ちの状態・条件を明記する。旧`改善候補.md`は参照専用とし、順位と次の行動は共通一覧で管理する |
| 差分整理 | 未実装の作業は`docs/backlog/未実装課題.md`、未確認は`docs/validation/未確認事項.md`へ分ける。現行の制限・非対応時の挙動は仕様に残す。目的と情報を保持したまま、現行仕様・残課題・未確認へ正しく分類する |

### 記載後に元の指示と意図を照合する

要求、課題、設計、仕様、手順、検証記録、担当者への引継ぎ、AIに作業を指示するスキルを書くときは、新規・更新・要約・翻訳のたびに、書き終えた文章を元の指示・背景・訂正に照らして読み直す。形式・リンクの自動検査とは別に毎回行い、転記や要約の正しさを更新後の文章だけから判断しない。単独作業では記載者自身が照合する。

- 対象・利用者・画面・状態・適用条件・優先順位・除外範囲が指示どおりかを確認する。
- 要求された操作と結果を具体例に戻し、表示だけの変更、操作可否の変更、保存や実処理の変更を取り違えていないか確認する。たとえば「コントロールを無効化」は既存コントロールを残して操作不可にする要求であり、「無効」という文字への置換ではない。補足説明を付けても、操作不可の代わりにはならない。
- 記載から別の担当が導く期待動作・完了条件を元の指示へ照らし、意味の欠落、逆転、根拠のない追加条件や範囲拡大を修正する。確定した要求と提案・未決事項を区別する。
- 要求・課題の詳細・共通一覧など同じ内容を載せた箇所も照合し、一方だけ異なる意味を残さない。記録しただけの状態と実装済みを区別する。

照合結果と修正点は、今回の変更の説明または既存の検証記録へ簡潔に残す。意図が定まらない箇所は推測で確定せず、その箇所を未決として扱う。元の指示で判断できる内容を再確認する必要はない。

#### 日本語の技術文書を検査する

仕様、要求、バックログを含む `docs/` 配下のMarkdownと開発スキルをtextlintで検査する。本文と表のセルに[日本語技術文書向けのルール](https://github.com/textlint-ja/textlint-rule-preset-ja-technical-writing)の全23項目を有効にする。表の項目名や状態には句点を求めない。

新しくクローンしたら、文書検査用の `package.json` が指定するNode.jsを用意する。リポジトリのルートで次の2行を実行する。1行目で依存パッケージを準備し、2行目でこのリポジトリのコミット前フックを有効にする。既に独自のGitフックを使っている場合は、既存のコミット前フックから `.githooks/pre-commit` を呼び、その終了状態を引き継ぐ。

```sh
npm ci --prefix tools/doc-lint --ignore-scripts --no-audit --no-fund
git config --local core.hooksPath .githooks
```

`git commit` は、ステージした文書と画面文言を自動で検査する。ファイルの一部をステージした場合も、コミットに入る内容を読む。「要修正」や検査の失敗があればコミットは止まる。「要確認」は判断を促すために表示する。文書検査のルールやツールを変更した場合は、ステージしたルールで全対象を検査する。

同じクローンの作業ツリーにはフックの設定が引き継がれる。依存関係の固定ファイルが一致すれば、主な作業ツリーにあるパッケージも使える。依存を更新したときは1行目をもう一度実行する。`python3 scripts/check_documentation.py` は作業中の変更も含めて全対象の文書とリンクを検査する。既存の文章も全文を検査し、「要修正」があれば失敗する。

| 場面 | 検査と修正の基準 |
|---|---|
| 通常の説明 | 技術文書向けプリセットの基準を使う。目安は1文100文字以内、読点は3個まで。名詞の列挙を区切る読点は数えない。文の長さを測るとき、コードとして記したパスやAPIの識別子は1つの参照として扱う。強調した文章も1文ずつ調べる。文を分けるときは、条件がどの操作にかかるかを保つ |
| 文体と引用 | 仕様は常体、利用手順は敬体で書ける。本文と箇条書きはそれぞれ文書内の文体をそろえる。画面から引用した文言は、その文体と疑問符を保つ。たとえば「表示しますか？」は仕様にもそのまま記す |
| 原因や見込みが未確定 | 推量を表す語句は「要確認」として表示する。観測した事実と推測を元の記録で照合する。確証のない原因を断定せず、何を確認すれば分かるかを添える |

指摘を直した後は、元の要求と照合し、条件と例外を保っていることを確かめる。表の結果欄も、設定を変えられる条件を残したうえで「設定を変更できます」と書ける。文の意味が決まらない場合は[監査の停止・再開条件](#監査の停止再開条件)に従う。

日本語の検査だけを実行するには `npm --prefix tools/doc-lint run lint:all` を使う。端末で直接実行すると、ファイル、行、桁、ルール名を確認できる。コマンドはGitの作業フォルダで実行する。

文書・スキルの本文と画面の日本語には、[用語の検査](../../tools/doc-lint/japanese-usage.mjs)も適用する。手元で検査すると、該当する箇所と規則名が分かる。[用例を比較する手順](日本語の用例.md)に従い、[用例の調査記録](../development/history/日本語の用例調査.md)に、同じ意味の候補を2024年8月より前の資料で比べた件数と、採用した表記を記録する。後の資料との比較は時期による変化を調べるときに使う。辞書にない表現を調べ、意味を保って書き直す手順は[日本語の用語を確認するスキル](../../.agents/skills/japanese-word-usage/SKILL.md)に従う。

#### 次の読者が同じ意味に読めるか確かめる

文書の整理では、[整理の目的と受入条件](開発方針.md#整理の目的と受入条件を分ける)に沿って、意味を保つ編集、判断の管理元を変える再設計、配置の変更を区別してレビューする。

[現在のバックログと変更の方向を照合する手順](開発方針.md#レビューで現在のバックログと変更の方向を照合する)を文書にも適用する。対象の記述を関連課題の状態・受入条件と読み比べ、次の読者が何を決め、どの作業に進むかを確かめる。例えば、判断待ちの案を確定仕様と読める箇所や、実機確認待ちの操作を利用可能と案内する箇所は、該当する文と課題を示して指摘する。

会話に参加していなかった読者の立場で、変更した文章から操作する人と時点を特定し、どの操作で誰に何が起きるかを自分の言葉で説明する。書き手が省いた主語や条件を会話の記憶で補う必要があれば書き直す。決定と希望、許可と義務、観測した結果と原因の推定を元の言葉に照らし、理由や例外によって判断が変わる部分を残す。

| 読み直す場所 | 意味が変わる例と確かめ方 |
|---|---|
| Standard画面と一般利用者が見るダイアログ | 見出し・本文・各ボタンを一緒に読み、日本語と英語それぞれで、押した後に起きることを説明する。「グループタブを表示しますか？」に対する「今はしない」／“Not Now” は、表示の案内を閉じる選択。「招待を断る」／“Decline invitation” と書けば、相手の招待まで断る意味になる。実際の操作、読み上げ、両言語の説明が一致するかを[画面文言の検査手順](開発方針.md#利用者向け文言の意味と平易さを継続検査する)で確かめる |
| 仕様・検証記録・引継ぎ | 「音声改善済み」では、次の担当が何を確かめたのか分からない。[送信側の声の分離の記録](../validation/history/音声同一性と途切れの再現.md#送信分離の再onで同じ症状が出たときの比較)を例にする。シミュレータで送信側の声の分離を入れ直すと、試験音に含めた397 Hzの音は初回と同じ大きさまで弱まった。一方、切り替えたときの無音は141ミリ秒で、上限の120ミリ秒を超えた。戻った性質と残る問題の両方が伝わるかを確かめる |
| 作業を指示するスキル・手順 | 「適宜対応」のように操作を特定できない表現を避け、その一文を読んだ担当が次に何をするかを書く。たとえば「文書と測定結果で対象の端末が違う場合は、測定に使った端末を検証記録に追記し、同じ条件の結果を比べ直す」。初めて読む担当が作業を始める条件と終える条件を判断できるかを試す |

新しい略称や名詞をいくつも重ねた言い方を作らず、読者が使う名詞と具体的な動詞を選ぶ。技術仕様では、照合に使うAPI名・ログの項目名・単位を正確に保ち、読者に説明が必要な語は初出で役割を添える。表の見出しや画面の問いで対象が明らかな場合は、その文脈を生かす。

変更中は `python3 scripts/review_wording.py` で読み直す候補のファイル・行・問いを確認できる。コミット後は `--base` に変更前のコミットを指定する。通常の検証でも `wording-review.log` に候補を残す。語が見つからなくても、削った一文にしかなかった条件や、自然に読める誤訳は元の指示と比較して初めて分かる。意味が二通りになる箇所は[監査の停止・再開条件](#監査の停止再開条件)に従って直し、同じ場面でもう一度読み直す。繰り返し誤解された言い方は、何と何を取り違えたのかを該当する用語集か手順の例に残し、語から見つけられるものは候補の検査にも加える。

### コード全体整理の次の回に仕様全体を簡素化する

[次回のコード全体リファクタリング](開発方針.md#次回リファクタリングの全体簡素化)を終えた次の回では、仕様全体の整理を最重要として扱う。コード整理の要求を置き換えず、2つの回の順序と各完了条件を分けて管理する。

App・UI・package・server・通信・音声・設定・配布・自動化等の現行仕様を全体から見渡し、参照する要求・方針・設計・手順も照合する。同じ契約の重複、矛盾、古い前提、責務の分散、不要な層・分割・中継・例外・独自管理を作らせる記載をすべて特定し、その内容を定める文書にまとめて修正する。文章の短縮だけで閉じず、文書どおり実装したときに冗長な構成へ戻らないことを確認する。要求・現行仕様・設計案・履歴・検証の役割を混ぜて一冊へ集めることは統合の目的にしない。

重要な情報は落とさない。目的・背景・理由、責務と依存、操作と状態遷移、可否・例外・失敗と復旧、既定値・数値・単位、OS／通信／codecの必要な差、認証・秘密・保存と通信互換性、品質・受入条件、未決・未確認の区別を保持する。整理前の重要情報と統合先を対応付け、移動・統合・削除の理由と参照先を確認する。重要情報を会話履歴やコードの読解だけに依存させず、簡素化後の文書から同じ振る舞いを再実装・検証できる状態を保つ。

整理後の仕様全体に敵対的レビューを3回行い、各回は修正後の最新文書と参照先を対象にする。構成・責務と重複、重要情報と条件の保持、実装・要求との整合と文書だけでの再実装を含む観点で反証する。対象・指摘・重要度と理由・対応差分・再検査結果を記録し、重要な指摘はすべて対応する。3回目の修正で生じた問題も再確認し、重要指摘を残したまま回数だけで完了にしない。後続課題への先送りや根拠のない重要度の引下げで対応済みとしない。指摘を不採用と判断する場合は反証と判断理由を残す。

小単位ごとに内容・参照・実装を照合し、commitし、main・origin・previewを同期する。完了時には、統合前後の情報対応、不要な構成を招く記載の修正例、3回のレビューと重要指摘の対応、文書からの再実装の監査結果を示す。仕様と実装の食い違いが残る場合は解消または未達を明示し、未確認を受入済みへ変えない。受入後は[全体整理のサイクル](開発方針.md#全体整理のサイクル)に従い、次の回でコード全体を再整理する。

### 再コード整理の次の回にデザイン資料とユースケース全体を再構成する

[次回のコード全体整理](開発方針.md#次回リファクタリングの全体簡素化)→[仕様全体整理](#コード全体整理の次の回に仕様全体を簡素化する)→[再コード全体整理](開発方針.md#仕様全体整理の次の回にコード全体を再び簡素化する)を終えた次の回では、デザイン資料とユースケース全体の再構成・簡素化を最重要として扱う。先の3つの回とは別の実施回・成果として管理する。

デザインシステム、Standard／Advanced・各OS・端末の設計、見本、操作・通知・招待の流れ、要求からのユースケース対応とストーリーマップを横断して見直す。重複・矛盾・古い前提と、冗長な画面・導線・層・独自状態管理など無駄な構成を生む記載をすべて洗い出し、基準となる資料・参照・必要な差分へ統合する。重要情報を保持しながら全体構成を練り直し、シンプルに記載する。文書の短縮だけでなく、それに従った設計・実装が不要な複雑さへ戻らないことを確かめる。

ペルソナ定義のない人物・一般的な「ユーザー」は、元の利用用途と背景に応じたペルソナへ対応付ける。既存定義で足りなければ、その用途に根拠のある目的・状況・制約で定義し、根拠のない人物属性や新しい用途を追加しない。方向のある関係・操作では、招待する側／受ける側、通知の送り主／受取人、削除・除外する側／反映を受ける側等の立場と、誰から誰へ何が届くかを明記する。ペルソナと場面ごとの立場を区別し、同じ人が別場面で反対の立場になることも表現する。利用者の動機、場面、端末・接続・権限、前景／背景、無音・聞き専、グローブ等の制約、操作・遷移、本人と相手に届く結果を保持してユースケースを改訂する。

重要な目的・理由・条件・例外・失敗と復旧、操作可否・状態・情報の所有、アクセシビリティ、安全性、必要なOS／画面差分、未決・仮実装・未確認の区別は落とさない。整理前の人物・ケース・契約と整理後のペルソナ・立場・ケース・基準となる資料を対応付け、網羅性と意味の保持を検査する。要求・設計案・現行仕様・検証結果を混ぜず、資料の整理だけで製品や実画面を受入済みにしない。

この回の最新資料全体に対して、新たに敵対的レビューを3回行う。各回で構成と重複、ペルソナ・立場・方向と用途の整合、重要情報・ケース・画面間の契約の保持を含む観点から反証し、前回の修正も再検査する。対象・指摘・重要度と理由・対応差分・再検査結果を残し、重要な指摘はすべて対応する。先の3つの回のレビュー回数は流用しない。3回目の修正後の重要指摘も確認し、先送り・根拠のない重要度引下げや回数の消化だけで完了にしない。指摘の不採用には反証と判断理由を残す。

小単位で内容・参照・要求との意図照合、必要な設計見本・関連仕様との整合を検査し、commitし、main・origin・previewを同期する。重要指摘や重要情報の欠落・ケース不整合が残る間は未完とする。受入後は、次の回で[テスト全体の構成・実効性・品質を見直す](開発方針.md#デザインユースケース整理の次の回にテスト全体を見直す)。

### 意味が削られた既存表現を画面と文書の全体で修復する

画面と文書全体の表現を点検するときは、短縮によって元の意味が伝わらなくなった箇所を特定して直す。新しい文言の混入防止だけでは完了にせず、既存の文言・本文全体を対象とする。Standardとダイアログを重点的に確認する。Advanced、各OS・端末、共通画面、通知、アクセシビリティの文言も対象に含む。要求・仕様・デザイン資料と見本・ユースケース・手順・エージェントルール・バックログなどと照合する。

元の利用者指示、用途・背景、意図が省かれる前の文書と現行の操作・契約を根拠に、主体・相手・対象・方向・条件・操作・結果・理由・強制力・例外・数値・未決や未確認の区別が失われていないか調べる。失われた情報を日常的で具体的な日本語・英語へ戻す。長文化や元の語への一律な差戻しを目的にせず、伝わる意味を回復する。元の意図を推測で追加せず、根拠が足りない箇所は未決として記録する。履歴・引用・証跡の原文を改変して過去の事実を消さず、現行文書の訂正と必要な注記を区別する。

修正後に少なくとも3回、各回で異なるモデルを使ってレビューする。少なくとも3種類の異なるモデルによる点検とし、同じモデルの別セッション・担当・思考設定だけを別モデルとして数えない。各回には元の根拠と最新の修正内容、前回指摘と対応を渡し、意図の保持と分かりやすさを再検査する。使用したモデル名・確認できるモデルのバージョン、対象、根拠、指摘と重要度、対応差分・再確認結果を記録する。必要なモデルを利用できない場合は不足を明示し、同一モデルによる代替を条件達成と扱わない。

重要な指摘はすべて対応し、3回目の修正後にも意味の欠落や新しい曖昧さがないか再確認する。回数だけの消化、根拠のない重要度引下げ、後続課題への移記だけで完了にしない。機械の単語検査・リンク検査だけで分かりやすさを受入済みにせず、必要な実画面・操作と文書から導く判断を照合する。根拠→修正前→失われた意味→修正後の対応を示し、小単位で検証してcommitし、main・origin・previewを同期する。

## 再実装に必要な記録

コード・テスト・会話履歴を失った場合にも、別の担当が[文書入口](../README.md)から対象の利用用途を選び、同じ操作、外部との互換性、品質を再現して合否を判定できる状態を保つ。変更が届く範囲について、次の問いに答える既存の基準となる資料を更新し、内容の分かる見出しで結ぶ。

| 再実装する担当が知る必要のあること | 記録する内容と置き場所 |
|---|---|
| 誰が何のために使い、なぜこの挙動が必要か | 利用者・相手・場面・背景・目的・守る制約は製品要求と用途別の索引へ。仕様の選択を左右した理由はその契約に添え、決定済みの要件と未決の案を区別する |
| 同じ入力から何が起きればよいか | 現行仕様に初期状態、入力、操作順、本人・相手への出力と副作用を示す。結果が変わる境界では既定値・範囲・単位、権限、失敗・中断・再開時の遷移、保存・通信形式と旧版との互換性を該当する範囲で具体化する |
| どの部品を、どんな環境で組み合わせるか | アーキテクチャ・機能仕様に責務の所有元、公開契約、依存先と組立順を残す。開発手順にはツールと依存パッケージのバージョン、必要な資産の取得・生成方法、設定、ビルド・試験の入口を記す。鍵などは安全な供給手順を参照する |
| どう作り直せば同じ結果だと分かるか | 期待結果・許容差と測定条件を要求・仕様に置く。代表入力と境界例は期待出力まで具体化し、試験コードがなくても再作成できるようにする。実測値・実行環境・証跡は検証記録へ、未確認は再開条件とともに未確認事項へ置く |

安定した仕組みは効く条件・理由、変更を閉じる境界と崩れた時に戻す処理を所有元の仕様へ記す。観測と推定を区別し、音声の成功・失敗・修復・試案の根拠は[音声トラブルの比較記録](../development/音声E2Eテスト.md#音声トラブルの比較記録)で検証履歴へつなぐ。利用・設定・運用の前提、操作、確認、復旧が変わるたび、同じ変更で利用者または開発者の手順を作成・更新する。外部設定は[更新責任](#更新責任)に従う。

### 複数の資産を同時に失ったときの復旧

対象はテスト（試験入力・期待値・判定）、環境（依存・設定・外部サービスの準備）、文書（要求・仕様・判断の経緯）、プロダクト（ソース・必要な資産・配布物）。別の担当が、失ったものを参照せずに復旧を始められる状態を保つ。

| 同時に使えなくなったもの | 残ったものから何を復旧し、何と照合するか |
|---|---|
| プロダクトとテスト | 仕様と環境定義から実装と試験入力を作り直す。変更前に確定した期待出力・許容差・失敗例と照合する |
| プロダクトと環境 | 文書にある依存・権限・設定を基に環境を用意し、契約と試験例から実装を戻す。残った受入試験を製品の入口から実行する |
| プロダクトと文書 | 独立して保管した確定版や判断の記録を探す。環境定義と試験例で契約を照合し、利用目的と採用理由を復元してから実装を受け入れる |
| テストと環境 | 製品と仕様を基に、環境と試験を空の状態から用意する。代表入力・境界・失敗例で、期待した成功と失敗を区別できるか確かめる |
| テストと文書 | 確定時の判断と受入結果を回収し、残った製品で観測できる振る舞いと照合する。既知の不具合を期待値として固定しない |
| 環境と文書 | 製品・試験と同じコミットから構築手順を戻す。外部の権限と設定は管理者の復旧手順で用意し、利用条件と運用上の理由も照合する |

担当は、対象の既存の仕様・開発手順・検証履歴に、復旧元の保管場所と対象コミットまたはバックアップの取得日時、そこへ到達するための権限、復旧する順序、合否の根拠を残す。端末・リポジトリ・外部アカウントなど、同じ障害で失うものを先にまとめる。3種類以上を同時に失う場合も、その場所や資格を使わずに、別の担当が最初の復旧元に到達できるか確かめる。同じリポジトリ内のコピーとリンクは、リポジトリ全体を失う場合の復旧元に数えない。文書と環境を同時に失う場合には、最初の保管先と利用手順を残る側から見つけられるようにする。唯一の復旧元を移すときは、移行先から取り出せることを確かめてから元の保管を終える。秘密値は転記せず、権限を取り戻す方法、再発行先と担当を示す。

設計の背景には、誰がどの場面で困るか、守る条件、その方式を選んだ理由、別の方式で起きた問題を残す。判断を記録した文書を失う想定では、その確定版を取り出せる別の保管先、または決定理由を残した変更履歴を確かめる。実装やテストから観測できる事実と、確認できない理由は区別する。全ての候補が同じ障害で失われる場合や、理由を推測するしかない場合は、復旧できない範囲と必要な対処を既存の課題に残す。

着手・再開時と引継ぎ前に、変更が届く組み合わせについて、失った側を見ずに手順をたどる。復旧元・依存先・判断の根拠を変更したら、空の作業場所で変更部分を取り出し、代表例の合否まで確かめる。結果には対象コミットと想定した喪失、使った復旧元、実行できた工程、残る条件を記す。手順を読んだ範囲と、実際に復旧を確かめた範囲を分ける。証拠と条件が今も同じなら再利用できる。根拠が欠けたときは[監査の停止・再開条件](#監査の停止再開条件)に従う。

[文書から音声設定を再実装した例](../validation/history/文書役割分離記録.md#文書だけから設定の振る舞いを再実装した範囲)と[文書とテストを共有mainから取り戻した例](../validation/history/文書役割分離記録.md#文書と試験を失った作業場所を復旧する)に、実行できた範囲を示す。

### 再実装の監査

監査の対象は今回の用途と変更が届く契約。着手時に期待を定め、各区切りで次の問いを該当する基準となる資料に当てる。新しい指示や訂正は理由とともに要求または該当する設計案へ反映する。共通の書き方や判定方法が増えたら、その規約・手順の所有元を改訂し、スキルには適用の契機と参照だけを保つ。

| 問い | 判定のしかた |
|---|---|
| 目的から実現方法へ往復できるか | [用途から仕様までの構造](#用途から仕様までの構造)に沿って、製品利用・開発・調査の該当ストーリーから体験、UIまたは画面外の結果、SLO、担当する仕様へ進む。逆向きに、その契約を変えたとき影響する利用者・画面・呼出元を特定する |
| 1つの判断を一か所で変更できるか | [仕様の分類と所有者](../spec/アーキテクチャ.md#仕様の分類と所有者)に沿い、UI・プラグイン間の契約・保存・ログなど、変更が届く判断ごとに所有元をたどる。同じ値や条件を独立に書き換える文書が複数あれば、所有元に統合し、利用側には見出し参照と固有の差だけを残す。過去の測定値・条件は当時の証跡として保持する |
| 初めての担当が何を作り、どう合否を決めるか | コード・テスト・会話を見ずに[文書入口](../README.md)から部品の組立順、対象操作の入出力と副作用をたどり、通常例と結果が変わる境界・失敗例の期待を具体化する。[条件と結果の記述](#条件と結果の記述)から各例の次状態・測定方法・合格値が一意に決まるかを見る。運用手順なら、初見で対象環境・権限を選び、値の取得から登録、確認、失敗時の中止・復旧まで判断できるかを試す |
| 判断を何で裏付け、どこから再開できるか | 先に導いた期待を要求者の決定、実装差分、既存の実測・試験と照合する。[分類の判断と完了時の移動](#分類の判断と完了時の移動)に沿って、未実装・要改善は同じ課題、確認だけなら検証の該当項目に残す。[基本順位と依頼ごとの優先指定](#基本順位と依頼ごとの優先指定)から次の一手と再開条件が決まるか確認する |

#### 実装状況と品質目標の合否を引き継ぐ

利用者の操作ごとに、要求から現行仕様、対応する試験、最新の有効な検証記録、残っている課題へたどれるようにする。現行仕様には実装した範囲と未対応の条件を書く。検証履歴には、測定したコミット・環境・操作・観測点・期待値・実測値・合否を書く。過去の成功は当時の条件とともに保つ。変更後も適用できるかは、該当する処理と試験条件の差を確認して判断する。

| 対象の操作と試験の状態 | 記録する判定 | 次に行うこと |
|---|---|---|
| 必要な振る舞いが未実装、または一部だけ実装 | 実装済みの条件と残る条件を明記 | 既存のバックログに残りの実装と、それを確かめる操作を書く |
| 実装済み AND（未実行 OR 対象を省略 OR 機器・計測の不備で有効な値がない） | 対象条件での品質は未確認 | 失敗した工程、最後に確認できた地点、再開に必要な条件を検証の未確認事項に残す |
| 有効な観測で必要な機能が動かない | その機能が失敗。目標値を測れない場合はその旨も記録 | 操作と想定した出力、最初に違いが現れた箇所を記録し、既存の不具合または実装課題を更新する |
| 測定が成立 AND 目標の判定式を満たさない | 測定した範囲で目標未達 | 失敗値と条件を検証履歴に残し、影響する利用場面と次の切り分けを同じ課題に結び付ける |
| 有効な測定 AND 要求した全条件で判定式を満たす | その環境・区間・対象に限り達成 | 受入済みの範囲を明記する。他の機器や実利用での確認が必要なら、その条件を残す |

品質目標（SLO）は[体験と品質目標の記載事項](#用途から仕様までの構造)に沿い、対象期間・母数・集計方法を試験の判定と照合する。単発の切替試験で上限を超えたら、その操作の失敗を記録する。一定期間の成功率を要求している場合は、必要な期間と件数がそろってからその目標を判定する。

未達を見つけたら、まず測定方法・入力・保存結果の対応を確認する。測定自体のエラーなら試験環境を直し、欠けた観測を補う。有効な失敗なら、初めて差が出た処理を調べ、修正後に同じ条件と判定式で比較する。単に再実行して成功したときは両方の結果を残し、原因と回復の確認は継続する。失敗値、修正後の値、確認できた範囲を履歴に残し、受入条件を満たした範囲だけ完了にする。要求者が品質目標を変更した場合は理由と適用時点を要求に残し、過去の結果は当時の基準で読めるようにする。

#### 品質に関する判断を更新する

継続して品質を追う操作では、検証状況の入口に「維持する実装と理由」「壊れた条件」「現在の結果」「測った限界と未確認の範囲」「利用者に保証する目標」「次に試す改善」を並べる。各行に現在の判断と根拠となる文書の見出しを示す。[音声の設定切替](../validation/README.md#音声の設定切替で守る動作と現在の品質)に記入例がある。原因や限界を特定できない場合は、判明した範囲と、何を比較すれば判断できるかを書く。

| 更新のきっかけ | 担当が更新し、主担当が確かめること |
|---|---|
| 仕様・実装・測定方法を変える前 | 守る動作とその成立理由、変更が届く範囲、比較に使う過去の成功例と失敗例を特定する。記録があれば再利用する |
| 新しい結果が出たとき、または保存済みの結果を読み直して判断が変わったとき | 実行条件と観測を検証履歴に残し、変わった行の判断と参照を更新する。原因の仮説には、支持する観測と仮説を退ける条件を添える |
| 修正案を選ぶとき | 残った差から次に変える箇所を絞り、良くなると予想する指標と、維持する隣の動作を書く。採用・撤回を決める条件を既存の課題へ結ぶ |
| 区切り・再開・引継ぎ | 担当が表の項目と参照先を文書検査で確かめる。主担当は入口から成功例と失敗例を1つずつ選び、履歴を基に目標の達否、変更の採否、未確認の範囲を説明できるか確かめる |

文書検査は音声切替の表に6項目の判断と根拠への参照がそろうかを調べる。主担当は、新しい実測と現在の判断の矛盾、古い成功例だけを根拠にした受入、異なる操作や環境の取り違えも点検する。矛盾や記載漏れがあれば、その判断を使う開発を保留し、同じ成功例・失敗例で再監査する。製品が目標未達でも、実測と次の判断が追える記録は監査に合格できる。

次の担当は、失敗を修正したあとで同じ操作の判断を更新する。改善が確認できた範囲は現在の結果へ反映し、修正前の値と採否の理由を履歴に残す。別の経路で悪化したら、その経路の結果も残し、既存の課題に戻す。引継ぎでは更新した判断の見出しと、まだ満たしていない条件を示す。

#### 成功と失敗の要因を次の変更に生かす

不具合の修正や、過去に品質が変わった処理の改修では、着手前に同じ操作・処理の検証履歴、仕様、関連課題を調べる。今回使う成功例・失敗例の見出しと、そこから選んだ変更範囲、守る条件、または見送った案を既存の作業記録に残す。該当例がなければ、調べた箇所と今回比較の基準にする条件を書く。

担当は同じ検証履歴で「なぜ成功したか」「なぜ失敗したか」をそれぞれ記す。操作、入力、観測点、判定値をそろえ、各要因を「確認済み」「推定」「不明」のいずれかで示す。確認済みなら、その要因が結果を変えたと判断できる比較や直接観測を示す。推定には支持する観測と、その説明を退けられる条件を添える。不明なら、足りない観測と候補を区別する次の確認を書く。成功例か失敗例をまだ観測していない場合も、その旨を明記する。

| 過去の記録と今回の観測 | レビューで求める判断と対応 |
|---|---|
| 症状が似ているが、要因の一致は未確認 | 比較できた条件と最初に差が出た処理を示す。再実行で成功しても失敗記録を残し、原因の確認を続ける |
| 同じ事象で別の要因を確認 | 以前の事例を参照し、両者を見分ける観測と、今回の要因に効く対策を記録する |
| 同じ事象で同じ要因を確認 | 以前の課題を再開するか、その課題から今回の修正をたどれるようにする。以前の対策や試験がどの条件で効かなかったかを調べ、その条件に届くように対策を改める |
| 同じ要因による再発を解決済みにする | 同じ入力・発生条件・判定方法で、以前の失敗を検出でき、対策後は成功し、従来の正常例も保てることを示す。レビュー担当が比較結果と、今後もその失敗を検出する試験または確認手順を照合してから、課題を解決済みにする |

過去の測定や既存の試験で判定できる部分は再利用する。追加の確認は結論を左右する差に絞る。記録の根拠が欠けたら[監査の停止・再開条件](#監査の停止再開条件)を適用する。根拠のある推定や未確認の範囲を明示すれば、切り分けは進められる。対策の効果が未確認の間は課題を未解決として扱い、次に比較する条件を残す。

#### 監査の停止・再開条件

| 条件 | 主担当と作業担当が行うこと |
|---|---|
| 対象の記録が監査の問いを満たさない（例：同じ入力に2つの期待結果がある、仕様の根拠や観測条件をたどれない） | 検知時点で監査を不合格とし、その記述に依存する実装・後続工程を保留する。主担当は基準となる資料の見出し、判定できなかった具体例、足りない根拠を示す。作業担当は既存の決定・差分・証跡を確認して基準となる資料を直す |
| 根拠や要求者の判断が必要で、まだ記録を直せない | 保留を維持し、必要な判断・証拠と再開条件を既存の課題か未確認事項に残す。担当交代時も保留を引き継ぎ、そこから再監査する |
| 修正した基準となる資料だけで同じ例の期待・合否が一意に決まる AND 根拠を照合できる AND 対象の記録不備がすべて解消した | 主担当が再監査の合格を記録し、保留を解除する。条件が1つでも欠ければ基準となる資料の修正へ戻る |

監査結果は既存の検証記録または引継ぎに、対象の見出し・照合した例・根拠とともに短く残す。記録が整い、実装や試験が要求と食い違うと判明した場合は、その差を対象に修正・再検証する。製品の未確認事項は確認済みの範囲と分けて管理する。

文書から受入例を導けた範囲、独立に再実装して試験を通した範囲、製品環境で確認した範囲を区別する。追加検証は変更の影響と既存の証拠に応じて選ぶ。再実装を実証する場合は、元のコードとテストを保全し、独立した作業領域で文書だけを使って最小の契約を実装・試験してから既存の動作と比較する。[設定の正規化を再実装した記録](../validation/history/文書役割分離記録.md#文書だけから設定の振る舞いを再実装した範囲)

## バックログの分類と全体優先順位

バックログは「改善」「デザイン」「機能」を分類として持ち、1つの一覧で管理する。改善候補と未実装は管理を分離せず、改善・機能の詳細は`docs/backlog/未実装課題.md`へ集約する。採用済み・判断待ち・中断中は状態で区別し、未採用を実装確約に変えない。改善は既存品質・不具合・性能・構造の修復や向上、デザインは画面・表示・操作体験の判断と調整、機能は未実装の振る舞いや契約を扱う。複数に関わる課題は主たる区分に詳細の基準となる資料を置き、関連区分から相互参照する。情報を重複して独立管理せず、目的・経緯・未決事項・受入条件を保持する。

`docs/backlog/README.md`を区分横断の優先順位の入口とし、各課題の区分、状態、全体での着手順、優先理由、依存・阻害条件、次の行動、詳細の参照先を一覧で管理する。区分内だけの順位で作業を選ばず、利用者の明示した優先順位、コア体験の阻害・デグレ、重大な不確実性、依存関係と利用者価値を全体で比較する。状態・依存・判断が変わった際には全体の着手順も見直す。採番IDを付けず内容の分かる見出しで参照する。

残項目の管理はシンプルに保つ。順位・状態・次の行動は既存の一覧、残作業・完了条件は参照先の課題へ集約し、管理項目や重複する一覧は、判断と再開に必要なものだけを残す。小さな区切りごとに既存項目を更新し、完了した内容を仕様・検証記録へ移して残項目を減らしながら、重要なものから進める。

デザイン残項目には、機能側の仮実装からデザイナーへ渡す判断材料を保持し、バックログのデザイン区分へ概要と参照を置く。デザインから生じた未実装機能は機能区分へ記録する。引継ぎの内容とタイミングは[開発方針](開発方針.md#機能実装とデザイン判断の引継ぎ)を適用する。機能実装済み・デザイン未確定・機能未実装・検証待ちを区別して追跡する。

既存バックログをこの分類へ整理する際は、現行項目の情報とリンクを保持して移行する。規約の追加だけでは分類移行済みと扱わず、既存項目の再編は別の作業として行う。

### 関連する要求と影響を受ける利用者を結ぶ

課題の登録・分割・統合・変更時には、その操作に関わる人を挙げる。操作する人、選ばれた相手、同じ場にいて選ばれなかった人について、誰の操作や状態によって誰の体験が変わるかを確かめる。関係がある場合は、課題の詳細から双方の要求の該当見出しへリンクし、どの条件と受入結果を一緒に確認するかを一文で示す。

| 関係 | どこから何をたどれるようにするか |
|---|---|
| 一方の要求が他方の成立条件や許される操作を決める | 条件を使う要求から、その条件を定める要求へリンクする。前提が変わったときに見直す操作や受入条件を書く |
| 一人の操作が別の利用者の体験を変え、どちらの要求を変えても相手側の受入を見直す必要がある | 双方の要求から相手側の要求をたどれるようにする。作業が別の課題に分かれていれば課題間にも相互リンクを置き、それぞれの立場で守る結果を書く |
| 作業順に制約がある | 後から着手する課題に先行課題と再開条件を記す。関連する要求があっても、独立して進められる課題は今の着手順を保つ |

同じ機能名が出てくるだけの箇所は結ばない。片側の条件を変えたと仮定し、もう一方で判断し直すことがあるかを確かめる。関係が未確定なら、疑問と判断に必要な根拠を課題に残す。要求本文と優先順位はそれぞれの管理先で更新する。課題を完了・移動したときは残る課題からのリンクを付け替え、今後も必要な関係は要求同士でたどれるように保つ。

### 改善と未実装を同じバックログで扱う

「改善・機能・デザイン」は作業の種類を示す。「採用前・着手可能・再開待ち」は作業の状態を示す。採用した改善と未実装機能は、[共通のバックログ](../backlog/README.md#管理のしかた)で同じ着手順、優先指定、依存・再開条件、完了条件を使う。例えば既存の通話で起きる途切れは「改善」、新しい招待経路は「機能」で、どちらも同じ一覧から次の一件を選ぶ。

| 判断する場面 | 更新する文書 |
|---|---|
| 新しい提案・報告 | 用途・期待結果・完了条件が同じ課題を候補と採用済みの両方から探す。既存要求との差が確認できれば修正すべき改善として扱い、採否を決める必要がある案は改善候補に根拠と判断条件を記す |
| 候補を採用する | 背景・根拠・完了条件・優先指定を既存の課題へ統合するか、新しい見出しへ移す。同じ変更で旧候補を整理し、共通一覧に着手順か再開待ちの一行を置く。デザインの詳細は画面差分に置く |
| 別の担当が進める・一部だけ完了する | 最新の一覧と詳細を照合して、同じ課題の残作業と次の一手を更新する。前の担当が完了した部分の仕様・証跡や、引き続き有効な優先指定を引き継ぐ |
| 実装・修正が終わる | 現行仕様と確認済みの結果をそれぞれの基準となる資料へ移す。確認だけが残れば未確認事項へ、追加実装・修正が残れば同じ課題へ。対象の作業が尽きた時点で一覧と詳細を閉じる |

確定要求が候補の一覧や実装前の資料にも残っている場合は、現在の課題へ誘導する。方式の選択や検証が残る場合も、採用の判断は確定済みとして扱う。課題間の依存は、影響を受ける側から先行する課題へリンクを張り、何を確かめれば先に進めるかを書く。

### 基本順位と依頼ごとの優先指定

基本順位はコア体験への影響、既知の阻害、重要な不確実性、依存、次の区切りで得る価値と所要時間で決める。一時的な優先・保留や個別の要求者の指定がある場合は、対象の課題・依頼者または利用場面・指示の根拠・適用範囲・終了または見直し条件を既存の着手順か再開待ちに添える。期間が明示されていなければ日付を推定せず、対象完了や次の指示など実際の区切りを示す。

明示された優先指示は、次の区切りで実際の着手・結果と照合する。完了条件を満たすか要求者が変更するまで有効とし、保留時は理由・先にできる作業・再開条件を同じ課題で追う。たとえばWatch音声の実験を保留していても、要求者が決定した一般向けの入口・案内の是正は独立して進める。方針が未決なら、同じ課題に高優先度と判断待ちを明示して要求者に確認する。

着手順を変えたときは、要求者の指定と、実際に着手した工程が同じ課題から追えるようにする。実装まで求められている課題では、調査や試験を終えた時点で実装を次の一手として残す。他を先に進めた場合は、先行した課題、理由、再開できる条件を記す。指定の確認や訂正が繰り返された場合は、判断の経緯が分かる記録へ課題からリンクする。

実行時は依存を満たした候補に、その依頼・利用者に有効な指定を適用し、残りを基本順位で選ぶ。個別指定を製品全体に適用する範囲は要求者の明示に従う。競合する指定の範囲が決められなければ判断待ちに理由を残す。指定の完了・解除・失効時は通常の基準で着手順を見直す。課題の詳細は1つに保ち、現在の適用順と指定の理由を同じ入口から読めるようにする。

| 仕様と要求 | specは現行のAPI・動作・設定・制約。要求はWhy/Whatと統一方針。未実装設計はbacklog、未確認一覧はvalidationへ置く |
| ファイル名 | 日本語文書は内容と役割が分かる名前にする。App/RTC等の実装上の固有名は維持。内容・役割・保存期間を説明できる具体名を使う |
| 移動 | 同じ変更で参照と索引を更新。空になった旧文書ディレクトリはrmdirで除く。文書清掃の対象は所有する文書と参照へ絞り、生成物・依存・Xcode内部の状態は専用の資源管理工程で扱う |
| 過去計画 | `docs/development/history`に旧計画として原文を保持し、現行との差と現在の参照先を添える。現行の実行用promptには最新の基準となる資料を参照する |
| ツール入口 | AGENTS.md / CLAUDE.md / .github/copilot-instructions.mdは共通の規約への必須参照だけにし、規約本文は該当する文書にまとめる |
| 継続検査 | scripts/check_documentation.pyでリンクと到達性を調べる。着手順・再開待ちから画面差分を含む課題詳細をたどり、分類・状態・次の行動が分かることを確認する。採用判断待ちの案も、統合した課題詳細と判断・再開待ちの一覧の両方から追えることを確かめる。文書ディレクトリが空でないことと、Settingsの記載も調べる。過去原文のコードブロックは履歴のリンクとして区別する |

過去資料の採番・旧パスは原文保全のため引用内に残す。現行規約の識別には説明的な見出しを使う。

## パッケージ要求の管理

対象は[パッケージ要求](../requirements/パッケージ要求.md)。packageが持つ恒久的な責務と判断基準を記録する。現状との差は課題、確認待ちは検証へ分ける。Appの暫定実装や既存コードの棚卸しはspec・backlogへ分類する。

| 工程 | ルール |
|---|---|
| パッケージ更新 | 要求を参照してApp側で回避している内容が解消されているか確認する。この工程での要求文書の扱いは参照と適合確認に限定する。要求の改訂は独立した要求判断の工程で扱う |
| App追従 | package APIを適用後、App仕様を実態に揃え、課題を更新する。未確認事項と証跡は検証へ記録。恒久要求は責務と判断基準として維持する |
| 追加判断 | 共通の責務方針は要求、実装すべき差分は課題へ記録する |

### 追記する内容

| 記録する項目 | 内容 |
|---|---|
| package | 変更対象package |
| packageが所有する責務 | Appではなくpackageが持つべき責務 |
| 責務をpackageへ配置する理由 | package独立性、OS差分吸収、準異常系処理、runtime情報通知、設定受け取りのどれに関わるか |
| 要求を満たす判断基準 | 利用者やAppが何を同じ意味で扱える必要があるか。具体的なAPI・処理順は仕様または課題の設計案へ分ける |

### App追従時の扱い

| 項目 | 方針 |
|---|---|
| App 側暫定実装 | App側の都合として扱い、Appの仕様や課題へ記録する |
| package に既にある責務 | `docs/spec/packages` と `docs/spec/App/Configuration/Bindings` を参照し、App 仕様から該当の基準となる資料を参照する |
| 新しい不足の判断 | App が OS 差分、継続可能な準異常系、runtime report/event、設定受け取りを自前で補う必要が出た場合だけ追記する |


## 分類の判断と完了時の移動

1つの用途に複数の残件があるときは、操作・環境・受入条件ごとに判断する。完了を判断できる最小の結果と、その結果を確認できる担当・手段を記す。依頼者の報告で条件を満たした範囲は、根拠を検証履歴に残して閉じる。

自動試験、Simulator、Macなどで条件を確かめられる項目は、その手段を使う。物理端末や実サービスでしか判定できない差が残る場合に、その差と観測点を検証一覧へ記す。分類を更新したら、一覧と詳細、検証一覧、完了記録を照合し、完了済みの作業や同じ確認が重複して残っていないことを確かめる。

| 条件 | 状態と更新先 | 次の判断 |
|---|---|---|
| 要求を採用済み AND 必要な振る舞いが未実装 | 共通バックログに主分類を付ける | 最小ストーリーの完了条件を定める |
| 実装済み AND 当該条件で結果が未確認 | 検証の未確認事項 | 確認する環境・期待結果・再開条件を残す |
| 実装済み AND 観測結果が要求を満たさない | 共通バックログで改善またはデザインに分類。失敗の証跡は検証履歴 | 期待と実際の差、変更できる所有元を示す |
| 実装済み AND 当該条件で受入済み | 現行仕様と検証履歴 | この範囲の課題を完了とする。他の環境は個別に判定する |
| 改善案の採否を決めていない | 改善候補 | 効果と採否を判断できる条件を残す |

| 問い | 置き場所 |
|---|---|
| なぜ必要か・何を統一して求めるか | requirements。作り方への共通制約はpolicies |
| 今のコードは何を行うか | spec。設定値、API、例外・制限も実態として記録 |
| これから何を作るか | backlog。未採用案と実装課題を分け、完了条件・設計案を置く |
| 実装したが何をまだ確かめていないか | validation/未確認事項 |
| どの条件で何を確認したか | validation/history。過去の条件と結果を保持し、現在の結果を別の記録として追加する |
| どう設定・操作・再実行するか | manual / development。試算は前提と確認日付きの開発資料 |

分類は文書名だけでなく本文にも適用する。要求・仕様には他分類への参照を置けるが、課題表・未確認表・試験結果は分類ごとに記録先を決める。実装後は課題から作業を外し、実態を仕様へ、確認待ちを検証へ移す。達成済みでも恒久要求は維持する。APIが値を取得できないことや非対応OSでのエラーは現在の仕様であり、現行仕様へ記録する。
