## 品質と開発プロセス

### 常設のセキュリティ監査

全作業で個人情報・トークン・秘密鍵を守り、初回設定後の通常運用で人が秘密を扱わずに安全性を維持できることを監査する。着手・再開時に情報の出口を確認し、コミット・成果物の共有・外部送信前に、[常設セキュリティ監査](../../.agents/skills/security-audit/SKILL.md)の手順に沿ってローカルで検証し、最新のAstraに判定を依頼する。定期実行は未変更のコード、依存、配布・運用を含むプロジェクト全体を対象にする。修正時は監査側が修正箇所・変更前後の内容・影響・検証根拠を求める。双方で個人情報の非保持と、読み取り権限で観測できるサーバーの稼働状態を確認する。監査への入力・報告は、公開可能な論理名と許可した分類・検証結果に限定する。

現在の使い方と保護策で安全要件を満たす所見は、対応不要として閉じる。定期作業でも対応不要の所見は課題に数えず、バックログへは実際に対応が残る課題を登録する。監査結果の報告は、[常設セキュリティ監査](../../.agents/skills/security-audit/SKILL.md#最新-astra-へ判定を依頼する)に従い、いま予定している操作と、その前に対応が必要な指摘に絞る。判断に必要な証拠が欠けた場合は、その判定に依存する共有を保留して不足分を確認する。安全要件を満たさない箇所が判明したら、権限内で修正し再検証する。定期的な手更新への依存は[定期更新と安全性の確認](../../.agents/skills/architecture-refinement/SKILL.md#定期更新と安全性の確認)に照らして審査する。

### ブランチ運用

共有の `origin/main` をトランクとする。通常作業と定期作業を通して、製品開発の主担当とその委任先を合わせて、進行中の作業は1件とする。[別チャットが文書を担当する条件](#別チャットが文書を担当する条件)は文書の担当者に適用する。着手前に既存の着手順と作業記録から、今の1件、担当、動作を確認できる最小の変更、完了条件を確かめる。担当が一人の場合も、[進行中の1件を決める手順](#進行中の1件を決める)で直前の単位の完了を確かめる。ローカルとクラウドで着手が重なる場合だけ、主担当が共有の作業記録に担当と対象を明示する。製品の担当が重なったら、主担当と受入条件を既存の作業記録で確かめてから編集する。着手宣言だけのコミットは作らない。先約があれば、その受入に必要な調査・検証・レビューを手伝う。新しい依頼や別の問題はバックログに残し、この区切りで次の1件を選ぶ。

1件ごとに、既存の main で変更し、対象の回帰と変更監査を通し、コミットを共有 main に反映して読み戻す。通常の製品変更は固定 preview まで同期する。テストが失敗したら、今の変更を小さくするか原因を直して同じ入口で確かめる。外部の判断が必要ならその場で依頼する。実機操作は[実機確認を一度のロック解除で終える](#実機確認を一度のロック解除で終える)手順に従う。動く範囲を受け入れ、残りと再開条件を既存のバックログまたは検証待ちに記録する。最優先の受入条件が未確認なら、[別項目へ移る前の確認](#実装判断の優先順位)に従う。送信を保留する変更は履歴と理由を保全し、保留対象を含む push はその受入後に行う。

定期作業と push には[節目の完了条件](#節目の目的と成果の確認)を優先する。定期作業中は、その回の点検・是正・再検証に集中する。是正の各小単位は、送信する履歴と自動配置先の受入条件を満たしたら、その区切りで共有する。送信自体に保留条件がある場合は、その解除を今の1件に含める。監査が対象とする配布や配置の保留は、その操作に適用する。通常作業は定期作業が完了してから再開する。

通常は既存の `main` の作業フォルダで編集・検証し、対象差分だけを監査して直接コミットする。着手時にfetchして共有基準の `origin/main` を確認し、他担当の編集範囲、ステージ済み差分、検証で使う資源を照合する。既存の差分があれば、その受入条件と所有者を確認する。ファイルやステージが異なる場合も、今の受入条件に沿って着手の可否を決める。クラウドではその環境で利用できる既存の作業領域を使う。

新しく作るコミットには、このリポジトリで依頼者が設定したGitの名義を使う。文書だけのコミットでも同じ設定を使い、担当名や自動化用の名前・メールアドレスで上書きしない。既存コミットを取り込むときは元の作者を保つ。

#### ローカルmainでコミットして共有する

製品・規定・スキル・バックログには同じ手順を適用する。別チャットの担当者も既存の作業フォルダとローカルの `main` を使う。こうすれば各担当が同じ先端と未コミット差分を確認でき、作業先ごとの変更の回収や取り込みマージを減らせる。編集範囲と検証が独立していれば別ファイルを並行して編集できる。短期ブランチや別worktreeを担当者ごとに作らない。

1. 編集前に `git branch --show-current` が `main` であることを確認し、fetchして[トランクの同期判定](#トランクの同期判定)を行う。手元が遅れているだけなら既存の編集を保ってfast-forwardする。分岐や以前の未送信分がある場合は、その解消を優先する。
2. 1つの動作や判断を検証できる範囲に絞る。検証・変更監査が通ったら、別件や後続の作業が終わるのを待たず、その場で閉じる。ステージからpush後の照合までは一人が担当する。通常のindexで自分の対象パス・差分だけをステージし、ステージ済みの差分全体を確認してローカル `main` にコミットする。他担当のステージがあれば交代を待つ。
3. そのコミットを直ちに `git push origin main` で共有する。固定previewも同時に同期する場合は、同じローカルmainを送信元とする通常のatomic pushを使える。fetch後、ローカル `main` と `origin/main` が同じコミットを指すことを確かめる。indexと作業フォルダに今回の未コミット差分が残っていないことも確認する。別担当の未コミット差分は保護する。別件へ移るときは[作業を切り替える前の確認](#作業を切り替える前の確認)まで行う。

pushを拒否されたら次の作業を止めて最新の共有履歴と照合する。分岐中や監査中の文書でも、共有先端から別にコミットを作ってpushする経路へ切り替えない。現在のローカルmainを経由する同じ手順で再開する。共有済みの文書が手元で変更として見える場合は、作業内容・index・ローカルmain・共有先のコミットを照合し、復旧対象を特定する。共有済みの内容の書き戻し、再コミット、取り込み専用マージで差を埋めない。

#### 別チャットが文書を担当する条件

依頼者から別チャットで直接頼まれた担当は、規定・スキルの修正や未着手課題のバックログ登録を、主担当の製品作業と並行して行える。文書担当も自分の依頼を1件ずつ完了する。製品の主担当とその委任先は、ファイルが異なっても今の受入条件を外れる別件に着手しない。自分でチャットや担当を増やしてこの例外を使うこともできない。

並行して編集できるのは、変更するファイル、判断に使う前提、検証や配置への影響を独立させられる場合に限る。主担当が編集中の文書と重なる、または新しい規定が進行中の受入条件を変えるときは、該当箇所の編集と反映順を調整する。文書担当は製品の修正・検証を引き受けず、主担当は別チャットの文書差分を自分のコミットに含めない。定期作業中や履歴の復旧中も、監査済み文書の共有には同じ条件を適用する。

文書担当も[ローカルmainでコミットして共有する手順](#ローカルmainでコミットして共有する)に従う。別チャットで編集を分担しても、1件を検証・コミットし、共有先で読み戻してから次の担当に交代する。

#### トランクの同期判定

着手・再開時と各小単位のpush後に `git fetch origin` を行い、`git rev-list --left-right --count origin/main...main` を確認する。左は共有側だけ、右は手元だけのコミット数を示す。通常の区切りを閉じる条件は両方が0であること。未コミットの変更、共有先のpreviewと[全worktreeの回収状況](#作業先をmainに集約する)も照合する。

- 共有側だけが進んでいれば、手元の作業差分を保ったまま `git merge --ff-only origin/main` で追従する。
- 手元だけが進み、全件が今の検証済みの小単位なら、送信範囲を監査して通常のpushを行い、再取得して照合する。
- 両側が進んだ場合や過去の未送信分が残る場合は、次の通常作業を保留し、復旧候補のうち1つの受入条件だけを今の1件として選ぶ。両端のコミットを固定し、そこから列挙した手元だけの履歴を照合の母数とする。既存の復旧記録で各コミットを共有済みの根拠、今回反映した共有コミット、または残作業に対応付ける。連続した範囲はまとめて記録できる。完了時は未分類のコミットが0件であることと最終的なファイル差分の両方を確認する。マージで加わった競合解消も対象に含める。履歴と最終的なファイル差分を照合し、既存の検証と監査を対応付けて共有可能な単位から反映する。保留対象・理由・解除条件は既存の作業記録に残す。
- 解消中の未コミット変更と元のコミットは保全する。未監査の履歴の一括送信、別ブランチへの移動だけでの完了扱い、差分を失うresetや強制pushを避ける。未送信分をすべて照合して共有し、手元との一致を確認するまで、復旧を継続する。

#### 作業先をmainに集約する

通常は既存の `main` だけを使い、製品の編集・統合は主担当一人が行う。調査やレビューを分担するときも、同じ小単位を読み取りで確認する。着手・再開時と各小単位の完了前に、主担当が `git worktree list --porcelain` で全作業先を照合する。

過去のソースコードはまず `git show` や `git diff` で調べる。実行が必要なら順番に試し、入力・出力先を分ける。それでも現行の編集を保ったまま検証できないときだけ、一時的なworktreeを1つ使う。作る前に、具体的な干渉、主担当、比較対象、終了条件を今の作業記録に残す。追加分が既にあるときは新設を止め、その目的と差分を確かめる。複数のコミットで動作を比較する場合も、各回の入力と結果を保存し、同じ場所を順番に使う。担当人数や比較対象の数に合わせて作業先を増やさない。

比較を終えた主担当は、各作業先でステージ済み・未ステージ・未追跡の差分、共有履歴にないコミット、稼働中の処理と検証証跡を確認する。採用する変更は検証して共有mainへ反映する。試験だけに使った変更は、基点・試験用差分・測定結果から検証条件を再現できることを確かめる。終了した作業先と不要な短期ブランチを安全に削除し、一覧を読み直して通常の作業先がmainだけに戻ったことを確認する。続いて[短期ブランチの回収](#短期ブランチの回収)を確認して、その小単位を完了とする。

使用中・所有不明・採否未決の差分があれば保護し、既存のバックログに作業先、残る判断、回収する担当、再開条件を記録する。回収は元の小単位の残作業として次の通常作業より先に扱う。結果の記録、退避、担当交代だけで完了にしない。

#### 短期ブランチの回収

常設するブランチは開発用の `main` と固定環境用の `preview` に限る。通常の編集・調査・レビュー・退避のためにブランチを作らない。過去のコミットを隔離して試すだけなら、上記の条件を満たしたworktreeでコミットを直接指定する（detached HEAD）。短期ブランチにコミットを積む必要がある場合だけ、主担当が既存の作業記録に用途・統合先・削除条件を残す。リモートにも必要な理由がある場合だけ、そのブランチを共有する。

着手・再開時と各小単位の完了前に、主担当が次の3つを照合する。worktreeに結び付いていないブランチも対象とする。

| 確認するもの | コマンド |
|---|---|
| ローカルの全ブランチと各先端 | `git for-each-ref --format='%(refname:short) %(objectname)' refs/heads` |
| originに実在する全ブランチと各先端 | `git ls-remote --heads origin` |
| 各作業先、使用中のブランチ、直接参照中のコミット | `git worktree list --porcelain` |

短期ブランチを見つけたら、作業先・利用中の担当と処理・未コミット差分を確認する。fetchした `origin/main` に先端が含まれるかを調べる。履歴が分かれていれば、未統合コミットの変更と共有側の実装・検証結果を照合する。最終的に採用した変更を共有し、試験だけの差分は再現を確認してから、終了したworktreeと対応する短期ブランチを回収する。originにも同名のブランチがあれば、その先端と配置への影響を別に確認する。削除時に先端が照合時から動いていれば中断して確認し直す。名前の一括指定や強制削除で残件を消さない。

回収後に同じ3つの一覧を読み直す。通常作業の完了条件は、手元とoriginの短期ブランチがともに0件、追加worktreeが0件で、今回の未コミット差分・未送信コミットが残っていないこと。結果は既存の作業記録に残す。いずれかを確認できない場合、または保護すべき差分がある場合は、ブランチ名・先端・担当・理由・次の回収条件を既存の残項目にまとめる。回収は元の作業の一部として継続し、次の通常作業への着手を保留する。

#### コミットと共有の手順

- コミット操作は一人ずつ行う。別担当がindexを使っていれば、その担当のコミットまで自分のステージを待つ。その間は同じ変更の検証を進める。他担当の作業領域に対するcheckout・reset・stash・削除は禁止する。
- 作業中の同期は、小単位の着手・再開、長時間の作業中、統合・pushの区切りで行う。続けて行う検証・監査・コミットには直前の同期結果を使える。originが進んだ場合は取り込んだ差分の影響を確認し、変更された監査対象と影響する検証だけをやり直す。
- 着手時と担当範囲の変更時に、利用可能な共有の作業記録・連絡手段へ担当、対象ファイル・責務、基準commit、作業branch、次の統合単位を記録する。origin上の作業branchや他担当の変更も確認し、同じ箇所への変更が重なる場合は編集範囲と統合順を調整する。連絡・確認ができない場合は既存の変更を保全し、作業記録から現在の1件と残る受入条件を確かめる。originには未pushの作業が見えないことも前提にする。
- 作業中も小単位の境界と長時間の検証後にoriginを再確認する。統合・pushの実行者を対象単位ごとに一人へ揃え、最新originとの差分を照合する。自分の検証後に他担当の変更が入っていたら取り込み、競合解消と影響範囲の回帰を済ませてからpushする。競合時は両者の目的・契約を保持して解消し、判断不能なら当該箇所を保留して担当へ引き継ぐ。
- mainとpreviewの同期中にも別担当のpushが入り得るため、可能な場合は両branchを同じコミットへatomic pushする。拒否時はfetchして最新mainとpreviewの未統合差分を確認し、必要な変更を統合して再検証し、通常のpushをやり直す。自分の対象コミットが共有のmain・previewへ届いたことと、手元のmainの同期判定を両方確認する。その後の別担当のコミットはその担当が同期する。同期後はoriginの両branchを再確認し、別担当が進めたmainを古いpreviewで上書きしない。同期の確認結果には対象commitを添え、その時点の結果として報告する。
- 継続開発と統合の基準は`main`一本とし、短期branchも統合先を`main`へ揃える。
- PR運用は行わず、検証済みの変更をmainへコミットして直接pushする。
- 小さく試し、必要な検証を終えた作業の区切りごとに、必ず実行環境の`main`へ同期・統合し、`origin/main`へpushする。手元の通常作業フォルダへアクセスできる環境では、そのローカル`main`にも取り込む。短期branchやworktreeだけに成果を残さず、対象コミットの反映と[トランクの同期判定](#トランクの同期判定)を確認する。統合対象は検証済みの自分の変更へ限定する。
- この同期は作業全体の完了時だけでなく、作業中の小さな検証済み単位ごとに直ちに行う。次の単位へ進む前にコミットし、実行環境の`main`に統合する。`origin/main`にpushしてから`preview`を同期し、こちらもpushする。未統合・未pushのコミットを積み上げない。編集再開・統合直前には他セッションの更新を確認し、他者の未コミット差分とindexを保護して自分の変更だけを反映する。
- 固定プレビュー用の`preview`も、区切りごとに検証済み`main`と同じコミットへ同期し、`origin/preview`へpushする。同期時の4参照を確認する。確認中に他担当が先へ進めた参照は、自分の対象コミットを履歴に含むことを確かめる。preview固有の未統合差分があれば保全・統合してから同期し、履歴を無断で破棄しない。branch同期とCloudflareのbuild・配置成功は分けて報告する。
- クラウドから手元の作業フォルダへアクセスできない場合も、originのmain・previewへ小さな区切りごとに変更を反映する。手元への取込待ちは対象コミットと取込手順を引き継ぎ、ローカル側は再開前にfetchして取り込む。アクセス不能な作業領域まで同期済みとは報告しない。環境・権限・検証不足で統合できない場合は、該当する変更を手元に残し、main 未統合の理由・担当・再開条件を記録する。受入済みの独立した変更はその都度 main に反映する。
- 隔離作業は区切りごとにmainへ統合し、不要になった作業branchとworktreeをこまめに削除する。ローカルとoriginの短期branchを整理対象とし、継続用の`main`・`preview`は維持する。削除前に未統合コミット・未コミット差分・未追跡ファイルの保全と統合、稼働process、残す検証証跡を確認し、使用中・所有不明の作業領域は保持する。実装済みの契約は仕様へ移し、課題一覧には残作業を保持する。 保全する旧projectやpackage sourceは、Xcodeの同期フォルダから開発用のproject／packageとして再検出されないアーカイブ形式で保存する。
- 継続作業では共通の規約に加え、対象機能の現行仕様・残課題・必要な証跡だけを読む。引継ぎには現在の作業領域・基準commit・未統合差分・生存中の検証handle・次の完了条件を絞って残し、再開時は現行の仕様・手順と引き継ぎ内容を照合する。

### 公開バージョンとビルド番号

- 公開バージョンは可能な限りSemantic Versioningの`major.minor.patch`を適用する。利用者に公開する機能・招待や保存形式・通信契約の互換性を基準に、非互換変更はmajor、互換性を保つ機能追加はminor、不具合修正はpatchを変更する。major変更時はminor・patch、minor変更時はpatchを0に戻す。
- 公開バージョンは利用者の明示指示で変更し、通常のビルド・Archive・アップロードでは現在値を維持する。
- ビルド番号はXcode標準の`CURRENT_PROJECT_VERSION`、公開バージョンは`MARKETING_VERSION`を使い、projectの共通設定をApp・Widget・Watch・テスト対象が継承する。通常ビルド・Run・Test・Archiveを含む全scheme・全構成でビルド番号を自動的に進める。採番は既存の共通設定と標準ツールで扱う。
- Xcode標準のBuild後処理とAppleの`agvtool`で次回用の番号を更新する。次回用設定が進むことを完了条件とし、開始時への反映タイミングと欠番を許容する。保存先の見直し後も自動インクリメントを維持し、Xcodeを開いたまま標準操作で実行できる構成を保つ。
- ビルド・テストで進んだ`CURRENT_PROJECT_VERSION`は、その検証を終えたコードと同じコミットに含める。関連作業の検証とコミットが確実に数分以内に終わる場合も、まとめてよい。前の作業の番号更新が漏れていた場合や、関連作業を数分以内にコミットできる見通しが立たない場合は、番号変更だけを先にコミットする。
- どちらの場合も、App・Widget・Watch・各構成の共通値が揃い、既知の配布・Archive番号を下回らないことを確認する。その作業で変更した箇所だけをコミットする。
- 同一ビルド・Archive内のApp・Widget・Watchの番号を一致させる。成果物の番号とBuild後処理で進んだ次回用設定値を区別する。配布時は既存の最大ビルド番号を超える番号を確認し、Organizerが配布時に番号を管理する場合もArchive内の番号と配布物の番号を区別して記録する。
- 並行作業・実行中のアプリやビルドを維持し、自分の検証に必要な実行資源を所有範囲で調整する。番号は全構成と既知の配布・Archiveにある最新最大値を基準に単調増加させる。設定の欠落・破損時は記録済みの最大値と履歴から復旧する。別checkoutや別Macからの配布は担当者間で番号を共有する。
- 配布用`CFBundleVersion`はAppleの規定する数字とピリオドの形式を使い、その形式で10進値を保存する。Apple OSの英字入りbuild-versionは別の識別子である。旧公式資料にある開発段階の`a`・`b`・`d`・`fc`接尾辞も16進数ではなく、製品配布時には除く。SemVerの`+build`などの付加情報は必要に応じて別の説明項目で扱う。Xcodeでの設定と配布手順は[開発環境](../development/開発環境.md)を参照する。

### ビルドが更新する追跡ファイル

Xcodeのビルドは、ビルド番号のほかにString Catalog（`*.xcstrings`）も、各targetが抽出した文字列から自動で同期する。これらの差分はビルドの成果であり、誰がどの目的でビルドしたかに関係なく、見つけた担当者が取り込む。

| 対象 | 取り込み方 |
|---|---|
| ビルド番号 | [公開バージョンとビルド番号](#公開バージョンとビルド番号)の条件に従ってコミットする |
| String Catalogの同期差分 | `python3 scripts/check_string_catalogs.py`で既存の訳が欠けていないことを確認し、他の変更と分けた独立コミットにする。Xcodeの同期は文字列を追加・並べ替えし、古い項目をstaleにして訳のない項目を削除し、訳を消さない。検査が通る差分はそのまま取り込める |
| 使われなくなった文字列（stale）の削除 | Xcodeは使われなくなった文字列をstaleにして訳ごと残す。削除は意図した変更であり、ビルドの成果ではない。staleの各文字列がどのtargetのソースからも参照されていないことを確かめ、削除だけの独立コミットにしてから検証する（検査は未コミットの差分だけを見る）。削除後のビルドが同じ文字列を戻した場合は、使用中の文字列なので削除を取り消す |
| 訳の欠落や、使用中の文字列のstale化など誤った出力 | 差分を破棄して終えず、出力の原因（抽出設定・targetの所属）を直してから再ビルドし、正しい出力を取り込む |

取り込める正しい差分だけを生む構成を維持する。全targetがSwift文字列を抽出するよう`SWIFT_EMIT_LOC_STRINGS = YES`をprojectの共通設定に置き、targetで上書きしない。`scripts/check_platform_configuration.py`がこの設定を、`scripts/validate.py`が訳の欠落を検査する。ビルドのたびに取り込めない差分が残る場合は、運用で避けずに構成を修正する。

### 実装と検証

#### テストの設計と結果を現在の課題に照らしてレビューする

[現在のバックログと変更の方向を照合する手順](#レビューで現在のバックログと変更の方向を照合する)を、試験を選ぶ前と結果を受け入れる前に適用する。設計時は、優先する課題の受入条件を、利用者の操作・環境・期待結果に分け、どのテストのどの判定で確かめるかを示す。削除・統合するテストに回帰を検出する役割があれば、代わりにその不具合を検出する試験と判定箇所を示す。

Simulatorを使う試験では、[試験後の端末の残数](#テスト後に残すsimulatorを確認する)も受入条件に含める。受入時は、レビュー担当が課題の見出しから、実行したテスト、実際に通った経路、観測結果までをたどる。例えば、通知の送信に成功しても、通話中の受け手に音を鳴らさず届いたかは端末での観測が要る。観測できていない条件は未確認として残し、今の試験が見逃す不具合の具体例と、それを検出する最小の追加検証を示す。後続課題で変わる実装の細部や未採用の案を期待値にした試験は、確定した振る舞いに沿って判定を見直す。

#### Swiftテストの準備と後片付けをレビューする

Swiftテストの設計・リファクタリングでは、[同じテストを個別または一括で選べる入口](../development/自動検証.md#appテストの対象を選ぶ)から、次の両方をレビューする。Swift Packageでも、対象のテストと、それを含むテスト群で確かめる。

| 実行単位 | 準備と後片付けの判断 |
|---|---|
| テストを1件だけ選ぶ | そのケースが使うデータ、サービス、端末だけを必要な時点で用意する。その1件を最初に実行し、準備から片付けまで完結することを確認する。 |
| 対象のテスト群を一括で実行する | ビルド、アプリやSimulatorの起動、試験データの生成など、時間のかかる処理の実行回数を確かめる。読み取り専用のデータや安全に再利用できる資源は必要な範囲で一度だけ用意し、最後に解放する。各ケースが書き換える状態は分離し、順番を変えた実行や並列実行でも判定を保つ。 |

準備の共通化は、関数の数と実際の作成回数を分けて評価する。同じ関数が各ケースや実行のたびに同じ環境を組み立てていれば、レビューで呼出箇所と回数を示し、重複する準備を取り除く。例えば、互換性のある常用Simulatorは次の実行でも選び直して使い、書き換えた試験データはケースごとに初期状態へ戻す。再利用する資源ごとに、所有者・必要な構成・利用可能な状態を確かめ、同時利用が干渉する場合は排他する。構成の変更や復旧できない破損があれば、該当する資源を作り直す。初回起動や新規環境への配置そのものを確かめる試験には、所定の新規作成手順を使う。

再利用を導入・変更した場合は、環境がない状態からの初回と、同じ構成で続けて実行する2回目を比べる。同じ資源を再利用したこと、2回目に省けた準備の回数と時間、試験開始時のデータと合否がそろうことを確かめる。

準備や後片付けの変更前後で、端末とビルド条件、キャッシュの状態をそろえる。代表のテスト1件を単独で測り、それを含むテスト群の一括実行も測る。開始から終了までの実時間と、準備・テスト本体・後片付けの内訳を既存の実行結果やログで照合する。並列実行では各ケースの秒数の合計と全体の実時間を区別する。レビュー記録に、繰り返していた処理、実行回数と所要時間の前後差、個別・一括それぞれの合否を残す。

削減するのは重複した準備や待ち時間とする。準備の途中で失敗した場合やテストが中断した場合も、作成済みの資源を回収し、次の単独実行が同じ初期状態から始まることを確かめる。受入に必要な起動・初期化・回帰検証や[Simulatorの回収](#テスト後に残すsimulatorを確認する)を維持する。

#### テスト後に残すSimulatorを確認する

テストのリファクタリングとレビューでは、各プラットフォームで通常の検証や通信試験に繰り返し使う端末を特定する。常用するSimulatorは必要なプラットフォームごとに1〜2台とし、単体の試験と通信試験で共用する。ふだんは1台で足り、特定の2台通信試験だけで相手端末が要る場合は、その端末を一時作成して試験後に削除する。特定のOSバージョン、機種、障害条件を試すための端末やテストランナーが作る複製も一時端末として扱う。[音声E2Eの再利用と後片付け](../development/音声E2Eテスト.md#再利用と後片付け)

開始前と終了後に `xcrun simctl list devices -j` で停止済みを含む端末一覧を取得し、プロジェクトの所有記録と照合する。常用端末は停止して残し、個別条件のために作った端末は成功・失敗・タイムアウト・中断のいずれでも削除し、一覧から消えたことを確認する。強制終了などで後処理が動かなかった場合は、次回の開始時に所有を確認して回収してから新しい端末を作る。

レビュー記録にはプラットフォームごとの常用台数と用途、一時端末の残数を示す。**プロジェクト所有の端末が上限を超えて積み上がっている場合や、一時端末が1台でも残る場合は要修正とし、回収を確認するまでテストの整理を受け入れない。** 他担当が使用中の端末や所有不明の端末は区別して記録し、所有者を確かめる。名前だけを根拠に一括削除することは禁止する。

#### テストの分類と影響範囲による実行

この分類と選択実行は重要度の高い品質要求として扱う。毎回のCI、定期的な広域・長時間検証、開発時の局所回帰で、それぞれ実行しやすい単位に分割・集約し、同じ分類から必要な集合を組み合わせられるようにする。毎回の枠から外した必須条件は定期・明示実行へ対応付け、試験を省略したままにしない。

**要求を守れているかを判定する試験と、現在どこまで動くかを調べる試験には、それぞれ独立した実行方法を用意する。** 同じ入力生成や測定処理は共用し、実行条件・合否の意味・結果の保存先を区別する。

| 目的 | 固定または変更する条件 | 結果をどう使うか |
|---|---|---|
| 基準の試験 | 利用者に保証する操作、代表入力、機器や経路の条件、測定方法、品質目標を固定する | 閾値を外れたらその操作は未達とする。限界試験で別の条件が成功しても、基準の失敗を残す |
| 今の限界を調べる試験 | 同じ操作で、切替間隔・通信負荷・人数など調べたい条件を1つずつ変える | 各条件の実測と目標内外を保存する。試した範囲で達成できた条件と、外れた条件を示す。欠測・環境不備は別に記録する。結果を恒久的な保証にする場合は要求と基準の試験を更新する |

設計の判断に必要な条件を選んで限界を測る。以前の測定で判断できる条件は、その記録を使う。既知の未達を基準の試験から外したり、受入値を実測に合わせて緩めたりして完了にしない。

リントへの対応でも、条件式の評価順、音声フレームの受け渡し、再生予約や時計の更新順を変える差分は動作に影響し得る。整形だけの変更と区別し、その境界の基準試験を選ぶ。短い試験で同じ問題を見分けられればそれを使う。実際の出力でしか差が出ないときは、関係する音声経路だけを測る。

テストは対象（package・App・server・UI・音声経路など）、要求・ユースケース、検証層（単体・結合・E2E・実機）で分類する。変更の影響範囲、実行条件・依存資源、所要時間からも、必要なテストを選んで実行できるようにする。複数の分類を組み合わせ、共通処理の変更ではその利用先の関連回帰も選べるようにする。対象外・未実行・非対応を成功と混同しない。

<a id="xcodeとスクリプトのテスト配置"></a>

Xcodeで実行できるApp・package・UIの試験は、対応するテストターゲットやTest Planから選べる構成にする。コマンドやCIでも同じ試験を選び、判定を共用する。`scripts/tests` に置くのは、スクリプト自体の動作確認など、その場所での実行が必要な試験に限る。そこに残る試験も同じ分類から見つけて実行できるようにする。

<a id="xcodeからのサーバーテスト実行"></a>

サーバーのテストは、macOSのXcodeのテスト一覧からケースごとに選び、個別に実行して合否を確認できるようにする。既存のテスト定義からケースと表示項目の対応を自動で作り、追加・改名・削除に追従させる。ケースごとに手書きのSwiftテストや対応表を保守する必要がない構成とする。ケースごとの実行結果と失敗の詳細をXcodeの結果に自動で取り込む。Xcode、CLI、将来のXcode Cloudは同じテスト定義、ケースの選択、合否判定を使う。

短時間で終わる検査・単体試験と、build・音声E2E・長時間継続・実機・実サービスなど時間や資源を要する試験は、独立した実行入口・suite／Test Plan等で分けられる構成にする。所要時間は実測に基づいて分類を更新し、高速な試験を選ぶだけで重い試験まで起動しない。将来のCIでも同じ分類を使って高速枠と長時間枠を分離・選択できるようにする。CIの新設や有料試験の実行にも、費用と外部サービスの利用条件を適用する。

基礎検証は、実機の接続、実アカウントへのログイン、外部サービスの稼働に依存せず、開発環境から単独で繰り返せるように設計する。対象の製品処理を通し、外部との境界だけを差し替える。入力と開始状態を再現し、正常時の出力に加え、その用途で重要な失敗や復旧も観測する。基礎検証に実機が必要な場合は、同じ変更の中で依存を切り離し、実機なしで試験を通す。

部品同士の接続とアプリの操作は、必要な範囲をローカルの結合試験やSimulatorのE2Eで確かめる。各試験が確かめた条件を記録し、実機でしか判定できない挙動が残る場合だけ、最後にその差を実機で確認する。

変更ごとの必要な試験集合と根拠を示し、短い回帰を先に通し、影響に応じて所要時間の長い試験も実施する。時間別の分離を理由に必須のE2Eや製品受入を省略せず、実行結果を分類・対象ソース・設定へ対応付ける。音声は[製品要求の組合せ検証](../requirements/製品要求.md)を適用し、対応する組み合わせを挙げ、実行済みと未実行の範囲を明示する。


- 開発はTDDを前提とする。
- 注入した音声入出力で再現できる音声TDDを維持し、音声品質・安定性・拡張性を確保する。
- 接続性や暗号化などの非音声処理も、可能な限りTDDで実装する。
- テストは実装・実行・結果解析を一単位とし、成功を確認する。
- コアの成立や重大な不確実性の先行検証を優先しても、既存機能を回帰テストで保護する。変更前に共通処理・状態・呼出元・依存先を含む影響範囲と、その既存動作を保護するテストの有無・網羅性を確認する。不足する回帰テストは製品コードの変更前に実装・実行し、変更前の基準結果と既存の失敗を区別して残す。
- 機能実装・修正後は、最終のソース・設定に対して影響範囲のリグレッションテストを必ず実行する。影響する結合経路・E2Eも対象とし、既存機能の維持は影響範囲の回帰結果で判断する。新規の回帰は修正・再実行し、必要な検証が成功した範囲を完了・引渡し対象とする。未実行・失敗は未完として記録する。検証範囲は影響する領域へ絞り、選定根拠と結果を残す。
- 各実装工程の変更対象はAppまたはpackageの一方に限定する。両方に変更が必要なら、package単独で契約を定め、実装と検証を済ませ、次の工程でAppを追従させる。
- 常にビルド・テストが成功し、ワーニングを解消した状態を維持する。
- パッケージライブラリはAppの都合に依存させない。OSや通信方式による違いと、処理を継続できる異常はパッケージの内部で扱う。呼び出し側は、実装の詳細や環境ごとの違いを意識せず、同じ設計・同じ呼び出し方で利用できるようにする。
- パッケージライブラリ修正時は現在の要求に合う契約へ直接更新し、呼出元も新APIへ揃える。旧契約専用のalias・wrapperは整理する。
- パッケージライブラリは、実行時に確認する情報を含め、呼び出し側が必要とする情報をすべてリアルタイムで渡せるようにする。必要な設定は呼び出し側から受け取れるようにする。
- パッケージライブラリごとの責務を再定義し、App都合ではなく通話音声基盤として整理する。
- Appから見たpackageの不足は、packageの責務と設計から見直して根本解決する。
- Appがやるべきことは UI、設定入力、package lifecycle 呼び出しだけにする。

#### 試験データを作り直し、同じ条件で判定する

繰り返し使う試験環境では、共有mainの対象コミット、管理された設定・資格、試験データの生成手順から、空の状態で同じ用途を検証できることを求める。環境の用途に応じて、再生成するデータと継続して保全する資源を手順に定める。再生成する扱いが決まった範囲は、件数にかかわらず既定の手順で破棄して作り直す。担当者はその都度の了承を求めずに進める。配置方法・設定・資格の供給元・保存形式が変わったら、再現に影響する箇所を再検証する。開発版の実環境試験には[共有mainから同じ試用先を作り直す手順](../development/Cloudflare試用手順.md#固定previewを作り直せる条件)を使う。

本番と試験環境で同じ役割を持つ設定項目には、両環境で同じ名前を使う。接続先や資格の値は環境ごとに管理する。試験専用の設定項目には、名前だけで試験用と用途が分かる語を入れる。たとえば、両環境で通話を有効にする設定は共通の `SERVICE_ENABLED`、試験用の中継だけを有効にする設定なら `TEST_MEDIA_RELAY_ENABLED` のように命名する。設定を追加・改名するときは、コード、配置設定、手順書で項目名を揃える。

試験環境で必要な設定は、現在の受入条件と採用した方式から決める。廃止済みの方式にだけ必要だった設定は再作成の対象から外す。必要な設定や登録が不足したら、共有mainの設定、管理された資格の供給元、稼働中の配置の順に、どこで不足したかを特定する。公開設定や登録手順の不足は共有mainで直し、必要な秘密は対象環境用の保管先から供給する。直接更新が拒否された場合も、配置担当は許可されたブランチ連携での再配置・同名環境の再作成を検討し、必要な入力が揃った経路を実行する。拒否された操作だけを理由に用途全体を実行不能と判断しない。配置後は対象コミットと実効設定を読み戻し、元の試験を再開して合否を記録する。

受入試験の入力と実行方法は共有 `main` で管理する。別の担当者が対象コミットから試験専用の空の領域を用意し、同じ前提と判定を再現できることを受入条件にする。サーバーにしかない登録・手入力したデータ・前回の試験が残した状態を次回の前提にすることを禁止する。受入のたびに、一時スクリプトやコマンドを手元で組み直して実行することも禁止する。共有mainにある同じ入口を使い、調査用の試験を受入に採用するときは生成手順・入力・判定を先にレビューする。

| 場面 | 担当が残し、レビューで確かめること |
|---|---|
| 試験を用意する | 入力データか生成コード、その実行方法と設定を追跡する。乱数・時刻・機器が結果を左右する場合は再現条件を書く。試験ごとに発行する鍵や識別子は作り方と役割を記す。秘密値や利用者データは保存しない |
| サーバーに試験データを作る | 生成前に対象環境、今回の試験が所有する範囲、回収方法を定める。試験の終了処理で、成功・失敗のどちらでも今回作った分を自動で回収する。途中終了で残る場合は有効期限か再実行できる回収手順を用意する。終了時に残数や失効状態を照合する。回収要求を送っただけでは回収済みにしない |
| 同じ試験を繰り返す | 同じ名前で結果を比べるときは入力・操作順・測定区間・判定式を固定する。その場で入力を組み替えたり、失敗を見て閾値や対象件数を変えたりして合格にすることを禁止する。調査のために条件を変えた結果は別の試行として残す |
| 基準を正式に変える | 根拠となる要求・試験方法の誤り・環境の変更を示す。同じ変更で試験定義と手順を更新し、変更前後の条件、その違いが判定に及ぼす影響、適用するコミットを残す。以前の失敗は当時の基準で保持する。条件が異なる結果から修正の効果は断定しない |

外部アカウントや共有の試験環境を継続利用する場合は、所有者、必要な理由、初期状態の確認方法、更新・廃止の条件を手順に記す。各回の試験データはその中で分離する。所有者不明のデータは一括削除せず、環境と種類、確認する担当、回収完了の条件を既存の課題に記録する。

レビューでは「前回のサーバーデータが空でも始められるか」「初回の失敗を同じ条件で判定できるか」「途中で止めても今回のデータだけを回収できるか」を、生成元・基準との差分・回収結果で確かめる。試験の仕組みを新設・変更したときは、変更が届く経路を空の状態から試す。条件が変わらなければ保存済みの証拠を使える。必要な根拠が欠けた場合は、再現できない条件と直す箇所を示し、その結果を使う受入を保留する。

#### 試験する組み合わせをバックログへ引き継ぐ

基準と限界を別々に調べられ、代表例・境界例・失敗例から記録と判定を追える時点で、試験の仕組みを引き渡せる。対応する全機種や全設定の組み合わせを試す作業は、対象の既存バックログへ引き継ぐ。記録には、確認済みの代表条件、未確認の組み合わせ、追加する順番と理由、再開する条件、何を確かめれば完了かを書く。受入に必要な未達や主要な用途を妨げている不具合は個別に追い、範囲を広げる課題の完了を待たずに扱う。

### デザイン・ユースケース整理の次の回にテスト全体を見直す

デザイン資料・ユースケース全体を整理する回の次のリファクタリング機会は、テスト全体の点検・修正を最重要の主題とする。既存の[分類と選択実行](#テストの分類と影響範囲による実行)を土台に、ディレクトリ、実行単位、実行範囲、実測した所要時間ごとの集合と、テストの不足・実効性・品質を徹底して見直す。App・package・server・UI・音声E2E・自動化・実機や実サービスの各検証入口を点検する。Xcode・CLI・CI・定期実行との対応を確認する。配置と責務をそろえ、見つけて選んだテストを実際に実行できる構成へ直す。

**テスト品質を落とさないことを重要な制約とする。** 高速化や構成簡素化のために検証範囲、判定の厳しさ、実製品経路との対応を弱めない。影響と要求に応じた実行集合を用意し、重い試験を別枠へ分けても必須条件の行き先を失わせない。期待値・許容差・音声品質・連続性・遅延の基準を都合よく緩めず、skip・実行数減少・未発見や未実行を成功と扱わない。整理前後の要求／ケース／判定と選択・実行結果、時間・資源条件を対応付けて、維持・改善を根拠で示す。

実際の製品では呼ばれない本番コードがテストを通すためだけに作られていないか、製品の入口から呼出先・最終結果とテストの対象経路を対比して確認する。本番と別の疑似実装や迂回経路だけを検証する試験は、実際の契約・製品経路へつなぎ直し、不要な本番コードは根拠を確かめて整理する。動的呼出し・別OS／target・拡張・復旧経路を調べずに未使用と断定しない。必要な依存注入の境界、テスト用fixture・fake・stub・harness等は役割を区別し、テスト専用であることだけを理由に削除しない。

不足は要求・用途・立場・環境・境界・失敗・復旧・組合せに照らして特定し、検証の必要なケースと有効な判定を追加・修正する。成功だけでなく、意図した不具合・負例を検出できるかも確認し、実装をなぞるだけで不具合を見逃す試験や、失敗を握り潰す仕組みを直す。実機だけの受入条件も担当する集合と実行条件を明示し、Simulatorやmockの成功へ置き換えない。

この回の最新の構成・テスト・製品経路に敵対的レビューを3回行い、構成と選択実行、製品経路との一致と不足、判定・品質と回帰保護を含む観点から反証する。各回の対象・指摘・重要度・対応差分・再検証結果を記録し、重要な点はすべて解決する。前の回のレビューは流用せず、3回目の修正後の重要指摘と回帰も確認する。重要指摘や必要な検証が残る間は未完とし、品質低下を隠す重要度の引下げや先送りで完了扱いにしない。

小さく動く単位で関連試験を実行・解析し、仕様・実行手順・分類と結果を揃えてcommitし、main・origin・previewを同期する。

### 進行中の1件を決める

通常作業・定期作業・滞留の復旧を通じて、製品の主担当とその委任先を合わせて進行中（WIP）の上限は1件とする。定期作業では開始した回全体、リファクタリングでは依頼された範囲全体を1件と数える。途中のコミット、担当交代、バックログへの記録後も、全体の受入までこの1件が進行枠を占める。監査中に調べる差分や領域は同じ監査に含む。通常の機能開発は1つの動作や判断、未送信履歴の復旧はそのとき照合する差分を選ぶ。同じ受入に必要なコード、試験、文書、阻害要因の解消は一緒に扱う。個別に合否を決めて共有できる変更は別件として待たせる。

1. 着手・再開時には、既存の作業記録の同じ箇所に「今の対象（動作・差分・必要なら元コミット）、受入条件、担当、直前の単位の完了を示す根拠」を短く示す。編集前に `git status --short --untracked-files=all` で未追跡ファイルを含む変更を確認する。`git diff --stat` と `git diff --cached --stat` で一覧を取り、該当箇所を読んで対象と既存の差分を区別する。[共有履歴](#トランクの同期判定)と[他の作業先](#短期ブランチの回収)も確認する。
2. 受入条件の異なる作業が既に複数あれば、新しい実装や検証を始めず、保全した差分のうち先に閉じる1つを選ぶ。ほかの差分は担当・現状・回収条件を既存のバックログに残して編集を止める。担当が分からない差分は保護する。試験後とコミット前に着手時の一覧と差分を照合する。同じファイルに混じった別件や対象外の変更を見つけたら追加編集を止め、担当と範囲を確かめる。主担当とその委任先に別件の編集があれば止めて1件に戻す。別チャットが直接依頼された文書変更は[別チャットが文書を担当する条件](#別チャットが文書を担当する条件)で干渉を確認する。作業先の追加、stash、退避コミットで進行枠を空けない。
3. 編集・ツール実行・委任の前に、その結果で今の受入条件の何を判定するかを確かめる。主担当が依頼する調査・試験・レビューもこの1件に限定する。対象外の発見は未着手の残項目に記録する。確認待ち・送信保留の単位も未完として扱う。最優先の受入が確認できない場合は[別項目へ移る前の確認](#実装判断の優先順位)に従う。
4. 次の1件を開く前に、受入結果・共有先のコミットと今回の差分の残りを照合する。共有済みと判明した履歴は該当する共有コミットと検証根拠を示せば閉じられる。差分を取り戻す場合は、その変更だけを検証・監査して共有し、読み戻してから閉じる。区切りでは確認できた結果と残る障害を報告する。全体の復旧が続く間は、着手時から保護した残件と今回の差分を区別し、新たな未コミット変更・未送信履歴・作業先を残さず次の復旧対象へ進む。復旧から別件へ移るときは、通常作業・定期作業ともに、次の確認とトランク・短期ブランチ・worktreeの完了条件を満たす。

#### 作業を切り替える前の確認

製品の主担当は、別件の着手・再開を宣言する前に、直前の作業を共有した後のローカル `main` で次を確認する。定期作業の期限が来た場合や、以前のリファクタリングに戻る場合も同じ条件を適用する。

1. `git status --porcelain=v1 --untracked-files=all` でステージ済み・未ステージ・未追跡をすべて確認する。fetch後の `git rev-list --left-right --count origin/main...main` で未送信・未取込も確認する。前者は作業中のファイル、後者はコミットの差を示す。
2. 主担当・委任先・引き継いだ製品差分、または帰属不明の差分が1つでもあれば、現在の作業を続ける。採用する変更は検証・監査して既存のmainからpushし、共有済み・後継実装で不要な変更は根拠を照合して該当差分だけを片付ける。所有者や採否が決まらない差分は保持し、その判断を確かめる。一括コミットや一括破棄で一覧を空にしない。
3. 前件の受入結果を共有先と照合し、上の2コマンドを再実行する。進める条件は、前件の未処理差分がなく、コミットの差が両側とも0で、作業ツリーが空であること。[依頼者が別チャットに直接頼んだ文書](#別チャットが文書を担当する条件)だけが編集中なら、担当・対象・次の作業の編集と検証に干渉しない根拠を確認した分だけ例外とする。文書という拡張子や別ファイルであることだけでは除外できない。
4. 既存の作業記録または区切りの報告に、確認した共有コミットと両方の結果を残す。パッチ・bundle・stashや台帳への記録は復元の証拠として扱う。作業ツリーを空にしても、退避した前件の必須差分が未判定・反映待ちなら切り替えず、残る受入条件を扱う。共有できる手段を尽くしたら事実・障害・次の手段を報告し、別件へ移る前に依頼者の判断を得る。

### 小さく動く単位で検証・コミットする

**着手する範囲を、小さく実装し、ビルド・最低限の実動作・影響範囲の回帰を確認してコミットできる単位に限定する。検証を終えた変更をコミットしてから次へ進み、未コミット変更を積み上げない。**

通常作業では編集前に、単独で動作と回帰を確かめられる変更を1つ選ぶ。その検証と変更監査を終えた時点でローカルmainにコミットして直ちにpushし、共有先と手元を照合してから次の変更を開く。途中で想定より広い修正が必要と分かったら追加編集を止め、今の変更を単独で検証・共有できる範囲に戻す。期限が来たら実行中の変更をこの手順で閉じる。後続の機能の実装や節目まで未コミットの差分を積まない。

リファクタリングや定期作業では、以下の表の分割・縮小は一度に編集・検証して共有する差分だけに適用する。依頼された範囲と、その回に満たす条件は着手時から受入まで1件として扱う。

| 判断する時点 | 必須の進め方 |
|---|---|
| 着手前 | 1つの動作や契約を検証するか、1つの判断を確定できる最小単位を選び、対象・依存先・維持する動作・必要検証・コミット境界を決める。その単位で実装や検証を終えられない範囲は着手前に分割・縮小し、切り出せない依存部分は保留する。関連機能を一緒に設計する場合も実装はこの単位へ分け、App/packageの工程分離を守る |
| 変更の大きさ | 対象ファイルと変更行を目的に必要な最小範囲へ絞り、無関係な整形・移動・改善は別単位へ分ける。必要な実装・呼出元・テスト・仕様は一体として成立させる。行数やファイル数だけで切る代わりに、各コミットが単独で動作・検証条件を満たす境界を選ぶ |
| 実装・検証中 | 主担当とその委任先が扱う対象を同じ受入条件の一単位に限り、既存の呼出元・設定・保存/通信契約を維持して、修正→ビルド→最低限の実動作→影響範囲の回帰・必要E2E→結果解析まで閉じる。TDDの失敗再現から修正までは担当の所有範囲で短く行い、新しい回帰は修正・再検証する。検証対象のソース・設定を固定して証跡を対応させる |
| コミット時 | 必要な検証・レビュー・仕様更新が揃ったら、別機能や全体整理の完了を待たず、許可された単位をコミットする。対象が別の未コミット/未追跡ファイルやローカル専用設定に依存せず成立することも確認する。未完成の大きな差分から事後的に一部だけを選ぶ運用より、着手自体を小さく分ける。後続の大量変更までビルド・動作を回復できない範囲をまとめて進めることは禁止する |
| 区切りの記録と定期作業 | 小さな区切りごとに検証してコミットし、既存の作業記録へ対象・結果・証跡・commit・残課題と次の作業を残す。[ビルド番号の節目](#ビルド番号で決まる定期作業)と[コード・文書整理の節目](#コードと文書の定期整理)、[定期Archive](#署名付きarchiveの定期作成)、[100コミットのフル監査](#100コミットごとのフルセキュリティ監査)、[6時間ごとのサーバー資源と費用](#6時間ごとのサーバー資源と費用の点検)を確認し、該当する作業も行う |
| 滞留の確認 | 各最小単位の検証直後、別の変更に着手する前、中断や引き継ぎの前に作業状況を確認する。対象は自分の未コミット・未追跡の差分、ローカルmainへの未統合分、originへの未push分、previewとの同期差分である。未完了単位の数と継続時間、依存関係、検証待ち・許可待ちも確かめる。原則30〜60分の確認は長引く一単位の追加点検とし、そこまで同期を待つ理由にしない。膨張・長期化した場合は追加着手より分割・動作回復・検証・コミットを優先する。時間経過は見直しの契機であり、コミット条件を省く理由にはしない |
| 保留と並行作業 | 同期できない場合は理由・担当・対象コミット/差分・次の回収手順を明記し、解消を追加着手より優先する。未検証の変更を同期のためだけにmainへ入れず、必要な検証を通して閉じられる範囲へ縮小する。質問・環境・検証/許可待ちは理由・担当・対象差分・再開条件を残し、保留分も未完了として数える。保留した単位は担当と再開条件を明示して引き継ぐ。再開するときは着手順から選び直し、全担当で進行中の1件を確かめる |

ビルド・最低限の動作確認は部分工程のコミット条件であり、必要な回帰・E2Eや製品story全体の受入条件を維持する。部分工程のコミット・main統合と製品機能の完成を分ける。スキル/文書だけの変更は形式・参照・指示の整合を検証する。差分・index保護と単一実行者は[efficient-work](../../.agents/skills/efficient-work/references/実行管理と指示更新.md#統合とコミットの単一実行者)に従い、mainへのmerge許可・保留は親/主担当が管理する。

### 実機確認を一度のロック解除で終える

通常の変更は手元の自動試験で検証を終える。受入条件のうち物理端末でしか観測できないものだけを[実機確認待ち](../validation/実機確認待ち.md)に集める。担当や作業の区切りごとに端末を求めない。

1. 主担当は一覧全体と関連する受入記録を照合し、既存の証拠で判定できる項目を除く。残件がゼロならここで終える。
2. 残件すべてについて、対象ビルド、端末・周辺機器、試験データ、実行手段、合否の判定方法、結果の回収先を解除前に揃える。端末なしで試験の起動手順と結果の回収を予行する。手元の準備不足はこの段階で解消する。同じ操作で複数項目を観測し、解除中に必要な操作を先に、ロック中の確認を最後に置く。
3. 準備が整ったら、所有者には必要な端末のロック解除を一度だけまとめて依頼する。解除後は主担当が全残件を順に実行して結果を回収する。途中で一件が失敗しても、独立して確認できる残件はその場で終える。
4. 各項目の合否と未実行の理由を一覧に照合する。失敗した項目は証跡から手元で再現・修正する。機材不足やOSが強制する再認証など、一度で観測できない条件は理由と再開条件を残す。同じ条件のまま再解除を求めない。

### 実サービスを使う検証の費用制約

- 単体・結合・Worker/DO・端末間契約・UI・音声E2Eの通常検証は、ローカルの代替provider・fixture・mockを使用する。通常検証とCIの接続先・資格はローカルfixtureに固定し、実Cloudflareへの接続は次項の明示実行で行う。
- 実Cloudflareを使う検証は、単体・結合を含む必要なローカル検証がすべて成功し、失敗・未実行・skipがなく、検証対象のソースと設定が一致することを確認した後に限る。原因調査と設定組合せの検証はローカル環境で閉じる。
- 実サービスの検証を既定の自動実行から分離し、目的・対象・最大人数・最大時間・最大回数を決めた明示実行にする。短い疎通から段階的に進め、再接続・retry・polling・反復は目的と上限を定め、判断に必要な証拠が得られた時点で試行を終える。実HTTP認証確認と媒体/SFU/TURN確認は区別する。
- 検証終了・失敗・timeoutで、この検証が作ったsession・channel・TURN資格等を回収する。費用・利用量を記録し、上限や停止条件に達した場合は追加試行を止める。金額の上限は参加者秒に加えて実利用量・単価・回収結果で確認する。
- 開発用の既定接続値はDebugの手動試用に限定する。Release・Archive・隔離検証には専用の資格境界を適用し、unit/UI/音声E2Eにはfixture資格を使う。実資格のログ・検証レポート・Gitへの出力は禁止する。
- GitHub連携のCloudflare buildも費用対象として扱い、実サービス検証の起動対象をサーバー関連の監視pathまたは明示実行へ絞る。本番用CIと試用用の入口はそれぞれの役割を維持する。

### VS Code でのテスト実行環境（macOS）

- `xcodebuild` や `xcresulttool` は、`xcode-select -p` が `CommandLineTools` を向いていると UI テスト実行や結果解析に失敗することがある。
- Xcode本体がインストール済みでも、向き先が `CommandLineTools` のままだと同様に失敗するため、テスト実行時は Xcode本体の Developer ディレクトリを明示する。
- 原則として、環境全体を変更する `sudo xcode-select -s ...` ではなく、まずはその場限りの `DEVELOPER_DIR` を使う。

#### 推奨手順

- Xcode本体の場所を確認する。
```bash
ls /Applications | rg 'Xcode'
```

- 現在の向き先を確認する。
```bash
xcode-select -p
```

- `DEVELOPER_DIR` を一時指定してテストを実行する。
```bash
DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer \
xcodebuild test \
  -project RideIntercom.xcodeproj \
  -scheme RideIntercom \
  -destination 'platform=macOS'
```

- `xcresulttool` を使うときも同じ `DEVELOPER_DIR` を明示する。
```bash
DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer \
xcrun xcresulttool get test-results summary --path <path-to.xcresult>
```

- `<path-to.xcresult>` は通常 `~/Library/Developer/Xcode/DerivedData/.../Logs/Test/` 配下に生成される。

#### 恒久対応が必要な場合

- ローカル環境を常に Xcode本体へ向けたい場合のみ、明示的に切り替える。
```bash
sudo xcode-select -s /Applications/Xcode.app/Contents/Developer
```

- 向き先変更後は、`xcode-select -p` で確認してから `xcodebuild test` を再実行する。

## プラットフォーム共通化

- macOSとiOSの処理は、可能な限り同一の実装経路を通す。
- 最新APIでも共通化できない限定部分のみ抽象化し、OS差分を最小化する。
- ViewModelロジック、画面構造、状態管理、アクセシビリティIDは共通化する。
- OS依存点は抽象境界へ集約し、実処理は共通の契約を使う。
- 共通化の点検では、各OS・機器で提供する機能と設定・操作の対応を照合し、対象外の項目・案内・入口も除く。同じ動作の規則・保存・適用は共通の所有元に置き、提供可否と一時的な操作不可は区別する。たとえばMacにはWatch専用設定を出さず、iPhoneでの配布見送り中のdisabled表示とは分ける。UIのStandard／Advanced分離を維持し、OS別の重複修正を増やさない。
- 音声処理と通信処理のフロー全体はパッケージライブラリ化で共通化し、改善の横展開を可能にする。

## 抽象化の設計原則

- 抽象化の目的は、OS差分や通信方式、その他の差分の吸収だけでなく、機能改善を全プラットフォームへ同時展開できる構造を維持することに置く。
- 現時点の主要な境界は「OS依存API」「コーデック差分」「通信方式差分」とする。将来の要件で新たな差分軸が見つかった場合は、同じ原則で境界を追加する。
- 境界を追加する条件は、共通フローを崩さずに差分を隔離でき、重複削減・変更容易性・テスト容易性のいずれかを明確に改善できることとする。
- macOS／iOS、通信経路、コーデックの各差し替え境界で、同じ入力・条件に対する判断、状態遷移、設定反映の順序と結果は、1つの実装経路に置く。共通側は必要な操作・能力・結果を既存の契約で受け取り、具体実装の選択は組み立て箇所または方式を所有するpackageに集める。
- 数値・対応範囲・既定値の違いは値または設定の組で渡す。OS固有API、経路固有の接続手順、符号化・復号方式のように動作そのものが違う部分だけを固有実装に置く。音声・通信の中核フローはどの組み合わせでも共有し、同じ規則を1か所で直せば、対象の全経路がその変更に従う構成にする。
- 抽象化は重複削減・変更容易性・テスト容易性の向上を根拠として、必要な範囲へ導入する。

### レビューで現在のバックログと変更の方向を照合する

設計案・デザイン案・文書の方針・試験方法を選ぶ前と、最終差分を受け入れる前に、レビュー担当は[バックログの着手順](../backlog/README.md#着手順)で今回の目的と優先順位を確認する。変更する機能・契約・利用場面を手掛かりに、関連する先行課題と後続課題の詳細を開き、受入条件、依存関係、判断待ちの理由を読む。レビュー中に課題が更新されたら、影響する判断だけを見直す。指摘がない場合も、照合した課題の見出しと、受入条件を満たすと判断した変更箇所を既存のレビュー記録に一組示す。関連課題が見つからない場合は下記に従う。

- 今回の差分がどの受入条件を前に進めるか、または既存動作を保ちながら後続の変更をどう容易にするかを確かめる。優先課題から外れる作業、採用済みの後続課題で捨てる実装、判断待ちの案を先に固定する変更は、具体的に指摘する。未採用の案は、今回の実装要件に加えず、選択の余地が残るかを確かめる。
- 指摘には課題の見出しへのリンクと変更箇所を添え、影響を受ける利用者の操作や、後で作り直す箇所を具体的に示す。既存のレビュー記録に、影響を避けるための最小の修正案を残す。範囲を絞る案や着手順を変える案も検討する。関連課題が見つからなければ、確認した範囲と今回の根拠となる要求を短く残す。
- 採用済みの受入条件や依存順と衝突する場合は、その変更の受入を保留し、修正後に同じ課題で照合する。依頼者の最新の指示とバックログが食い違う場合は、意図が明確なら既存の課題を更新し、優先順位や仕様の選択が残る場合だけ、手戻りの内容と選択肢を示して確認する。

### リファクタリングで既存要求の矛盾を検出する

部分的な整理、動作を維持する変更、定期の全体整理のすべてに適用する。関連要求を照合してから設計案を選び、着手前のレビューにかける。各巡の受入前には最終差分で再確認し、途中で要求・前提・影響範囲が変われば、その判断に戻る。

1. **変更前に、同時に守る要求を特定する。** 製品要求・該当するパッケージ要求・合意済みの追加要求を起点に、変更する判断や状態を使う側までたどる。別の画面・端末・通信経路や配布・運用で結果が変わる場合は、その利用者や運用担当者の要求も拾う。各要求の根拠となる見出しと、同じ場面で重なる条件・それぞれの期待結果を既存の作業記録に残す。
2. **同じ条件で両方を満たせるか確かめる。** 例えばマイクを切る処理の共通化では、送話を止めたまま画面をロックし、後から相手が参加したときにその声を受け取れるかを一続きで確かめる。要求は両立しても、送話と受話を一緒に止める設計では後者が破れる。この場合は案を直し、[変更前後の回帰検証](#実装と検証)にこの組合せを含める。[双方背景と無音状態を組み合わせた受入](../requirements/製品要求.md#双方背景と無音状態を組み合わせた受入)
3. **要求同士が対立するときは要求者の判断を得る。** 同じ条件で異なる結果を求めているなら、双方の原文、衝突する具体例、選択肢ごとに誰のどの用途が変わるかを示す。その決定に依存する変更は保留し、ブランチ運用の再開条件に従う。技術的に両立できるかが不明な場合は、判断を分ける最小の検証を先に行う。
4. **レビューでは別の要求を起点に反証する。** レビュー担当は現行の要求と利用経路から、実装担当が照合対象から落とした要求も探す。着手前は、ある要求を満たすために別の要求が破れる場面を設計案に当てる。受入前は同じ条件を最終差分と検証結果に当て、各要求の期待結果を同時に観測できたか確かめる。対象外とした関連要求にはその理由を示す。矛盾、関連要求の照合漏れ、または判定根拠の不足は**受入を止める必須の指摘**とする。既存のレビュー記録に反例と判定を残す。案に問題があれば設計を直し、要求者が要求を変更した場合は該当する要求文書を更新する。同じ条件で再検証・再レビューし、すべての指摘を解消してから統合する。

### 次回リファクタリングの全体簡素化

全体整理の主題がコードの簡素化なら、全体の構成をシンプルに直し、コード全体を見渡して冗長化と余計なコードを排除することを最重要要求として扱う。直近の差分だけの整理で閉じず、App・UI両モード・拡張・Watch・package・server・自動化・テストの構成、依存、状態・規則の所有元、入口から結果までを横断する。OS・通信・codecの必要な差と共通処理を区別し、不要な層・転送・重複判断・旧経路・使われないコード・設定を根拠付きで統合または削除する。単なるファイル移動、分割、行数削減は完了条件ではなく、必要な機能・互換性・品質と責務境界を保った簡素化を求める。

実施した整理に対して敵対的レビューを3回行う。各回は最新の変更後の全体構成を見直し、前回の修正と残る根因を再検査する。構成・責務と重複、実動作・OS／方式差分と互換性、回帰・保守性と文書からの再実装を含む観点で、前提や見落としを反証する。同じチェックを流して回数だけ数えず、対象、指摘、重要度と理由、対応差分、再検証結果を記録する。重要な指摘はすべて対応し、後続課題への移記だけで本整理を完了としない。修正による新たな重要指摘も解消し、3回目の修正後にも必要に応じて再レビューと回帰試験を実施する。正当な理由で指摘を不採用とする場合は、反証・影響・判断理由を残し、根拠なく重要度を下げて未対応を消さない。

小さく動く単位の検証・commit・main／origin／preview同期は継続し、全体整理の終了まで未コミットを蓄積しない。必要な回帰と品質・遅延・背景動作・互換性の条件を維持し、未実行と失敗を成功に含めない。重要指摘または必須検証が残る間は整理未完とし、具体的な阻害条件と次の一手を残す。完了時には、整理前後の構成・所有元と同じ変更例を対比し、どの重複や同時修正・不要コードがなくなったかを示す。受入後は[全体整理のサイクル](#全体整理のサイクル)に従い、次の回で仕様を扱う。

### 仕様全体整理の次の回にコード全体を再び簡素化する

[次回のコード全体整理](#次回リファクタリングの全体簡素化)→[その次の回の仕様全体整理](文書作成規約.md#コード全体整理の次の回に仕様全体を簡素化する)→さらにその次の回のコード全体整理、という順序を維持する。この再コード整理も最重要とし、先のコード整理や仕様整理で代替・完了扱いにしない。

全体の構成を改めて見渡し、冗長化と余計なコードを排除してシンプルに直す。対象範囲、必要なOS・通信・codec差分と共通処理の区別、品質・機能・互換性の維持、小単位での検証・commit・同期、構成改善の根拠は[コード全体整理の要求](#次回リファクタリングの全体簡素化)を共通の基準とする。仕様整理で統合・修正した契約を現行実装と照合し、文書だけが簡素化され実装に残った重複・不要な層や分割・旧経路、前の整理後に再発した冗長化も対象にする。仕様整理の差分に関係するコードだけへ対象を狭めない。

この回の変更後の全体構成に対して、新たに敵対的レビューを3回行い、重要な指摘はすべて対応する。先の2つの回のレビュー回数を流用せず、各回の対象・指摘・重要度・対応差分・再検証を記録する。3回目の修正後も重要指摘と回帰を再確認し、未対応の重要指摘や必須検証が残る間は完了としない。受入後は次の回でデザイン資料・ユースケースを扱う。

## Apple・Cloudflare等の外部設定を常に手順化する

インターネット通信・通知・認証・利用権などは、まず担当者がAppとサーバーの実装を整える。リポジトリの設定や自動化で完了できる作業も担当者が済ませる。その後、利用者がAppleやCloudflareなどの管理画面で行う設定を引き継ぐ。実装不足を利用者の設定待ちとして扱わない。

外部設定に影響する実装・構成・権限・secret・配布環境の変更時は、同じ変更で設定手順を必ず更新する。新設だけでなく、値や適用先の変更、不要になった設定の撤去、更新・失効・移行も対象にする。共通の入口は[Apple・Cloudflareの設定と受入順](../development/Cloudflare試用手順.md#利用者が行うapplecloudflareの設定と受入順)、Appleの詳細は[OS権限と配布設定](../development/OS権限と配布設定.md)、Cloudflareの詳細は[試用手順](../development/Cloudflare試用手順.md)へ集約する。

手順には目的、対象機能、必要な権限と事前条件、管理画面の場所、対象ID／環境、設定名と値の形式・取得元・登録先、実施順序、確認方法・期待結果、失敗時の復旧、必要な更新期限を記す。秘密そのものは記載しない。Appへ渡す設定とWorkerのsecret、APNsとAppleログインの資格、開発／preview／本番を区別する。

外部設定手順はマイグレーションと同じく、現状から目標状態へ安全に移す手順にする。「適宜設定する」等の判断を利用者へ残さず、各工程に実施条件・具体的操作・期待結果・次へ進む条件・停止条件を記す。

| 工程 | 手順に必ず含めること |
|---|---|
| 変更前の確認・保全 | 対象アカウント・App ID・Worker・環境・現行の設定と稼働中のバージョンを特定する。既存設定を上書きする範囲と影響、保持すべきデータ・資格・設定の安全な保全先を示す。秘密を文書やログへ転記させない |
| 段階的な適用 | 前提の実装・権限・構成が揃う順で、準備→検証環境→適用→確認→必要な本番切替を分ける。新規設定・既存値の変更・変更不要を区別し、各段階の確認が成功してから進む。意図しない環境の変更を防ぐ照合を操作直前に置く |
| 切替と後始末 | 旧版との互換範囲、切替の影響と必要な停止時間を明記する。鍵・secret等は利用先の切替と動作確認を済ませてから旧値を失効させる。取り消せない変更・削除は別工程として、その必要性と実施可能な条件を明記する |
| 失敗・中断・再実行 | 成功判定と、進めず停止する条件を具体化する。途中からの再開位置、既に適用済みかの確認、二重作成・二重適用の回避を示す。戻せる範囲と正確な復旧手順を用意し、戻せない場合は代わりの回復方法と影響を明示する |
| 最終照合 | 変更後の設定・実稼働・機能の期待結果を確認し、何を適用したか・未完了事項・残る旧資源と撤去条件を記録する。手順だけで事故防止を保証したり、未実行の復旧を検証済みと扱ったりしない |

実装済み・ローカル設定済み・管理画面では未設定・外部設定を確認済み・実環境で受け入れ済みを分けて記録する。手順は現行実装と照合し、未確認の管理画面操作や設定済み状態を捏造しない。利用者へ依頼する時点では、依頼対象だけで次へ進める具体的な設定一覧と確認手順を揃え、依頼目的と必要性を示す。実サービスの配置・試験は既存の承認範囲と費用制約を維持する。

## UI・UX方針

GUIの新規実装・変更・リファクタリングでは、[Scott HurffのUI Stack](https://www.scotthurff.com/posts/why-your-user-interface-is-awkward-youre-ignoring-the-ui-stack/)を設計・検証の観点として適用する。通常表示だけでなくIdeal・Empty・Error・Partial・Loadingの5状態と、その間の遷移を対象画面ごとに確認する。適用する状態・成立条件・表示・可能な操作・復帰先を画面仕様に残し、該当しない状態は理由を示す。

具体的な表示と本プロジェクトの状態種別との対応は[デザインシステムのUIスタック](../design/デザインシステム.md#uiスタック)に従う。変更対象に関係する状態と遷移を再現して検証し、既存の回帰保護と小さな検証済みコミットを維持する。重大不確実性の先行検証とコア優先の順序を保ち、必要な状態を実装する範囲へ絞る。

### 利用者向け文言の意味と平易さを継続検査する

[平易な日本語・英語の製品要求](../requirements/製品要求.md#利用者向けの平易な日本語と英語)を適用する。文言を新規作成・変更・翻訳するたびに、対象画面と利用者の立場、操作対象、表示前の状態、操作後の結果へ照らし、元の要求・実動作・各言語の意味を照合する。AIが短縮しがちな専門語、略語、名詞の連結、主体・対象・条件や微妙な意味を省いた言い換えを見直し、Standardと一般利用者向けダイアログでは日常的な語と具体的な動作で表す。開発ログやAdvancedの技術値まで機械的に言い換えない。

専門語・短縮語と過去の誤解例、文脈別の言い換え候補を共通の文言レビュー資料へ記録し、文字列カタログ・UI直書き・設計見本の変更から要点検箇所を見つける自動検査を既存の検証入口へ組み込む。最初に既存文言を棚卸しし、Standardへ届く共通のダイアログ・エラー・通知も含める。機械検査は候補の抽出と漏れの検知に使い、合格だけで分かりやすさを保証しない。対象外の技術語には使用場所・理由を付け、全体への一律な禁止・置換や例外の無条件適用を避ける。

[変更した文言から候補を拾う方法と日英の確認例](文書作成規約.md#次の読者が同じ意味に読めるか確かめる)を使う。抽出した文言は画面・操作の文脈で読み直し、次にできる行動と結果、取消・保留・拒否等の違い、日本語／英語・VoiceOverの意味が揃うことを確認する。省略された条件、誤った対象、意味のない短縮、技術語が残る場合は反映前に修正し、修正前後の意味と必要な実画面の表示も照合する。自動検査・文脈レビューの結果と未確認を区別し、文言変更後も同じ入口で継続して検査する。

### デザイン・UI・UX変更時の敵対的レビュー

デザイン・UI・UXに影響する変更のたびに、用途・目的・背景に照らして敵対的にレビューする。設計案や見本だけの変更、文言1つの変更、画面外の処理によって操作体験が変わる場合も対象とする。[要求とユースケースの対応](../requirements/README.md#要求とユースケースの対応)から影響する利用者の立場・シーン・環境を取り出し、「この条件では、変更のために誰が何を達成できなくなるか」という反例を探す。例えば通話開始後に確認操作を加える案なら、開始直後に端末をロックする人も通話を始められるかを確かめる。

[現在のバックログと変更の方向を照合する手順](#レビューで現在のバックログと変更の方向を照合する)に従い、[画面実装とデザイン見本の差分](../backlog/画面実装とデザイン見本の差分.md)から対象画面の課題をたどる。見本・画面遷移・文言のどこで利用者の操作が途切れるか、後続課題の受入時にどの画面を作り直すかを確かめる。

反例を設計案・見本上の操作の流れ、または変更した実装の挙動と照合する。問題があれば修正し、同じ条件で再レビューする。影響する用途に未解決の問題がないことを確認し、調べた条件と判断の根拠を示して変更を完了する。

要求・既存の決定・検証結果を照合しても自分では解決できそうにない問題に気づいた時点で、主担当は要求者に直接質問して回答を求める。誰がどの場面で何に困るか、それが用途や背景からなぜ問題かを伝え、判断してほしい点を具体的に尋ねる。回答に依存する判断は保留し、回答を受けて変更に反映したうえで、該当する場面を再レビューする。

### StandardとAdvancedの設計の絶対ルール

次の2つを絶対的なルールとする。StandardとAdvancedの画面の設計・実装・点検のすべてに例外なく適用し、ほかの規則と食い違う場合はこのルールを優先する。StandardとAdvancedは目的が異なるため、別々の原則で設計し、どっちつかずの共通化をしない。

| 画面 | 絶対ルール | 意味（満たすべき結果） |
|---|---|---|
| Standard（一般向け） | すべてのケースで、機械的な仕組みではなく利用者の意図から自然に分かるように、UXを先に定義する。全体の整合をとった上で、UIをデザインする | 一般の利用者が迷わず、すぐに利用できる。不要な情報を目にしない |
| Advanced（詳細表示） | すべてのケースで、実装と対になるように表す。実装と実際の動作の状態を表示に反映する | 設計の問題や実装の問題を、画面を見てすぐに見つけられる |

#### Standardで守ること

| 手順 | 内容 |
|---|---|
| UXを先に定義する | 画面を描く前に、利用者の意図と場面をすべてのケースについて挙げ、各ケースで「利用者の意図」「見えるもの」「すること」「アプリが引き受けること」「見せないもの」を定める。UIからUXを逆算しない |
| 全体の整合をとる | ケースどうしで、同じ意図には同じ入口・同じ語・同じ結果の表示を使う。内部の手段（届け方、経路、相手の登録の有無、処理の種類）の違いで、利用者の操作や語を途中から変えない |
| UIをデザインする | 整合したUXの定義から、画面・部品・語を決める。利用者の意図に必要のない情報（経路、ID、数値、内部の状態、内部の仕組みの説明）を画面に出さない |

#### Advancedで守ること

| 手順 | 内容 |
|---|---|
| 実装と対にする | 画面の各要素に、対応する実装（型、プロパティ、enumの値、snapshot、共通操作）を1対1で定め、設計の文書に対応表として記録する。実装にないものを描かず、実装にあるものを隠さない |
| 状態に連動させる | 表示する値と状態の語は、実装の値・enumの値・実装が返す語をそのまま使い、言い換え・まとめ・丸め・推測をしない。値が変わったら表示も変わる |
| ずれを不具合として扱う | 実装の状態と画面の表示が食い違う、または実装の状態そのものが利用者の実際の状況と食い違う場合、それを設計または実装の問題として記録し直す。画面の側で取り繕って隠さない |

共通にしてよいものは、次に限る。これ以外（画面の構成、部品、語、配置、説明の量）はStandardとAdvancedで別々に定め、一方のためにデザインした部品・語・配置を他方へ流用しない。

| 共通にするもの | 理由 |
|---|---|
| データと動作を管理する箇所（同じViewModel・共通操作・保存先） | 同じ通話・同じ設定を、2つの見せ方で扱うため |
| 色のトークン、取り消せない操作の安全の規則、[利用環境の前提](../design/デザインシステム.md#利用環境の前提) | ブランドと安全は表示の目的に関係しないため |
| HIGとアクセシビリティの下限（押せる範囲、Dynamic Type、VoiceOver、色だけに頼らない） | どちらの利用者にも必要なため |
| 表示・語・配置・操作が完全に同一の部品 | 同じものを二重に持つと片方だけ直る食い違いが起きるため。一部でも違う部品は共通化せず、モードごとに持つ |

共通にする部品とモードごとの部品は、置き場所で見分けられるようにする。StandardとAdvancedの両方を持つ画面のディレクトリは、`RideIntercom/UI/Call`と同じ`Common/`・`Standard/`・`Advanced/`の3つに分け、画面ごとに別の構成にしない。共通の部品は`Common/`に置き、モードの名前を付けない。共通化した部品に後から一方だけの違いが必要になったら、部品の中でモードを見て分けず、モードごとの部品へ戻す。置き場所の詳細は[UI全体構成のファイルの置き場所](../spec/App/UI/全体構成.md#画面コードの配置)に置く。

デザインの文書での扱いは[デザインシステムのStandardとAdvanced](../design/デザインシステム.md#standardとadvancedの違い)に置く。


- UIはSwiftUIのネイティブコントロールを標準とし、必要な機能は他のネイティブ標準UIで補う。この開発で扱うUIはこれらの標準部品に限定する。
- UIは最新のApple Human Interface Guidelinesに準拠し、実装前にAccessibility、Layout、Iconsの該当箇所を確認する。
- iOSはHIG準拠を必須とし、標準SwiftUIコンポーネント、safe area、Dynamic Type、VoiceOver、ライト/ダークモード、Reduce Motionを前提に設計する。
- macOSでも同じ構造・状態管理・アクセシビリティIDを維持する。そのうえで、ウィンドウサイズの変更、キーボード操作、VoiceOverに対応する。macOSに合うクリック対象の大きさと、ウィンドウ内で重要な操作を安定して行える配置も最低条件に含める。
- すべてのアイコン単体ボタンにVoiceOverで意味が分かるaccessibility labelを付け、状態を持つ操作にはaccessibility valueも付ける。accessibilityIdentifierはUIテストで使い、VoiceOverには専用のlabel/valueを設定する。
- 状態表示は色に加えて、テキスト、SF Symbols、accessibility label/valueでも同じ意味を伝える。音量メーター、通信状態、ミュート状態、エラー状態は必ず色以外でも判別可能にする。
- 主要操作のタップ/クリック対象はiOSで44pt以上、macOSで28pt以上を下限とし、隣接コントロールには操作対象を識別しやすい余白を確保する。
- 文字サイズに追随する高さと必要な複数行表示を使う。長い診断値はDiagnosticsへ配置する。
- レイアウトはsafe areaとシステム余白に従い、主要操作にはシステム標準の適切な幅と余白を設ける。iPhone portrait/landscape、iPad regular width、macOS window resizeで各操作の表示領域と操作領域が確保されていることを確認する。
- UIアイコンはSF Symbolsを優先し、outline/fillなど用途に合うvariantを選ぶ。アプリアイコン・ロゴ・商標的表現には用途に適した独自素材を使う。
- Standardの通話は利用者の意図に必要な状態と操作に限定し、TX/RX/JIT、ID、groupHash、transport詳細などの診断情報を出さない。Advancedの通話とDiagnosticsは、それらを実装と対で表す（[StandardとAdvancedの設計の絶対ルール](#standardとadvancedの設計の絶対ルール)）。
- SettingsはForm/Sectionなどプラットフォーム標準の設定UIに寄せ、Audio I/O、Codec、Audio Checkなどを意味単位で分ける。
- 体験を最優先し、UIの使いやすさと音声品質を継続的に改善する。
- レイテンシ最小化、ノイズ低減、VAD調整など、体験に直結する要素を優先する。

- 参照: https://developer.apple.com/design/human-interface-guidelines/layout
- 参照: https://developer.apple.com/design/Human-Interface-Guidelines/sf-symbols

### 機能実装とデザイン判断の引継ぎ

機能・音声・招待・通話などを成立させる都合でUIやUXへ影響する実装を置く場合、デザイン判断が未了の部分は「仮実装・デザイン未確定」と実装箇所のコメントと現行画面仕様に明記する。機能の成立・検証済み範囲と、表示・操作体験の確定状態を分け、仮実装がそのまま確定デザインとして継承されることを防ぐ。

同じ変更の中で、対象デザイン文書の残項目に対象画面・状態・操作と実装箇所を記録する。仮実装にした理由、機能上の制約、変更できる範囲を示す。現在の挙動と画面の証拠を添え、未解決のUX、デザイナーに判断してほしい事項、受入条件を残す。バックログのデザイン区分にも概要・状態・引継ぎ先へのリンクを置き、判断後の実装・検証まで追跡する。仮実装の明記は開発上の文書・コードで行い、利用者向け画面への表示はデザイン判断に従う。

UIやUXの検討から必要になった機能・状態・保存・通知・通信などが未実装なら、バックログの機能区分へ要求・目的・完了条件とデザイン側へのリンクを記録する。デザイン残項目と機能課題を相互参照し、どちらか一方の完了だけで全体を完了扱いにしない。分類と全体優先順位は[文書作成規約](文書作成規約.md#バックログの分類と全体優先順位)に従う。

## 技術選定方針

外部ライブラリとフレームワークは、上流の修正版を速やかに採用できる形で使う。上流のソースやビルド定義を独自に書き換えず、公式の設定で構成する。公式 SDK に含まれる未使用機能は、[採用部品の監査](../../.agents/skills/security-audit/references/監査範囲.md#採用部品の危険性保守状況使用版を調べる)に従い、利用経路がなく、配布への影響もビルドから除く明示要件もなければ対応不要とする。明示要件がある機能は、公式の設定とターゲットで対象を絞り、成果物で除外を確かめる。[WebRTCのカメラ撮影を除く手順](../development/BuildWebRTC/WebRTCビルドスクリプト.md#上流の無改変とカメラの不使用)

- Swiftバージョンはプロジェクトで利用可能な最新安定版を使う。
- 現行の最低対応OSはiOS/iPadOS/macOS/watchOS 27.0とする。Xcode project、各local Swift Package、同梱binary、build・検証script、現行の仕様・操作文書で最低対応バージョンを一致させる。projectで明示的に有効な他のApple platformも同じ最低対応バージョンを使う。
- 今後は可能な限り現行と直前のメジャーOSまでの最大2世代を支援する。最低対応バージョンを上げるときはすべての対象設定・依存binary・検証入口・現行文書を同じ作業単位で更新し、下位OSだけのavailability分岐、fallback、劣化経路を整理する。OS内のAPI実装差ではなく、iOS/macOS/watchOS等のplatform差、権限、機器・hardware能力による実際の差は必要な境界として維持する。
- 現在の開発段階は現行OS・アプリ版・API・データ形式を基準とし、旧版専用の互換処理は整理する。プラットフォーム固有の必要な処理分離とは区別する。
- 将来の更新でマイグレーションが発生する前提とする。将来必要になるデータ・設定・通信契約等の移行は、変更時に対象・適用条件・失敗時の復旧を定める。将来の移行でも利用者データを保護し、対象・条件・復旧を確認した操作だけを行う。利用者データの無断削除は禁止する。

## 実装判断の優先順位

利用用途に対する重要度で作業の優先順位を決める。コアな要求の実現とコアを阻害するバグの修正を横断して比較し、利用者の明示した優先順位を適用した上で、利用用途の成立・継続に重要なものから進める。これは作業対象の重要度の順位であり、実装・検証の手順とは区別する。周辺機能や細かな改善は、コアへの影響と依存関係に照らして選ぶ。

選んだ用途の優先順位は、その受入操作に必要な準備の順番で変えない。受入条件と対象環境で現在満たしている条件を照合し、そのまま試せる場合は直ちに試す。準備を要する場合は、不足を示す仕様・端末の状態・試行結果などを確かめ、同じ条件と権限を満たす手段同士で効果と所要時間を比べる。選んだ手段で不足する最小限の準備を元の作業に含める。準備に使う機能の包括的な検証は別に優先判断する。設定の確認だけで結果が変わらないと分かったら、次の有効な手段をその場で試す。権限や機材が不足すると判明した時点で、対象・試したこと・次の手段を報告する。所有者の判断や権限が必要ならその場で尋ね、端末のロック解除は実機確認の全件をまとめて依頼する。最優先の受入条件を確認できないと判明した時点で、確認済みの事実・具体的な障害・次に取れる手段を報告する。別項目へ移る前に依頼者の確認を取る。依頼者が切替に同意するまでは、最優先の項目を維持する。回答を待つ間も、同じ受入条件に向けて実行できる作業は続ける。区切りでは、前提の解消と元の用途の合否を別々に記録する。

画面・設定・利用案内に出す機能は、利用者に「この用途で今使える」と約束している。Standard（一般向け）で使えるように見え、案内された条件で使えないと判明した時点で、苦情の有無にかかわらず既存のバックログに高優先度で登録する。主担当は登録後すぐに、実際の入口・再現条件・期待と観測の差、対応案ごとの影響を要求者に示して判断を求める。修復、一般向けの入口・既定設定・案内からの除外、提供範囲の限定など、方針に依存する変更は回答を得てから行う。判断待ちの間も高優先度を保ち、回答を同じ課題の次の行動と完了条件に反映する。明示された指示の対象と条件が一致する場合は、その指示に従う。変更後は一般利用者が見る入口・案内と実際にできる操作を照合する。未確認の場合は提供条件に必要な証跡を先に照合する。

プラットフォームごとに「どの端末の利用者に、何が配布され、どの入口から使えるか」を確かめる。Watch Appなどの同梱は、機能設定や表示を切っても別端末への提供に影響する。開発用の構成と通常配布を分け、公開判断に対してReleaseのArchive内のApp・拡張と、配布用に書き出した場合はその成果物の中身を照合する。意図しない同梱や提供条件を満たさない同梱は、一般向け表示の不一致と同じ基準で扱う。

### 高重要度の候補を時間当たりの効果で選ぶ

明示された優先指定と期限を迎えた定期作業を適用し、通常作業を選べるときに、高重要度の候補を用途横断で比べる。リファクタリングと定期作業は価値分割の対象から除く。通常の機能要求や不具合の候補は、一人の利用者ができるようになる操作、直せる不具合1つ、または結果によって修正先や採否が決まる実験に切る。音声なら、通話全体の重要性を個々の再計測の効果に加算せず、今回どの条件の受話が改善するか、どの観測で次の判断が変わるかを示す。

設計と着手順を決める前に、製品要求・パッケージ要求と、すでに合意した追加要求を照合する。各案を採ったとき、誰がどの条件で何を使え、品質や運用負担がどう変わるかをたどる。その結果に関係する既存要求を拾い、実装や担当が異なる要求も同時に満たせるか、受入条件に沿った具体例で確かめる。互いの受入結果や着手順に影響しない要求は別々に進める。既存要求と両立しない案は見直し、両立するか分からず後で広く作り直すおそれがあれば、その判断に必要な最小の検証を先に行う。未決の案は確定した要求と区別し、先回りして実装する範囲を広げない。

- 最有力候補と実行可能な対案に、利用用途から重要度の重みを置く。目安は、通話の開始・受話・継続を左右する要求や阻害が8、一般利用者に使えない機能を提供している表示や主要操作の支障が4、回避できる不便が2、軽微な改善が1。対象者・影響範囲・代替手段から重みを調整し、理由を一言添える。明示指定が決めた着手順はそのまま適用する。
- **時間当たりの期待効果 = 重要度の重み × 今回解消できる割合 × その結果を得る見込み ÷ 確認までの予測時間**（時間単位）。割合と見込みは0〜1の概算とし、各候補で何を解消できれば1かを、分割前の利用上の問題に合わせて示す。作業を細分化するたびに分母を小さくして評価を上げない。実験は「結果によって決められること」を効果とし、同じ結果でも判断が進まない再試行の効果は0とする。候補ごとに準備・実装・検証を含む所要時間の幅を置き、類似作業や試験の実測で補う。既存要求も満たすまでに必要な作り直しと再検証が候補ごとに異なる場合は、その発生条件・見込みと所要時間を見積もりに含める。並行して待てる時間は重複計上しない。
- 同じ単位で比べて高い候補を選ぶ。見込みや所要時間によって順位が逆転するなら、その条件を明記し、既存の証跡か短い試行で判断する。数値は見積もりと分かるように記録し、細かな点差で断定しない。
- 比較と選択理由は既存の着手順か作業記録に短く残し、選択が変われば着手順を更新する。再現条件・機器・判断材料を欠く場合は、今できる独立した一手と再開条件を示す。調査には時間または試行の上限を決め、同じ結果を繰り返しても判断が変わらなければ切り替える。
- 区切りには、着手から結果を確認するまでの実時間と、実際に改善したこと・決まったことを見積もりと照合する。効果が得られなかった試行も含め、残る一手を新しい証拠で再比較する。試験ログの秒数は検証工程の実測として使い、実装を含む総所要時間は別に扱う。

### 節目の目的と成果の確認

着手・再開時と小さな区切りには、ビルド番号、mainの第一親のコミット数、日本時間の各基準を、既存の作業記録と照合する。すべての定期作業で、基準に達した時点で対象回を記録し、[前件の差分と共有先を確認した時点](#作業を切り替える前の確認)を開始できる最初の区切りとする。ビルドごとの重要度・バックログ・Xcode・コードの点検、コミット数ごとの整理・Archive・フル監査、時刻で決まる資源・費用の点検に共通する。実行の終了時にもその回で生じた変更を検証・共有し、同じ確認を通してから次の回または通常作業へ移る。複数回が到来しても、開始・終了条件は各回に適用する。

頻度の判定には通常変更で進んだビルド番号・コミット数を使う。定期作業を共有すると、Gitフックがその回をコミットに記す。判定器は共有mainの第一親から、そのコミットとそこで増えたビルド番号を差し引く。担当者がカウンターを更新する必要はない。節目の番号はこの換算値で記録し、実際に検査したコミット・ビルドを作業記録に示す。フル監査は定期作業の変更も含む実コミット100件ごと、資源・費用の点検は実時刻の6時間ごとに行う。各回で点検する差分には前回からの定期作業の成果も含める。

着手前の判定で次の通常作業を選ぶ。作業中に節目を通過したときは、新しい作業の追加を止め、前件の検証・受入記録とコミット・pushを先に済ませる。コミットが止まった場合も、自分の差分とステージ状態を確認し、下記の前件の共有手順で閉じる。前件の受入が未完ならその作業を続け、共有先への反映と手元の差分の解消を確認してから定期作業を始める。

作業選択時にはfetch後に `python3 scripts/check_periodic_work.py` を実行する。共有mainの実番号、除外した増分、通常換算値と、各作業の次回の節目・残り・実番号の最短見込みを確認する。進行中に定期作業が増えると実番号の見込みは後ろへ動く。すでに到来した未完の回は次回予定と併記する。差引の根拠は `--explain` で対象コミット・作業名と節目・ビルド増分までたどる。識別子がない変更は通常変更に数える。[定期作業の受入記録](../development/history/定期作業の受入.tsv)にある各種別の導入時の節目から、共有mainのビルド番号・第一親件数・現在の日本時間までを自動で照合する。終了0なら通常作業に進める。未完・記録なしの場合は、表示された組のうち1件だけを「進行中」にして、その回の成果と判定を既存の作業記録に残す。受入行には作業・節目・状態・証拠の文書と見出しをタブで区切って記す。共有できる成果と同時に更新し、過去の行を保持する。Xcodeの「指定延期」は自動点検を終え、依頼者が画面確認の延期を指定した記録と残件の参照先がある場合に限る。

既存のpre-commitフックでもステージした記録を照合する。未完の間、製品担当は `RIDE_WORK='作業@節目' git commit` で進行中の1件に関係する差分を共有する。独立した文書担当は規定・スキル・バックログの依頼に `RIDE_WORK=文書` を使う。前件の製品差分がある状態で到来した場合に限り、閉じる前件・受入結果・次の節目を作業記録へ追記し、`RIDE_WORK=前件の共有` と `RIDE_WORK_RECORD` にその追記の見出しを指定する。各指定は、その作業を共有する場合に限る。共有mainの到達点はpush後にも読み直す。

主担当は下表の全行を使い、前の区切りから今回までに到来した節目と、前回から未完の項目を突き合わせる。既存の作業記録には対象のビルド・共有main第一親件数・日本時間を示し、該当する「節目と作業」の組ごとに、進行中・着手待ち・完了のいずれかと根拠を短く残す。整理の主題を選んだ場合も、その節目に固有の作業を待ち順に含める。記録のない組は既存の検証・配布記録も探し、根拠が見つかれば参照し、不足する条件だけを待ち順に戻す。重なる作業で証拠を共用するときは、どの回のどの条件を満たすかを対応付ける。

各回を閉じるときに3つの基準を読み直し、実施中に到来した組を加える。時刻だけ進んだ場合も同じ手順を使う。進行中と着手待ちがともに空なら通常作業を再開する。照合結果は同じ区切りの作業記録にまとめ、確認だけのコミットや周期別の番号管理を増やさない。

- **節目の間**は、該当する定期作業がすべて完了していれば、通常の優先順位で作業し、検証した単位ごとにコミット・push・preview同期まで進める。前回の完了記録を引き継ぎ、同じ節目の再承認を待つ必要はない。
- **節目に達したか通過した最初の区切り**で通常作業の追加を止める。別件から定期作業に移る主担当は、[作業を切り替える前の確認](#作業を切り替える前の確認)で前件を片付けてから点検に入る。今回該当する項目と各項目の完了条件を同じ作業記録に示す。既存の作業記録で、進行中の定期作業を全担当で1件に絞り、重なった作業は着手待ちとする。再開時は進行中の作業を引き継ぐ。新たな節目が来ても待ち順に加える。その定期作業の担当者は、選んだ1件の完了に必要な点検・是正・再検証だけを行い、結果を記録してから次の1件に着手する。必須の証拠を得られない間は、その項目を未完とし、阻害条件と解消に必要な作業を明示する。試行までを求める項目には、個別の規定に沿って実際に試した結果を残す。
- **通常作業を再開する区切り**では、今回の全項目の結果を完了条件と照合する。定期作業で変更した箇所は、普段の開発で使うビルド・テストなど該当する入口で動作を確認する。その回の変更で生じ、完了条件を妨げる不具合は修正して再検証する。今回の完了条件を満たした後も追う改善は既存のバックログへ、配布後に初めて確認できることは該当する配布の検証記録へ引き継ぐ。完了の根拠と次の通常作業を記録し、その場で[ブランチ運用](#ブランチ運用)に従って検証済みの変更を同期する。

**定期作業は一回ごとに、その目的と指定範囲の全受入条件を満たして閉じる。** 主担当は途中のpush後と担当交代時に、開始した節目の記録を開く。各条件について、対象全体をどこまで確認し、どの差分・観測が達成を示すかを照合する。1つでも根拠が欠ければ同じ回を続行し、次の作業はその不足を解消するものに限る。残件の転記や後続の節目の到来で今回を閉じたり、通常作業・別の定期作業に移ったりしない。実行可能な手段を尽くしても進めないときは、確認済みの事実・障害・次に取れる手段を依頼者に伝え、切替の合意を得るまでは同じ回を未完のまま保つ。試行を求める項目の合否は、各項目に明記された終了条件で判定する。

監査・リファクタリングを含め、定期作業中に見つけた関連課題は、発見時にすべて既存のバックログへ登録する。同じ課題があれば更新し、何が起きたか、どの要求に影響するか、何が残るかを短く記す。現在の完了条件を直接妨げる課題だけは、その条件を示して今回必要な範囲を是正する。解決したら結果を仕様・検証記録へ移す。他の課題は着手待ちに置き、期限を迎えた定期作業をすべて終えてから、既存の候補と合わせて優先順位を決める。

各節目では、前回の整理で残した問題や再発、期間中に変わった要求とその影響先、次に予定している変更を照合する。対象は直近の差分を手掛かりに選び、古い原因や、差分に現れない呼出元・別端末・文書にも影響が及ぶ場合はそこまでたどる。着手時に「この節目で何を改善し、どの例で結果を確かめるか」を決める。

| 節目 | 改善する対象 | 完了を判断する例 |
|---|---|---|
| 10ビルド | 利用状況や阻害要因の変化に合わせて、次の作業を選び直す | 前回選んだ候補と現在の有力候補を、新しい観測・期待効果・所要時間で比べ、続行または切替の理由を示せる |
| 各20ビルド（バックログとXcodeは10ビルドずらす） | 課題一覧を現在の残作業に揃え、開発環境の変更をXcodeにも反映する | 一覧と詳細から次の行動が分かり、完了分と確認待ちは移記先をたどれる。開発入口・リソースの増減を実態と照合し、影響する操作をXcodeから再現できる。2つの結果を個別に確認する |

主担当はその区切りの作業を完了する前に、既存の作業記録で「以前に困った具体例 → 実施した変更または判断 → 同じ例で確認した結果」を差分・観測と対応付ける。期待した効果が出なければ原因と対象を見直し、修正と再確認を続ける。前回の成果が今も十分なら、今回の変化を含む例でそれを確かめる。実行環境などの制約で確かめられない目的は未完とし、残った問題と再開条件を引き継ぐ。

### コードと文書の定期整理

ビルドを伴わない変更も含めて整理が追いつくよう、通常変更のコミット数が50で割って25余る節目に達した、または通過した最初の区切りで、新しい機能・修正への着手を止め、コードと文書の両方を整理する。[節目の共通判定](#節目の目的と成果の確認)を使う。過去に手元の件数で記録した節目は、対象コミットと監査範囲を共有履歴に照合し、未確認の区切りを順番に点検する。別担当が同じ節目を整理済みかは既存の作業記録で確認する。

- **コード**は、前回の整理から今回の区切りまでの変更と影響先を確認し、[責務分離スキル](../../.agents/skills/architecture-refinement/SKILL.md#最低二巡の改善と段階的コミット)で最低二巡点検する。責務の混在や重複など、効果の高い箇所を実際に直し、既存の動作を回帰検証する。前回からの期間には定期作業で共有した変更も含める。
- **文書**は、同じ範囲の変更を要求・仕様・操作手順・課題・検証記録と照合する。[文書の分類](文書作成規約.md#分類の判断と完了時の移動)に沿って、古い記述・重複・参照切れを直す。実装済みの挙動は仕様に、確認待ちは未確認事項に移し、バックログには残作業を明示する。

必要な修正と検証を小さくコミットし、既存の作業記録に節目・対象範囲・結果を残してから次の作業へ戻る。再開前に主担当が、対象期間から整理箇所を選んだ理由、同じ要求変更で判断・修正が及ぶ範囲の前後差、文書から導いた期待と実装・証跡の一致を確認する。途中のコミットは局所成果として残し、節目全体はコードと文書の両方で根拠が揃った時に閉じる。変更が不要な範囲は点検した対象と根拠を記録する。ビルドの節目と重なれば、共通する整理は両方の範囲を満たす1回にまとめ、各節目に固有の点検も行う。

### 6時間ごとのサーバー資源と費用の点検

日本時間の毎日0時・6時・12時・18時に達した、または通過した最初の作業の区切りで点検する。ビルドやコミットの有無を問わない。着手・再開時も既存の作業記録で直近の対象時刻を照合する。別担当が同じ時刻の点検を済ませていればその結果を使う。休止中に複数の時刻をまたいだ場合は、前回の点検以降を一度に調べ、観測できた期間を明記する。

- **生成と残存。** [Cloudflareの環境構成](../development/Cloudflare試用手順.md)に沿って本番とPreviewを識別する。前回からのコード・配置設定の変更で、再試行や再接続のたびに同じ資源を作らないか、終了・失敗・期限切れで回収できるかを追う。実際の配置・利用記録と照合し、用途を終えたPreview、通話終了後も残るSFUセッションや動き続けるDurable Objectのalarmなどを調べる。
- **利用量と費用。** 利用できる読み取り専用の利用統計・請求情報から、対象期間のWorkerリクエスト・CPU、Durable Objectsの稼働時間、SFU／TURNの転送量などを前の同じ長さの期間と比較する。実請求は提供元の集計期間・更新日時に合わせ、金額の増加が実利用や検証で説明できるか確認する。請求の反映待ちや権限不足では、取得できた利用量と[費用試算](../development/Cloudflare費用試算.md)からの推計、未確認の値を区別する。
- 対象の試験環境を新しく作って試した記録を照合する。記録がない場合や前提が変わった場合は、[再作成の確認](../development/Cloudflare試用手順.md#固定previewを作り直せる条件)の担当と実施時期を検証待ちに残す。
- **区切りの記録。** 対象時刻・環境・観測期間・根拠・前回との差を既存の作業記録に短く残す。不要な生成・残存や想定外の増加があれば、影響と次の対応を既存のバックログで追う。取得できなかった項目は再確認条件を残す。実資源の削除・停止は用途と依存先を確認し、既存の変更手順に従う。

### 100コミットごとのフルセキュリティ監査

fetchした共有mainの第一親の通算コミット数を `git rev-list --first-parent --count origin/main` で確認する。100の倍数に達したか通過した最初の区切りでは、毎回[セキュリティ監査スキル](../../.agents/skills/security-audit/SKILL.md)の[全領域監査](../../.agents/skills/security-audit/references/監査範囲.md#定期実行でプロジェクト全体を調べる)（`project` 判定）を受ける。他の節目と重なる場合も実施し、同じ区切りの外部送信・配布より先に判定を得る。区切りの作業記録に節目と対象のmainコミットを対応付け、スキルが認める定型の監査結果と残る対応を記録する。次の100コミットに達した時点で前の監査が未完なら、[進行中の全体監査](../../.agents/skills/security-audit/references/監査範囲.md#監査中に次の節目を迎えたとき)の判定を先に終え、次の節目はその証拠を引き継いで順に扱う。担当交代時も既存の記録から再開する。

### 署名付きArchiveの定期作成

[節目の共通判定](#節目の目的と成果の確認)で通常変更のコミット数を確認する。40で割って30余る節目に達したか通過した最初の小さな作業の区切りで、その時点の検証済みmainから署名付きRelease Archiveを作る。毎回、Xcode OrganizerのArchives一覧に載せるところまで試す。iPhone用を優先する。コードと文書の整理やビルド番号の節目が重なれば、それぞれの作業も行う。

[標準のArchive手順](../development/開発環境.md#xcode標準のバージョン管理とarchive)に従い、通常の署名設定で `RideIntercom` schemeをArchiveする。定期Archiveは必ずXcodeの標準保存先 `~/Library/Developer/Xcode/Archives/日付/` に直接作成する。CLIではXcode本体の開発環境を使い、`-archivePath` を指定しない。別の場所で作成して後から取り込む手順は、この定期作業では使わない。既存の作業記録に、節目・対象commit・プラットフォーム・Version／Build・署名検証の結果・最終保存先を残す。別担当が同じ節目を実施済みなら、直接作成した根拠も照合してその記録を使う。

対象のApp・プラットフォーム・Version／BuildがOrganizerのArchives一覧に現れたことを確認できたら、根拠とともに記録する。署名と登録まで確認できた場合は「登録済み・一覧表示は未確認」として引き継ぐ。Archiveの作成・署名検証・Organizerへの登録は毎回必須とする。どれかが失敗したらその回を未完に保ち、原因を直し、不足する工程を再実行する。

定期Archiveは、対象成果物の作成・署名検証・Organizerへの登録を確認して完了とする。後日の画面確認は検証待ちに残す。担当者は登録した同じArchiveについて、送信前監査を通し、内部TestFlightへの送信をその区切りで1回試す。成功または失敗を記録すれば試行は終了する。権限・送信前監査などの条件で試せない場合や依頼者が送信を引き受けた場合は、「未試行」とその理由を配布記録に残す。どの場合もArchiveの受入行を閉じ、同じ回での再試行、Appleの処理結果や依頼者の切替判断を待たずに次の定期作業へ進む。TestFlightの接続先は内部・外部テストともに本番用のWorkerである。監査は実際の配布対象と操作に合わせ、内部テストの受入に一般公開や課金開始の条件を加えない。開発署名での試用は固定Previewを使う。

内部試用の送信時は対象のApp・チーム・Version／Buildを確認し、Xcodeの「TestFlight Internal Only」で同じArchiveを送る。配布署名はXcodeの配布処理で検証する。一般公開用のIPAを別途書き出す必要はない。内部試用でも本番Workerに接続し、通知はproduction APNsを使う。通知の到達は配布後の試験で確認する。依存部品は試用で使う経路と同梱物を対象とし、同じバイナリの検証結果は引き継ぐ。新しい告知や利用条件の変化があれば影響する部分を調べる。[配布成果物の確認手順](../development/OS権限と配布設定.md#生成物での確認)・[Appleの内部テスト配布手順](https://developer.apple.com/tutorials/develop-in-swift/test-your-beta-app)

#### Xcode開発環境の点検

定期点検では、共有scheme・プロジェクト設定・実ファイルの構造検査、同じ入口からのCLI・自動テスト・E2E、対象変更に有効な既存証跡を先に使う。Xcodeの表示やGUI操作でしか確かめられない項目は、対象・不足する証拠・再開条件を未確認事項にまとめ、点検中に実行できる他の検証を進める。利用者のPC画面を直接操作する場合、その許可を求める場合、利用者自身に操作を頼む場合には条件がある。画面操作を明示的に依頼されたときか、確認できないことが現在の目的を阻み、代替手段をすべて試したときに必要な範囲だけ行う。画面での再現性は引き続き受入条件とし、自動検証で確認できた範囲と分けて記録する。

点検結果には「構造・自動検査」「Xcode画面からの実行」「画面でのリソース表示」の各結果と根拠を示す。前回から入口・参照・実行条件が変わった部分には、その変更後の証拠が必要になる。画面でしか確かめられない条件が残る場合は点検の未確認範囲を明記する。依頼者が画面確認の繰り延べを指定した場合は、その範囲と再開条件を検証待ちに残して次へ進み、次の20ビルドでも残件と新しい変更を照合する。

- **実行できること。** 通常の作業フォルダのプロジェクトを開き、[開発環境の要求](#開発環境の要求)と現在のCLI・自動化の入口を照合する。編集・Build・Run・Test・Archiveに加え、技術検証やE2EもXcodeのUIから同じ設定・fixture・前提条件で実行でき、同じ結果を判定できることを確かめる。各入口の実行記録を照合し、新設・変更・影響不明の経路や証跡が足りない経路はXcodeから実行して結果を確認する。
- **リソースが見えて使えること。** [ファイル表示とビルド対象](../development/開発環境.md#ファイル表示とビルド対象)に沿ってProject navigatorと実ファイルを照合し、新規・移動分を含むソース、パッケージ、テストデータ、スクリプト、文書が適切な場所から開けることを確認する。[開発設定の構造検査](../development/開発環境.md#継続検証)も実行し、参照漏れ・自己参照・閲覧用ファイルの誤ったターゲット所属を確認する。

- **参照の増加と残存を点検する。** 前回の点検以降に追加・移動・削除したリソースの差分と、現在のProject navigator・各ターゲットのBuild Phasesを照合する。同期フォルダと手動追加で同じ実体を二重に参照している箇所、移動・削除前のパス、生成物や一時ファイルへの参照、使われなくなったリソースのコピー設定を確認する。編集・ビルド・テスト・配布での用途を確かめ、不要と確認できた参照や所属だけを外す。実ファイルと必要な共有参照・ターゲット所属を保ち、整理後はナビゲータの表示と影響するビルド・テストで確認する。

見つかった不整合は参照・所属・実行入口を修正して再確認する。既存の作業記録に、Xcodeでの表示・実行と構造検査それぞれの結果を残す。環境や権限を待つ確認は、対象と再開条件を未確認事項へ記録する。

### 設計判断の補足

- 設計判断では「短期の安定運用」と「中長期の拡張性」を両立させる。
- まず単純で検証可能な実装を成立させ、その後に抽象境界を段階的に拡張する。
- 抽象化の導入や変更は、テストで保護された経路を維持できることを必須条件とする。
- 責務・差分・テスト容易性に寄与する最小の抽象化を導入する。
- 常に実装のシンプルさとコード量の少なさ、可読性の高さと保守のしやすさを優先する。
- コード量を増やす変更は、機能維持・重複削減・テスト容易性のいずれかに直接寄与する場合のみ許可する。
- 既存コードの小さな修正で成立する場合は、変更対象を既存ファイル・型・protocol・adapterの必要箇所に限定する。
- 抽象化を追加する前に、既存の抽象・Port・Factory・Test Supportの適用可能性を確認する。
- 新規経路を追加した場合は、同じ変更内で不要になった旧経路、重複実装、一時的な補助コードを削除する。
- 同じ処理は積極的に共通化し、重複する処理は共通の経路へ集約する。
- 拡張点・設定・helper・fallback分岐は、現在の具体的な要求と利用経路を根拠に採用する。
- 本番コードの抽象化は製品の責務を基準にし、必要なテスト専用実装はTest Supportへ閉じ込める。
- 実装完了時は、追加行数・追加型数・追加ファイル数が目的に対して最小かを確認し、過剰な構造を削る。

<a id="一時物を残さない開発"></a>

### AIの署名付きarchiveをOrganizerから扱えるようにする

通常のコマンドで作成した署名付きArchiveをXcodeのOrganizerから選び、標準の検証・配布操作を続けられる状態を保つ。

既存の通常コマンド・scheme・署名設定・保存先を確認し、共通のarchive入口を通じてOrganizerが扱えるApp archiveを生成・保存する。署名とbundle情報・dSYM・Version／Build・生成元を保持し、署名後のbundle改変や重複archiveの作り直しで代替しない。新規Archiveは定期・臨時・検証用を通じてXcodeの標準保存先へ直接生成する。既存成果物の移送・復旧で取り込んだ場合はその経緯を記し、新規作成と区別する。既存のarchiveを上書き・削除しない。Organizerを起動するだけ、Finderでarchiveを開くだけ、署名なしbuildの成功だけを受入としない。

[Appleのarchive表示条件](https://developer.apple.com/documentation/technotes/tn3109-resolving-common-archiving-issues)と現行Xcodeの挙動を確認し、実機向けiOSとMacの対象Appについて、署名検証・App archive情報・Organizerの一覧と選択時の情報を照合する。archive生成、Organizerへの認識、export／validate、アップロードの成功を区別し、登録だけの要求で配布送信まで自動実行しない。署名資格不足やクラウド環境でOrganizerを開けない場合は不足と移送・ローカル受入の手順を残し、UIを確認済みとしない。利用者が同じ入口から再現できるコマンドとXcode側の確認手順を整える。

### 異常終了を継続確認しPCの利用阻害を抑える

開発用PCの通常利用を妨げる異常終了は、影響の大きい開発環境・品質の課題として扱う。製品、OS、Simulator、検証に使うツールを含め、実際のプロセス名・実行環境・発生条件をログと照合して原因を絞る。

作業開始前・実行中・終了後に、新たな異常終了・連続再起動・関連する実行資源の増加を軽量に継続確認できる仕組みを既存の実行入口へ組み込む。対象のprocess・時刻・実行条件・終了理由／crash reportと、その直前の起動・build・test・終了処理を対応付け、既存の記録と今回の発生を区別する。意図した正常終了・試験上の終了と予期しない異常終了も区別する。観測できない場合は正常とせず、確認不能の範囲を残す。記録は[ログ記録規約](ログ記録規約.md)に従い、秘密や不要な個人情報を集めない。

検出だけで終わらず、再現する最小経路で原因を切り分け、起動・終了・資源回収、負荷や並列度、再試行条件、権限・環境条件等の根因に対策する。異常終了や再起動の連鎖を検出したら、原因操作を無制限に再試行せず、所有する作業の再実行を抑止して証跡・再開条件を残す。常時監視自体の負荷やログの無制限増加を防ぎ、PCの応答性・通常操作とテスト品質を維持する。クラッシュ記録の削除・ダイアログ抑制だけを解決にしない。OS保護機能の無効化や、他作業・所有不明のprocessの一括停止で代替しない。

対策後は同じ起動・操作・終了と反復条件で、新規異常終了・再起動連鎖・資源残留が抑えられ、PCの通常利用を妨げないことを確認する。対象とそのバージョン・条件・観測時間・再現回数・対策前後の結果と残る制約を記録し、有限時間の成功で全環境の異常終了ゼロを保証しない。作業途中で新規に発生したものも同じ課題へ戻し、実行入口の継続確認を維持する。

### 作業完了時の整理と回収

作業の完了には後片付けを含める。成功・失敗・中断・案の不採用のいずれでも、その作業で不要になったものを回収し、担当交代や次の課題へ移る前に回収を閉じる。必要な検証証跡と再利用する資源は保ち、失敗や残課題の記録は保持する。 現在の参照先・明示した再利用目的がない一時物は、用途終了を確認して削除する。

| 対象 | 作成・維持と片付けの規則 |
|---|---|
| 配置根拠のない増設禁止 | 対象を問わず、必要性・責務・命名・配置の根拠を説明できないディレクトリやファイルの作成は禁止する。Xcode・言語・frameworkの標準と、既存のドメイン・依存境界・リポジトリの配置規則を先に確認する。一時的な都合や抽象化そのものを理由に汎用の格納場所・層・設定を増やさず、既存構造で扱う。既存の不適切な配置も対象範囲内で統合・移動・削除し、参照・target所属・文書・検証を同時に更新する。判断理由は既存規則で説明し、非自明な例外だけを既存の適切な仕様・コメントへ残す。説明は既存の適切な仕様・コメントへ集約する |
| 設定の増設禁止 | 設定管理や一時的な都合を理由に、独自の設定ディレクトリ・設定ファイル・Build Configurationの増設は禁止する。Xcode標準の既存Build Settings・scheme・Test Planを使い、標準の形式と配置に従う。役割・配置規則のない`Configuration`等の格納場所や、採番用target・別カウンタの追加は禁止する。不要になった既存設定は参照と生成物まで同じ作業で整理する |
| ビルド構成 | Xcode標準の構成とOSごとの出力を基準に、目的上必要な組合せだけを維持する。構成は目的に必要な最小の組合せへ揃え、既存scheme・Test Plan・テスト起動引数で表せる条件はそこへ置く。配布と検証の資格・保存先の分離は維持する |
| 一時コード・設定 | 調査用コード、fixtureの仮配線、フラグ、xcconfig、scheme、Test Plan、スクリプトは用途が終わった時点で削除する。恒久的な検証として採用するものだけを必要最小限で残し、不要な構成を消す際はproject・スクリプト・テスト・現行手順の参照も同時に除く |
| 生成物・一時ファイル | 不要になった構成のbuild生成物、診断用xctestrun、profile、コピー、重複ログ、作業所有の一時ファイルを確認して削除する。DerivedDataは標準の場所で再利用し、不要な生成物の作成元も同時に整理する。通常使用中のbuild cacheは再利用する |
| 実行資源・作業領域 | 自分の検証用process・session・lockを終了時に回収し、Simulatorとworktreeは上記の再利用・統合規則に従って整理する。実行中・所有不明・他作業の資源や未統合差分は、無断で停止・削除することは禁止する |
| 証跡と保留 | 判断と再現に必要なsource差分・条件・結果だけを既存の検証記録へ残す。依存する実行が続いている等の理由で片付けを保留する場合は、対象・残す理由・担当・削除する時点を既存の残課題または引継ぎへ記録する。保留には再開・削除の時点を定める |
| 完了確認 | commit・引渡し前に差分と未追跡ファイル、設定の参照、所有生成物・稼働資源を確認する。不要物の除去と影響する構成・検証入口の確認までを同じ作業単位で済ませる。対象と参照の状態を確認して片付け完了を記録する |
