# 通知宛先・呼出し・暗号化したグループ招待の送受信 API

## 範囲と認可

通常のAPNs表示通知から、利用者のタップをAppの共通通話操作へ渡すためのserver基盤。[WorkerのApple認証](Worker.md#apple認証と端末資格)で発行した有効な`ri1`端末Bearerを使う。[背景用のグループ招待受付](#背景用の一件分のグループ招待を受け付ける)は端末証明と署名した一件を照合する。試用の静的資格、公開IDの知識、groupの共有鍵、招待receiptは送信許可にならない。通知許可の拒否・通知設定の不足・通知の送信失敗を、既存の認証・Local通話・購入・復元の失敗へ変換しない。

受信者は送信者の公開`userID`を指定して、**呼出し通知専用**のcapabilityを発行する。署名には既存の`DEVICE_IDENTITY_SIGNING_KEY`を使うが、`typ=rideintercom-notification+jwt`、`aud=rideintercom-call-notification`、HTTPS originのissuer、送信者のsub、受信者のrecipient、ランダムUUIDのjtiを照合する。端末証明やgroup参加権には使えない。Appはcapabilityを不透明な文字列として保持し、serverから確認した本人IDと対応させる。

serverには受信者ごとの**有効なgrantIDのSHA-256集合**だけを保存する。取消済みtombstoneを積み上げず、取消時に集合から削除する。月ごとの再発行を要求する期限は設けない。再発行は新しいgrantIDなので取消済みcapabilityは復活しない。アカウント削除、公開IDの変更、署名鍵の変更でも旧capabilityは使えなくなる。宛先の登録資格は期限を持ち、再ログイン時に宛先を再登録する。通常のサインアウトはその端末の宛先と資格を失効させ、他端末と未取消のアカウント単位の通知同意は維持する。

**直接招待関係の成立・相手とのcapability交換・ユーザー削除時の取消はApp側の接続点**。serverは連絡先一覧を持たず、直接関係を推測しない。Appは直接招待した相手にだけ発行・交換し、groupで会っただけの相手には発行せず、送信・タップ時も保存ユーザーとの対応を確認する。このserver工程だけで、group外の通知を利用可能としていない。

## HTTP 契約

背景用のグループ招待受付を除くAPIは`Authorization: Bearer <ri1>`を必要とする。JSON応答に`Cache-Control: no-store`を付ける。以下のpathは`/api/notifications`からの相対表記。余分なJSON fieldを拒否し、共通bodyサイズ・読取時間制限も適用する。公開IDは64桁小文字hex。UUIDは大文字・小文字を受け付け、同じIDとして小文字へ正規化する。時刻はUnix epochの**ミリ秒**。

| 操作 | 要求 | 成功応答・認可 |
|---|---|---|
| PUT `/device` | `{token, environment, topic}` | `200 {registered:true}`。現在の資格のdeviceIDに1件。tokenはAPNsのバイト列をhexへ変換した2〜4096文字の偶数長。32byte固定にしない。environmentは`sandbox`または`production`でserver設定に一致、topicも設定に完全一致 |
| DELETE `/device` | bodyなし | `200 {}`。現在の資格に対応する宛先のみ解除。通知停止・設定不足でも可能 |
| POST `/grants` | `{senderUserID}` | `200 {grantID, capability}`。受信者本人だけ発行、本人宛てのgrantは拒否。senderUserIDへ送信者を固定。capabilityの最大受入長4096文字 |
| DELETE `/grants/{grantID}` | bodyなし | `200 {}`。自分の有効集合からのみ削除。存在しないIDも同じ応答。他人の許可を変更しない |
| DELETE `/grants` | bodyなし | `200 {}`。自分が発行した全許可を取消。端末の消去時や発行応答を失ったときの回復手段。相手一覧やcapability一覧は返さない |
| POST `/calls` | `{capability, requestID}` | `200 {requestID, expiresAt, status}`。capabilityのsenderと現在の本人公開IDが一致し、受信者の有効集合にgrantがある場合のみ受付。固定通知のみ。本文・名前・group・任意URLの指定は不可 |
| GET `/calls/{recipientUserID}/{requestID}` | bodyなし | `200 {requestID, expiresAt, status, senderUserID}`。受信者本人だけ取得。タップ時に期限・取消・有効grant・元送信者の資格世代を再確認する |
| DELETE `/calls/{recipientUserID}/{requestID}` | bodyなし | `200 {}`。元送信者の公開IDだけ取消。同じIDの取消再送も可。受信者や第三者には許可しない |

この表のGETとDELETEは通知機能の停止中でも可能。グループ招待については[招待の停止条件](#登録済みの相手への暗号化したグループ招待の送受信)に従う。認証不正は401、入力不正400、送信許可不正403、他人の取得・取消や未知の呼出し404、取得時の期限切れ・取消・grant失効・送信者の資格失効は410。発行の有効集合上限または処理中の本人失効は409 / `grant_limit_or_inactive`、頻度・保持上限は429。通知作成・登録に必要な設定不足や内部の通知処理の失敗は503 / `notifications_unavailable`。外部providerの本文や秘密を返さない。

`status`は`processing`、`accepted`、`no_destinations`、`retry_later`、`rejected`、`cancelled`のいずれか。`accepted`は少なくとも1端末について**APNsが200を返した**という意味で、端末表示・利用者の応答・通話接続成功ではない。`processing`は同時再送または処理中断後にも残り得る。同じrequestIDの再送は記録済み結果を返し、転送を追加しない。再試行は利用者による別requestIDの新規呼出しとし、自動再送queueは設けない。

## 費用・悪用を抑える境界

| 対象 | 上限・期限 | 回収・失敗時 |
|---|---|---|
| APNs宛先 | 有効なnative登録最大8端末、各deviceIDに1件 | credentialの30日期限内。再認証・sign-outで旧世代を外し、account削除で全件削除 |
| 宛先登録とgrant発行 | 合算60回/UTC分/account | 429。取消操作にはこの制限を適用しない |
| 有効grant | 最大256/account | 409。個別取消または全取消で枠を回復。取消済みhashを保持しない |
| 送信要求 | 60回/UTC分/sender account | 通常の重複要求も枠を消費する。背景用の要求は同じ宛先と送信IDを毎分一枠にまとめる。上限を超える新しい要求は429 |
| 新規呼出し | 20回/UTC分/recipient account | 重複は新規枠を消費しない。複数送信者による集中も同じ枠で制限 |
| 呼出し記録 | 最大512/recipient account、作成から24時間保持 | 重複抑止用。期限・取消後も保持期限まで再送しない。alarm・次回開始で削除 |
| 呼出しの応答期限 | 作成から120秒 | APNs expirationとGET検証へ同じ期限。24時間の通話利用権とは無関係 |
| 転送 | 1要求につき最大8宛先、各fetch timeout 8秒 | 固定Apple hostへ逐次送信。外部からURLを指定しない |
| 公開ID索引・token所有索引 | 登録資格の期限まで、最大30日 | 通常は置換・sign-out・account削除で該当索引を除去。障害や並行処理の残りはalarmで回収 |

同一account・公開IDのrouting索引は既存と新登録の長い方の資格期限を保持し、古い端末の再登録で他の有効端末の経路を短縮しない。token所有索引にはこの延長規則を適用せず、最後の登録世代を優先する。

索引は公開IDまたは`environment|topic|token`のSHA-256ごとに別のSQLite DOを使う。token索引は現在の所有account・device・ランダムregistrationIDを保持し、同じtokenが別アカウントへ登録された後に旧アカウント向け転送を続けない。grant集合、宛先数、短期呼出し記録は上限を持ち、索引は期限を持つ。これらの制限は通知の費用・濫用を抑えるもので、購入や通話権を表す台帳ではない。

転送直前にsender資格、recipientの公開ID・grant・呼出し・宛先世代、token索引の所有を再確認する。通常の呼出しとグループ招待は、宛先の所有確認とAPNs送信後の処理を共用する。APNsから410が返った場合は、送信に使ったregistrationIDと一致する宛先とtoken索引を削除する。応答が遅れたときも再登録後の宛先と索引は有効なままとする。索引の削除に失敗した場合は有効期限で回収する。取消・削除・sign-out中の残り端末への送信は止める。すでにAPNsへ渡った1要求は取り消せないため、payloadに個人名を載せず、タップ時GETで再検証する。索引掃除の失敗を既存認証や削除の停止条件にしない。残った索引だけでは旧UserAccountの資格・grantを通過できないが、物理的な索引消去完了と即時失効は区別する。

## 保存する情報と転送

UserAccountへの追加は以下に限る。まずAPNs token・environment・topic・端末資格hash・registrationID・期限、有効grantID hashを持つ。短期呼出しのID・sender公開IDと内部資格世代・期限・結果、固定少数のレートカウンタだけ追加する。索引には内部locatorと公開ID・端末/登録世代・期限を保持する。表示名、メール、連絡先一覧、group情報、購入状態、capability JWT、端末Bearerの秘密は保存・ログ出力しない。APNs tokenもログへ出さない。短期呼出しの送信者は取得時の本人照合に必要な情報であり、恒久的な友達一覧へ昇格させない。

APNsの固定payloadは次の形。Appは`CALL_REQUEST_TITLE`と`CALL_REQUEST_BODY`の英語と日本語の表示文字列を用意する。自由文や深いlinkは受け取らない。

```json
{"aps":{"alert":{"title-loc-key":"CALL_REQUEST_TITLE","loc-key":"CALL_REQUEST_BODY"},"sound":"default","category":"RIDEINTERCOM_CALL_REQUEST"},"version":1,"requestID":"<UUID>","recipientID":"<public userID>"}
```

`aps.category`は固定の`RIDEINTERCOM_CALL_REQUEST`だけを付ける。Appが同じcategoryへ応答actionを登録するための識別子であり、要求からcategory・action・通知本文を指定できない。category自体は送信許可や通話開始を意味しない。iPhone宛て通知のWatch転送と背景actionの応答先は[Appleのaction規則](https://developer.apple.com/documentation/watchos-apps/adding-actions-to-notifications-on-watchos)に従う。Appは同じcategoryへ「接続」「無視」を登録し、「接続」と本体のタップだけを共通判定へ渡す（[App通知仕様](../App/通知仕様.md)）。このserver変更だけで応答機能を完成扱いにしない。

`apns-push-type=alert`、priority 10、requestIDを`apns-id`と`apns-collapse-id`へ設定する。120秒期限を秒に変換して`apns-expiration`へ設定する。HTTP 200はaccepted、410は該当宛先失効、429・5xx・通信失敗はretry_later、それ以外はrejected。APNs応答本文をAppへ転送しない。ES256 provider JWTは同じWorker isolateで発行から50分未満の間、再利用する。isolate再作成・複数isolate間の接続共有条件は実環境で通知を送受信する試験で確認する。

発行から50分に達した後の最初の送信で、Workerは同じ署名設定から新しいprovider JWTを生成する。署名に失敗した結果は保持せず、次の送信で生成を試す。ローカル試験では、同じWorkerの時刻を進め、49分台での再利用、50分台での更新、元のJWTの発行から1時間を過ぎた後も新しいJWTが使えることを確認した。[Appleのトークン認証](https://developer.apple.com/documentation/usernotifications/establishing-a-token-based-connection-to-apns)

通知先の登録や新しい通知要求を受け付ける前に、APNsの署名鍵と通知許可証の署名鍵・検証鍵をES256用として読み込む。いずれかの鍵が未設定か読み込めない場合はHTTP 503と `notifications_unavailable` を返す。この場合、新しい通知先・呼出し・招待は保存せず、APNsへ要求しない。

通知許可証の署名鍵と検証鍵には `DEVICE_IDENTITY_SIGNING_KEY` を使う。読み込んだ鍵の組は、同じ設定を使うWorker isolate内で再利用する。読み込みに失敗した結果は保持しない。APNsに渡すprovider JWTは配信候補があるときに取得する。

## 設定と未受入の範囲

Sandboxでは、Workerが自動トレースなしと確認できないときに通知先の新規登録と送信を止める。応答はHTTP 503の `notifications_unavailable` とする。Cloudflareの外向き `fetch` はURLのパスを記録し、APNsはそのパスに端末トークンを要求する。クエリ文字列の除去で端末トークンは消えない。登録済みの通知先の解除と既存の取消は引き続き行える。Sandboxの実配信は、自動トレースにトークンを残さない経路を確かめてから試す。[Cloudflareの記録項目](https://developers.cloudflare.com/observability/traces/spans-and-attributes/)・[Appleの送信要求](https://developer.apple.com/documentation/UserNotifications/sending-notification-requests-to-apns)

公開設定は`APNS_TOPIC`（Appの`com.yowamushi-inc.RideIntercom.RideIntercom`を両環境へ設定済み）、`APNS_ENVIRONMENT`（Productionはproduction、Previewはsandbox）、`APNS_KEY_ID`、Sign in with Appleと共通の`APPLE_TEAM_ID`。secretは`APNS_PRIVATE_KEY`（PKCS8 P-256）と既存`DEVICE_IDENTITY_SIGNING_KEY`。`NOTIFICATION_INDEX` bindingとSQLite migration v3を使用する。通知設定を揃えても、既存SFUのSERVICE_ENABLEDやApple認証の設定を暗黙に変更しない。

Workerのnative fetchを実環境での送受信候補とする。Cloudflareの[workerd側の一次報告](https://github.com/cloudflare/workerd/issues/4841)では本番proxyがHTTP/2へ接続する一方、ローカルworkerdの直接接続とは挙動が異なる。`node:http2`のstubだけを理由にnative fetchが不能とは判断しない。本工程の試験はMiniflareのoutbound adapterが外部接続前に応答を代替し、実APNsへ送っていない。**配置したWorkerからのHTTP/2・provider JWT/接続再利用・APNs受入、署名entitlement/provisioning、実端末のtoken登録・通知許可・表示・応答は未確認**。iOSとmacOSのApp lifecycleへの接続、背景/終了/ロック状態、拒否・遅延・重複・取消後タップも別に受け入れる。PushKit、PTT、silent push、自動通話開始の実装ではない。

一次資料: [APNs登録](https://developer.apple.com/documentation/usernotifications/registering-your-app-with-apns)、[送信要求](https://developer.apple.com/documentation/usernotifications/sending-notification-requests-to-apns)、[応答処理](https://developer.apple.com/documentation/usernotifications/handling-notification-responses-from-apns)、[provider token](https://developer.apple.com/documentation/usernotifications/establishing-a-token-based-connection-to-apns)、[payload](https://developer.apple.com/documentation/usernotifications/generating-a-remote-notification)、[通知応答](https://developer.apple.com/documentation/usernotifications/handling-notifications-and-notification-related-actions)。

## 登録済みの相手への暗号化したグループ招待の送受信

通常の呼出しとは別のaud=rideintercom-group-invitationの許可を発行する。grantIDの有効集合と端末資格の失効確認を共用するが、呼出し専用capabilityと相互流用できない。暗号文の内容はAppが[既知の相手の端末鍵と署名](../App/通信仕様.md#登録済みの相手へのグループ配送の暗号形式)で検証し、serverはgroup名・ID・鍵を復号・保持しない。受信箱に保持するのは外側の転送メタデータと不透明な暗号文だけである。

通知が無効か、通知用の設定が欠けている場合は、グループ招待の配信を止める。鍵を読み込めない場合と、Sandboxで自動トレースなしと確認できない場合も、同じ[停止条件](#設定と未受入の範囲)を使う。新規送信、受信箱からの暗号文の取得、追加端末への転送の受付と取得、未受領の招待の受領確定にはHTTP 503と `notifications_unavailable` を返す。

有効な端末Bearerがあれば、本人による状況確認、確定済みの結果の再確認、送信者の取消、受取側の明示的な破棄はできる。[背景での取消](#背景用の一件分のグループ招待を取り消す)には端末証明の照合が必要。設定を戻すと、期限内の未受領分を同じ送信IDで再開できる。取得と受領確定によってAPNs通知は増えない。[停止と再開の検証](../../validation/history/Cloudflare検証.md#通知の停止と鍵の不備で保存済み招待の配信を保留する)

| 操作 | 要求・応答 |
|---|---|
| POST `/group-invitations/grants` | `{senderUserID}`。本人宛て以外の用途別capabilityを発行し、既存のgrant削除APIで取消できる |
| POST `/group-invitations` | `{capability, requestID, noticeID?, expiresAt, recipientKey, envelope, sourceRequestID?}`。expiresAtはUnix msで7日を基準とし、端末の時刻差を最大5分だけ許容する。期限切れは拒否する。recipientKeyは宛先公開鍵の87文字base64url、envelopeは暗号化EnvelopeのJSONをbase64化した最大21848文字。noticeID省略時はrequestID。`{requestID,expiresAt,status}`を返す |
| POST `/group-invitations/background` | [背景用の一件分の署名付き要求](#背景用の一件分のグループ招待を受け付ける)。通常の送信と同じ受信箱・結果・上限を使う |
| POST `/group-invitations/background-cancellation` | [送信者による一件の背景取消](#背景用の一件分のグループ招待を取り消す)。通常の取消と同じ受信箱と取消記録を使う |
| GET `/group-invitations?recipientKey=...` | 受取本人だけ、該当の公開鍵向けの未受領1件を取得できる。返す形式は`{delivery:{requestID,senderUserID,recipientKey,expiresAt,envelope}}`または`{delivery:null}`とする。候補の送信者資格を確認し、返す直前に受取アカウントのDurable Objectで暗号文・queued・期限・宛先鍵・受取資格・grantを一度に照合する。同じ転送の送信資格が候補取得後に変わっていないことも確かめる。候補が取消・受領済みとなった場合は次の候補へ進む。Appの32KiB応答上限内で1件ずつ保存する |
| GET `/group-invitations/{recipientID}/{requestID}` | 送った本人または受取本人だけが送受信の状況を確認できる。受諾期限を過ぎた未受領、保存期限を過ぎた結果、未知のIDは404 |
| DELETE 同上 | 受取本人は暗号文の仮保存成功後のreceived、送った本人はcancelledにする。受取側の`?discard=1`は検証できない暗号文をcancelledとして破棄する。状態変更と暗号文の消去を受取アカウントのDurable Objectで同時に行う。確定した結果は最初に受信箱へ保存した時刻から28日まで照会できる。200は確定した状態を `{status: 'received' \| 'cancelled'}` で返す。取消と受領確認が競合した場合も、同じIDのDELETEを受けると先に確定した状態を返す。期限切れの未受領は受け取れない。受取側のDELETEで照会できる該当結果がない場合や照合できない場合は404を返す。送信側の取消が初回受付に先行した場合は、送信者側に取消を保存し、未作成の転送を既存契約どおり404で返す。記録の上限に達した場合は429。取得済みでも受領確認が未確定なら、Appは先に確定した取消でグループを追加しない。受領確定後のグループへの反映は削除同期で扱う |
| GET `/group-invitations/additional-devices?recipientKey=...` | 認証済み受取人自身の受信箱から、追加端末が要求できる `{requestIDs:[...]}` を返す。受信箱の最大64件を対象に、期限切れ・取消・許可失効、指定された鍵を宛先とする記録がすでにある招待、または同じ端末資格から要求済みの招待を外す。同じ送信者の同じnoticeIDは1件にまとめる。相手・グループの情報や暗号文は返さない。指定鍵の所有確認は続くPOSTで行う。 |
| POST `/group-invitations/{recipientUserID}/{requestID}/additional-devices` | 受取本人の新端末から、その招待に限った宛先を受け付ける。本文は既存の端末署名と同じ `{publicKey,certificate:{certificate,issuerKey},signature}`。署名の用途は `requestGroupInvitationRedelivery`、対象データは小文字の `requestID` のUTF-8。発行元、端末証明の用途・期限、現在の資格の公開IDと端末ID、同じ端末鍵による署名、招待の期限と専用grantを照合する。同じ端末の再要求は1件に更新する。 |
| GET 同上 | 元の送信者の端末だけが、現在有効な追加宛先を `{devices:[{memberID,recipientKey}]}` として取得できる。元の招待・grantが有効な場合に限る。新端末の証明、端末資格、暗号文、グループ情報は返さない。 |

追加宛先は元の招待の受諾期限までに限って、その受信箱の記録に保持する。発行した端末証明そのものは保存しない。受取資格・証明の期限も取得時に再確認し、送信者による明示取消で追加宛先を回収する。元の状態がreceivedならその受領結果を維持する。受領・取消・期限の判定は元の招待と同じ所有元で行う。追加宛先の受付と取得はAPNs通知を送らず、暗号文も生成しない。アプリからの要求・再暗号化・受領は[Appの実行契約](../App/通信仕様.md#グループ自動配送の実行契約)を参照する。

追加端末用に再暗号化した転送は、元の送信IDを `sourceRequestID` に入れて送る。元の送信端末・受取アカウント・grant・通知ID・期限と、署名付き要求で確定した宛先鍵を照合する。追加端末用の転送をさらに元の転送として使うことはできない。受信箱で返す `sourceRequestID` はWorkerが照合したIDであり、暗号文の内側にある内容の検証はAppが行う。

追加端末用の暗号文は、要求した端末の有効な資格でのみ取得・受領確定できる。サインアウトして再ログインした場合は、新しい資格で同じ鍵を再証明すると未受領の転送を取得できる。元の招待を取り消す操作が先に確定した場合は、同じ受信箱で追加端末の未受領の暗号文も破棄する。すでに確定した受領結果は維持し、用途別の許可が失効した後は未確定の受領を認めない。

受取側がグループ招待の送信許可を取り消すと、取得済みでも未確定の招待は受領できない。遅れて届いた受領確認は、受信箱の記録から暗号文を外して `cancelled` を返す。先に確定した `received` は保持する。

受信箱の候補選択、暗号文の取得、受領の確定、APNsの通知先を選ぶ処理は、受取アカウントの保存側で同じ未受領の条件を使う。招待の記録は受取本人宛てで、状態が `queued` であり、用途別の送信許可が現在も有効であること。各操作で期限を確かめ、暗号文の取得と受領の確定では送信側の照会後にも現在の記録を確認する。

招待の有効期限に達したら、受取アカウントの保存側は `received` と `cancelled` の結果を保持期限まで返す。期限切れ処理の前後で、照会が返す状態と有効期限は同じ。保持期限以降は確定結果を返さない。未受領の招待も有効期限以降は返さない。

未確定の受領確認では、送り手のアカウントに送信時の端末資格を照会する。受取側の許可・期限・宛先が有効でも、送り手の資格が無効か照会中に受信箱の送信資格が変わった場合は、受領を保留して409を返す。同じ暗号文を現行の資格で再送したあと、同じ送信IDで受領を確認できる。確定済みの結果は再送を待たずに返す。

statusのqueuedは受信箱への永続保存、receivedは受取側の仮保存後の確認であり、APNsの200はどちらの保存完了も意味しない。同じID・宛先鍵・期限・grant・暗号文の再送は重複した転送しない。差替えは409。取消・受領済みのIDは再送で復活しない。サインアウトで旧資格の受け取りが確認できていない送信記録を使えなくし、同じ本人の現行資格による同一暗号文の明示的再送だけが転送資格を更新する。

初回受付前の取消には、認証済み送信者の領域に宛先の公開ID・送信ID・期限だけを保存する。同じ本人と宛先の同じIDを後から送っても、保持期間内はcancelledを返し、暗号文と通知を送りない。取消は最初に記録した時刻から28日、送信側1アカウント最大512件を保持する。期限切れとアカウント削除で回収し、受信箱の容量には加えない。

受諾期限は7日を基準に時刻差の許容5分まで。受領・取消・受諾期限・アカウント削除で暗号文を回収する。受諾期限を過ぎた受領・取消のレコードは、送信ID、両者の範囲を照合する識別子、元の期限、確定結果と保存期限だけを別に保存する。宛先は追加端末向けの場合に限り端末単位で照合する。結果の照会や再送で保存期限を延ばさない。有効な受信箱は1アカウント最大64件、受信箱と期限後の結果を合わせて最大512件。上限を超える新規保存は429を返す。作成は20回/UTC分/recipient、送信は既存の60回/UTC分/sender、grant発行は既存の60回/分・256件の枠を共用する。起動・前面復帰時の取得を主経路とし、polling・silent push・CallKit・VoIP Push・Apple PushToTalkを追加しない。

同じ送信者・noticeIDの最初の暗号文を保存するとき、受取側のDurable Objectが同じ同期処理の中で通知を担当する要求を決める。並行して複数の暗号文を受け付けても、既存の最大8台の有効なAPNs宛先へそれぞれ1回だけ送る。既存の認可・取消チェックを送信直前に適用する。再送や追加端末分の暗号文では通知を増やさない。固定payloadは`kind:groupInvitation`、categoryは`RIDEINTERCOM_GROUP_INVITATION`とする。表示には`GROUP_INVITATION_TITLE`／`GROUP_INVITATION_BODY`を使う。OSによる通知欄への静かな配信を指定するため、`aps.interruption-level=passive`を指定し、`aps.sound`は省略する。暗号文・group情報・任意URLは含まない。通知から通話を開始しない。設定と実APNsの受入条件は既存の呼び出しと共通。

### 背景用の一件分のグループ招待を受け付ける

アプリが画面を閉じる前に、登録済みの相手一人向けの招待を送信先と一件の操作に限定する。Mac Appの保存から組み立てた要求をローカルWorkerへ送り、受取側が既存の受信箱からグループを一件だけ保存できることを確認した。AppからiOSへ渡す処理と結果反映は[Appの通信仕様](../App/通信仕様.md#グループ自動配送の実行契約)に従う。

`POST /api/notifications/group-invitations/background` は[招待の背景転送の暗号化形式](Worker.md#招待の背景転送を保護する)に従う。JSONの `{sealed}` 一項目を64 KiB以下で受け付ける。復号したJSONは `{senderUserID, deviceID, sessionBinding, submission, proof}`。`submission` は通常の `POST /group-invitations` と同じJSONをUTF-8にし、標準Base64にした文字列で、最大36864文字。`sessionBinding` は[端末証明](Worker.md#ユーザーと端末の署名付き証明)に埋め込まれた64桁の小文字hex。`proof` は既存の `{publicKey, certificate, signature}` の形式とする。用途は `submitBackgroundGroupInvitation`、署名対象には `JSON.stringify([origin, sessionBinding, submission])` を使う。`origin` は端末証明の発行先でもあるHTTPSのorigin。配列をUTF-8の文字列にする際は空白を足さず、スラッシュをエスケープしない。端末Bearerや内部DO locatorを渡さない。

Workerは接続元の頻度枠を確認してから、要求先originの鍵で復号する。セッションの照会より先に、正規origin・送信者・端末ID・証明内の `sessionBinding` と署名を照合する。次に公開アカウント索引から送信者を解決し、現行の端末資格と期限を再確認する。その後の宛先の許可・期限・取消・暗号文の受付・結果は通常の送信処理を使う。復号や署名、送信者、期限内の端末資格の照合失敗は401、暗号化されていない要求や入力形式・招待期限の不正は400、相手の許可失効は403。OSが別のホストへ転送した場合も、署名付き要求の内容は発行先Worker宛ての暗号文で保護される。許可されるのは同じ正規originへの同じ招待の再送だけで、本文の差し替えや呼出し・資格更新への流用は拒否する。

同じ宛先と送信IDの背景用再送は、通常の60回/UTC分の送信枠で毎分一枠だけ消費する。追加のカウンタ用オブジェクトは作らず、既存の送信者のカウンタを分単位で更新する。同じ端末資格による同じ受付の再送では、招待の保存・通知・保持期限の設定を繰り返さない。保存済みの転送に必要なalarmが消えていれば再設定する。

### 背景用の一件分のグループ招待を取り消す

`POST /api/notifications/group-invitations/background-cancellation` は[背景送信と同じ暗号化・署名形式と端末資格の照合](#背景用の一件分のグループ招待を受け付ける)を使う。署名の用途は `cancelBackgroundGroupInvitation`。内側のJSONは `{recipientUserID, requestID, expiresAt}`。宛先の公開ID、元の転送UUIDと受諾期限（Unix時刻のミリ秒）を指定する。復号失敗、別用途の署名、本文の置換、失効した資格は401。暗号化されていない要求、時刻形式の不正、7日5分を超える将来の期限は400。

受付済みなら、元の送信者と期限が一致する場合に既存の受信箱を取り消す。受取側の受領が先なら結果を `received` のまま保ち、追加端末への転送を閉じる。受付前で元の期限内なら、送信者の既存の取消記録を使い、直後に受信箱が作られた場合も取り消す。受付前に取消が確定した同じ転送を後から送信しても、通知と受信箱を作らない。同じ取消を再送しても既存の保持期限を延ばさない。

成功はHTTP 200と `{requestID, expiresAt, status}` を返す。IDは小文字、結果は `cancelled` または `received`。他者の転送・自身宛ての転送・異なる期限・期限を過ぎて確定結果もない転送は404。未受付取消の保持上限に達した場合は429。APNsの配信設定とは独立して実行できる。通常のBearer付きDELETEの要求と応答形式は従来どおり。
