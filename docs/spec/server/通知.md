# 通知宛先・呼出し・暗号化グループ配送 API

## 範囲と認可

通常のAPNs表示通知から、利用者のタップをAppの共通通話操作へ渡すためのserver基盤。[WorkerのApple認証](Worker.md#apple認証と端末資格)で発行した有効な`ri1`端末Bearerだけを受け付ける。試用の静的資格、公開IDの知識、groupの共有鍵、招待receiptは送信許可にならない。通知許可の拒否・通知設定不足・配送失敗を、既存の認証・Local通話・購入・復元の失敗へ変換しない。

受信者は送信者の公開`userID`を指定して、**呼出し通知専用**のcapabilityを発行する。署名には既存の`DEVICE_IDENTITY_SIGNING_KEY`を使うが、`typ=rideintercom-notification+jwt`、`aud=rideintercom-call-notification`、HTTPS originのissuer、送信者のsub、受信者のrecipient、ランダムUUIDのjtiを照合する。端末証明としてもgroup参加権としても使用できない。Appはcapabilityを不透明な文字列として保持し、serverから確認した本人IDと対応させる。

serverには受信者ごとの**有効なgrantIDのSHA-256集合**だけを保存する。取消済みtombstoneを積み上げず、取消時に集合から削除する。月ごとの再発行を要求する期限は設けない。再発行は新しいgrantIDなので取消済みcapabilityは復活しない。アカウント削除、公開IDの変更、署名鍵の変更でも旧capabilityは使えなくなる。宛先の登録資格は期限を持ち、再ログイン時に宛先を再登録する。通常のサインアウトはその端末の宛先と資格を失効させ、他端末と未取消のアカウント単位の通知同意は維持する。

**直接招待関係の成立・相手とのcapability交換・ユーザー削除時の取消はApp側の接続点**。serverは連絡先一覧を持たず、直接関係を推測しない。Appは直接招待した相手にだけ発行・交換し、groupで会っただけの相手には発行せず、送信・タップ時も保存ユーザーとの対応を確認する。このserver工程だけで、group外の通知を利用可能としていない。

## HTTP 契約

全APIは`Authorization: Bearer <ri1>`を必要とし、JSON応答に`Cache-Control: no-store`を付ける。以下のpathは`/api/notifications`からの相対表記。余分なJSON fieldを拒否し、共通bodyサイズ・読取時間制限も適用する。公開IDは64桁小文字hex。UUIDは大文字・小文字を受け付け、同じIDとして小文字へ正規化する。時刻はUnix epochの**ミリ秒**。

| 操作 | 要求 | 成功応答・認可 |
|---|---|---|
| PUT `/device` | `{token, environment, topic}` | `200 {registered:true}`。現在の資格のdeviceIDに1件。tokenはAPNsのバイト列をhexへ変換した2〜4096文字の偶数長。32byte固定にしない。environmentは`sandbox`または`production`でserver設定に一致、topicも設定に完全一致 |
| DELETE `/device` | bodyなし | `200 {}`。現在の資格に対応する宛先のみ解除。通知停止・設定不足でも可能 |
| POST `/grants` | `{senderUserID}` | `200 {grantID, capability}`。受信者本人だけ発行、本人宛てのgrantは拒否。senderUserIDへ送信者を固定。capabilityの最大受入長4096文字 |
| DELETE `/grants/{grantID}` | bodyなし | `200 {}`。自分の有効集合からのみ削除。存在しないIDも同じ応答。他人の許可を変更しない |
| DELETE `/grants` | bodyなし | `200 {}`。自分が発行した全許可を取消。端末消去・発行応答紛失時の回復手段。相手一覧やcapability一覧は返さない |
| POST `/calls` | `{capability, requestID}` | `200 {requestID, expiresAt, status}`。capabilityのsenderと現在の本人公開IDが一致し、受信者の有効集合にgrantがある場合のみ受付。固定通知のみ。本文・名前・group・任意URLの指定は不可 |
| GET `/calls/{recipientUserID}/{requestID}` | bodyなし | `200 {requestID, expiresAt, status, senderUserID}`。受信者本人だけ取得。タップ時に期限・取消・有効grant・元送信者の資格世代を再確認する |
| DELETE `/calls/{recipientUserID}/{requestID}` | bodyなし | `200 {}`。元送信者の公開IDだけ取消。同じIDの取消再送も可。受信者や第三者には許可しない |

GETとすべてのDELETEは通知機能停止中でも可能。認証不正は401、入力不正400、送信許可不正403、他人の取得・取消や未知の呼出し404、取得時の期限切れ・取消・grant失効・送信者資格失効410。発行の有効集合上限または処理中の本人失効は409 / `grant_limit_or_inactive`、頻度・保持上限は429。通知作成・登録に必要な設定不足または内部通知処理失敗は503 / `notifications_unavailable`。外部providerの本文や秘密を返さない。

`status`は`processing`、`accepted`、`no_destinations`、`retry_later`、`rejected`、`cancelled`のいずれか。`accepted`は少なくとも1端末について**APNsが200を返した**という意味で、端末表示・利用者の応答・通話接続成功ではない。`processing`は同時再送または処理中断後にも残り得る。同じrequestIDの再送は記録済み結果を返し、配送を追加しない。再試行は利用者による別requestIDの新規呼出しとし、自動再送queueは設けない。

## 費用・悪用を抑える境界

| 対象 | 上限・期限 | 回収・失敗時 |
|---|---|---|
| APNs宛先 | 有効なnative登録最大8端末、各deviceIDに1件 | credentialの30日期限内。再認証・sign-outで旧世代を外し、account削除で全件削除 |
| 宛先登録とgrant発行 | 合算60回/UTC分/account | 429。取消操作にはこの制限を適用しない |
| 有効grant | 最大256/account | 409。個別取消または全取消で枠を回復。取消済みhashを保持しない |
| 送信要求 | 60回/UTC分/sender account | 重複要求もこの入口の枠を消費、429 |
| 新規呼出し | 20回/UTC分/recipient account | 重複は新規枠を消費しない。複数送信者による集中も同じ枠で制限 |
| 呼出し記録 | 最大512/recipient account、作成から24時間保持 | 重複抑止用。期限・取消後も保持期限まで再配送しない。alarm・次回開始で削除 |
| 呼出しの応答期限 | 作成から120秒 | APNs expirationとGET検証へ同じ期限。24時間の通話利用権とは無関係 |
| 配送 | 1要求につき最大8宛先、各fetch timeout 8秒 | 固定Apple hostへ逐次送信。外部からURLを指定しない |
| 公開ID索引・token所有索引 | 登録資格の期限まで、最大30日 | 通常は置換・sign-out・account削除で該当索引を除去。障害や並行処理の残りはalarmで回収 |

同一account・公開IDのrouting索引は既存と新登録の長い方の資格期限を保持し、古い端末の再登録で他の有効端末の経路を短縮しない。token所有索引にはこの延長規則を適用せず、最後の登録世代を優先する。

索引は公開IDまたは`environment|topic|token`のSHA-256ごとに別のSQLite DOを使う。token索引は現在の所有account・device・ランダムregistrationIDを保持し、同じtokenが別アカウントへ登録された後に旧アカウント向け配送を続けない。grant集合、宛先数、短期呼出し記録は上限を持ち、索引は期限を持つ。これらの制限は通知の費用・濫用を抑えるもので、購入や通話権を表す台帳ではない。

配送直前にsender資格、recipientの公開ID・grant・呼出し・宛先世代、token索引の所有を再確認する。遅れて返った410は配送時のregistrationIDと一致する宛先だけ削除し、新登録を消さない。取消・削除・sign-out中の残り端末への送信は止める。すでにAPNsへ渡った1要求は取り消せないため、payloadに個人名を載せず、タップ時GETで再検証する。索引掃除の失敗を既存認証や削除の停止条件にしない。残った索引だけでは旧UserAccountの資格・grantを通過できないが、物理的な索引消去完了と即時失効は区別する。

## 保存する情報と配送

UserAccountにはAPNs token・environment・topic・端末資格hash・registrationID・期限、有効grantID hash、短期呼出しのID・sender公開IDと内部資格世代・期限・結果、固定少数のレートカウンタだけ追加する。索引には内部locatorと公開ID・端末/登録世代・期限を保持する。表示名、メール、連絡先一覧、group情報、購入状態、capability JWT、端末Bearerの秘密は保存・ログ出力しない。APNs tokenもログへ出さない。短期呼出しの送信者は取得時の本人照合に必要な情報であり、恒久的な友達一覧へ昇格させない。

APNsの固定payloadは次の形。Appは`CALL_REQUEST_TITLE`と`CALL_REQUEST_BODY`の英日表示文字列を用意する。自由文や深いlinkは受け取らない。

```json
{"aps":{"alert":{"title-loc-key":"CALL_REQUEST_TITLE","loc-key":"CALL_REQUEST_BODY"},"sound":"default","category":"RIDEINTERCOM_CALL_REQUEST"},"version":1,"requestID":"<UUID>","recipientID":"<public userID>"}
```

`aps.category`は固定の`RIDEINTERCOM_CALL_REQUEST`だけを付ける。Appが同じcategoryへ応答actionを登録するための識別子であり、要求からcategory・action・通知本文を指定できない。category自体は送信許可や通話開始を意味しない。iPhone宛て通知のWatch転送と背景actionの応答先は[Appleのaction規則](https://developer.apple.com/documentation/watchos-apps/adding-actions-to-notifications-on-watchos)に従う。Appは同じcategoryへ「接続」「無視」を登録し、「接続」と本体のタップだけを共通判定へ渡す（[App通知仕様](../App/通知仕様.md)）。このserver変更だけで応答機能を完成扱いにしない。

`apns-push-type=alert`、priority 10、requestIDを`apns-id`と`apns-collapse-id`へ、120秒期限を秒に変換して`apns-expiration`へ設定する。HTTP 200はaccepted、410は該当宛先失効、429・5xx・通信失敗はretry_later、それ以外はrejected。APNs応答本文をAppへ転送しない。ES256 provider JWTは同じWorker isolateで50分再利用し、毎回生成しない。isolate再作成・複数isolate間の接続共有条件は実配送受入で確認する。

## 設定と未受入の範囲

`NOTIFICATIONS_ENABLED=false`がmain / previewの既定。公開設定は`APNS_TOPIC`（Appの`com.yowamushi-inc.RideIntercom.RideIntercom`を両環境へ設定済み）と`APNS_ENVIRONMENT`（Productionはproduction、Previewはsandbox）、secretは`APNS_PRIVATE_KEY`（PKCS8 P-256）、`APNS_KEY_ID`、`APNS_TEAM_ID`。既存`DEVICE_IDENTITY_SIGNING_KEY`も必要。`NOTIFICATION_INDEX` bindingとSQLite migration v3を追加する。実値の配布、鍵作成・登録、デプロイはこの実装に含まない。通知設定を揃えても、既存SFUのSERVICE_ENABLEDやApple認証の設定を変更しない。

Workerのnative fetchを実配送候補とする。Cloudflareの[workerd側の一次報告](https://github.com/cloudflare/workerd/issues/4841)では本番proxyがHTTP/2へ接続する一方、ローカルworkerdの直接接続とは挙動が異なる。`node:http2`のstubだけを理由にnative fetchが不能とは判断しない。本工程の試験はMiniflareのoutbound adapterが外部接続前に応答を代替し、実APNsへ送っていない。**配置したWorkerからのHTTP/2・provider JWT/接続再利用・APNs受入、署名entitlement/provisioning、実端末のtoken登録・通知許可・表示・応答は未確認**。iOSとmacOSのApp lifecycleへの接続、背景/終了/ロック状態、拒否・遅延・重複・取消後タップも別に受け入れる。PushKit、PTT、silent push、自動通話開始の実装ではない。

一次資料: [APNs登録](https://developer.apple.com/documentation/usernotifications/registering-your-app-with-apns)、[送信要求](https://developer.apple.com/documentation/usernotifications/sending-notification-requests-to-apns)、[応答処理](https://developer.apple.com/documentation/usernotifications/handling-notification-responses-from-apns)、[provider token](https://developer.apple.com/documentation/usernotifications/establishing-a-token-based-connection-to-apns)、[payload](https://developer.apple.com/documentation/usernotifications/generating-a-remote-notification)、[通知応答](https://developer.apple.com/documentation/usernotifications/handling-notifications-and-notification-related-actions)。


## 登録済みの相手への暗号化グループ配送

通常の呼出しとは別のaud=rideintercom-group-invitationの許可を発行する。grantIDの有効集合と端末資格の失効確認を共用するが、呼出し専用capabilityと相互流用できない。暗号文の内容はAppが[既知の相手の端末鍵と署名](../App/通信仕様.md#登録済みの相手へのグループ配送の暗号形式)で検証し、serverはgroup名・ID・鍵を復号・保持しない。受信箱に保持するのは外側の配送メタデータと不透明な暗号文だけである。

| 操作 | 要求・応答 |
|---|---|
| POST `/group-invitations/grants` | `{senderUserID}`。本人宛て以外の用途別capabilityを発行し、既存のgrant削除APIで取消できる |
| POST `/group-invitations` | `{capability, requestID, noticeID?, expiresAt, recipientKey, envelope, sourceRequestID?}`。expiresAtはUnix msで7日を基準とし、端末の時刻差を最大5分だけ許容する。期限切れは拒否する。recipientKeyは宛先公開鍵の87文字base64url、envelopeは暗号化EnvelopeのJSONをbase64化した最大21848文字。noticeID省略時はrequestID。`{requestID,expiresAt,status}`を返す |
| GET `/group-invitations?recipientKey=...` | 受取本人だけ、該当の公開鍵向けの未受領1件を`{delivery:{requestID,senderUserID,recipientKey,expiresAt,envelope}}`または`{delivery:null}`で返す。候補の送信者資格を確認し、返す直前に受取アカウントのDurable Objectで暗号文・queued・期限・宛先鍵・受取資格・grantを一度に照合する。同じ配送の送信資格が候補取得後に変わっていないことも確かめる。候補が取消・受領済みとなった場合は次の候補へ進む。Appの32KiB応答上限内で1件ずつ保存する |
| GET `/group-invitations/{recipientID}/{requestID}` | 送った本人または受取本人だけが配送状態を確認できる。期限切れ・未知は404 |
| DELETE 同上 | 受取本人は暗号文の仮保存成功後のreceived、送った本人はcancelledにする。受取側の`?discard=1`は検証できない暗号文をcancelledとして破棄する。状態変更と暗号文の消去を受取アカウントのDurable Objectで同時に行い、元の期限まで配送IDを保持する。200は確定した状態を `{status: 'received' | 'cancelled'}` で返す。取消と受領確認が競合した場合も、先に確定した状態を再試行の応答に返す。送信側の取消が初回受付に先行した場合は、送信者側に取消を保存し、未作成の配送を既存契約どおり404で返す。記録の上限に達した場合は429。取得済みでも受領確認が未確定なら、Appは先に確定した取消でグループを追加しない。受領確定後のグループへの反映は削除同期で扱う |
| GET `/group-invitations/additional-devices?recipientKey=...` | 認証済み受取人自身の受信箱から、追加端末が要求できる `{requestIDs:[...]}` を返す。受信箱の最大64件を対象に、期限切れ・取消・許可失効、指定された鍵宛てに配送済みまたは同じ端末資格から要求済みの招待を外す。同じ送信者の同じnoticeIDは1件にまとめる。相手・グループの情報や暗号文は返さない。指定鍵の所有確認は続くPOSTで行う。 |
| POST `/group-invitations/{recipientUserID}/{requestID}/additional-devices` | 受取本人の新端末から、その招待に限った宛先を受け付ける。本文は既存の端末署名と同じ `{publicKey,certificate:{certificate,issuerKey},signature}`。署名の用途は `requestGroupInvitationRedelivery`、対象データは小文字の `requestID` のUTF-8。発行元、端末証明の用途・期限、現在の資格の公開IDと端末ID、同じ端末鍵による署名、招待の期限と専用grantを照合する。同じ端末の再要求は1件に更新する。 |
| GET 同上 | 元の送信者の端末だけが、現在有効な追加宛先を `{devices:[{memberID,recipientKey}]}` として取得できる。元の招待・grantが有効な場合に限る。新端末の証明、端末資格、暗号文、グループ情報は返さない。 |

追加宛先は元の招待の保持期間に限って、その受信箱の記録に保持する。発行した端末証明そのものは保存しない。受取資格・証明の期限も取得時に再確認し、送信者による明示取消で追加宛先を回収する。元の状態がreceivedならその受領結果を維持する。受領・取消・期限の判定は元の招待と同じ所有元で行う。追加宛先の受付と取得はAPNs送信や暗号文の生成を行わない。アプリからの要求・再暗号化・受領は[追加端末の実装課題](../../backlog/未実装課題.md#グループの鍵を登録済みの相手へ届ける)で追う。

追加端末用に再暗号化した配送は、元の配送IDを `sourceRequestID` に入れて送る。元の送信端末・受取アカウント・grant・通知ID・期限と、署名付き要求で確定した宛先鍵を照合する。追加端末用の配送をさらに元の配送として使うことはできない。受信箱で返す `sourceRequestID` はWorkerが照合したIDであり、暗号文の内側にある内容の検証はAppが行う。

追加端末用の暗号文は、要求した端末の有効な資格でのみ取得・受領確定できる。サインアウトして再ログインした場合は、新しい資格で同じ鍵を再証明すると未受領の配送を取得できる。元の招待を取り消す操作が先に確定した場合は、同じ受信箱で追加端末の未受領の暗号文も破棄する。すでに確定した受領結果は維持し、用途別許可失効後は未確定の受領を認めない。

statusのqueuedは受信箱への永続保存、receivedは受取側の仮保存後の確認であり、APNsの200はどちらの保存完了も意味しない。同じID・宛先鍵・期限・grant・暗号文の再送は重複配送しない。差替えは409。取消・受領済みのIDは再送で復活しない。サインアウトで旧資格の未受領配送を使えなくし、同じ本人の現行資格による同一暗号文の明示的再送だけが配送資格を更新する。

初回受付前の取消には、認証済み送信者の領域に宛先の公開ID・配送ID・期限だけを保存する。同じ本人と宛先の同じIDを後から送っても、保持期間内はcancelledを返し、暗号文と通知を配送しない。取消の保持は最大7日5分・送信側1アカウント最大512件。期限切れとアカウント削除で回収し、受信箱の容量には加えない。

受信箱は1アカウント最大64件、保持は7日を基準に時刻差の許容5分まで、作成は20回/UTC分/recipient、送信は既存の60回/UTC分/sender、grant発行は既存の60回/分・256件の枠を共用する。受領・取消・期限切れ・アカウント削除で暗号文を回収する。起動・前面復帰時の取得を主経路とし、polling・silent push・CallKit・VoIP Push・Apple PushToTalkを追加しない。

同じ送信者・noticeIDの最初の暗号文を保存するとき、受取側のDurable Objectが同じ同期処理の中で通知を担当する要求を決める。並行して複数の暗号文を受け付けても、既存の最大8台の有効なAPNs宛先へそれぞれ1回だけ送る。既存の認可・取消チェックを送信直前に適用する。再送や追加端末分の暗号文では通知を増やさない。固定payloadは`kind:groupInvitation`、category=RIDEINTERCOM_GROUP_INVITATION、GROUP_INVITATION_TITLE／GROUP_INVITATION_BODYの表示を使う。OSが通知欄へ静かに置くように`aps.interruption-level=passive`を指定し、`aps.sound`は省略する。暗号文・group情報・任意URLは含まない。通知から通話を開始しない。設定と実APNsの受入条件は既存の呼び出しと共通。
