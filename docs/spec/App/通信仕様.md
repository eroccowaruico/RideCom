# RideCom App 通信仕様

## Appleログインと端末内データ

| 対象 | 現行契約 |
|---|---|
| 必須範囲 | Local・Internet・1対1・グループのすべての通話にAppleログインが必要。初回はApple標準の認証画面を使う。新規開発のためログイン導入前のデータの移行は行わない |
| 保存 | `AppleAccountSession`はAppleのuser識別子だけをKeychainへ保存する。メール・本名のscopeを要求せず、identity token・authorization codeを保存・ログ出力しない。requestのstateを一度だけ照合する |
| 再起動・圏外 | 成功済みの保存ログインは直ちに復元し、起動・前面復帰時にAppleのcredential stateを非同期確認。Local開始を応答待ちにしない。authorizedなら継続。確認エラーでは成功済みの保存ログインを維持し、近距離通話を毎回のInternet接続に従属させない。未ログインから確認エラーだけでログイン済みにはしない |
| 取消 | revoked・notFound・transferred、OSの取消通知で即時に通話を停止しログイン画面へ戻す。圏外で未知の取消を検出できるとは保証しない |
| サインアウト | 通話を停止し、ログインを解除する。先に端末の再ログイン必須フラグを保存するため、Keychain削除失敗後の圏外再起動でも古い資格を自動復帰しない。削除失敗を表示する。グループ・保存ユーザーは削除しない |
| 読書き失敗 | Keychain読出失敗を未登録に置き換えず、元データを保持して再読込を案内。資格を保存するまではログインを完了扱いにしない。中断・取消・サインアウトより古い非同期結果で権限を戻さない |
| アカウント分離 | `StorageNamespace.Account.<SHA256(Apple user)>`ごとにグループmanifest、鍵、保存ユーザー、端末member ID、設定、Internet資格を分ける。同じアカウントの再ログインは同じ保存先。別アカウントでは混在しない。SHA256値も公開ユーザーIDには使わない |
| 複数ウィンドウ | アカウントと通話モデルはAppが所有し、すべてのwindowで共有する。新しいwindowを開くだけでモデルを再生成・切断せず、サインアウトを全windowへ反映する |
| 呼出境界 | `IntercomViewModel`は生成時のログインアカウントとメモリ内の`accessID`を保持する。サインアウト・アカウント変更で世代を更新してから終了処理を呼び、同じユーザーの再ログインでも古いモデルを復活させない。通話・Audio Check開始、group／ユーザーの編集・再読込・reset、招待受理・鍵取得、設定保存・Internet資格設定と確認で照合する。AppCallOwnerが世代変更を監視し、旧モデルの通知・利用権観測・通話を停止して新しいモデルへ交換する。画面の生成を交換条件にせず、ContentViewは現在のモデルを表示する。ログイン前の招待URLはメモリで保留し、ログイン後に既存の招待検証へ渡す。server資格失効の後始末はサインアウト後も継続する |
| 背景操作前の確認 | `AppCallOwner.prepareForBackgroundCallAction()`が既存の保存ログイン・再ログイン必須フラグ・削除記録を読み直す。その後にcredential stateを確認する。同時操作は同じ確認結果を待ち、未完了の確認を素通りしない。非同期確認後も保存状態と本人・accessIDを照合し、別sessionでのサインアウト・削除、同じ本人の再ログイン、別アカウントへ旧操作を流さない。確認エラー時の保存済みログイン維持は上記と同じ。新たなログインを自動要求したり、失敗した操作を予約したりしない |
| iOSの保存保護 | AppのKeychain項目のうち、保護属性を`AfterFirstUnlockThisDeviceOnly`にする対象を限定する。対象はAppleAccount・AccountDeletion・GroupCredential.v2・InternetConnection・DirectInvitationsだけである。既存項目は正常読込後、属性が異なるときだけ属性を更新し、鍵本体を作り直さない。groupディレクトリ・lock・manifestとatomic置換後のmanifestは初回解除後にアクセスできる保護を指定する。MacのKeychain・ファイル保護は変更しない |
| 解除前・読込不可 | 再起動後の初回解除前、保存失敗・読込不可は未登録や空一覧へ置換しない。ログインを読めない間はモデルや鍵を生成せず、解除後の利用者操作で同じ保存先を再読込する。稼働中のモデルを重複生成せず、groupの一時読込失敗もidle時だけ再読込する。これらは保存アクセスの条件であり、OSの背景実行時間・ロック中の録音開始を保証しない |
| サーバーとの境界 | 端末ログインとInternet用の登録を分ける。Internet設定でserver nonceを取得し、同じAppleユーザーのidentity tokenを[認証API](../server/Worker.md#apple認証と端末資格)へ送る。server確認済みの不透明なユーザーID・端末UUIDを含む資格をKeychainへ保存する。資格は入力欄へ再表示しない。Apple生IDや保存ユーザーIDだけでは認可しない |
| 登録の制限と再試行 | HTTP 429の`Retry-After`秒数を待機期限へ変換し、同じ認証画面・originへの再準備を期限まで送信しない。自動再送・pollingは行わず、期限後の利用者操作で新しいnonceを取得する。不正・欠落・非正数は60秒、上限は3600秒。表示名・Apple token・サーバーの自由文をエラーへ流用しない。画面終了・URL変更で破棄される端末内の補助制限であり、強制はserverが所有する |
| 登録端末数の上限 | session交換のHTTP 409 / `device_limit_reached`だけを8端末登録済みとして、別の端末でRideComをサインアウトしてから再登録するよう案内する。待機だけで解消する頻度制限とは区別し、既存の資格・Localログイン・通話を変更しない |
| Internet登録の保護 | HTTPS originのみ、HTTP redirect拒否、応答最大32KiB。state・nonce・現在のAppleアカウントとログイン世代を照合し、URL変更・画面終了・キャンセルより古い応答を保存しない。保存失敗・遅延完了で不要になった発行済み資格は失効を試みる |
| Internetサインアウト | 通話を停止し、端末側の使用禁止を保存してからserverの端末資格を失効。通信・Keychain失敗時は再試行用の元資格を保持するが通常loadでは返さない。次にInternet設定を開いた際に再試行する。古い失効応答で新しい資格を削除しない。失効成功時は削除復旧用の最後の登録を同じアカウントのKeychain `deletion-account`へ保存してから`current`を消す。退避書込失敗なら元資格を残し、通常使用は禁止したまま再試行する |
| 登録応答の識別子 | 公開server userIDとBearer内の認証用locatorを区別し、一致を要求しない。公開ID・locator・秘密の形式、要求した端末IDと期限は検証する。削除後の公開ID更新はWorker側の契約に従う |
| 端末証明の取得 | Internet登録時にアカウント別KeychainのP-256秘密鍵を用意し、serverへ公開鍵とmember IDを送る。認証済みuserID/deviceIDに対するES256証明を検証後、資格と証明・信頼する発行公開鍵を同じKeychain項目へ保存する。署名・用途・origin・期限・要求したID／鍵の不一致なら資格を回収して保存を拒否する |
| 証明と鍵の保持 | サインアウトで資格と証明を使用禁止にし、再ログイン用の端末秘密鍵は残す。再起動では同じ鍵を使う。証明読込で鍵が欠けた場合に新しい鍵で置き換えず、読取・破損のエラーを返す。アカウント削除ではこの鍵・証明も消去対象。手動の別資格への置換は以前の証明を引き継がない |
| Localとの境界 | 証明取得はInternet登録時の追加処理であり、Localの通話開始・継続時にネットワーク要求や定期更新を追加しない。証明なし・期限切れの自己申告を同一ユーザーへ統合しない |
| 関連境界 | 通知先登録は[通知仕様](通知仕様.md)へ接続済み。削除対象サービスの範囲・別本人端末への反映は[後続課題](../../development/history/旧未実装課題の完了済み経緯.md#実装の接続点と残作業の再点検)。WebRTC予約のユーザー単位制限とserverの端末登録削除は[Worker契約](../server/Worker.md)を参照。端末資格の失効をApple連携解除と表示しない |

保護属性はAppleの[Keychain仕様](https://developer.apple.com/documentation/security/ksecattraccessibleafterfirstunlockthisdeviceonly)と[ファイル保護仕様](https://developer.apple.com/documentation/foundation/nsdata/writingoptions/completefileprotectionuntilfirstuserauthentication)に従う。端末固有のKeychain項目は別端末のbackup復元では移行しない。実端末での初回解除前・解除後の再ロック・背景接続成立は別の受入条件とする。

現行の保存読込は、すべての通話先に起動中の端末のmember IDが含まれることを確認する。旧端末のmember IDだけを含む保存データを新端末へ戻すと読込を拒否し、元のデータを保持する。アプリの自動保存は[復元候補の自動保存](#アプリの操作を起点に復元候補を自動保存する)に従う。現在のビルドでは実iCloudの保管先と復元の操作を提供していない。[端末変更時の復元要求](../../requirements/製品要求.md#icloud自動保存と端末変更時の復元)と[設計条件](../../backlog/機能拡張の実装前整理.md#icloudへの保存と自分の端末間同期)を参照する。

Apple標準の認証と起動時の資格確認は[公式実装例](https://developer.apple.com/documentation/authenticationservices/implementing-user-authentication-with-sign-in-with-apple)を参照。実AppleログインにはApp IDと署名profileの両方でSign in with Appleを有効にする必要がある。ローカルfixture検証と実認証の受入は区別する。

### 保存データから通話関係の復元候補を作る

`GroupRepository.callRelationshipBackup` は有効な端末証明を持つ本人について、確定済みの端末内データを `CallRelationshipBackup` 型の復元候補にまとめる。保存先をロックして読み直し、別の処理による変更を検出した場合は、候補を作らず再読込を求める。自動保存は同じ型で候補を比較し、CloudKitへ送る処理が書込直前に所有者と内容を再照合してJSONに変換する。

保存形式はJSONとする。形式を示す `version` に `1` を入れ、所有者の `owner`、通常グループの `groups`、個別通話で登録した相手の `contacts` を持つ。グループは識別子・本人が保存した名前・招待で加入したかを表す `joinedByInvitation`、相手は保存した識別子とアカウントを持つ。照合先を1台に特定できる個別通話の相手には[宛先の照合値と、確認済みの場合は受諾ID](#個別通話の復元を保存時の相手端末に照合する)を入れる。照合先の端末証明を取得するための[受け渡し専用値](#確認済みの招待から端末証明の受け渡し先を求める)も、元の端末対の通話鍵を読み取れた場合に含める。端末ID、公開鍵、端末秘密鍵、通話鍵、通知設定、処理中の招待は書き出さない。グループに記録した本人のアカウント・公開鍵が現在の端末証明と一致し、本人が除外されていない関係を選ぶ。個別通話の相手は、その中のアカウント宛て通話に対応し、同じ発行元で登録済みの場合に限る。

`CallRelationshipBackup.read` は有効な端末証明から本人を確認し、所有者が一致するデータを読む。作成・読込・CloudKitへの書込で同じ内容の検査を使う。別の本人、期限切れ、対応していない形式番号、同じ識別子や同じ相手が重複した内容、不正な名前・アカウントを拒否する。読み出した識別子を現在の参加資格の照合に使う。これらの値から通話鍵を生成したり、グループへ参加できると判断したりしない。

本人との対応を記録していない通常グループ、個別通話との対応を確認できない相手、相手の呼び名や個人設定は、保存時にどの本人の情報かを決める手順を追加してから扱う。実iCloudの設定と接続、現在の参加資格を確かめる処理は[バックログ](../../backlog/未実装課題.md#icloud自動保存と招待をやり直さない端末復元)で追う。

[個人登録を兼ねるグループ招待](#個人登録を兼ねるグループ招待)で初めて保存したグループは、相手から到着確認を受け取って本人のアカウント・公開鍵を保存した時点で、招待で加入したグループとして復元候補に含める。受諾して返信を送った段階では、その招待を根拠に候補へ追加しない。

### 復元候補をiCloudのアプリデータ領域に保存する

`CloudKitCallRelationshipBackupStore` は指定されたアプリ用CloudKitコンテナの非公開データベースを使う。RideComアカウントごとに `CallRelationshipBackup` レコードを1件使う。レコードの名前は `call-backup-` とSHA-256の小文字16進表記を結合する。ハッシュの入力は `ridecom.call-backup.v1|` に、発行元のUTF-8をBase64にした文字列、`:`、アカウントIDを順に足した文字列とする。保存には現在のRideComの端末証明を確認する。

| 条件 | 読込・保存の結果 |
|---|---|
| 作成または更新 | 所有者と形式を照合し、復元候補の型をJSONに変換して暗号化フィールド `payload` に保存する。端末鍵・通話鍵・未知のJSON項目は送らない |
| 読み込む | レコードの種類・識別子・所有者・暗号化フィールドを照合する。暗号化されていないフィールドを含むレコードは拒否する。CloudKitが `unknownItem` を返した場合は記録なしと扱う |
| 複数端末で書き込む | 新規作成または読み込んだ記録を元に、`ifServerRecordUnchanged` で1件だけ書き込む。別端末の変更と競合した場合は失敗を返す。CloudKitから保存済みの候補が返り、内容と所有者を照合できた場合に保存を完了する |
| 空の候補、復号不能、iCloud未設定、通信失敗 | 空の候補は、削除の記録が示す内容と読み込んだ保管先が一致する場合にだけ更新に使う。記録がない場合と他の失敗を区別し、失敗を呼出元へ返す。読めなかった内容を空で上書きしない |

アプリでの保存には、次節で定める保管先の設定を必要とする。[CloudKitの暗号化フィールド](https://developer.apple.com/documentation/cloudkit/encrypting-user-data)・[CloudKitの競合判定](https://developer.apple.com/documentation/cloudkit/ckmodifyrecordsoperation/recordsavepolicy/ifserverrecordunchanged)

### アプリの操作を起点に復元候補を自動保存する

`IntercomViewModel` は保管先の設定、端末内のグループ・相手の保存の確定、端末証明の保存、前面復帰で自動保存を要求する。端末内の保存は読み返して確定する。端末内の書込に失敗した操作では要求しない。`CallRelationshipBackupSync` は要求をまとめて1件ずつ処理する。問い合わせ中に端末内で編集が重なったら、古い候補を送らず改めて読み直す。失敗時は次の要求を待つ。

| 保存の条件 | 結果 |
|---|---|
| 初回で保管先に記録がない | 現在の端末の候補を新規保存する。競合はCloudKitが検出する |
| 保管先と端末の候補が一致 | 書き込まず、その内容のハッシュ値を比較に使う。端末内に変更がなければ再送しない |
| 保管先が前に確認した候補または送信を試みた候補と同じで、端末で候補が変わった | 読み込んだCloudKitの記録を元に更新する。再起動しても、この端末に残るハッシュ値で照合する |
| 保管先が別の端末で変わり、削除した相手の登録が変わっていない | 下記の条件を満たす相手だけを保管先から除く。保管先の他の相手とグループ、端末内の編集を保つ |
| その他の競合、確認済みの記録の消失、初回に異なる内容があった場合 | 端末内の編集と保管先の状態を維持し、統合を待つ |
| 一連の削除で最後のグループまたは登録済みの相手を削除した | 保管先がいずれかの削除直前の候補と、この端末が確認済みまたは送信を試みた内容の両方に一致し、保管先に残る全項目を一連の削除で消した場合は、空の候補で更新する。更新後も所有者と形式を持つ記録を保持する |
| 空の候補に対応する削除記録がない、または端末の保存に失敗 | 初回の空の記録は送らない。すでに保管先を確認した履歴があり、削除前の内容との一致を確認できなければ統合を待つ |

端末の保存形式27では、グループや相手の削除で、復元候補からその1件だけが除かれた場合に、同じ確定操作で `backupRemovals` を保存する。`steps` は操作順に並べ、削除した対象 `item` のUUID `id` と種類 `kind`（`group` または `contact`）、削除直前のハッシュ値 `before` を記録する。`result` は最後の削除直後のハッシュ値。ハッシュ値には自動保存と同じ計算を使う。直前の記録の `result` が次の削除直前の候補と一致するときだけ記録をつなぎ、それ以外は今回の削除から始める。端末の再起動後も使い、削除した対象が端末内の保存に戻った場合は一連の記録を除く。

確認済み受諾IDのある相手を削除した場合、その相手の候補全体のハッシュ値も、同じ計算で `steps` の `contactFingerprint` に保存する。この値は端末内の削除記録にだけ入れる。保管先が変わっていたら、この端末が最後に保存を確認した候補のハッシュ値と `before` が一致する箇所から、後続の削除だけを調べる。保管先の相手のIDと候補のハッシュ値が削除の記録に一致し、現在の端末内の候補に同じアカウントの相手がいない場合、その候補を保管先から除く。受諾IDが異なる再登録や、削除記録が指していない候補は保つ。削除する候補がなければ書き込まない。

書き込みは読み直したCloudKitレコードを元に行い、その後に別の変更が入っていれば失敗として次の自動保存要求を待つ。この更新で保管先と端末の候補が一致した場合は保存を確認した内容を更新する。他の違いが残れば最後に確認した記録を保ち、統合を待つ。応答が失われても候補が除かれていれば再送しない。削除対象が保管先の最後の相手で、この処理で保管先が空になった場合も、所有者と形式を持つ記録を保持する。

空の候補で更新する直前に、保管先と一致した `before` から最後までの削除対象が、保管先にあるグループ・相手の全項目と一致することを確かめる。`result` は同じ所有者の空の候補と一致する必要がある。記録がない場合や別の操作で候補が空になった場合は、空になったことから削除を推定しない。

RideComの本人と端末証明に加え、現在のCloudKitコンテナ・環境・iCloudアカウントが保管先の設定と一致する場合に処理を始める。ネットワークから戻った後も照合し、切替後は新しい書込を始めず、切替前の処理の結果を保存済みとして採用しない。サインアウトやアカウント変更で通話モデルを作り直すときは、進行中の処理を取り消す。

保管先を設定したアプリでは、指定されたCloudKitコンテナのアカウント状態が `.available` の場合に、同コンテナが返す本人のレコードIDを確かめる。確認が取れるまで自動保存を開始しない。iCloudアカウントの切替通知を受けたら、前の処理を取り消してから再確認する。前の確認が後から完了しても保管先の設定には使わない。各レコードを読み書きする直前にもRideComの本人とCloudKitのレコードIDを確かめる。利用できるアカウントを確認できなかった場合は、次の前面復帰で再確認する。[Appleのアカウント状態](https://developer.apple.com/documentation/cloudkit/ckcontainer/accountstatus(completionhandler:))・[本人のレコードID](https://developer.apple.com/documentation/CloudKit/CKContainer/fetchUserRecordID%28completionHandler%3A%29)・[アカウント切替通知](https://developer.apple.com/documentation/foundation/nsnotification/name-swift.struct/ckaccountchanged)

`CallRelationshipBackupCheckpointStore` は、JSONのキーを昇順に並べ、スラッシュをエスケープせずSHA-256を計算する。結果は小文字の16進表記。Keychainのサービス名は端末内のアカウント用名前空間に `.CallRelationshipBackupCheckpoint.v1` を足す。Keychainのアカウント名には、次のJSONのハッシュ値を使う。

- `cloud` は `container`、`environment`、`account` を持つ。
- `owner` はRideComアカウントの `issuer` と `userID` を持つ。
- `deviceKey` は端末の公開鍵を持つ。

Keychainに保存する値は、最後に確認した候補のハッシュ値 `saved` と、送信を試みた候補のハッシュ値 `pending` のJSON。値がない項目は省略する。iOSでは最初の解除後にこの端末でだけ読み書きできる保護を使う。アカウントの端末内データを消去するときに、同じ名前空間のハッシュ値も消す。

送信前にハッシュ値を保存して読み返し、保管先から一致する結果が返ったら確認済みにする。応答を受け取れないまま再起動しても、保管先が送信途中のハッシュ値と一致すれば、端末内の新しい編集を保存できる。Keychainの記録を読み込めない場合や送信前に確定できない場合は、その回の送信を中断する。

現在のビルドでは実iCloudの保管先を設定しない。実iCloudの設定と接続、相手削除の反映後も残る競合の統合、現在の参加資格の照合は[バックログ](../../backlog/未実装課題.md#icloud自動保存と招待をやり直さない端末復元)で扱う。

### 個別通話の復元を保存時の相手端末に照合する

個別通話の候補を作るとき、保存した相手と個別通話の両方で相手端末が1台であり、アカウント・端末ID・公開鍵が一致する場合に `restoreRecipientFingerprint` を入れる。この値は、順に文字列 `rideintercom.call-restore-recipient.v1`、個別通話のUUID（大文字の表記）、相手の端末ID、相手の公開鍵を並べたJSON配列のSHA-256。スラッシュをエスケープせず、SHA-256の結果はパディングなしのBase64URLで保存する。候補の読込では省略を受け入れ、値がある場合は同じ表記の32バイトであることを検査する。

schema 28では、招待で作った端末対の個別通話に `contactRegistration` を保存する。署名済み受諾に含まれる `receiptID` と、確認済みかどうかを表す `isConfirmed` を持つ。送り手は受諾を検証して登録したときに確認済みとする。受け手は受諾時に未確認として保存し、送り手の署名付き到着確認が同じ受諾IDを示す場合に確認済みとする。以前の招待の到着確認は、別の受諾IDを確認済みにはしない。招待記録を期限後に外しても、端末対の通話を保存している間はこの情報を保つ。

相手端末の照合値と確認済みの受諾IDがそろった場合だけ、復元候補の相手に `confirmedRegistrationID` を含める。値はUUIDで、記録のない旧保存と未確認の場合は省略する。通話先IDが同じでも、削除後に新たな招待で登録すると別の受諾IDを保存する。

`CallRelationshipBackup.directRestoreRequest` は、保存した相手の識別子、照合する端末の検証済み証明、新端末の署名を使う。候補の所有者が新端末の本人と一致し、相手の証明が期限内で、相手のアカウントと計算し直したハッシュ値が候補と一致するときだけ、個別通話の復元要求を組み立てる。相手端末の照合値か確認済みの受諾IDが欠ける候補、同じアカウントの別端末には要求を組み立てない。保存時の相手端末に照合できたことは、現在の参加資格や通話鍵を確認したことにはならない。

新端末の `CloudKitCallRelationshipBackupSession.prepareDirectRestore` は、選んだ相手が含まれる復元候補の所有者と本人を照合し、新端末が現在使うiCloudから候補を読み直す。読み込み前後で同じiCloudアカウントとRideComのログインが有効であることを確かめ、端末ID・公開鍵・サービスの署名鍵も確認する。候補の相手が消えた場合や、相手のアカウント、宛先の照合値、確認済みの受諾IDが変わった場合は `backupChanged` として署名しない。他のグループや相手だけが変わっても、選んだ相手の記録が一致すれば照合先の選定に進む。iCloudアカウントや有効な端末が読み込み中に変わった場合は `accountUnavailable` とする。

照合先の候補は署名を検証する前の端末証明として受け取る。新端末は有効なセッションが持つサービスの接続先と発行者公開鍵を使い、証明の署名・有効期限・発行元を検証する。候補の相手のアカウントと、個別通話ID・証明の `memberID`・公開鍵から求めた照合値が一致する証明だけを選ぶ。サービスの `deviceID` が同じ証明が複数あれば、有効期限が最も先の証明を使う。一致する証明がなければ要求を作らない。異なる `deviceID` の証明が複数照合を通った場合も、宛先の確定を保留する。選んだ端末の検証済み証明と、その端末に宛てて署名した要求を返す。この時点では送信や保存に進まない。

Workerには[指定したアカウントだけが端末証明の暗号文を取得する経路](../server/Worker.md#個別通話の復元先の端末証明を預かる)があり、ローカル試験でのみ有効にする。

#### 確認済みの招待から端末証明の受け渡し先を求める

両端末は、確認済み招待を確定した端末対の通話鍵を標準Base64から32バイトに戻す。その32バイトをHKDF-SHA256に入力し、saltに `rideintercom.direct-restore.device.seed.v1`、infoに大文字の受諾UUIDのUTF-8を使う。32バイトの出力をパディングなしのBase64URLにし、`restoreDiscoverySeed` としてCloudKitの非公開データベースにある暗号化フィールドへ保存する。この値は証明の受け渡しに限って使う。通話鍵を読み取れない場合は値を省く。削除前後の候補にも同じ生成処理を使い、保管先と比較する。

`DirectRestoreDeviceAddress` はこの専用値を32バイトに戻し、HKDF-SHA256の入力にする。saltは `rideintercom.direct-restore.device.v1`。infoは用途名、発行元、預ける側と読む側の公開アカウントID、個別通話ID、確認済み受諾ID、預ける側の端末の照合値を順に並べたUTF-8 JSON配列。UUIDは大文字とし、空白を足さずスラッシュをエスケープしない。用途名が `slot` の32バイト出力を小文字16進表記にし、`certificate` の32バイト出力を暗号化鍵にする。Workerは取得時に読む側のアカウントを照合する。

| 処理 | 条件と結果 |
|---|---|
| 暗号文を作る | `GroupRepository.directRestoreDevicePublication` は端末内の確定済みの保存をロック中に読み合わせる。指定した相手の受諾IDが確認済みで、個別通話の記録で相手端末を1台に絞れた場合、処理を続ける。自端末の証明から照合値を求め、証明を暗号化する。相手を削除した場合は新たな暗号文を作らない |
| 暗号文と署名を組み立てる | 証明のJSONをAES-GCMで暗号化する。認証データは用途名・slot・期限を順に並べた空白なしのUTF-8 JSON配列。AES-GCMの結合形式を標準Base64にする。[WorkerのPUT](../server/Worker.md#個別通話の復元先の端末証明を預かる)が定める5項目に署名する。期限は作成から24時間後と証明期限のうち早い時刻。発行時刻と期限はいずれもUnixミリ秒に切り捨てる |
| 取得するslotを求める | 新端末は有効な自身の証明から本人を確認する。選んだ復元候補から相手の照合値、確認済み受諾ID、受け渡し専用値を得る。この3項目がそろえば照合先と同じslotを求められる。削除後に招待をやり直すと、受諾IDが変わり別のslotになる |
| 取得した証明を開く | 復元候補を読む本人と暗号文の期限を確認する。復号した証明をサービスの発行者公開鍵で検証し、期限、発行元、相手の公開アカウントID、セッション照合値の形式、保存時の端末の照合値を確かめる。改変、期限切れ、別の相手、別の登録の暗号文を拒否する。有効な証明は[上の宛先の選定](#個別通話の復元を保存時の相手端末に照合する)へ渡せる |

`InternetAccountClient` は同じ発行元のHTTPS接続と操作する本人の端末Bearerを照合し、[Workerの預け入れ・取得・取消](../server/Worker.md#個別通話の復元先の端末証明を預かる)を呼び出す。預け入れは `stored`、取消は `revoked` を確かめる。取得の404は記録なしとして扱い、それ以外の通信・認可・形式の失敗は呼出元に返す。標準のHTTP処理で別URLへの応答を拒否する。

新端末の `CloudKitCallRelationshipBackupSession.prepareDirectRestore` は、iCloudの復元候補を読み直し、選んだ相手と照合値・受諾ID・受け渡し専用値が同じ場合だけ最新の候補から取得先を求める。Workerから応答が返った後、iCloudと候補をもう一度読み直す。iCloudや接続先の端末資格が途中で変わった場合は中断する。相手が消えたり候補が変わったりした場合は `backupChanged` を返す。確認を通過した場合だけ証明を開き、宛先を検証して要求に署名する。

`IntercomViewModel.publishTrackedDirectRestoreDevice` は、現在のアカウントと発行端末を照合し、確認済みの相手への預け入れを送る前に `GroupSnapshot.directRestoreDevices` へ記録する。保存に失敗した場合は送信しない。保存するのは相手の保存ID、発行するアカウントと端末ID、読む側の公開アカウントID、slot、受諾ID、期限、取消待ちの有無。slotごとに1件、全体で最大64件。証明、秘密鍵、通話鍵、受け渡し専用値、Bearerは保存しない。この一覧は端末内に保存する。

| 状況 | 記録と処理 |
|---|---|
| 同じ登録の証明を再送する | 先に保存し、同じslotに記録した最も遅い期限を保持する。応答が失われても記録を保つ |
| 相手の削除や招待の更新で、確定済み受諾IDとの対応が外れる | 同じ保存で取消待ちにする。取消待ちのslotを預け入れには使わない。同じ相手を招待し直した場合は新しいslotを使う |
| 取消処理を実行する | `IntercomViewModel.synchronizeDirectRestoreDeviceWithdrawals` は、有効期限前で現在の発行アカウント・端末と一致する取消待ちの記録を読み取る。Workerへ保存済みのslotと読む側の公開アカウントIDを送る。同じ資格で `revoked` を確認した後に、その記録を回収する |
| 通信や保存が途中で失敗する | 取消待ちを保持し、保存を開き直した後も同じ内容で再試行する。資格が途中で変わった場合も同じ記録を保持する。期限が過ぎた記録は送信せず、次の保存で回収する |

#### 確認済みの相手への証明の預け入れと取消を再開する

端末内の保存を共有する `AppCallOwner` に復元専用の通信先を指定した場合、現在のアカウントに自動同期を設定する。通信先を指定するのはローカルWorkerとの結合試験。通常起動時の設定は空で、画面やPublic APIで利用者に提示する入口はない。

起動・アカウントの設定、利用者がアプリに戻ったとき、確認済みの相手や通話先が保存で変更されたとき、Internet経路の復帰、端末資格の保存で同期を要求する。預け入れ・取消の内部記録だけを保存した場合は要求しない。同期を同時に2つ実行せず、実行中に要求が来た場合は、新たな保存に基づいて処理する。サインアウトとアカウント切替で停止する。

各回は現行の発行端末に属する取消待ちを先に送り、現在の確認済みの登録から照合先を決め直して証明を預ける。端末資格と照合できる相手だけが対象で、暗号化とWorkerの認可は[証明の受け渡し契約](#確認済みの招待から端末証明の受け渡し先を求める)を使う。相手の通話鍵や受け渡し専用値を読み出し後に変更した場合は、次の送信前に保存を読み直す。空き枠のある範囲で保存し、取消待ちのslotには送らない。

同じアプリプロセスと端末資格で `stored` を確認したslotは、期限まで1時間を超えて残っていれば送信を省く。期限が近づいた場合は、同じ端末セッションの証明で期限を先に延ばせるときだけ再び預ける。アプリを起動し直すか別の端末セッションに切り替わった場合は、応答を受け取った記録を使い回さない。途中で通信に失敗したら次の起点で再試行する。時間だけを起点とする更新と、iOSがアプリの実行を止めている間の処理は[残作業](../../backlog/未実装課題.md#icloud自動保存と招待をやり直さない端末復元)で扱う。復元用の通信先を設定した場合の要求と応答の自動受信は、[中継の処理](#中継を通じて復元の要求を送り通話鍵を保存する)に従う。

#### 復元する相手を選び直さずに端末証明を待つ

復元専用の通信先を持つ `CloudKitCallRelationshipBackupSession` は、選んだ相手を現行のiCloud候補で照合する。候補に確認済み受諾ID・相手端末の照合値・受け渡し専用値がそろっていれば選択を保存する。この設定を使うのはローカル結合試験。通常の起動では空にする。

選択の保存先は既存のバックアップ用Keychainで、端末内のRideComアカウント、iCloudのコンテナ・環境・アカウント、サービスの本人と端末公開鍵に範囲を限る。保存項目は選択ごとのUUID、相手の保存IDと、相手の復元候補をキー順固定JSONで表したSHA-256の照合値。選択は同じ範囲につき1件。再び選ぶと選択UUIDが変わる。同じ項目に[復元要求の送信状態](#中継を通じて復元の要求を送り通話鍵を保存する)を保持できる。復元候補の内容、通話鍵、受け渡し専用値、Bearerや端末秘密鍵はこの項目に保存しない。

| 条件 | 次の状態と処理 |
|---|---|
| 選択操作、起動・iCloud再接続、前面復帰、Internet復帰、端末資格の保存 | 選択があれば、現在の端末資格とiCloudの候補を読み直す。再開できる要求がなければ証明を照会する。照会中に次の起点が来れば古い処理を取り消す。選択が空なら保存候補や証明を照会しない |
| 証明が未登録か期限切れ | 選択を保持し、次の起点まで待つ。Workerが証明を返した後に期限を迎えた場合も、古い証明を使わず再試行を待つ |
| 相手が新しい証明を預け、次の照会で取得する | 同じ相手の候補がiCloudに残ることを応答後にも確かめ、署名付きの復元要求を作ってから選択の送信処理へ進む |
| iCloudの候補から相手が消えた、または照合値が変わった | 該当する選択だけを回収する。別の選択が既に保存されていれば保つ。無効になった選択から準備した要求は送信できず、その応答による保存も行わない |
| サインアウト、iCloudまたは端末資格の切替、通信失敗 | 現在の照会を終了する。別アカウントや別の端末鍵の範囲で、前の選択を読み込まない。元の範囲に戻った後は現在の候補を読み直して再試行できる |

### 現在の保存を照合して復元の確認を返す

`CallRelationshipRestoreRequest` は、通話先、照合する相手のアカウントと端末ID・公開鍵、新端末ID、要求ごとのUUIDと有効期限を、新端末の証明付き署名で結ぶ。個別通話の候補から作る場合は、候補の `confirmedRegistrationID` を `challenge` のフィールドに加えて署名する。通常グループの要求では省略する。有効期限は作成から300秒とする。照合側の時計では期限より前で、期限までが330秒以内の場合に限り署名を照合する。署名にはキーを昇順に並べ、スラッシュをエスケープしないJSONと、通常の端末署名の `requestCallRelationshipRestore` 用途を使う。

`GroupRepository.confirmRestore` は、既に登録されたサービスの署名鍵で新端末の証明を確かめる。要求に含まれる宛先の本人・端末ID・公開鍵が、照合する端末の証明と一致した場合にだけ応答する。保管ファイルをロックして読み返し、読み込み済みの保存内容と一致する場合にだけ、次を判定する。

| 対象 | 確認を返す条件 |
|---|---|
| 共通 | 確定した通話先があり、照合する端末の本人・端末ID・公開鍵がその通話先に登録され、現在の通話鍵を読める。要求した本人の参加端末を1台に特定でき、新端末IDと公開鍵はその端末と異なる |
| 通常グループ | 要求に個別通話の受諾IDがない。照合する端末、以前の参加端末、新端末とそれぞれの本人に適用される除外がなく、以前の端末が現在も所属している |
| アカウント宛ての個別通話 | 通話先に登録されたアカウントの組が双方と一致し、照合する端末の相手一覧にも本人と以前の端末ID・公開鍵がそろっている |

確認は、署名を含む元の要求全体と以前の端末IDを `confirmCallRelationshipRestore` 用途で署名する。要求を作った側は、元の要求の署名・端末証明・期限を再検査し、現在使う新端末の本人・端末ID・公開鍵が要求と一致することを確かめる。そのうえで指定した相手の本人・端末ID・公開鍵と確認の署名を照合する。両方が通ったときだけ、通話先、以前の端末ID、新端末と相手の本人・端末ID・公開鍵を `CallRelationshipRestoreConfirmation.Verified` として後続の検査に渡す。

個別通話の照合先で `CloudKitCallRelationshipBackupSession.respondToDirectRestore` を使う場合、その端末が現在使用するiCloudのアプリデータ領域から、その本人の復元候補を読み直す。読み込み前後でiCloudのアカウントとアプリのセッションを確認する。読み込み後は端末ID・公開鍵・サービスの署名鍵も照合する。

読み直しの前に、要求の署名と期限、宛先、双方のアカウントから求めた個別通話ID、受諾IDの有無を検査する。相手が1台で、登録時の端末対の通話鍵を使える場合は、その相手の[個人削除の暗号文](#個人削除の送信待ち)を既存の中継から照会する。有効な削除は通常の受取処理で反映し、削除した相手に確認を返さない。照会に失敗した場合も確認を保留する。中継に該当する記録がない場合や照会対象を特定できない場合は、後続の保存の照合だけを行う。中継の応答から現在の参加資格は確定しない。

照合先は、要求した相手のアカウントと旧端末を端末内の記録から確認する。同じ相手が読み直した復元候補に残り、個別通話ID・旧端末ID・公開鍵から計算した[照合値](#個別通話の復元を保存時の相手端末に照合する)が一致することを確かめる。要求に含まれる受諾IDは、照合先と旧端末の組で保存した確認済み受諾IDと、読み直した復元候補の受諾IDの両方と同じ場合に限り、確認に署名する。復元候補や受付に必要な値が欠けている場合や、照合結果が異なる場合は応答を作らない。読み込み中にアカウントや端末の鍵が変わった場合は現在のセッションを確かめ直す。

同じiCloudに反映された削除と、照合先が中継から受け取れる個人削除を確認できる。中継に未送信の場合や、回収済み・期限切れの場合は、別の根拠で現在の関係を確認する必要がある。[復元の残作業](../../backlog/未実装課題.md#icloud自動保存と招待をやり直さない端末復元)を参照する。

#### 通常グループの照合先が現在の通話鍵を暗号化する

`CloudKitCallRelationshipBackupSession.respondToGroupRestore` は、通常グループに対する署名付き要求が現在の自端末宛てで、端末内にそのグループがあることを確かめる。同じiCloudのアプリデータ領域を読み直し、読み込み前後で本人、端末資格とiCloudアカウントを照合する。

| 照合先の状態 | 結果 |
|---|---|
| 照合先の最新のiCloud候補に同じグループIDがあり、端末内の現在の記録でも双方の所属を確認できる | `GroupRepository` が保存先のロックを保持して、現在の通話鍵を新端末の公開鍵宛てに暗号化する。確認の署名と暗号化された鍵を返す |
| 照合先または要求者が退出・除外済み、通話鍵が読めない、または照合先のiCloudに同じグループIDがない | 鍵を暗号化した応答を返さない。以前の候補だけが残っていても、読み込み後の端末内の所属を使う |
| 個別通話の受諾IDがある、署名や期限が不正、または宛先の本人・端末ID・公開鍵が一致しない | 通常グループの要求として扱わず、鍵を暗号化しない |

通常グループの `groupMembership` には、現在のメンバーのIDと共有表示名、そのうち本人との対応を確認した端末の公開鍵、現在のメンバーに対して保存した招待時の公開鍵、有効な除外記録を入れる。未確定の招待枠、端末内で付けた呼び名、鍵参照、招待ID、照合先自身の招待経緯を含めない。除外記録には対象の端末ID、判明している本人、除外時刻を残す。暗号文から取り出した参加情報を、署名済みの応答に含まれるハッシュ値と照合する。

照合先の自動選定と通信での要求・応答は[復元の残作業](../../backlog/未実装課題.md#icloud自動保存と招待をやり直さない端末復元)で扱う。

### 復元する新端末へ通話鍵を暗号化して渡す

呼出元は現在の参加資格を確認して復元を許可し、渡す通話鍵を確定する。`CallRelationshipRestoreCredential` は要求・応答それぞれの署名と期限を確認する。署名者と指定された照合先は一致する必要がある。対象の通話先に属する鍵を暗号化する。

| 項目 | 形式と検査 |
|---|---|
| 暗号化の入力 | `fingerprint` に参加情報のSHA-256の32バイトをBase64で入れ、`secret` にUTF-8で1〜256バイトの通話鍵を入れる。アカウント宛ての個別通話では `directMembership`、通常グループの応答では `groupMembership` も入れる。暗号化するJSONは8,192バイト以下。元の `request` と `confirmation` をキー昇順のJSONでまとめ、スラッシュをエスケープせず、SHA-256の32バイトを認証データに使う |
| 鍵の導出と暗号文 | 送信ごとの一時P-256鍵と新端末の公開鍵で鍵共有する。既存のHKDF-SHA256の入力に共有値、saltに `rideintercom.call-restore-credential.ecdh.v3`、infoに認証データを使い、AES-GCMで暗号化する |
| 送る項目 | `packet` は一時公開鍵のX9.63形式65バイトとAES-GCMの結合形式。認証データ `header` と `packet` のJSONへ `deliverCallRelationshipRestoreCredential` 用途で署名し、その署名を `proof` として添える。JSON内のバイト列はBase64で表す |
| 新端末で受け取る | 元の要求と応答、現在の新端末の証明、送信元が指定した照合先であること、暗号文の長さと署名を確認してから復号する。`fingerprint` が保存対象から計算し直した値と一致し、`secret` が長さの制約を満たすときに元の通話先の鍵として使う |

参加情報のハッシュ値は、`id`、`kind`、昇順のメンバーID列 `members`、`accountPair`、`accountDevices`、`invitationDeviceKeys`、`joinedByInvitation`、`removedMembers` をキー昇順のJSONにし、SHA-256で計算する。除外記録は保存順を使い、各記録の `memberIDs` と `priorInvitationIDs` は昇順にする。UUIDは大文字の表記とし、値がない項目や空の除外記録は省く。表示名・端末内の鍵参照・通知設定はこの計算に含めない。ハッシュ値は暗号文の中に入れる。

`directMembership` には、端末IDをキーとするアカウントと端末公開鍵の組 `devices`、照合先本人の表示名 `responderName`、保存されていれば `joinedByInvitation` を入れる。照合先が相手につけた呼び名や、端末内の鍵参照は含めない。新端末は元の要求と署名付き確認から復元する本人と相手を確定し、相手の端末と旧端末の公開鍵を `devices` で照合する。自分の表示名は新端末の設定を使い、相手は候補にある保存IDと暗号文内の本人の表示名で組み立てる。通話先IDと参加情報を復元したあと、暗号文内の `fingerprint` と一致する場合にだけ保存の検査に進む。

個別通話の照合先は、削除中継の照会とiCloudの読み直しを済ませてから `GroupRepository.sealDirectRestore` を呼ぶ。端末内の保管ファイルのロックを保持したまま、最新の通話先・登録済みの端末・確認済みの受諾IDを照合し、その通話先の通話鍵を読み込む。同じ処理で確認に署名し、新端末の公開鍵に合わせた暗号文を作る。保管ファイルが他の処理で変わった場合はエラーを返す。関係が消えた場合、照合に失敗した場合、対象の通話鍵を参照できない場合は応答を作らない。復元の呼出元に返す内容は署名付き確認と署名付き暗号文。端末の保存レコードや平文の通話鍵は返さない。

端末内の保存処理は暗号文と署名を受け取り、復号が成功してから照合済みの通話先と合わせて保存する。

### 個別通話の復元要求と応答を中継用に暗号化する

`DirectCallRestoreRelayPacket` は同じ発行元で別のアカウントに属する送信・宛先の検証済み端末証明を使う。両方の証明が期限内で、小文字16進64桁のセッション照合値を持つことを確認する。中継IDは送信ごとに生成した小文字UUID。期限のUnixミリ秒は現在から300秒後と両方の証明期限のうち最も早い時刻を切り捨てた値とする。

| 処理 | 形式と検査 |
|---|---|
| 暗号化 | 署名済みの要求は `{"request":{"value":…}}`、署名済みの確認と通話鍵の暗号文を含む応答は `{"response":{"value":…}}` のJSONにする。専用の用途名は `rideintercom.direct-restore.relay.ecdh.v1`。認証データには、用途名・宛先公開アカウントID・宛先端末ID・宛先セッション照合値・中継ID・期限・送信元公開アカウントIDをこの順で並べた空白なしのUTF-8 JSON配列を使う。一時P-256鍵と宛先公開鍵で鍵を共有し、用途名をsalt、認証データをinfoにしてHKDF-SHA256で32バイトの鍵を導出する。AES-GCMで暗号化し、一時公開鍵のX9.63形式65バイトと結合した結果を標準Base64にする。Base64は24,576文字以下 |
| 受付用の署名 | [Workerが定める6項目](../server/Worker.md#個別通話の復元で暗号文を一時中継する)を順に並べたJSON配列に `submitDirectCallRestoreRelay` 用途で署名する。宛先と中継期限だけでなく、暗号文も署名に含める |
| 復号と照合 | 受取側は自端末の証明とWorkerから受け取った中継ID・送信元・期限で認証データを組み立てる。期限切れ・別端末・更新前のセッション・改変があれば拒否する。要求は宛先と送信元本人を、応答は元の要求と指定した照合先が署名した確認を検証し、署名で確かめたアカウントをWorkerの送信元と照合する。要求では署名に添えた端末証明のセッション照合値も確認し、同じ端末証明を返信先として返す。その後の参加資格・通話鍵・保存の検査はそれぞれの処理で行う |

#### 中継を通じて復元の要求を送り通話鍵を保存する

以下は復元用の通信先を設定した構成での動作である。現在この構成を使うのはローカルWorkerとの結合試験。通常起動では通信先を設定しない。iOSがアプリの実行を止めている間は同期が進まない。

`CloudKitCallRelationshipBackupSession` は[Workerの一時中継](../server/Worker.md#個別通話の復元で暗号文を一時中継する)を、同じ発行元のHTTPSと現在の端末資格で呼ぶ。受信箱は最大8件とし、重複したIDや256KiBを超える応答を拒否する。操作の途中でAppのアカウント、端末資格、iCloudの利用アカウントが変わった場合は、その操作を引き継がない。

| 処理 | 条件と結果 |
|---|---|
| 新端末で要求を預ける | 選択に対応する要求を作り、署名付きの元の要求、Workerへ送る暗号化済みの内容と署名、受付確認の有無を、端末のKeychainに1件として確定する。保存と再読込による照合に成功した後、iCloudの候補と端末資格を再確認して自動送信する。送信の応答を失った場合は、次の同期で同じ送信ID・期限・暗号文を使用する。Workerの `queued` または `retired` が確認できたら、受付を保存して応答を待つ |
| 照合先が要求に応答する | 復元同期を設定したAppでは、起動・iCloud再接続、前面復帰、Internet復帰、端末資格の保存を起点に受信箱を確認する。同じセッションで1件ずつ処理する。照合先は署名付き要求を開き、宛先と[現在の登録と鍵](#現在の保存を照合して復元の確認を返す)を検査する。応答を用意したら端末に保存し、指定された端末へ預ける。Workerの受付後に要求の暗号文を回収する |
| 新端末が応答を保存する | 選んだ相手の要求を預けた後、同じ同期の起点で自動受信する。元の要求に対応する応答だけを開き、[現在の候補と照合して未保存の個別通話を追加する](#新端末に確認済みの通話関係を保存する)。通話鍵への参照と応答の回収待ちを同じ保存で確定し、その後にWorkerから応答を回収する。回収を確認したら次の相手を復元できる |

復元要求の保存は選択を合わせてUTF-8のJSONで48 KiBを上限とする。再開時は元の要求の署名と期限、送信端末の本人・端末ID・公開鍵・セッションの照合値、および現在のiCloud候補との宛先・受諾IDの一致を検査する。元の要求が期限切れ、または端末セッションが変わっていた場合は、古い送信の記録を外してから新しい証明を照会する。受付確認後は同じ要求を自動で再送しない。中継用の送信期限を過ぎても元の要求が有効な間は、既に作られた応答を照合できるよう要求を保つ。

照合先では、同じiCloud・アカウント・端末鍵に範囲を限ったKeychainを使う。受信した要求の中継IDごとに1件を保持する。保存するのは受信暗号文のSHA-256照合値、現在の通話鍵を指す保存参照、応答する端末セッションの照合値、Workerへ渡す応答の暗号化済みの内容と署名。1件は48 KiBまでとする。通話鍵そのものはこの項目に保存しない。応答を読み返せた後にWorkerへ送る。

| 照合先での経過 | 次回の処理 |
|---|---|
| 応答の受付確認を失った。要求と応答は期限内で、相手・現在の通話鍵と受諾ID・端末資格が引き続き一致する | 端末に保存した同じ送信IDと暗号文で再送する。再起動後も既存の要求に対して同じ手順を使う |
| 相手の削除、通話鍵の更新、宛先・資格・期限の変更で照合を通らない | 保存済みの応答を再送せず、同じ要求に新しい応答を発行しない。要求はWorkerの期限に従う。次の照会で受信箱から消えていれば端末内の応答記録を回収する |
| 応答の受付を確認した | 元の要求をWorkerから回収する。回収済みを示す404も確認とし、端末の応答記録を除く。通信に失敗した場合は次の同期で受信箱を調べる |
| 応答処理の途中に次の同期が要求された、またはアカウントが切り替わった | 同じセッション内では終了後にもう一度受信箱を確認する。アカウント切替では処理を中断する。成功した受信箱の照会結果にない要求の応答記録を回収する |

#### 通話鍵の保存後に応答の回収を続ける

新端末の `GroupSnapshot` schema 30以降では、復元した相手・通話先・鍵参照と一緒に `completedDirectRestore` を確定して読み返す。これは回収待ちの1件で、復元先の本人・端末ID・端末セッションの照合値、選択UUID、応答の中継ID、期限を持つ。schema 29までの保存では回収待ちは空とする。通話鍵は既存の端末内Keychainに置く。回収待ちはiCloudの復元候補に含めない。

| 新端末での経過 | 次の処理 |
|---|---|
| 通話関係と回収待ちの保存を確かめた | 同じ選択UUIDのKeychain記録を回収し、Workerへ応答の回収を送る。保存を確かめられない場合はWorkerの応答を保持する |
| ローカル保存の後で通信失敗・中断が起きた | 起動・前面復帰・通信復帰に回収待ちがあれば先に処理する。保存対象の再取得、要求の再送、通話鍵や名前の書き換えは行わない |
| 同じ本人・端末が回収を確認した。応答の期限か端末セッションの有効期間を過ぎた場合も含む | 同じ回収待ちだけを端末内から除く。同じセッションで期限内ならWorkerの成功または404で確認する。期限後や別の端末セッションからWorkerへ回収は送らない |

復元後は、双方が保存した相手を選んで元の個別通話を開始する。相手側は旧端末の登録を保持していても、通話の相手確認で現在の端末証明が元の相手のアカウントに一致すれば入室を許可する。新端末も同じ方法で相手側を確認する。通話鍵を使って接続できただけでは、相手を入室済みとして扱わない。

復元後、双方が元の通話に入室し、送信した音声パケットを相手のアプリが出力用データにするまでを[試験用の伝送層で確認した](../../validation/history/端末変更と通話関係の復元.md#復元した個別通話で双方の音声が出力処理に届く)。実際の近距離・Internet経路での通話、新端末が実iCloudから対象を選ぶ条件、双方のアプリが長時間実行できない条件は[残作業](../../backlog/未実装課題.md#icloud自動保存と招待をやり直さない端末復元)で扱う。

### 新端末に確認済みの通話関係を保存する

CloudKitを使う復元では、`CloudKitCallRelationshipBackupSession.restore` に、選択時の復元候補と確認済みの通話関係を渡す。保存の直前に保管先から候補を読み直し、読み込みの前後でiCloudアカウントとアプリのセッションを照合する。読み込み後にRideComの本人・端末ID・公開鍵とサービスの署名鍵も確かめる。読み込み中にアカウントや端末の署名鍵が切り替わった場合は、その結果を使わない。

個別通話の `restoreDirect` は、元の要求、署名付き応答、選んだ相手の保存ID、選択時の候補を受け取る。候補の所有者と新端末の本人を確認し、暗号文から参加情報を組み立てて `restore` に渡す。旧端末の保存レコードは必要としない。

通常グループの `restoreGroup` は、元の要求、署名付き応答、選んだグループIDと候補を受け取る。新端末の鍵で暗号文を開き、グループの参加情報を組み立てる。本人のiCloudを読み直し、同じグループID・保存名・招待経緯が残る場合に限って保存する。名前と削除・退出を決める招待経緯は本人の候補から引き継ぐ。招待経緯が欠けた候補からは保存せず、本人の記録を更新できるまで待つ。

復元する通常グループは識別子と名前、相手は識別子・アカウント・宛先照合用のハッシュ値が、選択時と読み直した候補の両方にそろうことを確かめる。対象が削除された場合、対象の内容が変わった場合、保管先の記録を確認できなかった場合は保存せず、候補の読み直しを待つ。対象外の変更は今回の保存を妨げない。

個別通話は、通話先と相手に加え、要求に含まれる宛先と受諾IDも最新の候補と照合する。要求作成と同じ計算で[保存時の照合値](#個別通話の復元を保存時の相手端末に照合する)が一致し、候補と要求が同じ受諾IDを示す場合に保存の検査へ進む。候補に必要な値が欠ける場合や、同じアカウントの別端末宛ての要求は保留する。

| 新端末で1人ずつ選ぶときの状態 | 結果 |
|---|---|
| 対象の相手と個別通話が未保存で、応答の回収待ちがない | 選択を保存できる。送信直前と応答の保存直前にも確認する。確定した個別通話を一覧に追加し、ほかの相手の呼び名、グループ、鍵、招待と進行中の通話を保持する。既存のiCloud候補には[自動保存の照合条件](#アプリの操作を起点に復元候補を自動保存する)を適用する |
| 同じ相手の保存IDまたはアカウントが登録済み、個別通話IDが保存済み、またはその相手を端末内で削除済み | 選択時に拒否する。選択後に同じ状態へ変わった場合は要求を送らず、届いた応答からも保存しない。同じ相手を明示的に再登録する場合は通常の招待を使う |
| 前の復元の応答が回収待ち | その応答の回収だけを再開する。回収後に次の相手を選べる |

`GroupSnapshot` schema 31は、相手の削除と同じ保存で、本人と相手のアカウントから求めた個別通話IDを `directCallRestoreExclusions` に残す。端末内の一覧と鍵を削除しても、古いiCloud候補から同じ相手が復元されることを防ぐ。IDの集合は端末内の保存に限り、iCloudやWorkerには送らない。schema 30までの保存ではこの集合を空にする。

通常グループを1件選んで復元する場合も、既存の相手・グループ・鍵と進行中の通話を保ったまま追加する。参加者を相手一覧へ登録しない。すでに保存したIDと、端末で削除・退出済みのIDは拒否する。schema 32では削除・退出と同じ保存でグループIDを `groupRestoreExclusions` に記録する。この集合は端末内に限り、schema 31までの保存では空になる。正当に受けた新しい招待は通常の加入処理で扱う。

この検査は、読み直した保管先に対象の候補が残っているかを確認する。iCloudの保存に反映されていない相手側の削除・退出・除外と、読み出しの後に別端末で起きた変更は、現在の参加資格を確かめる経路でも扱う。

端末内の保存を `GroupRepository.restoreCallRelationships` が担当する。復元元の読み出しと現在の参加資格の照合は呼出元の責務とする。

復元の呼出元は、保存データの所有者を確認し、最新の削除・退出・除外・失効を反映した相手と通話先を用意する。通話先ごとに現時点の参加資格と通話鍵を確認する。保存処理にはこの確認済みのデータ、新端末の有効な署名主体、既存の認証で登録したサービスの署名鍵、通話先ごとの署名付き要求・応答と暗号化された通話鍵を渡す。iCloudから読み出した内容や端末証明だけで、現在の参加資格を判断しない。

アプリ内では、元の要求・応答・保存する参加情報を `CallRelationshipRestoreContext` に入れる。これと暗号文を通話先ごとに保持する。CloudKit候補の照合、復号、保存ではこの組を使う。

保存処理は、鍵や通話関係を書き込む前に、通話先ごとの要求と応答をその時点の時刻と新端末の鍵で再検査する。検査結果の通話先と旧端末IDが保存対象と一致し、相手の本人・端末ID・公開鍵が通話先に登録されている場合に、検査結果の新端末IDと公開鍵へ置き換える。どれか1件でも照合できなければ、まとめて渡した一覧と鍵を保存しない。通話鍵を取得する経路と、照合先に届いていない失効を確かめる責務は呼出元に残る。

相手一覧に保存するアカウントは、同じ復元で確認した個別通話の相手と1人ずつ対応させる。端末を相手一覧に保存するには、暗号文と照合済みの参加情報に、相手のアカウント・端末ID・公開鍵の組が必要。未登録の端末や異なる公開鍵が含まれる場合は、相手一覧と通話鍵を書き込む前に処理を止める。通常グループだけを復元する場合は、その所属を保存する。グループの確認だけで、参加者を個別通話の相手一覧へ登録しない。

| 条件 | 保存処理の結果 |
|---|---|
| 所有者と新端末の証明が一致し、保存先が空 | 自分の参加情報を新端末IDと公開鍵に置き換える。相手・通話先のID、グループの参加経緯と除外記録を維持する。招待時の公開鍵は引き続き参加する相手の分だけを残す |
| 確認済みの通常グループとアカウント宛て個別通話 | 通話鍵を端末内のKeychainに新しい参照で保存してから、相手・通話先・鍵の参照を一度に確定する。招待の途中状態、確定前の招待枠、24時間の猶予を数える起点は引き継がない |
| 別人・期限切れ・候補の不整合・既存の保存あり | 復元を拒否し、既存の端末データを保持する。新端末が旧端末の公開鍵を使っている場合は、グループにその鍵が招待時の記録としてだけ残っていても拒否する。端末IDだけで識別する個別通話の復元と、既存データとの統合は後続の実装で扱う |
| 鍵の保存または検証に失敗 | 一覧を変更せず、復元済みとして扱わない。一覧の保存や読み返しに失敗したときは保存先を再読込し、一覧が確定したかを確認する |

## 目的

本書は、現行のRideCom App が RTC package をどう使うかだけを定義する。

接続、経路選択、近距離のQUIC制御・UDP音声、WebRTC、packet audio、handover、暗号化の詳細は[RTCの仕様](../packages/RTC.md)に従う。本書では App 本体に残る責務だけを扱う。

## 責務境界

| 領域 | App 本体の責務 | 詳細仕様 |
|---|---|---|
| グループ | group ID、表示名、group secret の保存と選択 | 本書 |
| ローカルメンバー | local member ID、display name の生成と保存 | 本書 |
| 招待 | join URL の生成、共有、受理 | 本書 |
| RTC 接続 | RTC へ credential、peer、route 設定を渡す | `docs/spec/packages/RTC.md` |
| 音声 media | 明示した通話で先にnative音声を準備し、相手の認証・利用条件の成立後にmediaを開始する。一時切断ではmediaだけを閉じ、入出力を維持する | `docs/spec/App/音声処理仕様.md`、`docs/spec/packages/RTC.md` |
| App data | RideCom 固有 namespace と payload schema を管理する | 本書 |
| UI 表示 | 接続状態、参加者、エラー要約を表示する | `docs/spec/App/UI` |

## 基本方針

| 項目 | 方針 |
|---|---|
| RTC 詳細 | App は route、packet、handshake、WebRTC native 型を直接扱わない |
| 接続と media | 接続成立と音声開始を分ける |
| 認証 | group secret 由来の credential を RTC へ渡し、認証結果は RTC event として受け取る |
| 設定 | RTC へ渡す route / codec / credential 設定は本書に重複定義せず、`docs/spec/App/Configuration` に集約する。通信 route の opt-out は Settings の `enabledRTCTransportRoutes` を RTC package configuration へ渡す |
| runtime status | RTC の package-owned runtime status を App data より先に decode し、通信相手の package 状態として保持する |
| 機密情報 | group secret と invite token はログへ出さない |
| ログ | RTC event / route metrics は `docs/policies/ログ記録規約.md` と `docs/spec/App/ログ仕様.md` に従って構造化ログへ変換する |

## App が保持する通信状態

| 状態 | 内容 |
|---|---|
| local member | この端末の member ID と表示名 |
| group list | 参加済みグループの ID と表示名 |
| group secret | 新規作成時に256bit乱数を生成しKeychainへ保存・読戻し確認する。接続・招待・再接続は同じsecretを使う。group一覧には保存しない |
| selected group | 画面で選択中の group |
| active group | RTC 接続中または接続準備中の group |
| members | RTC event と App data から得た参加者の表示状態 |
| connection summary | RTC の接続状態を UI 用に要約したもの |
| remote runtime statuses | `RTCRuntimeStatusTransport` で受信した peer ごとの package runtime status |
| enabled RTC routes | Settings で選択した RTC route の有効集合。既定は `.multipeer` と `.webRTC` の両方を有効にし、App は空集合を既定 route へ修復して RTC package へ渡さない |

## 設定値

RTC へ渡す route、credential、peer、codec UI 設定、Application Data namespace の設定は [設定値一覧](Configuration/設定値一覧.md) を正とする。

RTC package の型名や内部設定の詳細は `docs/spec/packages/RTC.md` を正とする。

## 接続操作

### 通話先と操作対象の共通境界

`IntercomViewModel`の`startCall(to:accountAccessID:)`は、`CallDestination`の保存ユーザーUUIDまたはgroup UUIDを実行時に解決する。ログイン世代と`canStartCalls`を確認してから既存の接続lifecycleへ渡す。現在閲覧しているgroupを宛先として暗黙に使わず、同じ進行中通話への重複開始は接続を作り直さない。保存ユーザーを削除すると、その相手の個別通話groupも同時に消える（[永続化と入力検証の所有](#永続化と入力検証の所有)の「ユーザー更新」）ため、そのユーザー指定と旧個別通話group指定のどちらからも新しい開始を拒否する。通常group内だけの相手を直接の通話先へ昇格させない。

ショートカットとSiri、Widget、iOS Control、Watchから開始する場合、Appが現在のログインと宛先を確認し、共通の`startCall`へ`allowSwitchingCall: false`を渡す。[自動切断期限](#自動切断タイマー)を過ぎた通話は先に終了し、その要求で次の通話を開始しない。宛先の照合後、表示先の変更や初回の個別通話の保存より前に、別の通話が接続待ちまたは進行中かを判定する。その場合は現在の選択と通話を保ち、個別通話や鍵を作らず、先に現在の通話を終了する必要があることをApp内の拒否理由にする。宛先が消えた場合も開始を拒否する。開始の結果は要求の受理を表す。接続成立、相手の応答、通知の送受信はそれぞれ別の結果である。利用者への応答は[ショートカットとSiri](#ショートカットとsiriの通話操作)、[WidgetとControl](システム表示と通話操作.md#操作の所有者)、[Watch](Watch操作.md#操作と状態の契約)の各入口で扱う。

[`CallReference`](../packages/CallControl.md)はログイン世代、接続世代、対象groupを保持する。`endCall(_:)`は一致する通話だけを終了し、別通話への切替・切断後の再接続・再ログインより古い終了操作を無視する。終了時に保存ユーザーや新規開始権利を要求しない。相手を削除するとその相手との進行中の個別通話は削除と同時に終わるため、削除前の参照による終了は無視される。transportが停止した後の明示的な再接続は、同じgroupでも新しい接続世代とする。

`setCallMuted(_:for:)`は同じ参照を照合して明示的な真偽値を設定する。同じ値を重複して渡しても反転・再送しない。通話前のマイク設定も扱い、その古い設定操作が新しい接続へ遅れて適用されることを防ぐ。Call画面のConnect・Disconnect・マイク操作は描画時の対象と値をこの境界へ渡し、既存の一覧選択による開始も同じ処理へ接続する。閲覧だけで別の進行中通話を切り替えない動作は維持する。

個別通話から相手の設定を開く操作、最近の通話の宛先、保存した招待返信の再開では、同じ保存ユーザーを照合する。アカウント宛ての個別通話は、登録済みの端末が変わっても、通話が保持する相手のprincipalから同じ人を解決する。端末宛ての通話は、保存した相手の端末IDで照合する。

この境界は端末内の共通操作であり、App Intents等のOS入口、利用権・24時間条件、通知送信の実装完了を表さない。操作要求のIDへ鍵・Bearer・保存モデル全体を複製しない。

### 直近の成立済み通話先

直近1件の`CallDestination`を、既存のアカウント別AppSettings保存先へ保持する。対象は保存ユーザーUUIDまたは通常group UUIDだけとし、表示名・相手鍵・通話記録を複製しない。現在の参加者署名を確認し、ローカル媒体も起動できた通話で更新する。選択・開始要求・transport接続・未確認のgroup鍵認証だけでは更新せず、媒体起動に失敗した場合も成立後の復旧まで前の記録を保つ。

個別通話は保持済みの直接相手へ解決してユーザーUUIDを記録する。通常groupの参加者をUsersへ追加せず、内部direct group UUIDを直近宛先として保存しない。`recentCallDestination`と`recentCallTitle`は現在のログインと保存一覧を照合して返し、名前変更は現在の名前へ追従する。Siri／ショートカットとiOS Controlからの直近再開は、`AppCallOwner.startRecentExternalCall()`が現在の宛先を取得し、共通の通話開始操作へ渡す。

対象の削除成功後は直近も無効化する。相手の削除はその相手との進行中の個別通話も終える。group読込や削除の失敗は対象消失と扱わず、記録を保持して再読込を待つ。不正な履歴データは未設定として扱う。サインアウト後は旧モデルから取得・更新・再開始できず、同じアカウントへの再ログインでは復元する。アカウント消去では同namespaceとともに削除する。音声設定の変更・Reset Allでは消さない。保存の永続化保証は既存UserDefaultsの設定保存と同じであり、この補助履歴のために通話を停止したり、server台帳・journal・端末間同期を追加したりしない。

### ショートカットとSiriの通話操作

App bundle内の次の操作を`AppShortcutsProvider`から公開する。対象を指定して開始する操作は`StartSavedCallIntent`。直近に成立した通話先への再開は`StartRecentCallIntent`。現在の通話の終了には`EndCurrentCallIntent`を使う。ミュートの値を明示して設定する操作は`SetCallMutedIntent`。`supportedModes = .foreground(.immediate)`と`requiresLocalDeviceAuthentication`を指定する。これらの操作は前面表示と端末の認証を必要とする。背景通知・ロック状態のまま送話を開始する経路や、新しい通話sessionを作らない。[Appleの実行mode](https://developer.apple.com/documentation/appintents/configuring-the-runtime-behavior-of-your-app-intents)と[認証policy](https://developer.apple.com/documentation/appintents/intentauthenticationpolicy)を参照。

`AppCallOwner`へAppの既存accountとViewModelの所有を移し、App初期化時に同じownerを`AppDependencyManager`へ登録する。画面はそのViewModelへのbindingを使い続け、Intentは`@AppDependency`から同じ実体を取得する。操作後はCallタブへ表示を戻す。[依存の登録](https://developer.apple.com/documentation/appintents/creating-your-first-app-intent)を参照。ログイン途中や古い世代の要求を保存・予約し、後のログインで自動実行する仕組みは置かない。

開始は[通話先と操作対象の共通境界](#通話先と操作対象の共通境界)に従う。App所有者は開始要求が受理されたときにCall画面の表示を更新し、Intentは開始した旨を応答する。拒否時は、App所有者が宛先や共通判定の理由を `CallIntentError` として返す。

`CallTargetEntity`はID、表示名、ユーザー／groupの区別だけを渡す。IDはアカウント別の端末member ID、種別、宛先UUIDで構成し、同じgroup UUIDを別アカウントで使っていても古いshortcutの対象を引き継がない。生Apple ID、鍵、Bearer、購入証明を含めない。queryと実行時の両方で現在の保存一覧へ照合し、削除済みの相手、内部direct group、group内だけの参加者を候補へ出さない。名前検索は現在の端末内表示名を使う。[EntityQuery](https://developer.apple.com/documentation/appintents/entityquery)を参照。

終了はperform内で現在の`CallReference`を取得して、awaitを挟まず共通終了へ渡す。

`SetCallMutedIntent`は実行時に同じApp所有者から現在の`CallReference`を取得し、awaitを挟まず共通`setCallMuted(_:for:)`へ渡す。Boolは明示値であり、二重実行で反転しない。ログアウト・旧ログイン・端末内データの再設定待ちなど共通操作が許可しない状態では変更しない。無通話時も共通仕様に従って次の通話用のマイク設定を変更できるが、それだけで接続・録音を開始しない。結果のmute／解除は論理設定の反映であり、マイク権限・機器・音声接続の成立を保証しない。

Siri用の追加phraseは`Set microphone mute in ${applicationName}`の1件とし、アプリ名placeholderを保持する。Boolをphraseへ埋め込まず、既定値のない必須parameterとして扱う。値を設定済みのShortcutsはその値で実行し、未指定ならOSが実行前に「Should the microphone be muted?」で値を要求する。[必須parameter](https://developer.apple.com/documentation/appintents/adding-parameters-to-an-app-intent)と[phrase省略時の質問](https://developer.apple.com/videos/play/wwdc2023/10102/)の契約を適用する。Siriの発話認識・実際の質問・OSのApp起動はローカルperform試験と分ける。

操作名・説明・通話先の種類・応答・Appが定義するエラーは英語と日本語の文字列リソースを持つ。呼出フレーズは`AppShortcuts.xcstrings`でアプリ名placeholderを保持して翻訳する。保存ユーザーの本人名・受取側の別名とgroup名は翻訳keyにせず、現在の表示名をそのまま挿入する。未知のエラー文は翻訳せず元の文を表示する。

App単体でのperform/query検証と、OS経由のforeground起動・Shortcuts表示・Siri発話・端末ロック解除の受入は分ける。利用権・24時間条件は今後も共通操作へ接続し、Intent側へ独立判定を追加しない。

### lifecycleへの接続

| 操作 | App の動作 |
|---|---|
| group 選択 | active group がなければ選択 group を画面へ反映し、credential と local peer を RTC へ渡して接続を開始する。既存の active group は勝手に切り替えない |
| connect | 切断済みの選択 group を再接続する |
| route opt-out | Settings で Local Network / Internet toggle を変更した場合に適用する。App は更新後の `enabledRTCTransportRoutes` を `CallSession.setEnabledRoutes(_:)` へ渡す。接続中のRTCがあれば停止する。最後の有効 route は OFF にできず、旧設定などで空集合を読んだ場合は既定 route へ修復する |
| 音声準備と媒体開始 | 近距離・Internetで[同じ音声の起動手順](音声処理仕様.md#起動停止とcallback所有)を使う。[準備と開始を別に判定する](#接続状態の表示境界)。WebRTCは符号化済み音声をDataChannelで運ぶ |
| codec 変更 | App の `preferredTransmitCodec` を RTC / Codec adapter へ反映する。経路が未対応の場合やcodecを利用できない場合は、代替codecの選択結果をDiagnosticsへ表示する |
| disconnect | RTC 接続と App の音声 pipeline を停止する |
| group 切替 | active group がある場合は明示操作で切断してから別 group へ接続する |
| 画面遷移 | 画面を戻るだけでは接続を切らない |

保存済みログインと通常グループの鍵が読み取れ、近距離を有効にしているときは、一覧のグループを選んで近距離接続を始める。Internetが無効な場合も、両経路を有効にしてInternetが初回の接続要求に応答していない間も、近距離で相手を認証し、通常の[通話利用権](通話利用権仕様.md)で音声を許可する。[保存状態からの回帰手順](../../development/音声E2Eテスト.md#保存済みグループから近距離通話を始める)

### 自動切断タイマー

| 条件 | 動作 |
|---|---|
| 明示的な新規開始・別通話への切替 | 資格・招待鍵を確認して接続処理を始めるときに、通常／Watchの選択時間からdeadlineを設定 |
| 相手待ち・音声準備失敗・一時切断・自動復帰 | deadlineを維持し、既存のcall tickerで期限を確認。重複startとmuteでも更新しない |
| 期限到達 | 共通disconnectで世代を失効し、音声と接続を終了。終了理由を画面へ表示し、自動再接続しない。次tick前でも開始・ミュート要求や音声の再準備から期限を確認して古い要求を拒否する。終了時の機器変更で音声一時停止を残さず、終了後の新しい明示開始は可能 |
| 終話・サインアウト・RTCの接続終了 | deadlineを消去。RTCからの終了は[接続の終了条件](#rtc-error-の扱い)に従う |
| 利用権との関係 | 購入者ありの開始から24時間の猶予とは独立。利用権の24時間経過だけでは継続中の通話を切らないが、自動切断は設定した時刻に適用 |

初期値と保存は[設定値](Configuration/設定値一覧.md)、表示と操作は[Settings](UI/Settings.md#自動切断)を参照する。新しい監視・polling・server側のタイマー台帳は設けない。

## RTC error の扱い

| RTC event | App の扱い |
|---|---|
| route scoped error | `connectionFailed(.webRTC, ...)` など route 単体の失敗は通話全体の `linkFailed` に変換しない。WebRTC の失敗理由を UI に表示し、RTC package の fallback / restore に任せる |
| `connectionBlocked(.webRTC, reason)` | `serviceBlocked`として手動復帰の意味を維持し、Callへ理由を表示する。「自動再試行中」と案内せず、他の有効なLocal通話は維持する。HTTP codeや理由の文字列判定はAppへ複製しない |
| `noEnabledRoute` | App 設定修復後も発生した場合は通話全体の失敗として扱う |
| `stateChanged(.reconnecting)` | `linkFailed(willRetry: true)`を通し、`connectionState = .reconnectingOffline`へ反映する。Internetが手動復帰待ちでも、Localの独立した再試行は妨げない |
| `stateChanged(.disconnected)` / `stateChanged(.failed)` | adapterはそれぞれ接続終了と再試行なしの失敗を渡す。Appの共通の終了処理が接続世代と終了期限を無効にし、期限を調べるtickerと音声を止める。接続・認証の参加者を外してidleへ戻す |

終了した接続の遅いイベントは旧世代として破棄する。利用者が再度開始した場合は同じ保存済みの通話先も選べる。新しい接続世代と終了期限を使う。接続失敗で案内した理由は保持し、開始・切断・Internet接続復帰で消す。

## 招待 URL

App はグループ参加用に `rideintercom://join?token=...` を扱う。

| 項目 | 仕様 |
|---|---|
| URL scheme | `rideintercom://join` |
| query | `token` |
| token 形式 | base64url JSON |
| 生成元 | 共有対象 group |
| 受理先 | App の deep link 入口 |
| 失敗時 | group へ参加せず、受理失敗として表示する |

### token 内容

| フィールド | 内容 |
|---|---|
| `version` | 現行は4。招待専用の確認情報を持たない旧1〜3は拒否し、新しい招待を受け取る |
| `groupID` | 参加先 group ID |
| `groupName` | 参加先 group 表示名 |
| `groupSecret` | RTC credential 生成に使う secret |
| `inviterMemberID` | 招待元 member ID |
| `inviterDisplayName` | 招待者本人の名前。Appは本人名を含める。省略時は既知の名前またはInviterを表示。UTF-8をbase64化して署名に含め、名前内の区切り文字を許す。相手側の別名は共有しない |
| `recipientMemberID` | 個別通話で必須。指定された端末member ID以外での受理を拒否し、署名の対象に含める |
| `issuedAt` | 発行時刻 |
| `expiresAt` | 失効時刻。Appの共有は7日間。招待確認情報の期限とも一致させる |
| `directInvitation` | 招待ID・group ID・招待者member ID・宛先member ID（個別通話）・期限と、その組合せ専用の32byte秘密。JSONのkey順を固定してbase64化し、group署名にも含める。招待URL外へ秘密を再送・保存しない |
| `signature` | 改ざん検知用署名 |

### 受理フロー

| 手順 | 動作 |
|---|---|
| decode | URL から token を復元する |
| validate | version、signature、expiresAt を検証する |
| store | GroupRepositoryで新しい参照UUIDの鍵をKeychainへ保存・読戻し確認し、参照を含むmanifestをatomic replaceする。旧鍵はcommit後に回収する |
| select | 受理した group を選択状態にする |
| report | 成功または失敗を UI に表示する |

## App data

RTC の `ApplicationDataMessage` は任意 payload の転送だけを担当する。RideCom 固有の namespace と payload schema は App が管理する。

| namespace | delivery | 所有者 | 用途 |
|---|---|---|---|
| `rideintercom.rtc.runtimeStatus` | RTC package が決める | RTC package | 接続、route、media、codec、local control、他 package runtime report を同期する |
| `rideintercom.keepalive` | reliable | App | 参加・設定変更時にpeerのlightweight metadataを同期。無音frame数による定期送信はしない。接続維持のpresenceはRTCが所有 |
| `rideintercom.profile-challenge.v1` | reliable | App | group認証済みのpeerごとにランダムUUIDの確認値を要求。group ID・宛先・最大1KiBを確認。接続中の端末署名確認に使い、一覧登録の根拠にしない |
| `rideintercom.display-name.v2` | reliable | App | group・送信member・宛先member・確認値・単調増加revision・本人名へ端末署名を付ける。最大8KiB。受信側の確認値、署名、保存済み端末鍵、利用可能な本人証明を照合する。v1の未署名更新は受理しない |
| `rideintercom.peerMuteState` | reliable | App | ローカルマイクミュート状態を相手画面へ同期する |

RTC package-owned namespace は App 固有 schema より先に `RTCRuntimeStatusTransport.decode(_:)` で判定する。decode できた場合は `remoteRuntimeStatuses[peerID]` へ保持し、App data として再解釈しない。

### `rideintercom.rtc.runtimeStatus`

| フィールド | App の扱い |
|---|---|
| `connectionState` / `isMediaStarted` | remote peer の control / media 状態として保持する |
| `routeSnapshot` / `routes` | active route、media route、route capability、media ownership を package 情報として保持する |
| `audioPolicy` / `routes.selectedAudioCodec` | remote peer の codec policy、送信 format、実選択 codec として保持する |
| `localMute` / `outputMute` / `remoteOutputVolumes` | remote peer が公開した local control 状態として保持する |
| `packageReports` | SessionManager、Codec、AudioMixer、Effectors など他 package の report として保持する |

### `rideintercom.keepalive`

| フィールド | 内容 |
|---|---|
| `activeCodec` | peer が最後に選択した codec。受信側の `GroupMember.activeCodec` に反映する |

### `rideintercom.peerMuteState`

| フィールド | 内容 |
|---|---|
| `isMuted` | 送話ミュート状態 |

未対応 namespace は無視する。未認証 peer からの App data 受理可否は RTC package の責務とする。

## Package runtime report 送信

App は RTC 以外の package runtime report を集め、`CallSession.updateRuntimePackageReports(_:)` で RTC へ渡す。RTC は payload を解釈せず、`RTCRuntimeStatus.packageReports` として package-owned runtime status に同梱する。

ローカル診断画面を表示中の0.5秒更新とネットワーク送信を分離する。診断画面を閉じている間のsnapshot作成は5秒間隔とし、開いた時点と設定操作時は即時更新する。RTCは最新reportを保持し、既定5秒のstatusまたは接続・操作の即時statusへ同梱する。診断値の更新回数に比例したnative通信統計の取得や送信は行わない。mute・codec設定など利用者操作の通知は待機させない。

| package | report kind | payload |
|---|---|---|
| AudioMixer | `snapshot` | `AudioMixerSnapshot` |
| Codec | `runtimeReport` | `CodecRuntimeReport` |
| VADGate | `runtimeSnapshot` | `VADGateRuntimeSnapshot` |
| SoundIsolation | `transmitConfiguration` / `receiveMasterConfiguration` | `VoiceIsolationConfiguration`（要求値） |
| DynamicsProcessor | `transmitConfiguration` | `DynamicsProcessorConfiguration`（要求値） |
| PeakLimiter | `transmitConfiguration` / `receiveMasterConfiguration` | `PeakLimiterConfiguration`（要求値） |
| SessionManager | `audioSessionConfigurationRequest` | `AudioSessionConfiguration` |
| SessionManager | `audioSessionConfigurationReport` | `AudioSessionConfigurationReport` |
| SessionManager | `inputStreamOperationReport` / `outputStreamOperationReport` / `voiceProcessingOperationReport` | `AudioStreamOperationReport` |

| 送信契機 | App の動作 |
|---|---|
| 接続開始 / 認証 / 切断 | report を強制更新し RTC へ渡す |
| media start / media stop | 音声 pipeline の開始停止結果を report に反映して渡す |
| 設定変更 | codec、bitrate、VAD、mute、ducking、output mute、master volume、peer volume、SoundIsolation を変更した時点で渡す |
| SessionManager report 受信 | session / stream / voice processing report を保持して即時渡す |
| 通話 tick | 診断表示中は最短0.5秒、非表示は5秒間隔で最新reportを渡す |

RTC package は接続開始、route変更、media開始/停止、local control変更、定期周期で `rideintercom.rtc.runtimeStatus` を送る。package report更新は周期へ集約し、周期を無効にした明示配信方式だけ更新時に送る。App はこの status を、通信相手の設定や操作状態の判断の基準として扱う。音声設定そのものの適用は即時であり、遠隔診断の更新周期によって音声処理を待機させない。

## 接続切替の所有と通知順

| 条件 | 現在の挙動 |
|---|---|
| 通話A中にBを閲覧 | selectedGroupだけ変更し、activeGroupID=Aと通話を維持 |
| BでConnect | Aを共通停止処理で終了し、認証・受信診断・VAD履歴を初期化してBを開始 |
| 通話groupの再表示 | 再接続しない |
| 閲覧中の非active group削除 | 通話を継続。active group削除時は切断 |
| RTC操作 | Adapter内でprepare、connection、media、stopを呼出順に直列実行 |
| RTC session再構成 | 旧sessionのstop完了後に新sessionを準備。event購読はprepare前に確保 |
| 旧接続の遅延通知 | AdapterとViewModelの世代チェックで破棄 |
| peer mute / metadata / runtime / audio | 認証済みpeerだけ反映 |
| peer切断 | RTC側の認証解除・再handshakeに従い、Appは該当peerの未再生PCMを停止。他peerが残れば通話継続、認証peerがゼロなら音声資源を停止して待受を維持 |

公開招待URLは維持。全員通話の中継に伴いRTC内部wireはgroup envelope / DataChannelへ変更し、同じバージョンのアプリを使う端末で試用する。Internet通話の完成・Workerデプロイ・実機通話確認は今回の自動検証の範囲外。

| 項目 | 契約 |
|---|---|
| 接続設定 | Settings の Worker HTTPS origin と端末 access token。Keychain に一括保存。保存時は現在の通話を終了する |

| 経路切替 | RTCが接続可能な全経路を維持。Appの音声pipelineを止めず、重複排除・中継はRTCが担当 |
| Local優先と媒体不達 | RTCが実媒体の最近の認証済み受領確認と、そのframeのUDP即時受付を照合してInternetコピーの省略を決める。初回・確認期限切れはInternetも送り、受領確認後の新しい音声からLocal優先へ戻す。AppはQUIC接続表示・native readyだけで到達性を推定しない。期限・wire・置換flowは[RTC仕様](../packages/RTC.md#local媒体の受領確認)を参照 |
| WebRTC 音声 | SFU DataChannelで共通packet audioを転送。AppのCodec / VAD / Mixer effect / peer volumeを適用。[交渉と媒体の契約](../packages/RTC.md#cloudflareの媒体契約) |

|---|---|
| RTCの経路 | InternetではICE接続とpublisher DataChannelのopenで経路の`mediaReady`となる。失敗routeだけを再試行し、他の有効routeを維持する |
| RTCの通話 | `RouteManager`は参加者がいる場合、Appの媒体開始要求がRTC側に反映済みなら通話の`mediaReady`、反映前なら`connected`を通知する |
| App adapter | RTC状態とavailableRoutesをViewModelへ渡す。経路変更でpacket audio所有権を切り替えない |
| 参加状態の通知 | 接続参加者のID一覧が変わったときに接続を通知する。認証済みの参加内容は、参加ID・表示名など経路以外の内容が変わったときに通知する。既存参加者のpacket到着経路だけで通話開始・参加許可・メタデータ再送の処理を繰り返さない。経路状態・到達経路の診断は独立して更新する |
| 端末の音声準備 | ViewModelの`isAudioReady`は端末の入出力が準備できた状態。相手に接続していなくても成立する |
| Appの媒体開始要求 | `isCallMediaStarted`は期限を持つ現在の通話で、ログイン、端末の音声準備、相手の認証、媒体の利用条件を確かめて開始を要求した状態。実行順は[Appのコマンド待ち](#app-command待機の所有)に従う |
| 会話中の条件 | `callStatus(for:)`が対象の進行中の通話で音声の準備完了と、現在の参加参照に対応する相手の本人確認を確かめる。商用条件を適用する場合は成立済みの利用権も必要。音声停止・準備失敗の表示は[画面の状態](UI/画面・状態遷移.md#call-操作遷移)に従う |
| 資格保存 | ViewModelからKeychain保存、切断、RTC設定適用を順に実行。Viewで通信実装を持たない |

相手へ音声が届いたことは、受取側の受信と出力で観測する。媒体開始要求、参加者一覧、経路の表示は、それぞれ上表の時点を示す。

## 混在グループと利用者への表示

| 状態 | 動作と表示 |
|---|---|
| Local / Internet両方 | `Local + Internet / Relay`。Local専用参加者と遠隔参加者を接続可能な参加者経由で中継 |
| InternetをOFF | 自端末はSFUに接続しない。他の参加者経由で遠隔音声を受けられる。Settingsで意味と電池・通信量を説明 |
| Internet失敗 | 通常は自動再試行を案内。既存Local通話を停止せず、失敗詳細はDiagnosticsへ表示。既存アカウント通話との競合はCallに手動復帰の理由を表示し、自動再試行と混同しない |
| 一部離脱 | 該当peerを除外。代替経路があれば残りの通話を継続。presence失効まで最大8秒 |
| 最後の中継者が離脱 | 分断された相手には届かない。同じ連結成分の通話は維持。再接続・再認証後に自動合流 |
| 音声機器が消失 | 自分の送受話を一時停止して再開を案内。中継は維持 |
| 手動route設定変更 | 現在の通話を停止する操作であることをSettings footerへ明示。自然な経路喪失とは区別 |

接続グラフ上の経路が存在し、認証・lease・OS実行・通信品質の条件が成立する間の到達性を対象とする。経路の切替瞬間の無音ゼロ、ネットワーク分断中の全員通話、予算上限後の無期限継続は保証しない。

試験範囲と確認状況は[検証](../../validation/README.md)を参照する。

## 本人名と端末内の呼び名

| 対象 | 契約 |
|---|---|
| 自分の名前 | Settingsで自由に設定。空白のみ・制御文字・UTF-8で320byte超は拒否。アカウント別UserDefaultsへ保存し、IDは変えない。招待と認証済みgroup通信で本人の名前を共有する |
| 再起動と通話継続 | 自分の名前はlocal identityに従い、保存groupを開く際にも反映。編集中の通話や鍵を作り直さず、新しい名前を通知する |
| 保存ユーザー | 呼び名はこの端末のユーザー一覧と所属groupで共通。本人名も常に確認できる。変更・復元を相手へ送信しない。受信した本人名の更新には、直接招待で保存した端末鍵との一致が必要。同じ鍵でも双方に確認済みprincipalがあり異なれば更新しない |
| 接続中の証明 | peerごとの新しい確認値とgroup・相手・宛先・revision・名前を`shareDisplayName`用途で署名する。`VerifiedPeerProfile`だけを保存処理へ渡し、未知group・別鍵・別の確認済み本人は更新しない。アカウント宛てdirectの未知memberは、相手principalの有効な証明がある場合だけgroup内へ追加する。不正な入力は保存障害にせず無視する。利用可能な自分の登録先の発行鍵で証明を検証し、証明がないLocalでは端末鍵を確認する |
| 音声許可 | RTCの現在の参加参照と接続ごとの署名確認結果を対応させ、アカウント宛てdirectでは相手principalまたは保存済み端末鍵も確認し、自分の確認済みprincipalは除外する。許可した参加者だけを`RTCAudioPolicy.peerPolicy.admittedMemberships`へ渡す。接続前・確認前は空集合。codec/format更新でも同じ確認状態を合成し、既定の全group参加者方式へ戻さない。受信待ちと音声の伝送の判定は[RTC](../packages/RTC.md#参加単位の音声許可)へ委ね、AppのUIイベントで音声を後から除外しない |
| 再送と順序 | 未確認の相手への確認要求は既存の通話tickを使い、1・2・4・8・16・32秒、以後60秒へ間隔を広げる。確認後は定期要求を停止。相手からの要求への返信はpeerごとに毎秒1回までとし、同じ確認値・名前なら同じ署名済みbytesを再送する。本人の名前編集時は新しいrevisionで送る。受信済み以下のrevisionは保存せず、古い名前への巻戻しを拒否する |
| 証明状態の寿命 | 最大7peerの確認値・署名応答・確認結果をメモリだけに保持。peer消失・通話切替・切断・全経路失敗・サインアウトで破棄し、再接続では新しい確認値を使う。別groupの閲覧だけでは進行中の通話の証明を破棄しない |
| group内だけの相手 | 呼び名は対象group内だけに保持。署名付き本人名を受けてもSaved Usersへ追加せず、別groupの名前や操作権限を増やさない。同じ接続中に確認した端末鍵の差替えを拒否する。直接招待で保存した鍵がない相手の自己提示鍵を、group外の権限に使わない |
| server | 名前の中央保存は追加しない。接続中の名前更新も既存の暗号化application dataを使用する |

この確認は端末署名と保存鍵の対応に基づく音声許可である。group内だけの相手は今回提示された端末鍵を使い、別groupへの権限を持たせない。RTCのgroup共有鍵による暗号化を維持しており、音声packet個別の署名・送信先ごとの暗号化を追加するものではない。 メンバーを外す操作は、自端末の音声許可を更新する。残ったほかの相手と音声を送受信する間、同じ鍵を持つ除外済み端末への送信や中継が起こり得る。

## 永続化と入力検証の所有

この節は端末内の通話関係の保存を定める。グループと登録した相手の一覧は端末内ファイル、鍵はKeychainに置く。[復元候補](#保存データから通話関係の復元候補を作る)はこの保存形式と別に管理する。現在の製品構成では、Appの署名権限にiCloudサービスとコンテナを含めない。

`GroupSnapshot`の現行形式はversion 32。保存には現行形式を使い、これより古い対応形式は下表の「旧保存形式の読取」に従って移行する。[応答の回収待ち](#通話鍵の保存後に応答の回収を続ける)と、[相手およびグループの削除](#新端末に確認済みの通話関係を保存する)で保持する項目と導入時の形式は、それぞれの契約に従う。

JSONの上限は1 MiB。ファイルを読み込む前とJSONをデコードする前に確認し、保存時も同じ値を使う。先に形式番号を読み、対応版より新しいときは通話関係の項目をデコードせずに未知形式と判定する。移行や保存前にも同じ対応範囲を適用する。

| 境界 | 現行契約 |
|---|---|
| GroupRepository | 読込、初回の空manifestの作成、既存JSONのスキーマ更新、新しい鍵の準備、manifest commit、不要鍵回収、明示resetを一箇所で所有。ViewModelはcommit・読戻し成功後に一覧を確定する |
| GroupSnapshot / FileGroupStore | アカウント別の `Application Support/<namespace>/Groups/groups.json` に従う。現行形式を使い、group/directのkind、generation UUID、独立したusers配列、group ID/nameを保存する。memberにはID、displayName（本人名）、localName（端末内の呼び名）、usersへのuserID参照を保存する。credentialReference UUIDも保存する。アカウント宛てdirectでは二人のprincipalと確認済み端末鍵をgroup内にも保存。groupごとに購入者相当を含めた成立時刻lastSponsoredStartを任意値として保持し、現在の通話成立状態とは分ける。通話状態・認証状態・mute・音量・packet counter・secretは保存しない。最大256group、JSON最大1 MiB。トップレベルのcontactInvitationsとgroupDeliveriesは各専用契約に従って保持する |
| SavedUser | 端末内で安定したUUID、名前displayName、任意の端末内呼び名localName、既知のmember ID配列。直接招待した・された相手を自動保存し、グループ削除後も保持。表示名の一致で別人を統合せず、仮ID・他のgroup参加者から自動生成しない。直接招待で確認した端末公開鍵をmember IDごとに保持する。同じサービスoriginと確認済み公開userIDを持つ直接招待相手の別端末は1つの一覧項目へ統合する。端末内UUIDと認証済みprincipalを区別し、どちらも単独では通知の認可根拠にしない |
| ユーザー更新 | 受け取った本人名と自分用の呼び名を別々に保存し、同じmanifest内の該当group memberへ反映する。本人名の更新で呼び名を上書きせず、Use Shared NameでlocalNameを消すと最新の本人名を表示し、以後の本人名更新にも追従する。一覧から相手を削除するときは`GroupRepository.removeUser`を使う。対象の個別通話groupは`kind == .direct`である。端末宛ては相手のmember ID、アカウント宛ては相手のprincipalで対応付ける。usersの相手、該当する個別通話group、鍵、未応答の受取証明を同じatomic commitで消す。保存に失敗したら両方とも元のまま残る。進行中の通話がその個別通話なら切断し、選択も外す。通常groupのID・表示名・所属・鍵は保持する。通常のgroup再保存で削除ユーザーを再登録しない。読込時（通話のない時点）に、相手の保存ユーザーがいない個別通話group（以前のアプリで相手だけを削除して残ったもの）を見つけたら、鍵とともに消してcommitする |
| 直接招待の登録 | 有効なversion 6招待URLの受取時に招待者を登録し、招待専用秘密から受取証明を作る。受取証明は`rideintercom.direct-invitation.v3`の認証済みapplication dataで送る。招待者は保存済みの発行者用乱数から同じ招待専用秘密を導出する。期限・group・送信peer・宛先・受取ID・受取人公開鍵を含むHMAC・受取端末署名を照合した`VerifiedDirectInvitation`だけを保存処理へ渡す。group所属や未確認の自己申告から保存ユーザーへ昇格させない |
| 端末署名 | 発行・受理・ACK・接続中の本人名を異なる用途としてP-256署名する。`rideintercom.device-proof.v1`のdomain、用途、member ID、端末公開鍵、任意の証明と発行公開鍵、対象payloadを、この順に並べる。各UTF-8/byte列の4byte big-endian長とともに署名する。発行は招待全体のHMAC、受理は一意な招待・受取IDと内容、ACKは受取署名を含む内容を対象とする。一意な招待IDが使い回しを拒否するため、一覧保存のためだけの追加challenge往復は行わない |
| 信頼とLocal | 端末の秘密鍵はInternet登録と共通のアカウント別Keychainで管理し、Localだけでも用意できる。自分のHTTPS登録先から取得済みの発行鍵で検証でき、member ID・端末鍵が一致した証明だけをprincipalへ対応付ける。証明未取得・期限切れ・別サービスの証明は同一ユーザーの根拠にせず、直接招待の端末鍵の確認だけでLocal利用を継続する。相手の証明を信頼する起点には使わない |
| 鍵と名前の衝突 | 保存済みmember IDの鍵が違う、同じ端末鍵でも確認済みアカウントが違う場合は既存の相手を上書きしない。同一人物への統合では既存UUID・呼び名を維持する。別々の項目の呼び名が衝突する場合は自動で片方を消さず、一覧の名前整理・削除後の新しい招待で解決する |
| 受信の失敗 | 不正な署名は保存障害として扱わず破棄し、一覧編集を使用不能にしない。ACKは元の招待発行端末の署名を必要とする。再送・ACK作成時に元の鍵が欠けていたら新しい鍵で代用しない |
| 招待発行者の鍵 | アカウント別namespaceの`.DirectInvitations` service、`author` accountへ32byte乱数をKeychain保存する。初回はSecItemAddで既存値を置換せず、同時作成時は先に保存された鍵を読み直して使う。読取不能・不正な既存値を別の鍵で上書きしない。group ID・招待ID・招待者とその公開鍵・宛先・期限を区別したHMAC-SHA256から招待専用秘密を導出する。非公開鍵はURL・manifest・application dataへ出さない |
| 再送と削除 | 通常group/direct招待の受諾側は未応答の受取証明をmanifestへ保持し、招待者との認証成立後・既存keepalive時に期限内だけ再送する。招待専用秘密は保存しない。受取IDは招待IDと受取人member IDから固定し、同じURLの再受理も同一の受取となる。招待者は処理済みIDを保存してから応答し、一覧削除後に再送・再受理・任意IDへの付替えで再登録しない。新しく発行した招待は別の受取となる。受理側も同じ処理済みIDを保存し、削除した招待者を古いリンクから復活させない。schema 5への更新では旧形式の未応答receiptだけを終了し、group・ユーザー・鍵を維持する。旧形式の無署名ユーザーをmember IDだけで確認済みの相手へ昇格させない |
| 使用済みの通常グループURL | schema 16のgroupLinkReceiptsに、署名済みの通常グループURLを受諾したときのgroup ID・受取証明のID・期限を保持する。グループを抜ける保存で該当IDを同時に無効化する。同じURLは再起動後や新しい招待で戻った後も受け付けず、現在の通話・グループ鍵・個人の登録を保つ。旧データはグループに残っている処理済みのIDを使う。署名の期限が分かる無効化済みIDは期限後の保存時に回収する。期限の記録がない旧IDは保持する。 |
| 招待の発行時点 | 画面と診断の可否表示はメモリ上の状態だけを使い、鍵を読み込まず、鍵の作成や署名もしない。OS共有画面がURLデータを要求した時点で、表示時のgroup ID、現在のログイン世代、保存状態、所属、個別通話の宛先を再確認し、鍵を取得して新しい招待IDを発行する。画面切替・相手削除・再ログイン・保存競合後の古い共有要求は拒否する。新しい共有要求を過去の招待URLの無期限キャッシュに置き換えない |
| 競合した個別通話の再共有 | 同じ個別通話の異なる鍵が届いたとき、保存済みの鍵を保持する側を既存のprincipalまたはmember IDの順序で決める。保持する側のStandardには[案内と共有操作](UI/Call.md#ユーザー指定の個別通話)を出す。対象の通話IDと既存の鍵から、同じ相手宛ての招待を既存のURL発行処理で作る。相手がそのURLを開いて受理した時点で鍵を揃える |
| 招待確認の境界 | 通常groupのURLは所持者が受け取れる招待情報であり、転送すれば招待情報も渡る。個別通話は署名対象の端末／アカウント宛先を照合するが、URL内のgroup秘密情報そのもののコピーを防ぐものではない。group内で受取証明だけを見た第三者は別の受取人・招待・期限・受取IDの有効な証明を作れない。本人名も受取端末署名で保護するが、名前の一致ではIDを統合しない。直接招待の本人対応と、通知先の用途別許可・解除は別契約であり、この確認値を公開通知APIの認可へ流用しない |
| group内だけの相手 | 直接招待関係がない参加者のID・表示名はgroup内で保持するが、独立ユーザー一覧へ登録せず、一覧を使う別groupへの追加対象にも解決しない。ユーザー指定の個別通話にも解決しない。グループ内だけの相手は個別通話の呼出し通知の対象外とし、group共有や相手IDの知識をgroup外操作の権限にしない |
| 仮名の由来と選択 | `SavedUser.usesProvisionalName`は空欄で生成候補を採用した場合だけtrue。nilは由来不明の旧データ、falseは手入力・明示編集・選択済み。`needsNameConfirmation`はtrue・登録済み・localNameあり・本人名と異なる場合に導出する。文字列から生成元を推測しない。`resolveProvisionalName`は表示した旧名と本人名を確認する。本人名を使うならlocalName=nilとし、維持するなら現在値を使う。どちらもマーカーをfalseにして同じmanifestで保存する。編集・リセットもマーカーを解除する。本人ID・招待・鍵を変えない。schema 10に任意のメタデータとして追加し、旧データと名前の選択を保持する。画面の接続状態は検証記録へ分ける |
| 旧保存形式の読取 | schema 1・2のgroupはkind=group、schema 3以降は既存kindを維持する。ID・member・最後の保存名・鍵参照・受取記録・users・contactInvitationsを保って現行形式でatomic commitし読戻す。schema 27までの通話には確認済みの受諾IDを補わない。schema 28までの保存では端末証明の預け入れと取消の記録を空にする。旧形式の未署名の送信待ち受取証明は破棄する。失われた本人名・未確認の旧ユーザー鍵は推測せず、本人確認のうえ一覧から削除して新しい直接招待で登録し直す。schema 1の所属からusersを登録しない。失敗時は旧bytesと鍵を保持。schema 2以降のusers不整合、schema 3以降のkind欠落・不正は読込失敗。schema 5の署名済み送信待ちreceiptは維持する。schema 5以前でaccountPairを宣言した入力は拒否し、各版は対応範囲より新しいschemaを拒否する。新しい起算点の欠落から時刻を作り直さない。schema 9の受信pendingに対応する人が残っていない場合は、移行の同じcommitでcancelledにしてKeychain参照を外す。相手や通話を旧返信から作り直さず、再登録の通信を始めない。移行失敗時は旧snapshotと参照を保って再読込から回復する。 |
| KeychainGroupCredentialStore | RideIntercom.GroupCredential.v2 service内の新しいUUID accountへ鍵を保存。参照先の鍵を上書きしない。保存後に同じ値を読めることを確認してからmanifestへ参照を追加 |
| commit境界 | 同じdirectoryでのJSON atomic replaceを唯一の確定点とする。replace前の中断は旧一覧と旧鍵、replace後の中断は新一覧と新鍵を選ぶ。途中で残った未参照鍵は正常読込後または次のcommit後に回収 |
| 多重起動 | 読込・移行・commit・回収・resetを同じflockで排他。取得できなければ待ちTaskを増やさず失敗。読込時のgenerationを含むsnapshotが変わっていれば書込を止め、Reloadを要求 |
| 復元 | groupは1–8人、ID重複なし。member IDはASCII英数/ハイフン/アンダースコアの1–63 byte、表示名は空白のみ不可・制御文字不可・UTF-8最大320 byte。local memberを先頭へ配置し、不在なら読込失敗 |
| 読込失敗 | 空の初期データと区別。元データと鍵を保持し上書き・回収を禁止。GroupsのReload Saved Groupsで再試行。通話中は先にDisconnect |
| 保存失敗 | group作成・参加・削除をUIで成功としない。replace後の読戻し失敗では実際にはcommit済みの場合があるため、旧状態へrollbackせず再読込で確定する |
| 更新候補の不正 | identity/人数のdomain違反はcommit前で拒否し既存snapshotを保持。保存済みデータの破損とは区別してReloadを案内し、reset操作は出さない |
| 鍵の欠落 | Keychainのnilと読取errorを区別。nilはgroupを残して再招待を案内。アクセスerrorは読込を止め、端末ロック解除などの後にReload |
| 鍵回収失敗 | commit成功を取り消さない。回収待ちを表示し次の正常読込・commitで再試行。削除groupは復活しない |
| 初回の読込 | manifestが存在しない場合は現行スキーマの空manifestを確定し、読戻しを確認する。書込が失敗した場合は読込を失敗として扱い、再試行できる |
| 破損のreset | 確認後、排他内で保存ファイルを読み直す。破損を確認した場合だけ、同じdirectoryへ元のJSONを退避してusers・groupsが空のmanifestをcommitする。退避できなければ削除しない。group鍵のみ回収し、rider identity・音声設定・Internet資格を保持する。復旧済み、ファイルなし、破損以外の読取エラーのいずれかなら、保存データを変更せずに処理を終える |
| 未知schema | versionを先に確認し新しい形式は対応版で開くよう案内。旧形式へfallbackせず、resetも拒否する |
| runtime更新 | voice level、talking、codec、認証・接続通知、frame counterの変化では保存しない。参加者追加・置換など永続情報が変わった場合だけ保存 |
| 人数 | 自分を含む最大8人。通常groupは確認済みprincipalごとに代表memberを1つ保存し、保存ユーザーを追加するときも同じ人の端末を人数へ重複算入しない。SavedUser.groupMemberIDsを選択画面の人数・保存可否と実保存に共用し、作成／追加の前から同じ枠数を示す。principalを確認できないLocal相手は従来のmember ID単位。満員時に別人を自動で追い出さず、メンバーを整理してから追加する |
| 通常groupの代表端末 | 既存のaccountDevicesへprincipalと端末公開鍵を保持する。現在の認証・challenge確認が有効な旧代表は維持し、離脱後の別端末が現在のchallengeに応答して同principalを証明したときに置換する。待機中の旧応答は離脱時のchallenge更新で無効化する。本人確認の一時候補は人数枠と分け、通常groupでは相手7人×2端末の最大14件を保持する。同じmembershipで確認済みの継続代表を優先し、新候補のID順で接続中の代表を落とさない。membershipが変われば新しいchallengeで確認し直す。追加の保存台帳・アカウント登録端末数の上限・polling・端末間合意は設けない。自分の代表はローカルmemberのままで、別の本人端末を重複参加させない |
| 代表の交換と保持 | group ID・名前・秘密鍵・自分を先頭とする所属・相手の呼び名・24時間起点を保持する。旧端末の音声・ミュートなどruntime値は新端末へコピーしない。既存groupに同本人の別端末から明示招待を受けても、旧代表が有効な参加中は代表を維持し、直接招待の受取だけを保存する。認証前の発見では保存を変更しない。保存失敗時は新代表を音声許可へ加えず、成立済みの通話を保存失敗だけで切らない |
| 代表と関係の範囲 | 通常group内の本人確認はSavedUser・その端末鍵・member ID一覧・通知許可を追加しない。既に直接保存した同principalの相手ならそのUUIDと本人名・呼び名を参照する。ユーザー削除後はgroup情報だけを残し、プロフィール更新で連絡先を復活させない。音声許可・利用権参加者・全相手消失・通話中表示・直近通話先は同じ現在代表の確認結果を使う。groupから削除した代表の音声許可も取り消す |
| 招待で確認したメンバーの端末鍵 | schema 14では、通常groupの既存メンバーについて、署名を確認した招待の受諾・返信・自動送信で得た端末公開鍵を `invitationDeviceKeys` に保持する。個人の登録を削除した後や端末証明が取得できないときも、近距離とInternetの本人確認で同じIDの別の鍵を受理しない。対象のメンバーを外すか、確認済みの同一アカウントで代表端末が交代すると、退いた端末の公開鍵も同じ保存で除く。旧データでは既存の端末鍵・メンバー・通話の鍵を保持し、招待による公開鍵の確認をあとから推定しない。 |
| メンバーの除外 | schema 13以降の通常groupは、外した人の既知のmember ID・確認済みprincipal・確定時刻をそのgroupのremovedMembersに保持する。メンバーと既知の端末を外す保存と同じcommitで更新する。近距離・Internetに共通する本人確認でこの記録を参照し、再接続後もこの端末では対象をメンバー一覧・利用権判定・受信音声許可へ入れない。登録済みの相手は保つ。明示的に相手を選んで追加した保存、または除外より後に自分から保存した名前付き招待の検証済み返信で、再接続の拒否を解除する。schema 15では除外と同時に同じgroupの保留中の送信招待IDを保存する。再追加後も対象の端末IDか対象のアカウントから届く該当の返信を拒否し、個別通話の鍵・所属・名前を保つ。別の相手の返信は受け取れる。古い招待が保留を離れたら再追加済みの除外記録を回収する。schema 14以前の除外は従来どおり発行時刻を照合する |
| 削除 | manifestからgroup参照を除いた後にKeychainの未参照鍵を回収。独立usersは残す。配布済み招待や別端末の鍵は維持される。他端末の一覧と送信・中継を含む音声経路全体への除外反映は[受取確定後のメンバー除外](../../backlog/未実装課題.md#受取確定後のメンバー除外)で扱う。別groupの参加者削除でactive groupの認証・音声状態を変更しない |
| Internet設定 | composition時に一度読み、Adapterへ注入。Keychain読込/JSON不正は未設定と区別して表示。transport層から保存先へ直接アクセスしない |

通常groupの「外す」は、操作の認可と、保存・通話への反映を順に行う。反映は保存が成功してから行い、外した人の受信許可を更新し、残る人は同じ通話を続ける。受信時の認可と転送は引き続き[削除同期](../../backlog/未実装課題.md#受取確定後のメンバー除外)で扱う。

schema 17は、検証済みの除外を適用する保存で、group ID・イベントID・署名済みデータのSHA-256・期限を同じmanifestに置ける。自分自身が外れた場合はgroupの削除と同時に確定し、groupを消した後も期限まで同一の受取を判別できる。別のデータによる同じIDの再利用を拒否する。期限済みの記録は次の保存で回収し、有効な受取は最大1024件。schema 16までの保存は受取を空で移行する。製品の受信口・利用権の認可・転送応答は[削除同期](../../backlog/未実装課題.md#受取確定後のメンバー除外)で扱う。

この設計はプロセス中断時の旧/新snapshotの整合性を対象とし、電源断・媒体故障に対する耐久性を保証しない。fsyncを含む永続transaction、履歴の選択復元、破損内容の推測修復は設けない。退避ファイルは自動復元しない。Keychainとmanifest自体が別々に消去された場合は再招待が必要。UserDefaultsに残る設定・identityのset成功もディスク同期保証ではない。

### 個人削除の送信待ち

個人削除の確定時に、保存した相手の端末鍵と、その端末との個別通話鍵、自端末の既存署名鍵があれば `ContactDeletionNotice` を作る。対象は端末ID2つで特定できる個別通話。アカウント宛ての個別通話やローカルの名前だけの相手には、従来の端末内の削除を適用する。

| 境界 | 契約 |
|---|---|
| 保存 | schema 19の `contactDeletions` に、イベントID・両端末ID・宛先鍵・期限・認証タグ・送信端末の署名を保持する。名前・音声用の鍵・サービス証明書は保存しない。個人、個別通話、招待の更新と同じmanifest置換で確定する。保存の失敗時は送信待ちも作られない。成功後は旧個別通話鍵を回収する。schema 18以前の一覧は空で移行し、既存の近距離取消を保持する |
| 認証 | 個別通話鍵からHKDF-SHA256（salt `rideintercom.contact-deletion.v1`、infoは空、32 byte）で鍵を導出する。sortedKeysのJSONで表した対象に、この鍵でHMAC-SHA256を計算する。対象と認証タグを既存の端末署名の `deleteContact` 用途で署名する |
| 照合 | 受取端末が確認済みの送り主IDと鍵、自端末IDと鍵、および現在の個別通話鍵を使って検証する。署名・HMAC・宛先がすべて一致し、`now < expiresAt <= now + 28日 + 300秒` のときに有効。新しい個人招待で個別通話鍵を交換した後は、旧鍵に対する削除を拒否する |
| 初回受取 | 受取端末の保存済み相手が送り主の1端末だけで、確認済み端末鍵と現在の端末対の個別通話鍵を読める場合に照合する。検証後は通知を抑止し、個人・個別通話・保留招待の削除と受取確認を同じmanifest置換で確定する。確定後は対象の個別通話を終了し、通常グループの所属・通話を維持する |
| 双方が先に削除した場合 | ローカルの削除と同じ保存で、schema 23の `contactDeletionFormerPairs` に旧い端末対のID・公開鍵・期限を残す。削除用のHKDF鍵をbase64urlでアカウント内のKeychainに保持し、manifestには参照だけを置く。両アカウントを確認済みなら、相手が送信元となる逆向きのslotも保持する。自分の送信待ちを回収した後も旧い相手からの削除を検証できる。旧い端末IDまたは確認済みアカウントの現在の登録がある場合は、現在の関係の鍵で照合する。現在の登録がなく、削除用の鍵・端末署名・期限が一致した場合は、個人やグループを変更せず、受取確認だけを保存する。同じ保存で旧い端末対の記録を外し、確認成功時に使用済みの鍵を回収する。未使用の記録はローカル削除から28日で失効し、次の保存で回収する。schema 22からは従来の送信待ち・確認を引き継ぐ |
| 受取確認 | 受け手は削除のsortedKeys JSONのSHA-256、元の対象、送り主の公開鍵を `acknowledgeContactDeletion` 用途で署名する。schema 20の `contactDeletionReceipts` に保存する。保存に成功してから確認を返し、再起動後の再送では同じハッシュ・相手・宛先・期限に一致する場合だけ保存済みの確認を返す。同じIDで内容が異なる場合は拒否する。schema 19の移行では送信待ちを引き継ぎ、受取確認は空で開始する |
| 近距離での転送 | 近距離が有効な場合は、招待と共有する `RTCLocalDataChannel` の宛先別認証を使う。[探索の開始と停止](#自動探索の開始と停止)も共有する。確定済み端末鍵、期限内の送信待ちと受取確認を使って相手を照合する。保存済みの現在の鍵を優先し、両端末の鍵と削除の対象が一致するときだけ `contactDeletion` を送る。受け手は `contactDeletionReceipt` を返す。現在の個人登録で送信・受取を認可するグループ招待と、送信・確認に使う削除記録の認可は独立する |
| 試行と再開 | 削除を保存すると、近距離で招待に使う20秒の有限試行へ同じ送信待ちを加える。iOSの背景実行時間を同じ入口で要求し、先に実行時間が切れたら送信待ちを保持する。起動・復帰で近距離が使える時に同じ削除を試みる。Internet利用の有無にかかわらず、個別通話と同じ相手鍵で照合する。受取確認を失った場合も、再接続時の再送で保存済みの確認を返す |
| Internet用の送信待ち | 既存の端末対の削除を作れる場合に、両者が同じWorkerで照合済みの別アカウントなら、schema 21の `contactDeletionPublications` へ暗号文を同じ保存で確定する。送信元アカウント・端末公開鍵、イベントID、slot、期限のUnix ms整数（秒値から切り捨て）、宛先アカウント・端末公開鍵、暗号文を保持する。接続・通知許可の状態にかかわらず一度だけ暗号化する。schema 20以前の移行では、元の削除と受取確認を引き継ぎ、Internet用の送信待ちは空で始まる |
| slotと暗号文 | slotの導出にはHKDF-SHA256を使う。入力鍵材料は旧個別通話鍵のUTF-8、saltは `rideintercom.contact-deletion.slot.v1` とする。infoは送信・受取の順に端末IDをNULで連結する。出力32 byteを小文字hexにする。暗号鍵は両端末のP-256 ECDHからHKDF-SHA256で導出する。saltは `rideintercom.contact-deletion.relay.v1`、infoは端末IDの昇順で端末IDと公開鍵の組を並べ、最後にslotを足し、各項目をNULで連結する。鍵は32 byte。署名付き削除のsortedKeys JSONをAES-GCMで暗号化する。追加認証データにはUTF-8の `rideintercom.contact-deletion.notice.v1` を使う。保存するpacketはnonce・暗号文・tagの順の標準base64とする |
| Internet用の受取確認 | 両者が同じWorkerで照合済みの別アカウントなら、受け手は初回に削除を検証した時点で旧個別通話鍵から同じslotを導出する。送信側と同じ暗号鍵で署名付き確認のsortedKeys JSONを暗号化する。AES-GCMの追加認証データにはUTF-8の `rideintercom.contact-deletion.receipt.v1` を使う。送信元と受取側の公開アカウントID・issuer、slot、ID、Unix msの期限、packetをschema 22の `contactDeletionRelayReceipts` に記録する。この記録は個人削除・署名付き確認と同じ保存で一度だけ確定する。再送・再起動後も同じ暗号文を使う。schema 21以前からは従来の記録を引き継ぎ、Internet用の受取確認は空で始まる |
| Internet経由の転送 | 送信元アカウントと現在の端末鍵が一致する場合に、保存した暗号文を[Workerへ送る](../server/Worker.md#個人削除の暗号文中継)。受け手は同じWorkerの確認済み相手の1端末と個別通話鍵からslotを求め、端末証明付き署名で取得する。暗号文を開いた後にID・期限と既存の削除署名を照合してから、一度だけ適用する。受け手は保存した確認をWorkerへ送り、Workerが確認を保持した応答で端末内の送信待ちの確認暗号文を回収する。近距離用の署名付き確認は期限まで保持する |
| Internet試行の条件 | 起動・前面復帰時の転送処理と、削除・確認の保存後に実行する。実行中のアカウントと端末資格を通信前後で照合する。保存後に配信すべき削除・確認・回収があれば、招待の送受信と共通のiOS背景時間を直ちに要求する。ユーザーの通知許可・相手の通知grant・APNsは配信条件に含めない。[回線復帰を受け取ったとき](#回線復帰を受け取ったときの個人削除の照会)も送信・受信を同期する。OSによる実行時間終了の後は、次の同期機会に同じ暗号文を使う |
| 期間と回収 | 期限は削除確定時刻から28日。送り手が期限内に元の削除と宛先の検証鍵に一致する署名付き確認を受け取ると、送信待ちを回収する。Internet用の記録があれば同じ保存で暗号文と宛先を消し、Workerが回収したと応答するまで送信元・slot・ID・期限を残す。近距離で先に確認し、Workerへの送信が未受付なら、回収を先に依頼する。期限切れの記録は次の保存で回収する。[同期の残作業](../../backlog/未実装課題.md#個人の削除を相手側へ同期する)、[Internetの実環境受入](../../validation/未確認事項.md#internetの個人削除の実環境受入) |

#### 回線を待つ個人削除の送出

個人削除を保存した直後、iOSは現在のアカウント・端末鍵に対応する未送出の暗号文を[招待と共通の背景URLSession](#グループ自動配送の実行契約)に渡す。送信ID・現在の端末セッション・個人削除の操作につき1件。復元中に保存した場合は、同期の最初に既存タスクを取り込んでから渡す。有効な端末証明とWorker公開鍵を使い、`publishBackgroundContactDeletion` 用途で署名して[個人削除の背景受付](../server/Worker.md#背景転送から個人削除を預かる)宛てに封印する。背景用ファイルと通信に使うのは封印した要求で、Bearerを添えない。通知許可とAPNsに依存しない。

OSに渡している間は通常の送出を重ねない。鍵がないか背景転送を開始できない場合は、保存済みの暗号文を通常HTTPで送る。転送が終了しても成功を確認できない場合は、同じ記録を次の同期で再び使う。近距離で先に有効な受取確認を得た場合や、期限切れ・セッション変更・サインアウトでは、送出タスクを取り下げる。近距離で受取確認を得た後は、通常の回収を依頼する。

送出タスクの成功応答は元のURL、HTTP 200、現在の端末セッション、期限、送出待ちの記録、`pending` または `received` を照合する。照合できたら送信用の `payload.backgroundPublished` を保存し、同じ送出を繰り返さず、署名付きの受取確認を照会する。`received` は照会をすぐに要求する。送出待ちの記録がなくなった場合は応答を破棄する。Workerへの保管で削除の到着を確定せず、受取確認の検証と回収は既存の契約に従う。

#### 回線復帰を受け取ったときの個人削除の照会

実行中のAppが回線の切断から復帰への変化を受け取ったとき、送信待ちがある場合に加え、削除を照会できる相手がいる場合も既存の同期を一度起動する。対象は、同じWorkerで照合済みの1端末と端末宛ての個別通話を保存している相手、または現在の端末鍵と一致する有効な旧い端末対。候補の条件は個人削除の照会と共用する。受信側に送信待ちがなくても照会する。通知許可とAPNsの条件は適用しない。背景にいるiOS Appではこの同期を終えるための有限な実行時間を要求する。回線復帰が重複して届いても変化がなければ起動し直さない。

#### iOSが背景更新を許可したときの招待と個人削除

iOS版Appは起動時に、Infoで宣言した招待・削除の同期用の `BGAppRefreshTask` を登録する。端末が背景へ移った時点で、現在のWorker資格で扱える対象を調べる。招待の返信、グループ招待、個人削除のいずれかが同期の条件を満たす場合に、背景更新を1件予約する。グループ招待は、未完了の保存記録があれば対象となる。この端末で招待の送信を許可した登録済みの相手がいる場合も、新着を確認するため対象に含める。保存済みの招待がなく、通知を許可していない場合も、この条件を使う。個人削除は送出・受取確認・回収・受信照会が対象となる。返信の条件は[通常グループ](#通常グループの受諾を遠距離で届ける)と[個人招待](#個人招待の受諾を中継する暗号文)に定める。予約時刻から15分が経過すると実行可能になり、実際の時刻はiOSが決める。前面に戻ったときは予約を取り下げる。サインアウトやアカウントの切替では旧アカウントの実行を取り消し、予約条件を照合し直す。

iOSが実行を許可すると、Appは保存したログインを読み直す。予約時と同じ判定を使い、現在の記録から同期の対象を決め直す。対象になった招待の返信と個人削除は、それぞれ一巡する。グループ招待が同期の条件を満たす場合は、対象となった個人削除を先に同期し、続けて招待を同期する。送信や照会に使う端末資格と証明を既存の条件で確認する。通常同期と個人削除の実行を重ねず、実行期限が切れた場合はこの仕事を取り消す。保存済みの削除・受取確認・回収待ちを使って後で再試行できる。実行条件が続いていれば次の背景更新を予約し、対象がなくなれば取り下げる。[Appleの背景更新](https://developer.apple.com/documentation/backgroundtasks/choosing-background-strategies-for-your-app)

| 所有者・境界 | 契約 |
|---|---|
| CallSessionContracts | AppのCallSession portとイベント語彙。RTCへの依存変換はadapterが所有 |
| CallCommandQueue | typed commandを最大64件、application payload合計256 KiB・単件64 KiBまで保持。待機ごとのTaskは作らない |
| 集約 | 同一接続世代かつ最後の順序境界より後にあるconfiguration、mute、output mute、runtime reports、既知の状態通知だけ最新値へ置換。置換値は末尾へ移動 |
| 順序境界 | connect / startMedia / stopMedia / disconnect、一般application messageはFIFO。別世代や境界を跨いで設定を消さない |
| 実行 | adapterの単一workerがRTCをawaitする。設定commandが実行される時だけRTC sessionを生成し、中間設定ごとの重い生成を避ける |
| 上限超過 | 待機commandを破棄し停止commandを確保、送話受付を止め、UIへ明示通知。実行中処理が戻った後に停止。利用者の明示再接続で最新の希望設定を再適用 |
| 音声送信 | Appの符号化済み音声を入力ごとに作ったコールバックで受ける。入力の有効性は送信待ちに入れる時点で確認し、commandとは別の1 workerで送る。待機上限は[音声処理仕様のRTC送信](音声処理仕様.md#経路共通の操作とcallback配送)に従う。非協調の送信awaitが残る間も新workerを重ねない |
| 送話できる条件 | RTCの媒体開始が完了した時点で、現在の接続世代と媒体開始要求の両方に一致すれば送話を許可する。ミュート中は待機中の音声を破棄し、解除だけで新たな媒体開始要求を作らない |
| 接続を明示的に準備し直す場合 | 同じ通話先でも開始要求を無効にする。接続世代を進め、送話許可と待機中の音声を破棄する。新たな媒体開始要求と、そのRTCでの開始完了が必要 |
| 同じ通話で設定を変更する場合 | 接続経路やInternet設定でRTCを作り直すときは、接続世代を進め、送話許可と待機中の音声を破棄する。現在の開始要求は新しいRTCへ引き継ぎ、その開始完了後に新しい音声を送る |
| 媒体の停止 | 開始要求を無効にし、待機中の音声を破棄する。同じ接続で媒体を再開しても、停止前の開始完了で送話を許可しない |

実行中の非協調RTC処理を強制終了する仕組みは設けない。待機メモリとTask数は制限するが停止完了時刻は保証できず、処理が戻るまで再接続を拒否する。一般messageの過負荷は黙って欠落させず切断として扱う。64件は待機分で、実行中1件は別枠である。

## 招待受理の追加制約

URLは最大8192 UTF-8 byte、token queryは1つだけ。userinfo・port・path・fragmentを拒否する。復号後にversion、非空secret（最大256 byte）、name/ID、有限かつ非負のissuedAt、issuedAt以上のexpiresAt、signatureを確認する。署名入力の曖昧さを避けるためname/secretの`|`は拒否する。

同じgroup・同じ鍵の再招待は保存メンバーを置換しない。自分が招待元なら重複メンバーを追加しない。active groupの鍵を変える招待は、先にDisconnectするよう案内して拒否する。共有secretのHMACに加えて発行端末署名を照合する。アカウント宛て招待では信頼済みserviceの証明も必須とし、共有secretだけを本人証明にしない。

## 保存ユーザーを指定する個別通話

| 対象 | 現行の契約 |
|---|---|
| 通話先の解決 | `selectUser`は独立usersのUUIDを受け取り、直接招待関係として保存した相手だけを解決する。画面はgroup IDや鍵を作らない。削除済みUUID・group内だけの相手は拒否する |
| 同じ二人の再利用 | 双方の確認済みprincipal（service originと公開userID）を順序によらないUUIDへ変換し、kind=directの内部groupを保存する。端末の追加・変更で通話IDは変わらない。同じ二人の再選択・再起動では保存済みのIDと鍵を再利用する。鍵は別途Keychainへ保存する |
| 初回の鍵 | アカウント宛てでは、鍵を読み出せる端末宛て個別通話が一件に定まればその相手端末、次に下記の条件を満たす保留中の受諾の端末、次に既知の相手端末が一台ならその端末を選ぶ。選んだ端末を参加端末枠に残し、その公開鍵とアカウント宛て通話IDで下記の方式の鍵を作る。端末宛て個別通話がどの招待経路で作られたかによって鍵は変わらない。端末対が定まらないときは256bit乱数で作る。両端で鍵が異なる場合は、優先側が同じアカウント宛ての個別通話の招待を共有する。アカウントを使わない端末宛て個別通話は、その端末宛てに保存済みの鍵を使う。通常グループの鍵は別に保持する |
| 対象の単位 | 直接招待で保存した相手だけが対象。同じprincipalの複数端末は1つの相手として選択でき、自分の別端末はUsersの個別通話対象から除外する。相手にprincipalがないLocalでは従来の2つのmember IDを使い、複数memberの宛先を推測しない。確認済みの相手に対して本人principalが欠ける場合はInternet Connectionでの確認を案内し、端末宛ての別通話を作らない。端末宛てとアカウント宛ての保存通話は自動統合しない |
| 初回の共有 | 本人名と招待確認情報を含む相手宛てのversion 6招待を明示共有する。アカウント宛てでは発行者・受取人のprincipalを招待HMACと端末署名へ含め、双方の有効な証明・宛先・pair ID・期限・既存kindを確認する。同じ相手の別端末は受理でき、第三者は一覧・groupを保存しない。新しいアカウント招待に証明が足りなければInternet Connectionでの確認を案内する。共有と受諾は利用者が行い、呼び出しは下欄の通話開始で扱う |
| 同時作成 | 両側が先に同じ二人の通話を作った場合は、principalの固定順（originのbase64とuserID）で先の側の招待へ鍵を揃える。端末IDの順に依存しない。端末宛てLocalはmember ID順を維持。鍵を替える側で同じ通話が進行中なら、Disconnect後に招待を開く。アカウント宛て個別通話では `GroupRepository` が既存の通話に登録済みの端末と公開鍵を保ち、招待者の端末を参加者の条件で照合してから、新しい鍵と受諾を同じ保存で確定する。参加枠が満杯で招待者の端末が未登録なら、受諾を失敗させ、端末と現在の鍵を保持する |
| オフライン | 自分の確認済みprincipalは、member ID・公開鍵・originと同じKeychainレコードに保持し、証明期限後も保存済み通話を解決する。相手はgroup内に保存した端末公開鍵で新しい接続確認値への署名を照合する。期限切れ証明で未知端末を登録しない。資格の差替え・サインアウトで自分のキャッシュを解除する |
| 表示と切替 | 通常のRecent Groupsには内部groupを出さず、Usersで相手名を選ぶ。画面タイトルも相手名を使う。別通話中の選択は今の通話を開くだけで置き換えない（切断してから選ぶ）。通話のアクセサリ（AdvancedはCurrent Callも）から進行中の個別通話へ戻れる |
| 参加者の範囲 | アカウント宛てdirectは二人のprincipalに固定し、端末rosterと鍵対応を最大8件（自端末を含む）保持する。未知端末はgroup認証だけでは音声を許可せず、接続ごとの署名と相手principalの有効な証明が必要。確認済み端末鍵の差替え・別principal・自分の別端末を拒否する。満杯時のprofile登録は未接続の相手端末だけを置換し、全件接続中なら拒否する。招待再受理は既存rosterを追い出さず、追加枠がなければ拒否する。端末宛てLocalは2member固定で、想定外peerなら停止する。UIから第三者の追加・削除・通常groupへの変換は認めない |
| 一覧削除 | usersからの削除と同じcommitで、アカウント宛てdirectの内部group・鍵も消し、進行中ならその通話を切断する。削除UUIDによる新しい解決と招待リンクの共有は認めない。新しい直接招待で再登録すると新しい内部groupを作る |
| ログインと追加端末 | Appleログインを必須とし、直接招待でserver userID、端末member ID、保存ユーザーを対応付ける。追加端末には下記の受諾で保存済みの個別通話鍵を引き継ぐ。条件が揃わない場合は個別通話の招待を共有する |
| 通話開始時の呼び出し | 保存した相手への新規通話の開始から、既存の用途別許可で[通常のAPNs通知を送る](通知仕様.md#送信結果tap保持する情報)。受け取った側では通知の接続操作と再確認を経て通話を開始する |
| 購入と販売の条件 | 公開商品が未設定の間は試用を続ける。設定後の購入確認は各端末の[StoreKit確認結果](利用権仕様.md#復元判定不能ユーザー切替)、24時間の再開条件は[通話利用権](通話利用権仕様.md#成立と24時間)に従う。販売開始の条件は[利用権とデータ保持の設計](../../backlog/利用権とデータ保持の設計.md)で追う |

確認済みの二端末が個別通話鍵を初めて作る場合は、自端末の秘密鍵と照合済みの相手端末の公開鍵でP-256 ECDHを行う。HKDF-SHA256のsaltはUTF-8の `rideintercom.account-direct-call.v1`。sharedInfoは端末ID昇順の端末IDと公開鍵（X9.63のパディングなしbase64url）を交互に並べる。その末尾にアカウント宛て個別通話IDの `UUID.uuidString` を追加し、UTF-8のNULで区切る。出力は32バイトを通常のBase64で保存する。通常グループの招待で相互登録した二人は、この条件が揃えばUsersの同じ相手を選ぶと同じ個別通話鍵を用意できる。[登録から初回の個別通話までの試験](../../validation/history/招待返信の手動共有.md#通常グループで相互登録した確認済み二端末の個別通話)

保存済みの端末宛て個別通話を照合するときは、同じ保存状態のもとで、鍵を実際に読み出せた通話を数える。鍵が欠けた通話は保存したまま候補から外す。たとえば相手の電話とタブレットを登録し、電話との鍵だけが残っていれば、電話とのアカウント宛て個別通話鍵を導出する。鍵の読み取りがエラーになった場合は通話の作成を止める。

宛先なしの通常グループ招待で、同じ認証先に属する別々のアカウントを署名と証明で確認できた場合は、今回確認した端末対の鍵を上記のアカウント方式で準備する。準備の時点は、招待者では受諾の登録時、受諾者では到着確認の保存時である。同じ端末対の個別通話がまだ保存されていないときだけ、内部の端末宛て通話として保存する。片側だけが相手の別端末も登録済みでも、この端末対が保存先で一件に定まれば、Usersから初めて開始するアカウント宛ての個別通話で両側が同じ鍵を使う。既存の個別通話の鍵は保持する。受諾・到着確認の再送や鍵の準備によって、現在の通話を切り替えたり通常グループの鍵を変えたりしない。

受諾者は到着確認を待つ間にも、Usersからこの鍵で初めての個別通話を開始できる。相手の別端末も登録済みの場合、連絡先に対応する保存済みの端末宛て個別通話の鍵を一件に絞れなければ、有効期限内の通常グループ招待の受諾を調べる。`GroupRepository` は、保存した受諾が示す招待者の端末IDと公開鍵を連絡先および招待時に記録した公開鍵と照合する。グループに保存した両端末のアカウントと公開鍵が、現在の本人と連絡先、および受諾時の署名の公開鍵と一致し、招待者がグループから除外されていないことを確認する。条件を満たす受諾がすべて同じ端末対を指す場合は、招待者の端末を通話の参加端末枠に残す。通話開始時は、受諾時と同じ自端末のアカウントと署名鍵を使えることを確認し、通話の参加端末に登録する相手の公開鍵からアカウント方式の鍵を作る。この鍵の生成は、相手の確認済み端末が一台だけの場合にも同じ手順を使う。異なる端末対を指す場合は保留の順番で選ばない。招待者が受諾を保存して同じ鍵を準備すれば、受諾者に到着確認が届く前でも接続できる。

### 通常グループの到着確認で既存の個別通話鍵を揃える

通常グループの受諾を確認した招待者が、アカウント順で個別通話の鍵を優先する側なら、その通話の保存済みの鍵を到着確認に添える。優先側は明示共有と同じ `AccountCallPair.first`。双方は同じ認証先の異なる確認済みアカウントとする。招待者は、受諾端末が通常グループから除外されておらず、その端末と公開鍵が相手の登録にあることを確認する。

優先側の招待者が個別通話を未保存の場合、受諾の処理より前から相手のアカウント・端末・公開鍵を登録していれば、今回受諾した端末を使って初回の鍵を作る。受諾の署名と期限を照合し、元のグループの鍵参照が残り、相手がグループから除外されておらず、自端末が招待時と同じ署名鍵を使っていることを確かめる。双方が相手の端末を複数登録していても、今回の受諾で確認した端末対とアカウント宛て通話IDを上記の鍵生成に使う。受諾の記録、通話先と鍵参照を一緒に保存し、到着確認にその鍵を添える。既存の通話は通常通り保存済みの鍵を使う。[双方が相手の複数端末を登録した場合の検証](../../validation/history/招待返信の手動共有.md#通常グループの招待者が初回の個別通話鍵を用意する)

受諾に署名した端末だけが復号できるよう、既存の招待暗号化を使う。暗号文は受諾のIDと期限に結び付け、到着確認の署名に含める。近距離とInternetで同じ到着確認を使う。暗号文を作れない場合や、暗号文を含む確認が8 KiBを超える場合も、通常グループの到着確認は返す。

受け手は、保存済みの受諾に対する到着確認の署名を確認する。発行者の本人アカウント、端末と公開鍵、招待の宛先と期限が一致する場合に、個別通話の鍵を照合する。発行者が優先側で、[保存済みの鍵を更新できる端末](#通常グループの返信で個別通話の鍵を更新できる端末)の条件に合い、その個別通話が進行中でなければ、届いた鍵と異なる鍵を置き換える。到着確認と鍵の置換を一度に保存する。同じ鍵なら置換は省く。未保存の場合は[通常グループの返信で初回の個別通話を準備する](#通常グループの返信で初回の個別通話を準備する)に従う。

対象の個別通話が進行中なら、現在の鍵で通話を続け、到着確認とともに新しい鍵を[次回用に保留する](#通話中に届いた個別通話鍵を次の開始で使う)。相手の登録、グループの鍵、現在の通話先と保存済み端末は維持する。同じ到着確認の再送では保存済みの個別通話鍵を置き換えない。通常グループの招待をやり取りできない場合は、個別通話の招待を共有する。

### 通常グループの受諾で招待者の個別通話鍵を揃える

鍵の優先側が通常グループを受諾するときは、保存済みの個別通話鍵を招待者の端末に宛てて暗号化する。宛先には、招待に署名した端末と、保存済みの相手アカウント・端末・公開鍵が一致するものを使う。暗号化した招待データをJSONのキー順で並べ、全体のSHA-256を受諾の署名に含める。署名付き受諾と暗号文は一緒に保存する。

受諾側が個別通話を未保存の場合も、受諾より前から相手のアカウント・端末・公開鍵を登録していれば、招待の署名に使われた端末との初回の鍵を作る。受諾時の自端末と照合済みの相手端末の鍵を、アカウント宛て通話IDと組み合わせる。同じ通常グループを保存済みなら、相手が除外されていないことと、その端末の公開鍵を照合する。暗号化した鍵を含む署名付き受諾、通話先、鍵参照は同じ保存で確定する。

再起動、経路の切替、同じリンクの開き直しでも同じ暗号文と署名を使う。暗号文を用意できない場合や、受諾が8 KiBを超える場合は通常の受諾を保存する。招待者と受諾者を入れ替えた結果は[双方が複数端末を登録した場合の検証](../../validation/history/招待返信の手動共有.md#通常グループの受諾者が初回の個別通話鍵を用意する)に記録する。

招待者は通常の受諾の署名と、暗号化した招待データ全体のSHA-256を照合する。受諾端末の登録、グループからの除外、アカウント順、宛先と期限は、到着確認で鍵を受け取る場合と同じ条件を使う。[保存済みの鍵を更新できる端末](#通常グループの返信で個別通話の鍵を更新できる端末)から届き、個別通話が切断中なら、受諾と鍵の置換を一度に保存する。未保存の場合は[通常グループの返信で初回の個別通話を準備する](#通常グループの返信で初回の個別通話を準備する)に従う。個別通話が進行中なら現在の鍵で通話を続け、受諾とともに新しい鍵を[次回用に保留する](#通話中に届いた個別通話鍵を次の開始で使う)。同じ受諾を再送しても再度の置換は行わない。

到着確認には受諾の署名を含める。受諾側は端末に保存したSHA-256から受諾の署名を検証し、届いた到着確認と照合する。到着確認から受諾側への暗号文の送り返しは省く。

### 追加端末が送った通常グループの招待に既存の個別通話鍵を返す

鍵の優先側が相手と個別通話を保存済みなら、同じ相手の追加端末から署名付きの通常グループ招待を受けたときも、保存済みの鍵を返せる。受諾側は署名と現在有効な端末証明を照合し、発行元と本人のアカウントが保存済みの相手と一致することを確かめる。既に使われている端末IDには、同じ保存ユーザーの同じ公開鍵を要求する。保存済みのグループでは相手の除外と端末鍵も照合する。

追加端末をその相手に登録し、追加端末だけが開ける暗号文を含めた受諾を同じ保存で確定する。招待者の端末では、受諾者のアカウント・端末・公開鍵が既に登録されている場合に受諾と個別通話先を保存する。利用者は各端末の既存の相手の行から、同じ通話IDと鍵を使う。元の端末の登録と鍵を保ち、接続先の本人確認は既存の参加端末の規則に従う。[追加端末での確認](../../validation/history/招待返信の手動共有.md#同じ相手の追加端末へ受諾で個別通話鍵を渡す)

### 通常グループの返信で初回の個別通話を準備する

優先側がアカウント宛ての個別通話の鍵を返し、もう一方が個別通話を未保存なら、上記の受諾または到着確認で受け取った鍵を使って、同じ通話IDの個別通話を準備する。優先側が個別通話を未保存の場合は、招待者なら受諾の処理で、受諾者なら招待の処理で鍵を用意できる。返信の相手のアカウント・端末・公開鍵は返信を処理する前の登録と照合する。自端末とその相手の保存済み端末で通話先を構成し、返信の署名に使われた端末を参加枠に優先する。相手との端末宛ての通話が複数保存されている場合も、受け取った鍵を使う。

個別通話の記録と鍵は返信の処理と一緒に確定する。鍵の参照を保存するまでUsersの通話先として表示しない。元のグループの鍵、現在の通話と画面選択を保つ。受け取った鍵を確認できない場合は、通常グループの返信だけを処理する。結果は[複数の登録端末がある場合の検証](../../validation/history/招待返信の手動共有.md#通常グループの返信で未保存の個別通話を準備する)に記録する。

### 通常グループの返信で個別通話の鍵を更新できる端末

通常グループの返信を処理するとき、個別通話の鍵が残っているか、その通話が進行中なら、鍵の送信端末を個別通話に保存したアカウント、端末ID、公開鍵と照合する。すべて一致した場合は、上記の条件に従い鍵を更新するか次回用に保留する。端末が相手の連絡先だけに登録されている場合は、通常グループの返信を保存し、既存の個別通話鍵と保留を保つ。このため、個別通話にまだ登録されていない追加端末から鍵が届いても、元の端末対で同じ鍵を使い続けられる。

対象の個別通話が切断中で鍵を保存していない場合は、上記の署名と連絡先の照合に従って鍵を保存できる。鍵の読み取りが失敗した場合は保存の処理を中止する。保留を次回に適用するときも、個別通話に保存した送信端末を照合する。[元の2端末での検証](../../validation/history/招待返信の手動共有.md#鍵の優先側の追加端末から返信が届いても元の通話鍵を保つ)

### 通話中に届いた個別通話鍵を次の開始で使う

受諾と到着確認のどちらから受け取っても、対象の個別通話が進行中なら同じ保存処理で保留する。schema 25の個別通話記録に、暗号化した招待データ、発行時刻、元の通常グループのIDと鍵参照を1件保存する。有効な保留がある場合は、発行時刻が古い受取で置き換えない。通信に使う鍵は現在のまま保つ。

次回の接続前に、現在の本人アカウントと端末鍵で保留を照合する。有効なら新しい鍵をKeychainへ保存し、鍵参照の置換と保留の削除を一度に確定する。再起動後の開始も同じ処理を使う。進行中に一時的に経路が切れた場合は、同じ通話の鍵で復旧する。

期限切れ、元のグループの削除・鍵の変更、相手の登録の解除や除外、個別通話鍵の別操作による置換で保留を外す。保留の検査は起動時と保存時にも行う。現在の本人アカウントや署名鍵が一時的に読み出せない場合、有効な保留は次回の照合に残す。

### 通常グループの招待返信で端末宛て個別通話を準備する

初めて個別通話する二端末は、通常グループの署名付き招待を受諾し、招待者が受諾を受け取れば、追加の個別通話招待を使わずにUsersから同じ相手と通話を始められる。対象は期限内の手動招待で、アカウントの宛先指定がなく、対象の双方が端末単位で相手を照合し、同じ端末対の個別通話がまだない場合。双方が署名済みの招待条件に対応する端末鍵を持つことを条件とする。

| 端末と契機 | 保存と結果 |
|---|---|
| 受諾者が、招待の発行署名と招待条件を照合して受諾する | 通常グループ、招待者の登録と受諾を保存する。個別通話をまだ開かなければ個別通話鍵を作らない |
| 受諾者が、到着確認を待つ間にUsersから相手を選ぶ | 期限内でアカウント証明なしの保存済み受諾を照合する。宛先なしの通常招待で、確認済みの同じ相手端末への受諾が一件以上あり、対象の受諾がすべて同じ自端末公開鍵を使い、その公開鍵に対応する自端末の署名鍵を読めるとき、端末対から個別通話鍵を作る。どのグループの返信を送るかは別の判断とし、複数ならUsersの選択だけで返信先を決めない。選択だけで進行中の通常グループは切り替わらない |
| 招待者が、接続先の端末IDと署名を照合した受諾を受け取る | 相手の登録、受諾ID、内部の個別通話と鍵を同じ保存で確定した後、署名付きの到着確認を返す。この時点から、到着確認を待つ間に上の条件で準備した受諾側の個別通話も同じ鍵で接続できる |
| 受諾者が、保存した受諾ID・招待条件・端末鍵に対応する署名付き到着確認を受け取る | 登録済みの招待者の端末IDと公開鍵、および双方の署名を照合して返信待ちを解消する。個別通話鍵がまだない場合はこの時点で準備する。受諾を再送した際の署名と表示名の更新を許す |

両端末は端末IDから端末宛ての個別通話IDを作り、自分の端末秘密鍵と相手の公開鍵でP-256 ECDHを行う。HKDF-SHA256のsaltはUTF-8の `rideintercom.ordinary-group-direct-call.v2`。sharedInfoは端末ID昇順の端末IDと公開鍵（X9.63をパディングなしbase64urlで表記）を交互に並べ、UTF-8のNULで区切る。出力32バイトを通常のBase64で表し、既存の個別通話鍵と同じ保存先に保持する。双方の招待が交差した場合も、同じ相手から複数のグループへ招待された場合も、どの受諾が先に届いても同じ1つの個別通話鍵を準備する。

同じ受諾や到着確認の再送で鍵を替えたり、削除した個別通話を復元したりしない。既存の個別通話は保存済みの鍵を使い、対象外の条件では従来どおり登録と返信だけを処理する。選択中の通常グループや進行中の通話は維持する。[到着確認を保留した検証例](../../validation/history/招待返信の手動共有.md#到着確認を待つ間に個別通話を始める)、[複数の招待が保留されている検証例](../../validation/history/招待返信の手動共有.md#同じ相手への複数の返信を保ったまま個別通話を開く)

### 通常グループの受諾を通話とは別に近距離で届ける

双方で近距離が有効な場合、通常グループの手動共有URLを発行した端末と、そのURLを受諾した端末は、通話と独立した `RTCLocalDataChannel` を通じて受諾と到着確認を往復できる。招待者が通話中でなくても、受諾側が個別通話に切り替えた後でも、両端末が近距離で実行できる間は返信を続ける。既存の通常グループ通話内で受諾と到着確認を往復する経路も使える。

- 招待者はURL発行結果を返す前に、schema 24の `issuedOrdinaryGroupInvitations` へ招待条件と通常グループ鍵の参照を発行順で保存する。同一端末で最大32件を保持し、上限に達したら既存の招待を保って新規の発行を止める。期限切れ、グループ削除、鍵の置換で対応する記録を外す。URLや招待専用秘密は保存しない。発行の記録は共有先への送信や受諾の確定には使わない。schema 23以前からは発行待受の記録を空で始める。近距離の発行側では、起動・前面復帰と前面で近距離を有効にした時、グループと元の鍵参照、発行端末の鍵、期限が一致する各招待の待受を再開する。後の発行は先の待受を置き換えない。
- 受諾者は受諾保存時と対象グループまたは対象の個別通話の開始時に、保存済みで期限内の受諾から試す。個別通話の開始時は候補を1件に絞れる場合だけ使う。近距離の試行は発行側では招待ID、受諾側ではグループIDごとに保持する。同じ条件の再要求では開始し直さない。
- 起動・前面復帰と前面での近距離の再有効化では、`GroupRepository` が現在の保存条件で有効な通常グループの保留を確認し、グループごとに元の受諾を再送する。すでに試行中の同じ受諾は続ける。別のグループに対する受諾・到着確認・削除は、他のグループの試行を入れ替えたり終了したりしない。特定のグループを指定して試行できる入口も使える。復元時に通話を開始・終了・選択しない。
- 実行中のAppは、現在の通話の利用可能経路に近距離が加わった時も同じ条件で待受を再開する。接続待ちの間に初めて経路が使えるようになった場合と、経路断から復旧した場合が対象。音声がInternet経由のままでも試行する。同じ利用可能経路の通知が続く場合は試行を追加しない。
- `RTCCredential.derived` のgroupIDには `rideintercom.ordinary-group-reply.v1:` に招待IDの `UUID.uuidString` を連結した値を使う。secretには保存済みの通常グループ鍵を使う。通話の探索・認証とは用途を分ける。受諾者は元の招待者との認証済み接続が成立した後にだけ署名付き受諾を送る。
- Appは同じ招待条件と認証済みの送信元、HMAC、端末署名を照合する。招待者は現在もグループのメンバーであり、除外した相手や保存済み端末鍵と異なる相手を受理しない。既存の保存処理で受諾ID、相手、個別通話を確定してから、送信元にだけ署名付き到着確認を返す。他の相手のグループや通話開始状態は変更しない。
- 近距離の試行は招待ごとに1回60秒以内か招待期限までとする。iOSでは端末上の近距離の試行が1つの背景実行時間を共有し、最後の試行が終わったら返す。OSの実行時間切れでは共有中の試行を終了し、以前の実行時間の終了通知は新しい待受に適用しない。受諾側は到着確認の保存後、双方とも近距離無効化・アカウント終了で試行を終了する。発行側の記録が失効したか、同じグループ鍵を読めなくなった通信は処理しない。受諾は保存先に保持し、通常の再試行で同じIDを使う。実行時間切れの後は前面復帰等の復元機会に再試行する。
- 発行条件または保留中の受諾と、開始時のグループ鍵参照が現行の保存に残る間だけ待受を維持する。`GroupRepository` がこの判定と鍵の読み出しを所有する。近距離・遠距離は、発行済みと受諾済みの候補を列挙する時点から同じ保存済み鍵参照の条件を使う。開始とイベント受取では鍵と参照を組にして照合する。イベント受取時はその組が開始時と一致することを確認し、保存更新直後の終了判定は参照の有効性を確認する。グループ削除・鍵参照の置換・招待者の連絡先削除・署名付き到着確認により無効になった待受は、保存確定時に通信と実行時間を回収する。旧保存に連絡先を失った受諾が残っていれば、読込時に回収する。同じ到着確認の再送は保存を更新しない。

[近距離経路の復旧試験](../../validation/history/招待返信の手動共有.md#通話の近距離経路が戻ったときに保存済みの返信を再開する)、[通話を切り替えた試験](../../validation/history/招待返信の手動共有.md#通話を切り替えても近距離で受諾を届ける)、[発行側を作り直した試験](../../validation/history/招待返信の手動共有.md#招待者を起動し直して同じリンクへの受諾を受け取る)、[受諾側を前面に戻した試験](../../validation/history/招待返信の手動共有.md#受諾側を前面に戻して保留を届ける)

### 通常グループの受諾を遠距離で届ける

遠距離の通常グループの招待返信は、期限付き中継へ既存の署名付き受諾または到着確認を暗号化して渡す。発行端末と受諾端末のAppは以下の形式を共有する。Workerには照合用の受諾ID、受け渡し先、暗号文を渡し、復号には宛先端末の秘密鍵を使う。[Workerの中継契約](../server/Worker.md#通常グループの受諾と到着確認の暗号文中継)

| 部分 | 形式と照合 |
|---|---|
| `slot` | 通常グループの保存済み鍵をUTF-8でHKDF-SHA256の入力とする。saltは `rideintercom.ordinary-group-reply.slot.v1`、infoはグループIDと招待IDの `UUID.uuidString` をNULで区切ったUTF-8。出力32byteの小文字hexを使う。期限は招待の期限をUnix msへ切り捨てて算出する |
| 宛先鍵と平文 | 受諾は署名付き招待にある発行端末鍵、到着確認は受諾にある受諾端末鍵を使う。平文は既存の署名付き `DirectInvitationReceipt` をJSONで符号化し、上限は8,192byte |
| 暗号化 | パケットごとに新しいP-256一時鍵を使い、宛先端末鍵とECDH。HKDF-SHA256のsaltは `rideintercom.ordinary-group-reply.ecdh.v1`。infoとAES-256-GCMの追加認証データは、同じsalt文字列、`slot`、受諾IDの小文字UUID、`accepted` または `acknowledged` の順で、UTF-8のNUL区切りとする。HKDF出力は32byte |
| `packet` | 一時公開鍵の非圧縮X9.63表現65byte、GCMのnonce 12byte、暗号文、認証タグ16byteを順に連結し、標準base64を使う。Appは平文と暗号文のサイズを制限し、Workerからの `inbox` は最大8件、応答は100KiBまで受ける |
| 復号と受け渡し | 現在の招待期限、招待条件、受諾ID、方向、宛先端末IDと鍵が一致すると既存の受諾・到着確認として扱う。受諾IDは元の招待IDと受諾端末IDから再導出する。その後、既存の受諾・到着確認の署名照合で保存の可否を判断する。中継の成功応答だけで登録や返信待ちを確定しない |

Internet経路が有効で、同じWorkerの端末資格を使える場合に、招待の発行条件や受諾の保存が完了したところから同期を開始する。発行端末は保存済みの有効な招待を発行順に読み、招待ごとに受け渡し先を開き、受諾を取得する。発行端末の照合では、近距離の再開と同じ発行者の端末IDと署名鍵を使う。受諾端末は、招待者の端末IDと鍵を保存済みの確認済みアカウントと照合してから、そのWorkerへ受諾を預ける。1回の同期では有効な受諾を順に試す。通常のグループ招待の送受信、通知許可、進行中の通話から独立し、iOSでは保存直後に利用可能な背景実行時間を求める。

同期はすぐに一度行い、未完了なら前回の同期が終わってから1秒、2秒、4秒、8秒、8秒の順で待って再試行する。待機を含む試行の上限は30秒とし、OSの実行時間が先に尽きた場合はそこで終了する。成功した受け渡し先の登録と受諾の送信は同じ試行中に繰り返さず、受諾一覧と到着確認だけを取得する。頻度制限、対象の消滅、サインアウト、Internet無効化で試行を終了し、得た実行時間を返す。新しい発行や受諾は直ちに試行し直し、前の試行の時間切れは新しい試行に影響しない。[UIKitの背景実行時間](https://developer.apple.com/documentation/uikit/extending-your-app-s-background-execution-time)

発行端末は署名を照合して相手登録を保存してから到着確認を返す。受諾側は保存した受諾と照合した到着確認を保存した時点で保留を解消する。途中で切れたときは、起動・前面復帰や前面でのInternet経路再有効化で、保存済みの条件と同じIDを使って再試行する。試行を始めるときに `GroupRepository` から、保存済みの招待条件と期限を満たすグループ鍵と鍵参照を組にして読み出す。受信を適用する前に、同じ保存条件から得た鍵と参照が開始時と同じで、ログイン世代・経路設定が有効であることを確認する。削除・期限切れの保留から通信を再開しない。

実行中のAppは、現在の通話の利用可能経路にInternetが加わった時も同じ同期を始める。接続待ちの間に初めて経路が使えるようになった時と、切断後に復旧した時が対象。音声が近距離経由のままでも試す。Internetを含む通知が続いても追加の試行は開始せず、すでに動いている同期は継続する。

iOSが[背景更新](#iosが背景更新を許可したときの招待と個人削除)の実行時間を与えたときも、同じ返信同期を一巡する。有効な発行記録がある場合は受け渡し先を開いて受諾を取得する。受諾の保留がある場合は、保存済みの発行者の端末を照合して受諾を送り、到着確認を照会する。通常の返信処理が実行中の場合はその処理に任せる。背景更新の中では再試行の待機を入れず、実行期限やアカウント変更で中断された保留は同じIDで後から再試行できる。発行記録は、同じリンクを使う別の人の受諾に対応するため、有効な間は同期対象になる。

Appの通常操作、遅着、通話のInternet経路復旧、背景更新からの返信同期をローカルWorkerで検証した。実機ではロック中の背景更新の起動と、その後の受諾・到着確認を受け入れる。[経路復旧の検証](../../validation/history/招待返信の手動共有.md#通話のinternet経路が戻ったときに保存済みの返信を再開する)、[遅着の検証](../../validation/history/招待返信の手動共有.md#最初の同期の後に届く通常招待の返信を受け取る)、[通常操作の検証](../../validation/history/招待返信の手動共有.md#通常の招待操作から遠距離で相手登録と到着確認を進める)、[CryptoKitのGCM格納形式](https://developer.apple.com/documentation/cryptokit/aes/gcm/sealedbox/combined)

## アカウント削除と端末内消去

`InternetConnectionSettingsStore`はApple登録と接続資格を、ビルドが選んだHTTPS originに限定する。TestFlightを含むReleaseは本番、Debugは固定Previewが既定。Debugのビルド時に指定した試用先も同じ照合を通る。別環境の保存資格は読み飛ばし、この判定でKeychainを変更しない。

保存した登録を読む際は、通話、通知、招待、署名付き本人情報、サインアウト、新たなサーバー側のアカウント削除で接続先を照合する。Apple登録に成功すると選択済みの接続先の資格を保存する。[画面仕様](UI/Settings.md#internet-connection)

`AccountDeletion`は通常のサインアウトと独立した削除記録をbase namespaceのKeychain `.AccountDeletion/pending`へ保持する。記録の保存成功後にログイン世代を失効し通話を停止する。この間はサインアウト用の`DELETE /api/auth/session`を送らず、削除記録が所有するBearerを`DELETE /api/auth/account`の再送に使う。記録はnative Apple ID、接続先・端末ID・Bearer・削除対象の公開ID、未送達の再認証proof、serverの受理／Apple取消／媒体回収状態、端末内消去の完了を保持する。秘密・識別子をログへ出さない。

serverの`deleted:true`を受け取って永続化してから端末内データを消去する。Apple取消または媒体回収がpendingでもserverのアカウント削除が受理されていれば端末内消去を進め、再試行のBearerと未完状態を別記録へ残す。受理済みのproofは除去する。HTTP 401は通常の端末サインアウトでは再送完了にできるが、アカウント削除では拒否とする。削除結果の矛盾・不足、通信／保存エラーを成功に変換しない。server未受理時のApple証明更新・証明なしへの変更は本人の明示操作に限る。起動時に一度再開し、失敗後は操作による再試行とする。401で取消待ちの受領記録を確認できなくなった場合も、端末内消去済みという状態は保持し、明示的なApple再認証へ戻す。再認証proofには保存済み公開IDを`expectedUserID`として含め、別世代の登録を削除しない。serverの`newerAccountPreserved`は保存済みの削除対象IDがある場合だけ受理する。fresh proofによる復旧と、確認済み受領記録への再送の両方に適用する。取消済み／取消待ち／媒体回収待ちとの矛盾を拒否する。この応答では新しいアカウントのApple認可を保持したと表示し、手動解除を勧めない。

`appleRevocationPending`と`mediaCleanupPending`のいずれかがtrueなら完了操作を出さず、残る処理を案内する。どちらも再起動後の再試行対象とし、片方だけ完了しても残りを失わない。再登録の`409 deletion_pending`は削除開始端末での完了を案内し、8端末上限とは区別する。未知の409 codeを端末上限と決めつけない。

`AccountDataEraser`はnative Apple IDから導いた既存のaccount namespaceだけを対象とする。Groupsの非ブロッキングlockを取得し、新しいgenerationの空manifestへ置換して古いrepositoryの書戻しを拒否する。同じアカウントのGroupCredential v2／旧形式、Internet資格・端末署名鍵・証明、招待発行者鍵、UserDefaultsを消去し、破損時の退避ファイルも除去する。個人データを含まない空manifestとlock inodeは残す。別アカウントを走査・削除せず、対象namespaceまたはGroupsがsymlinkなら拒否する。中断・部分失敗は同じ消去を再実行する。

サインアウト成功後も最後の登録の接続先・公開ID・端末ID・失効済みBearerを保持する。`deletionAccess`は削除復旧に使い、新しいApple本人確認を必須にする。同じ退避の確認済みprincipalと発行者の公開検証鍵は、nativeログインとアカウント別保存領域の境界内でLocal通話の本人識別・相手証明の検証にも使う。保存破損・読取失敗を「Internet未登録」と扱わず、通常の資格load・端末証明・開発fallbackには復帰させない。退避もアカウント消去時のKeychain列挙で削除する。

現在資格にも削除復旧用の退避にも公開Internet登録がなければ、端末内消去とApple手動解除を案内する。開発用fallback資格をアカウント削除APIへ送らない。未知の別サービス登録、他端末のオフライン保存、共有済みのグループ情報、購入解約まで消去したとは扱わない。server契約は[Worker](../server/Worker.md#アカウントの端末登録削除)、操作は[Settings](UI/Settings.md#アカウント削除)を参照する。

## 公開IDの再登録後に残った端末内データ

同じサービスへのApple再認証で、確認済み公開IDが以前と変わった場合は、旧アカウントの端末内関係を新アカウントへ引き継がない。本人の公開IDが同じ通常の再ログイン・資格更新はこの処理に入らない。オフラインのLocal開始をserver照会待ちにせず、登録時に確認できた変更だけを扱う。

| 段階 | 動作 |
|---|---|
| 検知 | `InternetConnectionSettingsStore.save`は現在の確認済み登録、なければ最後の退避登録と、新しい確認済み証明のissuer・公開IDを比較。同じissuerで公開IDが違えば上書き前にアカウント別UserDefaultsの`InternetAccount.requiresDataReset`を立てる |
| 停止 | 通話を切断しInternet確認世代を更新。通話・招待・保存変更と資格差替えを止める。nativeログイン世代の有効性は別判定とし、復旧操作を残す。再起動や、別の資格を保存する操作ではflagを解除しない |
| 明示的な消去 | Rootの復旧画面で確認すると、既存`AccountDeletion`へ`localReset`と端末登録IDを永続記録してからサインアウト。server削除や追加Apple証明は要求せず、`AccountDataEraser`で旧Users・groups・member ID・署名鍵・招待鍵・設定を消す |
| 端末枠 | 再設定で同じ端末登録枠を更新できるよう、`device-id`だけ書き戻す。Bearer・本人principal・所属・秘密鍵は残さない。新資格のbest-effort失効が通信断で失敗しても、次の登録で同じdeviceIDのtokenHashが更新され、端末枠を増やさない。失効の即時完了を保証するものではない |
| 失敗・再起動 | ローカル消去と端末ID書戻しが成功するまで完了にしない。記録を使って再試行し、通信を待たない。完了後だけ再ログインとInternet再設定へ戻り、新しい招待・鍵で関係を作り直す |
| 通常削除との違い | 新serverアカウントとApple認可は保持し、Apple手動解除を案内しない。通常のDelete Accountは従来どおりserver上で削除し、端末登録IDも消す |

本人の確認済み証明を持たない資格を内部の検証で保存する場合も、現在の確認済み登録を退避し、サインアウトでそれを上書きしない。退避失敗・破損は既存登録を残してエラーにする。これは現在または最後に退避した確認済み登録の比較であり、過去の複数サービス全履歴を管理する機能ではない。


## 利用権と通話成立

通常groupの作成・追加・招待と、認証後の音声許可・24時間起算点は[通話利用権仕様](通話利用権仕様.md)の共通判定を使う。接続準備・プロフィール交換・直接通話への呼出しは本人購入を前提にせず、相手の権利を確認できる経路を保つ。

## 新規相手招待の通知処理

`ContactInvitationSession`は通常の通話と別に所有する、音声を開始しない招待通知の処理である。既存の署名・grant・受諾receiptを共用し、署名対象の`contactBootstrap`と`rideintercom://contact`を対応させる。通常の`join`入口はこの用途を拒否し、既存group/direct招待の意味を変更しない。期限の既定値は、既存の招待と同じ7日である。

受諾側は署名検証後の明示受諾で招待者を登録できる。送信側は認証済みpeerから、発行した用途・招待ID・期限・本人の署名が一致する受諾通知を受けて登録する。音声接続やACKは登録条件ではない。ACKは通知の再送終了に使用する。同じ招待の通知は最初に確定した受諾者へ固定し、同じ通知の再送で登録を繰り返さず、別peerへの再利用を拒否する。

保存callbackは成功時のみ確定を返す原子的な処理を契約とする。失敗時は成功ACKを送らず再試行できる。sessionは単回のlifetimeとし、停止は一度だけ切断し、停止後の遅着通知と再開始を拒否する。通信の所有者は通常通話と分け、登録情報の保存先をsession内に増やさない。

`ContactInvitationTransport`は、個人招待と個人登録を兼ねるグループ招待の署名付き受諾・到着確認・用途別許可を運ぶ。近距離が有効なら、招待専用の共有資格を使い、[独立したQUICデータ経路](../packages/RTC.md#通話を開始しない近距離データ交換)で届ける。近距離の転送は通話用の`CallSession`・音声経路・Internetの資格を必要としない。Internetも有効で資格を読める場合だけ既存の音声なしのInternet接続を併用する。両経路は到達できる認証済みpeerをまとめて通知し、同じ受諾・到着確認は既存の保存IDと署名で照合する。近距離のフレームは12 KiB、署名付きreceiptと用途別許可は8 KiBを上限とする。

保存とAppの接続は次の境界を持つ。Usersの追加UIと明示受諾の確認画面は[画面仕様](UI/Call.md#新しい相手への直接招待)へ接続する。

| 項目 | 保存と動作 |
|---|---|
| データの保存先 | schema 10から導入したGroupSnapshotトップレベルの `contactInvitations` を使う。ここに招待ID・方向・期限・状態・単回確定した相手とreceipt ID・Keychain参照を保持する。通常のgroupsへ招待用groupを登録しない（招待完了時の二人の個別通話は次の「個別通話の完成」に従う）。全snapshot更新で保持し、schema 8以前からは空の招待一覧を追加して移行する |
| 招待前の人の保存 | `saveContactPerson(_:name:)`は明示したUUIDと名前だけを`SavedUser`へatomic保存する。未登録は`memberIDs=[]`、`principal=nil`、`deviceKeys=nil`とし、仮のリモートID・署名鍵・招待・通信接続を作らない。`directoryUsers`は未登録を含み、`savedRemoteUsers`は識別済みだけを返すため、通話・グループ追加・通知許可へ名前だけの人を渡さない。schema 9以前は空のmemberIDsを拒否する |
| 人と送受信の記録 | `ContactInvitationRecord.personID`は端末内の人への参照で、本人の識別情報ではない。`stageContactInvitation`は保存済み未登録の人への紐付けを検証する。同じ人に期限内のpendingを重ねない。受諾の確定では新しく確認した人へ元のUUIDと呼び名を引き継ぐ。既に確認済みの同じ本人がある場合はその人のIDと呼び名を保って未登録の重複だけを除く。本人名へ追従する`localName=nil`も既存の選択として保持し、新しい招待用の呼び名で上書きしない。表示名だけで統合しない。削除時はその人の未完招待も同じcommitで取消し、確認済みbindingは重複ACKのため保持する |
| schema 9の招待の移行 | pendingまたはexpiredの送信招待に未登録の人を1件ずつ作り、元の呼び名・招待・鍵参照を保持して紐づける。同名でも別の招待は統合しない。受信・確認済みの記録は保存済みpeerに紐づける。移行失敗は旧manifestと鍵を保つ |
| 秘密の保存 | 既存のaccount別`.GroupCredential.v2`のimmutable UUID slotへ、token・再送receiptのblobを保存する。`RideIntercom.ContactInvitation.v1:`で用途を区別する。通常groupの生の通信鍵とは専用encode/decodeで区別する。URL・rendezvous secret・grant secretをmanifest、UserDefaults、ログへ平文保存しない。回収時はgroupとcontact双方の参照集合を使用する |
| 登録と通知の原子性 | 明示受諾時はUsersと送信待ち通知を同じmanifest置換で確定する。作者は検証済receiptでUsersと単回受諾者のbindingを同じ置換で確定してからACKを送る。途中失敗では成功ACKを送らず、再読込から回復する |
| 明示登録・再試行直後のiOS背景処理 | 登録ではUsersと受諾を保存する。登録と利用者が押した再試行は、返信sessionの開始・再試行の前に既存のUIKitの有限の背景実行時間を要求する。同じ試行に時間を取得済みならその時間を使う。OSから時間を得られたら、直後のロックや他のアプリへの移行後も同じsessionで署名付き受諾とACKを扱う。時間切れではsessionと実行時間を解放し、同じアカウントの保存済み返信を次の再開機会に使う。期限・取消・サインアウトで停止し、通常通話中は近距離だけを使う |
| 手動共有の保存API | `ContactReplyURL`は`rideintercom://contact-reply?receipt=...`へ既存の署名済み受諾／ACKだけをbase64urlでencodeする。上限はURL 16,384byte・JSON 8,192byte、単一query・空path・userinfo／port／fragmentなし。group秘密・grant秘密・秘密鍵は含めない。parseだけで登録せず、現アカウントの同じ招待checkpoint・期限・宛先・署名で再検証する。共有のexportは配達状態を書き換えず、無通信で実行できる。表示条件・実exportとも現在の同一送受信の記録と、peerMemberID・peerDeviceKeyが一致する登録済み相手を照合する。削除・取消前に作った共有値も再検証し、確認済みbindingを保持していても削除した相手へ手動共有しない |
| 手動返信の適用 | 作者は保存済みtokenのcontext一致と既存authorityのHMAC・受諾署名で確認し、同じconfirmContactInvitationで登録。受け手は保存済み受諾との一致・作者ACK署名・本人の受諾署名で配達済みを保存する。確認済みの重複は副作用を増やさない。取消・期限切れ・別account・別受諾者・改ざんは拒否する。通常通話・ミュート・開いている人の詳細を保持し、通信を必須にしない。ContentViewの専用URL入口から同じ処理へ接続する。手動受領はContactInvitationRecord.receivedBySharing=trueを登録と同じ置換で保存し、schema 10で追加し、値を持たない旧データはnilで読む。この値から相手に届いたかどうかは分からず、返信を受けた作者の手動ACK共有を案内するための由来である |
| 共有・受領前の読込失敗 | 返信のexportと受諾／ACKのimportが読むcheckpointは同じloadContactReplyPayloadを通し、例外を既存reportGroupStorageErrorへ渡す。分類に応じた既存の保存復旧案内へ接続し、保存した相手・返信・通話を保つ。読めないまま配達済みや登録済みへ進めず、再読込後は同じ返信を再試行できる |
| 期限切れ招待の置換 | 画面の表示と保存の置換は、`ContactInvitationRecord.isExpiredOutgoing(at:)` に従う。元と同じ人の招待を作り直せる条件は次のとおり。 `direction == outgoing AND (state == expired OR (state == pending AND now >= expiresAt))`。時刻が非有限なら新しい招待の保存を拒否する。グループ招待の作り直しには元のグループと予約枠も必要。新しい招待とKeychain参照・元の`nickname`・旧記録の除去をまとめて確定する。`stageContactInvitation(_:now:replacingExpiredInvitation:)`でmanifestを1回だけ置換する。期限内・存在しないIDは無書込で拒否する。保存失敗では旧manifestと呼び名・表示対象を保ち、既存の読取専用／再読込による復旧を使う。commit成否が不明な場合に古いsnapshotを書き戻さず、新旧の秘密は再読込後の参照確認で整理する |
| 個別通話の完成 | 招待の完了で、その二人の個別通話を通話開始に追加操作が要らない状態まで確定する。受諾側は明示受諾時、作者は受諾の署名と招待条件を照合して保存する際に、Usersと同じmanifest置換で端末member ID二人の`directCallID`の個別通話groupと通信鍵を保存する。通信鍵は両者が招待tokenで共有済みのgroup秘密からHKDF-SHA256で導出する。saltは `rideintercom.contact-direct-call.v1`、infoはgroup UUID文字列、出力は32byteとする。このため両端末が同じ鍵を持ち、Internetやその後の鍵交換なしで近距離通話を認証できる。同じ二端末の再招待は両側で端末宛ての個別通話鍵を置き換える。導出した通信鍵だけを通常のgroup鍵slotへ保存し、tokenのgroup秘密そのものは通話鍵として保存しない。新規のアカウント宛て個別通話は、端末宛て個別通話が一件に定まれば相手の端末を選ぶ根拠とし、両端末の鍵とアカウント宛て通話IDからアカウント宛ての鍵を作る。通常グループ招待で相互登録した後、片側だけがアカウント宛ての個別通話を先に作っていても、個人登録の再招待で入れ替わる端末宛ての鍵とは独立して、同じアカウント宛ての鍵で通話できる。既存のアカウント宛て通話は保存済みの鍵を使用する。既存の鍵が相手と食い違う場合は「競合した個別通話の再共有」に従う。通常のgroupsとしては表示・作成扱いにせず、通常group作成の購入条件も適用しない |
| 再起動・再送 | 再起動時は保存済みpendingを読む。同じ人の詳細を開く操作・共有・明示Retry、または同じログイン世代のforeground復帰で停止対象一件だけ通信を起動し、同じtoken・本人鍵で通知を再送する。ACK後は受諾者側の秘密を回収し、処理済みIDを保持する。作者側の確定済みbindingは、登録した相手が残っている間の再送へのACKに使う。作者の`outgoing/confirmed`と受諾側の`incoming/delivered`は完了状態として未完了一覧から外す。人を基準に表示する`.person`詳細は状態だけを更新して維持し、旧未紐付け招待の互換詳細だけは完了で閉じる。作者のbindingは表示のために消去せず、既存の有限な通信試行中は詳細を閉じても重複receiptへACKを再送できる。旧形式では詳細を閉じると試行を止める。通常通話中の経路は下記の併用条件に従う。サインアウト・期限で停止する |
| 返信の期限表示 | `ContactInvitationRecord.hasExpired(at:)` で期限ちょうど・非有限な現在時刻・expired tombstoneを無効と判定する。`canResume(at:)` は保持している有効なcheckpointを判定し、返信共有とAdvancedの再試行・取消の表示が使う。登録済み相手との鍵・保存可否の照合は共有時にも行う。古い表示から再開した場合も招待専用通信だけを止め、理由と現在の表示を更新する。保存した人・名前・通常通話と期限切れ記録の整理契約を維持する。画面は再表示・既存の状態更新・操作時に期限を確認する |
| 通信の時間と経路 | 各明示操作の通信は最大60秒と招待の残り期限の短い方で停止する。7日の招待期限と通信試行の時間を区別し、停止後も未完通知は保存して次の明示再開に使う。常時scan・background pollingを追加しない。route設定と設定済みInternet configurationを既存の共通値から渡す |
| 通常通話との併用 | 通話開始前は進行中の招待のInternet接続だけを閉じる。近距離の試行・署名付き返信・到着確認・試行期限は維持する。通話中のRTCによる返信は近距離に限る。本人確認済みのInternet返信は既存のWorkerへHTTPで預ける。近距離とInternet返信のどちらも試せない場合は手動共有か通話終了後の再試行を案内する。通話先・ミュート・音声処理・通話の終了期限を変更しない。通常通話の終了後も進行中の近距離試行は続く。サインアウト・保存のリセット・経路設定やInternet資格の変更では招待の接続を閉じる |
| 権利 | ログイン世代と保存可能性を確認し、直接の連絡先招待に通常group作成の購入条件を流用しない。通常group作成・追加・招待と音声の利用権判定は従来どおり |
| 人物詳細・設定での再試行と停止 | 登録直後のaccepting詳細・person詳細・相手の設定は、同じ相手IDと招待IDを共通操作へ渡す。現在の保存済み相手に属しcanResumeであることを実行時に再確認し、別人・削除済み・停止済みの操作を拒否する。再試行は既存の期限と通話中に使える経路の判定を通し、iOSでは同じ返信に有限の背景実行時間を使う。停止はcancelledを保存し、再試行・返信共有を外して「Retries stopped on this device.」を表示する。相手・名前・開いている人物詳細／設定は保つ。旧未紐付けsharingだけは対象が一致するとき閉じる |
| 取消と消去 | 相手の削除と、紐づく旧招待（受諾済みを含む）のcancelled化・秘密への参照解除を、同じmanifest置換で確定する。その後に対象のsessionを止め、秘密を回収する。保存済みの本人がいない旧データも再読込時に同じ条件で修復する。通信で届く旧返信にはACKを返さず、共有で届く旧返信も受理しない。再登録は新しい招待IDから行う。共有済みURLの相手側での失効と削除同期は別の契約。サインアウトは即停止し古いログイン世代のcallbackを拒否する。同一アカウントの再ログインは保存pendingを明示再開できる。account削除・保存グループresetは既存namespaceのmanifestとKeychainの消去へ追随し、音声設定resetの消去範囲は拡大しない |


## 個人登録を兼ねるグループ招待

新しい相手への招待は、独立した個人招待の秘密にContactGroupInvitation（対象id・名前・group鍵）を添えた署名付きcontact tokenで表す。個人通話の鍵をgroup鍵から導出しない。既存の通常招待・添付なしの個人招待は従来のv6の署名入力を維持する。

| 契約 | 内容 |
|---|---|
| 署名の結合 | tokenのinvitedGroup全体と、DirectInvitationContextのinvitedGroupID・invitedGroupDigestを作者署名へ結合する。digestは添付の正規JSONのSHA-256。添付だけの後付け・削除・名前／鍵の変更を拒否する |
| 返信 | 受諾署名・作者のgrantは同じcontextの対象IDとdigestを含む。返信へgroup鍵や添付の平文を出さず、再送・到着確認も同じcontextへ結合する |
| 原子的な受取 | 受諾時は相手・個人通話鍵・通常groupとその鍵・返信checkpointを同じmanifest commitで保存する。groupは一覧へ加えるだけで現在の通話を切り替えない。同じIDの別kind／別鍵は拒否し、既存groupを上書きしない。保存失敗は旧manifestを保ち、再読込から同じ招待をやり直せる |
| 到着確認と復元候補 | 共有URL、近距離、Internetのどの経路でも、受諾と到着確認の署名を検証する。受諾署名から確認したアカウントと公開鍵が現在の端末の資格に一致し、対象グループが本人を参加者として保持している場合、到着確認を確定する保存処理で本人の対応を記録する。資格を照合できなくても個人登録の到着確認は完了できる。その場合は本人の対応を追加しない。削除・除外済みの参加者を戻したり、既存の対応を上書きしたりしない |
| 送信側の参加枠 | ContactInvitationRecord.invitedGroupIDと招待IDから導くinvite-pending-contactの枠を同じ保存で結合。検証済み返信が対応する枠だけを参加者に置換し、同じ本人が既にいるときは重複枠だけを外す。通常groupのプロフィール発見でこの予約枠を流用しない。取消・対象group／枠の削除は同じcommitで待機を無効にし、古い返信で関係を戻さない。保存済みの人の名前は保持 |
| 受取後の削除・退出 | incoming pendingの対象groupがなくなったら同じcommitでcancelledへ変え、返信checkpointの秘密参照を外す。成功した保存を読戻してから秘密を回収し、VMは対応する返信sessionを停止する。相手と独立した個人通話・鍵は残し、旧URLでgroupを再作成したり保存成功と扱ったりしない。旧経路で保存された欠落もload時に修復し、修復保存が失敗した場合は旧snapshotと鍵を保つ |
| 期限切れの送信枠 | `direction == outgoing AND state == expired` は、同じグループに対応する予約枠がある間だけ同じ人・グループへの招待を作り直せる。対象グループまたは枠を外す保存と同じcommitで `cancelled` にする。古い保存で取り残された記録も、グループを読み込むときに同じ判定で修復する。Usersの人を保持し、その人の次の共有は添付なしの個人招待とする |
| 保存と互換 | 添付の秘密は既存のContactInvitationPayloadのKeychainだけで保持。公開manifestとreceiptへgroup鍵を記録しない。添付なしは旧形式と同じ。旧アプリは新しい添付の署名を検証できず、この招待を受理しない |

この署名形式は保存・受諾・画面の共通操作から使う基盤である。関係とグループを同時に保存する共通操作と選択UIは実装済み。登録済みの相手への自動送信は下記の共通処理で実装済み。実環境受入は[新しい人のグループ招待](../../validation/未確認事項.md#新規相手招待の実環境受入)と[登録済み相手への自動送信](../../validation/未確認事項.md#登録済み相手へのグループ自動配送の実環境受入)で追う。


saveGroupInvitationSelectionは複数の未登録の人・予約枠・署名済みtokenと、対象groupを同じmanifest commitで保存する。MemberSelectionのdraftと新規group IDは編集画面の間固定し、保存失敗後の再読込で同じ人・groupが既にあれば追加し直さない。人数は保存と同じ代表枠で数え、新規groupが保存済みになった後も既存の選択者を二重に数えない。呼び名の編集はsynchronizeUserReferencesで未登録の招待名・予約枠へ反映し、未確認のmemberを本人のuserIDへ紐付けない。期限切れの再発行は同じ人・同じgroupと現在の鍵を使い、古い枠を置き換える。


### 個人招待の受諾を中継する暗号文

個人招待と個人登録付きグループ招待の受諾・到着確認には、[通常グループの返信中継](#通常グループの受諾を遠距離で届ける)のHTTP操作と暗号文形式を共用できる。Appは `contactBootstrap == true` の招待の形式・署名と添付の整合を照合してから、中継用の `slot` を組み立てる。HKDF-SHA256の入力は個人招待の `token.groupSecret` のUTF-8とする。saltは `rideintercom.contact-invitation-reply.slot.v1` とする。infoは個人招待の `token.groupID` と招待IDの `UUID.uuidString` をNULで区切ったUTF-8。出力32byteを小文字hexにする。期限は同じくUnix msへ切り捨てる。添付グループのID・鍵はslot導出に使わない。

受諾は招待した端末の公開鍵、到着確認は受諾端末の公開鍵へ封印する。開いた後も元の招待条件、対象の端末・公開鍵、受諾ID、方向、期限を照合し、署名の検証を経て保存する。中継で扱うのはslot、転送に必要な識別子と暗号文。受諾と到着確認の往復はローカルWorkerで確認した。発行者が受け渡し先を開く前でも、[Workerが発行者の署名と現行資格を照合して受諾を預かる](../server/Worker.md#発行端末が圏外の間に個人招待の受諾を預ける)。個人招待の発行時、端末証明に有効な形式のsessionBindingがあれば、同じ端末鍵でこの用途に署名し、リンクのtokenに `replyAdmissionSignature` を入れる。証明と公開鍵は招待の発行署名から共用する。受取側は信頼する発行元、招待した端末と公開鍵、slot・期限に対する署名を確認して、Workerの `admission` を組み立てる。証明がない場合や署名が一致しない場合は返信箱を開く許可を組み立てず、招待自体は既存の検証を使う。同じInternet設定の公開アカウントと端末鍵を照合できる場合、受諾・再試行、共有の完了、起動と前面復帰、Internet経路の復帰で既存の有限な返信処理を開く。受け手は保存した受諾を送り、発行端末は受信箱を取り込み、同じ人・個別通話と対象グループの参加者を保存してから到着確認を返す。到着確認をWorkerが受け付けたら、発行側で同じIDの確認の再送を終える。受け手は元の受諾に対応する到着確認を検証したときだけ保留を消す。発行者の資格の置換で署名付き受付を拒否されたときは、同じ転送を既存の受け渡し先に一度試す。期限、取消、サインアウト、資格または経路の変更では取込前の条件を再照合する。iOSは現在のアカウント・端末証明・経路を照合できる受諾を、保存後に既存の招待用背景URLSessionへ渡す。Appは署名済み受諾を封印し、同じ受諾ID・期限で[一件分の背景用のWorker入口](../server/Worker.md#背景転送から個人招待の受諾を預かる)へのファイル転送を開始する。iOSに渡すのは、現在の端末証明の署名・サービスorigin・発行区間を照合した公開鍵で、署名済み要求全体を封印した一件。送信元や宛先、受諾ID、端末資格をURL、ヘッダー、暗号化の外へ出さない。鍵がない場合、証明の区間と一致しない場合、期限を過ぎた場合は背景ファイルを作らず、Appが実行できる間は通常の受諾を使う。[Workerの暗号化契約](../server/Worker.md#背景転送から個人招待の受諾を預かる)タスクは同じ招待ID・セッションの照合値・受諾操作につき1つとし、再起動時には既存のタスクを取り込む。取消・期限切れ・資格変更等で対象外になったタスクは取り下げる。OSへ引き渡せなければ、実行時間内に既存のHTTP処理を使う。転送中も到着確認を照会できる。

Appからの通常の受諾もOSに預けた受諾も、Workerの受付が確認できたら同じ保留記録に受付を保存する。通常の受諾の成功後は現行のアカウント・端末資格・保留記録を再照合する。OSに預けた受諾では、元のURLからのHTTP 200、現行のアカウント・セッション照合値・保留記録・受諾ID・期限を照合する。受付が保存できたら同じ受諾の送信を終え、アプリを開き直しても到着確認の照会から再開する。受付後も表示と保存状態は返信待ちを保ち、相手の署名付き到着確認を検証して受け取ったときにだけ保留を解消する。確認できなかった転送は同じ保留から再試行できる。発行側の受信・到着確認の送信、受諾側の到着確認の取込はAppが実行できる間に進む。ロックが長く続くときの回線復帰と両端での完了は[実環境受入](../../validation/未確認事項.md#新規相手招待の実環境受入)に残る。

iOSが[背景更新](#iosが背景更新を許可したときの招待と個人削除)の実行時間を与えたとき、実行中の返信処理がなければ、保存済みの個人招待と個人登録付きグループ招待の返信を一度同期する。現行のアカウントとWorker資格が有効で、Internet経路を許可している場合に実行する。共有済みで有効な発行記録、到着確認の送信待ち、発行端末を照合できる受諾記録を対象とする。通知の許可は不要。通常と同じ署名・期限・アカウントの照合を使う。発行側は受諾を適用して到着確認を送り、受諾側は到着確認を取り込み、双方が現在の通話を維持する。通常の返信処理が前面復帰や回線復帰で引き継いだ場合は、古い実行の応答を適用しない。実行期限やアカウント変更で取り消した後も、有効な保留記録から次の機会に再試行できる。iOSが預かった受諾の受付を背景更新の最中に保存した場合は、同じ更新の終わりに該当する到着確認を1回照会する。返信処理は開始時に背景更新と通常の再試行を区別する。受付の保存後も同じアカウントの背景更新が実行中であれば、その更新に照会を引き継ぐ。照会の前に現行のアカウントと保留記録を読み直し、受諾を再送せず通常と同じ署名付きの到着確認を待つ。

## 登録済みの相手へのグループ招待の送受信の暗号形式

GroupInvitationEnvelopeは、既知のSavedUser.deviceKeysに対応する1端末へ、署名済みの通常group tokenを暗号化する。送受信のAccountPrincipalと端末ID・宛先鍵・無作為に生成する送信ID・期限・ephemeral公開鍵をAES-GCMの認証対象とする。ciphertextを含む全体をdeliverGroupInvitation用途で署名する。既存の署名形式・呼出し通知の許可とは独立した契約である。

| 契約 | 内容 |
|---|---|

## グループ招待の送信待ちと受領の原子的保存

GroupSnapshotはschema 11でトップレベルにgroupDeliveriesを追加し、schema 12で受取の仮保存と取消を表せるようにした。schema 18への移行でも既存の送受信記録、除外の受領記録と未登録の人・contactInvitationのpersonIDを保持する。schema 10以前の転送一覧は空で開始する。古いAppは未対応のschemaを開かず、読み捨てて上書きしない。

| 項目 | 保存と状態 |
|---|---|
| GroupDeliveryRecord | id・通知をまとめるnoticeID・groupID・宛先AccountPrincipal／memberID／既知公開鍵・期限・direction・state・任意のKeychain参照。仮保存中の受取だけ既知の送り主のmemberIDも保持する。確定した受取には封筒の署名対象データのSHA-256も保持する。既存の確定記録はこの値なしで読める。最大512件で、groupと同じ1 MiB manifestの上限を共用する。秘密と暗号文をmanifestへ置かない |
| outgoing pending | groupと直接相手の選択に結合し、同じmanifest commitで保存する。公開IDだけでは作らず、SavedUserのprincipalとmemberID・公開鍵を確認し、相手が対象groupに選択されていることを検証する。まだ署名準備ができない場合もKeychain参照なしで送信待ちを保持できる |
| 準備・queued | 送信IDと期限を固定してEnvelopeを用意し、暗号文のJSONを専用のimmutable Keychain参照へ保存・読戻してから送信へ進む。再試行では同じ暗号文を使う。server受付後はqueuedとなり、受取保存を確認したreceivedと区別する |
| incoming pending | 署名・宛先・既知の送り主と既存groupの鍵を照合し、送受信の記録と暗号文へのKeychain参照を先に確定する。この段階では一覧・通話先・タブ案内へ出さない。仮保存の失敗ではACKしない |
| received | 送信側のreceivedはKeychain参照を外し、送信待ちを終了する。同じグループ・同じ相手への新しい招待を保存すると、古いnoticeIDのoutgoing receivedを同じcommitで除去する。再読込時も保存順から同じ処理を行う。同じnoticeIDの複数宛先端末の記録、取消待ち、受取側の重複防止記録は保持する。受取側はgroup・鍵・incoming receivedを同じcommitで保存する。Internetでは先にWorkerの受領を確認する。既存の同じ鍵のgroupと呼び名は保つ |
| 削除・取消 | 送信側のgroup・選択相手・既知の宛先鍵がなくなるとpending／queuedをcancelledへ揃え、暗号文の参照を外す。相手アカウントの代表端末交代だけでは選択を取消さない。Internet側で取消を確認した送信記録は、近距離の送出記録がない場合に回収する。近距離の送出記録がある場合は別の確認として保持する。受取側は先に確定した取消、転送が見つからない場合、または確定待ちに送り主・対象groupを自分で削除した場合にincoming cancelledを残し、仮保存の参照を外す |
| 重複受取・期限 | incoming received／cancelledの送信IDは期限まで残す。同じ暗号文を再受取しても書き直さず、後から削除したgroupを作り直さない。期限経過した記録は除去し、未参照のKeychain項目はmanifestの読戻し成功後に回収する |
| 失敗 | groupと送受信の記録の部分保存をしない。書込失敗では旧manifestを保ち、再読込まで新しい書込を止める。秘密の回収はgroup・contact・groupDeliveryの3つの参照集合を使う |
| 実装段階 | UIの選択保存からHTTP自動送信、受取の仮保存・受領確認・一覧反映まで実装。新規groupは選択画面の固定IDを使い、曖昧な保存後の再試行でも二重作成しない |

<a id="グループ自動配送の実行契約"></a>

## グループ招待の自動送信の実行契約

Appは同じ保存操作から確定した、自分の未送信の送受信の記録を指定すると、[Workerの署名付き背景送信](../server/通知.md#背景用の一件分のグループ招待を受け付ける)用の要求を端末だけで組み立てられる。対象は現在のアカウント、相手の用途別許可、有効な受諾期限、未送信の状態が揃う場合。端末証明のアカウント・端末・セッションが現在の資格と一致する場合に署名する。通常送信と同じ送信ID・通知ID・期限・暗号文を使い、端末Bearerを認証ヘッダーや本文へ含めない。端末の保存を読み直した場合も内側の送信本文は同じ。既に受付または受領が確定した転送は対象から外す。

メンバーを外すなどして未確認の取消を保存すると、[Workerの署名付き背景取消](../server/通知.md#背景用の一件分のグループ招待を取り消す)を組み立てる。同じ端末資格で宛先・送信ID・元の期限に署名し、送信とは別用途にする。相手の送信許可や暗号文は取消の前提に含めない。背景送信の署名対象は37 KiBまでを扱い、背景取消や他の用途の端末署名には従来の上限を適用する。

iOSの通常Appは、未送信の招待や未確認の取消が保存されたとき、[端末証明に含まれる有効なWorker公開鍵](../server/Worker.md#招待を預けるサービスの暗号化公開鍵)で署名付き本文を暗号化する。アプリ用一時領域には `{sealed}` だけを書き、ファイル送信として1つの背景URLSessionに渡す。OSがコピーした後はApp側の一時ファイルを削除する。起動時は同じセッションから実行中の転送を復元し、送信ID・操作の種類・現在の端末資格を照合する。復元中に保存した場合は同期の最初に復元を終えてから渡す。OSが引き受けている間は同じ転送・操作の通常HTTP要求を重ねない。送信は同時に60件までとし、取消を先に渡す。有効なWorker公開鍵や端末証明を得られない場合、またはOSに渡せなかった場合は、記録を保ち、Appが実行できる間に既存の認証付き有限同期で進める。引き渡した時点では送信はpending、取消はInternet未確認のままとする。

背景URLSessionで維持する招待の送信・取消・個人招待の受諾は、現在の端末セッションを使って一度に判定する。起動時の復元と各操作の送信時に、この全体を照合して不要なタスクを取り下げる。グループ招待を取り消しても、条件を満たす別の受諾の転送は取り下げない。

取消の保存と近距離の受領確定では不要になった送信を取り下げ、資格の置換やサインアウトでは旧資格の転送を取り下げる。応答は元のURL、HTTP 200、現在の資格、保留中の操作・送信ID・期限を照合する。送信の結果はqueued・received・cancelledを保存する。取消の結果はcancelled・receivedのいずれでもInternet側の取消を確認済みとし、受領が先だった相手の保存結果を保つ。送り手が外したメンバーを戻さず、近距離に送出済みなら近距離の取消に必要な記録を保つ。転送失敗・不正な応答・実行打切りで結果を確認できなければ保留を保ち、次の既存同期で再評価する。UIKitが背景セッションの結果を渡すときはAppが同じセッションで結果を処理し、OSに完了を返す。OSが実機で回線を待つ時間とロック中の処理完了は[実環境受入](../../validation/未確認事項.md#登録済み相手へのグループ自動配送の実環境受入)で追う。[Appleの背景転送](https://developer.apple.com/documentation/foundation/downloading-files-in-the-background?changes=_8)

通常Appのログイン中は、Appが実行できる間に利用可能な回線の変化をOSから受け取る。利用不可から利用可へ変わったとき、同じアカウントの未完了の操作を調べる。招待では送信・取消・確定結果の照会・仮保存の受領確認、個人削除では送信・受領応答・回収が対象となる。いずれかが残っていれば、期限内の記録で既存のInternet同期を一巡する。招待を受け取れる状態で画面を開いている場合も、端末にまだ受取の記録がなくても同じ同期で受信箱を確認する。まだ同期中なら次の一巡を予約し、重なった要求はまとめる。最初の回線状態と利用可のままの更新は再試行の条件に含めない。近距離で受領済みの招待を再送せず、個人削除の中継は近距離で受領済みなら回収だけを進める。通知や前面復帰をきっかけに同期するときは、端末に記録のない招待も受信箱から取得する。保存済みの対象で同期を再開するときも同じ受信箱を確認する。

iOS版Appが背景で実行中に回線復帰を受け取ったときは、再開できる招待や個人削除がある場合か、現在のアカウントでグループ招待の送信を許可した登録済みの相手がいる場合に、同期の実行時間を要求する。招待をまだ保存していない受け手も、この条件で受信箱を確認する。回線復帰では、OSが実行を停止したAppを起動できない。回線が利用可能でもサーバーへの到達はHTTPの結果で判定する。

[iOSが背景更新を許可したとき](#iosが背景更新を許可したときの招待と個人削除)は、回線復帰の通知がなくても、グループ招待を同期する。期限内の送信・取消・仮保存の受領確認と、保持期間内の確定結果の照会を対象とする。現在のアカウントでグループ招待の送信を許可した登録済みの相手がいれば、通知の許可や端末に保存済みの招待がなくても、同じ同期で受信箱を一巡する。受取後は既存の署名・期限・保存の条件で確定し、通話を開始・切替しない。通常の同期がすでに進行中なら、その処理に任せる。背景更新の実行期限やサインアウトで中断したあとは、遅れて届く応答を適用しない。OSが引き受けている転送は背景更新で重ねない。

IntercomViewModel+GroupDeliveryが通常groupの作成・追加・新しい人との混在選択から同じ送受信の記録を作る。初回の自動送信はSavedUserのprincipalと確認済みdeviceKeysがある端末を対象にし、同一アカウントの複数端末へ個別暗号化する。noticeIDは相手アカウントごとに独立し、同じ相手の端末分だけ通知をまとめる。個人招待の署名付き受諾・返信で同じ保存ユーザーの追加端末が確認できた場合は、端末の登録と同じmanifest commitで追加端末向けに送信待ちを作る。対象は、同じ相手を現在も選択していて、期限内の最新の招待に有効な転送が残る通常group。新しい送信IDを使い、元のnoticeIDと期限を引き継ぐ。同じ端末への記録があれば重ねず、除外済みの相手には作らない。転送数の上限内で記録し、保存直後に既存の有限同期を要求する。追加端末は受信箱から取得し、既存の送り主検証と受領・保存を経る。追加端末が自分宛ての元の送信IDを使って署名付き要求を出せる。元の送信端末は既存の同期で候補の宛先を取得し、送信ID・所属・除外・最新の招待・期限を再照合する。確認できた宛先を同じ保存に加え、元の通知IDと期限を使って端末別に再暗号化する。要求されていない端末を列挙せず、保存ユーザーの端末鍵の登録も増やさない。

保存・起動・前面復帰・用途別許可の受取・グループ通知で有限の同期を起動する。新しい処理が必要になる保存・許可の受取・通知の到着またはタップが進行中の同期と重なったら、同じ同期の後にもう一巡を予約する。同じ巡の間に届いた要求を1つにまとめる。周期polling・silent pushを使わず、受信はWorker mailboxの保持上限に合わせて1回最大64件とし、空なら終了する。無効な封筒の破棄に失敗したら同じ封筒を再取得せず、その回を終了する。未到達・許可未交換はpendingのまま残し、後のイベントで同じID・期限・暗号文を再送する。送信の403は宛先ごとの許可拒否として、その記録をpendingに残して他の相手へ進む。401・429・サーバー障害・通信失敗では送信のその回を止め、周期再試行しない。HTTPクライアントは403をforbiddenとして識別し、成功や取消へ変換しない。serverのqueuedは受付、receivedは相手端末の仮保存後に受領確認を確定した状態を意味する。新しい暗号文を取得する前に、同じアカウントと宛先端末の仮保存を再開する。受領確認の応答消失や受領後の書込失敗では、同じ送信IDで次の同期時に確定状態を確認する。受領確認のDELETEは200と `status: received` で確定し、期限内なら一覧へ一度だけ反映する。`status: cancelled` や404は仮保存を取り消す。招待を取得したあと、受領確定より先に受取側が招待の送信許可を取り消した場合も、同じように仮保存を取り消す。200で状態が欠落しているか不正な場合は仮保存を維持し、通信断と同じ入口で次の同期を待つ。転送を破棄する条件は次の3つである。保存済みの同じgroup IDに確認できる別の鍵がある。種類が異なる。このgroupで送り主のmember IDや確認済みアカウントを除外している。どれかに該当すれば、その転送だけを破棄して次へ進む。除外判定は手動の通常招待と通話の本人確認と共用する。仮保存を再開するときも照合し、該当する仮保存と鍵参照を解放する。受領確定の応答を待つ間に競合や除外が生じた場合は、既存のgroupを維持して仮保存を取り消し、次の招待へ進む。Workerで既に確定した受領は変更しない。鍵を読めない場合は保管状態の再確認を待ち、破棄と区別する。

受領確認に対する409は、送り手が同じ招待を現行の資格で再送するのを待つ応答。受け手はその招待を仮保存したまま、同じ同期の残りでほかの招待を受け取る。次に同期できるときに、保留した招待を同じ送信IDで確認する。

通知の停止中にWorkerがHTTP 503を返した場合は、期限内の送信待ちと受領確認前の仮保存を維持する。受領の確定後にグループを一覧へ追加し、同期を再開するときは同じ送信IDを使う。[Workerの停止条件](../server/通知.md#登録済みの相手への暗号化したグループ招待の送受信)

通常の受信箱が空になったら、現在のアカウントに結び付いた端末証明を使って、追加端末として取得可能な招待を[Worker](../server/通知.md#登録済みの相手への暗号化グループ配送)へ照会する。端末鍵で小文字の送信IDを用途別に署名し、元の招待ごとに受取宛先を登録する。取得・要求は既存の同期機会に限り、1巡で最大64件。404は古いWorkerや該当しなくなった招待として扱う。個別の403では次の招待へ進み、通信や資格の失敗では次回の同期を待つ。応答後に同じログイン世代と資格を照合し、他のアカウントに要求を引き継がない。要求の時点で相手登録・グループ保存・通話は始めない。

追加端末への送信では、暗号文の署名・認証対象に元の送信IDを含め、受信箱から照合済みとして返るIDと一致させる。宛先の端末鍵で復号し、送り手の端末証明は自身が登録した同じHTTPSサービスの発行鍵で検証する。元の送信IDと用途別の転送認可に基づき、そのグループの受領だけを認める。個人登録・1対1・通知の権限を追加しない。元の送信IDは仮保存の送受信の記録にも保持し、受領確定の応答を失った場合は再起動後も同じIDで確認する。既存のグループ鍵の競合や除外を検査し、受領の確定後にグループと鍵を一度だけ保存する。追加端末の到着で通知を増やさず、両端末の既存の同期機会で進める。

受諾期限内は送信または取消の要否を送受信の記録で決め、Internetの実行順、応答後の再評価、取消の確定、保存時の背景実行時間の要求で共用する。`outgoing AND (pending OR queued)` は送信、`outgoing AND cancelled AND Internet取消未確認` は取消とする。Internet側の取消が確定し、近距離分だけが残る転送は、Internetの保存時処理の対象外とする。通知受信と受信箱の同期条件は従来どおり適用する。

発行から7日で受諾期限となる。Appは同期時に期限切れの封筒と近距離の送信情報を回収する。送信側で受領・取消が確定済みの場合、または結果の確認に使える送信・取消の記録がある場合は、発行から28日を上限に送信ID、相手、期限と状態を保持する。暗号文をまだ作っていない未送信の記録は受諾期限で回収する。確定を待つ記録には送信待ちの表示を出さず、保存済みの受領・取消結果には同じ表示を使う。

期限後の同期では、未確認の結果を同じ宛先アカウントと送信IDの `GET` で照会する。応答のIDと元の受諾期限が一致し、結果が受領または取消の場合だけ、現アカウントの保存済み転送に反映する。404なら照会用の記録を回収し、通信や応答の照合に失敗したら次の同期機会に照会できるよう保持する。受諾期限が切れた招待は送り直せず、その招待から受取側のグループも追加できない。Worker側の結果保存の起算点は最初の受信箱への保存時刻で、App側の上限は手元の発行時刻から数える。[Workerの送受信の状況の契約](../server/通知.md#登録済みの相手への暗号化グループ配送)

iOSでは、操作や通知処理を中断できる地点まで進めるため、UIKitの `beginBackgroundTask` で有限の実行時間を要求する。実行時間は、未完了の送信・取消がある保存操作、現在のアカウント宛てのグループ招待通知の処理（前面での到着・本体のタップ）、再開できる記録がある背景での回線復帰で要求する。起点となる処理から戻る前に要求する。通知経由では送信記録がない受取側も対象とする。既に同期中なら同じ同期に時間を確保する。通常の起動・前面復帰の確認だけでは追加時間を要求しない。完了・サインアウト・OSの時間切れで時間を返す。時間切れではApp内の同期を取り消し、その同期から遅れて届いた応答は書き込まない。別にOSへ引き渡した転送は、OSが完了を通知したときに照合する。保存済みの記録と暗号文を保ち、次にOSが実行を許した同期機会に同じ送信IDを使う。実行時間を取得できない場合は、その時点で実行できる範囲に限り、同じ処理を進める。[Appleの実行時間の仕様](https://developer.apple.com/documentation/uikit/extending-your-app-s-background-execution-time)。

awaitの後には同じアカウント・資格世代を再確認し、サインアウト後の応答を書き込まない。保存の読込失敗・通知同意台帳の読込失敗では取得を進めない。受信は保存だけで、現在の通話・選択中のgroup・音声を切り替えない。メンバーを外した場合も、保存が成功した直後に同じ転送同期を要求し、未受領の送信IDをserverで取り消す。各巡では、未完了の取消を先に試みる。通常のHTTP送信では、受付をまだ確認できていない招待を、受付済みの招待の再送より先に処理する。Workerは送信を停止していても取消を受け付ける。同期中に別の転送の取消が確定した場合は、各送信前に現行記録を読み直す。圏外・時間切れでは取消済みの記録を保ち、次回の同期で再試行する。受信箱の最終確認までに反映された取消は、開始済みの取得にも適用され、ほかの招待は受信できる。送信の応答が不明な間に取り消した場合、Workerは初回受付に先行した取消も記録し、保持中に遅れて届いた同じ送信IDはcancelledとなる。Appは未作成を表す既存の404を取消の完了として扱い、429や通信失敗では再試行を残す。Workerは取消・受領確認が成功した応答に受信箱の確定状態を含める。相手が暗号文を取得した後でも、受領より先に取消が確定すると一覧に出さない。受領確定後のgroup・手動共有・近距離で受け取ったデータへの削除反映は削除同期で扱う。[Workerの取得契約](../server/通知.md#登録済みの相手への暗号化グループ配送)。

### 近距離での転送の保存と確認

近距離の接続資格は、確認済みの自身のアカウントと、同じ発行元の別アカウントとして保存済みの相手端末に対して求める。自身の端末秘密鍵と、個人登録で照合した相手端末の公開鍵でP-256 ECDHを行う。資格を求める段階で、未登録の端末、公開鍵のない端末、自身の端末IDまたは公開鍵、形式の不正な端末情報を退ける。

HKDF-SHA256のsaltにUTF-8の `rideintercom.group-delivery.nearby.v1` を使う。sharedInfoには端末IDの昇順で並べた両端の端末IDと公開鍵を交互に置き、NULで区切る。端末IDはASCII、公開鍵は65バイトのX9.63形式をパディングなしのbase64urlで表す。32バイトの出力を同じbase64url形式で表し、用途名をgroupID、符号化した出力をsecretとして既存の `RTCCredential.derived` に渡す。両端が同じ端末IDと鍵の組で計算すると同じ資格になる。導出した値は交換せず、保存先へ書き込まない。

既知の端末と接続済みの場合のApp処理は、Internetと同じ送信ID・暗号文を使う。受け手は通信の相手IDと封筒の送り主、保存済みの個人登録・署名鍵、宛先、期限、グループの鍵と除外を照合する。通常の転送を対象とし、Workerで追加宛先を照合した転送はInternetで扱う。

受け手はグループ・鍵・受領記録を同じ保存で確定した後、暗号文を含む封筒の署名対象データのSHA-256に、受領専用の用途で署名する。送り手は受領の送信元・端末鍵・保存済みの暗号文と照合してから受領済みにする。遅れたInternet側の受付で受領済みを送信待ちに戻さない。受け手は期限内に同じ内容が再送された場合、保存済みの値で受領を確認できる。同じ送信IDでも内容が違う場合や旧記録に照合値がない場合は近距離の受領を返さない。受領済みのグループを後で削除しても再送では復活させない。

### 自動探索の開始と停止

圏外で登録済みの仲間をグループへ招待できるよう、Appの保存と前面への起動・復帰からRTCの[宛先別探索](../packages/RTC.md#登録済み端末を宛先にした探索)を開始する。Appは受領と画面状態を所有し、RTCは広告・認証・送信だけを担う。保存済みの本人確認情報を使い、新しいInternet資格の取得・通知許可・通話開始を待たずに近距離を試す。もともとのグループ作成で利用者が選んだ接続と、既に続いている通話を保つ。

準備済みの条件は `現在のアカウントの保存が可能 AND 保存済みの本人確認情報が有効 AND 近距離が有効 AND 照合できる相手端末が1台以上`。送信候補には、次の条件をすべて満たす転送を含める。 `outgoing AND (pending OR queued) AND 現在時刻 < expiresAt AND sourceRequestID == nil AND 宛先情報が保存値と一致`。時刻はepoch秒で比較する。照合する宛先情報はアカウント、端末ID、公開鍵である。Workerの認可で追加した端末への転送は既存のInternet同期を使う。

Appが近距離の処理を呼び出す理由は、起動・復帰や経路設定の変更、保存、探索の再評価、送信試行内での次の宛先への切替のいずれかとする。新しい送信試行を開けるのは起動・復帰や経路設定の変更と保存である。保存だけが新しく加わった送信候補を優先し、背景実行時間の要求につながる。Appが現在の試行で広告する宛先を決め、RTCには照合済みの相手と広告する宛先を渡す。

| 条件 | 探索・試行 | 保存と表示 |
|---|---|---|
| 準備済みで起動・前面復帰 | 既知の相手の広告を探索。送信候補があれば広告も開始。送信候補がない間は探索だけ | 自分宛ての有効な招待を受け取り、グループ・鍵・受領を一度で保存 |
| 準備済みで保存後の送信候補あり | 一度に1つの送信試行を開始し、同じ試行中の保存はその回で反映。iOSでは保存が戻る前に有限の背景実行時間を要求 | 保存の成功によって送信待ちが確定。その場で通信エラーを保存失敗へ変えない |
| 送信試行中の保存で、直前の候補集合にない送信IDと操作種別の組が加わる | Appの期限をその保存から20秒に更新し、旧タイマーの終了を無効にする。宛先と資格が同じなら接続・送信済み記録を維持。既に取得したiOSの背景実行時間を使う | 新旧の受け取りが確認できていない送信記録を同じ試行で進める |
| 送信試行中に同じ送信IDと操作種別の候補を再評価 | Appの期限を維持 | 同期要求だけでは試行が延びない |
| 前面を離れる | 開始済みの送信試行を保つ。通話の音声が使える状態なら、マイクをミュートしていても、探索と自分宛ての受取を続ける。背景でも、音声を開始・再開した時点で探索を始める | 現在の通話と保存値を保ち、受け取った招待で通話先を替えない |
| 背景で通話の音声を止める | 自分の送信試行が残っていなければ探索を止める。iOSが実行を停止したAppは、近距離の招待では起動しない | 未受領の招待は次に探索できるときに、相手の同じ送信から受け取る |
| まだ広告していない宛先がある AND（現在の宛先の処理が完了 OR 現在の宛先集合を選んでからの経過 ≥ 8秒） | 広告を一度切り替えて次の宛先を試す。試行全体の期限とiOSの背景実行時間を共用する | 先行する宛先が不在でも後続の宛先に進み、先行する未受領の記録を保持 |
| 後続がなく現在の宛先の処理が完了、開始または最後の期限更新からの経過 ≥ 20秒、またはiOSの時間切れ | その回の広告を終了して背景実行時間を返す。前面または通話の音声が使える状態なら探索を維持。保存・起動・復帰の次の機会に送信候補を再評価 | 未受領の同じ送信ID・期限と準備済み暗号文を保持 |
| サインアウト、近距離を無効化、保存不可、またはRTCの起動失敗 | 近距離の試行・探索を止める。交換を更新した場合は前回から遅れて届くイベントを捨てる | 有効な既存データを保ち、到達していない相手を受領済みにしない |

1つの広告では宛先端末を最大7台選ぶ。新しい保存、同じ広告で試行中の端末、未試行の端末の順とし、各区分の中ではexpiresAtの降順とする。全体の実行時間が切れた場合、同じアプリモデルでの次の同期は、現在の順送りでまだ広告していない宛先から進める。全宛先に一巡した後の新しい同期で、残った未受領に再び試行の機会を与える。プロセスを作り直したときは保存済みの未受領から選び直す。各宛先に認証済みの接続がある間は、その接続につき各送信IDの招待・取消をそれぞれ一度送る。切断後に同じ試行内で再認証した場合は、受領がない転送を同じ暗号文で再送する。転送するフレームはUTF-8 JSONで、外側に単一の `invitation` または `receipt`、その内側の `_0` に既存の封筒または受領を置く。送信側は保存済みの暗号文で署名付き受領を照合して `received` にする。受信箱経由の `queued` と、近距離かInternetでの受領確定は同じ送信IDの状態として扱う。

送信前にその転送の取消と保存済みの宛先を再照合する。近距離送信をRTCへ渡す直前に、同じ送信IDでKeychainに保存した封筒を取り出す。その署名対象データのSHA-256を計算し、Appのmanifestの `nearbyHandoff.envelopeDigest` に保存する。確認値の保存に失敗したらRTCへ渡さない。同じ封筒の再送で値を追加書込しない。近距離を試していない転送や旧形式の値はこの項目を持たない。

| 記録の条件 | 保存に残すもの |
|---|---|
| 受領を確認 | 送出の照合値と暗号文参照を外す |
| 未受領の取消を保存 | 暗号文参照を外し、送出時に保存した照合値・宛先・期限を同じ送信IDで保持 |
| Internet側の取消を確認 AND 近距離の送出記録あり | `nearbyHandoff.internetCancellationConfirmed` を保存し、同じInternet側の取消を再要求せず、近距離の記録を保持 |
| Internet側の取消を確認 AND 近距離の送出記録なし | 送受信の記録を回収 |
| 現在時刻 ≥ expiresAt | 経路にかかわらず送受信の記録を回収 |

Internet側の取消の確認には、既存契約でWorkerに記録がないことを示す404を含む。送出という記録はRTCに渡す準備の成立を示し、相手側の受信や受領は署名付き受領の照合で判定する。

### 近距離の取消を受け取る

受取側は、招待を保存する前の取消を確認し、同じ封筒が遅れて到着しても確定しない。受領確定後のグループには、別の所属変更や削除の契約が適用される。Appが保存と署名付き応答を所有し、RTCは既存の宛先別通信で運ぶ。

フレームの外側は `cancellation` または `cancellationReceipt`、内側の `_0` は取消または応答。取消の `target` は、送信ID・group ID・送信者のアカウントと端末ID・宛先のアカウントと端末IDと公開鍵・期限（epoch秒）・署名対象の封筒のSHA-256で構成する。`proof` はキー順を固定したUTF-8 JSONの `target` に対し、`cancelGroupInvitation` 用途で署名する。受取側は、接続の送信元とtargetの端末ID、保存済みの送り手のアカウントと端末鍵、現在の宛先と自分の鍵、`現在時刻 < expiresAt ≤ 現在時刻 + 7日 + 300秒` を照合する。応答は `decision` に同じ `target` と結果 `outcome` を含む。宛先端末が `acknowledgeGroupInvitationCancellation` 用途で同じキー順のJSONに署名する。

| 入力と前提 | 結果 | 副作用 |
|---|---|---|
| 接続元・署名・宛先・期限のいずれかが不一致 | 応答なし | 保存を変更しない |
| 同じ転送・宛先・グループ・封筒の受領が既に確定 | `alreadyReceived` | 既存グループと鍵を保持 |
| 上記の受領がなく、同じtargetの取消を既に保存 | `cancelled` | 同じ結果を返し、追加保存しない |
| 上記の受領がなく、未記録の有効な取消 | `cancelled` | targetを保存してから応答。同じ封筒が仮保存されていれば、同じcommitで取消に変え暗号文参照を外す |
| 取消済みtargetと完全に一致する封筒が後着 | 保存なし | 近距離の受領を返さない。Internetでも確定せず既存の破棄を使う |

GroupSnapshotのschema 18に `nearbyGroupCancellations` を加える。既存の除外の受領記録を保って移行し、schema 17以前の取消一覧は空とする。取消のtargetは最大512件とし、manifestの1 MiB上限を共用する。永続化に失敗した場合は署名付き応答を返さない。期限到達後は次の保存または回収で除去する。追加端末向け転送、別の送信IDや暗号文、手動共有済みのグループに適用しない。取消の送信側は、保存・起動・復帰の際に次の条件を満たす転送を候補に含める。 `outgoing AND cancelled AND expiresAt > 現在時刻 AND 近距離の送出記録あり AND 近距離の結果未確定`。現在も照合できる宛先のアカウント・端末ID・鍵が一致するときに、その転送のtargetを保存済みの値から作り、招待の再送より先に取消を送る。同じ送信IDの招待と取消を別の操作として記録するため、招待を送った接続を継続していても取消を送れる。取消の保存で新しい操作が加わると、既存の送信試行の期限を更新する。

| 送信側が受け取った結果 | 管理する送受信の状況 |
|---|---|
| 同じ宛先の署名付き `cancelled` AND Internet側の取消確認済み | 取消の送受信の記録を回収 |
| 同じ宛先の署名付き `cancelled` AND Internet側の取消未確認 | 近距離の送出記録を外し、Internetの取消が終わるまで送信IDを保持 |
| 同じ宛先の署名付き `alreadyReceived` | `nearbyHandoff.recipientAlreadyReceived` を期限まで保持し、近距離の再送を終了。相手のグループ・鍵・通話には別の所属変更を適用 |
| 応答なし、署名・対象が不一致、または保存に失敗 | 近距離の取消を確定せず、次の実行機会で同じ対象へ再送 |

近距離だけで確認した取消も、あとからInternetで確定すれば同じ記録を回収する。相手の登録または旧鍵がすでに失われた場合の転送と、受領確定後の所属変更は[削除同期](../../backlog/未実装課題.md#相手とグループの削除を同期する)で扱う。

iOSがアプリを停止すると、近距離通信だけで受信処理を起こせない。許可された時間に実行できなかった分は次の同期で同じ記録から進める。[Appleの背景実行制限](https://developer.apple.com/forums/thread/685525)

## グループタブ案内の保存メタデータ

GroupSnapshot.Record.groupTabOfferAcknowledgedは任意のBool。新しく招待で受け取った通常groupだけfalseで保存する。通常の招待URL・個人登録を兼ねる招待・自動送信の3経路で同じ契約を使い、既存groupの再受取では戻さない。nilは旧データとして案内の対象外、trueは回答済み。schema 11へ任意の表示メタデータとして追加し、groupの編集で保持する。

回答は、到着済みのfalseのgroupを同じmanifest commitでtrueにする。通話・参加権・鍵・転送ACKには影響しない。旧groupやこの端末で作ったgroupへ後から案内を作らず、削除したgroupを案内のために復元しない。

グループ一覧の表示と、表示中のグループタブを明示的に隠す操作も、同じ確認済み保存を使う。通常groupの受取・鍵・転送ACKとは独立しており、確認を理由に参加済みデータを削除しない。

署名対象の個人招待・返信は共通のCodable型をJSONEncoderのsortedKeysでencodeする。小数付きの期限も同じ表記を使う。JSONSerializationの辞書を別途encodeした数値表記を署名対象として混ぜない。
