# 通話の通知仕様

CallKit・VoIP Push・AppleのPushToTalk frameworkを使わない。通常のAPNsアラートとUserNotificationsから、利用者のタップを既存の通話開始処理へ接続するAppの契約である。通知の受信・送信許可と、通話の所属・本人確認・利用権・24時間条件を分ける。認証資格と公開IDは[Worker契約](../server/Worker.md)、通話の実行は[共通操作](通信仕様.md#通話先と操作対象の共通境界)を使う。通知APIの詳細はserver側の通知仕様で定めており、Appはその固定DTOを使用する。

## 責務と入口

通常のAPNsでは通知の種類に対応する固定文を表示する。呼び出しの送り主を照会するのは、受け手が通知を開いても未接続の場合。名前と画像を表示前に解決する案は[通知拡張の設計](../../design/通知の設計.md#受け取る側の表示)で追う。

| 対象 | 契約 |
|---|---|
| HTTP | `InternetAccountClient`の通知extensionでdevice・grant・call requestを扱う。既存のHTTPS origin検証・redirect拒否・10秒request timeout・32KiB応答上限を共用し、native `ri1`資格だけを送る |
| 状態 | `CallNotifications`はログインモデルに属し、Nativeログイン世代、現在の確認済み公開principal、サービスと資格の一致を各await後に確認する。旧結果で新モデルの状態を変えない |
| OS | `NotificationSystem`が許可とAPNs登録を扱い、`AppNotificationBridge`がnative delegateを現在のAppCallOwnerへ渡す。単体・ローカル自動検証では実OS許可・APNs登録を要求しない |
| 許可 | OSでの許可とWorkerへの通知先登録は別の結果として扱う。[許可と通知先登録の順序](#端末の登録取消)に従う |
| 受取後の表示 | 前面ではpayloadのデータ形式のバージョン・requestID・recipientIDに加え、現在ログインのrecipient一致と端末受信ONを端末内で確認する。OFF・ログアウト・別recipient宛を表示しない。共通の`presentationOptions(for:)`で、`hasAnyActiveGroupConnection`が真なら`[.list]`（通知センターのみ。バナー・音なし）、偽なら`[.banner, .list, .sound]`を返す。接続待ち・音声一時停止も接続中として扱い、到着だけでは通話・画面の選択を変えない。この表示判定だけのためのネット照会はしない |
| 通知を開く | 通知の受信ON・現在のアカウント・recipient一致を端末内で確認する。接続待ち・音声の一時停止を含め現在の通話があれば、照会せず同じ通話の画面を開く（`callPresentationID`）。未接続でインターネットがオフなら、照会せずユーザー一覧を開く（`usersPresentationID`） |
| 送り主を照会する | 未接続でインターネットがオンならserverへ照会する。応答後は同じアカウント・モデルと受信条件を確認する。照会中に通話が始まった場合は今の通話を開く。未接続のままなら、経路設定がオンで現在のSavedUserを特定できた場合に限り共通の`requestCallStart`へ渡す。マイクの許可を待った場合も開始前に経路設定を確かめる。照会で特定できないか、応答時点でオフならエラーを出さずユーザー一覧を開く |
| 照会中にインターネットをオフにする | `CallNotifications`が進行中の送り主照会を取り消す。通知を開いた時点のアカウントと受信条件が続いていれば、今の通話かユーザー一覧を開く。照会後にマイクの許可を待っていた場合は、通話を始めずに現在の画面を保つ。オンに戻しても同じ操作から照会や通話を再開しない |
| 「接続」「無視」 | iOS・macOSは固定category`RIDEINTERCOM_CALL_REQUEST`へ2つのactionを登録する（[応答の操作](../../design/通知の設計.md#応答の操作)）。「接続」（`RIDEINTERCOM_CONNECT`、`phone.fill`）はoptions`.foreground`でアプリを前面にし（ロック中は解除を求める）、本体のタップ（default）と同じ応答処理へ通す。「無視」（`RIDEINTERCOM_IGNORE`、`xmark`）はoptionsなしの背景actionで、通知を閉じるだけ。何も読まず、送り主へ何も送らない。未知action・dismiss・別categoryのactionでは処理を起動しない |

## 端末の登録・取消

通知の許可と登録は購入状態から独立する。購入の確認は[利用権の仕様](利用権仕様.md)で定める。

| 状態・操作 | 契約 |
|---|---|
| 登録 | OSが返す可変長device tokenをその処理中だけ保持し、hex・environment・bundle topicをPUTする。tokenをUserDefaults・Keychain・ログへキャッシュしない |
| environment | Infoの`RideIntercomAPNsEnvironment`を優先し、developmentをsandbox、productionをproductionへ変換。キーがない検証buildではDebug/sandbox・Release/productionへfallbackする。Info・OS別entitlement・単一build設定を揃える設定本体はOS設定工程の責務 |
| OSの許可 | `ContentView` が起動時にOSへalert/soundの許可を求める。OSの初回シートの後は、同じ要求でもOSが現在の結果を返す。通知設定はOSで行う。[通知の許可を求める時点](../../design/通知の設計.md#通知の許可を求める時点) |
| 登録の起点と前提 | 起動時にOSの許可が得られ、現在の通話モデルがあれば `CallNotifications.start()` を呼ぶ。サインイン後、前面復帰時、インターネット通話の端末資格を保存したときは、OSの許可によらず呼ぶ。現在のアカウントの資格とOSの許可がそろえば、登録の希望をアカウント別の既存Defaultsに保存する。通話用の端末資格は[回線に応じた端末登録](通信仕様.md#通常サインインからインターネット通話の端末を登録する)で準備する |
| 登録と通信設定 | インターネットがオフ、または回線が使えないと判明している間は、OSへトークンを求めず、Workerへの登録と解除を始めない。待機中にOSから届いたトークンは保持しない。OSの許可と現在のアカウントに基づく受取判定は続ける |
| 登録の確定と再試行 | OSからトークンが届いたらWorkerへ登録する。Workerの成功応答と現在のアカウント・登録世代を確認して登録完了を示す。アプリが実行できる間に回線を検出したとき、または設定をオンに戻したときは、許可と端末資格を確認し、登録が未完了ならOSへトークンを要求し直す。前面復帰時や端末資格の保存後も登録を試す |
| OSで通知をオフにしたとき | アプリがOSの設定を確認した時点で受信の希望をオフにし、タップと前面表示を拒否する。資格や回線を使えなくても、端末側の受信を止めて宛先の取消を待機させる。回線検出、設定をオンにしたとき、前面復帰で、現在も取消が必要ならDELETEを試す |
| 端末側の取消と再開 | 同じモデルのPUTとDELETEは直列に処理し、実行直前に資格・通信設定・通知の希望を確認する。インターネットをオフにしたか回線断を検出したら、実行中と待機中の要求を取り消す。Workerで処理済みの場合もあるため、復旧時は現在のOS許可を読み、登録か取消をやり直す。[通知先変更の番号](#通知先変更の番号を保存する)を付け、遅れて届いた古い要求はWorkerで拒む |
| ログアウト・削除 | 待機と旧表示を退役させる。通信できる間は進行中の登録の後に旧資格で宛先の取消を試みる。通信できない間は取消待ちを保つ。既存の資格失効とアカウント削除も送信対象を無効にする。宛先の取消の応答を待たずログアウトを進める |

### 通知先変更の番号を保存する

登録と解除は、待機列へ入れる前に番号を確定する。Keychainで保存した番号を1増やして保存する。途中で取り消した処理や応答を受け取れなかった処理にも同じ番号を割り当て直さない。要求には[Workerが受け付けるヘッダー](../server/通知.md#apns端末トークンの更新と失効)で送る。Workerが409を返した場合も成功と扱わない。その後の登録・解除は、現在のOS許可と資格を確認し、新しい番号で試す。

番号の保存先は、既存のアカウント別 `InternetConnection` Keychainサービスの `notification-device-revision` である。iOSでは通話用の端末資格と同じ端末専用の保護を使う。再起動や同じ端末での資格更新でも、保存済みの番号から続ける。アカウント内データの消去では既存の資格と同様に削除する。番号を読み書きできない場合や上限に達した場合は、宛先を変更する要求を送らない。

### APNs端末トークンの取得と再インストール

APNs端末トークンは、端末上のアプリに通知を届けるための宛先である。利用できる範囲は端末・アプリ・APNs環境の組み合わせで決まる。通知が許可され、現在の端末資格が使えるときに、上記の登録処理でOSから受け取った値をWorkerへ送る。有効な同じ宛先への複数の通知には同じ値を使える。アプリはトークンを端末内に永続保存せず、登録のたびにOSから現在の値を受け取る。[AppleのAPNs登録仕様](https://developer.apple.com/documentation/usernotifications/registering-your-app-with-apns)・[APNsの送信仕様](https://developer.apple.com/documentation/usernotifications/sending-notification-requests-to-apns)

| 条件 | 扱い |
|---|---|
| 同じ端末でアプリを削除して再インストール | トークンが変わり得る。初回起動後は通知の許可と端末資格を確かめ、OSが今回返した値で登録する。再インストール前の値や、その値のAPNs応答を起動の前提にしない。[Apple担当者の説明](https://developer.apple.com/forums/thread/818187) |
| バックアップからの復元、別端末への新規インストール、OSの再インストール | Appleは新しいトークンを発行する。復元したアプリのデータと通知先の登録は別の手続きであり、新しい環境でOSから受け取った値を登録する。[AppleのAPNs登録仕様](https://developer.apple.com/documentation/usernotifications/registering-your-app-with-apns) |
| iOS Simulator | APNsから発行されたトークンは、そのSimulatorと実行するMacの組み合わせに固有で、Sandboxで使う。有効な間は同じ組み合わせへの再送に使える。別のSimulator、別のMac、実機への流用はできない。[AppleのSimulatorの仕様](https://developer.apple.com/documentation/xcode-release-notes/xcode-14-release-notes) |
| 開発署名とTestFlight | 開発署名はSandbox、TestFlightを含む配布署名は本番APNsに登録する。同じ端末・同じアプリでも各環境で取得したトークンを別々に使う。[AppleのAPNs環境entitlement](https://developer.apple.com/documentation/bundleresources/entitlements/aps-environment)・[APNsの応答仕様](https://developer.apple.com/documentation/usernotifications/handling-notification-responses-from-apns) |

Workerは[通知先の更新と失効](../server/通知.md#apns端末トークンの更新と失効)に従って再登録を扱う。

## 相手ごとの用途別許可

| 対象 | 契約 |
|---|---|
| 対象 | 直接招待でSavedUserになり、同じサービスの確認済みprincipalと保存端末鍵がある相手だけ。group内だけの相手、名前の一致、相手IDの知識だけでは発行・送信しない |
| 同意 | 個人で登録した相手（直接招待のSavedUser）は全員、通知を送ってよい相手とする（2026-11-11の利用者指示。相手ごとの切替は置かない）。OSが通知を許可している場合に限り、受信者はまだgrantがない相手ごとにserver grantを発行する。その機会は`start()`、直接の招待で互いの登録が済んだとき、1対1の接続で相手を本人確認できたとき（`allowEveryContact()`）である。オフラインなどで失敗したら次の`start()`で再試行する |
| 交換する接続 | 相手との内部1対1groupで、対象principalが一致し、接続・認証中のpeerがその相手1人だけの場合に限定する。自分の別端末を相手扱いせず、通常groupでは送信と受理の両方を禁止する。既存broadcastへ個人用capabilityをそのまま流さない |
| 登録の時点での交換 | 直接の招待の受け渡し（`ContactInvitationSession`）でも交換する。最初の接続を待たずに、最初の呼び出しから通知できるようにするためである。互いの保存が済んだ後（招待した側は相手の受領を保存した後、受け取った側は確認の返信が届いた後）で、接続・認証中のpeerが登録した相手1人だけの間に限り、送信と受理の両方を認める。招待のリンクは転送され得るため、他のpeerがいる間は送らず、届いても捨てる。署名と保存済みの端末鍵の照合は1対1の接続での交換と同じ。受け取った側は、2つの許可が行き交うか10秒たつと受け渡しを閉じる（この端末が通知を使えないときは、これまでどおり登録の完了で閉じる）。発行や受け渡しに失敗しても登録は成立し、最初の1対1の接続で交換し直す |
| 署名 | 既存の端末署名鍵を用途`callNotificationPermission`へ区切って使う。owner・allowedSender・revision・grantを署名し、受信は保存済みの直接相手の鍵と照合する。group共通秘密を通知許可の発行権限へ変換しない |
| capabilityの照合 | 受領時と送信前にJWT内のissuer・audience・recipient・sender・grantIDが選んだ相手と本人に一致することを拒否条件として確認する。decodeだけでserver署名や有効性を信頼せず、実送信の署名・active grant・本人資格の検証はserverに任せる |
| 保存 | 発行したgrant、相手から受け取ったcapability、取消と再送のrevisionを保存する。保存先は既存のアカウント別`.InternetConnection` Keychainの`notification-permissions`とする。GroupSnapshotや通常設定へcapabilityを混ぜない |
| 発行revisionと回収 | アカウント別の既存Defaultsへ単一の発行counterを保存し、新しいrevisionはcounterと現在行のrevisionの大きい方に1を加える。取消済みでreceivingがなく受信OFF、同principalのSavedUserもない現在ownerの行だけを回収する。回収前に旧行の最大revisionをcounterへ引き継ぎ、Keychain保存成功後だけメモリから外す。再追加でrevisionを戻さず、符号・破損・上限は既存の失敗経路へ戻す |
| 既知の別端末 | 最後に受領した相手端末鍵とrevisionだけを保持し、同じ鍵の古い更新を拒否する。別の既知端末の独立counterで新grantを受け取れ、その端末の取消だけが現在選択中のgrantを外す。他端末の取消で現在の別grantを消さず、端末別の履歴台帳は作らない |
| 連絡先統合 | 既に確認済みの同じprincipalへ端末を統合しSavedUserのUUIDが変わっても、既知の許可と元のgrantIDを維持する。別principal・別サービスへ持ち越さない |
| 相手削除 | ローカルの受信許可を先に無効化し、本人が発行したgrantをDELETEする。送信権限とtapも現在のSavedUserから再解決し、削除済み相手を復活させない。失敗した既知の取消はオンライン復帰時に再試行する |
| 保存失敗 | 新grantを発行した後にKeychain保存が失敗した場合は、そのgrantをbest-effortで1回取消す。保存を成功扱いにしたり、独自の永続orphan台帳を増やしたりしない |
| 読取不能 | 読み取れない許可を空データで上書きしない。前面復帰の確認で再読取でき、端末の宛先取消は相手の許可データが読めなくても実行できる |

許可の保存・交換は現状端末別である。他の本人端末が別に発行したgrantの一括取消や、端末間の即時同期は提供しない。端末通知OFFは当該端末の宛先を外す。アカウント削除はserver側の当該公開IDの許可を取消し、再登録で旧許可を復活させない。新しい端末間同期の仕組みをこの工程へ追加しない。

## 送信結果・tap・保持する情報

| 対象 | 契約 |
|---|---|
| 送信 | 直接相手から受け取ったcapabilityとUUID requestIDだけをPOSTする。名前・自由text・group情報をserverへ送らない。送るのは1対1の接続を新しく始めたとき（`startCall`の`.user`。一覧・Widget・Watch・Siriのどこから始めても）に1回だけで（`noticeNewDirectCall`）、すでにその通話中なら送らない。端末の登録や受信許可の発行（起動・サインインの後に自動で進む）の処理中でも、送信は待たせず捨てない。手動の送信操作は置かない（[製品要求](../../requirements/製品要求.md#利用者に提供すること)の「呼び出しは親切な知らせとして1回送り、会話の始め方は利用者に任せる」） |
| 結果 | acceptedは通知サービスの受付であり、転送・閲覧・応答・通話成立を意味しない。結果は画面に出さず、再送・状態の定期polling・応答待ちの表示をしない（呼びっぱなし） |
| 通知本文 | serverの固定`CALL_REQUEST_TITLE`/`CALL_REQUEST_BODY`を英日でlocalizeする。payloadはデータ形式のバージョン・requestID・recipientIDだけで、表示名・自由文・group秘密・capabilityを含めない |
| 未接続で開くときの再確認 | recipient一致・端末ONを端末内で確認後、GETでserverの120秒期限、取消、grant、元sender資格を再検証する。戻ったsenderを現在の直接相手へ照合し、await後も世代・資格・期限・ローカル許可を再確認する |
| 通知を開いてからマイク許可を待つ | 送り主の照合に使ったサーバーの期限を通話開始へ引き継ぐ。許可待ちで期限に達した場合は、許可しても接続と新しい呼び出しを始めない。未接続ならユーザー一覧を開く。許可を待つ操作が取り消された場合や、その間に通話が変わった場合は、現在の画面を保つ。通知からの接続が引き続き有効でもマイクを拒否した場合は、接続せず設定での許可を案内する。閉じると開始前の画面に戻る |
| 受信許可の取り消し | 通知を開いた時と同じ受信許可が、接続直前にもこの端末で有効か確かめる。マイク許可を待つ間に端末の通知が無効になった場合や、受信許可の取り消しが端末に反映された場合は、現在の画面を保つ。端末の通知を有効にし直したり、受信を許可し直したりしても、その通知からの操作は再開しない |
| 取消 | Appは送った通知を取り消さない（server側の取消APIは使わない）。期限切れの通知は既存の通話を終了させず、新しい開始だけを拒否する |
| データ消去 | Keychainは既存のアカウント別`.InternetConnection`全消去、希望と取消pendingは同じDefaultsの全消去へ含まれる。serverへ相手一覧・表示名を保存する機能を加えない |

Workerは1対1の呼び出しを、OSの既定音を指定した通常のAPNsアラートとして送る。Appの[前面での表示判定](#責務と入口)は、OSが背景で表示する通知には適用されない。背景でも静かに届ける変更は[未実装課題](../../backlog/未実装課題.md#背景の通話中は呼び出しを静かに届ける)で追う。接続の開始には利用者の操作が必要。実OS、鍵設定、外部転送と署名の受入は[未確認事項](../../validation/未確認事項.md#通常通知の受入)、ローカル証跡は[通知Appの接続と認可の検証](../../validation/history/通知Appの接続と認可の検証.md)を参照する。

## グループ招待の送受信の用途別許可

登録済みの相手へのgroup転送は、呼出し通知のcapabilityと独立したaud=rideintercom-group-invitationを使う。CallNotificationPermissionのgroupReceiving／groupSendingを既存のアカウント別Keychainへ保存する。CallNotificationPermissionMessage.groupGrantとgroupInvitationsSupportedを署名に含める。外付けの未署名grant、呼出しaud、未知の相手・端末鍵を拒否する。groupの受信revisionとsourceは呼出しと別に保持し、別の既知端末の取消や旧版メッセージで現在のgroup grantを誤消去しない。

| 条件 | 挙動 |
|---|---|
| 発行 | 起動・前面復帰と直接登録の交換で、未発行の直接相手に専用grantを用意する。OSの表示通知がOFFでも受信箱の取得許可は発行でき、APNs宛先の登録は行わない。失敗は次回の起動・登録交換で再試行し、periodic pollingを設けない |
| 交換 | 既存の本人確認済み1対1と、直接登録の有限な制御専用sessionを共用する。新しいrideintercom.group-invitation-permission.v1へ両用途の署名済み許可を先に送る。続いて従来のrideintercom.call-notification-permission.v1は旧形式のまま続けて送る。旧相手は新namespaceを無視して従来の呼出し許可を検証できる |
| 旧形式 | groupInvitationsSupportedのない署名メッセージは従来どおり呼出しだけを更新する。group grantを消去せず、新用途の許可が未交換の相手に自動送信が使えるとは扱わない |
| 取消 | 相手の削除で両用途を端末内で先に抑止し、各grantを既存のDELETEで取消す。未完了の取消は再開可能。通知のOS表示OFFはgroupの受信箱許可を取消す操作にしない |
| 実装段階 | 用途別の発行・交換からgroup送信待ち・HTTP受取保存まで実装。新しい相手には従来の名前付き共有を維持する |

## グループ招待の通常通知

前面に届いたときと通知を開いたときは、`AppCallOwner` が同じ手順で受取側を確認する。現在のログインに属するモデルで通知資格を読み、受取公開IDが一致するときだけ受信箱の同期へ進む。通知を開いて同期した後は、同じモデルとログイン世代が有効かを確認して画面を開く。

kind=groupInvitationはGroupInvitationTapでだけ解析し、CallNotificationTapはkind付きpayloadを拒否する。RIDEINTERCOM_GROUP_INVITATIONカテゴリには通話のConnect／Ignoreを付けない。通知は通話の有無にかかわらず通知センターだけに残す。背景はWorkerがpassive・音なしを指定し、前面はAppが現在の受取アカウントを確認して`[.list]`を返す。同じ招待の端末ごとの送信をまとめ、受取アカウントの[有効な通知先ごとに1回送る](../server/通知.md#登録済みの相手への暗号化グループ配送)。payloadは送信IDと受取公開IDだけを使う。受信では受信箱の保存を試み、現在の画面と通話を維持する。本体をタップすると受信箱を同期し、通話中は同じ通話、未接続ならグループ一覧（タブ非表示ならユーザー一覧）を開く。進行中の同期があれば、その同期の後にも受信箱を確認してから開く。iOSで通知処理の直後に画面を閉じた場合は、[有限の実行時間と再試行](通信仕様.md#グループ自動配送の実行契約)に従って受取と確認を続ける。Standardでグループタブが非表示なら、次にユーザー一覧へ戻り他の操作を終えたときだけ一度の表示確認を出す。通話画面や相手の詳細が表示中なら案内を保留する。

OSの通知許可がなくても、前面に戻ったときや、画面を開いたまま回線が戻ったときに招待を取得できる。グループ招待の送信を許可した登録済みの相手がいれば、iOSの背景更新や実行中の回線復帰でも受信箱を確認する。受け手が追加した端末宛ての招待も[通常の同期](通信仕様.md#グループ自動配送の実行契約)で受け取る。通知同意台帳が読めない場合とサインアウト後は転送を進めない。通知の到着・OS共有・APNs 200から受領を推測しない。
