## 移記後の判断基準を元の事例と別の事例で確かめる

2026-11-23。移記前の判断材料を `3a567f4c` の親と照合し、移記後の共有先 `1bf40108` の規定を読み戻した。2人の読み手には当時の回答を渡さず、現行の規定から次の行動と確認済みの範囲を答えてもらった。表の別事例は条件を変えた机上の検証である。

| 判定対象 | 元の事例で導いた判断 | 別の事例で導いた判断 |
|---|---|---|
| 用途の成立 | 音声UIの起動と単体試験の成功では相手の受話は未確認。受話を左右する経路と実際の出力を先に確かめる | エクスポート要求の受付だけならファイルの内容は未確認。利用者の手順で開き、期待したデータを照合する |
| モデル選択の効果 | 指示の読み取りに成功した時点で確認できるのは、例に対して正しい判断を返せたことまで | 単価と担当工程の時間が減っても、再入力・引き継ぎ・手戻りを含む完了までの費用・時間と品質を比較するまで全体の改善量は未確定 |
| 標準の入口での受入 | 署名付きArchive生成後も、登録・対象バージョンの一覧表示・選択後の詳細は観測した段階ごとに記録する | バックアップ保存後、想定した喪失条件から標準手順で復元し、必要な状態を照合するまで復元の成功は未確認 |
| PCを妨げる異常終了 | 不鮮明なプロセス名だけで原因を決めず、報告時刻・正式名称・直前の操作と終了理由を合わせる | アプリの試験が成功しても、補助ツールの再起動が続けば連鎖を起こす再実行を抑え、同条件で原因と対策の効果を調べる |
| 設定の実効値 | 固定環境の管理APIを読めても、ローカルの設定を変えただけでは次のビルドへの反映は未確認。環境側の値と実行結果を照合する | 保存API成功後も既存セッションが旧値なら、即時反映か次回開始時かを仕様で確かめ、その時点の動作で判定する |
| 担当間の連絡 | 宛先への直接送信が失敗したときは、未達の内容を特定し、主担当が使える経路で必要な内容を中継する | 新指示を送信しても旧条件で動いていれば、変更が影響する作業を止め、その担当に適用範囲と完了条件を読み戻してもらう |
| 依頼の範囲 | 試験の分類を記録する依頼では、対象・条件・判定を文書に残す。CIの新設や有料試験は着手範囲外 | 移行案だけを求められたら実施・停止・復旧条件を記す。書き込み権限があっても設定の変更や配置には進まない |
| 全体整理の受入 | 局所の改善を共有しても全体レビューと重要指摘への対応が残れば、同じ回を続ける | 仕様整理後に行うコード再整理は、更新後の構成で回帰試験を実行し、その構成全体を3回レビューする。前回のレビュー回数を流用しない |
| UI部品の所有 | 同じ表示でも操作が異なる場合、両モードの部品を分け、共通の機能・状態はその所有元で管理する | 表示・語・配置・操作が一致する共通部品は所有元で直して両モードを確認する。一方の操作だけ変わる要求なら境界を見直す |
| 用例の比較 | 表示色は「赤」「緑」、試験の成否は「失敗」「成功」で示す。色名の3資料から試験報告の表現頻度は推定できない | 改訂版で票が増えても転載を除くと同数なら採用を保留する。同じ用途の独立資料と不足する根拠を示す |
| 意味の修復 | 全体修復のレビューで同一モデルを3担当に分けても1種類。必要な種類が揃うまで完了を保留する | 英訳が自然でも操作主体が消え、原文と違う行動に読めるなら、元の要求で主体・条件・結果を確かめ、両言語を直して再度照合する |
| 作業場所と統合権限 | 担当が増えても製品を編集するのは既存mainの主担当1人。同じ受入の読み取り検証を分担する | 隔離を許可した変更でも統合には対象差分と共有先についての許可が要る。許可後の変更が影響する範囲を確かめる |

外部設定を利用者へ引き継ぐ条件も主担当が照合した。元のApple・Cloudflare設定では実装・自動化で済む準備を先に終える。別の例で通知連携に管理者の初回同意が必要なら、担当が設定できる部分と自動試験を済ませ、管理者にしかできない操作と同意後に確認する結果を渡す。いずれも実装不足を利用者の操作待ちに移す判断にはならない。[外部設定の引き継ぎ](../../policies/開発方針.md#applecloudflare等の外部設定を常に手順化する)

### 読み戻しで直した箇所

- コア優先スキルに、文書の形式・参照だけで受け入れる読み方が残っていた。判断基準を変えたときは、元の事例と別の事例で行動・停止・受入条件を照合するよう、入口と参照資料を文書作成規約に揃えた。[事例で判断を確かめる条件](../../policies/文書作成規約.md#望ましい行動を示す書き方)
- モデルの自己申告の扱いは過去の評価記録に偏っていた。利用可能な設定は実行環境で、依頼する仕事への適性は成果物と検証結果で判定する条件を戻した。[モデルの選択基準](../../../.agents/skills/efficient-work/references/モデル選択と再利用.md#仕事に必要な能力から選ぶ)
- 隔離した差分の統合条件は残っていたが、作業分担スキルの入口が旧見出しを参照していた。現行の判断手順へ修正した。[隔離した変更の統合条件](../../../.agents/skills/efficient-work/references/実行管理と指示更新.md#隔離が必要な変更をmainへ統合する)


修正後、読み手が現行の入口とそこからたどれる参照だけを使い、3組を再判定した。

| 確かめた箇所 | 元の事例の再判定 | 条件を変えた再判定 |
|---|---|---|
| 規定変更の受入 | 旧評価を移しリンクが通った段階では形式だけ合格。元の事例と別の事例から意図した判断を導けるまで受入を保留する | 通知の「受付」を「配達済み」に変えた規定は、リンクが通っても不合格。受付後に端末へ届かない例と端末到達を観測した例を区別できるよう直し、再判定する |
| 自己申告の扱い | モデルが設定を使えると答えても、実行環境で選べる根拠がなければ利用可能と判定しない | 未経験の領域を任せられるという申告には、範囲を絞った成果物と検証を求める。その仕事で確認した範囲までを次の担当選択の根拠にする |
| 統合の許可 | 作業分担スキルの入口から該当節に到達し、隔離だけの許可では統合を止めると判断できた | 許可後に差分や共有先端が変われば影響を調べる。元の検証と許可の有効性を示せた範囲で進む。影響を受ける箇所と有効性を示せない箇所は止めて再判定する |
