# ビルド・起動と自動検証

## 目的と境界

放置後の復旧結果を同じ入口から再確認する。システムのxcode-select設定、利用者の実データ、Cloudflareのデプロイ状態は変更しない。実機の録音再生・無線通話・画面ロック・Bluetooth切替は自動テスト成功と区別する。

共有するXcode / VS Codeの入口とファイル自動同期は [開発環境](開発環境.md) を参照する。全modeで最初に開発設定と文書参照・到達性・デザインHTMLの文書内ID重複・Settings仕様の網羅を検査し、不整合も失敗として記録し、独立した検査を継続する。依存する前段が失敗した段階はblockedとして実行しない。

MacのApp／StoreKit検証、iOS検証、独立音声E2Eは既存の共通run lockで排他する。Mac-only検証はlockを取得するだけでSimulatorを作成・起動しない。Simulatorは[音声E2Eの資源管理](音声E2Eテスト.md#再利用と後片付け)と同じ所有記録を使う。作成前に端末一覧を確認し、不要な停止済み専用端末を削除する。既存互換端末を優先し、実行中や一般用途の端末には触れない。

## 入口

| コマンド | 処理 |
|---|---|
| `scripts/build_and_run.sh` | Xcode標準設定でbuild、通常起動、プロセス確認。利用中の既存アプリを事前停止しない |
| `scripts/build_and_run.sh --logs` | build・通常起動後にAppの統合ログを表示 |
| `scripts/build_and_run.sh --debug` | build後にLLDBで起動 |
| `scripts/validate.sh` | 全段階を実行。失敗を記録し他の独立した段階を継続、全体は非zeroで終了 |
| `scripts/validate.sh headless` | 9 package、native SDPと実SDK loopbackペア、Worker、Swift/Workerペア、scripts。UI・実マイクに依存しない |
| `scripts/validate.sh pair` | クリーンinstall、Worker回帰、実Swift client 2台のHTTP/WS/DO統合 |
| `scripts/validate.sh ios-ui` | 再利用する専用SimulatorのUIのみ。大きな文字・dark・landscape、隔離manifest破損からの復旧操作を含む |
| `scripts/validate.sh packages` | 9 Swift Package単体テストとRTCNativeWebRTCのnative交渉・loopbackテスト |
| `scripts/validate.sh worker` | npm ci、型検査、workerdでHTTP / WebSocketを検証。外部APIはtest側で代替 |
| `scripts/validate.sh macos` | macOS App単体テスト。利用者のgroupを削除するUIテストは実行しない |
| `scripts/validate.sh ios` | 共通の専用SimulatorでApp単体・UIテスト。終了時にshutdownして次回再利用 |
| `python3 scripts/validate_storekit.py --output .validation/storekit-日時` | 専用schemeとローカルStoreKit fixtureで購入・復元・利用権を検証。App Storeへの実購入は行わない |
| `scripts/validate.sh scripts` | 文書検査と開発設定の回帰、WebRTC更新失敗時の旧成果物保持、不正成果物拒否、Cloudflare資格/費用試算 |

CodexのRunアクションは `.codex/environments/environment.toml` から `scripts/build_and_run.sh` を実行する。

### Appテストの対象を選ぶ

`macos`、`ios`、`ios-ui` では、`--only-testing TARGET[/SUITE[/METHOD]]` を繰り返して、同じ実行に複数の対象を指定できる。Macは `RideIntercomTests`、iOSは `RideIntercomTests` と `RideIntercomUITests`、iOSのUIだけを調べる場合は `RideIntercomUITests` を選ぶ。Xcodeでは同じ共有schemeのTest navigatorで対象を選んで実行する。StoreKitは専用schemeを使う。

Swift Testingの関数だけを指定する場合は、`'RideIntercomTests/Suite/function()'` のように括弧を含むXcodeの識別子を引用符で囲む。引数付きの関数は `function(argument:)` のように引数ラベルも含める。XCTestのUI試験は下例のようにメソッド名を指定できる。

```sh
scripts/validate.sh macos --only-testing RideIntercomTests/ContactReplyTests
scripts/validate.sh ios \
  --only-testing RideIntercomTests/ContactBootstrapTests \
  --only-testing RideIntercomUITests/ContactReplyUITests/testStandardGroupReplyCanRetryInSettingsAndConfirmationClearsPending
```

iOSでは選択に含まれる端末と条件を準備する。破損した保存領域の復旧ケースは同じiPhoneの独立実行、広い画面幅のケースはiPadで実行する。入力・出力の48kHz固定は、選択に録音再生のAudio Checkまたは背景通話ライフサイクルのUI試験を含む場合に行う。Watch UIは対象指定のないiOS検証に含む。

結果には、選択した対象と実行したケースの識別子を段階ごとに記録する。指定した対象に実行結果が一つもない場合、指定外のケースが実行された場合、または概要に失敗・skip・実行時警告がある場合は失敗とする。

## 環境と出力

通常の単体・結合・UI・音声E2Eはローカルproviderを使い、実Cloudflareの資格を読み込まない。UI testのAppには`RIDEINTERCOM_LOCAL_TESTING=1`を渡し、保存済み資格とDebug既定資格の流用を防ぐ。実SFU/TURNを使う検証はこの通常入口へ追加せず、単体・結合を含むローカル検証の全成功後に、対象・人数・時間・回数を限定した明示実行とする。[費用制約](../policies/開発方針.md#実サービスを使う検証の費用制約)を適用する。

| 変数・出力 | 内容 |
|---|---|
| `DEVELOPER_DIR` | 既定 `/Applications/Xcode.app/Contents/Developer`。各プロセスへ渡す |

| `results.tsv` / `results.json` | 段階名、passed/failed/blocked/timeout/interrupted、終了コード、所要秒数。JSONはコマンド・理由も保存。全段階passedだけが全体成功 |
| `*-host-preflight.json` | 起動前に検査したxctestrun、期待namespace、hostのInfo.plistパス。Info全体や資格値は出力しない |

| `*-selection.json` | 対象指定時の選択、実行したケース、実行結果のない指定、指定外のケース。`*-tests.log` のxcresult内訳と照合する |

| `ios-recovery.xcresult` | 復旧操作の独立したUI結果。再起動時に同じUUIDの元bytes退避と空manifestを確認 |

Nodeはpackage.jsonの要件（22以上）を満たすこと。macOS入口はこのMacのarm64を対象とする。依存再取得が必要なクリーン環境ではネットワーク接続も必要になる。

## Xcodeテストの起動前検査

App・StoreKitのCLI入口はshared schemeのTestAction構成を読み、標準の`build-for-testing`で生成したxctestrunが参照するAppのInfo.plistを確認する。明示Test Planがあるschemeは、StoreKit設定等の実行条件を維持するため、同じproject・scheme・Test Planを指定して`test-without-building`を実行する。Test Planがないschemeは検査済みのxctestrunを指定する。scheme・platform・構成に合うAppの生成先を参照するxctestrunだけを選び、別platformの新しい残骸を使わない。namespace・compiler条件・entitlementsをCLIから上書きしない。

Appテストと音声E2Eでは、xctestrun内の絶対パス、または先頭が`__TESTROOT__`のパスから、ビルド成果物内のAppを特定する。パスを解決した後にAppとInfo.plistの所在を確認してから隔離された保存先を照合する。成果物ディレクトリ名には連続したアンダースコアも使える。

| 確認 | 失敗時の扱い |
|---|---|
| 実際のhostの保存先 | `StorageNamespace`がXcodeの検証構成で解決された値と完全一致すること。通常版、別構成、欠落、空、未展開の変数、壊れたInfoは起動前に拒否 |
| 実資格の混入 | `DevelopmentInternetConnection`を含むhostは拒否。値は診断へ出さない |
| 参照先 | xctestrunとApp・Infoがそのbuild products内にあること。外部pathやsymlinkによる脱出を拒否 |
| buildを再利用する場合 | 同じxctestrunと生成済みInfoを再確認する。test-without-buildingへ設定引数を足して保存先を変更できたとは扱わない |
| Macの後片付け | 正常終了はXcodeに任せ、path一致によるhost停止は行わない。timeout・中断時は起動時に取得したprocess identityと所有子孫だけを回収する。所有を証明できない既存hostは停止しない |

独立した音声E2Eも同じhost検査を使い、標準検証構成のnamespaceと実際のhostを照合してから起動する。音声測定自体の成功と、この起動前検査の成功は別に記録する。

## 成功判定と異常終了

`--clean`は各packageの標準`swift package clean`を先に実行し、通常のpackage内`.build`でテストする。Swift/WorkerペアもRTC packageの同じ`.build`を使い、package段階でclean済みなら再cleanしない。pair-onlyではRTCを一度cleanしてから実行する。clean失敗時は依存するtest／pairを起動しない。各段階は順に実行し、別のscratch pathや一時buildコピーは作らない。Xcodeは通常どおり既定のDerivedDataを再利用する。OS SDK・グローバル依存cache・インストール済みツールまで消去した環境を意味しない。`--thread-sanitizer`はSwift packageとpairのThread Sanitizerを有効にする。App/UIの検査へ自動拡張しない。

Swift 6.3以上、Node 22以上を明示的に確認する。WebRTCは格納zipのSHA-256とmetadataを照合し、展開したframeworkのplatform/architecture/headerを検査する。更新用depot_toolsや外部の最新版照会は通常検証の前提にしない。

RTC packageは`--no-parallel`を明示する。SwiftPMの既定表示だけではSwift Testingのsuite並列実行を止められない。10分相当のcodec/暗号化を数秒で処理する耐久試験、制御actorを意図的に止める試験、50ms配送・100ms鮮度期限を持つ試験を同時実行しない。期限・欠落・波形の判定は緩めず、8名の同時配送は試験内部で維持する。

Swift/Python/Nodeの終了コードが0でも、実行件数0、失敗、skip、todoは成功としない。RTCのWorkerPairTestsはpackage単体から除き、pair modeでserverを起動して必ず実行する。UIのtestCorruptGroupStoreRecoveryも通常のios-testsから除外し、同じbuildを使うios-recovery stageで必ず実行する。fixtureの準備と確認はtest自身が行う。いずれも未実行のskipとして成功扱いにしない。`VALIDATION_TIMEOUT_SECONDS`は各段階の上限秒（既定1800）。App単体とUIテスト全件を1台のSimulatorで直列に実行する`ios-tests`だけは既定7200（2026-11-17の実測でUIテスト61件が4307秒）で、`VALIDATION_TIMEOUT_SECONDS`を指定すればその値に従う。明示的な準備・展開・Simulator操作はより短い上限を持つ。timeoutや中断では、開始時のPID・UID・起動時刻で親を確認し、停止前に取得した所有子孫を子から順にTERM／KILLで回収する。別session／process groupへ移ったテスト子も対象とし、signal直前に同一性を再確認する。利用者の別ビルドを名前検索で停止しない。回収失敗でも元のtimeout 124／interrupted 130を保持し、理由へ回収失敗を追記する。起動時刻はpsの秒精度であり、停止前snapshot以降に増えた子を常時追跡する仕組みではない。

`inputs-before.json`と`inputs.json`は実行前後のtrackedおよび未ignoreソースのSHA-256。実行中に変更されれば検証結果を失敗にする。ただしBuild後処理による共通`CURRENT_PROJECT_VERSION`の増加だけは許容し、元のSHA-256と番号も残す。他のproject設定・構成の変更、番号の減少や構成間の不一致は許容しない。内容そのものはコピーしない。証跡の`*-build-settings.json`でXcodeが解決した構成と生成先を確認できる。未追跡の秘密ファイルはhash記録対象になるため、資格は所定のignore対象へ置く。

GitHub Actionsのpush・pull_request triggerは使用しない。既存workflowは明示的な手動dispatchのみ残し、この検証では起動しない。mainへのpush前にローカルで必要なmodeを成功させる。サーバー側の強制gateがないため、検証を省略したpushまでは防止できない。

## テストデータの扱い

| 対象 | 方針 |
|---|---|
| Simulator | unit / UI・音声E2E入口は共通の所有journalとlockで専用端末1台を再利用し、終了時はshutdownする。毎回既存端末を棚卸しし、不要な停止済み専用端末を削除する。既存端末をeraseしない |
| UIテスト | 専用Simulator内のTalk Groupを作成・削除する。利用者の端末で直接実行しない |
| App単体のhost起動 | macOSでも標準検証構成のnamespaceでbuildする。host起動時の旧データ移行が利用者の保存先へ到達しない。終了時は当該DerivedDataの実行ファイルpathに一致するhostだけを終了する |
| 保存復旧fixture | compile時に隔離したTestSupportが、現在プロセスの検証アカウント内groups.jsonだけを破損させる。通常namespace・不正mode・symlinkを拒否。UIのreset後に同じUUIDで再起動し、実GroupSnapshotの空groupsとその回の元bytes退避を確認する。外部simctlによるdata container指定は不要 |
| App起動分岐 | 本番Appにテスト専用launch argumentや偽の通信・音声分岐を入れない |
| PCMテスト | AVAudioEngineのoffline render、偽の入出力backend、生成波形をTest Support側だけで使用 |
| 10分相当の検証 | 20ms PCMを各方向3万フレーム生成。Codec・暗号化・RTC受信待ち・重複破棄・復号の数と順序を検証。実時間10分や音響品質を示す結果ではない |
| Worker | Miniflare/workerdをローカル実行。Calls / TURN APIはoutboundServiceで代替。deployはdry-runだけ |

復旧UI試験はXcodeのTestActionとCLIで同じ自己完結したfixtureを使用する。CLIは通常suiteの後に同じbuildで独立実行し、XcodeからはTest navigatorや⌘Uで実行できる。証跡とXcode既定のbuild cacheは保持し、CLIが所有するSimulatorは停止して再利用する。namespaceを通常版へ変更して検証アプリを利用データ上で起動しない。

## 結果の読み方

成功時でもSDK・vendorの警告はログで区別する。Simulatorのオーディオデバイス診断、XcodeのAppIntents metadata診断、WebRTC vendorの非推奨API警告を実機成功や警告ゼロへ読み替えない。復旧時の実績・採用版は [復旧検証記録](../validation/history/復旧検証記録.md)、中継前の履歴は [品質点検](../validation/history/品質点検.md)、現在の混在通話・機器切断と残件は [混在通話検証](../validation/history/混在通話検証.md) を参照する。

## 実音声のE2E

音声発話・通信・受話の試験は[音声E2Eテスト](音声E2Eテスト.md)で独立して実行する。`python3 scripts/audio_e2e.py`が短い検証の入口であり、通常のunit/integration検証へ同じ試験を重複登録しない。

## 近距離媒体だけの遮断と代替経路

RTC packageの`NativeRouteContinuityTests.nativeQUICControlSurvivesMediaBlackholesAndWebRTCRecovers`は、近距離のQUIC認証・制御を保ったまま音声UDPだけをowned loopback proxyで遮断する。片方向／両方向と、最初から／通話途中の4条件を実行する。Internet側は本番のrouteとnative WebRTCエンジンを使い、サーバー側の接続交渉・中継だけを試験内fixtureへ置き換える。外部のApple／Cloudflare資格や、hostのネットワーク設定変更は要らない。

```sh
DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer CI=1 \
  swift test --package-path RideIntercom/packages/RTC --no-parallel --filter NativeRouteContinuityTests
```

XcodeではRTC packageを開き、標準`RTC-Package` schemeから`RTCNativeWebRTCTests`の同じテストを選び、MacまたはiOS SimulatorでTestする。CLIのiOS実行も同じschemeと`-only-testing:RTCNativeWebRTCTests/NativeRouteContinuityTests`を使う。通常のpackage検証にも含まれる。Local部品の`LocalMediaReceiptPathTests`と、試験専用の`RTCTestSupport` targetで同じUDP proxyを共有し、製品productの依存へは加えない。

合格は、到達可能なnative WebRTC経由の新しい音声packetを両端のRouteManagerが受信し、QUICの制御を実配送できること、遮断解除後にLocalを再優先してInternetコピーを省略すること、重複・古い音声の再配送とグループの再開始がないこと、stop後に再配送しないことで判定する。ここでの最終出力は認証・復号後のpacketイベントである。マイク・codecの実出力波形、App UI、実HTTP／WebSocketサービス、実Cloudflare、実Wi-Fi分離、実機ロック中の受入は別に確認する。

## Appleログインのローカル検証

`validate.py`はshared schemeの標準検証構成を使い、その構成で隔離storage namespaceと`RIDEINTERCOM_VALIDATION`条件を設定する。`RideIntercom/TestSupport/AppleAccountFixture.swift`はこの条件かつDebugでのみcompileされ、`RideIntercom.Validation.`名前空間、`RIDEINTERCOM_LOCAL_TESTING=1`、明示した`RIDEINTERCOM_ACCOUNT_FIXTURE=signed-in/signed-out`をすべて満たすときだけ認証providerを置き換える。Xcodeの標準TestActionも同じcompile条件と隔離namespaceを設定する。隔離namespaceの検証Appを試験設定なしで起動した場合は、試験用アカウントを指定して起動する案内を表示する。Apple認証の操作と保存済みの試験用アカウントの読込は閉じる。隔離namespaceを欠くビルドは初期化で拒否する。通常Debug・Release・Archiveでは環境変数だけでログインを迂回できない。

App単体テストは注入したKeychainとcredential stateで認証・失敗・取消・競合を確認し、UIはsigned-inで通話操作、signed-outで初回画面を確認する。音声E2Eもtest bundle側で認証済みのfixtureを明示注入する。復旧fixtureは当該検証アカウントの保存先だけを書き換える。

macOSの隔離検証では専用構成（CLIでも同じ指定）でApple実サービスcapabilityのentitlementsを外し、既存の開発署名を使う。実Apple認証の成功はこの結果に含めず、通常buildのSign in with Apple entitlementとApple側のApp ID・profileを別に確認する。実Cloudflare資格を使わない既存の制限は維持する。

## ローカルStoreKitの標準TestPlan

`RideIntercom-StoreKitTests` schemeのTestActionは`Configuration/StoreKit.xctestplan`を使用する。既存の`LocalPurchases.storekit`とローカルfixtureをplanに指定し、Xcodeからも確認・変更できる。CLIはschemeのdefault plan名と一致する生成xctestrunだけを選び、旧自動生成planやtarget空の定義で成功した扱いにしない。商品取得と取引反映の試験結果は[検証記録](../validation/history/Xcode標準設定への復帰と一時領域の整理.md)で区別する。

## iOSの背景待機とnative音声の局所検証

`python3 scripts/background_call_e2e.py --out .validation/background-call-run`で、隔離したiPhone Simulatorと既存の`BackgroundCallLifecycleUITests`を使う。マイク許可を準備し、Simulatorの入出力を同じ48kHz duplex deviceへ一時固定する。終了時は元の選択へ戻し、所有するSimulatorを停止する。Macのdefault deviceは変更しない。deviceの選定と固定は音声E2Eの共通入口を使う。XcodeのTestからも同じUIテストを実行できるが、SimulatorのAudio Input／Outputは同じ有効なduplex deviceを選び、マイク許可を準備する。

Standard・Advancedそれぞれで相手のいないgroupへ接続し、マイクON／OFFからHomeへ移って35秒待機し、同じ通話の終了まで操作する。音声の準備完了や相手を待つ明示的な待機は置かないが、XCTestのtapは自動でidleを待つため、操作直後の数ms以内のロック競合を証明しない。背景中のnative入力・出力callbackから、入出力と期限を保持しnetwork mediaは未開始であることをJSONへ記録する。マイクOFFでは入力配送を閉じるため、native出力callbackの継続を検査する。観測は隔離した保存先を使うDebug-ValidationのiOSで明示的に有効にし、PCM・相手の名前・鍵は保存しない。Simulatorの模擬中断は実機では有効にならない。

この局所試験は物理iOSの実行停止、双方背景での後参加・通話成立・再接続、無音での長時間継続、実SFUを受け入れるものではない。[製品要求](../requirements/製品要求.md#双方背景と無音状態を組み合わせた受入)を満たす両端の実媒体試験は別に必要となる。

`background_call_e2e.py --scenario resumed`は両画面の相手待ちからResume Audio→Home→背景のnative入力を確認する。`--scenario all`は通常・mute・再開の6条件を実行する。再開試験の前提となる中断は、Debug-Validationの明示したfixtureで最初の実入力後に一度だけmodelへ通知する。OSの実際の中断や背景からの自動再開の受入とは区別する。再開後のactivation、native入出力、media gate、期限、終了は実処理を使い、相手の認証を待つUI操作は加えない。

`--scenario first-permission`は両画面でアプリのマイク許可を初回状態へ戻し、OSの実ダイアログを承認した直後にHomeへ移る。背景中のcallbackはOS許可がgrantedであることも必要とする。`--scenario all`は既存6条件と初回許可2条件の計8条件を実行する。許可待ち・拒否・取消・期限切れ・別の通話への切替は`MicrophoneAuthorizationTests`でも検証する。

## iOS実機の準備とロック中の検証を分ける

実機向けの準備は、通常のproject／scheme／DerivedDataを使い、`xcodebuild build -project RideIntercom.xcodeproj -scheme RideIntercom -configuration Debug-Validation -destination 'platform=iOS,id=<端末UDID>'`で行う。共通の`xcode_build_settings`も同じ明示したplatformから`iphoneos`を選び、Simulatorの設定やplatform不明の結果は拒否する。ビルド・署名・登録端末・`StorageNamespace`の隔離・音声背景modeの確認は、端末の前面表示を維持する操作から独立させる。build自体はインストール・起動や実機の動作確認を意味しない。

開発用インストールと最初の前面起動、初回のOS権限確認は、利用者が解除できる準備段階にまとめる。[Appleが説明するロック中の前面起動の拒否](https://developer.apple.com/forums/thread/732481)を回避するため、ロック解除を繰り返す運用を採用しない。準備後は起動済みAppをロックしたまま観測し、開始待ち・相手参加・切断後の復旧に前面復帰を要求しない。登録用に一度起動しただけのAppや、プロセスの存在だけを通話・背景処理の証拠として扱わない。

背景実行の受入では、debuggerやtest runnerの保持による実行継続と通常のOS条件を区別し、App・相手側・OSの状態と実処理の進行を照合する。`BackgroundCallValidationObservation`はDebug-ValidationのiOSで、`StorageNamespace`が`RideIntercom.Validation.`から始まり、起動時の`RIDEINTERCOM_BACKGROUND_OBSERVATION=1`を指定した場合だけ動作する。Releaseや通常の保存先では動作しない。実機向けの模擬中断は提供しない。

| 観測 | 内容と判定の境界 |
|---|---|
| 実処理 | native入力／出力callbackをAppが受け取った時点と停止時の状態、認証人数、利用可能な経路、受信packetの計数、native出力で最後に有声を検出したApp側時刻を記録する。後参加・復旧後の受話は相手が発話した区間で新しい有声出力を確認する |
| 受信の切り分け | 近距離UDPで音声形式として読み取れたデータグラムの累積件数と診断の取得時刻、RTCの経路・セッションのイベント配送破棄、PCMが出た復号件数と復号失敗を取得する。取得できていない経路・診断は `null`。UTC時刻と各測定の区間を照合し、復号件数やUDP件数が初期化されたところで区間を区切る |
| 出力とApp配送の切り分け | `nativeOutput`には出力グラフごとの一時的な乱数、MainActorへ渡す前の出力callback件数と有声判定したフレームの累積秒数、最終render時刻とrender clock上の最大空白秒数、workerの最終uptimeと最大callback間隔を記録する。render時刻は同じグラフ内で比較する。App側記録の空白と前後の累積値で、出力キャプチャ、worker、App配送の進行を照合する。render clockの空白にはキャプチャ欠落も含まれるため、スピーカーからの聴感は別途確認する。直近と最長のダック切替も記録し、開始uptime・処理秒数・切替先を同じ時間軸で確認する |
| 同じ通話 | 接続処理の世代を表す一時的な乱数と終了期限を照合する。利用可能な経路は制御だけでも現れるため、経路の復帰に続く認証・メディア開始と有声出力まで確認する |
| 実行条件 | platform、build、PID、起動ごとのランダムな識別子、時刻・uptime、背景状態、マイク許可状態、`isProtectedDataAvailable`、自身へのdebugger接続状態、自プロセスのXCTest検出を記録する。debugger照会失敗はunknownとなる。XCTest未検出だけでは外部runnerの不在を証明しないため、起動方法と外部processも照合する |
| 保存 | `tmp/background-call-{standardまたはadvanced}-{open、muted、first-permissionのいずれか}.json`。各source最大1回／秒、最新256件。音声・相手の情報を含めず、[初回解除後はロック中もアクセスできる保護](https://developer.apple.com/documentation/foundation/fileprotectiontype/completeuntilfirstuserauthentication)を各atomic書込に指定する。書込や取得に失敗した場合は証拠不足とする |
| ロック | 背景状態と保護データの可用性をOSの実状態・時刻と照合する。背景移行だけを画面ロックの証拠にしない。ファイル保護属性とロック中の書込は物理iOSで受け入れ、SimulatorのJSON更新成功と分ける |

standaloneの測定は通常のインストール後、`devicectl device process launch`で起動時環境を渡すか、debuggerを無効にしたRunから始める。`--start-stopped`やXCTestからの保持を使わず、接続操作・初回OS許可の後は端末をロックし、前面復帰を待たず観測する。検証用のサインインfixtureは既存の隔離条件で使用できるが、実Apple認証の受入とは分ける。登録用に起動した旧buildの終了・上書きと、測定用の新規起動を混同しない。

`lastNativeAudibleOutputAt`は通話の共有エンジンでダック判定が使う時刻を示す。`lastAudibleOutputAt`はAppに反映済みの有声出力時刻。共有エンジンでは既存通話tickが出力workerから値を読み、`outputCallback` 行を記録する。両時刻と出力workerの計数を送話区間と照合し、出力が続く間のダック解除、App反映の空白、停止した旧グラフの時刻を確認する。

後参加を観測する前に、招待先の試験グループを両端で照合する。今回の名前を過去の試験グループと区別し、検証用の保存領域に相手側と同じグループが記録されたことを確認する。起動コマンドの成功は、招待先が選ばれた証拠に含めない。保存領域を調べる場合は一致したかだけを証跡に残す。

`BackgroundCallLifecycleUITests`の`testExternalGroupInvitation`で始まる3件では、署名済みの合成招待を開いて、招待先の名前・接続待ち・再起動後の一覧を照合する。終了中は`XCUIApplication.open`でURL起動する。表示中と背景中は`XCUIDevice.shared.system.open`でOSにURLを渡し、表示された場合はOSの確認で「開く」を選ぶ。アプリ指定のURL起動は実行中のプロセスを再起動することがあるため、表示中・背景中の試験には使わない。[XCTestのアプリ起動](https://developer.apple.com/documentation/xcuiautomation/xcuiapplication)、[OSによるURLのオープン](https://developer.apple.com/documentation/xcuiautomation/xcuisystem/open(_:))。

記録の回収は次の読取操作を使う。回収ごとに新しい保存先を指定し、転送の成功と最新の記録時刻を確認する。長時間の試験では最新256件を上書きする前に待機・後参加・無音・経路断と受話再開の区間を回収する。ロック中に取得できない場合は端末側の記録を保ち、後の取得まで未取得とする。取得のためにAppを前面へ戻して処理を続けさせない。利用者が見張れない間も、ビルド・修正・Simulatorの自動検証を継続する。

```sh
xcrun devicectl device copy from --device '<端末UDID>' \
  --domain-type appDataContainer \
  --domain-identifier com.yowamushi-inc.RideIntercom.RideIntercom \
  --source tmp/background-call-standard-open.json \
  --destination .validation/physical-background-call.json
```
