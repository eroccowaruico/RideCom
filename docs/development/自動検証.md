# ビルド・起動と自動検証

## 目的と境界

放置後の復旧結果を同じ入口から再確認する。システムのxcode-select設定、利用者の実データ、Cloudflareのデプロイ状態は変更しない。実機の録音再生・無線通話・画面ロック・Bluetooth切替は自動テスト成功と区別する。

共有するXcode / VS Codeの入口とファイル自動同期は [開発環境](開発環境.md) を参照する。全modeで最初に開発設定と文書参照・到達性・デザインHTMLの文書内ID重複・Settings仕様の網羅を検査し、不整合も失敗として記録し、独立した検査を継続する。依存する前段が失敗した段階はblockedとして実行しない。

MacのApp／StoreKit検証、iOS検証、独立音声E2Eは既存の共通run lockで排他する。Mac-only検証はlockを取得するだけでSimulatorを作成・起動しない。Simulatorは[音声E2Eの資源管理](音声E2Eテスト.md#再利用と後片付け)と同じ所有記録を使う。作成前に端末一覧を確認し、不要な停止済み専用端末を削除する。既存互換端末を優先し、実行中や一般用途の端末には触れない。

通常検証、音声E2E、StoreKitのローカル検証は、Gitの追跡ファイルと無視対象に含まれない追加ファイルを同じ処理で列挙し、入力のハッシュを取る。通常検証は全ファイル、音声E2EとStoreKitはXcodeの試験に使う形式とアセットを照合する。StoreKitはローカル購入のfixtureも直接照合する。いずれも実行中の入力変更は検査の失敗とし、プロジェクト全体で共通のビルド番号だけが進む場合は許容する。

## 入口

| コマンド | 処理 |
|---|---|
| `scripts/build_and_run.sh` | Xcode標準設定でbuild、通常起動、プロセス確認。利用中の既存アプリを事前停止しない |
| `scripts/build_and_run.sh --logs` | build・通常起動後にAppの統合ログを表示 |
| `scripts/build_and_run.sh --debug` | build後にLLDBで起動 |
| `scripts/validate.sh` | 全段階を実行。失敗を記録し他の独立した段階を継続、全体は非zeroで終了 |
| `scripts/validate.sh headless` | 11個のSwift Package、native SDPと実SDK loopbackペア、Worker、Swift/Workerペア、scripts。UI・実マイクに依存しない |
| `scripts/validate.sh pair` | クリーンinstall、Worker回帰、実Swift client 2台のHTTP/WS/DO統合 |
| `scripts/validate.sh ios-ui` | 再利用する専用SimulatorのUIのみ。大きな文字・dark・landscape、隔離manifest破損からの復旧操作を含む |
| `scripts/validate.sh watch-ui` | Watch Simulatorだけで検証用WatchのUIを確認する。Watchの共有スキームを使い、iPhone・iPadを起動しない |
| `scripts/validate.sh packages` | 11個のSwift Packageの単体テストとRTCNativeWebRTCのnative交渉・loopbackテスト |
| `scripts/validate.sh worker` | npm ci、TypeScript・JavaScriptのlintとWorkerの型検査、workerdでHTTP / WebSocketを検証。外部APIはtest側で代替 |
| `scripts/validate.sh macos` | macOS App単体テスト。利用者のgroupを削除するUIテストは実行しない |
| `scripts/validate.sh ios` | 共通の専用SimulatorでApp単体・UIテスト。終了時にshutdownして次回再利用 |
| `python3 scripts/validate_storekit.py --output .validation/storekit-日時` | 専用schemeとローカルStoreKit fixtureで購入・復元・利用権を検証。App Storeへの実購入は行わない |
| `scripts/validate.sh scripts` | 文書検査と開発設定の回帰、WebRTC更新失敗時の旧成果物保持、不正な成果物の拒否、Cloudflare資格/費用試算 |

CodexのRunアクションは `.codex/environments/environment.toml` から `scripts/build_and_run.sh` を実行する。

### プログラムのlintと型検査

開発用Macには `brew install swiftlint biome ruff ty shellcheck` でツールを用意する。この構成で確認したツールのバージョンはSwiftLint 0.65.1、Biome 2.6.6、Ruff 0.17.4、ty 0.0.99、ShellCheck 0.11.0。Workerは `npm --prefix server ci` で用意したTypeScriptを使う。lintはソースを書き換えず、必要なツールが欠けた場合は失敗する。

| 対象 | 実行する検査 |
|---|---|
| TypeScript・JavaScript | Biomeの推奨ルールを使い、明示的なany、非null表明、型エラーの抑制、不要な型変換等をエラーにする。Workerには既存のstrict型検査と、二重アサーション・型の複製・中継関数等を拾う構文検査も適用する |
| Swift | SwiftLintの標準規則に強制アンラップ・暗黙アンラップ型・不要な型注釈の検査を加え、警告も失敗として扱う。対象targetの型検査は既存のXcode／Swift Packageビルドで行う |
| Python | Ruffの標準規則にバグの疑い（B）、型注釈（ANN）、不要な抑制（RUF100）の検査を加える。tyは引数・戻り値などの型を検査し、警告も失敗として扱う |
| シェル | ShellCheckでスクリプトのシェルに合わせて引用・変数展開をstyleレベルまで検査する。コマンド置換の失敗や `set -e` が呼出側に隠れる箇所も調べる |

リポジトリのルートで `python3 scripts/lint.py` を実行すると全言語を監査する。Xcodeでは Settings → Behaviors でカスタム動作を作る。Run に `scripts/lint.py` を指定する。Xcode → Behaviors でこの動作を選ぶと全言語を検査できる。Web側だけなら `npm --prefix server run lint` を使う。変更の受入には `python3 scripts/lint.py --base <変更前のコミット>` を使い、変更ファイル全体と未追跡のソースを調べる。標準の検証では `all`・`headless`・`scripts` は全言語、`worker`・`pair` はWeb側を対象とする。`HEAD^` 以降を検査し、結果を `language-lint.log` に残す。設定の変更・削除・移動では、その言語の既存ファイルも再検査する。Workerの型定義を削除・移動したときもWorker全体の型を検査する。

エディタと自動検証はルートの `biome.json`、`.swiftlint.yml`、`pyproject.toml`（Ruff・ty）、`.shellcheckrc` を共有する。個々のファイルを調べるときも同じ規則が適用される。Biomeは `.validation` を探索から外し、検証で作った別のソースや設定を読み込まない。

エラーが残れば終了コードは非ゼロになる。Workerの構文検査が出す `review` は型や中継が役割を持つか呼出元で判断するための候補で、件数だけで削除を決めない。各巡で[責務分離スキル](../../.agents/skills/architecture-refinement/SKILL.md#型と重複の点検)に従って指摘の処置と再検査結果を照合する。

Workerの構文検査では、Durable Objectの宣言元とインストール済みのCloudflare型パッケージを、OSが解決した実パスで照合する。macOSで作業フォルダ名に大文字が含まれても、同じ宣言に対する検査結果は変わらない。

稼働用WorkerでCloudflareの `DurableObjectStorage.onNextSessionRestoreBookmark` を参照すると、`durable-storage-restore` をエラーにする。プロパティ名、型で値が決まる添字、分割代入を検査する。同名の別の型や、復旧時点を調べる読み取りAPIは許容する。[SQLiteの復旧範囲](Cloudflare試用手順.md#sqliteの復旧範囲を確認する)

Cloudflareの `DurableObject` 基底クラスを継承する公開クラスでは、他のオブジェクトや関数に処理を渡す公開RPCメソッドを検査の指摘から外す。基底クラスや従来の `DurableObject` インターフェイスが宣言するイベントハンドラも、実行時の入口として扱う。いずれも継承・実装する型がCloudflareの型宣言に解決されることを確認する。同じオブジェクトのメソッドに処理を渡すRPCの別名、非公開メソッド、静的メソッド、通常のクラスや関数の中継は引き続き検出する。 委譲先のシンボル、呼び出し先を指す式、引数の型と順序が同じ場合は、RPCのメソッド名が異なっていても重複として検出する。 [CloudflareのRPC公開条件](https://developers.cloudflare.com/workers/runtime-apis/rpc/visibility/)

### コミット時の自動リント

新しくクローンしたら、[文書検査と共通のコミット前フック](../policies/文書作成規約.md#日本語の技術文書を検査する)を一度設定する。コミット時に文書と画面の文言を検査し、続いて対象言語のコードと型を検査する。

対象言語のリンターを用意し、Workerの型検査には各worktreeで `npm ci --prefix server` を済ませる。コミット対象の内容は一時ディレクトリで検査するため、同じファイルに未ステージの変更があっても、Gitがコミットに含める内容で判定する。指摘やツール不足で検査が失敗するとコミットは止まる。修正をステージして再度コミットする。コミット前に両方の検査を試すには `git hook run pre-commit` を実行する。コードだけを検査するには `python3 scripts/lint.py --staged` を使う。

### Swift Packageの対象を選ぶ

`packages` で `--package` を指定すると、選んだパッケージの試験だけを実行する。同じ引数を繰り返して複数選べる。たとえばPCMの入出力と発話検出を一緒に調べる。

```sh
scripts/validate.sh packages --package AudioCore --package VADGate
```

各パッケージのXcodeと同じテストターゲットを、標準の `swift test --package-path` で実行する。`--help` に選べる名前を表示する。`RTC` を選ぶと既存のWebRTC成果物を検査する。Workerとつなぐ試験は従来どおり `pair` または `headless` で行う。パッケージを指定しない `packages`、`headless`、`all` は全11個を実行する。

### WorkerとAppをつなぐ試験を選ぶ

Workerの通信や保存を変更したときは、Workerの型検査・回帰に続けて、影響を受けるmacOS Appの試験を選べる。例えばグループ招待では、保存後の再起動や再送、受領側のグループと鍵を確かめる。

```sh
scripts/validate.sh worker --only-testing RideIntercomTests/GroupDeliveryWorkerTests
```

Workerの依存を用意し、ローカルのWorker回帰を先に実行する。App側はXcodeと同じ共有スキームで、選んだ試験の結果を照合する。実サービスへの接続はなく、選択を省いた `worker` はWorkerの検証だけを行う。

`scripts/validate.sh pair` は、合成のApple認証をローカルWorkerで検証し、別々のアカウントの端末資格を得る。TURNを有効にし、Swiftの通信部からICEの準備、2人の入室、制御通信、期限の更新、再参加を確認する。Apple・TURN・SFUの提供元には試験用の応答を使う。実回線のICEと発話の再生は、別に音声試験で確認する。[音声試験](音声E2Eテスト.md#音声機器を使わずにwebrtcの発話を往復させる)

### Workerのテスト定義をケース単位で一覧にする

Workerの依存を準備してから、リポジトリのルートで `node server/test/worker-cases.mjs` を実行する。Node.jsの標準ランナーが使う `server/test/*.test.mjs` から、登録された試験の一覧をJSONで得られる。ファイル、外側のsuiteからケースまでの名前、同じ場所・同じ名前での登録順で識別する。

一覧の作成ではsuiteの登録を読み、試験本体や準備・後片付けのhookを実行しない。suiteの中のケースは同期的に登録する。ファイルやケースの追加・改名・削除は次の一覧に反映される。Node.jsの[同期モジュールフック](https://nodejs.org/api/module.html#moduleregisterhooksoptions)を一覧作成のプロセス内で使う。通常のWorkerの試験は `node:test` で実行する。

一覧の1要素をJSONのまま引数に渡すと、Workerをローカルで準備し、同じ定義を1件だけ実行できる。

```sh
npm --prefix server run --silent test:case -- '<一覧にある1件分のJSON>'
```

結果には実行したケース、合否、所要時間、スキップ理由を含める。失敗時はNodeのアサーション、ファイルと行番号を含む呼出し記録、期待値・実値、関連する出力も確認できる。指定がなくなった場合や、選んだ1件の結果が揃わない場合の終了コードは非ゼロになる。

### XcodeからWorkerのケースを選ぶ

共有スキーム `RideIntercomWorkerTests` とmacOSを選ぶ。スキームをビルドすると、Node側の一覧から対応するテストをケースごとに生成する。追加・改名・削除は次のビルドで反映される。XcodeのTest Navigatorで `WorkerCaseTests` の実行したいケースを選ぶ。結果の `Node test result` 添付で所要時間、失敗の場所、期待値・実値、出力を確認できる。ケースの完全な名前と同名の場合の登録順も添付に残る。

ビルド時にNode.jsのバージョンを検査し、必要な依存とローカルのWorkerを準備する。依存はpackageの定義とlockfileが一致する間は再利用する。Nodeの配置先は実行時に同じものを使う。macOSのシステム上でWorker試験だけを実行し、Appの起動やSimulatorの準備は不要。CLIではXcodeの識別子を列挙して同じケースを選べる。

```sh
xcodebuild -project RideIntercom.xcodeproj -scheme RideIntercomWorkerTests \
  -destination 'platform=macOS,arch=arm64' -enumerate-tests -test-enumeration-format json test
xcodebuild -project RideIntercom.xcodeproj -scheme RideIntercomWorkerTests \
  -destination 'platform=macOS,arch=arm64' '-only-testing:RideIntercomWorkerTests/WorkerCaseTests/<識別子>' test
```

Xcode Cloudで使う際は、同じ共有スキームのTestを選び、ビルド前に条件を満たすNode.jsをPATHへ用意する。クラウドでの実行と結果の表示は確認待ち。

### Appテストの対象を選ぶ

`macos`、`ios`、`ios-ui` では、`--only-testing` を繰り返して、同じ実行に複数の対象を指定できる。Xcodeの識別子に従い、テストターゲット名の後に、必要に応じて外側から順にsuite名とメソッド名を `/` でつなぐ。Macは `RideIntercomTests`、iOSは `RideIntercomTests` と `RideIntercomUITests`、iOSのUIだけを調べる場合は `RideIntercomUITests` を選ぶ。Xcodeでは同じ共有schemeのTest navigatorで対象を選んで実行する。StoreKitは専用schemeを使う。

Swift Testingの関数だけを指定する場合は、下例のように括弧を含むXcodeの識別子を引用符で囲む。引数付きの関数は `function(argument:)` のように引数ラベルも含める。XCTestのUI試験はメソッド名を指定できる。

```sh
scripts/validate.sh macos --only-testing RideIntercomTests/ContactReplyTests
scripts/validate.sh macos \
  --only-testing 'RideIntercomTests/AppTests/RealtimeConversationTests/receiverReportsTheAdjustmentOnlyForThePacketThatMoved()'
scripts/validate.sh ios \
  --only-testing RideIntercomTests/ContactBootstrapTests \
  --only-testing RideIntercomUITests/ContactReplyUITests/testStandardGroupReplyCanRetryInSettingsAndConfirmationClearsPending
```

iOSでは選択に含まれる端末と条件を準備する。破損した保存領域の復旧ケースは同じiPhoneの独立実行、通話の幅が広い場合に限るケースはiPadで実行する。一覧と設定の読みやすい幅は、iPhoneで左右の余白、iPadでサイドバーを避ける配置を確かめるため、同じケースを両方で実行する。入力・出力の48kHz固定は、選択に録音再生のAudio Checkまたは背景通話ライフサイクルのUI試験を含む場合に行う。Watch UIは対象指定のないiOS検証に含む。Watchだけの場合は、Xcodeの `RideIntercomWatch` スキームと同じ試験を `watch-ui` から選べる。

```sh
scripts/validate.sh watch-ui --only-testing RideIntercomWatchUITests/WatchLaunchUITests
```

これは検証用Watchの画面と操作の試験。実機でのロック中の連携は[Watchの運用条件](../spec/App/Watch操作.md)に従う。

検証用Simulatorがまだない場合は、必要な端末をiPhone、iPad、Apple Watchの順に作成する。端末ごとに準備の段階名と記録を変える。対象と同じ種類の停止済みSimulatorがあれば再利用する。

結果には、選択した対象と実行したケースの識別子を段階ごとに記録する。同じケースがsuite指定と個別指定の両方に合う場合、実行結果は一度だけ保存し、両方の指定に実行結果があると判定する。指定した対象に実行結果が1つもない場合、指定外のケースが実行された場合、または概要に失敗・skip・実行時警告がある場合は失敗とする。

## 環境と出力

通常の単体・結合・UI・音声E2Eはローカルproviderを使い、実Cloudflareの資格を読み込まない。UI testのAppには`RIDEINTERCOM_LOCAL_TESTING=1`を渡し、保存済み資格とDebug既定資格の流用を防ぐ。実SFU/TURNを使う検証はこの通常入口へ追加せず、単体・結合を含むローカル検証の全成功後に、対象・人数・時間・回数を限定した明示実行とする。[費用制約](../policies/開発方針.md#実サービスを使う検証の費用制約)を適用する。

| 変数・出力 | 内容 |
|---|---|
| `DEVELOPER_DIR` | 既定 `/Applications/Xcode.app/Contents/Developer`。各プロセスへ渡す |
| `VALIDATION_DIR` | 既定 `.validation/<実行日時>`。各runに新しいパスを使う。results.tsvが既存なら開始前に拒否し証跡を保持 |
| Xcode build出力 | mainの通常作業フォルダのprojectとXcode既定のDerivedDataを使う。生成先は`-showBuildSettings -json`から必要なpathだけを取得し、資格を含み得る全JSONはログ・証跡へ保存しない。CLIで専用DerivedDataや別projectコピーを指定しない |
| `SIMULATOR_RUNTIME` | 省略時は、Xcodeが利用可能と報告し、実行するiPhone・iPadの機種をすべてサポートする最新のiOSランタイム |
| `SIMULATOR_APPEARANCE` | 専用Simulatorの外観。既定 `dark`、`light`も指定可能 |
| `SIMULATOR_DEVICE_TYPE` | 既定 `com.apple.CoreSimulator.SimDeviceType.iPhone-17-Pro`。未導入なら利用可能な型へ明示変更 |
| `environment.log` | HEAD、作業状態、OS、Xcode / Swift / Node / npm |
| `results.tsv` / `results.json` | 段階名、passed/failed/blocked/timeout/interrupted、終了コード、所要秒数。JSONはコマンド・理由も保存。必要な全段階が合格すれば全体成功。音声E2Eでその実行の測定条件に含まれない遅延は`not-applicable`と記録する |
| `*-host-preflight.json` | 起動前に検査したxctestrun、期待namespace、hostのInfo.plistパス。Info全体や資格値は出力しない |
| `*-summary.log` | xcresulttoolのJSON概要。0 tests・failed・skip・runtimeWarnings・testFailures・解析不能を失敗にする。Appと独立音声E2Eは同じ判定関数を使う |
| `*-selection.json` | 対象指定時の選択、実行したケース、実行結果のない指定、指定外のケース。`*-tests.log` のxcresult内訳と照合する |
| `simulator-inventory.json`、`ipad-inventory.json`、`watch-inventory.json` | iPhone・iPad・Apple Watchの準備時に見つかった検証用Simulator。各準備で新規作成した場合は、同じ接頭辞の `*-create.log` に識別子を記録する |
| `*.log` | コマンド出力。Xcodeが報告した `.xcresult` を標準の `Logs/Test` から読み取る。詳細結果とUI添付画像はその結果ファイルに入る |
| `simulator-id.txt` | そのrunで再利用または作成した専用SimulatorのID |
| `RIDEINTERCOM_STORAGE_NAMESPACE` | 通常buildはRideIntercom。`Debug-Validation`／`Release-Validation`は共通のRideIntercom.Validation.Xcode。StoreKitも専用scheme／Test Planの選択で同じDebug-Validationを使う。CLIは構成で解決された値を読み、独自のrun名への上書きはしない |
| `ios-recovery.log` | 復旧操作の独立したUI結果の場所を記録する。再起動時に同じUUIDの元bytes退避と空manifestを確認 |

Node.jsはWorkerと文書検査の`package.json`に指定した範囲（26.13.1以上の26系）を使う。macOS入口はこのMacのarm64を対象とする。依存再取得が必要なクリーン環境ではネットワーク接続も必要になる。

## Xcodeテストの起動前検査

iPhoneの検証では、実際の音声入出力を使う試験を選んだ時点で、Simulatorの入力と出力を同じ音声機器に設定する。TXの閉じた行で動作中の音声分離を確認する試験も含む。音声機器の設定を戻せなければ、`simulator-audio-restore` を失敗として記録する。その場合も、今回借りたSimulatorの停止と回収を試みる。

App・StoreKitのCLI入口はshared schemeのTestAction構成を読む。次に、標準の`build-for-testing`で生成したxctestrunが参照するAppのInfo.plistを確認する。明示Test Planがある場合は、StoreKit設定などの実行条件を維持する。そのために同じproject・scheme・Test Planを指定して`test-without-building`を実行する。Test Planがないschemeは検査済みのxctestrunを指定する。scheme・platform・構成に合うAppの生成先を参照するxctestrunだけを選び、別platformの新しい残骸を使わない。namespace・compiler条件・entitlementsをCLIから上書きしない。

Appテストと音声E2Eでは、xctestrun内の絶対パス、または先頭が`__TESTROOT__`のパスから、ビルド成果物内のAppを特定する。パスを解決した後にAppとInfo.plistの所在を確認してから隔離された保存先を照合する。成果物ディレクトリ名には連続したアンダースコアも使える。

| 確認 | 失敗時の扱い |
|---|---|
| 実際のhostの保存先 | `StorageNamespace`がXcodeの検証構成で解決された値と完全一致すること。通常版、別構成、欠落、空、未展開の変数、壊れたInfoは起動前に拒否 |
| 実資格の混入 | `DevelopmentInternetConnection`を含むhostは拒否。値は診断へ出さない |
| 参照先 | xctestrunとApp・Infoがそのbuild products内にあること。外部pathやsymlinkによる脱出を拒否 |
| buildを再利用する場合 | 同じxctestrunと生成済みInfoを再確認する。test-without-buildingへ設定引数を足して保存先を変更できたとは扱わない |
| Macの後片付け | 正常終了はXcodeに任せ、path一致によるhost停止は行わない。timeout・中断時は起動時に取得したprocess identityと所有子孫だけを回収する。所有を証明できない既存hostは停止しない |

独立した音声E2Eも同じhost検査を使い、標準検証構成のnamespaceと実際のhostを照合してから起動する。音声測定自体の成功と、この起動前検査の成功は別に記録する。

## 成功判定と異常終了

Nodeの試験結果には、件数、合格、失敗、skip、取消、todoの集計を各1回必要とする。途中までの出力や、同じ集計項目が複数回現れる結果は失敗とする。

`--clean`は各packageの標準`swift package clean`を先に実行し、通常のpackage内`.build`でテストする。Swift/WorkerペアもRTC packageの同じ`.build`を使い、package段階でclean済みなら再cleanしない。pair-onlyではRTCを一度cleanしてから実行する。clean失敗時は依存するtest／pairを起動しない。各段階は順に実行し、別のscratch pathや一時buildコピーは作らない。Xcodeは通常どおり既定のDerivedDataを再利用する。OS SDK・グローバル依存cache・インストール済みツールまで消去した環境を意味しない。`--thread-sanitizer`はSwift packageとpairのThread Sanitizerを有効にする。App/UIの検査へ自動拡張しない。

Swift 6.3以上を確認する。ローカルのWorker検証と文書検査には、Node.js 26系の正式版で26.13.1以上を使う。両方の `package.json` が同じ範囲を指定し、実行中のNode.jsがその範囲に入ることを事前に確認する。条件に合わなければ、文書検査とWorkerの依存パッケージのインストールを実行せず、検証は失敗とする。[Node.jsのサポート期間](https://nodejs.org/en/about/previous-releases) [26.13.1のセキュリティ修正](https://nodejs.org/en/blog/vulnerability/november-2026-security-releases)

macOSのAppとローカルWorkerの結合試験でも、起動前にNode.jsのバージョンを同じ条件で確かめる。CLIの自動検証は、Xcodeの `TEST_RUNNER_PATH` を使ってCLIの `PATH` をmacOSのテストプロセスへ引き継ぐ。個別に `TEST_RUNNER_PATH` を指定した場合はその値を使う。結合試験はテストプロセスの `PATH` を優先し、Homebrewなどの標準的なインストール先はその後に探す。Xcodeから試験を選んで実行するときも、選ばれたNode.jsが条件に合わなければ、ローカルWorkerの起動前に失敗する。

WebRTCは格納zipのSHA-256とmetadataを照合し、展開したframeworkのplatform/architecture/headerを検査する。更新用depot_toolsや外部の最新版照会は通常検証の前提にしない。

RTC packageは`--no-parallel`を明示する。SwiftPMの既定表示だけではSwift Testingのsuite並列実行を止められない。10分相当のcodec/暗号化を数秒で処理する耐久試験、制御actorを意図的に止める試験、50ms転送・100ms鮮度期限を持つ試験を同時実行しない。期限・欠落・波形の判定は緩めず、8名の同時転送は試験内部で維持する。

Swift/Python/Nodeの終了コードが0でも、実行件数0、失敗、skip、todoは成功としない。RTCのWorkerPairTestsはpackage単体から除き、pair modeでserverを起動して必ず実行する。UIのtestCorruptGroupStoreRecoveryも通常のios-testsから除外し、同じbuildを使うios-recovery stageで必ず実行する。fixtureの準備と確認はtest自身が行う。いずれも未実行のskipとして成功扱いにしない。`VALIDATION_TIMEOUT_SECONDS`は各段階の上限秒（既定1800）。iPhoneでUIテスト全件を含む`ios-tests`の既定は7200（2026-11-17の実測でUIテスト61件が4307秒）。`--only-testing RideIntercomUITests`で全件を指定した場合も同じ上限を使う。クラスやメソッドだけを選ぶ場合は既定1800。`VALIDATION_TIMEOUT_SECONDS`を指定すればその値に従う。明示的な準備・展開・Simulator操作はより短い上限を持つ。timeoutや中断では、開始時のPID・UID・起動時刻で親を確認し、停止前に取得した所有子孫を子から順にTERM／KILLで回収する。別session／process groupへ移ったテスト子も対象とし、signal直前に同一性を再確認する。利用者の別ビルドを名前検索で停止しない。回収失敗でも元のtimeout 124／interrupted 130を保持し、理由へ回収失敗を追記する。起動時刻はpsの秒精度であり、停止前snapshot以降に増えた子を常時追跡する仕組みではない。

`inputs-before.json`と`inputs.json`は実行前後のtrackedおよび未ignoreソースのSHA-256。実行中に変更されれば検証結果を失敗にする。ただしBuild後処理による共通`CURRENT_PROJECT_VERSION`の増加だけは許容し、元のSHA-256と番号も残す。他のproject設定・構成の変更、番号の減少や構成間の不一致は許容しない。内容そのものはコピーしない。証跡の`*-build-settings.json`でXcodeが解決した構成と生成先を確認できる。未追跡の秘密ファイルはhash記録対象になるため、資格は所定のignore対象へ置く。

`scripts/validate.sh` は、実行前、コマンド段階の開始と終了、15秒を超えるコマンドの待機中、全段階の終了時に、ホストMacと当該コマンドが借りたSimulatorのクラッシュレポートを確認する。`crash-reports.json` に、観測期間・各コマンド段階の時刻、取得できた保存場所、新規イベントを最大32件記録する。対象はRideIntercom本体と関連target、Xcode・Simulator・試験の関連プロセス、SpringBoard、PosterBoard、dtdeviceinfod。既存のレポートを除く際はレポート内の時刻を使い、作成が遅れたレポートも発生時刻に該当する段階へ対応付ける。対応する段階がなければ `stage` は `null`。Macに保存されたレポートでも `launchd_sim` 由来の場合はSimulatorとして記録する。

レポートの実ファイル・スタック・利用者名はコピーせず、プロセス名・バージョン・時刻・例外・シグナル・終了理由の分類だけを記録する。保存場所が読めない場合、レポートが解析できない場合、記録上限に達した場合はそれぞれ結果に示す。空のイベント一覧は、取得できた対象と観測期間の範囲を表す。段階との同時発生は因果や所有の確定を意味しないため、テストの終了コードと照合して調査する。

GitHub Actionsの文書検査の起動条件は、手動の `workflow_dispatch` だけとする。公式のcheckoutとsetup-nodeをコミットIDで固定し、リポジトリの読み取り権限で実行する。setup-nodeは `tools/doc-lint/package.json` の範囲内で最新の正式版を選ぶ。依存パッケージを入れる前にローカルと同じ手順でバージョンを検査する。サーバー側で自動的に強制する検査はなく、各担当者がmainへのpush前にローカルで必要なmodeを成功させる。

## 近距離媒体だけの遮断と代替経路

RTC packageの`NativeRouteContinuityTests.nativeQUICControlSurvivesMediaBlackholesAndWebRTCRecovers`は、近距離のQUIC認証・制御を保ったまま音声UDPだけをowned loopback proxyで遮断する。片方向／両方向と、最初から／通話途中の4条件を実行する。Internet側は本番のrouteとnative WebRTCエンジンを使い、サーバー側の接続交渉・中継だけを試験内fixtureへ置き換える。外部のApple／Cloudflare資格や、hostのネットワーク設定変更は要らない。

```sh
DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer CI=1 \
  swift test --package-path RideIntercom/packages/RTC --no-parallel --filter NativeRouteContinuityTests
```

XcodeではRTC packageを開き、標準`RTC-Package` schemeから`RTCNativeWebRTCTests`の同じテストを選び、MacまたはiOS SimulatorでTestする。CLIのiOS実行も同じschemeと`-only-testing:RTCNativeWebRTCTests/NativeRouteContinuityTests`を使う。通常のpackage検証にも含まれる。Local部品の`LocalMediaReceiptPathTests`と、試験専用の`RTCTestSupport` targetで同じUDP proxyを共有し、製品productの依存へは加えない。

合格には次の条件をすべて満たす必要がある。

- 両端のRouteManagerが、到達可能なnative WebRTC経由で新しい音声packetを受信する。
- QUICの制御を実際に届けられる。
- 遮断解除後にLocalを再び優先し、Internetへのコピーを省略する。
- 重複した音声や古い音声を再送しない。グループを再開始しない。
- stop後に再送しない。

ここでの最終出力は認証・復号後のpacketイベントである。マイク・codecの実出力波形、App UI、実HTTP／WebSocketサービス、実Cloudflare、実Wi-Fi分離、実機ロック中の受入は別に確認する。

## Appleログインのローカル検証

`validate.py`はshared schemeの標準検証構成を使い、その構成で隔離storage namespaceと`RIDEINTERCOM_VALIDATION`条件を設定する。`RideIntercom/TestSupport/AppleAccountFixture.swift`はこの条件かつDebugでのみcompileされ、`RideIntercom.Validation.`名前空間、`RIDEINTERCOM_LOCAL_TESTING=1`、明示した`RIDEINTERCOM_ACCOUNT_FIXTURE`をすべて満たすときだけ認証providerを切り替える。`signed-in`は試験用ログインを保存し、`signed-out`はサインアウトする。`restored-offline`は既に保存した試験用ログインを新しいプロセスで読み直し、資格照会が圏外エラーを返す。Xcodeの標準TestActionも同じcompile条件と隔離namespaceを設定する。隔離namespaceの検証Appを試験設定なしで起動した場合は、試験用アカウントを指定して起動する案内を表示する。Apple認証の操作と保存済みの試験用アカウントの読込は閉じる。隔離namespaceを欠くビルドは初期化で拒否する。通常Debug・Release・Archiveでは環境変数だけでログインを迂回できない。

保存済みグループからの圏外再起動を確認するときは、共有`RideIntercom`のTestで`RideIntercomUITests/BackgroundCallLifecycleUITests/testSavedGroupStartsLocalAfterColdOfflineLaunch`を選ぶ。CLIの`validate.sh ios-ui --only-testing`で同じ識別子を指定できる。招待から保存し、近距離を有効・Internetを無効にして終了する。再起動で同じ設定とグループを読み直し、一覧からの選択で待機し、明示終了できるかを確認する。[近距離オフライン通信の結果](../validation/history/近距離オフライン通信.md#圏外でアプリを再起動して一覧から通話を始める)

App単体テストは注入したKeychainとcredential stateで認証・失敗・取消・競合を確認し、UIはsigned-inで通話操作、signed-outで初回画面を確認する。音声E2Eもtest bundle側で認証済みのfixtureを明示注入する。復旧fixtureは当該検証アカウントの保存先だけを書き換える。

macOSの隔離検証では専用構成（CLIでも同じ指定）でApple実サービスcapabilityのentitlementsを外し、既存の開発署名を使う。実Apple認証の成功はこの結果に含めず、通常buildのSign in with Apple entitlementとApple側のApp ID・profileを別に確認する。実Cloudflare資格を使わない既存の制限は維持する。

## iOSの背景待機とnative音声の局所検証

隔離したiPhone Simulatorで既存の`BackgroundCallLifecycleUITests`を使う。次のコマンドで開始する。

```sh
python3 scripts/background_call_e2e.py --out .validation/background-call-run
```

スクリプトはその実行の中でテスト用のAppをビルドする。開始時と終了時の入力を通常の自動検証と同じ処理で照合する。共通のビルド番号が進む場合を除き、入力が変わった実行は失敗とする。

スクリプトはマイク許可を準備し、Simulatorの入出力を同じ48kHz duplex deviceへ一時固定する。終了時は元の選択へ戻し、所有するSimulatorを停止する。Macのdefault deviceは変更しない。deviceの選定と固定は音声E2Eの共通入口を使う。XcodeのTestで個別実行するときは、SimulatorのAudio Input／Outputに同じ有効なduplex deviceを選ぶ。初回許可の試験を除き、マイクを許可しておく。CLIの標準入口でも同じ試験を選べる。

```sh
scripts/validate.sh ios-ui --only-testing RideIntercomUITests/BackgroundCallLifecycleUITests/testStandardMutedWaitingKeepsAudioInBackground
```

Standard・Advancedそれぞれで相手のいないgroupへ接続し、マイクON／OFFからHomeへ移って35秒待機し、同じ通話の終了まで操作する。音声の準備完了や相手を待つ明示的な待機は置かないが、XCTestのtapは自動でidleを待つため、操作直後の数ms以内のロック競合を証明しない。UIテストは背景中のnative callbackの観測が20件以上、観測区間が29秒以上、隣り合う観測の間隔が2.5秒以下であることを確かめる。その間に同じ通話が続き、切断期限を過ぎず、音声入出力、マイク状態・許可が保たれることを確認する。相手の認証・音声受信・network media開始があれば失敗とする。マイクONは入力、OFFは無音のnative出力を検査する。観測は隔離した保存先を使うDebug-ValidationのiOSで明示的に有効にし、PCM・相手の名前・鍵は保存しない。スクリプトはXcodeの試験結果を使い、各条件の観測JSONを保存する。Simulatorの模擬中断は実機では有効にならない。

この局所試験は物理iOSの実行停止、双方背景での後参加・通話成立・再接続、無音での長時間継続、実SFUを受け入れるものではない。[製品要求](../requirements/製品要求.md#双方背景と無音状態を組み合わせた受入)を満たす両端の実媒体試験は別に必要となる。

Appの `UserCallAudioPreparationTests` は、近距離・Internetそれぞれの設定で、マイクOFFの待機から後参加した相手の音声を受け、一時断の後にも新しい音声を出力に渡すことを確認する。通話先と期限を保ち、マイクの音声を送信しないことも確かめる。通信の認証と断線を試験用の処理で発生させ、音声はAppの受信処理から出力予約までを使う。macOSとiOSで `--only-testing RideIntercomTests/UserCallAudioPreparationTests` を指定できる。

`background_call_e2e.py --scenario resumed`は両画面の相手待ちからResume Audio→Home→背景のnative入力を確認する。再開試験の前提となる中断は、Debug-Validationの明示したfixtureで最初の実入力後に一度だけmodelへ通知する。OSの実際の中断や背景からの自動再開の受入とは区別する。再開後のactivation、native入出力、media gate、期限、終了は実処理を使い、相手の認証を待つUI操作は加えない。

`--scenario first-permission`は両画面でアプリのマイク許可を初回状態へ戻し、OSの実ダイアログを承認した直後にHomeへ移る。背景中のcallbackはOS許可がgrantedであることも必要とする。`--scenario all`は既存6条件と初回許可2条件の計8条件を実行する。許可待ち・拒否・取消・期限切れ・別の通話への切替は`MicrophoneAuthorizationTests`でも検証する。

## iOS実機の準備とロック中の検証を分ける

実機の準備には通常のproject、scheme、DerivedDataを使う。既定は通常の保存先で本番相当の動作を確かめる。起動済みのTestFlightを使える場合はそのまま使う。開発署名のAppを使う場合は、対象端末のUDIDを指定して通常のReleaseをビルドする。

```sh
xcodebuild build -project RideIntercom.xcodeproj -scheme RideIntercom -configuration Release -destination 'platform=iOS,id=<端末UDID>'
```

通常のReleaseは保存先 `RideIntercom` と本番Workerを使う。上書き前にBundle IDと署名のアプリ識別子、Keychainの利用範囲を照合する。配布署名や利用権など、TestFlightでのみ成立する条件は実際のTestFlightで確かめる。

合成アカウント、試験用の保存データ、専用の背景観測を使うときに限り、対象端末を指定して明示的にDebug-Validationを選ぶ。

```sh
xcodebuild build -project RideIntercom.xcodeproj -scheme RideIntercom -configuration Debug-Validation -destination 'platform=iOS,id=<端末UDID>'
```

共通の`xcode_build_settings`も同じ明示したplatformから`iphoneos`を選び、Simulatorの設定やplatform不明の結果は拒否する。ビルド・署名・登録端末・`StorageNamespace`・音声背景modeは、端末の前面表示を維持せずに照合する。build自体はインストール・起動や実機の動作確認を意味しない。

[実機試験の受入条件](../requirements/製品要求.md#実機試験の受入条件)に従い、依頼者の操作はロック解除だけとし、その時間を含めた在席を合計2分以内に収める。担当者は、使うビルドと接続先を照合し、相手側を待機させる。今回専用のグループや招待、計測と回収もあらかじめ用意する。必要な許可と認証を済ませた端末を使い、起動と試験開始は担当者側で行う。後参加・経路断と復旧・受話の判定は、端末が再びロックされてから行う。

開発用インストール、最初の前面起動、初回のOS権限確認は、[ロック解除だけで進められるように担当者が事前に準備する](../policies/開発方針.md#実機試験をいつでも始められるようにする)。[Appleが説明するロック中の前面起動の拒否](https://developer.apple.com/forums/thread/732481)が起きる条件も事前に照合する。準備後は起動済みAppをロックしたまま観測し、開始待ち・相手参加・切断後の復旧に前面復帰を要求しない。登録用に一度起動しただけのAppや、プロセスの存在だけを通話・背景処理の証拠として扱わない。

背景実行の受入では、debuggerやtest runnerの保持による実行継続と通常のOS条件を区別し、App・相手側・OSの状態と実処理の進行を照合する。`BackgroundCallValidationObservation`はDebug-ValidationのiOSで、`StorageNamespace`が`RideIntercom.Validation.`から始まり、起動時の`RIDEINTERCOM_BACKGROUND_OBSERVATION=1`を指定した場合だけ動作する。Releaseや通常の保存先では動作しない。実機向けの模擬中断は提供しない。

| 観測 | 内容と判定の境界 |
|---|---|
| 実処理 | native入力／出力callbackをAppが受け取った時点と停止時の状態、認証人数、利用可能な経路、受信packetの計数、native出力で最後に有声を検出したApp側時刻を記録する。後参加・復旧後の受話は相手が発話した区間で新しい有声出力を確認する |
| 受信の切り分け | 近距離UDPで音声形式として読み取れたデータグラムの累積件数と診断の取得時刻、RTCの経路・セッションのイベントの受け渡し破棄、PCMが出た復号件数と復号失敗を取得する。取得できていない経路・診断は `null`。UTC時刻と各測定の区間を照合し、復号件数やUDP件数が初期化されたところで区間を区切る |
| 出力とApp転送の切り分け | `nativeOutput`には出力グラフごとの一時的な乱数を記録する。MainActorへ渡す前に、出力callbackの件数と、有声と判定したフレームの累積秒数を記録する。最終render時刻、render clock上の最大空白秒数、workerの最終uptimeと最大callback間隔も記録する。render時刻は同じグラフ内で比較する。App側記録の空白と前後の累積値で、出力キャプチャ、worker、App転送の進行を照合する。render clockの空白にはキャプチャ欠落も含まれるため、スピーカーからの聴感は別途確認する。直近と最長のダック切替も記録し、開始uptime・処理秒数・切替先を同じ時間軸で確認する |
| 同じ通話 | 接続処理の世代を表す一時的な乱数と終了期限を照合する。利用可能な経路は制御だけでも現れるため、経路の復帰に続く認証・メディア開始と有声出力まで確認する |
| 実行条件 | platform、build、PID、起動ごとのランダムな識別子、時刻・uptime、背景状態、マイク許可状態、`isProtectedDataAvailable`、自身へのdebugger接続状態、自プロセスのXCTest検出を記録する。debugger照会失敗はunknownとなる。XCTest未検出だけでは外部runnerの不在を証明しないため、起動方法と外部processも照合する |
| 保存 | `tmp/background-call-{standardまたはadvanced}-{open、muted、first-permissionのいずれか}.json`。各source最大1回／秒、最新256件。音声・相手の情報を含めず、[初回解除後はロック中もアクセスできる保護](https://developer.apple.com/documentation/foundation/fileprotectiontype/completeuntilfirstuserauthentication)を各atomic書込に指定する。書込や取得に失敗した場合は証拠不足とする |
| ロック | 背景状態と保護データの可用性をOSの実状態・時刻と照合する。背景移行だけを画面ロックの証拠にしない。ファイル保護属性とロック中の書込は物理iOSで受け入れ、SimulatorのJSON更新成功と分ける |

standaloneの測定は通常のインストール後、`devicectl device process launch`で起動時環境を渡すか、debuggerを無効にしたRunから始める。`--start-stopped`やXCTestからの保持を使わず、接続操作・初回OS許可の後は端末をロックし、前面復帰を待たず観測する。検証用のサインインfixtureは既存の隔離条件で使用できるが、実Apple認証の受入とは分ける。登録用に起動した旧buildの終了・上書きと、測定用の新規起動を混同しない。

`lastNativeAudibleOutputAt`は通話の共有エンジンでダック判定が使う時刻を示す。`lastAudibleOutputAt`はAppに反映済みの有声出力時刻。共有エンジンでは既存通話tickが出力workerから値を読み、`outputCallback` 行を記録する。両時刻と出力workerの計数を送話区間と照合し、出力が続く間のダック解除、App反映の空白、停止した旧グラフの時刻を確認する。

### 試験用グループをマイクOFFで自動開始する

Debug-Validationの実機では、送話側を先に用意して試験用グループの署名済み招待を発行する。受話側の起動時に既存の観測設定と招待を渡す。招待はアクセスを制限した試験用ファイルから読み、端末やシェルのログには出さない。

```sh
DEVICECTL_CHILD_RIDEINTERCOM_LOCAL_TESTING=1 \
DEVICECTL_CHILD_RIDEINTERCOM_ACCOUNT_FIXTURE=signed-in \
DEVICECTL_CHILD_RIDEINTERCOM_BACKGROUND_OBSERVATION=1 \
DEVICECTL_CHILD_RIDEINTERCOM_BACKGROUND_MUTED=1 \
DEVICECTL_CHILD_RIDEINTERCOM_BACKGROUND_GROUP_INVITATION="$(cat "$TRIAL_INVITATION_FILE")" \
xcrun devicectl device process launch --device "$DEVICE_ID" com.yowamushi-inc.RideIntercom.RideIntercom
```

通常のミュート処理でマイクをOFFにしてから、グループ招待を受ける。画面操作は不要。今回のプロセスの `tmp/background-call-startup.json` で `startedMuted` を確認してから後参加を始める。相手が来るまでは受信0、その後は新しい有声出力があることを確認する。この自動開始は、起動時に試験条件を指定したDebug-Validationに限る。

後参加を観測する前に、招待先の試験グループを両端で照合する。今回の名前を過去の試験グループと区別し、検証用の保存領域に相手側と同じグループが記録されたことを確認する。起動コマンドの成功は、招待先が選ばれた証拠に含めない。保存領域を調べる場合は一致したかだけを証跡に残す。

`BackgroundCallLifecycleUITests`の`testExternalGroupInvitation`で始まる3件では、署名済みの合成招待を開いて、招待先の名前・接続待ち・再起動後の一覧を照合する。終了中は`XCUIApplication.open`でURL起動する。表示中と背景中は`XCUIDevice.shared.system.open`でOSにURLを渡し、表示された場合はOSの確認で「開く」を選ぶ。アプリ指定のURL起動は実行中のプロセスを再起動することがあるため、表示中・背景中の試験には使わない。[XCTestのアプリ起動](https://developer.apple.com/documentation/xcuiautomation/xcuiapplication)、[OSによるURLのオープン](https://developer.apple.com/documentation/xcuiautomation/xcuisystem/open(_:))。

記録の回収は次の読取操作を使う。回収ごとに新しい保存先を指定し、転送の成功と最新の記録時刻を確認する。長時間の試験では最新256件を上書きする前に待機・後参加・無音・経路断と受話再開の区間を回収する。ロック中に取得できない場合は端末側の記録を保ち、後の取得まで未取得とする。取得のためにAppを前面へ戻して処理を続けさせない。利用者が見張れない間も、ビルド・修正・Simulatorの自動検証を継続する。

```sh
xcrun devicectl device copy from --device '<端末UDID>' \
  --domain-type appDataContainer \
  --domain-identifier com.yowamushi-inc.RideIntercom.RideIntercom \
  --source tmp/background-call-standard-open.json \
  --destination .validation/physical-background-call.json
```

### インストール済みのTestFlight版で試験招待を開く準備

既存のTestFlight版と保存先を使う場合は、iPhone向けに共有 `RideIntercom` スキームの `build-for-testing` で署名済みの `RideIntercomUITests-Runner.app` を用意する。通常生成されたiPhoneOS用 `.xctestrun` から、`scripts/prepare_installed_call_trial.py` で `UseDestinationArtifacts` と `testStartInvitedTrialGroupMuted` を指定した試験定義を作る。端末上の既存アプリを、起動引数の指定と画面の自動添付を無効にした試験定義で使う。実行は、試験ランナーが導入されたiPhoneを宛先とする `xcodebuild test-without-building -xctestrun` を使う。テスト結果はXcodeの標準保存先に残す。

解除を頼む前に、Xcodeの実行先から選んだ端末の状態を次のコマンドで確認する。

```sh
python3 scripts/prepare_installed_call_trial.py --check-device '<端末識別子>'
```

出力は本体とランナーの有無、本体のビルド番号、ロック状態に絞る。導入状況かロック状態を読み取れなければ終了コードは `2`。両方の状態を読み取れた場合、本体かランナーの片方でも見つからなければ `1`、どちらもあれば `0` になる。既存版とランナーがある場合は、すでに使える接続を優先する。ランナーが未導入の場合は、署名済みランナーの導入と初回起動を予定に含め、本体の既存版を使う。相手側の準備、招待、計測、本体やランナーの起動可否は別に確認する。

試験ごとのUUIDを決め、送話側に `RideCom Trial ` と大文字のUUID先頭8文字を連結した新しい試験グループと短期の署名済み招待を用意する。そのUUIDを試験定義の生成に渡す。試験ランナーの `RIDE_INSTALLED_INVITE_READY` の後、担当側から標準の招待経路で招待を渡す。進行中の通話があれば試験を止める。端末で使っているStandardまたはAdvancedのまま通話を開く。開いた通話名が今回の名前と一致した場合に限り、その画面のマイクをミュートして状態を確かめる。`RIDE_INSTALLED_GROUP_CALL_MUTED` を確認するまで相手側は通話に参加しない。招待の値をランナーの環境や結果へ渡さない。

Simulatorでは `testStartInvitedTrialGroupMuted` と `testStartInvitedTrialGroupMutedInAdvanced` で、合成招待をOS経由で開くところから通話とマイクOFFまでを両画面で予行できる。iPhoneOS向けの試験定義で、実際に既存版へ招待が届くこと、ランナー終了後も通話が続くこと、後参加と受話、終了後の片付けまでの一連の動きは[実機確認待ち](../validation/実機確認待ち.md#最新の残件に対する準備状況)で追う。
